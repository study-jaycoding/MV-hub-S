# 기능 작업실과 통합 시험실

Claude·Codex가 같은 방식으로 작업 위치를 정하기 위한 기준이다. 역할·모델·독립 리뷰는
[AGENT_WORKFLOW](AGENT_WORKFLOW.md), 안전·병합·배포 권한은 [AGENTS](../AGENTS.md)와
[CLAUDE](../CLAUDE.md)를 따른다. 이 문서는 기존에 합의한 작업실 운영을 dev 지침에 반영한다.

## 요청을 받았을 때

1. 저장소 루트·브랜치·Git 상태와 [CURRENT_STATUS](CURRENT_STATUS.md)의 관련 작업 기록을
   확인한다. 기존 worktree 목록과 해당 작업 기록의 담당자·`touched_paths`를 대조한다.
2. “편집 탭을 고쳐줘”처럼 기능만 지정해도 해당 기능의 기존 작업실부터 찾는다. 같은 작업의
   작업실을 담당 범위 안에서 재사용하고, 없으면 승인된 작업 범위 안에서 새 기능 작업실을
   만든다. 다른 담당자가 작업 중이면 임의로 인계받거나 같은 경로를 동시에 수정하지 않는다.
3. 새 작업실은 확인한 dev 기준 커밋에서 분리한다. 기존 기능 브랜치를 이어야 하면 그 이유와
   기준 커밋을 기록한다. Git의 원격 기본 브랜치가 main이라는 이유만으로 main에서 시작하지 않는다.
   기존 dev의 미커밋 변경을 일괄 복사하거나 몰래 커밋하지 않는다.
4. 담당 폴더·브랜치·수정 경로·검증 화면을 짧게 알린 뒤 작업한다. 편집 개선은 편집 관련
   경로가 기본 범위다. 공통 코드 변경이 필요하면 영향과 다른 작업의 소유권을 먼저 확인한다.
5. 기존에 진행 중인 dev 작업은 그대로 이어간다. 새 규칙을 적용하려고 기존 세션·프로세스를
   중단하거나 작업을 다른 폴더로 옮기지 않는다. 작은 문서·문구 수정은 충돌 없는 현재 폴더에서
   처리할 수 있으며, 읽기 전용 리뷰마다 새 작업실을 만들 필요는 없다.

작업실별 기록에 담당자·관련 경로·기준 커밋·상태·확인 주소를 남긴다. 다른 담당자와 경로가
겹치거나 기록만으로 소유권을 확인할 수 없으면 해당 변경을 멈추고 충돌 범위를 보고한다.
문서 갱신은 실행 중인 세션에 지침을 강제로 다시 읽히거나 폴더를 자동 전환하는 기능이 아니다.
기존 세션은 다음 작업 전 최신 프로젝트 지침과 이 문서를 다시 읽는다. 기존 작업실의 지침은
별도 사본이므로 dev 문서 변경이 자동 전파되었다고 가정하지 말고 차이를 먼저 확인한다.

## 구현과 사용자 확인

`dev 기준 → 기능 작업실 → 선택한 변경을 담은 통합 시험실 → 검증된 변경의 dev 반영`

- 기능 작업실마다 소스·브랜치·포트·시험 데이터·브라우저 프로필을 분리한다. 기존 dev와
  다른 작업실의 프로세스·DB·계정 설정·전역 MCP 설정은 변경하지 않는다.
- 프런트 수정은 해당 작업실의 개발 화면에 반영된다. 통합 화면은 선택한 버전을 가져올 때
  갱신된다. 기능 작업실 여러 곳의 편집이 통합 화면에 자동으로 동시에 반영되지는 않는다.
- 백엔드는 해당 작업실만 수동 재시작한다. `uvicorn --reload`는 사용하지 않는다.
- 통합 담당자가 대상 커밋과 필요한 변경만 선택한다. 진행 중인 폴더 전체를 동기화하지 않는다.
  탐색용 사본도 기준 SHA·패치·허용한 미추적 파일 해시로 고정하고 검증 결과와 연결한다.
- dev에 정식 반영할 때는 검증한 커밋을 사용한다. 통합 시험 통과만으로 dev/main 병합이나
  배포를 자동 실행하지 않는다. 사용자 승인 범위와 기존 Gate를 적용한다.
- DB 사본과 과거 미디어는 서로 다른 준비 항목이다. 자료가 안 보인다고 원본 DB를 초기화하거나
  운영 폴더를 통째로 덮지 않는다. 필요한 자료만 검증된 준비 절차로 사본에 추가한다.
- 시험실의 실행 차단 장치는 OS 샌드박스가 아니다. 실제 유료 생성·운영 서버 쓰기·전역 설정
  변경은 기존 안전선에 따라 제한한다.
