## 2. 개념 모델

```
메인 워크스페이스(1개)  ── 할당 ──▶  서브 워크스페이스(N개)
  잔액(보고값)                        정기 할당(매월) + 추가 할당 기록
  할당 합계·미할당                     └ 그룹(인당 한도·기간·허용 모델)
                                          └ 참가자(이메일, 개인 몫 덮어쓰기)
```

- **메인의 '서브 할당'은 기존 `workspace_credit_plan.recurring_topup`(정기 충전) + `workspace_credit_topup`(긴급 충전)을
  그대로 뜻을 옮겨 쓴다.** 이름만 화면에서 '정기 할당'·'추가 할당'으로 부른다. 새 저장소를 만들면 대시보드와 두 벌이 된다.
- **서브의 그룹·크레딧·참가자 = 기존 크레딧 플랜의 그룹·몫·배정**(09-29 인당 한도 규칙 그대로, `CREDIT_QUOTA_DESIGN.md`).
- **참가자** = 이 서브의 (a) 에이전트가 보고한 멤버(`workspace_member.is_available=1`) ∪ (b) 그룹에 배정된 이메일.
  (b) 에만 있는 사람은 '힉스필드 확인 전' 표시. 프로젝트 멤버십은 이 설계 범위 밖(기존 대시보드 그대로).

## 3. 데이터 — 새로 필요한 것은 표 하나

`content_hub.db` 사이드카(`manage_schema.py`, 다른 크레딧 표와 같은 DB):

```sql
CREATE TABLE IF NOT EXISTS workspace_console (
  workspace_id TEXT PRIMARY KEY,           -- workspace_registry.id (힉스필드 id)
  tier         TEXT NOT NULL CHECK (tier IN ('main','sub')),
  sort_order   INTEGER NOT NULL DEFAULT 0,
  archived     INTEGER NOT NULL DEFAULT 0, -- 서브를 콘솔에서 내림(데이터는 보존)
  created_by   TEXT, created_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_workspace_console_main ON workspace_console(tier) WHERE tier='main';
```

- **메인 지정**: 부분 유니크 인덱스로 메인은 최대 1개. 첫 부팅 시드 — 등록부에서 이름을 정규화(대문자·공백 제거)해
  `MILLIONVOLT` 와 **정확히 하나** 일치하면 main 으로 넣는다. 0개·여러 개면 비워 두고 콘솔이 '메인 지정' 단추를 보인다.
- **서브 시드**: 기존 등록부의 이름 있는 워크스페이스 중 메인이 아닌 것을 모두 sub 로 넣는다(Jay: "나머지는 서브").
  시드는 표가 **비어 있을 때 한 번만** — 이후 새로 보고된 워크스페이스는 자동으로 서브가 되지 않고 '연결 대기'에 뜬다.
- 등록부에서 사라진 id(보고 끊김)는 콘솔 행을 지우지 않는다 — '최근 보고 없음' 표시만(부재를 삭제 의도로 읽지 않는다).

## 4. API (모두 `/api/manage/console/*`, 서버 권위 — 로컬 허브는 프록시)

| 메서드·경로 | 권한 | 내용 |
|---|---|---|
| `GET /console/overview` | `read_all` | 메인 1 + 서브 목록. 각 서브: 잔액·최근 보고 시각·정기 할당·이번 주기 추가 할당·이번 주기 사용·그룹 수·참가자 수(보고/미확인)·경고. 메인: 잔액·서브 할당 합계. + `pending`(콘솔에 없는 보고된 워크스페이스) |
| `POST /console/workspaces` `{workspace_id}` | `create_project` | 서브로 등록(= '워크스페이스 만들기'). `pending` 에 있는 id 만 허용 |
| `PATCH /console/workspaces/{id}` `{archived?, status?}` | `create_project` | 내리기·다시 올리기 · 서브 상태(active·inactive·done). 순서는 프로젝트 순서(`POST /api/projects/reorder`)로 정한다 |
| `PUT /console/allocation-base` `{credits, day}` | `create_project` | 메인의 '할당된 크레딧' 기준값(힉스필드 화면 값)과 그 날짜. `credits: null` 이면 지워서 기록 기준 추정으로 |
| `PUT /console/main` `{workspace_id}` | `grant_global`(admin) | 메인 **최초 지정만**(2026-09-30 메인 고정) — 이미 메인이 있으면 다른 id 는 409·행 그대로, 같은 id 는 변경 없음. 메인이 등록부에서 사라지면 개요가 `main_orphan: {id}` 를 주고 화면은 지정 선택기 대신 복구 안내(조용히 바꾸지 않는다 — 수동 복구) |
| 할당·그룹·참가자 쓰기 | 기존 `PUT /credit-plan/{ws}` | **새 쓰기 API 를 만들지 않는다** — revision 409·충돌 병합(`useManageEditConflict`)·감사 기록·몫 보존(KEEP) 계약을 그대로 물려받는다 |
| 서브 상세 읽기 | 기존 `GET /credit-plan/{ws}/settings` + `GET /credit-plan?workspace_id=` | 그대로 |

- overview 는 여러 워크스페이스를 한 번에 돌며 `manage_credit_plan` 의 기존 계산 함수(주기 시작·정기 할당 파생·사용량 인덱스)를
  **불러 쓴다** — 새 계산식을 만들지 않는다. 사용량은 `manage_hub.db` 팩트라 두 DB 스냅샷이 어긋날 수 있음(관리 표와 같은 한계, 표시용).
- 구서버(콘솔 API 없음)면 404 → 탭에 '서버 업데이트 뒤 사용' 안내만(관리 표와 같은 방식).

## 8. 열린 질문

  대안 = 이름만 먼저 예약하고 보고가 오면 이름으로 자동 연결(동명·오타 위험 → 비추천).

- **그룹 알약**(Jay): 그룹 표 = 알약 누르면 색 12가지(`GROUP_COLOR_PALETTE`, `groupColorBody`), 참가자 표 = 알약 누르면 그룹 알약 목록
  (+ 그룹 없음, `groupAssignBody`). 서브 화면 탭 순서 = 그룹·참가자·크레딧.
- 서브 화면 **크레딧 탭을 메인과 같은 규칙으로**(Jay): 충전 줄 = `scheduleLabel`(자동 · 매월 N일 / 매주 X요일 / 매일 · 수동) + Next,
  이번 주기·추가 크레딧·사용 = 개요의 그 서브 줄(할당 주기 창) 값. 입력은 메인과 같은 ＋ 크레딧 창(자동 | 수동 | 추가) 하나 — 밑줄 칸과
  별도 추가 기록 창(TopupDialog)은 뺐다. 충전일은 서브 자기 플랜 한 줄이라 메인·서브 화면이 같은 값을 읽고 쓴다.
- 참가자 탭(Jay): **내 몫 = 그룹이 정한 값만 표시(수정·'자동' 표기 없음)** — 사람별 덮어쓰기는 콘솔에서 뺐다(저장 계약·관리 표의 몫 칸은 그대로).
  **검색 + 칩 필터**(그룹·힉스필드 확인·몫 초과) — 작업 탭 필터 바와 같은 클래스의 `ConsoleFilterBar`(WorkFilterBar 는 Task 필드 전용이라 못 씀),
  검색 상자는 `WorkSearchBox` 재사용. 예전 '이메일·그룹 선택' 칸은 필터가 아니라 추가 입력이라 헷갈렸다 → '＋ 참가시키기' 창(이메일 + 그룹 알약)으로 옮김.
- 왼쪽 목록(Jay): '서브 워크스페이스' 제목 바로 밑 **＋ 서브 워크스페이스**(옛 '워크스페이스 만들기' — 이제 메인을 고르지 않아도 보이고,
  연결 대기 수는 단추 배지로), 그 아래 **활성 · 비활성 · 완료** 묶음. 상태 알약을 바꾸면 해당 묶음으로 옮겨진다(개요 다시 읽기).
- 참가자 표 **프로젝트 역할 알약**(Jay): 그룹 앞 '역할' 열 — PM·Sup·Creator(관리 표와 같은 `mtable-chip role-*` 색). 데이터는 관리 표 API
  (`GET member-table?workspace_id` — 이메일↔uid↔프로젝트별 역할, `caps.project_roles` 없으면 열을 숨김), 저장은 기존 `setProjectRoles`,
  마지막 역할을 끄면 '프로젝트에서 빼기' 확인 뒤 `removeProjectMember`. 프로젝트가 여럿이면 머리에 '역할 프로젝트' 선택.
  uid 없음·계정 엉킴(`project_editable=false`)은 읽기 전용. 실측: 감튀 PM·Creator → +Sup → −Sup 원복(DB 대조).
- 서브 표 **렌더 폴더 단추**(Jay): ＋ 앞 폴더 아이콘(편집 권한만) → 그 서브의 보관 안 된 프로젝트마다 경로 한 줄(`taskProjects(ws)` →
  `projectFolder`/`setProjectFolder` — 프로젝트 관리 창과 같은 API·같은 규칙: 루트가 그대로면 고른 하위 폴더 유지). 렌더 폴더는 **프로젝트마다·이 PC 에**
  저장되는 설정(`/api/manage/project-folders` 는 로컬 전용).
- **프로젝트 기간**(Jay): 개요 서브 줄에 `projects`(보관 안 된 프로젝트의 이름·시작일·종료일 — 개인 정보 없음). 서브 표 '기간' 열(남은 크레딧 앞) =
  달력 단추 + 요약(`periodSummary` — 여럿이면 가장 이른 시작 ~ 가장 늦은 종료). 단추 → 프로젝트마다 시작·종료 입력 창, 저장은 기존 기획 API
  (`getPlanning` → `savePlanning` 409 병합). **달력**: 이름 '달력', `기간 | 크레딧` 필터(둘 다 켜기 가능), 기간 = 프로젝트 시작~종료를
  여러 날 막대로(시작일·주 첫날에 이름, 프로젝트마다 색). 날짜 줄 높이를 20px 로 고정해 오늘 칸에서도 막대가 한 줄로 이어진다.

## 12. 프로젝트 관리 창 대체(설계 — 2026-09-29, Jay 결정 후 Codex 검토 전)

**목표**: 이제 프로젝트 관리 창 대신 서브스페이스를 쓴다. 관리 창이 영향을 주던 곳에 서브스페이스도 똑같이 영향을 준다.
**Jay 결정**: 서브 = 힉스필드 워크스페이스를 연결한 것이라 만들기·이름·워크스페이스 지정은 불필요 · 상태로 보관을 대신 · 순서 끌기는 넣는다 ·
자동 보관 일수는 기간 창에 · **상태 매핑 = 활성→진행(보관 해제) · 비활성→보류 · 완료→완료+보관** · **서브 연결 때 프로젝트가 없으면 같은 이름으로 자동 생성**
(Education 처럼 이미 없는 서브도 한 번 채움) · 워크스페이스 미지정 프로젝트(블룸메이커)는 그대로 둠.

**사실(코드 확인)**
- 역할·렌더 폴더·기간·생성물 배정·작업 탭·최종 권한은 전부 **프로젝트**에 붙는다 → 프로젝트 없는 서브는 이 기능을 못 쓴다(사본: Education 0개).
- 사본의 서브↔프로젝트는 1:1(R&D↔RnD, 뻘뻘뻘, 산해학원), 메인 MILLION VOLT·Education 은 0개.
- 보관(`project.archived`)은 메인 목록·생성물 필터·팀 집계 여러 곳이 본다. 관리 창의 보관 PATCH 는 라우터에서 `asset_watcher.unwatch` 도 부른다(부수 효과).
- `create_project(name)` 은 **같은 이름의 진행 중 프로젝트가 있으면 그것을 돌려준다**(워크스페이스가 달라도) — 그대로 쓰면 남의 프로젝트를 서브에 붙인다.
- 자동 보관 일수(`project_planning.archive_after_days`)는 프로젝트가 아니라 **작업 탭 작업**의 자동 보관 기준(N일 새 생성물 없음, 단 프로젝트 종료일 전이면 보관 안 함).

**설계**
1. **상태 → 프로젝트**(`set_status`): 그 서브의 프로젝트 전부(보관 포함)에 한 번에 적용.
   `active` → archived=0 · planning.status='active' / `inactive` → archived=0 · 'hold' / `done` → archived=1 · 'done'.
   보관 변경은 관리 창과 같은 경로(`update_project_identity`) + 라우터에서 `asset_watcher.unwatch`. 기획 상태는 revision+1·updated_by·감사 기록(관리 창
   저장과 같은 규칙 — 다른 창의 편집은 409 로 잡힌다). 콘솔 상태·프로젝트 보관·기획 상태를 **한 트랜잭션**으로 쓸 수 있는지 Codex 확인 요청.
2. **프로젝트 자동 생성**: `link_sub` 성공 뒤, 그 워크스페이스 소속 프로젝트가 보관 포함 0개면 새로 만든다 — 이름 = 워크스페이스 이름, 같은 이름이 다른 곳에
   있으면 `이름 (워크스페이스)` 로. `create_project` 의 이름 재사용 분기를 피하려고 워크스페이스를 확인한다. 워크스페이스 멤버 자동 편입은 `create_project`
   의 기존 동작 그대로. 기존 서브(Education 등)는 **1회 백필**(표식 `workspace_console_project_backfill_v1`, 쓰기는 표식 없을 때만).
3. **순서 끌기**: 왼쪽 목록(상태 묶음 안)에서 끌어 놓으면 서브 순서 = 그 서브 프로젝트들의 순서로 `reorder_projects`(전체 순서 재기록). 콘솔 서브 목록도
   프로젝트 sort_order 순으로 정렬(이름순 대신).
4. **자동 보관 일수**: 기간 창 한 줄에 '작업 자동 보관(일)' 칸 추가(기존 기획 저장 경로).
5. **개요의 projects** 는 보관된 것도 포함(완료 서브의 기간·폴더를 다시 볼 수 있게) + `archived` 표시.
6. 프로젝트 관리 창('＋ 프로젝트')은 이 단계에서는 남겨 둔다. 서브스페이스 실측 뒤 Jay 가 없앨지 정한다.

### §12 수정안(Codex 1차 '수정 요청' 반영 — 관리 창과 **같은 API 를 같은 방식으로** 부른다)

Codex 치명 2건(트랜잭션 중첩·`set_planning` 이 안 보낸 칸을 NULL 로 덮음)과 중요 '프록시 모드에서 watcher 미해제'는 모두 **서버 쪽에 새 트랜잭션
코드를 만들 때** 생기는 문제다. 관리 창은 보관·기획·순서를 각각 기존 API 로 따로 부른다(`ProjectManagerPanel.tsx:321-325,378-379,396`).
서브스페이스도 **같은 API·같은 순서**로 부르면 영향이 관리 창과 정확히 같고 새 서버 코드가 없다.

1. **상태 변경**(프런트가 차례로): ① `PATCH /console/workspaces/{id} {status}` ② 그 서브의 프로젝트마다 보관이 달라지면 `api.updateProject(pid, {archived})`
   — `/api/projects` 는 로컬 경로라 **이 PC 의 watcher 해제·감사·서버 위임을 관리 창과 똑같이** 거친다 ③ `getPlanning` → `savePlanning(baseline,
   {...baseline, status})` — 읽은 기획 전체를 보내므로 기간·예산·메모가 보존되고 409 병합 창도 그대로. 관리 창처럼 원자적이지 않다: 중간 실패는 알림에
   남기고 같은 동작을 다시 누르면 수렴(각 단계 멱등). 다른 PC 의 watcher 는 관리 창과 같은 한계(중앙 전파 없음).
2. **재활성화 멤버**: 보관 중 새로 들어온 멤버는 보관 해제 뒤 **다음 자기 보고(최대 10분)** 에 자동 편입된다 — 관리 창의 보관 해제와 같은 동작(새로 만들지 않음).
3. **이름 충돌**: 보관 해제가 같은 이름의 활성 프로젝트와 부딪치면 기존 409 문구를 그대로 보여 준다(관리 창과 같음).
4. **자동 생성**(서버, `link_sub` 커밋 **뒤** 별도 호출 — 중첩 없음): 그 워크스페이스 프로젝트가 보관 포함 0개일 때만. 이름 = 워크스페이스 이름, 그 이름이
   다른 워크스페이스의 활성 프로젝트면 `이름 (워크스페이스 id 앞 6자)`. `create_project` 가 돌려준 프로젝트의 workspace_id 가 맞는지 확인(아니면 오류).
   **메인은 제외**. 기존 서브 1회 백필 = 시드와 같은 '표식 없을 때만' 경로(`workspace_console_project_backfill_v1`), 쓰기 트랜잭션 밖에서 `create_project`.
   연결(재연결 포함) 직후 프런트가 1번 동기화를 '활성'으로 한 번 돌려 보관된 프로젝트도 맞춘다.
5. **순서**: 왼쪽 목록에서 끌면 `api.projects("team", true)`(관리 창과 같은 전체 목록)를 받아 **콘솔 서브들의 프로젝트를 새 순서로 앞에, 나머지는
   원래 순서 그대로 뒤에** 붙여 `reorderProjects(전체)` — 관리 창처럼 전체를 다시 쓴다. 서브 순서 = 그 서브 프로젝트 중 가장 앞 sort_order(없으면 이름순).
6. **자동 보관 일수** = 기간 창 한 칸(기존 `savePlanning`). **개요 projects** 는 보관 포함 + `archived`.
7. **보관의 사용자 영향(명시)**: 완료(보관)된 서브의 프로젝트는 메인 목록·기본 생성물 목록·facet·관리 표에서 빠지고, 새 생성물 자동 배정(활성 1개일 때만)과
   월 예산 파생 합에서도 빠진다. 기존 생성물은 보관 프로젝트에 남는다 — 관리 창의 보관과 같다.

**§12 구현 결과(2026-09-29)** — Codex 설계 2회(수정 요청 → 수정안) · 코드 리뷰 2회(수정 요청 3건 → **승인**).
- 서버: `ensure_sub_project`(서브 = 프로젝트 1개 보장, 0개일 때만·메인 제외·이름 겹치면 `이름 (ws 6자)`·결과 워크스페이스 확인·`project.created` 감사),
  연결 때마다 재시도(실패 = `project_error`), 1회 채우기(`workspace_console_project_backfill_v1`, 전부 성공 뒤 표식, **create_project 권한자의 조회에서만**),
  개요 projects 는 보관 포함 + 서브 정렬 = 프로젝트 순서.
- 화면: 상태 → `consoleSetStatus` → `updateProject(archived)` → `getPlanning`→`savePlanning`(관리 창과 같은 API·순서, 같은 상태 재클릭 = 재시도),
  왼쪽 목록 끌기 → 전체 프로젝트 `reorderProjects`, 재연결 뒤 활성 동기화(실패 표시), 기간 창에 작업 자동 보관(일).
- ★실측으로 잡은 결함: 열 간격 수정 때 표 모든 칸에 `overflow: hidden` 을 걸어 **상태·⋯ 메뉴가 잘려 누를 수 없었다** → 잘라내기는 이름 칸만.
- 실측(사본): 산해학원 비활성(0, hold) → 완료(1, done) → 활성(0, active), 끌기 전체 재정렬. 확인 뒤 순서·상태 원복. 1회 채우기로 Education 프로젝트 생성(결정대로).
- 한계: 동시 연결 시 생성 감사가 두 번 남을 수 있음(데이터는 한 번) · 다른 PC 의 Assets 감시는 관리 창과 같은 한계(중앙 전파 없음) ·
  보관 해제 뒤 새 멤버 편입은 다음 자기 보고(≤10분).

## 13. 대시보드를 서브스페이스 값으로 표시(설계 — 2026-09-29, Jay 요청 · Codex 검토 전)

**Jay 요청**: "서브스페이스에서 정한 값을 토대로 대시보드에 표시가 되어야 한다."

**사실(코드 확인)**
- 서브스페이스의 크레딧(정기·추가·주기)은 워크스페이스 크레딧 계획(`workspace_credit_plan.recurring_*`·topups)에 저장된다. 워크스페이스 사용 현황 카드(`plan_view`)는
  이미 이 값을 읽는다 — 손 입력(`recurring_topup`)이 있으면 그것, 없을 때만 프로젝트 '매월 예산' 합으로 파생(`_monthly_budget`).
- 서브스페이스의 상태·기간은 프로젝트 기획(`project_planning.status/start_date/due_date`)에 저장된다 → 대시보드의 상태 칸·기간 툴팁은 이미 서브스페이스 값을 보인다.
- **프로젝트 예산(`project_planning.budget_credits/budget_period`)을 직접 읽는 표시가 남아 있다**: ① 대시보드 '프로젝트 요약' 표의 '크레딧(한도)' 칸

**설계**
1. 서버 `dashboard_summary`(매니저 보기)의 프로젝트 행에 `console_limit` 을 붙인다 — 그 프로젝트의 워크스페이스가 **콘솔 서브**일 때만:
   `{workspace_id, workspace_name, credits: 한 번 충전액(수동이면 월), period: day|week|month, topups_cycle: 이번 주기 추가 합, shared_projects: 같은 서브의 활성 프로젝트 수}`.
   값은 서브스페이스 개요와 **같은 계산**(`_sub_summary` 의 충전액·주기·주기 창)에서 뽑는다 — 새 규칙을 만들지 않는다.
   충전액이 없으면(정기 없음) `credits=null`. 서브가 아니면(메인·워크스페이스 없는 프로젝트) 필드 없음 → 종전 프로젝트 예산 표시.
2. 대시보드 '크레딧(한도)' 칸: `console_limit` 이 있으면 `정기 + 이번 주기 추가`를 보이고 툴팁에 `서브스페이스 · 서브 {이름} · 월/주/일 정기 N + 추가 M`,
   공유면 `· 프로젝트 K개가 함께 씀`. 없으면 종전(프로젝트 예산).
3. 멤버 보기(`project_dashboard_summary`, viewer 있음)는 **붙이지 않는다** — 풀 충전 정보는 멤버에게 주지 않는 기존 원칙(`plan_view` viewer 분기).
4. PM 관리 표 프로젝트 시트: 서브 프로젝트의 예산 칸은 **읽기 전용 + '서브스페이스에서 설정'**(값은 `console_limit`), 월 예산 합도 서브스페이스 값으로.
   서브가 아닌 프로젝트는 종전대로 편집 가능. (두 곳에서 쓰면 어느 쪽이 현행인지 잃는다.)
5. 파생 폴백(`_monthly_budget`)은 건드리지 않는다 — 서브스페이스에서 정기를 비운 서브는 종전처럼 프로젝트 예산 합으로 파생된다. 서브스페이스 화면은 이미 '없음'으로 표시(파생 숨김, Jay 결정).

**Codex 확인 요청**: ⓐ `dashboard_summary` 에서 서브마다 `plan_view` 를 부르는 비용(서브 수 × 사용량 조회)이 괜찮은지, 가벼운 읽기(계획 행 + 주기 창)로 충분한지

## 16. 관리 표 = 서브스페이스의 표 버전(설계 — 2026-09-29, Jay 요청 · Codex 검토 전)
