# PR로 연결하는 기능 묶음 리뷰

운영 확장: pr-review-2026-10-21-r1. 기존 역할·적대적 검토·필수 검증은 [AGENT_WORKFLOW](AGENT_WORKFLOW.md), 작업실 운영은 [WORKROOMS](WORKROOMS.md), main/배포 게이트는 [위험 축소 계획](RISK_REDUCTION_PLAN_2026-08-15.md)을 유지한다. 이 문서는 PC 전역 파일 없이도 적용할 수 있는 MV Hub의 PR 인계 규칙이다.

## 언제 적용하는가

- 사용자 요청에 따라 새 기능 묶음·새 후보부터 적용한다. 이미 진행 중인 작업·고정 후보·미커밋 변경·세션을 강제 전환하지 않는다. 다른 작업실의 변경을 이번 PR에 가져오지 않는다.
- 기능 작업실과 통합 시험실은 그대로 쓴다. 통합 브랜치 전체를 배포하지 않고 사용자가 선택한 작업실의 변경과 승인된 의존성만 후보로 정한다.
- 작은 편집마다 독립 리뷰하지 않는다. 완성된 기능 묶음, 요청된 누적 검토 또는 후보를 고정한 시점에 검토한다. 위험 변경의 실사용 통합 전 리뷰는 유지한다.
- GitHub PR은 리뷰·수정·검증 이력을 모으는 곳이다. 상주 AI, 매 Push의 양측 전체 리뷰, 무인 자동 수정·병합·배포를 설치한 것이 아니다.

## 리뷰와 수정

1. Claude 설계 → Codex 적대적 검토·실제 합의 → 한 담당자 구현·자기 검토·관련 시험을 유지한다.
2. Codex가 구현하면 새 Claude 리뷰 세션, Claude가 구현하면 새 Codex 리뷰 세션을 쓴다. 중요한 변경은 설계·합의에 참여하지 않은 세션으로 분리한다. 같은 기능 묶음의 전체 리뷰를 양쪽이 반복하지 않는다.
3. 첫 독립 리뷰는 요구·합의 계약·후보 diff·head/base·완료 조건을 받는다. 구현자의 정당화나 이전 승인 결론을 근거로 삼지 않는다. 코드의 실제 호출·실패 경계를 확인한다.
4. 로컬과 PR의 지적을 ID·우선순위·파일/위치·발생 조건·근거·담당자·상태가 있는 한 목록으로 합친다. 리뷰어는 수정하지 않으며 한 구현 담당자가 고친다.
5. 수정 후에는 이전 지적 ID, 수정 커밋/diff, 영향 경로와 관련 시험만 재검토한다. 이전 리뷰 범위와 실제 변경을 대조해 그대로인 부분은 유효한 근거를 재사용한다. base·주변 맥락·환경 변경, 새 실패·반례, 공유 계약·DB·보안 경계 변화나 영향 범위 불명확 때는 필요한 전체 검토를 확대한다. patch-id 일치만으로 재사용하지 않는다.
6. 필수 지적·시험 실패·미확인이 남으면 완료가 아니다. 지적 상태는 수정 후 검증 / 오탐 근거 확인 / 미해결·보류 / 사용자 결정 필요로 기록한다. 선택적인 취향 개선은 후속으로 둔다. 같은 문제로 두 번 왕복해도 진전이 없으면 사용자 판단을 요청한다.

## 후보 PR 만들기와 기록

- 기존 Git 승인 범위에서 선택한 변경만 커밋한다. 공개 저장소로 전송하기 전 비밀값·개인 자료·사용자 데이터·원본 로그/대화를 제외하고 diff를 확인한다. 제품/설정 외 다른 세션의 변경을 섞지 않는다.
- 리뷰된 깨끗한 후보를 전용 브랜치에 Push하고 main 대상 Draft PR을 만든다. 로컬 원본 리뷰 결과를 재사용하며 PR 생성 때문에 전체 리뷰를 다시 호출하지 않는다. 현재 묶음이 준비되지 않으면 기존 PR을 보류 상태로 둔다.
- PR 본문에는 현재 head/base SHA, 포함 묶음과 의존성, 구현자, 리뷰 결과 링크, 검증·미확인, 사용자 승인 대기 여부를 둔다. 세부 작업 상태 정본은 기존 작업 기록을 유지한다.
- 총괄이 독립 리뷰 결과를 버전별 댓글로 게시한다. 원본 지적과 이전 버전 댓글은 지우지 않고 새 수정 커밋·재검토 결과를 연결한다. 게시자는 AI 응답을 전달하는 사람/계정이며 실제 리뷰 제공자와 구분한다.
- 결과에는 head/base SHA, 실제 검사 SHA, 전체 묶음 또는 이전 head 이후 변경·영향 범위, 요청 모델/추론과 실제 확인값, 구현자/비구현 리뷰 주체, 지적 상태, 시험 결과·링크·미확인을 둔다. 세션 원본·로컬 절대경로·토큰·개인정보는 공개하지 않는다.
- 실제 PR head가 바뀌면 이전 검토/승인의 유효 범위를 다시 판단한다. PR이 여러 개인 경우 자동으로 다른 PR까지 수정하지 않는다.

## CI와 로컬 검증

- PR policy workflow의 policy-check는 지침 일관성과 검사기 단위시험만 확인한다. 제품 시험·독립 리뷰·Gate 6-A·사용자 승인을 대체하지 않는다.
- CI는 pull_request 이벤트의 임시 merge commit을 검사한다. 이벤트의 head/base SHA와 실제 checkout SHA를 각각 기록한다. head에서 수행한 로컬 시험을 merge SHA의 시험으로 바꾸어 보고하지 않는다.
- 깨끗한 checkout에서는 python -B tools/check_agent_guidance.py --tree HEAD로 실제 Git snapshot을 검사한다. 인자가 없으면 기존 pre-commit용 staged 검사다. YAML 문법 검증은 이 검사기의 범위 밖이며 실제 Actions 실행 결과를 따로 확인한다.
- 제품 변경의 관련 시험과 Gate 6-A 필수 전체 시험은 기존 규칙대로 수행한다. 동일 대상·환경의 기존 유효 근거는 재사용한다. 이 설정 PR의 policy-check 성공을 제품 전체 통과로 보고하지 않는다.

## 사용자 승인·main·배포

- 기능 구현·설정·PR 생성·AI 리뷰 통과는 main 병합 승인이 아니다. 사용자가 승인한 PR과 후보 SHA·포함 범위를 병합 직전에 실제 원격 head/base와 대조한다. 변경되면 기존 승인을 그대로 쓰지 않는다.
- 첫 단계는 기존 Gate 6-A와 정확한 후보의 fast-forward 병합 방식을 유지한다. 사용자의 직접 병합 지시 뒤 한 담당자만 승인 후보를 main으로 FF 반영·Push한다. GitHub의 merge/squash/rebase 버튼으로 다른 SHA를 만들거나 관리자 우회를 쓰지 않는다. PR은 정책상 필수인 검토 기록이며 서버가 PR 경유를 강제한다는 뜻은 아니다.
- 병합 뒤 원격 main과 승인 후보의 일치, PR의 실제 merged/closed 상태를 조회한다. 상태를 보기 전에 PR이 자동 병합 처리됐다고 주장하지 않는다. PR을 단순 close해서 실제 병합처럼 기록하지 않는다.
- 배포는 별도 사용자 승인과 Gate 6-B/C, 고정 릴리스 작업실에서만 한다. PR 승인/병합으로 서버·설치본을 재시작하지 않는다. 자동 병합·자동 배포는 사용하지 않는다.
- 같은 GitHub 인증을 공유하면 사람의 승인과 AI의 기록을 서버에서 구별할 수 없다. main 강제 Push·삭제 방지/직선 이력 보호와 PR 필수/사람 승인 강제는 서로 다른 상태다. 실제 적용 설정만 완료로 보고한다.
- PR 필수·필수 검사·필수 승인 수는 현재 FF 방식과 인증 주체·실제로 실행 가능한 검사를 먼저 맞춘 뒤 별도 활성화한다. 같은 계정의 자기 승인을 요구하거나 실행할 수 없는 검사로 저장소를 잠그지 않는다.

## 다음 단계와 완료 범위

이 문서·workflow가 설정 PR에만 있는 동안 저장소 기본 브랜치 설치는 승인 대기다. 기존 작업실을 자동 업데이트하지 않는다. 병합 후 필요한 작업실에서 최신 지침을 읽고 충돌을 확인한다. 기존 미커밋 지침을 덮어쓰지 않는다.

리뷰 시작/종료·왕복 횟수·재검토 범위·대기 이유는 기존 작업 기록이나 PR에 남겨 효과를 확인한다. 고정 시간 절감률을 약속하지 않는다. main 승인 확인을 기술적으로 분리하려면 별도 인증 주체와 권한 설계가 필요하며 이번 설정은 그 인증을 변경하지 않는다.
