## 1. 이 문서의 목적

최근 검증 구현 기준 `dev`에는 생성·DB·백업·Comfy·Resolve·운영 안정성 수정이 한 통합 후보로

자동 테스트와 관리 화면 브라우저 실측은 통과했지만, 실제 외부 시스템과 결합된 운영 위험은
여전히 별도 Gate로 남아 있다.

이 문서는 다음 세 가지를 위해 사용한다.

1. 이미 해결한 감사 항목을 다시 수정하지 않는다.
2. 남은 위험을 사용자 영향과 재현 가능성 기준으로 다시 우선순위화한다.
3. Codex와 Claude가 설계 결정을 합의한 뒤 작은 커밋 단위로 구현한다.

기존 감사 이력은 [AUDIT_2026-08-15.md](AUDIT_2026-08-15.md)에 보존한다. 현행 구조와 데이터

## 3. 불변 원칙

다음 원칙에 반하는 제안은 구현 전에 별도 설계 승인을 받는다.

1. 개인 생성물·개인 자산·캔버스는 로컬 우선이다.
2. 공유는 명시적인 publish 동작으로만 이루어진다.
3. 공유 서버는 생성하지 않는다. 실제 생성은 사용자 PC의 에이전트와 CLI가 수행한다.
4. 알 수 없는 계정·워크스페이스·권한은 추측하지 않고 실패 처리한다.
5. `generation.id`는 로컬·서버에서 다를 수 있으며, 경계 간 추적 기준은 `job_id`다.
6. DB 삭제·복원·정리처럼 되돌리기 어려운 작업은 백업과 사용자 확인 없이 실행하지 않는다.
7. 로그에는 인증정보, 전체 프롬프트, 원본 URL 같은 민감정보를 그대로 남기지 않는다.

### Gate 1 — 작업 대시보드의 데이터 의미 확정 (P0, 완료)

완료 전 위험:

- 작업 화면은 로컬 실제 폴더가 아니라 공유 서버의 `generation.folder_path`에서 만들어진 누적
  작업을 표시한다.
- 현재 선택 워크스페이스가 작업 조회에 일관되게 전달되지 않는다.
- 작업 행은 추가 중심이라 과거 또는 삭제된 기록이 계속 보일 수 있다.
- 프로젝트 수·멤버 수와 시퀀스 작업 집계가 서로 다른 범위를 사용할 수 있다.

완료 전 코드에서 확인한 원인:

- `frontend/src/components/manage/WorkBoard.tsx`가 선택 워크스페이스를 전달하지 않고
  `projects("team")`의 전체 팀 프로젝트를 불러온다.
- `backend/app/routers/manage.py`의 `/summary`, `/project-summary`, `/tasks-batch`는 읽기 권한은
  확인하지만 선택한 `workspace_id`를 공통 조회 조건으로 사용하지 않는다.
- `backend/app/repo/manage_tasks.py`의 폴더 작업 동기화는 로컬 디스크를 읽는 기능이 아니라
  공유 DB의 과거 `generation.folder_path`를 작업 행으로 만든다. 따라서 현재 PC에 없는 폴더도
  공유 작업 기록으로 표시될 수 있다.
- 생성에서 파생된 작업 행에는 명시적인 현재·과거 수명주기가 없어, 과거 행이 활성 프로젝트
  화면에 계속 남을 수 있다.

즉 화면 오류 하나가 아니라 **데이터 출처 표시, 워크스페이스 범위, 작업 수명주기**가 한 계약으로
묶이지 않은 문제다. 사용자 PC 폴더를 공유 서버가 직접 검사하는 방식으로 고치면 다른 사용자의
작업이 사라지므로 사용하지 않는다.

권장 설계:

1. `작업` 기본 화면은 **선택한 워크스페이스 + 사용자가 볼 수 있는 활성 프로젝트**로 제한한다.
2. 서버가 확인할 수 없는 사용자 PC의 물리 폴더 존재 여부를 서버 진실값으로 삼지 않는다.
3. 생성 기록에서 유도된 작업에는 `active`, `archived`, `source_last_seen_at` 같은 수명주기 개념을 둔다.
4. 오래된 항목은 자동 삭제하지 않고 `과거 기록`으로 분리한다.
5. 화면에 `공유 서버 작업 기록`처럼 데이터 출처를 표시한다.
6. 프로젝트 요약·멤버·시퀀스·Yield가 같은 workspace/project/visibility 조건을 사용하게 한다.

1. 관리 조회에 명시적인 `workspace_id`를 전달하고, 프로젝트 목록·요약·작업이 같은 범위 헬퍼를
   사용하게 한다.

결정이 필요한 질문과 **검토 합의 권장 답**(최종 확정은 사용자):

  별도 토글. 자동 삭제 없음(불변 원칙 6).
- archived 판정 시점? → **`max(마지막 생성 기록 후 30일, 프로젝트 계획 마감일)`** 경과.

  과금된 공간의 불변 사실 스냅샷이다(WORKSPACE_DATA_CONTRACT). 이동은 명시 재배정 작업으로만
  하고 별도 이력/필드로 남겨 과금 스냅샷을 지우지 않는다.

선결 조건인 **RL-01과 RL-03** 위에서 RL-02도 완료했다. 생성 당시 workspace와 주기 동기화
텔레메트리가 보존되는 데이터 입구를 기준으로 화면 범위와 자동 작업 수명주기를 통일했다.

### Gate 2 — 생성 완료·소유권·과금 경계 강화 (P0)

대상 위험:

- claim 후 에이전트가 사라졌을 때 lease 만료·재할당 계약이 불완전할 가능성.
- 캔버스 재시도 충돌에서 placeholder가 남을 가능성.
- 견적용 CLI subprocess 동시 실행 수가 제한되지 않을 가능성.
- 요청 취소 시 subprocess가 완전히 회수되지 않을 가능성.
- 알 수 없는 workspace가 직전 team workspace로 귀속될 가능성.

권장 순서:

1. 상태 전이표와 DB CAS 조건을 먼저 문서화한다.
2. claim에 소유자, lease 만료, heartbeat, 복구 조건을 명시한다. **lease 만료 자체는 재큐잉
   근거로 사용하지 않는다.**
3. workspace 미확정은 개인/이전 공간으로 추측하지 않고 요청을 거절한다.
4. placeholder 생성과 요청 등록을 하나의 원자적 작업으로 묶거나 실패 보상한다.
5. CLI 실행에 공통 세마포어·취소·프로세스 종료 계약을 적용한다.

RL-05 안전 복구 기준:

| 중단 시 상태 | 자동 처리 | 이유 |
|---|---|---|
| `claimed` | CLI 제출 전임이 확인된 경우에만 재큐잉 | 아직 외부 과금이 시작되지 않았음이 증명돼야 함 |
| `submitting` | 자동 재큐잉 금지, 외부 생성 조회 후 `running` 복구 또는 `recovery_required` | CLI가 생성했지만 `job_id` 저장 전에 끊겼을 수 있음 |
| `running` + `job_id` 있음 | 새 생성 없이 기존 작업 추적 재개 | 이미 제출된 생성의 상태만 이어서 확인 |
| `running` + `job_id` 없음 | `recovery_required`, 자동 재제출 금지 | 외부 제출 여부를 확정할 수 없음 |
| `done` | 변경 금지 | 늦은 lease·에이전트 응답으로 완료를 되돌리지 않음 |

`recovery_required`는 자동 재생성 상태가 아니라 운영자 또는 복구 루틴이 외부 생성 여부를 확인해야
하는 보류 상태다. 외부 생성이 실행되지 않았음이 확인된 경우에만 새 요청으로 되돌릴 수 있다.

상태 어휘 매핑(구현 완료): 새 에이전트는 `pending → claimed → submitting → running →
tracking/verifying → done/failed/canceled`을 사용한다. 외부 제출 여부가 모호하면
`recovery_required`로 격리한다. 구 에이전트는 혼합 업데이트 호환을 위해 기존 `submitting`
claim을 사용하되, 새 서버가 알려진 모호한 실패와 만료를 자동 재큐잉하지 않는다. 상세
전이·호환·복구 절차는 [GENERATION_SUBMISSION_RECOVERY.md](GENERATION_SUBMISSION_RECOVERY.md)를
단일 세부 계약으로 사용한다.

검증:

- 에이전트 강제 종료 후 같은 작업이 두 번 과금되지 않고 복구된다.
- 완료된 작업은 늦은 응답으로 running/failed로 되돌아가지 않는다.
- workspace가 없거나 권한이 사라진 요청은 생성 전에 명확히 실패한다.
- 취소 후 CLI 자식 프로세스가 남지 않는다.

완료 조건:

- `pending → submitting → running → done/failed/canceled` 전이가 테스트와 실제 로그에서
  동일하다(신설 상태 도입 시 그 어휘로 갱신).
- 생성 1건마다 workspace, account, job_id, 최종 결과가 한 경로로 추적된다.

### Gate 3 — 공유·프록시·텔레메트리 신뢰성 (P1)

대상 위험:

- 일부 401 응답에서 토큰을 지우고 로컬 모드로 전환하면 장애가 데이터 없음처럼 보일 수 있다.
- 네트워크 호출 중 텔레메트리 락을 오래 잡을 가능성.
- ingest가 기존 workspace 정보를 덮어쓸 가능성.
- 크레딧 보고·주기 동기화 실패가 운영자에게 충분히 보이지 않을 가능성.
- publish/unpublish 실패 후 로컬 뱃지와 서버 상태가 달라질 가능성.

권장 설계:

- 인증 만료, 권한 거부, 서버 장애, 비정상 응답을 서로 다른 오류로 유지한다.
- 네트워크 전송은 DB 락 밖에서 수행하고 결과 반영만 짧은 트랜잭션으로 처리한다.
- workspace/account 필드는 권한 있는 명시적 이동 작업 외에는 덮어쓰지 않는다.
- publish 상태는 서버 ACK를 받은 항목만 확정한다.
- 재시도 큐의 크기, 가장 오래된 항목, 마지막 성공 시각을 운영 상태에 노출한다.

RL-10 구현 결과(`dfaa2672`):

- 과거 감사의 “DB 락 안 60초 네트워크” 표현은 실제 코드와 달랐다. SQLite 조회 연결은 원격
  호출 전에 이미 닫혔고, 실제 병목은 프로세스 전체 drain 소유권 락과 ingest의 직접 호출이었다.
- ingest와 MCP ingest는 generation/outbox 저장 뒤 백그라운드 drain만 예약하고 응답한다.
- 동기 FastAPI 작업 스레드는 시작 때 등록한 메인 이벤트 루프에 신호만 게시한다.
- 전송 소유권 상태는 짧게만 잠그고 DB 조회·원격 HTTP·DB 정산은 상태 락 밖에서 수행한다.
- 전송 중 새 요청은 기다리지 않고 후속 drain을 한 번 더 수행한다. 실패·취소도 소유권을 해제한다.
- 같은 밀리초 안의 재변경도 증가하는 `dirty_rev`로 구분하고, 옛 성공·실패가 새 dirty 상태를
  덮지 않게 CAS 정산한다. 구버전 DB에는 기본 revision을 추가하면서 대기 행을 보존한다.
- 대상 37개를 5회 연속, 전체 백엔드 766개, 프론트 527개, 업데이트 40개, 아키텍처 검사와
  프로덕션 빌드를 통과했다. 격리 앱의 주요 화면 전환·콘솔·포트 반환과 기존 빌드 서버 부팅도
  확인했다.
- 세부 상태 흐름과 제외 범위는 [TELEMETRY_DRAIN_LIFECYCLE.md](TELEMETRY_DRAIN_LIFECYCLE.md)를
  따른다. `account_status`·`account_transactions`는 RL-13에서 생성 텔레메트리와 분리된 영속
  재시도 채널로 전환했다.

RL-11 구현 결과(`18d63560`):

- 로컬 생성물이 최종 선택 상태면 공유 서버를 호출하기 전에 공유 해제를 `409`로 막아
  `is_final → shared` 불변식을 보존한다.
- 공유 해제의 명시적인 `generation 없음`만 이미 해제된 멱등 성공으로 인정한다. 구버전 서버의
  라우트 부재처럼 의미가 불명확한 `Not Found`는 로컬 상태를 바꾸지 않고 그대로 실패 처리한다.
- 원격 최종 해제 뒤 로컬 쓰기는 한 번 재시도하고, 응답 유실 가능성 때문에 실제 DB를 다시 읽는다.
  그래도 최종 상태면 원격을 다시 최종 지정해 이전의 일관된 상태로 보상한다.
- 대상 12개, 관련 공유·프록시·감사 62개, 백엔드 전체 778개, 업데이트 40개와 격리 앱의
  로그인·주요 화면 전환·콘솔·포트 반환을 통과했다.
- 상세 판정표는 [SHARE_STATE_COMPENSATION.md](SHARE_STATE_COMPENSATION.md)를 따른다. 실제
  두 계정과 공유 서버를 잇는 왕복은 Gate 6 외부 실측으로 남긴다.

RL-12 구현 결과(`46c6198b`):

- outbox 행의 `pushed_at`과 독립된 `telemetry_delivery_state` 한 행에 마지막 실제 성공 시각을
  UTC ISO 형식으로 보존한다. 기존 DB는 최초 마이그레이션 때 과거 최댓값을 한 번 이관한다.

  성공과 대기 건수를 표시하고, 공유 서버 화면에서는 작업자 로컬 큐를 폴링하지 않는다.

  왕복은 Gate 6 외부 실측으로 남긴다.

- 대상 백엔드 19개, 백엔드 전체 790개, 프론트 76개 파일·533개, 업데이트 40개,

### Gate 4 — 자산·미디어 보안과 수명주기 (P1)

대상 위험:

- **RL-14 완료:** `/api/assets/file`에서 허용되지 않은 확장자 또는 HTML이 같은 출처로 열릴 가능성.
- **RL-15 완료:** multipart 업로드 크기 상한이 불명확하고 테스트 스냅샷 ZIP 추출 계약과 혼동될 수 있다.
- **RL-16 완료:** 삭제·이동된 폴더의 watcher 핸들이 남거나 공유 폴더의 다른 등록까지 끊을 가능성.
- **RL-17 완료:** 대형 Comfy 입력이 메모리에서 여러 번 복사될 가능성.
- 캐시 생성·교체 사이 파일 변경 경쟁 조건 가능성.

권장 작업:

- **RL-14 완료:** 허용 확장자·MIME·다운로드 헤더 정책을 명시한다.
- **RL-15 완료:** 업로드 총량·파일 수·개별 파일 크기 제한을 둔다.
- **RL-16 완료:** watcher 등록부에 명시적인 unregister와 종료 검증을 추가한다.

### Gate 5 — WebSocket·장시간 운영·복구 실측 (P1)

대상 위험:

- WS 재연결에 jitter가 없어 여러 사용자가 동시에 재접속할 수 있다.
- 느린 클라이언트 전송에 타임아웃이 없으면 브로드캐스트가 막힐 수 있다.
- 인증 만료 close code가 사용자에게 보이지 않고 실시간 갱신만 멈출 수 있다.
- 백업이 존재해도 실제 복원 드릴을 하지 않으면 복구 시간을 알 수 없다.

검증 시나리오:

1. 100명 연결을 가정한 WS 재연결·댓글 카운트·team-fresh 부하.
2. 공유 서버 5분 단절 후 복구, 클라이언트 동시 재접속.
3. 8시간 저사양 서버 soak test: 메모리, 핸들, DB lock, outbox, 로그 크기 측정.
4. 백업 복사본으로 별도 임시 경로 복원 후 `/api/ready`, 로그인, 프로젝트 수 대조.
5. 워치독이 busy/maintenance를 사망으로 오판하지 않는지 확인.

| 공유 서버 | publish, 다른 계정 조회, unpublish, 권한 거부 |
| Comfy | 병렬 2건, 취소, 재시작 복구, 입력 혼입 없음 |
| Resolve | 설치 탐지, UNC/매핑 경로, 가져오기, 내보내기 |
| NAS | 정상·느림·단절 각각에서 UI가 멈추지 않음 |
| 릴리즈 | 기존 설치 업데이트, 서버 sparse checkout 업데이트, 실패 후 재시도 |

#### 6-A. Git 병합 Gate

`dev` 코드를 `main`에 넣어도 되는지를 판단한다. Git 병합만으로 실행 중 서버나 작업자 PC가
재시작되지는 않는다.

필수 조건:

- 전체 자동 테스트·프론트 빌드·아키텍처 검사 통과.
- `dev` 작업 폴더가 깨끗하고 병합 대상 커밋이 확정됨.
- DB 스키마가 기존 데이터와 하위 호환되거나 명시적인 마이그레이션·롤백 계획이 있음.
- 기존 `main`보다 생성·공유·업데이트 경로가 악화되지 않았음.

Gate 1 대시보드 문제는 `3d4107e3`에서 해결했다. 병합 시에는 해당 커밋을 포함하고 전체 회귀와
DB 하위 호환 마이그레이션 결과를 다시 확인한다.

#### 6-B. 운영 배포 Gate

운영 서버나 작업자 PC가 새 코드를 pull·업데이트하고 프로세스를 재시작해도 되는지를 판단한다.

필수 조건:

- 운영 서버 DB 수동 백업과 세트(content·trash·manage) 복구 검증(RL-21).
- 대상 서버의 non-terminal 요청이 0건이거나 중단·복구 계획이 기록됨.
- 업데이트할 작업자 PC에서 진행 중 Higgsfield·Comfy·Resolve 작업이 없음.
- 배포 전 커밋과 되돌릴 커밋, 재시작 절차가 기록됨.

#### 6-C. 배포 완료 선언 Gate

사용자에게 새 버전 배포가 정상 완료됐다고 선언할 수 있는지를 판단한다.

필수 조건:

- 실제 Higgsfield 생성 1건 왕복(`claim → anchor → ingest → done`).
- `publish → 다른 계정 조회 → unpublish` 왕복(RL-11/F7 실검증).
- 남아 있는 P0가 해결됐거나 사용자가 영향과 임시 운영 방법을 확인하고 명시적으로 승인함.
- 실측 결과와 로그 위치, 배포 식별자와 롤백 기준점이 기록됨.

### Gate 7 — 구조 부채 축소 (P2)

대상 파일은 기능 수정과 섞지 않고 별도 브랜치·커밋에서 다룬다.

|---|---:|---|

| `App.tsx` | 1,607줄 | 인증, workspace, library, 라우팅, WS orchestration |
| `SpotlightPrompt.tsx` | 1,236줄 | 입력 UI, 명령 해석, workspace/tag 액션 |

| `repo/identity.py` | 941줄 | account link, visibility, members, identity resolve |

원칙:

- 동작 변경 없는 추출부터 한다.
- 기존 공개 함수와 API 응답을 먼저 테스트로 고정한다.
- 한 커밋에서 한 책임만 분리한다.
- 각 추출 후 전체 테스트와 실제 해당 화면 smoke test를 실행한다.

## 6. 구현 단위와 역할 제안

| 단계 | 주도 제안 | 교차 검토 |
|---|---|---|
| 데이터 소유권·대시보드 의미 결정 | Claude | Codex가 쿼리·경계조건 검토 |

역할은 권장안이며 파일 소유권이 아니다. 어느 쪽이 구현하더라도 다른 쪽이 첫 구현은 틀렸다고

## 7. 각 작업의 공통 완료 형식

모든 작업은 다음 정보를 남긴다.

1. 문제와 재현 조건
2. 변경 전·후 데이터 흐름
3. 변경 파일과 변경하지 않은 범위
4. 자동 테스트 결과
5. 실측 결과와 로그 위치
6. DB·API·배포 호환성
7. 남은 위험과 롤백 방법

커밋은 작업 하나당 하나를 기본으로 하고, 커밋 메시지에는 변경 내용보다 변경 이유가 드러나게 한다.

## 8. Claude 검토 요청

Claude는 구현 전에 아래 형식으로 이 계획을 검토한다.

```text
1. 동의하는 Gate와 이유
2. 우선순위를 바꿔야 할 Gate와 근거
3. 현재 코드에서 이미 해결되어 제거할 항목
4. 빠진 P0/P1 위험과 파일·함수 근거
5. Gate 1 대시보드 결정 질문에 대한 권장 답
6. dev → main 병합을 막아야 하는 조건
7. 첫 번째로 구현할 가장 작은 커밋 범위
```

검토 시 추측으로 항목을 추가하지 않고, 현재 `dev` 코드 또는 재현 결과를 근거로 삼는다.
