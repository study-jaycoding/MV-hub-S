## 설계

1. **미리 띄우기(prestage)** — 에피소드를 고르고 컷 빈 표를 받은 뒤, 미리 캐시가 그 판의 원본을 다 받으면 그 에피소드 컷 빈들을 채운다(고른 컷 먼저, 그다음 MV 컷 순서 — 미리 캐시 목록과 같은 컷·같은 ID = 거르기 통과·오래된 200개). **조각으로 나눈다** — 자식 작업 하나 = 이어진 컷들을 항목 합 40개가 될 때까지(컷 하나가 40 을 넘으면 그 컷 하나, 최대 200) · 화면이 대기열에 조각을 하나씩 이어 넣고 **조각 사이마다 판(run)·문맥·에피소드·다빈치 프로젝트를 다시 보고** 바뀌었으면 멈춘다(사이사이 다빈치 빈 읽기·띄움·NAS 옮기기·저장이 끼어든다 — 저장은 조각 하나만 기다린다). 자식은 컷 사이마다 guard(프로젝트)와 지금 빈을 다시 본다. 컷마다 기존 묶음 띄우기(`_panel_stage`)를 쓰되 가져오는 자리만 다르다:
   - 다빈치 지금 빈 == 그 컷 빈 → 그 빈에 바로(지금과 같음).
   - 지금 빈 == 에피소드 빈 → **에피소드 빈(가져오는 자리)에 가져온 뒤 `MoveClips` 로 그 컷 빈에 옮긴다**(지금 빈을 옮겨 다니지 않음). '이번 클립' 판정·짝짓기·안쪽 확인은 모두 **가져오는 자리(에피소드 빈) 기준** — 그 묶음 직전 에피소드 빈 ID 집합(엄격)에 없고, 돌려받았고, 경로가 맞고, **에피소드 빈 목록에 있다고 확인된 클립만** 옮긴다. 옮긴 뒤 컷 빈 목록 되읽기로 확인 — 못 옮긴 것은 에피소드 빈 안에 있다고 확인된 것이니 사용 0 이면 지우고(되읽어 확인) 못 지우면 복구 기록. 에피소드 빈 밖으로 들어간 것(그사이 빈 전환)·확인 전 예외는 1단계처럼 owned:false 기록만(옮기기·지우기 0).
   - 그 밖(사람이 다른 컷 빈에 들어가 있음) → 그 컷은 건너뛰고 deferred(사람이 보는 빈에 남의 클립을 잠깐이라도 넣지 않는다). 들어갈 때 띄움(1단계)이 채운다.
   - 이름은 이 작업에서 바꾸지 않는다(표식만). 클립 상태 = 표식이 붙으면 staged.
   - 나머지 규칙(돌려받은 클립만·직전 ID 엄격·owned:false·예외 leftover·같은 경로 대표·상태 약속)은 1단계 그대로. 예외로 조각이 멈추면 그 조각에서 이미 끝낸 컷들의 복구 기록도 leftover 에 합쳐 올린다.
   - 딜레이 0 은 **그 컷의 미리 띄우기가 끝난 뒤**에만 성립한다 — 받기 전·deferred 컷·새 생성물은 들어갈 때 띄움(1단계 ~1.5초)이 채운다.
2. **이름 뒤따르기(rename)** — 미리 띄우기 조각 뒤 화면이 대기열에 작은 이름 작업을 이어 넣는다(한 번에 최대 10개 — 사이사이 다빈치 빈 읽기·띄움·NAS 옮기기가 끼어들게). 라벨은 라우터가 권한을 확인한 생성물에서 바로 만든다(받기 잠금을 잡지 않음). 자식은 그 에피소드 컷 빈들에서 **이 허브의 내 항목이고 그 생성물 라벨이 있고 클립 이름이 아직 파일 이름 그대로인 것**만 라벨로 바꾸고 되읽는다(사람이 바꾼 이름은 파일 이름과 달라 덮지 않는다 · 끊겨도 다음 작업이 남은 것을 다시 찾는다). 남은 수를 돌려주고, 0 이 되거나 진전이 없으면 멈춘다.
3. **[저장] 단추** — 패널 머리줄 오른쪽 라임 단추 '저장'(리졸브 안·쓰기 담당일 때만). 누르면 진행 중인 미리 띄우기·이름 작업을 멈추고(조각 하나까지 기다림) 대기열에 한 덩어리로:
   ① 이 다빈치 프로젝트의 내 항목을 inventory 로 모두 읽고 그 결과의 `resolve_project_id` 를 **저장할 프로젝트로 고정** — 이후 **모든 adopt(그 ID 를 resolve_project_id 로)·unstage·save 요청에 그 ID 를 실어 자식이 변경 전에 대조**하고(다르면 쓰기 0 · project_changed), 어느 단계든 결과의 프로젝트가 다르면 멈춘다. **쓴 것(사용 >0)과 adopt 복구 기록(adopt 흐름이 남긴 소유 확인된 것)은 NAS 로 옮긴다**(prepare+adopt — 보내기와 같은 폴더·이름). import 기록의 owned:false 는 옮기기 대상이 아니다. 저장 길의 adoptOne 은 생성물 단위 기억(이미 옮김·전에 실패)을 쓰지 않고 그 항목 ID 로 다시 한다(같은 생성물을 다시 띄워 새로 쓴 클립도 옮기게).
   ② **안 쓴 것(사용 0)은 빈마다 unstage**(정리 플래그 없이 — 에피소드 빈·다빈치 지금 빈 포함, 빈은 지우지 않음, 사람 클립·남의 허브·사용 중·모르는 것은 그대로).
   ③ **새 `save` 작업(자식, 쓰기 잠금 안)**: expect_project 대조 → guard → SaveProject 바로 전에 **미디어 풀 전체를 훑어** 다음이 하나라도 있으면 저장하지 않고 `not_clean`(개수: 쓰는 중·안 쓰는 중 + 사람이 직접 지울 수 있게 빈 경로 최대 5개) — (가) 이 PC MV 미디어 폴더 아래 경로인 클립(사용 여부 무관) (나) 패널 표식(`staged_by`, **어느 허브든·파일이 있든 없든**)이 남은 클립 — 파일이 없다는 것만으로 동료 PC 것이라 판정할 수 없어(다른 설치본 캐시가 지워졌을 수도) 막는다(Codex P2). 동료가 남긴 것이라 내 패널이 정리하지 못하면 not_clean 의 빈 경로를 보고 사람이 다빈치에서 지운다. **한계**: 같은 PC 의 다른 설치본(dev·릴리스처럼 미디어 폴더가 다름)이 남긴 표식 없는 클립(owned:false·표식 실패·unexpected)은 (가)(나)에 안 걸린다 — 드묾, 알고 감. **훑기를 끝내지 못하면 깨끗함으로 보지 않고 `scan_failed` 로 저장하지 않는다** — 엄격한 읽기로: 빈·클립 목록이 예외이거나 `None` · `GetClipProperty()` 가 예외이거나 dict 가 아님 · 표식 읽기가 예외 · MV 표식이 있는데 경로가 빈 값 → 실패. '경로가 원래 없음'(타임라인·합성 클립 등)은 dict 를 정상으로 받았고 그 안의 경로가 빈 값이며 MV 표식이 없을 때만 인정한다. 깨끗하면 **SaveProject 바로 전에 열린 프로젝트 ID 를 고정 ID 와 다시 대조**(훑는 사이 사람이 프로젝트를 바꿨으면 저장 0 · project_changed)한 뒤 `ProjectManager.SaveProject()` → ok/save_failed. 성공 안내는 "이 저장 시점의 검사 통과". 최종 검사와 저장이 한 자식·한 쓰기 잠금 안이라 다른 패널 창·보내기는 끼어들지 못한다(사람의 동시 편집은 막지 못함 — 한계). SaveProject 자식에는 시간 제한이 없다(쓰기 자식과 같음).
   ④ 상태 줄에 "저장했습니다 — NAS 로 옮김 n · 정리 m"(not_clean·실패면 무엇이 남았는지).
   ⑤ 끝나면 지금 에피소드를 **다시 미리 띄운다**(딜레이 0 유지). 사람이 컷 빈 안에서 저장했으면 그 컷 말고는 deferred 가 되므로, **다빈치 지금 빈이 에피소드 빈으로 돌아와 따라가기 읽기 두 번 연속 머물면 미리 띄우기를 다시 돌린다**(앞 미리 띄우기가 deferred 컷을 남겼을 때만 · 돌아올 때마다 한 번 · 진행 중인 판과 겹치지 않게 새 판 — 지나가기만 하면 돌지 않아 깜빡임이 없다). '깨끗하다'는 그 SaveProject 시점에만 — 다시 띄운 뒤 단축키(Ctrl+S)·리졸브 자동 저장(Live Save 포함)이 저장하면 이 PC 클립이 함께 저장되어 다른 사람에게 오프라인으로 보인다(1단계보다 범위가 넓음 — 상태 줄 안내 한 줄, 다시 볼 조건).
4. **지우기를 묶어서** — 정리·안 쓴 것 지우기(`_panel_stage` 의 지우기 단계)를 한 클립씩 지우고 확인하던 것을 **후보를 먼저 고르고(이 프로젝트·원하지 않는 생성물·내 항목·사용 0) 20개씩, 각 묶음의 `DeleteClips` 바로 전에 사용 값을 한 번 더 읽어 0 인 것만 지운 뒤 목록 되읽기**로(실측: 한 개씩 ~170ms, 20개 한 번 6ms). 지운 수 = 되읽어 사라진 것. 리졸브가 쓰는 중인 클립을 DeleteClips 로 지울 때의 동작은 미확인 — 그래서 바로 전 사용 값 확인을 둔다.
5. **남은 작은 고침** — ① 미리 캐시: 대기열을 기다린 뒤 이미 받은 ID 를 다시 걸러 빈 요청을 보내지 않는다(1단계 리뷰 P3) ② 트리·자동 순서: 빈 만들기 도우미 안 실패 시험에 keep_current 경우 추가(그 기록의 리뷰 P3).
