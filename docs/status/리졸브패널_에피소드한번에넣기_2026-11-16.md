## 왜 느렸나 (코드)

`useResolvePanel.ts` `fillEpisode` 가 '컷 하나 받기 → 그 컷 prestage 조각을 대기열에서 끝날 때까지 기다림 → 다음 컷 받기'로 한 줄이다(:658-697, 받기 전마다 대기열 비기 기다림 :664). 자식 `_panel_prestage` 도 컷마다 따로 ImportMedia 하고(컷마다 `_panel_stage_import`), 다른 빈에 있으면 조각마다 지금 빈을 빌린다 → 컷 수만큼 자식 실행·빌리기·깜빡임.

## 설계

**A — 화면(프런트)**
1. **받기를 멈추지 않기**: 에피소드를 고르면 받을 것을 컷 순서대로 끝까지 받는다. 받기 사이에 리졸브 쪽 미리 띄우기 조각을 끼워 기다리지 않는다(받는 동안 prestage 를 보내지 않음). 선택의 일(stageCut 의 cache·target·stage)이 먼저라는 규칙과 seq 로 끊기·[저장] 중 멈춤은 그대로. 동시 받기 수(3)는 그대로.
2. **다 받으면 한 번에 넣기**: 받기가 끝나면 받은 컷들을 **항목 합 200개 안팎** 조각(합이 220 을 넘기 전까지는 묶어 작은 초과 허용 — e035 201개는 한 조각, 큰 컷 하나는 단독)으로 prestage 한다. 이름 뒤따르기는 모든 조각 뒤(지금과 같음). 새 선택이 seq 로 끊은 받기는 같은 판의 받기 끝에서 한 번 더 받는다(실패로 세지 않음). 조각 사이에는 선택의 일(stageCut)이 다음 조각보다 먼저이고, [저장]을 누르면 다음 조각을 보내지 않는다. '진전 없음' 판정은 받기·넣기 한 순회가 끝난 뒤에 하고, **진전은 다 찬 컷 수뿐 아니라 아직 안 찬 대상 ID 수가 줄어든 것도 포함**한다 — 스틸 상한으로 넘긴 항목은 진전이 있는 동안 같은 안정 구간에서 다음 빌리기로 이어 가고, 진전 없는 deferred 는 앞 작업처럼 빈이 바뀔 때까지 멈춘다. 빌린 조각이 끝나면 '두 번 연속 같은 빈' 셈을 처음부터 다시 해(다음 창은 새로 두 번 읽은 뒤 — 창이 잇달아 열리지 않게) 사람이 가만히 있는지 다시 확인한다.
3. **진행 표시**: 받는 동안 `· e035 받는 중 120/201`(항목 수), 넣는 동안 `· e035 컷 빈 채우는 중 n/31`, 다 차면 지움, 남으면 `· e035 컷 빈 n/31 · 남음 k`(앞 작업 규칙 그대로).
4. 앞 작업의 나머지 규칙(같은 에피소드 안 컷 바꿈으로 새 판 없음, borrow·borrow_bin_id·두 번 연속 같은 빈, 같은 판 안 다시 채우기, deferred 는 안정 구간마다·그 밖 실패는 판마다 1회, 진전 없으면 빈이 바뀔 때까지 멈춤, 받기 묶음 예외 격리, 판이 끝난 뒤 알림)은 그대로. 다시 채우기도 '남은 것 다 받고 → 한 번에 넣기' 순서.

**B — 리졸브 쪽(자식 `_panel_prestage`)**
1. **컷을 넘어 묶어 가져오기**: 조각 안에서 가져오는 자리가 에피소드 빈인 컷들(지금 빈 = 에피소드 빈이거나 빌려 채우기)의 새로 가져올 것을 모아, **영상·오디오를 먼저 컷을 넘어 한 묶음으로 정렬해 한 번의 ImportMedia**, 그 뒤 스틸은 한 장씩 가져온다(스틸을 한 호출에 섞으면 이미지 시퀀스로 합쳐지므로). 각 호출 직전에 지금 빈·에피소드 빈 기존 ID 엄격 읽기, 돌려받은 새 ID 만·에피소드 빈 안 확인 규칙 그대로. 고른 컷 직접 stage 의 묶음 순서(`_import_groups`)는 그대로. 지금 빈 = 그 컷 빈인 컷은 지금처럼 그 빈에 바로.
2. **짝짓기를 먼저 다 하고 옮기기**: 돌려받은 클립 ID 를 조각 공통으로 먼저 보관하고, 전부를 경로로 (컷, 항목)에 짝지은 뒤 **컷마다 MoveClips 한 번**(각 MoveClips 직전에 그 클립들이 아직 에피소드 빈에 있는지 다시 확인)·옮김 되읽기 → 그다음 표식 → 실패 정리·복구 기록. 배분 도중 예외에도 기록 누락·중복이 없어야 한다. 같은 정규화 경로가 조각 안 두 컷 이상의 **새로 가져올 후보**에 있으면 한 번의 가져오기에 섞지 않는다(첫 컷만 이번에, 나머지는 deferred — 다음 조각·다시 채우기에서). 앞 컷의 present 항목은 뒤 컷을 막지 않는다.
3. **빌리기는 조각마다 한 번**(앞 작업 규칙 그대로 — 조건부 되돌리기, borrow_bin_id 대조, 새로 가져올 것 없으면 전환 생략). **빌린 창 안에서는 영상·오디오 한 묶음 + 스틸 최대 10장까지만** 가져오고 나머지 스틸은 deferred 로 다음 창(다음 안정 구간)에 넘긴다(스틸 한 장 약 0.34초 실측 — 창을 수 초 안으로). 지금 빈 = 에피소드 빈일 때(빌리지 않음)는 스틸 상한 없음. 영상 위주 에피소드면 e035 기준 깜빡임 1번.
4. **미리 띄우기에서는 끌기 정보(drag_items)를 만들지 않는다**(화면이 안 쓴다 — 고른 컷 stage 는 그대로 만든다).
5. 조각 전체의 미처리 돌려받은 클립 추적·leftover·restore_failed·restored·처리 가능한 예외의 조건부 되돌리기·비정상 종료 한계는 앞 작업 그대로.

**안 바꾸는 것**: [저장]·adopt·NAS·자동 지우기 끔·끌기·릴리스 차단·target·settle·고른 컷 stage·이름 뒤따르기 규칙·받기 동시 수 3.

## 알고 가는 한계

- 처음 여는 에피소드는 **다 받을 때까지 빈이 차지 않는다**(Jay 가 고른 '한 번 기다린 뒤 바로'). 예상: 201개 받기 약 1~2분 + 넣기(Codex 추정 — 'mv test' 에서 잰다).
- 이미 받아 둔 에피소드도 넣기·표식 시간(201개 기준 수십 초, 추정)은 든다 — '보이기 먼저'(2단계)가 이것을 줄이는 후보.
- 조각이 커질수록 자식이 비정상 종료할 때 미처리 클립 수가 커진다(기록은 자식 응답 뒤 저장 — 앞 작업과 같은 한계).
- 조각을 처리하는 동안(넣기·표식) 패널 따라가기·컷 전환이 그만큼 기다린다. 앱의 '리졸브로 보내기'도 잠금이 풀릴 때까지 기다리고, 프로젝트 열기는 바로 `resolve_busy` 로 돌아온다(`resolve_status_runner.py` 변경 문). 쓰기 자식은 시간 제한이 없어(timeout=None) 시작한 조각은 끝까지 간다.
- 빌린 창 시간은 '영상 한 묶음 가져오기 + 스틸 최대 10장 × 약 0.34초'(추정 수 초) — 스틸이 많은 에피소드는 창(깜빡임)이 여러 번 생긴다.
- 컷을 넘어 묶은 영상 한 호출에서 파일 하나 때문에 ImportMedia 가 통째로 실패하면 그 조각 전체가 재시도 1회를 쓴다(리졸브가 일부만 가져오는지 통째로 실패하는지는 미확인) — 실측 항목.
- 1~2조각·깜빡임 1번 목표는 같은 경로 중복·실패·재시도가 없는 경우다.
