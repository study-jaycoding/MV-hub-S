# 리졸브 패널 — 이 PC 로 받아 두기 병렬 (2026-11-12)

owner: Claude(설계·구현, 세션 `85e432e7`) · reviewer: Codex(설계 검토·독립 리뷰, 명령줄) · status: 완료 · touched_paths: 아래 계약 · updated: 2026-11-12

## 지금(코드로 확인)

- `backend/app/services/resolve_panel.py` `cache()` — 받을 생성물을 **하나씩** 돈다. 생성물마다 `joined`(같은 생성물 요청 합치기) 안에서 허브 전체 잠금 `_prepare_lock` 을 잡고 `transfer._cached_source` 로 받는다.
- `_cached_source` — 이 PC `/media` 에 이미 있으면 바로 끝. 없으면 `media_cache.cache_url` 로 공개 CDN 에서 받는다(사설 대역 차단). `media_cache` 는 주소마다 잠금 + 잠금 뒤 다시 확인 + 임시 파일(`.part`, 고유 이름) → 이름 바꾸기 + 조각 스트리밍 + 받기 전 디스크 여유 확인, 받기는 스레드에서(`asyncio.to_thread`).
- `_prepare_lock` 은 `prepare`(NAS 복사)·`stage_items`(띄울 파일 경로 확인)도 같이 쓴다 — 그래서 미리 받던 큰 파일 하나가 끝날 때까지 고른 컷의 받기·띄움 준비가 기다릴 수 있었다(띄움 속도 기록의 '알고 가는 비용').
- 리졸브 쓰기(빈 만들기·가져오기·이름·지우기)는 이 일과 별개 — 그대로 하나씩(이번 범위 밖).

## 설계

1. `cache()` 를 **요청 하나당 일꾼 3개**가 목록 순서대로 하나씩 집어 받게 바꾼다. 결과는 요청 순서 그대로.
2. **패널 받아 두기(cache) 요청을 모두 합쳐 동시에 받는 수는 3개까지**(모듈 세마포어 `_CACHE_SLOTS`) — 미리 받기와 고른 컷 받기 요청이 겹쳐도 인터넷을 다 쓰지 않게. `prepare`·`stage_items` 의 받기는 이 상한 밖이고 지금처럼 `_prepare_lock` 으로 하나씩이다(그래서 순간 최대 = cache 3 + 그쪽 1, Codex 1차 P2).
3. 받기는 `_prepare_lock` 을 잡지 않는다 — `prepare`·`stage_items` 는 지금처럼 그 잠금. 같은 파일을 동시에 받으려 하면 `media_cache` 의 주소 잠금이 한 번만 받게 한다. 그 위에 **패널 쪽 원본 주소 차례 `_source_turn`**(구현 리뷰 1·2차 P2): `_cached_source` 가 처음 받으려는 http 주소(`file_path` 가 http 면 그것, 아니면 `source_url`)마다 잠금 하나 — cache 는 차례 → 자리 → 다시 확인 → 받기, `prepare`·`stage_items` 도 원본 받기를 같은 차례 안에서 한다(`_prepare_lock` → 차례 순, cache 는 차례 → 자리 순이라 교착 없음). 그래서 cache 가 `media_cache` 잠금 안에서 남의 받기를 기다렸다가 다시 확인 없이 받는 일이 패널 안에서는 없다. 쓰는 수가 0 이 되면 사전에서 지운다. `stage_items`·`prepare` 는 차례를 받은 직후 `check_context`(구현 리뷰 3차 P2).
10. **받기 직전 확인 칸 `before_download`**(구현 리뷰 3차 P2 — 패널 밖 기능, 예: 보내기·라이브러리가 같은 주소를 `media_cache` 로 받는 중이면 cache 는 그 잠금 안에서 기다리므로 `_source_turn` 만으로는 못 막음): `media_cache._cache_http_url_result` 가 **주소 잠금을 잡고 완성 파일·실패 기억 확인을 지난 뒤, 실제 받기 직전에만** 호출자가 준 `before_download()` 를 부른다. 그 예외는 받기 없이 그대로 올라가고(일시 실패로 바꾸지 않음) 잠금 표는 `finally` 로 비운다. `cache_url`·`cache_url_result`·`resolve_transfer._cached_source` 는 이 인자를 그대로 넘기기만 한다(기본 None = 지금과 같음 — 다른 호출자 동작 그대로). 패널 cache 는 `before_download` 로 `check_context`(계정 바뀜 → AccountChanged) + stale 이면 내부 표시 예외 → 그 생성물은 None(시작 0).
4. 자리(세마포어)는 **`joined` 의 주인 작업 안에서만** 잡는다(합류한 요청은 자리를 안 잡고 결과만 기다림). 순서 = 자리 잡기 → `check_context`·stale 다시 확인 → `_cached_source`. 자리를 기다리는 사이 seq 가 올랐으면 시작하지 않는다.
5. **이미 이 PC 에 있는 파일**(`/media/…` 이고 파일 있음)은 자리를 기다리지 않고 바로 '받음'으로 — 큰 파일 셋이 자리를 쥐고 있어도 고른 컷의 이미 받은 파일 결과가 늦지 않게(별도 Claude 1차 P3).
6. **멈춤은 '새로 집지 않기'로만** — 일꾼을 취소하지 않는다. 계정이 바뀌면(AccountChanged) 그 일꾼은 오류를 적어 두고 끝나고, 다른 일꾼은 새 항목을 집지 않으며, 받던 것은 끝까지 기다린 뒤(자리·주소 잠금을 그때까지 쥠) `cache()` 가 AccountChanged 를 올린다. `cache()` 는 모든 일꾼이 끝나기 전에는 결과도 오류도 돌려주지 않는다. 취소하면 스레드 다운로드는 계속 도는데 자리·잠금만 먼저 풀려 상한이 깨지고, `joined` 에 합류한 다른 창이 CancelledError 를 받기 때문(Codex·별도 Claude 1차 P2). 요청 끊김은 라우터의 `run_non_abandon`(`resolve_queue.py:17-33`, 안쪽 작업을 shield)이 막는다.
7. 그대로 지키는 것: 생성물마다 받기 직전 계정·허브 확인 · 새 선택이 seq 를 올리면 **새로 시작하지 않음**(받던 것 최대 3개는 끝까지 — 캐시에 남음, 결과에 들어감) · 같은 생성물 요청은 `joined` 로 하나(앞 요청의 주인이 stale 로 None 을 돌려주면 지금 요청이 stale 이 아니면 다시) · 한 생성물 실패는 그 생성물만 failed.
8. 동시 수 3 — 상수 하나(`_CACHE_PARALLEL`). 실측으로 정한 값이 아니라 Jay PC 인터넷을 다 쓰지 않을 보수적인 값(추정).
9. 알고 가는 한계: 빠른 길은 `/media/…` 경로만 본다 — `file_path` 가 http 주소인데 이미 받아 둔 파일(`media_cache.cached_rel_for`)은 자리를 기다린다(빈도 미확인, 별도 Claude 2차 P3). 또 디스크 여유 확인이 파일마다 따로라(`media_cache.py:365`) 큰 파일 셋이 각자 통과해 합계가 넘칠 수 있다 — 16MB 마다 다시 확인하고 `.part` 를 지워 파일이 깨지지는 않고 그 파일이 실패로 끝난다(실측 때 실패 수를 본다).
