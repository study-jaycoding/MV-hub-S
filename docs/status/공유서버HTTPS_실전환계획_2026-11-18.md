## 한 줄 결론

**"함부로 못 바꾼다"는 판단이 맞다 — 지금까지 세 번 막힌 곳이 모두 '실제 서버 PC 에서 안 해 본 길'이었다.** 그래서 순서를 ① 남는 PC 로 **실전과 같은 릴리스 ZIP** 리허설(되돌리기 연습 포함) → ② 그 결과로 Jay 가 날짜를 정함 → ③ 당일은 정해 둔 확인표대로, 15분 안에 핵심이 안 되면 바로 되돌림. 서두를 이유는 **팀 Comfy 키를 서버에 등록할 때** 커진다(그 전엔 사무실 망을 믿는 한 위험이 낮은 편).

## 1. 지금 상태 (직접 확인 · 2026-11-18 dev `9043a381`)

- 준비 끝: 1~4묶음·격리 리허설·전체 게이트 — main·현재 릴리스에 **꺼진 채**(`backend/app/services/shared_transport.py:17` `TLS_REQUIRED = False`).
- **한 앱 판은 http 서버와 TLS 서버 중 한쪽에만 붙는다**: 꺼짐이면 저장 주소(http)를 그대로 쓰고 https 는 시스템 기본 신뢰라 우리 자체 서명 서버에 실패(`shared_transport.py:44-47,58-61`), 켜짐이면 http 전송을 거절(`:93-97`). → 서버만 되돌리면 새 앱이 끊기고, 앱만 되돌리면 TLS 서버에 못 붙는다. 되돌림은 **서버와 앱을 짝으로** 해야 한다.
- 서버 TLS 스위치 = `%PROGRAMDATA%\MVHub\server-tls\server.pem`·`server.key` 둘 다 있으면 on, 둘 다 없으면 off, 하나만·`promote.pending` 이면 error(`tools/server_tls.py:55-85`). 인증서 명령은 `create`(언제나 next.* 만)·`promote` 두 개뿐 — **TLS 를 끄는 명령은 없다**(`tools/server_tls_cert.py:494-501`).
- **옛 앱도 전환 뒤 업데이트 알림은 받는다**: 알림센터가 60초마다 로컬 업데이트 상태를 읽고(`frontend/src/components/NotificationCenter.tsx:138,203`), 그 API 는 공유 서버가 아니라 NAS 를 읽는 이 PC 전용(`backend/app/routers/_proxy.py:611`). 다만 관리자가 쓴 '공지 글'(`/api/update-notices`)은 공유 서버를 거쳐 못 받는다(`NotificationCenter.tsx:145`).
- **공개본 되돌리기는 이미 있다**: 옛 판을 다시 배포하면 클라이언트가 그 판으로 내려간다(`backend/app/services/release_update.py:1022-1080` `rolled_back`, `:1417-1430`; 시험 `backend/tests/test_release_deploy_package.py:178`). 서버 관리 창(`tools/server_console/release_helper.py:172`)과 `release/select_release.ps1` 로 할 수 있다. **앱 업데이트 탭 [배포]는 공유 서버의 공지 항목을 읽어야 해서**(`backend/app/routers/release_update.py:127-151`) 서버·앱 TLS 가 엇갈린 순간엔 못 쓴다 → 당일·되돌림 공개는 서버 관리 창으로.
- **릴리스는 origin/main 에서만 만들어진다**(`release/make_release.ps1:622-625`) — 리허설용 다른 인증서를 실은 ZIP 을 따로 만들 길이 지금은 없다(J3).
- 서버 이사 도구는 TLS 서버의 이전을 **막는다**(`tools/server_move_easy.py:78,349,716`) — 전환 뒤 서버 이사는 새 인증서 절차가 생길 때까지 안 된다.
- 로그인 토큰은 서버 비밀값 서명·수명 2주(`backend/app/services/auth.py:26`), 운영용 비밀값 회전 명령은 없다(DB 복원 때만 회전, `auth.py:39-42`).
- 'TLS 접속 확인 목록'(설계 '실제 전환 완료 조건')은 **코드에 없다** — `tls_seen|TLS 접속 확인|tls_confirmed|tls_clients|X-MVHub-Version|client_version` 를 저장소 전체(node_modules·work·.venv 제외)에서 찾아 설계 문서 2장과 무관한 시험 이름 하나만 나왔다. 다만 비슷한 재료는 있다: 작업자 백업이 PC 별 기기 ID(`backend/app/services/worker_backup.py:356` `_device_identity`)와 앱 판(`:211,682`)을 서버 백업 세트에 남긴다(백업을 켠 PC 만).

실제 서버 PC 에서 **아직 안 해 본 것**(이번 계획의 표적): 서버 PC 의 신뢰 Git `openssl.exe` 존재 · 관리자 권한 `create`/`promote` 의 실제 ACL 경로 · SYSTEM 예약 작업 서버가 보호된 개인키를 읽고 TLS 로 뜨는지 · 감시기·관리 창·[관리 도구 갱신]·[Git 업데이트] stage 검사가 실물 TLS 에서 도는지 · 팀원 PC 의 실제 업데이트·접속 · 옛 판 앱의 실제 증상 · 브라우저 직접 접속.

## 3. 실제와 같은 리허설 (B)

**장비**: 남는 PC 1대 = 리허설 서버(이하 R서버) · 팀원 역할 PC 2대(가 = 업데이트할 PC, 나 = 옛 판 그대로 둘 PC) · Jay 관리자 권한.
**실사용 보호(먼저)**: 세 PC 는 실서버에 닿지 않아야 한다 — 별도 스위치(추천) 또는 세 PC 에 192.168.1.171 차단 규칙(J4). 앱의 공유 서버 기본값이 실서버라서(`backend/app/services/shared_server_config.py:8`) **첫 실행 전에 주소를 R서버로 바꾸고**, B0 에서 실서버 연결이 실패하는지부터 본다. NAS 의 실제 릴리스 폴더에는 쓰지 않는다(리허설 릴리스 폴더를 R서버 공유 폴더에 따로 — ZIP·표지·qualify 기록을 복사).
**R서버 설치**: 실서버가 지금 도는 판(Git 설치본)과 같은 커밋으로 시작해야 '옛 → 새' 길을 본다. R서버의 git 원격은 리허설용 미러(실서버·`MV-hub-S.git` 와 별개)로 두어 리허설 중 '다음 커밋'을 만들 수 있게 한다. `register_autostart.bat` 은 **R서버에서만 Jay 가** 실행(이 PC·실서버에서는 계속 금지). R서버 관리 창이 보는 릴리스 위치도 리허설 폴더로 둔다(실 NAS 아님 — 설정 위치는 설치 때 확인).

**리허설 ZIP = 실전 R2 ZIP 그대로(R-f, J3)**: 릴리스는 origin/main 에서만 만들어지고(`make_release.ps1:622-625`) 개인키는 서버 밖으로 못 나가므로, R2 의 신뢰 묶음에 **실서버 인증서와 R서버 인증서 2장**을 함께 넣어 한 ZIP 이 두 서버에 다 붙게 한다(묶음 2장은 릴리스 검사·회전 시험이 이미 통과 — 4묶음). Codex `01a1ed93` 2차 = `VERDICT: R-f`(조건부):
- 조건: R서버 인증서의 SAN 에 **실서버 IP·운영 DNS 이름을 넣지 않는다**(`--dns` 금지) — 그러면 R서버 키로 192.168.1.171 을 사칭할 수 없다(같은 CN 만으로는 이름 검증 통과 못 함, `server_tls_cert.py:322`).
- 손해: 전환 뒤 한동안 R서버 IP·`127.0.0.1`·`localhost` 에 대한 신뢰가 하나 더 생긴다 — 공유 서버 주소를 localhost 로 둔 PC 가 있으면 그 PC 의 loopback 을 가로챌 수 있는 R키 보유자가 사칭 가능(`backend/app/routers/publish.py:495`). 서버 관리 창의 loopback 요청은 설치된 `server.pem` 을 쓰므로 영향 없음(`tools/server_console/install.py:63`). 대응 = R키는 R서버에만·리허설 끝나면 삭제, **다음 릴리스에서 R서버 인증서 제거**(그 릴리스를 깐 PC 부터 효과 — 이미 새어 나간 키 사본은 삭제로 회수 못 함).
- 다른 안: R-g(make_release 에 리허설 모드를 새로 — 코드·검토 필요, 실전 ZIP 과 달라짐) · R-c(설치 뒤 pem 바꿔 끼우기 — 파일 지문 불일치(`tools/release_contract.py:54`, `update_release_contract.ps1:180`), 재설치·업데이트가 원래 pem 을 되살려 시험 조건이 유지 안 됨, '실제 ZIP 그대로' 증거가 사라짐 → 비권고).
- 리허설 완료 조건에 더할 것: 2장 묶음으로 **두 서버 모두 접속 성공** + **R서버 인증서만 내미는 서버로는 192.168.1.171 이름 검증이 실패**(B17).

## 4. 전환 당일 (D)

1. **하루 전 공지**: "N시에 서버 보안 연결(HTTPS) 전환. 그 뒤 업데이트 안 한 앱은 공유 기능만 끊기고 개인 작업은 그대로. 벨의 업데이트를 누르면 다시 붙음. 쌓인 공유는 업데이트 뒤 자동 처리."
2. **T−30분**: 서버 관리 창 정상(A1 상태)·R2 후보 qualify 통과·R1 이 NAS 에 남아 있음·서버 백업 한 번·Jay 가 서버 앞.
3. **T — 서버 먼저**: 관리 창 [끄기](서버·감시기·감독기를 함께 멈추고 예약 작업을 잠시 끔, `tools/server_console/power.py:192-211,323-327`) → 관리 창을 닫는다 → 승격 창 `tools\server_tls_cert.py promote` → **관리 창을 다시 연다**(열린 창은 연 때의 TLS 상태를 들고 있음 `tools/server_console/install.py:183-184` — Codex `01a1ed93` ③) → [켜기](`power.py:377-395`). 서버는 **예약 작업째 전체**가 다시 떠야 한다 — 감독기는 시작할 때 http/https 판정과 인증서를 고정해 두므로 자식 서버만 다시 띄우면 부족(`tools/server_activation.py:331`, `restart_server_task.ps1:103-119` 도 감독기까지 정리). 이 손 순서가 SERVER.md 의 '감시기 정지 → promote → 재시작 → 재개' 와 같은 효과인지는 리허설 B5 에서 확인.
4. **서버 TLS 확인**: 관리 창 로그인·상태 https·만료 날짜 · `server_tls.py --probe 8010` 0. 여기서 막히면 아직 아무 PC 도 R2 를 받지 않았으므로 서버만 되돌린다(5절 2).
5. **그다음 앱**: 서버 관리 창 [배포]로 R2 공개. 공개를 서버보다 먼저 하지 않는 이유 = 서버 전환이 실패해도 팀원이 R2 를 설치해 버리는 일을 막기 위해(Codex ①). 서버 전환~공개 사이 몇 분은 모든 PC 가 공유 기능만 끊긴다.
6. **핵심 확인(공개 뒤 15분 안)**: Jay 앱 R2 업데이트 → 로그인·공유 읽기·실시간·백업 · 팀원 1명 같은 확인. 일반 smoke·Git stage 통과는 실서버 TLS 성공의 증거가 아니다(Codex ③).
7. 하나라도 안 되고 원인이 15분 안에 안 보이면 **5절 되돌림**. 일부 PC 만의 문제면 서버를 되돌리지 않고 그 PC 만 본다.

## 5. 되돌리기 (몇 분 안에 http 로)

**원칙**: 서버와 앱을 짝으로 — 새 앱(R2)은 http 를 거절하므로 서버만 되돌리면 업데이트한 PC 가 모두 끊긴다.

1. 서버 관리 창 [배포]로 **R1 을 다시 공개**(공개본 되돌리기 — 후보 표지·공개 표지를 함께 R1 로 바꿈, `release_update.py:1058-1068`). 앱 업데이트 탭 [배포]는 이 순간 못 쓸 수 있다(1절). R2 를 공개하기 전(4절 4 단계)에 막혔다면 이 단계는 없다.
2. 관리 창 [끄기] → 창 닫기 → 서버 TLS 끄기 → 창 다시 열기 → [켜기](감독기 포함 전체) → `server_tls.py --probe 8010` 0(http).
   - 끄는 방법(J5): 지금 명령이 없어 손으로 하면 승격 창에서 `server.pem`·`server.key` 를 **둘 다** 같은 폴더의 `previous.pem`·`previous.key` 로 이름 바꾸기(하나만 바꾸면 error 로 멈춤 — 안전한 쪽, `tools/server_tls.py:60-85`). 다시 켤 때는 `previous.*` → `next.*` 로 되돌린 뒤 `promote`(previous 가 남아 있으면 promote 가 멈춤 `tools/server_tls_cert.py:434`, 폴더 허용 이름도 정해져 있음 `:151`). Codex 는 **`demote` 명령을 만들 가치가 있다**고 봄(관리자·짝·기존 파일 충돌·중단 복구 검사, 다음 promote 로 이어지는 규칙) — 그 전엔 감시기·서버·감독기를 멈춘 손 절차를 B13·B14 에서 실측해 굳힌다.
3. 각 PC 는 벨의 업데이트로 R1 로 내려간다(자동 아님 — 사람이 눌러 설치·재시작). 저장 신원은 http 그대로라(3묶음, `shared_connection.py:63`) 내려간 앱은 바로 붙는다. 서버 주소·포트를 고치며 되돌리지 않는다(Codex ⑥). 브라우저로 서버를 직접 열던 사람은 Secure 쿠키 때문에 다시 로그인해야 할 수 있다.

**R1 로 내려가도 안전하려면**(Codex ④⑤⑥ 반영):
- R2 = R1 + (공개 인증서·`TLS_REQUIRED = True`)만 — 사이에 DB 마이그레이션·설치기 계약 변경·다른 기능이 끼면 내려갈 때 로컬 DB 가 새 스키마인 채 옛 코드가 돈다. 그래서 C 단계에 **main 동결**(R1 판 커밋 뒤엔 TLS 커밋·문서만, Jay "병합"으로 통제)을 둔다(J9).
- R1 의 **ZIP·후보 기록·qualify 검증 기록을 NAS 에 함께 보관**(릴리스 정리 때 지우지 않음) — 검증 기록 없는 옛 판으로는 내려가기가 거절된다(`release_update.py:976-1003`). 내려갈 때도 설치기의 실제 DB 호환 검사를 통과해야 한다(`update_release_worker.bat:1508`).
- 리허설(B13)에서 **실제 두 패키지로 R1→R2→R1 왕복**을 한 번 해 본다.
**'되돌림 릴리스'를 미리 만들지 않는 이유**: 릴리스는 origin/main 에서만 만들어지고 판 번호는 만든 시각이라(`make_release.ps1:622-625`), R2 보다 새 'R2+꺼짐' 판을 미리 만들 수 없다. 대신 **이미 팀이 쓰던 R1 자체가 되돌림 릴리스**다(NAS 에 지우지 않고 둔다). R1 로 내려갈 수 없는 사정이 생기면(예: R2 에 꼭 필요한 다른 고침이 섞임) 그때 main 에 `False` 되돌림 커밋 → 새 릴리스 → 공개(수십 분, 리허설에서 시간 측정).

## 6. 확인 목록 — 'TLS 접속 확인된 계정·PC 와 판 / 아직 확인 안 된 팀원' (설계 초안, 코드 0)

없다는 근거는 1절. 초안:

- **서버 기록**: 인증된 요청이 실제 TLS 로 왔을 때(`request.url.scheme == "https"` — 서버는 `proxy_headers=False` 라 원격이 위조 못 함, 설계 D1) `(계정, 기기 ID, 허브 판, 마지막 시각, 처음 시각)` 을 작은 표에 갱신(같은 키는 10분에 한 번만 쓰기). http 요청도 `scheme` 칸만 달리 해 같이 남기면 **전환 전에 '누가 어떤 판인가'** 를 볼 수 있다.
- **허브 머리글**: 공유 서버로 가는 요청에 `X-MVHub-Hub-Version`(설치본 VERSION)·`X-MVHub-Device`(작업자 백업과 같은 기기 ID `worker_backup._device_identity` 재사용)를 한 곳(공유 전송 출구)에서 붙인다. 서버는 **표시용으로만** 쓰고 권한 판단에 안 쓴다(길이·문자 제한).
- **화면**: 서버 관리 창(또는 관리자 화면)에 '전환 확인' 표 — 승인된 계정 전체 vs 기록: 확인됨(계정·PC·판·시각) / 미확인(이름). 꺼진 PC 는 셀 수 없으므로 '0' 이 아니라 이름 목록으로 판단(설계 N4).
- **배포 순서 이점**: 머리글·기록은 TLS 와 무관하므로 **다음 일반 릴리스(R1)에 먼저** 실으면, 전환 전에 '대상 팀원 모두 R1' 을 확인하고 나서 서버를 바꿀 수 있다(되돌림 안전 조건과도 맞물림).
- 규모(추정): 서버 표 1개·미들웨어·허브 머리글·관리 창 표·시험 — 보통 일. 서버 DB 표 추가라 설계 합의·독립 리뷰 대상.
- 대안: 서버 백업 세트의 기기 ID·판으로 근사(백업을 켠 PC 만 보이고 TLS 여부는 모름) + 당일 손 확인.

## 8. 전환 뒤 — http 시절에 지나간 비밀

- 로그인 토큰·비밀번호: http 시절 토큰은 최대 2주 유효(`auth.py:26`)이고, 로그인 때 비밀번호도 평문으로 오갔다. **Codex 권고 = 전환 확인 뒤 팀 비밀번호 변경 + 다시 로그인**(2주 기다림·로그아웃만으로 대응하지 않음, 같은 비밀번호를 다른 곳에 쓴 사람은 그쪽도). 비밀번호를 바꾸면 그 전에 발급된 토큰이 전부 무효가 되는 장치가 이미 있다(`backend/app/repo/accounts.py:196-199` `password_changed_at`, 요청 때 검증 `backend/app/main.py:947`) — 새 코드 없이 된다. 서버 서명 비밀값(auth_secret) 자체는 토큰 도청으로 새지 않으므로 회전 도구는 필요 없다(유출 의심 때만 별도 절차). = J7.
- 팀 Comfy 키: 등록돼 있었다면 http 응답으로 배포된 적이 있으므로 전환 뒤 **새 키 등록 → comfy.org 에서 옛 키 폐기**([팀 키 검토](Comfy팀키_보안검토_2026-11-15.md) — 서버에서 지워도 복사된 키는 comfy.org 에서 폐기해야 무효, 관리 창 안내 `tools/server_console/comfy_key.py:39`).
- 서버 개인키: BackupCopy 는 백업 폴더 복제일 뿐 **TLS 개인키 복구 수단이 아니다**(`tools/backup_replicate.py:70`, Codex ⑨). 개인키는 서버 밖으로 안 나가는 설계라 **분실(서버 디스크 고장·재설치) = 새 인증서 발급 + 새 공개 인증서 릴리스**가 기본 방침(J8).
