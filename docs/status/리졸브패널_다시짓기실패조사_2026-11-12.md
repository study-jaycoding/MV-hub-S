## 결론

- **직접 원인(코드로 확인)**: 빠른 다시 짓기(`_sort_by_moving_bins`)가 꼬리 빈 셋을 루트 임시 빈으로 `MoveFolders` 한 직후 검사에서 걸렸고, 자동 되돌리기가 '기록한 ID 의 빈만 돌려놓고 이번에 만든 빈만 지운다'는 규칙이라 그 상태를 못 풀고 멈췄다. 남은 복구 기록이 그 뒤 모든 패널 쓰기를 막았다.
- **그때 리졸브 안 상태(남은 증거로 추정, 근거 강함)**: 옮긴 컷 빈 셋이 **원래 자리(E11)와 임시 빈 양쪽에 다 있는 '두 벌'** 이었다. 임시 빈 쪽은 새 ID 의 사본이었을 가능성이 크다.
- **왜 그때만 두 벌이 됐는지는 미확인.** 오늘 같은 순서로 다시 짓기 42번(실패 때와 같은 빈 트리 포함)을 돌려도 한 번도 안 났다 — 리졸브 쪽의 드문 경합으로 추정. 재현 조건은 확정하지 못했다.
- **추천 = A안**(되돌리기가 '원본이 멀쩡할 때의 빈 빈 사본'은 스스로 치우고, 실패하면 본 것을 기록에 남김) · `delete_empty` 는 **입구째 끄기**.

## 패널에서 이 길을 타는 때

- settle 이 앞 에피소드의 빈 컷 빈을 지운다 → 그 에피소드로 돌아오면 target 이 지운 빈을 다시 만든다. 남은 빈(쓰인 클립·사람 클립이 든 빈) **앞에** 들어갈 빈이 하나라도 있으면 순서가 깨져 빠른 다시 짓기(저장·DRP·`MoveFolders`, 한 번 1.3~2초 — 오늘 실측)를 탄다. 새 에피소드 빈이 기존 에피소드 앞 자리에 생길 때도 같은 길(뒤 에피소드를 통째 옮김).
- 실제 사용에선 꼬리 빈에 **클립이 들어 있다**(쓰인 클립이 남은 빈) — 11-12 실패처럼 빈 빈만 꼬리인 경우보다 무겁다. 클립 든 빈이 두 벌이 되는지는 미확인.

## 고칠 방향

### A안 (추천) — 되돌리기가 '빈 빈 사본'은 스스로 치우고, 실패하면 본 것을 남긴다

1. `_restore_after_failed_move` 에 한 갈래: 부모에 기록한 꼬리가 **ID·하위 트리 그대로 모두** 있고(처음 상태), 임시 빈 안에 남은 자식이 **기록에 없는 ID · 꼬리와 같은 이름 · 클립 0 · 하위 0** 뿐이면 → 그 사본만 지우고 임시 빈을 지운 뒤 처음 상태를 다시 확인 → 기록을 지우고 기존 느린 다시 짓기로 이어 간다. 그 밖(같은 ID 가 두 곳 · 사본에 클립·하위 빈 · 부모 꼬리가 달라짐)은 지금처럼 멈춘다.
2. 첫 이동 검사·되돌리기 실패 문구와 복구 기록에 **본 것**을 남긴다: `MoveFolders` 돌려준 값 · 임시 빈 자식(ID·이름) · 부모 자식(ID·이름). 다음에 나면 '새 ID 사본인지, 같은 빈이 두 곳인지'가 확정된다.

- 좋은 점: 11-12 와 같은 경우 사람 손 없이 풀려 패널이 막히지 않는다. [보내기]의 다시 짓기도 같은 코드라 같이 좋아진다. 지우는 것은 '원본이 멀쩡할 때의 빈 빈 사본'뿐이라 잃을 것이 없다.
- 한계: 꼬리의 클립 든 빈이 사본이 되면 여전히 멈춘다(실제로 나는지 미확인 — 2번 기록으로 알게 됨). 재현이 안 돼 가짜 미디어 풀 시험으로만 검증하고, 실기기는 정상 길 회귀만 본다. 사본을 지우면 `DeleteFolders` 가 다빈치 지금 빈을 옮기지만 target 이 끝에 지금 빈을 다시 맞춘다(`keep_current` 는 되돌리기가 있음) — 구현 때 시험으로 확인.
- 범위(예상): `backend/app/services/resolve_bridge.py` · `backend/tests/test_resolve_bridge.py`. 공통 위험 코드라 계약·Codex 합의·독립 리뷰.

### B안 — 패널이 다시 짓기를 거의 안 타게(settle 규칙) + A안 2

- settle 이 **남는 컷 빈(쓰인·사람·지금 빈)보다 앞 순서의 빈 빈은 지우지 않고**, 마지막으로 남는 빈 뒤의 빈 빈만 지운다. 돌아오면 빠진 빈이 늘 끝에 붙어 순서가 맞으니 저장·DRP·`MoveFolders` 를 타지 않는다(돌아오기도 다시 짓기 한 번만큼 빨라짐 — 실측 아님).
- 한계: 앞 에피소드에 빈 빈이 몇 개 남는다(11-12 Jay 요청 "Del 키처럼 한 번에 지우기"와 어긋남). 새 에피소드가 앞 자리에 생길 때의 다시 짓기는 그대로라 그쪽 실패는 못 막는다. 에피소드 빈 안의 사람 빈까지 따져야 해 settle 판정이 복잡해진다.
- 범위(예상): `resolve_bridge.py`(`_panel_settle`) · 시험.

- 추천 = A. 두 벌이 되는 것 자체는 리졸브 쪽이라 막을 수 없고, 막혔을 때 풀리는 길과 다음 실패의 단서가 먼저다. B 는 빈도만 줄이면서 보이는 동작을 바꾼다 — 돌아오기가 느리다는 말이 나오면 그때 더한다.

1. **빈 빈 사본 치우기** — `_sort_by_moving_bins` 가 첫 `MoveFolders` 직전에 미디어 풀 전체의 빈 ID 를 한 번 적어 둔다(GetSubFolderList·GetUniqueId 만 — 못 읽으면 적지 않음 = 사본 치우기 꺼짐). **첫 이동 단계(호출 예외 또는 바로 뒤 검사 어긋남)에서 실패했을 때만** 그 목록을 되돌리기에 넘긴다 — 첫 이동이 맞은 뒤 단계(새 빈 만들기·두 번째 이동·임시 빈 지우기)의 실패는 지금처럼(Codex 1차 P2). `_restore_after_failed_move` 는 기록한 꼬리 ID 를 부모로 돌려놓은 뒤, 임시 빈에 남은 자식 중 '이번에 만든 빈'이 아닌 것이 있으면 그것들이 **모두** 다음을 만족할 때만 사본으로 보고 지운다(하나라도 아니면 아무것도 안 지우고 지금처럼 멈춤): ⓪ 첫 이동 단계 실패라 목록을 받음 ① 그 빈의 ID 가 **첫 이동 직전 미디어 풀에 없던 ID**(사람이 다른 곳에서 옮겨 넣은 빈은 있던 ID 라 걸러짐 — Codex 1차 P1) ② 그런 자식들의 이름이 **꼬리 이름과 하나씩 정확히 맞음**(개수까지 — 11-12 흔적은 꼬리 셋 모두 사본, Codex 2차 P2) ③ 클립 0·하위 빈 0(엄격히 읽음, 읽기 실패는 비었음 아님) ④ 부모에 기록한 꼬리가 **모두** 같은 ID·같은 하위 트리(클립 ID 포함)로 있음. 판정을 모두 끝낸 뒤 하나씩 지우고, 지우기 바로 전마다 클립·하위 빈을 다시 엄격히 확인한다. ④는 그런 자식이 있을 때만 읽는다(평소 되돌리기 동작은 그대로). **남는 위험(허용)**: 빈 ID 훑기는 한순간의 사진이 아니라서, 훑기 시작부터 지우기까지(수백 ms) 사람이 꼬리 이름 **전부**와 같은 빈 빈들을 새로 만들거나 훑는 사이에 옮긴 뒤 임시 빈에 넣으면 그 빈 빈들은 지워진다 — 잃는 것은 빈 빈뿐이고, settle·옛 `delete_empty` 의 '확인~지우기 사이 동시 편집'과 같은 종류다(Codex 2차 P2). 대가: 빠른 다시 짓기마다 빈 목록 훑기 한 번(저장·DRP 내보내기 1~2초에 견주어 작을 것으로 **추정** — mv test 실측으로 확인, 큰 프로젝트는 미확인). 지운 뒤에는 지금처럼 임시 빈을 지우고 처음 상태(`_root_as_before`·`_restored`)를 다시 확인해야 기록을 지우고 기존 느린 다시 짓기로 간다. 같은 ID 가 두 곳에 보이거나(꼬리 ID 인 자식이 돌려놓은 뒤에도 남음), 사본에 클립·하위 빈이 있거나, 부모 꼬리가 달라졌으면 지금처럼 멈춘다. 빈을 지우면 다빈치 지금 빈이 옮겨 가지만 지금 되돌리기의 새 빈·임시 빈 지우기와 같은 일이고, 보내기는 끝에 처음 빈으로, 패널 target 은 목적 빈·`keep_current` 되돌리기로 다시 맞춘다(바뀌지 않는 동작).
2. **본 것 남기기** — 첫 이동 검사가 어긋나면 그 순간 읽은 것(`MoveFolders` 돌려준 값, 임시 빈 자식·부모 자식의 ID·이름)을 기록 사전에 담아 두고, **되돌리기가 처음 상태를 확인하지 못해 멈출 때만** 되돌린 뒤의 임시 빈·부모 자식(ID·이름, 못 읽으면 그 오류 글)과 실패 글을 더해 복구 기록 파일을 한 번 더 쓴다. 이 추가 쓰기가 실패해도(쓰기·직렬화 오류) 결과(`rebuild_recovery_needed`·leftover)는 같다(Codex 1차 P3). 화면·[보내기] 오류 글은 바꾸지 않는다(ID 목록이 길어 상태 줄에 부적합). 다음 보내기의 기록 풀기(`_settle_recovery_record`)는 추가 키를 보지 않는다.
3. **`delete_empty` 끄기** — 라우터 `UnstageIn.delete_empty` 필드·payload 줄·unstage 뒤 `forget_bin` 두 줄, 자식 `unstage` 분기 두 줄과 `_panel_drop_empty_bin` 을 지운다(몇 줄짜리라 주석 단계 없이). 라우터 모델은 모르는 필드를 무시하므로 옛 화면이 보내도 빈만 안 지운다. 프런트 API 타입의 `delete_empty`·`TargetResult.bin_deleted`(unstage 전용) 제거. settle 은 그대로.
