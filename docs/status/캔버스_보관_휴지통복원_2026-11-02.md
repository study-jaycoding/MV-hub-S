# 캔버스 보관 — 휴지통 결과도 그대로 불러오기 (2026-11-02, Jay 결정)

owner: Codex(구현)·Claude(설계·총괄) · reviewer: 구현·합의와 분리된 Claude 세션 · status: 완료 · touched_paths: 아래 계약 · updated: 2026-11-02

Jay: "보관은 save, 불러오기는 load. 내가 작업한 게 그대로 저장되고 그대로 불러들어 와지는 거다." 보관한 뒤 휴지통에 넣은 결과가 옛 보관본에서 어떻게 나올지 묻자 **"그대로 나오게"** 로 정했다. 지우고 나서 보관하면 지운 대로 열린다(씬에 없으니 해당 없음).

앞선 계약 `scene-keep-20261102` 의 "휴지통·삭제 이동 중인 것은 안 되살아나며" 중 **휴지통 부분을 이 결정이 대체한다.** 삭제 이동 중인 결과는 그대로 막는다. 영구 삭제한 결과가 다시 들어오는 동작도 같은 기준으로 그대로 둔다. 시험 `test_trash_tombstone_wins_over_matching_live_result` 의 `by_job=True` 도 이 결정이 대체한다.

## 설계

불러오기(`POST /api/scene-keeps/restore`)는 세 단계로 나눈다. 휴지통 [복원] 단추와 같은 `restore_from_trash` 를 쓰고, 봉투 내용으로 휴지통 결과의 새 행을 만들지 않는다. 그래서 태그·코멘트·공유·참조가 원래대로 돌아오고, 휴지통에서 빠지며, 두 벌이 되지 않는다.

**1단계 — 먼저 판정(읽기만).** 봉투 항목마다 꺼낼 휴지통 행을 정한다. 트랜잭션과 연결은 판정이 끝나면 닫는다(풀 연결을 재사용하므로 연 채로 복원 함수를 부르지 않는다).
- 그 결과에 살아 있는 완료 행이 이미 있으면(같은 id 또는 같은 job) 꺼내지 않고 그 행으로 잇는다.
- 후보 = 봉투의 id 나 job_id 가 맞는 휴지통 행. id 만 맞는 경우는 job 도 같아야 한다(둘 다 비면 같다). job 없는 항목은 id 로만 찾는다.
- 조건: `payload["generation"]["status"]` 가 done · `provider_terminal` 이 실패가 아님 · `_payload_has_usable_asset` 참(자산 판정은 이 함수 기준을 그대로 쓴다) · `trashed.creator_uid` 가 지금 계정의 작성자 집합에 들거나 NULL · 메인에 같은 id 행이 없음 · 삭제 이동 중 표식이 없음. 깨진 payload 는 그 항목만 후보에서 뺀다.
- 한 job 에 꺼낼 행은 하나다. id 가 정확히 맞는 행이 있으면 그 행, 없고 여럿이면 고르지 않는다. 봉투 전체로 봐서 같은 job 에 둘이 되면 고르지 않는다.

**2단계 — 꺼내기.** 고른 행을 하나씩 `restore_from_trash(id, account_uid=None)` 로 꺼낸다.
- 항목마다 `transition_lock` 을 잡고, 그 잠금 안에서 ① epoch 확인 ② **그 항목을 1단계 규칙으로 다시 판정**(연결은 닫는다) ③ 아직 꺼낼 대상이면 꺼낸 뒤 놓는다. 두 보관본을 동시에 열어도 뒤 요청이 앞 요청이 꺼낸 행을 본다. 쓰기 대기가 다른 요청을 묶지 않게 잠금을 들고 전체를 돌지 않는다. 전체 시한은 60초이고 넘으면 남은 항목은 꺼내지 않는다.
- 항목 하나가 실패하면 그 항목만 못 꺼낸 것으로 치고 계속한다.
- **B1 표식이 남으면 다르다.** 어떤 예외든(`sqlite3.OperationalError` 포함) 항목 실패 뒤 `generation_transfer` 표식이나 `prepared` 작업이 남았는지 보고, 남았으면 기존 `trash_transfer.reconcile` 로 정리해 미완료가 없을 때만 계속한다. 판단 기준은 오류 종류가 아니라 남은 표식이다. 정리도 실패하면 더 쓰지 않고 요청을 실패로 끝낸다(409 "잠시 뒤 다시 열어 주세요"). 다시 열면 이어진다.

**3단계 — 판정(`restore_keep`).** 규칙을 다음처럼 바꾼다. 매 요청 살아 있는 행을 다시 보므로 두 번째 열기도 같은 결과다.
- 삭제 이동 중 표식은 언제나 막는다(`rejected`).
- 살아 있는 완료 행이 있으면 잇는다. job 에 완료 행이 여럿이면 봉투 id 와 같은 행을 고르고, 없으면 `rejected`. 같은 job 의 휴지통 행이 남아 있어도 막지 않는다.
- 살아 있는 행이 없을 때 봉투로 넣는 것은 **휴지통에 같은 id 행이 없고, 같은 job 의 휴지통 행이 없거나 모두 실패로 확정된 행**일 때만이다(완료 행을 영구 삭제한 경우). 완료·미완료·상태 불명·깨진 payload 행이 있으면 `rejected`(빈 카드, 다음 열기에 이어짐). 실패 판정은 `payload["generation"]["status"]` 나 `provider_terminal` 실패로 한다.
- 그 밖의 규칙(같은 id 의 다른 작업·미완료 → `rejected`, 남의 서버 결과는 넣지 않음)은 그대로다.

응답 모양과 화면은 바꾸지 않는다. `restored` 는 봉투로 새로 만든 행 수 그대로다.
