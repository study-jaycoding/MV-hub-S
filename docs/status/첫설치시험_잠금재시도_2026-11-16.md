# 첫 설치 시험 — 파일 잠금이 걸리면 재시도 없이 실패하던 시험 장치 고침 (2026-11-16)

> [격리 리허설](공유서버HTTPS_4묶음_격리리허설_2026-11-16.md)의 전체 게이트 2회째(ef9ad1d9)에서 `test_first_install_bootstrap.py::…[ready_nonce_mismatch]` 하나만 실패했다. 단독으로는 같은 커밋·d36d9946 모두 3/3 통과.

## 확인한 것

- 게이트 실패 내용: `journal.db_mutation_possible False`(기대 True) · `runtime_checks 2` — 의도한 '준비 확인 불일치' 지점에 닿기 전, 부품 교체 단계에서 끝났다.
- Codex 읽기 전용 진단(`work/fix-designs/bootstrap-flake-diagnose-codex.md`): 1순위 = 실제 파일 잠금(검사기 등) + 시험 장치의 가짜 시계(`Get-Date` 를 부를 때마다 1분 전진)가 재시도 기한(15초, `update_release_worker.bat:299`)을 첫 실패에서 바로 지나게 함.
- 총괄 추가 확인: 재시도할 잠금 코드 `$script:RetryableMoveCodes = @(5, 32, 33)`(`update_release_worker.bat:237`)는 **함수 밖 한 줄**이라 함수만 꺼내 쓰는 시험 장치(`first_install_harness.ps1:9`, 꺼내는 초기화 구간은 117~150행)에서는 비어 있다 → 시험 안에서는 시계와 상관없이 잠금 오류가 한 번도 재시도되지 않는다. 실제 설치 프로그램에서는 이 줄이 실행되므로 제품은 정상.
- 재현(스크래치 사본, 저장소 안 건드림): staged 검사 때 다른 프로세스가 `*.next.*` 파일 하나를 1.5초 잠그게 하면 옛 장치는 게이트와 똑같이 실패(`The process cannot access the file…`, `Move-PathWithRetry` ← `Invoke-ComponentSwap`, runtime_checks 2, db_mutation_possible False). 시계만 고친 판도 같은 실패(재시도 코드가 비어서). 둘 다 고친 판은 재시도로 넘어가 의도한 실패까지 감(runtime_checks 3 · process_starts 1 · ready_calls 180 · 통과).
- 잠금 없이 20개 시나리오: 옛 31.01초 · 새 31.12초, 모두 통과.

## 구현·검증

- 고칠 것(시험 장치 한 파일): ① 함수 꺼내기 뒤에 워커 원문의 `$script:RetryableMoveCodes = …` 줄을 그대로 읽어 실행(줄이 없으면 경계 바뀜으로 멈춤) ② 가짜 시계를 '실제 시각 + 건너뛴 초'로 — `Start-Sleep -Seconds` 는 기다리지 않고 시계만 앞으로(3분 준비 대기 반복이 즉시 끝남), `Start-Sleep -Milliseconds` 는 실제로 기다림(잠금이 풀릴 시간).
- 시험 기록: bootstrap `aac45baa`(20개 시나리오 통과) · lock `d1a182cb`(같은 잠금 주입으로 HEAD 장치 = 게이트와 같은 실패, 고친 장치 = 통과 — 스크래치 `lock_proof.py`). 고친 파일은 미리 재현한 스크래치 판과 바이트 단위로 같음.
- 통합 검사: `check --stage integrate` 통과(지문 `0f76efb1`).
- Codex 리뷰(gpt-6-astra, read-only, 세션 `01a1e356`): **PASS** — 높음·중간 없음. 재시도 목록의 `$script:` 범위가 재시도 함수와 같음, 매개변수 있는 `Get-Date`·위치 인자 `Start-Sleep` 없음, 60초 `UtcNow` 대기는 모의 함수로 대체되고 90초 복구 대기는 호출되지 않음을 확인. 낮음 2(반영 안 함, 이유: 원래 시험 범위): ① 실제 기동·배수·런타임 검사는 여전히 모의 — 이번 고침은 잠금 재시도 재현성만 다룬다 ② 시나리오별 60초 제한은 여러 파일의 긴 잠금이 겹치는 최악 조건까지는 보장하지 않음.
