# Draft 표시·단추, 빠른 클릭, 탭 전환 지연 — 2026-10-22 (Jay 보고)

owner: Claude 총괄 · reviewer: Codex(묶음 검토 때) · status: 구현 중 · touched_paths: 아래 계약 · updated: 2026-10-22

Jay(원문 요지):
1. 캔버스 카드에는 Draft 표시가 있는데, 캔버스 '생성 결과' 창과 워크스페이스 격자에도 Draft 생성물이라고 보여야 한다. 워크스페이스 선택바에서도 Draft 생성물이면 Draft 생성을 할 수 있어야 한다.
2. 어셋·워크스페이스·카드를 빠르게 클릭하면 바로 선택되지 않고 천천히 누르면 된다. 일부러 딜레이를 줬나? 앱 전체에서 빠른 클릭·입력이 바로 반응하게 고쳐라.
3. 편집·공유·어셋·워크스페이스·캔버스 탭을 옮길 때의 지연을 재고 해결 방법을 검토하자(검토만).

## 1. Draft 표시·단추

- 표시: 캔버스 카드는 `HistoryBoardNode` 의 `.linb-draft`(라임 알약, 오른쪽 위, 마우스를 올리거나 고르면 숨김)로 보인다. 격자 카드(`GenerationCard` — 워크스페이스·'생성 결과' 창·폴더 창이 같이 쓴다)에는 없다.
- 단추: Draft 생성 단추는 캔버스·계보 선택바(`BoardSelectionActionBar`)에만 있다. 라이브러리 선택바(`LibrarySelectionActionBar`)에는 없다.
- `finishDraft`(App)는 활성 씬이 있으면 그 캔버스 카드에 결과를 쌓으려 하고, 카드가 없으면 실패한다 — 워크스페이스에서 부르면 활성 씬이 남아 있을 때 실패하므로 라이브러리 경로는 캔버스에 잇지 않는다.
- 고침: 격자 카드에 `.linb-draft`(격자 보기만, 남의 카드는 작성자 배지 아래, 호버·선택 때 숨김) · 단추를 `DraftFinishButton` 하나로 빼서 두 선택바가 같이 씀 · `finishDraft(generation, onCanvas = true)` — 라이브러리 바는 `false`. 고치기 전 판에서 새 시험 2개 실패 확인, 관련 시험 5파일 통과(영수증은 아래 계약).
- 남는 것: 워크스페이스에서 만든 1080p 결과는 캔버스 카드에 쌓이지 않는다(라이브러리에만). 목록 보기에는 Draft 표시가 없다.

## 3. 탭 전환 지연 실측 (검토만 — 코드 변경 없음)

방법: dev `db1d0b8e` 고정 사본 + `tools/browser_measure/servers.py`(시험 DB 읽기 전용 복사·CLI 차단·일회용 관리자 — 생성물 885개 소유) · 헤드리스 크롬 1680×1000 · 상단 탭 5개를 5바퀴 돌며 탭마다 Event Timing(클릭 → 다음 그림, INP)과 long-animation-frame(50ms 넘는 프레임, 스크립트·스타일·배치 분해), DOM 변화가 처음 300ms 멎기 전까지의 시간(내용 잠잠)을 잼. 배포 빌드(서버가 dist 를 서빙)와 개발 모드(Vite, API 만 격리 서버로) 둘 다.

| 탭(들어갈 때) | 배포 INP 중앙(최대) | 배포 내용 잠잠 | 개발 INP 중앙(최대) | 개발 내용 잠잠 |
|---|---|---|---|---|
| 워크스페이스 | 40ms (40) | 150ms (164) | 40ms (48) | 186ms (206) |
| 공유 & 리뷰 | 32ms (40) | 19ms (26) | 32ms (48) | 21ms (30) |
| 캔버스 | 24ms (32) | 23ms (25) | 32ms (32) | 31ms (119) |
| 편집 | 24ms (24) | 31ms (57) | 24ms (32) | 52ms (58) |
| Assets | 24ms (56) | 0 | 48ms (56) | 0 |

- 50ms 넘는 긴 프레임: 배포 0개 · 개발은 워크스페이스에서 2/5회 52ms 한 프레임(목록 virtua 콜백 20ms + 스타일·배치 38ms — 보이는 카드를 다시 붙이는 비용, 09-20 '보이는 카드 ~42장 마운트' 분해와 같은 정체).
- 결론(이 환경): 탭 전환은 1~3프레임 안에 끝나고 워크스페이스만 카드를 다시 채우는 데 0.15~0.2초가 든다.
- 이 실측이 **못 본 것**: ① 캔버스 씬은 서버가 아니라 브라우저 저장소(IndexedDB)에 있어 격리 프로필에는 Jay 의 큰 씬(수백 장)이 없다 — 캔버스 전환은 빈 보드로 잰 값 ② 편집 탭의 실제 타임라인 ③ 썸네일 그림이 늦게 차는 것(그림 받기는 DOM 변화가 아니다) ④ Jay 의 화면 크기·크롬 상태. Jay 가 느끼는 지연은 ①·③일 가능성이 크다(추정).
- 다음 측정 제안: Jay 의 씬을 [전체 내보내기] 파일로 받아 격리 프로필에 넣고 캔버스·편집 전환을 다시 잰다.
- 사고 기록: 개발 모드 측정용 Vite 를 사본에서 띄울 때 사본의 `node_modules` 가 dev 폴더로 이어져 있어, Vite 가 공용 의존성 캐시(`frontend/node_modules/.vite/deps`)를 08:42 에 다시 만들었다. Jay 의 5173 서버는 그 뒤에도 의존성 파일을 200 으로 서빙(확인) — 같은 소스·같은 의존성이라 내용도 같을 것(추정). 5173 화면이 이상하면 새로 고침. 다음부터 사본의 개발 서버는 `cacheDir` 를 사본 쪽으로 따로 준다.
