## 설계

### 1. 서버에 올리는 것 = '보이는 것 한 줄'(저장하는 순간 펼친 것)

문서 전체가 아니라 그 사람 화면의 **재생 배치를 펼친 것** — Jay ④ '보이는 컷만' 그대로.

```
{ v: 1, total, cuts: [ { name, folder, len, parts: [ { len, gen, job?, kind, head, speed } | { len, gap: true } ] } ] }
```

- `cuts` = 그 사람의 배치 순서(숨긴 컷 없음 · 숨기지 않은 비활성 컷은 있음 — 그 사람의 재생과 같다). `name` = 자리 이름(C0050 ①), `folder` = 실제 폴더(생성물 찾기용 — 반복 자리면 같은 폴더가 여러 번), `len` = 컷 길이.
- `parts` = 그 컷의 `visibleSegments`(맨 위에 보이는 것 하나씩, 빈 구간은 `gap`). **`head` = 그 조각이 시작하는 순간의 원본 시각**(`mediaAt(clip, from)`), `speed` = 속도(1 이면 생략 가능).
- 받는 쪽 배치(`shareLayout`)는 **조각마다 자리 하나**: 자리 열쇠 = `"<컷 번호>:<조각 번호>"`(반복 자리도 겹치지 않는다), `start` = 앞 조각들의 합, `len` = 조각 길이,
  클립 = `{head: 조각 head, speed, kind, len: 조각 길이}` 를 **그대로**(`clipHead`·`clipLen` 으로 다시 계산하지 않는다 — 다시 반올림하면 원본 배치와 어긋난다).
  그러면 `useEditFollow` 의 `head + (자리 안 시각) × speed` 가 곧 `조각 head + (컷 안 시각 − 조각 시작) × speed` 다. 상자 그리기는 같은 컷 번호의 조각을 묶어 컷마다 하나. [C1-3·C1-4]
- **재생용 클립의 열쇠와 미디어 찾기를 나눈다** [C2-B]: 재생용 `SlotClip` 의 `cut` = 자리 열쇠(`"i:j"`) · `slot` 없음 · `gen` = 원래 gen → `clipKey`(cut·slot·gen)가 조각마다 고유하다
  (같은 영상이 두 조각에 있어도 겹치지 않는다). 실제 폴더·gen·job 은 자리 열쇠 → `{folder, gen, job}` 표로 따로 들고 V0 링크·`sourceOf` 가 그 표를 본다. 이 객체는 편집 문서 파서에 넣지 않는다.
- 알려진 한계 [C2-H]: 조각마다 영상을 다시 싣는다(`pause → load`) — 같은 영상이 이웃 조각으로 이어지면 경계에서 끊길 수 있다. 한 컷 안의 같은 gen 은 `visibleSegments` 가 이미 한 조각으로
  합친다. 첫 구현은 합치지 않고 시험으로 끊김을 확인한다(합친다면 같은 소스·속도·원본 시각이 이어지는 조각만).
- 왜 펼치나: 받는 쪽은 그 사람의 폴더 트리·컷 순서·끔·트랙·판(v1~3)을 몰라도 된다. 이 **스냅샷 형식 v1 을 아는 빌드**면 읽는다. [C1-1]
- 순수 함수(새 `lib/editShare.ts`): `shareSnapshot(layout, doc)` · `serializeSnapshot`(키 순서 고정 JSON — 보낸 글자 그대로가 hash 원천) · `parseShareSnapshot`(아래 검사) · `shareLayout`.

### 2. 스냅샷 검사(서버 repo · 화면 `parseShareSnapshot` 같은 규칙) [C1-7]

`v === 1` · 모든 수 유한 · `len > 0` · `total ≤ 6시간` · `speed` 는 `SPEED_MIN~SPEED_MAX` · `head ≥ 0` · `kind ∈ {video,image}` · 글자 칸 길이 상한(name 200 · folder 1000 · gen/job 200) ·
`cuts ≤ 2000` · 컷마다 `parts ≤ 64` · `|Σparts.len − cut.len| ≤ 1e-6` · `|Σcuts.len − total| ≤ 1e-6` · **크기**(아래). 하나라도 틀리면 서버는 400, 화면은 'V0 을 읽지 못함'.

**크기 = 'ASCII 로 감싼 길이'** [C2-E]: 허브가 서버로 넘길 때 `raw_request` 가 `json.dumps(body)`(기본 `ensure_ascii`)로 다시 쓴다(`_proxy.py:279`) — 한글 1자 = `\uXXXX` 6바이트,
`"`·`\` = 2바이트. 그래서 상한을 **`len(json.dumps(data))` ≤ 256 KiB**(스냅샷 글자를 JSON 문자열로 감싼 ASCII 길이)로 정한다. 화면은 같은 값을 직접 센다
(코드 포인트마다: 0x20~0x7E = 1, 단 `"`·`\` = 2 · `\b\f\n\r\t` = 2 · 그 밖의 0x00~0x1F 와 **0x7F** = 6 · 0x80~0xFFFF = 6 · 보조 평면 = 12 · 앞뒤 따옴표 +2 — 화면의 JS 는
UTF-16 이 아니라 코드 포인트로 센다) — 브라우저→허브 본문은 이보다 작다(한글이 UTF-8 3바이트).
덧붙는 칸도 **같은 'ASCII 로 감싼 길이'로** 상한을 둔다 [C3-4]: `project_id ≤ 512` · `seq ≤ 4096` · `expect_account ≤ 1024`(합 5.5 KiB + 키 이름·괄호) — 글자 수가 아니라 이 길이라서
보조 평면 글자가 많아도 넘지 않는다. 요청 상한 = 256 KiB + 8 KiB = **264 KiB**.

### 3. 서버 저장(새 표 하나 · 마지막 한 벌)

```sql
CREATE TABLE IF NOT EXISTS edit_share (
  project_id TEXT NOT NULL, seq TEXT NOT NULL,
  owner TEXT NOT NULL,              -- 정규화한 계정 email(edit_doc_head 와 같은 까닭 — creator_uid 리맵에도 같다). 응답에 내보내지 않는다
  owner_key TEXT NOT NULL,          -- 응답용 열쇠 = 처음 저장할 때 만든 무작위 32자(덮어써도 유지 — email 을 대입해 맞출 수 없다) [C1-10·C2-G]
  owner_name TEXT, revision INTEGER NOT NULL CHECK(revision > 0),
  data TEXT NOT NULL, data_hash TEXT NOT NULL,
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  PRIMARY KEY (project_id, seq, owner));
CREATE INDEX IF NOT EXISTS idx_edit_share_key ON edit_share(project_id, seq, owner_key);
```

- 공유 서버의 본 DB(`folder_cover` 와 같은 곳) · `schema.sql` + `db_migrations.py`(`CREATE TABLE IF NOT EXISTS`).
- 저장 = **한 트랜잭션**에서 `data_hash` 가 같으면 그대로(revision 유지), 다르면 덮어쓰고 revision +1(UPSERT). owner·이름은 **인증 계정에서** 정한다 — 요청에 owner 칸은 없다. [C1-8·C1-2]
- 지우기는 이번에 없다(Jay 가 묻지 않음 — 미룬 것).

### 4. API — 새 접두사 `/api/edit-shares` · **로컬 목록에 넣고 핸들러가 직접 중계** [C1-1·C1-9]

| 요청 | 하는 일 |
|---|---|
| `POST /api/edit-shares/save` `{project_id, seq, data, expect_account}` | 내 것을 저장 → `{revision, data_hash, updated_at}` |
| `GET /api/edit-shares?project_id=&seq=` | 저장한 사람 목록 `[{key, name, revision, data_hash, updated_at, mine}]`(본문 없음 · `mine` = 요청한 나) |
| `GET /api/edit-shares/doc?project_id=&seq=&key=` | 한 사람의 것 `{data, revision, data_hash, updated_at}` — 없으면 **200 `{data: null}`**(404 는 '경로 없음'만 뜻하게) |

- 핸들러는 모드로 갈린다 [C2-A]:
  - **로컬 허브(AUTH off)**: ① 저장은 **먼저 `require_local_browser_context(request)`**(로컬 목록에 넣으면 미들웨어의 출처 검사를 건너뛰므로 — `_proxy.py:897`) ②
    `pinned_account_scope()` 안에서 `X-MVHub-Expect-Account` 를 **반드시** 대조(없거나 다르면 409 — `edit_docs._owner` 와 같은 규칙) ③ 계정 범위 안에서 **주소·토큰을 읽어
    `pinned_connection` 으로 고정**(지금 `asset_sync.py:78`·`mcp_v2.py:115` 과 같은 방법 — 새 잠금은 만들지 않는다) ④ `proxying()` 이면 `proxy_json` 으로 서버에 — 저장 본문에 `expect_account` = 고정한 계정 email ⑤
    **위임이 아니면 409 '공유 서버에 로그인하지 않아 서버에 저장할 수 없습니다'**(로컬 DB 에 저장하고 '서버에 저장됨'으로 보이는 일을 없앤다). [C1-9]
  - **서버 본체(AUTH on)**: 조회(목록·한 사람) = 인증 + 프로젝트 권한만(머리글 대조 없음 — `proxy_json` 은 머리글을 넘기지 않는다), 저장 = 본문 `expect_account` **필수**이고 인증 계정 email 과 같아야(아니면 409).
  - ③ 의 주소·토큰이 어긋난 쌍(새 주소 + 옛 토큰 등)으로 잡히는 위험 [C3-1·C4]: Codex 4차 — 토큰에는 서버 식별이 없고(`services/auth.py:143`) 응답 전에 토큰·본문이 이미 나가므로
    '다른 서버면 401'은 보호가 아니다(정정: 3판의 그 근거를 거둔다). 다만 이 위험은 **이 기능이 새로 만드는 것이 아니다**:
    - 공용 중계의 **기본 연결 조회 경로**(`_forward`·`proxy_json` — 이미 `pinned_connection`·명시 `base` 를 쓰는 호출은 예외)가 같은 두 설정을 따로 두 번 읽는다(`shared_connection.py:52-57`).
    - 쓰는 쪽도 따로 쓴다 — 로그인은 주소 → 토큰 순서(`publish.py:203-206`), **주소만 바꾸는 `set_shared_url`(`publish.py:681`)은 토큰을 그대로 둔다** → 경합이 없어도 그 뒤 모든 중계가 옛 토큰을 새 주소로 보낸다.
    - 이 기능은 그 공용 경로를 그대로 쓰고(새 읽기 방법·새 목적지를 만들지 않는다) 같은 위험을 **물려받는다**(새 스냅샷도 잘못 보내질 수 있는 대상에 든다). `expect_account` 는 '남의 이름으로 저장'만 막는다 — 목적지 보호가 아니다.
    → **연결 설정을 한 묶음으로 쓰고 읽기**(쓰기 트랜잭션 + 한 번에 읽기 + 주소만 바꿀 때 토큰 처리)는 앱 전체 중계의 일이라 **별도 작업으로 뺀다**(위험 기록 후보 — Jay 에게 보고).
- 권한(서버 repo 의 SQL 조건으로 — 목록·한 사람·저장 모두): 그 프로젝트가 있고 요청 계정이 **멤버이거나 전역 `read_all`** 일 때만(`folder_cover` 와 같은 범위).
  저장은 자기 것만(owner = 인증 계정). 스냅샷의 `gen`·`folder` 는 서버가 따라가 읽지 않는다 — 받는 화면이 **자기 팀 목록**(자기 권한)으로만 찾는다. [C1-2]
- 크기: 저장을 **POST** 로 두고 `UPLOAD_REQUEST_LIMITS` 에 `/api/edit-shares/save` = 264 KiB(위 'ASCII 로 감싼 길이' 256 KiB + 덧붙는 칸 8 KiB)를 넣어 본문을 읽기 전에 413. 허브·서버 같은 미들웨어. [C1-7·C2-E]
- 알림: `/api/edit-shares/save` 를 `_NOTIFY_NO_LIBRARY_CHANGE_PATHS` 에 — 저장이 라이브러리 다시 읽기를 부르지 않게. [C1-10]
- 화면의 오류 구분: 목록 GET 의 404 = '서버가 아직 이 기능을 모름(서버 업데이트 필요)' · 401 = 로그인 필요 · 403 = 이 프로젝트 권한 없음 · 409 = 계정이 바뀜(새로 고침)/서버 미연결 · 502·연결 실패 = 서버 연결 안 됨.
  어느 것도 '빈 목록'으로 숨기지 않는다. [C1-9]

### 5. 바뀜 알기 = 주기 조회(15초) + 창 초점 [C1 질문 3]

- **'서버에 저장' 방식이거나 '다른 편집 보기'가 켜져 있으면** 목록을 15초마다 + 창 초점이 돌아올 때 읽는다(V0 을 끈 채 서버에 저장 중이어도 다른 창의 저장을 따라오게). [C2-F]
  하나가 도는 동안 다음을 보내지 않는다. 계정·서버·프로젝트·시퀀스가 바뀌면 늦게 온 응답은 버린다.
- 고른 사람의 `revision` 이 V0 에 넣은 것보다 크면 'V0 · 이름' 알약이 라임. 새 WS 종류는 만들지 않는다.
- 내 '서버에 저장' 라임: 지금 보이는 것을 `serializeSnapshot` 한 글자의 hash ≠ **확인된 내 것 `{revision, hash}`** 의 hash → 라임. 확인된 내 것은 (a) 저장 응답(`data_hash` 가 **보낸 글자**의 hash 와 같을 때)과
  (b) 목록의 `mine` 행에서 오며, **revision 이 지금 것보다 작거나 같으면 적용하지 않는다**(같은 문맥 안에서만 — 늦게 온 목록이 저장 응답을 되돌리지 못한다). 저절로 다시 보내지 않는다(사용자가 누른다). [C1-8·C2-F]

- 시계(Jay ③ + Codex 질문 4): **'다른 편집 보기' 중에는 재생 시계의 끝 = max(내 끝, V0 끝)** — 방법은 **재생용 배치에 빈 꼬리 자리 하나를 붙이는 것** [C2-C]:

  - 엔진은 **최소한만 고친다** [C3-2]: 엔진이 범위가 바뀔 때·내릴 때 적어 두는 재생 위치(`lastPos`, `useEditPlayback.ts:566·598`)가 꼬리 열쇠면 **내 끝(마지막 실제 컷, 그 컷 길이)**으로 적는다.

  - 꼬리가 줄어드는 때(V0 끄기·사람 바꾸기·최신 받기로 더 짧아짐): `settlePos` 의 '마지막 자리 −1프레임' 보정(`editTimeline.ts:643·662`)에 맡기지 않고, 재생헤드가 새 끝 이상이면
    `EditTab` 이 **새 끝 시각으로 정확히** `seek` 한다(새 배치를 엔진에 넘기기 전에 계산). [C3-3]
  - **꼬리 구간(시각 > 내 끝)에서의 위치 편집은 하지 않는다** [C3-3]: 마크 인·아웃·북마크 찍기·지우기·D(지금 컷)는 `owns` 거짓(키를 안 먹음 — 단축키 표의 넘김) + 한 줄 안내

  - 내 배치를 따라가는 판(타임라인 판·한 트랙 보기·클린 피드)은 시각 ≥ 내 끝이면 **명시적으로 비운다**(`posAt` 은 끝으로 잘라 마지막 화면이 남는다 · 꺼진 긴 클립이 비치는 한 트랙 판도). V0 판은 계속 V0.
  - 전체 반복 = 늘린 끝까지 · 마크 구간 반복은 그대로.
