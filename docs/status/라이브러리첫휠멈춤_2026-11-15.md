# 라이브러리 첫 휠 멈춤 — 원인 조사와 기각한 고침 (2026-11-15)

> 배포 후보 점검([Gate 6-A](배포후보_Gate6A_2026-11-15.md))의 넓은 실측에서 '라이브러리 끝까지 스크롤' 에 남은 긴 작업 1회 139ms 를 조사했다. **결론: 제품 코드는 바꾸지 않는다.** 시도한 고침(포스터 없는 영상 한 번에 하나씩)은 실제 사용 조건에서 오히려 나빠져 되돌렸다.

## 어떻게 쟀나

격리 H/S(시험 자료 읽기 전용 복사, 후보 `61eba19a` 빌드), 헤드리스 Chrome(실제 GPU — WebGL 렌더러 `ANGLE … RTX 4090 … D3D11`). 라이브러리를 연 뒤 끝까지 스크롤하는 동안 페이지 안에서 긴 작업(PerformanceObserver)·다음 쪽 목록 응답 시각·DOM 변경량을 함께 기록했다(`work\widemeasure\append_probe.py`, 측정기 자체 부하가 없는 판). 원인은 Chrome 추적(blink·cc·gpu)으로 펼쳤다(`first_wheel_probe.py`).

## 원인

- '다음 200장이 붙을 때' 라는 처음 기록은 틀렸다. 차가운 새 프로필 5회에서 다음 쪽 도착 20번은 긴 작업과 한 번도 겹치지 않았고, 긴 작업은 **라이브러리를 연 뒤 첫 휠 80~350ms 안**에 났다(5회 중 2회 271·188ms).
- 추적: 98ms 중 74ms 가 주 스레드의 `LayerTreeHost::WaitForCommitCompletion`(화면 확정 대기)이고, 그동안 GPU 프로세스의 래스터(`RendererRasterWorker` 77ms)·ANGLE 작업·영상 해독기 스레드(COM STA 72ms)가 바빴다. 스크립트는 1ms 아래.
- 첫 화면에 포스터 없는 원격 영상(`MediaThumbnail` 'video' 갈래, `<video preload="metadata">` 로 원본 해상도 첫 프레임 해독) 4개와 포스터 있는 영상 6개가 있다. 그림 썸네일은 256×143 이라 무게가 아니다. 공개판 `3d0ff280` 에도 같은 코드다(회귀 아님).
- 즉 **새 브라우저 프로필의 차가운 시작 비용**(빈 GPU 셰이더 캐시 + 영상 해독기 첫 준비)이다. 같은 프로필을 다시 쓴 '두 번째 실행' 에서는 거의 사라진다(아래).

## 시도한 고침과 기각

포스터 없는 영상의 `<video>` 를 한 번에 하나씩 붙이는 자리 방식(첫 프레임·오류·4초에 넘김)을 만들어 같은 조건에서 비교했다.

| 조건(n=5) | 옛 빌드(후보 그대로) | 한 번에 하나씩 |
|---|---|---|
| 차가운 새 프로필 — 100ms 넘는 긴 작업 | 271·188 (2회), 87 | 199 (1회), 68·82 |
| 같은 프로필 다시 실행(실제 두 번째 실행) | **106 (1회, 다음 쪽 도착 18ms 뒤) · 나머지 4회 0** | 131 (1회) · 80·76·55 · 0 |

- 고친 빌드는 긴 작업 구간에서 영상 해독기 스레드가 사라졌지만 GPU 래스터 대기가 남았고, 실제 사용 조건에서는 자리표시→영상 교체가 스크롤 중에 이어져 긴 작업이 더 자주 났다.
- Codex 리뷰(`01a1de90`, gpt-6-astra 읽기 전용)도 CHANGES — 중간 2: React StrictMode 에서 정리 때 넘긴 자리를 무효화하지 않아 영상이 다 붙음(재현), 기다리는 동안 올린 마우스는 나중에 영상이 붙어도 재생하지 않음.
- 그래서 고침을 되돌렸다(dev 프런트 변경 없음). 시험 파일은 `work\fix-designs\rejected-mediaThumbnailFirstFrame.test.tsx` 에 근거로만 남겼다.

## 남은 것

- 실제 두 번째 실행 조건에서 5회 중 1회 106ms(다음 쪽 도착 18ms 뒤). 같은 조건에서 추적을 켜고 9회 다시 잡으니 긴 작업 7건이 모두 `Commit`(주 스레드가 GPU 래스터를 기다림) 33~100ms 가 대부분이고 스크립트는 1.1ms 이하, 직후에 새 줄의 썸네일 요청이 따랐다. 다음 쪽 도착과 겹친 것은 0건 — **새 줄이 화면에 들어올 때 썸네일을 GPU 로 올리는 브라우저 단계**이고 다음 쪽 붙이기·스크립트 탓이 아니다(추적은 그 자체로 긴 작업을 늘린다). 차가운 첫 실행(업데이트 직후 첫 화면 등)에는 첫 휠 100~270ms 가 한 번 날 수 있다 — Chrome 의 GPU 셰이더 캐시·영상 해독기 준비 비용.
- 근본 개선 후보(이번에 하지 않음): 포스터 없는 원격 영상에 포스터를 갖추기(서버가 원격 원본을 받지 않는 현재 규칙과 충돌 — `frontend/src/lib/media.ts` `mediaThumbUrl`).
