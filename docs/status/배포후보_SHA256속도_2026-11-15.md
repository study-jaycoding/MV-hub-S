# 배포 후보 — JS SHA-256(`sha256Js`)이 느려 확정·편집 열기마다 50~100ms 멈추던 것 (2026-11-15)

## 무엇을 찾았나

[미러 지문 중복 계산 고침](배포후보_미러지문중복_2026-11-15.md)(`64b45a50`) 뒤 같은 조건으로 다시 잰 넓은 실측(후보 `3089d245`, 격리 S, 헤드리스, 5회)에서 휠 확대·카드 이동의 긴 작업은 0 이 됐지만, 휠 축소·판 이동·카드 선택에는 확정마다 바뀐 씬 하나를 해싱하는 50~100ms 가, '편집 열기'에는 회마다 약 55ms × 2 가 남았다. CPU 상위는 모두 번들의 `Gf` = `frontend/src/lib/editShare.ts` `sha256Js`.

- `sha256Js` 는 보안 문맥이 아닌 화면(공유 서버에 http LAN 주소로 붙은 화면)의 대체 계산이면서, 씬 미러 출처(`sceneBackup.ts`)·편집 백업 복구 표시(`editDocBackup.ts`)·씬 공책 닫기 직전 본문(`sceneNotebook.ts`)·Comfy 입력 지문(`sceneComfyInputs.ts`)이 **동기로 직접** 부른다 — 편집 백업은 공책 허브에서도 탄다.
- 느린 까닭(코드): 안쪽 64회 반복마다 8칸 배열을 새로 만들어 맞바꾸고(`[k, g, f, …] = [g, f, …]`), 블록마다 배열 구조 분해·`forEach`, 바이트마다 `forEach` 콜백으로 전체 메시지를 낱말 배열에 옮긴다.

## 고침

값은 그대로, 계산만 빠르게 다시 쓴다(FIPS 180-4 그대로).

- 맞바꿈은 지역 변수로, 블록 단위 낱말은 `DataView.getUint32`(빅엔디언)로 원본에서 바로 읽는다. 꼬리(마지막 불완전 블록 + 0x80 + 비트 길이)만 64 또는 128바이트 새 버퍼로 만든다.
- 시험: 기존 표준 값·블록 경계·한글·보조 평면·큰 글자 비교에 더해, 바이트 길이 0~200 전부와 버퍼 중간을 가리키는 바이트 배열(`subarray`), 수 MB 무작위 바이트를 `crypto.subtle` 과 견준다.

## 리뷰·확인

- 속도(node, 5MB 같은 바이트): 옛 판 약 230~245ms → 새 판 약 68~70ms, 해시 같음.
- 독립 리뷰 Codex `01a1dd90`(읽기 전용) PASS — 실제 소스를 변환해 Node SHA-256 과 407개 입력·2^29+1 바이트까지 대조해 모두 일치. [낮음] 2GiB 이상에서 `length >> 6`·`whole << 6` 이 음수(옛 판도 대용량 길이 한계는 있었음) → `Math.floor(length / 64)`·`whole * 64` 로 고침, 같은 세션 재확인 PASS(0·2^29·2^31·2^32 주변 715개 길이를 BigInt 기준과 대조).
- 시험 기록 6개: editShare 시험 · 옛 구현으로 되돌려도 같은 시험 통과(시험이 값만 본다) · sha256Js 를 쓰는 5개 파일 · 프런트 전체 · 빌드 · 경계 검사.
- 화면 효과는 후보를 이 커밋으로 옮긴 뒤 넓은 실측으로 따로 잰다.
