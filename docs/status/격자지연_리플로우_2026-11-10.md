**원인 = `composition-manage.css` 의 두 줄**(관리 창 전용인데 메인 앱 CSS 에도 실린다):

```css
.manage-window:has(> .work-root .work-table) > * { flex: 0 0 auto; }
.work-root:has(.work-table) > * { flex: 0 0 auto; }
```

'부모가 무엇을 품었으면(`:has`) 그 **모든 자식**(`*`)' 꼴 — 요소가 새로 붙을 때마다 크롬이 이 조건이 바뀌었을 수 있는 곳을 좁히지 못하고 문서 전체 스타일을 다시 계산하는 것으로 보인다(기전은 추정, 규칙과 비용의 관계는 위 실측). 같은 `:has` 라도 대상이 정해진 꼴(`body:has(.folder-peek) .sl-dockbar` 등)은 비용이 없었다.

## 고침

같은 자리(순서 유지)에서 `:has` 없는 규칙으로 바꾼다.

- `.manage-window:has(> .work-root .work-table) > *` → `.manage-window > .manage-tabs` — 작업 탭 표 보기에서 창의 자식은 배너(`position: fixed` 라 flex 무관)·탭 줄·`.work-root`(바로 뒤 규칙이 `1 1 auto` 로 덮음) 셋뿐이라 실제로 닿던 것은 탭 줄 하나다. 창이 flex 가 아닐 때(대시보드 등)는 효과 없음.
- `.work-root:has(.work-table) > *` → `.manage-dash.work-root > *` — 명시도 같음(0,2,0). `.work-root` 가 flex 인 것은 표 보기(`.manage-window > .work-root:has(.work-table)`)뿐이라 다른 보기에서는 효과 없음.

동등성(같은 페이지에 관리 창 모양 DOM 을 넣고 원래 규칙·대체 규칙으로 모든 상자 비교): 긴 표·짧은 표·완료·보드 네 보기 **상자 위치·크기 차이 0**. 계산값만 다른 곳은 배너(fixed)와 보드 보기 자식(부모가 flex 아님)의 flex-shrink — 화면에 닿지 않는다.

## 남은 후보 (아직 안 고침 — Jay 판단)

1. **어셋 폴더 카드 격자가 전부 그린다**(300장 = 요소 6,400·그림 1,200). 4배에서 열 때 한 프레임 1.0~1.3초 멈춤(1배는 긴 프레임 0). 실측 페이지에서 화면 밖 카드를 건너뛰는 CSS(`content-visibility: auto` + 자리 높이 짐작)를 넣으면 최대 0.32~0.34초 · 스크롤 끊긴 프레임 78~84→3~32. 위험: 짐작 높이가 실제와 다르면 스크롤 막대·위치가 처음 지나갈 때 바뀔 수 있고, 선택 테두리(바깥 그림자)가 잘려 선택 카드만 예외로 둬야 한다. 가상 목록(virtua)으로 바꾸는 길은 키보드 이동·선택 코드까지 닿아 더 크다.
2. **깊은 목록·빠른 스크롤의 남은 긴 프레임** — 이제 대부분 React 의 줄 그리기(한 번 15~80ms, 4배)와 줄 높이 재기(ResizeObserver). 카드 한 장의 요소를 줄이는 쪽이라 범위가 크다. 카드의 컨테이너 쿼리(`@container`)는 고친 빌드에서 빼 본 2회가 엇갈려(긴 프레임 27→53 · 24→19) 원인으로 보지 않았다(결론 보류).
3. **창 복귀·공유 탭 15초 새로고침의 목록 처리** — 936장 다시 받기가 4배에서 한 프레임 최대 158~183ms(응답 처리 `Response.json.then` 180ms). 격자 스크롤 고침(`12f5baab`)의 '받은 만큼 다시 받기' 비용.
4. 어셋 스크롤 위치 저장 타이머의 `scrollTop` 읽기 강제 리플로우 — 60걸음에 9~17번, 한 번 약 1~3ms(4배). 작다.
5. 공유 탭 격자는 못 쟀다 — 격리 관리자가 팀 멤버가 아니라 빈 화면(사본에 멤버를 넣는 스크립트만 준비).
