## 0. 1판 → 2판 (Codex 사전 검토 반영)

1판(Claude)에 Codex 가 반례 C1~C7 과 빠진 범위를 냈다(원문: 스크래치 `codex_design/reply.md`, 요지는 아래 각 절에 [C#] 로 표시). 1판의 영구 기록 추천 (가) 장부 확장은 철회하고 Codex 추천 (나) 전용 표로 바꾼다 — 장부(미회수 출력)와 카드 연결 대기는 생명주기가 다르고, 장부 상한(전체 200)에 연결 대기가 쌓이면 새 실행이 막힌다. 1판 §2 의 "running 은 씬에 저장된다"는 틀렸다 — 저장할 때 `settleComfyRunning` 이 정규화한다(useSceneHistory·scenes.ts).

## 1. 목표

- L1. 창(앱)을 닫아도 **서버에 접수된 각 Comfy 실행**의 결과가 '내 작업'에 저장되고, 그 카드에 붙는다(캔버스를 가진 창이 다시 열리면).
- L2. 실행을 건 보드가 아니어도(탭을 옮김·떠 있는 창·새로 고침) 결과가 카드에 붙는다.
- L3. 새로 고쳐도 되돌리기 기록이 **마지막으로 저장 완료된 체크포인트까지** 이어진다.
- 제외: ① 묶음 실행(렌더 계획)의 조율 — 창이 닫히면 **아직 서버에 내지 않은** Comfy 단계·대기 중 복사본·다음 생성 단계는 시작되지 않는다(이번 완료 조건은 '접수된 실행의 결과 보존'이지 계획 완료가 아니다. 내지 않은 단계는 running 으로 예약하지 않는다) [6]. ② 다른 PC 의 자동 복구 — 새 표도 실행한 PC 의 로컬 DB 다. 다른 PC 에서는 '원래 PC 에서 확인 필요'로만 보인다 [2]. ③ 생성 위치의 폴더 고정 — 지금처럼 프로젝트는 실행 장부의 `asset_project_id`, 폴더는 정하지 않는다(동작 추가 금지) [4].

## 2. 지금 구조 (코드 확인)

(1판과 같음 — 요점) 창이 `/api/comfy/run`(즉시 job_id, `run_key` 는 `comfyApi.run` 안에서 생성) → 백엔드 스레드가 실행·출력 내려받기·장부(`run_journal`, 전체 200 상한) → 창이 `run_status` 폴링 → 창이 `save-to-library`(출력마다 생성물 커밋, finally 에서 장부 ack, 다 ack 면 장부 행 삭제. 서버의 실행 스냅샷이 프롬프트·파라미터·입력보다 우선) → 창이 보드 세션 `saveComfyOutputs`(보드 의존 명령 — 문서 포트 명령이 아님). superseded 판정 = 설정 지문 + 준비된 입력(연결 텍스트·엣지·고른 생성물·레퍼런스·상류 Comfy 실행 번호 — `runId` 숫자는 보드마다 다시 시작). 대표 = 성공한 복사본 중 가장 큰 copyIndex. 텍스트 출력은 장부 manifest·라이브러리 저장에서 빠진다.

## 3. 설계 A — Comfy 실행을 '접수 → 서버 마무리 → 아무 창이 반영'으로 (L1·L2)

**A0. 기능 표시.** 허브가 새 기능 표시 `comfy_canvas_runs_v1` 을 줄 때만 새 길을 쓴다. 한 실행의 길(옛/새)은 시작 때 고정한다. 표시가 없거나 불명확하면 옛 길 그대로 — 새 `/run` 으로 넘겨짚지 않는다 [6]. 새 필드 없는 `/run` 은 지금과 똑같다(옛 판 앱).

**A1. 실행 목록은 카드 밖, 씬 수준·되돌리기 밖** [C7]. 씬에 `comfyRuns: ComfyCanvasRun[]` — `{attemptId(UUID), runGroupId(UUID), copyIndex, cardId, configFp, inputFp, state, createdAt, jobId?}`. 되돌리기 스냅샷(cards·edges·groups)에 들지 않으므로 Ctrl+Z 가 지우거나 되살리지 않는다. 카드를 지워도 실행은 취소되지 않는다(결과는 '내 작업'에 남고 표식만 정리). 복사·붙여넣기·씬 가져오기·DB 백업 사본에는 `comfyRuns` 를 싣지 않는다(지금 `pendingGenerationAttempts` 를 지우는 자리와 같은 곳) [6].

**A2. 접수 순서** [C1·C6]. 실제 `/run` 하나마다 attempt 하나(단독 실행의 batch·계획의 복사본 각각). 창은 ① attemptId 를 만들고 → ② 입력 준비가 끝난 뒤(미디어 내려받기·seed 정하기·`onRunPrepared` 를 기다릴 수 있게 바꾼다) configFp·inputFp 를 정하고 → ③ `comfyRuns` 에 `submitting` 으로 저장하고 **저장소 확정을 기다린 뒤** → ④ `/run` 에 `canvas_run={attempt_id, run_group_id, copy_index, scene_id, card_id, config_fp, input_fp}` 와 `save_meta={name}` 을 싣는다(재전송 열쇠 = attemptId). ⑤ 확정 못 하면 보내지 않는다.

**A3. 서버 접수 기록 — 새 표 `comfy_canvas_run`** [2·C1]. 열쇠 `(account, attempt_id)` 유일. 스레드를 시작하기 **전에** 행을 만든다: 계정·실행 기기·attempt·group·copy·scene/card·지문·요청 지문·원래 job_id·상태(`accepted`). 같은 attempt 가 다시 오면: 같은 요청 지문이면 원래 job 을 돌려주고(살아 있지 않으면 표의 상태를 알려 줌), 다르면 409(실행 안 함). 영구라서 `comfy_run_keys`(24시간·1,000건)에 기대지 않는다. 장부(미회수 출력)는 지금처럼 따로 쓴다 — 장부 상한에 연결 대기를 넣지 않는다.

**A4. 서버 마무리** [C2·C3·4]. 작업 스레드는 출력을 다 받으면:
  - 지금 `save-to-library` 의 저장 문맥을 서버 함수로 뽑아(새 `usecases/comfy_save.py`) 스스로 저장한다. 프롬프트·파라미터·입력 증거는 **서버의 실제 실행 스냅샷**이 기준(지금 우선권 그대로 — 변환된 영상의 실제 바이트 계보 포함), 비밀값 제거 규칙 유지. 창이 보내는 것은 이름(`save_meta.name`)뿐.
  - **출력마다** 생성물 id(또는 텍스트 값)를 새 표에 먼저 기록하고, 그 뒤에 장부 ack 한다(순서: 생성물 커밋 → 표에 기록 → 장부 ack). 중간에 죽으면 다음 시작 때 표의 '저장 중' 행을 이어 받는다 — 이미 저장된 출력은 생성물 중복 검사(같은 파일·작성자, `BEGIN IMMEDIATE`)로 다시 만들지 않는다. 사용자가 지운 생성물은 되살리지 않는다(지운 것으로 기록).
  - **전체 출력**(텍스트 포함, 순서 보존)을 표에 남긴다. 저장할 미디어가 0개인 정상 완료(텍스트만)도 `saved` 다.
  - 상태: `accepted → running → saving → saved | failed{message} | needs_collect`(허브 재시작 등 — 지금 재시작 처리가 원격 취소하는 경우를 존중해 무조건 running 으로 되살리지 않는다).
  - 창이 살아 있어 `run_status` 로 기다리던 경우도 같은 결과(저장된 id 포함)를 받는다 — 창의 `save-to-library` 호출은 새 길에서 없앤다(두 번 저장 방지). 옛 길은 그대로.

**A5. 반영 = 캔버스를 가진 아무 창** [C4·C5·C6·6]. 새 훅 `useCanvasComfyRuns`(일반 생성 복구 옆, 2.5초, 숨은 창·떠 있는 동안 메인 창은 쉼):
  - 씬의 `comfyRuns` 를 모아 `POST /api/comfy/canvas-runs/resolve {attempt_ids}` → 각 attempt 의 상태·전체 출력·출력별 저장 id.
  - `saved`: 카드가 아직 있고 **configFp·inputFp 가 지금 카드와 모두 같으면** 결과를 붙인다. 다르면 붙이지 않는다(결과는 '내 작업'에). 붙이기는 **순수 반영 함수**(지금 `saveComfyOutputs` 의 반영 부분을 뽑음 — 보드 없이도, 문서 포트 명령으로)를 즉시 경로(살아 있는 보드)와 함께 쓴다. 같은 결과를 두 번 받아도 바뀌지 않는다(멱등).
  - 대표: 같은 runGroup 의 성공 결과 중 **가장 큰 copyIndex**(지금 규칙). 늦게 온 작은 copyIndex 가 대표를 되돌리지 않는다. 카드 runtime(running/done/failed)은 그 카드의 **가장 새 runGroup** 이 정한다 — 옛 group 의 실패가 새 실행의 running 을 덮지 않는다.
  - 반영과 '처리 완료' 표시(`comfyRuns` 의 그 attempt 를 `applied`)를 **한 번에 저장 → 저장소 확정·저장본 확인 → 서버에 확인(`/canvas-runs/ack`)** → 확인되면 `comfyRuns` 에서 지운다. 확인이 실패하면 다음 주기에 다시 보낸다(`applied` 로 남아 있으니). 서버는 확인받은 행을 '연결 완료'로 표시하고 상세는 정리하되 **최소 완료 기록은 남긴다**(늦은 재조회·옛 씬 사본 대비).
  - 비동기 응답 뒤, 문서를 바꾸기 **직전마다** 계정·연결·'지금 이 창이 씬을 쓰는 창인가'(떠 있음)를 다시 본다 — 요청 도중 캔버스를 띄우면 늦은 메인 창 응답이 쓰지 않는다 [6].
  - `failed`: 카드 runtime 실패 표시 후 표식 정리. `needs_collect`·`unknown`: running 과 다른 '확인 필요' 표시 — 자동 재실행 금지(과금). 회수는 설정 화면.

**A6. '생성중'과 중복 실행 막기** [3]. 새 길의 '생성중' = 저장된 `comfyRuns`(submitting/accepted/running/saving) + resolve 결과. 오늘의 창끼리 실시간 나눔(`shareWindowLive`)은 옛 길 실행에만 남기고, 새 길에는 '다시 조회하라'는 알림으로만 쓴다(단순 OR 금지 — 창이 닫혔다는 'gone' 이 실행이 끝났다는 뜻이 아니다). 단독 실행·계획 실행 진입점 모두 같은 카드에 진행 중 runGroup 이 있으면 새로 내지 않는다(표시만으로 막았다고 보지 않음).

**A7. 설정 화면 회수와 같은 길** [6]. 미해결 실행의 `collect`·`resave` 도 A4 의 저장·표 기록을 거친다(collect 가 만든 임시 job_id 와 원래 job_id 를 구분). `dismiss` 하면 표의 그 실행을 `dismissed` 로 — 캔버스는 표식을 정리하고 '정리됨'을 알린다.

**A8. 실행 소유권 식별자** [C4]. 보드 메모리의 숫자 `runId` 를 영구 판정에 쓰지 않는다 — 카드 runtime 의 실행 소유는 runGroupId(UUID)로. 입력 지문의 '상류 Comfy 실행 번호'도 runGroupId 로.

## 4. 설계 B — 되돌리기 기록 보존 (L3)

B1. **별도 작은 IndexedDB**(`mvhub-undo`) — 씬 DB 버전을 올리지 않는다(옛 창의 씬 저장에 영향 없게) [5]. 열기·읽기 실패·차단·시간 초과면 기록 없이 진행한다 — 앱 부팅을 막지 않는다.
B2. **불변 체크포인트 + 탭별 최신 포인터** [5]. 저장은 매번 새 UUID 의 체크포인트 레코드(`{account, sceneId, history, savedAt}`)로 쓰고, 그 탭의 `sessionStorage` 에 '씬별 최신 체크포인트 id' 포인터만 둔다. 복제 탭은 포인터를 복사받아 같은 체크포인트를 읽을 수 있지만, 이후 저장은 각자 새 레코드라 서로 덮지 않는다(복제 감지 불필요). 캔버스 창이 opener 로 받은 기록도 자기 새 체크포인트로 저장한다.
B3. **언제 남기나** [5]. 모든 편집 커밋·Undo·Redo·파생 저장 뒤에 체크포인트를 예약한다(지금은 파생 저장·언마운트 때만 메모리 store 에 남긴다 — `persist`·`restoreState` 도 남기게). 쓰기는 디바운스, 성공한 씬 저장과 짝지은 시점에 묶는다. 가려질 때·pagehide 는 마지막 보강일 뿐(완료 보장 안 됨).
B4. **계정은 예약 때 고정** [5] — 늦게 실행되는 쓰기가 그때의 계정으로 쓰지 않는다. 읽기·opener 받기·적용도 계정이 같을 때만.
B5. **어느 기록을 쓰나** [5]. 후보(메모리·opener 로 받은 것·IDB 체크포인트) 중 `lastCommit` 이 지금 씬과 같은 것만. 늦게 끝난 IDB 읽기가 그사이 받은(더 새) 기록을 덮지 않는다 — 적용은 '아직 그 씬의 기록이 없을 때'만.
B6. **삭제** [5]. 씬 삭제는 세대값을 올려 그 씬의 대기 중 쓰기를 모두 무효화한다(지금 tombstone 은 한 번만 막는다). 직렬 쓰기 큐.
B7. **크기·정리** — 씬당 200단계 그대로. 전체 바이트 상한·오래된 체크포인트 정리(정책 후보: 30MB·7일 미사용 — 측정값 아님). 지금 쓰는 체크포인트는 지우지 않는다.

## 5. 위험·실패 경계

- 두 번 저장: 새 길은 서버만 저장한다. 같은 attempt 재전송은 표가 막는다. 저장 재개는 생성물 중복 검사로 다시 만들지 않는다.
- 결과 유실: 생성물 커밋 → 표 기록 → 장부 ack 순서. 카드 반영 → 저장 확정 → 서버 확인 순서.
- 잘못된 카드: attempt·scene·card·configFp·inputFp 가 모두 맞을 때만.
- 영원한 '생성중': 서버 표가 상태의 원천. 창 메모리·실시간 'gone' 으로 끝을 짐작하지 않는다.
- 과금: 자동 재실행 없음(unknown·needs_collect 는 안내).
- 계정 섞임: `_comfy_request_scope`(계정 핀) · 프런트 계정 검사.
- 다른 PC: 약속하지 않는다(§1 제외).

## 9. 3판 공통 계약 (Codex 2차 `DESIGN-CHANGES` 반영 — §3·§4 보다 우선)

Codex 2차(같은 세션, 원문 스크래치 `codex_design/reply2.md`): 1차 필수 9개 중 2개(문서 저장 확정 후 연결 확인·A6 미제출 단계) 해결, 7개 부족 + 새 반례 R1~R5. 아래가 그 반영이다.

### 9.1 실행 데이터 (④ Codex 소유 · ⑤ 는 정규화 함수만 사용)

- 씬 수준 두 가지, 둘 다 **되돌리기 밖**:
  - `comfyRuns: ComfyCanvasRun[]` — 진행 중·처리 대기 attempt. `{version, originHubId, originDeviceId, attemptId, runGroupId, groupSeq, copyIndex, cardId, configFp, inputFp, localState: "reserved"|"submitted"|"applied", receipt?}`.
  - `comfyCardRuns: Record<cardId, {groupId, groupSeq, representative?: {groupId, copyIndex, attemptId}, settledState?}>` — 카드별 **현재 실행 묶음과 대표 결과**. ACK·`comfyRuns` 삭제 뒤에도 남는다 [R2]. `groupSeq` 는 카드마다 늘기만 하는 번호(UUID 는 순서를 모른다) — 새 묶음은 예약 성공 때 현재 묶음을 바꾸고, 낮은 groupSeq(옛 묶음)는 대표·상태를 못 바꾼다. 같은 묶음 안 대표 = 성공한 copyIndex 중 가장 큰 것, 작은 copyIndex 가 늦게 와도 되돌리지 않는다.
- 카드 runtime 의 실행 소유·상태는 **원본이 아니라 위 두 가지에서 계산**한다 [R4]. 되돌리기 스냅샷·`lastCommit` 비교·복원은 모두 같은 정규화 함수(`normalizeForUndo` — 카드의 실행 소유·상태를 뺀다, ④ 제공)를 쓴다. 결과·대표의 지금 되돌리기 보존 규칙은 그대로.
- 지문: `configFp` = 편집 설정(카드 Comfy 설정), `inputFp` = 준비된 입력에서 **자기 실행 소유를 뺀** 것(상류 Comfy 는 상류 카드의 `comfyCardRuns` 현재 묶음 id 로). 서버 `requestFp` = 무작위 seed 까지 적용한 실제 제출 내용. 셋을 섞지 않는다.
- 원본 식별: 프런트 항목에 `originHubId`·`originDeviceId` — 다른 PC 의 `not_found` 와 이 PC 의 '모름'을 가른다(다른 PC 는 '원래 PC 에서 확인 필요').
- 모든 새 id 사본(씬 충돌 사본 `scenes.ts`, `sceneArchive`, `sceneBackup`·서버 `scenes_backup`, 붙여넣기 `sceneInteractions`, 씬 가져오기)에서 `comfyRuns`·`comfyCardRuns` 를 뺀다 [R1].
- 옛 판 흡수(`sceneAbsorb`): **편집 내용 비교에서 두 필드를 빼고**, 옛 씬을 채택할 때도 지금 씬의 두 필드를 보존한다(attempt 별 합집합, comfyCardRuns 는 groupSeq 큰 쪽) [R1].

### 9.2 예약 (③④ Codex)

- `reserveComfyAttempt(sceneId, attempt)` = 저장소 연산(최신 문서에서 판단): 같은 카드에 진행 중(아직 처리 안 된) 묶음이 다른 groupId 로 있으면 `conflict`, 카드·씬이 없거나 지문이 지금과 다르면 `stale`, 저장 실패면 `storage_failed`, 아니면 `comfyRuns` 추가 + `comfyCardRuns` 현재 묶음 교체 → `reserved`. 두 창이 동시에 다른 묶음을 예약하면 최신 문서 위 연산이라 하나만 `reserved` [1차 1].
- **`reserved` 이고, 확정된 저장본에 자기 attempt 와 묶음 소유가 실제로 남아 있을 때만** `/run` 을 보낸다 — `confirmed=true` 만으로 보내지 않는다 [R1].
- `onRunPrepared` 를 기다린 **뒤에** 계정·입력·쓰는 창(떠 있음)을 다시 확인한다 [R4].

### 9.3 서버 기록·저장 (①② Codex)

- 표 `comfy_canvas_run`(attempt 단위) + 출력 표(또는 같은 표의 JSON 열) `(attempt_id, output_key) → {kind, text?, generation_id?, state}`.
- **출력 목록(안정 키)·확보한 텍스트를 먼저 기록**하고 출력별 진행을 갱신한다 [R3]. **완료 판정은 하나다(3차 ①)**: `saved` = 출력 목록이 확정됐고 모든 출력이 '저장됨(생성물 id)' 또는 '사용자가 지움' 또는 '텍스트 값 보존' — `isRunFullySaved(outputsEnumerated, outputs)`. 받지 못한 출력(`unavailable` — `provider_gone`·`detail_missing` 포함)이 하나라도 있으면 `saved` 가 아니라 `needs_collect`(미해결). 미수신 출력을 포기하는 것은 기존 `dismiss` 로만 명시적으로 끝낸다. 부분 실패를 `failed` 로 정리해도 남은 복구 근거(출력 표·장부)는 지우지 않는다.
- **생성물·asset 생성과 `(attempt, output_key) → generation_id` 기록은 같은 SQL 트랜잭션**(파일 내려받기는 밖) [R3]. 출력 연결 기록은 생성물 삭제(휴지통 이동)에 따라 사라지지 않는다 — 재개 때 연결 기록이 있으면 다시 만들지 않는다(지운 것 되살리지 않음).
- 재시작: `accepted·running·saving` 을 장부·출력 기록과 대조해 정산한다. 메모리 job 이 없다고 영구 `accepted` 로 두지 않고, 자동 재제출하지 않는다.
- 완료 영수증: `resolve` 는 `{attemptId, state, resultRevision, outputs, disposition?}`. ACK = `{attemptId, resultRevision, disposition: attached|superseded|card_missing}` — 같은 attempt·revision 의 반복 ACK 는 성공. 서버는 ACK 뒤 상세를 정리해도 최소 기록(`requestFp`·원래 job·`resultRevision`·`disposition`)을 남기고, 그 뒤 `resolve` 는 `linked`(명시)를 돌려준다. `dismissed`·다른 원본·일시 연결 실패·진짜 모름을 구분한다.

### 9.4 반영 (③④ Codex)

- `applyComfyResolution(scene, resolution)` = 순수 함수 — 최신 지문·묶음·groupSeq·copy 순서를 검사하고 카드 변경 + 적용 영수증을 함께 돌려준다. 살아 있는 보드의 즉시 경로와 복구 경로가 같은 함수.
- 로컬 `comfyRuns` 정리는 **영수증이 일치하는 항목만**. ACK 응답이 유실되면 다음 주기에 같은 영수증으로 다시 보낸다.

### 9.5 되돌리기 보존 (⑤ Claude — 위 계약 사용)

- 보장 범위를 줄인다 [R5]: **"생성 후 7일 안의 체크포인트로 복원"**. 체크포인트는 생성 후 7일 동안 지우지 않는다. 용량 상한(정책 후보 30MB)에 닿으면 **새 체크포인트 저장을 실패 처리**하고 기존 것을 지킨다(사용 중 판정 없음). 1·2판의 '7일 미사용 정리'·'사용 중 보호' 문구는 이것으로 바꾼다.
- 체크포인트 저장 계약(④ 가 영수증 제공, ⑤ 저장): `{account, sceneId, deleteGeneration, historyRevision, snapFp(normalizeForUndo 지문), history(예약 때 복제), sceneWriteReceipt}`. **그 편집의 씬 저장 영수증이 확정되고 snapFp 가 저장본과 같을 때만** IDB 에 쓰고, IDB 커밋이 끝난 뒤에 sessionStorage 포인터를 갱신한다. 이를 위해 `useSceneHistory` 의 `onChange` 가 그 저장의 `CanvasWriteReceipt`(또는 같은 확인 콜백)를 돌려받게 계약을 바꾼다(④ 의 `useCanvasSession`·`App` 연결, ⑤ 의 `useSceneHistory` 사용).
- 채택 규칙은 **부팅 복원과 창 인계를 나눈다(3차 ②)** — `adoptSceneHistory(target, candidate, gate)` → `"adopted"|"stale"|"mismatch"`. 공통 조건: 계정·snapFp 일치.
  - 부팅 복원(`gate.kind="bootstrap"`, `readEpoch`·`expectedLocalRevision`): 읽기를 시작한 뒤 **이 창에서 로컬 편집이 없었고 더 우선하는 인계도 없었을 때만** 채택. 처음에 만든 빈 기록은 '채택'으로 치지 않는다. 늦게 끝난 IDB 읽기는 그사이 받은 인계를 덮지 않는다.
  - 창 인계(`gate.kind="handoff"`, `handoffId`·`expectedLocalRevision`): 지금 진행 중인 창 인계(`handoffId`)와 맞고 **받는 창이 인계 뒤 따로 편집하지 않았으면** 기존 기록을 교체할 수 있다 — 이미 기록을 채택한 메인 창도 캔버스 창이 돌려준 기록으로 바뀐다.
  - `historyRevision` 은 **받는 창 안에서 편집이 있었는지** 보는 데만 쓴다. 서로 다른 탭·창 기록의 우선순위를 번호 크기로 정하지 않는다(같은 화면이어도 스택이 다를 수 있다).

### 9.6 구버전·다른 PC

- 구버전 호환 = **이미 시작된 실행의 완료·저장 호환**만. canvas 식별을 보내지 않는 구버전 창의 수동 새 실행까지 묶음 잠금이 막는다고 보장하지 않는다.
- 다른 PC 자동 복구 없음(§1). 다른 PC 의 항목은 '원래 PC 에서 확인 필요'.

### 9.9 4판 — 구현 착수 뒤 고친 두 곳 (§9.5 의 저장 방식보다 우선)

- **B 저장 방식(Codex 5차 `B-STORAGE-CHANGES`, 원문 스크래치 `codex_design/reply5.md`)**: 편집마다 전체 이력을 새 불변 레코드로 쌓으면 레코드 사이에 공유가 없어 30MB 상한에 금방 닿고, 그 뒤 7일 동안 보존이 조용히 멈춘다(추정 — 실측 아님). → 페이지 로드마다 새 `writerId`, `(writerId, account, sceneId)` 슬롯을 그 로드 동안 덮어쓰기, 슬롯마다 진행 하나·최신 대기 하나. 보존은 **마지막 성공 저장부터 7일**, 용량은 교체 후 크기로 같은 IDB 트랜잭션에서 검사. 부팅용 빈 이력은 쓰지 않는다. 보장은 "지금 저장본과 지문이 맞는 마지막 성공 이력이 있을 때 복원"이며, 빠지는 편집 수의 상한은 약속하지 않는다. 복제 탭은 읽은 시점의 원본 이력을 채택한 뒤 자기 슬롯으로 옮긴다(복제 시점 이력의 불변 보존은 보장 안 함). 계약 B 의 goal·decisions 를 이에 맞춰 고쳤다.
- **A 등록 위치**: 새 표의 스키마 호환 등록(`schema_compat.record_baseline…("content_comfy_canvas_runs")`)은 다른 구성 요소(asset_sync 등)처럼 `backend/app/db.py` 의 초기화 순서에 둔다 — `db_migrations.py` 안에서 하면 "이전 실패 시 완료 기록 금지" 시험이 깨진다(Codex 1단계 보고). 계약 A 의 touched_paths 에 `backend/app/db.py` 를 더했다.
- **A 릴리스 호환 선언**: 새 구성 요소 `content_comfy_canvas_runs` 를 `release/compatibility.json` 의 `supported_components` 에도 올린다 — 앞선 구성 요소(asset_sync·asset_destination)와 같은 관례이고, 빠지면 `test_release_contract` 가 실패한다(총괄의 백엔드 전체 시험에서 발견). 이 선언이 있어야 업데이트 관문이 새 구성 요소가 든 DB 와 판의 호환을 맞게 판단한다. 다른 값(rollout·db_schema·설치기 기능)은 그대로. 계약 A 의 touched_paths 에 더했다(총괄이 한 줄 넣는다).
