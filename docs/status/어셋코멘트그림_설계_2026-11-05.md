## 3. 서버·DB

### 3.1 표(서버·로컬 같은 표, 본 DB)

```text
asset_comment_drawing(            -- 생성물 generation_comment_drawing 과 같은 칸
  id TEXT PRIMARY KEY,            -- 클라 uuid
  comment_id TEXT NOT NULL REFERENCES asset_comment(id) ON DELETE CASCADE,
  idx INTEGER NOT NULL,           -- UNIQUE(comment_id, idx), 0..11
  kind TEXT NOT NULL,             -- 'image' | 'video' (파일 종류)
  width INTEGER NOT NULL, height INTEGER NOT NULL,   -- 좌표계 = 원본 픽셀
  time_sec REAL,                  -- 영상만
  strokes_json TEXT NOT NULL,     -- 획 v1 정규화본
  thumb_jpg BLOB,                 -- 영상만(없어도 정상 — C6)
  content_hash TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
)
asset_comment_request(            -- 재시도 장부(생성물 C1 과 같은 규칙)
  id TEXT PRIMARY KEY,            -- = 코멘트 id
  fingerprint TEXT NOT NULL,
  asset_key TEXT NOT NULL,        -- real_meta_key 로 정규화한 project + '\0' + path
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
)
```

- **삭제 기록 표는 두지 않는다** — 장부 행을 코멘트를 지워도 남겨, '장부에 있는데 코멘트가 없다' = 지워진 코멘트로 판정한다(§3.2). 어셋은 발행 합치기가 없어 되살아나는 길이 재시도뿐이라는 전제(§2 · §10-1).
- 외래키 연쇄 삭제: 생성물 그림 구현이 쓴 방식(연결의 `PRAGMA foreign_keys` 상태 확인, 꺼져 있으면 저장소 함수가 명시 삭제)을 그대로 따른다.
- 이름표: 생성물 그림 표처럼 **schema_migrations 이름표·기준 목록(BASELINES)에 넣지 않는다**(`comment_strokes.py:232` 방식) — "새 DB 이름표가 서버 업데이트를 막는다" 함정 회피(`schema_compat.py:260` 은 모르는 마이그레이션 이름을 거절 — Codex). 대신 새 표의 **PK·UNIQUE(comment_id, idx)·FK 구조 검사**를 생성물 그림 표 검사와 같은 자리에 더한다. `schema.sql` 은 기존 DB 시작에도 적용되므로 새 표만이면 데이터 이동은 없다.
- 저장소 = **어셋 전용 모듈 `repo/asset_comment_drawings.py`**(Codex 추천 채택) — 작성·지문·재시도·삭제 판정을 소유하고, 획 검증·정규화·해시는 `services/comment_strokes.py` 를 그대로 쓴다. 생성물 `create_comment_v2()` 를 대상 매개로 일반화하지 않는다(삭제 기록·발행 합치기·휴지통 분기가 섞임). **생성물 `fingerprint` 의 직렬화 키(`gen_key`)와 바이트는 바꾸지 않는다** — 이미 저장된 생성물 장부 지문이 달라진다. 그림 삽입·메타 조회 같은 작은 함수만 고정 대상 매개로 공유할 수 있다.

### 3.2 API — 전부 `/api/assets/` 아래(허브 로컬 예외, 핸들러가 나눈다)

- **문맥 고정(Codex P1-1)**: 지금 어셋 경로는 DB·서버 주소·토큰을 부를 때마다 읽는다(`assets_metadata.py:153`·`db_paths.py:20`·`_proxy.py:438`). 새 경로(comments-v2·목록의 그림 메타·그림 조회)는 요청을 받을 때 **계정 DB 키·행위자·서버 연결(주소·토큰)을 한 번 잡아** 끝날 때까지 쓴다 — 생성물이 쓰는 `pinned_account_scope`(`active_account.py:142`)·`pinned_connection`(`_proxy.py:65`) 재사용. 로컬 장부 확인과 쓰기가 다른 계정 DB 에서 일어나지 않게 한다.
- **화면의 기대값과 대조(Codex 2차 P1-3 · 3차 P1-1·P1-2)**: 고정은 '받은 순간의 상태'를 지킬 뿐 화면이 뜻한 상태와 같다는 보장이 아니다(화면 확인 뒤 다른 창에서 허브 계정을 B 로 바꾸면 A 의 초안이 B 로 가고, 같은 계정으로 서버 A→B 로 옮겨 재시도하면 B 에는 장부가 없어 새로 저장된다). comments-v2 는 기대값을 싣고, 받는 쪽이 **장부를 보기·쓰기 전에** 대조한다. 다르면 아무것도 쓰지 않고 409 `{"code":"context_changed"}`, 필수 기대값이 없으면 400 — 화면은 초안을 지킨다.
  - 기대값: 머리글 **`X-MVHub-Expect-Account`**(`acct:<email>` | `local`, 브라우저→허브 — `deps.py:93`. 헤더가 없으면 지금 함수는 '같음'으로 보므로 새 경로는 **빈 헤더를 거절**한다, `edit_shares.py:42` 와 같게) · 본문 **`expected_target`**(`local` | `server`) · 본문 **`expected_server_url`**(정규화한 서버 base URL, local 이면 null) · 본문 **`expected_server_account`**(서버 계정 이메일, local 이면 null). 허브는 본문을 그대로 서버에 중계하므로(`proxy_json` 은 머리글을 옮기지 않는다 `_proxy.py:448`·`:270`) 서버가 볼 기대값은 **본문**에 둔다(`edit_shares.py:76` 꼴). 이 값들은 내용 지문에 넣지 않는다(지문 형식 그대로).
  - **받는 쪽 모드별 대조**:

    | 받는 쪽 | 실제 저장 대상 | 대조 |
    |---|---|---|
    | 로컬 허브 — 중계 중(`proxying()` 참) | 비공개 → `local` · 공유 → `server` + 고정한 서버 주소 | 머리글 필수·고정 계정과 비교 · `expected_target` · 공유면 `expected_server_url` 을 고정한 주소와 비교 → 통과하면 공유는 본문 그대로 서버로 |
    | 로컬 허브 — 중계 안 함(서버 없음·`CONTENT_HUB_NO_PROXY`) | 비공개·공유 모두 `local` | 머리글 필수·고정 계정 · `expected_target == local` |
    | 공유 서버 본체(`is_shared_team_server()`, 중계 안 함 `_proxy.py:188`) | 공유 → `server`(자기 자신) · 비공개 → 지금처럼 거절 | `expected_target == server` · `expected_server_account` 를 **인증된 계정 이메일**과 비교(없으면 400). 서버 주소는 허브가 이미 비교했다고 보고 서버는 보지 않는다(서버가 자기 공개 주소를 확실히 모를 수 있다) |
- **저장 대상의 정의(Codex 2차 P1-2)**: 기존 전역 `authority`(local/team)는 `auth_enabled` 로 정해져 **서버로 공유 코멘트를 중계하는 로컬 허브도 `local`** 이다 — 코멘트 저장 위치가 아니므로 뜻을 바꾸지 않고 따로 정한다(위 표). 통신 장애는 저장 대상을 바꾸지 않는다(`proxying()` 은 토큰·설정으로 정해지고 통신 장애만으로 꺼지지 않는다 `_proxy.py:188` — 그 요청은 '불확실'이지 '로컬로 전환'이 아니다).
- **화면이 저장 대상을 아는 길(Codex 3차 P2)**:
  - **허브 화면**(로그인 끔, 보통의 로컬 허브): 로컬 전용 `/api/shared-server/status`(`publish.py:512` · 프런트 `sharedServerStatus` `lib/sharedApi.ts:21`)가 `url`·`email`·`has_token` 을 준다. `has_token` 은 중계 여부가 아니다(`CONTENT_HUB_NO_PROXY=1` 이면 토큰이 있어도 중계를 끈다 `_proxy.py:197`) → 응답에 **실제 `proxying` 판정값을 더하고**, 계정·주소·중계 여부를 **한 번 고정한 계정 문맥에서** 읽어 준다.
  - **서버 직결 화면**(LAN 브라우저 → 공유 서버, 로그인 켬): 그 상태 API 는 루프백 전용이라 403 이다(`publish.py:468`) → 인증된 계정과 지금 서버 주소로 문맥을 꾸린다(공유 = `server`, `expected_server_account` = 로그인 계정). 비공개는 지금처럼 숨긴다.
  - 상태 조회 실패는 `local` 로 보지 않는다 — **준비 안 됨**으로 보고 [편집]·전송을 막는다.

- **작성 `POST /api/assets/comments-v2`** — 본문 `{id(클라 uuid), project, path, text(1자 이상), parent_id: null, private, drawings[0..12]}`(1단계는 `parent_id` 가 null 이 아니면 400).
  - 길: 비공개 = 늘 로컬(장부 포함) · 공유 + proxying = 본문 그대로 서버로(`proxy_json`) · 공유 + 서버 없음 = 로컬 · 공유 팀 서버 본체에 비공개 = 거절(지금 규칙).
  - 옛 서버: 서버의 **경로 없음** 404(FastAPI 기본 `{"detail":"Not Found"}`, 프런트 `isRouteMissing` 과 같은 기준)만 허브가 409 `{"code":"server_update_needed"}` "팀 서버 업데이트 뒤 그림을 붙일 수 있습니다"로 바꾸고 화면은 쓰던 글·그림을 지킨다. 그 밖의 404·403 은 그대로.
  - 오류 본문은 **안정된 `code` + 안내 `message`** 를 함께 싣는다(`code` ∈ `deleted`·`conflict`·`stored_local`·`context_changed`·`server_update_needed`) — 기존 `lib/http.ts:106` 이 `message` 있는 본문을 `HttpError.info` 에 보존하므로 화면이 그대로 나눈다(Codex 2차 P2).
  - 처리 순서(한 트랜잭션, 받는 쪽, 위 기대값 대조 뒤): ① 장부에 id 가 있고 코멘트 행이 없음 → 410 `{"code":"deleted"}`(만들지 않음) ② 장부에 있고 지문 같음 → 처음 결과 그대로 ③ 장부에 있고 지문 다름 → 409 `{"code":"conflict"}` ④ 장부에 없는데 같은 id 의 코멘트가 있음 → 409 `conflict`(어셋은 생길 길이 없는 방어) ⑤ 없으면 코멘트 + 그림 + 장부를 함께 씀. 검증 실패 = 통째 취소(글도 안 생김).
  - 지문(서버 계산 SHA-256) = 인증 신원(본문 author 안 씀) · `asset_key` · 공개/비공개 · parent_id · 작성 때 글 · 그림 `{drawing_id, content_hash}` 순서 목록 — 생성물 `fingerprint` 와 같은 꼴(키 자리만 asset_key).
  - 허브의 처리 장소가 바뀐 재시도(생성물 C1 3차 규칙 + Codex P1-3): 허브는 comments-v2 를 받으면 **로컬 장부를 먼저** 본다.
    - 로컬 장부에 있고 그 코멘트가 **비공개**면 → 로컬의 처음 결과(비공개는 늘 로컬이라 장소가 안 바뀐다).
    - 로컬 장부에 있고 그 코멘트가 **공유인데 로컬에 저장된 것**(서버 없을 때 저장) — 지금 서버 없음이면 처음 결과, **지금 서버에 연결(proxying)이면 409 `{"code":"stored_local"}`** "서버 연결 전에 이 PC 에만 저장된 코멘트입니다 — 팀에는 보이지 않습니다". 성공으로 돌려주지 않는다(목록은 서버 공유 + 로컬 비공개만 합쳐 그 코멘트가 안 보이고, 수정·삭제는 서버로 가 404 — Codex). 자동 동기화는 하지 않는다. (보통은 위의 기대 저장 대상 대조가 먼저 걸러 `context_changed` 가 되고, 이 판정은 대조를 지난 경우의 방어다.)
    - 로컬 장부에 있고 코멘트 행이 없으면 → 410(지워짐).
    - 로컬 장부에 없으면 → 지금의 분기(공유 + proxying = 서버, 그 밖 = 로컬).
    - 반대 방향(서버에 저장됐는데 응답을 잃고, 그 뒤 허브의 중계가 꺼진 채 재시도 → 로컬에 같은 id 로 새로 생김)은 **두 겹으로 막는다**: 화면은 초안을 처음 보낼 때의 계정·저장 대상에 묶어 대상이 바뀌면 다시 보내지 않고(§4), 허브는 기대 저장 대상(`server`)과 지금 실제(`local`)가 다르면 `context_changed` 로 거절한다(위 대조). 통신 장애만으로는 중계가 꺼지지 않는다(`_proxy.py:188`).
  - 응답 `{id, result, drawings:[{id, content_hash}]}` — 화면이 보낸 것과 대조해 다르면 실패로 보고 초안을 지킨다.
  - 권한: 공유 = `require_asset_comment_access(write=True)`(서버·서버 없는 허브), 비공개 = 작성자 본인(로컬).
- **목록 `GET /api/assets/comments`** — 각 코멘트에 `drawings` **메타만**(id·idx·kind·width·height·time_sec·has_thumb·content_hash·v — 생성물 `attach_meta` 와 같은 칸). proxying 이면 서버가 공유분에 메타를 붙여 주고, 허브가 로컬 비공개분에 로컬 메타를 붙여 합친다.
- **그림 `GET /api/assets/comments/{comment_id}/drawings/{drawing_id}`**(획) · **`…/{drawing_id}/thumb`**(영상) — 길: 로컬 행이 비공개면 로컬 · 그 밖에 proxying 이면 **서버 권위**(로컬에 공유 행이 없어도 서버로 보낸다 — 허브가 로컬 프로젝트 조회 실패로 먼저 막지 않는다, 서버 403·404 를 로컬로 대체하지 않음) · 서버 없음이면 로컬.
  - **권한(Codex P1-2)** — 획·thumb 같은 규칙: **비공개 = 작성자 == 행위자**, 아니면 404(`_assets_access` 는 작성자를 안 본다 — 생성물은 `generation.py:1405` 에서 따로 본다). 프로젝트 권한은 비공개에 강제하지 않는다(공유 권한을 잃은 작성자도 자기 로컬 메모를 본다). **공유 = 코멘트 행의 project 로 읽기 권한**(`require_asset_comment_access(write=False)`, 서버·서버 없는 허브에서).
  - **중계(Codex P1-4)**: `_forward_stream`(`_proxy.py:889`)은 오류 본문·성공 총량에 상한이 없다 → **`proxy_bytes`(`_proxy.py:569`)** 를 쓴다. 상한 = thumb 64KiB · 획 응답 320KiB(획 256KiB + 포장 여유). 넘으면 502 로 끊고 일부만 보이지 않는다.
  - `Cache-Control: private, no-store` 를 **정상 응답과 403·404·410 오류 응답 모두**에 단다.
- **기능 표식**: 허브 `features` 에 `asset_comment_drawings_v1`(이 앱이 아는가) · 서버 `/api/share/capabilities` 에 `asset_comment_drawings: 1`(서버가 받는가). 서버 없는 허브는 허브 표식만 본다.
  - `/api/share/capabilities` 는 로컬 예외가 아니라 **proxying 이면 허브 미들웨어가 먼저 서버로 중계**한다 — `share.py:1119` 의 404·405 변환이 늘 도는 것이 아니다(Codex). 화면이 응답을 나눈다: `asset_comment_drawings: 1` = 보임 · 경로 없음(옛 서버)·401·403·연결 실패·5xx·시간 초과 = **모두 숨김**(실패를 지원으로 보지 않는다). 결과는 문맥(계정·서버 주소·권위)별로 기억하고 문맥이 바뀌면 버리며, 다른 문맥의 늦은 응답은 버린다.
- **상한**(생성물 C5 그대로): `services/upload_limits.py` 파싱 전 규칙에 `/api/assets/comments-v2` 5MiB · 획 JSON 그림당 256KiB · thumb 64KiB · 그림 ≤ 12장. 검증기는 `services/comment_strokes.py` 를 그대로 쓰고 kind 는 파일 종류에서.
- **삭제**: 지금 규칙(부모 + 직접 답글) 그대로, 그림은 연쇄 삭제, 장부 행은 남긴다. 비공개 답글이 달린 부모 409 도 그대로.
- **계정(Codex P2-7 정정)**: 계정 정리는 코멘트를 **지우지 않는다** — 댓글은 계정 이력으로 세고(`account_cleanup.py:101`) 이력이 있으면 계정 삭제를 막는다(:148, 실제 삭제 목록은 :300 의 별도 표). 이 정책을 그대로 두고 그림 표는 정리 대상에 넣지 않는다. 작성자 이관(`identity.py:578` author)은 코멘트 행만 바뀌고 그림은 comment_id 로 따라간다. 장부 지문은 바꾸지 않는다 → 이관 뒤 같은 id 재시도는 409 — 받아들일 경계(화면은 새 작성 때 코멘트 id·그림 id 를 함께 새로 만든다).

## 4. 화면 동작(모양은 §6 확정 표가 정본)

- **어셋 작은 창 [편집]**: 허브 표식 + (proxying 이면) 서버 표식이 모두 있을 때만 보인다(A1). 이미지·영상 파일만(오디오·그 밖은 없음). 누르면 작은 창에 쓰던 글을 그림 창 입력칸으로 옮기고(작은 창 입력은 비움 — 제안) 그림 창을 연다. 그림 창을 닫으면 떠 있던 작은 창으로 돌아오고 목록이 새로 읽힌다.
- **크게 보기(어셋) `c` 키** = Ctrl 카드 C 와 같은 작은 창 열기(지금은 아무 일도 없다 — `canComment` 가 genId 를 요구).
- **그림 창 대상 일반화**: `{kind:"generation", genId}` 또는 `{kind:"asset", project, path, url, type}`. 대상은 창뿐 아니라 **그림 보기 꼴(`CommentDrawingView`)·그림 조회 훅(`useCommentDrawing` — 지금 생성물 API 고정 `GenCommentPanel.tsx:52`)·그림 칩·크게 보기 겹쳐 보기 이벤트**까지 실어 보낸다(Codex). 목록·새로 읽기 책임은 지금 담당(생성물 = `GenCommentPanel`, 어셋 = `useAssetCommentActions`)에 남긴다. 어셋 API 의 실제 정의 자리는 `lib/assetsApi.ts`(Codex).
- **오른쪽 칸 입력의 책임(Codex P2-6)**: 오른쪽 칸 = 대상의 코멘트 목록 + 한 줄 입력 + [전송] + 비공개 쓰기·읽기. 지금 `CommentPanel` 은 새 글·답글이 같은 `onSend` 를 쓴다(`CommentPanel.tsx:198`) → **새 코멘트 전송만** 그림 창의 전송(그림 있으면 대상의 comments-v2, 없으면 지금 글 경로)에 연결하고, **답글·수정은 지금 경로 그대로**(답글에 초안 그림이 붙지 않는다). 새 코멘트의 글·비공개 체크·보내는 중 상태의 **주인은 그림 창 하나**다. 작은 창에서 옮긴 글은 **인계가 끝난 뒤** 작은 창에서 비운다(두 번 보내기 방지). 닫기 확인은 그림 판·새 글뿐 아니라 오른쪽의 **보내지 않은 답글·수정**도 센다.
- **초안 규칙**(생성물 C1 화면 규칙 + Codex 1차 P1-1·2차 P1-1·P2):
  - 초안은 **재시도 id(코멘트 id·그림 id)를 스스로 들고** 있고, 그 id 는 작성 의도(글·그림·비공개 체크)가 바뀔 때만 새로 만든다. **세션 번호·토큰 변경·재인증만으로는 id 를 바꾸지 않는다**(같은 계정·같은 서버에서 재인증 뒤 새 id 로 보내면 앞서 서버에 저장된 코멘트가 둘이 된다 — Codex 2차).
  - 초안은 처음 보낼 때의 **계정·저장 대상·서버 주소**(§3.2 — 비공개 = local, 공유 = server(+주소)/local)에 묶인다. 진행 중인 작업(영상 thumb 캡처·해시 계산·전송)은 `isOperationContextCurrent` 가 거짓이 되면 멈춘다 — 세션 검사는 **진행 중 작업을 멈추는 데만** 쓴다. 캡처·해시 앞뒤와 전송 직전에 확인한다.
  - 다시 보내기: **계정·저장 대상·서버 주소가 처음과 같으면** 새 실행 문맥에서 **같은 id·같은 본문·같은 기대값**으로 다시 보낸다(장부가 처음 결과를 돌려준다). 하나라도 다르면 자동으로 다시 보내지도 id 를 새로 만들지도 않는다.
  - 상태와 안내를 셋으로 나눈다: **보내기 전에 멈춤** = "보내지 않았습니다" · **보냈는데 결과 모름**(응답 유실·시간 초과·통신 장애) = "이번 재전송은 중단했습니다. 앞선 요청은 저장됐을 수 있습니다"(같은 계정·대상이면 [다시 보내기] = 같은 id) · **저장 확인** = 성공. 다른 문맥의 늦은 응답은 버린다.
  - **`stored_local`**(Codex 2차 P2) = "이 PC 에 저장됨 · 팀에 저장 안 됨" 상태. 글·그림을 지키고, 성공 처리·초안 비우기·자동 id 갱신을 하지 않는다(같은 id 로 다시 눌러도 같은 409). **[팀에 새로 보내기]** 는 사용자가 고른 **새 작성**으로 보고 코멘트 id·그림 id 를 함께 새로 만든다. `context_changed`·`server_update_needed`·`conflict` 도 초안을 지킨다. `deleted` 는 "이미 지워진 코멘트입니다".
  - 닫을 때 쓰던 것이 있으면 "버릴까요?".
- **문맥 초기화(Codex 2차 P1-2·3차 P2 — 확정 요구)**: 지금 어셋 분리 창은 문맥을 설정하지 않는다(코드 확인 — `main.tsx:105` 가 App 을 거치지 않고 렌더, `AssetsWindow.tsx:13` 에 설정·감시 호출 없음, `configureOperationContext` 의 제품 호출부는 `App.tsx:509` 하나) → 기본값 `serverOrigin=""`·`authority="local"`·`ready=true` 가 남는다. **분리 창도 메인 앱과 같은 근거로 계정·연결 문맥을 초기화하고 변경을 감시(`watchOperationContext`)해야 하며, 준비되기 전에는 [편집]·전송을 막는다.** 근거 = 허브 화면은 `/api/shared-server/status`(실제 `proxying` 포함), 서버 직결 화면은 인증 계정 + 지금 서버 주소(§3.2). 메인 앱은 지금 로그인 끔일 때만 상태를 읽는다(`useHubAuth.ts:68`) — 서버 직결 쪽 꾸리기도 같이 확인한다. 저장 대상은 §3.2 표로 따로 판정한다.
