## 측정(임시 DB, 실제 DB·서버 무관)

- 작업 목록(`tasks-batch`)의 서버 계산을 가짜 팩트로 쟀다(한 사람 5,000 + 나머지 2,997, 폴더 60): **2.97초 중 2.7초가 `manage_db.task_activity_facts`**. 원인 = `local_gen_id` 짝 찾기가 맞는 색인이 없어 `idx_tgf_creator` 로 그 사람의 팩트 전체를 **번호 하나마다** 다시 훑는다(EXPLAIN 확인, 400개 묶음당 177ms) → 생성물 수의 제곱으로 느려진다. 같은 쿼리를 '그 생성자 팩트를 한 번 읽고 파이썬에서 짝 맞추기'로 바꾼 시안 = **0.59초**(같은 결과).
- 콘텐츠 DB 쪽 앵커 대조(`load_activity_snapshot`)의 `job_id` 짝도 `idx_generation_job` 대신 `idx_generation_creator_sort` 를 탄다(EXPLAIN 확인) — 서버 공유 생성물이 많을수록 같은 꼴로 느려진다.
- 서버는 작업자 허브가 생성 기록을 올릴 때마다(`POST /api/manage/telemetry/push`) 출처 없는 `manage_changed` 를 모든 창에 보내고(`mutation_notify.py:110`, `main.py:986`), 관리 창은 0.18초 뒤 작업 목록 전체를 다시 받는다(`useManageRealtime.ts`). 이 쓰기가 서버 캐시 표식도 바꿔 매번 처음부터 다시 계산한다 → 팀이 생성할수록 열린 관리 창 수만큼 위 계산이 반복된다(빈도는 미측정).
- 작업 탭은 열 때 시퀀스 칸 후보(전역 태그) 하나 때문에 `/api/facets` 로 내 생성물 전체를 집계한다(`WorkBoard.tsx`). 같은 값은 `/api/auto-tags` 가 준다.

## 결과

- 서버 `manage_db.task_activity_facts`: (생성자, 앵커) 짝을 400개씩 `VALUES` 로 조인하던 것을 **생성자별로 한 번 읽고 파이썬에서 job·local_gen_id 짝을 맞추기**로. 처음엔 job 쪽에 `+f.creator_uid` 만 붙였는데 2만 건에서 플래너가 job 색인을 버리고 묶음마다 표 전체를 훑어 31초가 나왔다(EXPLAIN: `SCAN f` + `AUTOMATIC COVERING INDEX`) → 두 짝 모두 한 번 읽기로 바꿨다. 같은 행 집합이다.
- 서버 `manage_task_activity.load_activity_snapshot`: 콘텐츠 앵커 대조를 `WHERE g.job_id|g.id IN (…)`(늘 색인) + 파이썬 생성자 대조로.
- 프런트: `manageRefreshDelay`(출처 없는 manage 신호 10초 간격) · `useManageRealtime` 은 더 일찍 잡힌 재조회를 미루지 않는다 · 작업 탭 전역 태그는 `/api/auto-tags`.
- 측정(임시 DB, 같은 스크립트 `bench_tasks.py`): 한 사람 5,000 + 나머지 약 3,000 = **2.97초 → 0.33초**. 한 사람 20,000 + 나머지 약 6,000 = **1.26초**(고치기 전은 원래 쿼리 3묶음을 재어 비례 환산한 **추정** — local_gen_id 짝만 묶음당 1.75초 × 65묶음, 무거운 사람 몫이 대부분이라 실제로는 약 1분 반 안팎).
- 새 시험 `test_same_local_id_from_other_account_in_other_project_stays_ambiguous` 는 교차 조회를 뺀 가짜 구현에서 실패하고 실제 구현에서 통과한다(스크래치 돌연변이 확인).
- 시험: 작업·활동 관련 백엔드 10파일 · 프런트 6파일 · `lint:architecture` · `build` 통과(위 계약의 시험 기록).
- 못 한 것: 실제 서버 데이터로는 재지 않았다(서버 DB 사본 없음 — 운영 서버 시험 금지). 효과는 **서버 업데이트**(서버 쿼리)와 **앱 릴리스**(재조회 간격·전역 태그) 뒤에 생긴다. 서버 코드라 main 병합 전에 Codex 독립 리뷰가 필요하다.
- 남긴 후보(이번 범위 밖, 상대 보고 + 일부 코드 확인): 허브 중계 `_forward` 가 gzip·ETag 를 쓰지 않음(관리 응답 무압축) · 조회자마다 서버 캐시가 따로라 같은 신호에 창 수만큼 계산 · 완료 탭의 final/shared 대상 순차 조회 · 권한 확인 3단 순차 · 대시보드 집계 캐시 없음.
