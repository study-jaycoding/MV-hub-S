# 배포 후보 — 이번 릴리스는 허브 공책을 명시적으로 켤 때만 (2026-11-15)

> 2026-11-17 Jay가 팀 기본 켬과 출처 미확인 최초 시작 확인을 결정했다. 이 문서의 11-15 기본 끔 결정·J3를 대체한다([새 결정·Codex 자문](허브공책_기본켬_첫시작확인_2026-11-17.md)). 아래의 당시 코드·시험·배포 기록은 과거 근거로 보존한다. `=0`으로 이미 시작한 공책의 데이터를 되돌리는 것은 아니다.

## 왜

[Gate 6-A 점검](배포후보_Gate6A_2026-11-15.md)의 BLOCKER: 합류 기록(nj) 없는 브라우저는 첫 공책 전환에서 `adoptRestoredNotebook`(`frontend/src/lib/sceneNotebook.ts:628`)으로 가고, 로컬 씬이 허브 옛 미러와 정확히 같지 않으면 로컬 씬 전부를 '복원 전에 남겨 둔 것'에 보관하고 캔버스를 허브 판으로 바꾼다(빈 미러면 빈 캔버스, 5MiB 초과 씬 하나만 있어도 전체 보관). 공개판(`3d0ff280`)에는 공책 코드가 없어(`backend/app/services/scene_writer.py` 없음) 업데이트 뒤 팀원 대부분이 이 전환을 지난다.

Codex `01a1ddbc`(읽기 전용) 판정 두 번: 1차 BLOCKER(중간) · 자동 예외 확대는 복원 직후 옛 자료를 되살리는 구멍이라 불가 · 2차 **RECOMMEND-ii** = 이번 릴리스는 공책 기본 끔, 첫 전환 복구 동선은 다음. 조건: 이미 공책을 시작한 설치본은 `CONTENT_HUB_SCENE_WRITER=1` 을 명시 유지(그냥 끄면 시작된 공책의 토큰 없는 미러 PUT 이 409 — `backend/app/routers/scenes.py:128`).

이미 공책을 시작한 곳(직접 확인, 읽기 전용 조회): 공유 서버는 로그인 모드라 원래 꺼짐(`enabled()` = `not AUTH_ENABLED and …`). 이 PC 의 dev 화면 `test_dev.bat` 은 `CONTENT_HUB_AUTH=1`(43행)이라 꺼짐. dev 의 계정 DB 를 세어 보니 `backend/data_test/db` 는 `scene_notebook` 0행, `backend/data`·`backend/data_hub_dev`(로컬 허브 화면 실행기 `test_dev_hub.bat` → `tools/dev_hub.py` 의 자료)의 계정 DB 는 `scene_notebook` 표가 아예 없다 — 확인한 범위에 시작된 공책은 없다. 그래서 dev 허브 실행기는 릴리스 기본(끔)을 그대로 따르고, 공책 전용 격리 실측 도구(`tools/browser_measure/canvas_notebook.py` `make_env`)만 `=1` 을 넣는다. 이 판은 공개판에서 바로 업데이트하는 설치본을 대상으로 한다 — 별도 dev·시험판으로 공책을 시작한 설치본은 자동 다운그레이드 대상이 아니다(그런 곳은 `=1` 을 명시해야 한다).

### 끔에서 팀 기본이 되는 미러 경로의 보강

끔이면 공책 없는 1C 미러 경로(`frontend/src/lib/sceneBackup.ts`)가 팀 기본이 된다. 이 경로의 첫 접촉은 허브 미러와 다른 씬을 캔버스에 그대로 두되 자동 전송을 보류하고 그 원문을 localStorage 기록(`mvhub.mirrorRecovery:*` 의 `originals`)에 복사한다(`checkMirrorGeneration` 130-143행, 같은 세대에서 지문이 안 맞는 씬도 124행에서 같은 일). 비참여 Claude 합의 검토 `bd383363` 이 짚은 대로, 5MiB 를 넘는 지금 본문은 미러로 전송되지 않아(허브에는 작은 이전 사본이 남아 있을 수 있다) '다름'으로 보류되고, 그 원문이 localStorage 한도를 넘으면 기록 저장이 예외로 끝나 그 계정의 미러 동기화 전체가 재시도에 묶인다(코드 추론). 공개판은 큰 씬만 빼고 나머지는 올렸다.
- 5MiB 초과 씬은 **보류(blockedIds — 전송 차단)는 그대로 두고, 그 원문만 `originals` 에 복사하지 않는다**(두 분기 모두). 원문은 IndexedDB 의 그 씬 자체로 남고 캔버스에 보인다. 세대가 확인되지 않은 초과 씬은 현재 세대의 정상 자료로 승격하지 않는다 — 크기를 줄이거나 편집·새로 고침을 해도 자동 전송이 다시 시작되지 않고 명시적 재개(전체 내보내기 → 전체 가져오기, `importSceneArchiveText` → `resumeImportedMirror`) 뒤에만 보낸다(Codex `01a1ddbc` 높음 지적: 보류에서 빼면 줄인 옛 씬이 빈 복원본에 되살아난다). 보관본 내려받기에는 원문이 있는 씬만 담긴다(큰 씬은 캔버스의 전체 내보내기로 받는다).
- 원문 없는 보류가 화면에서 사라지지 않게 한다(Codex 3차 중간): 크기는 `recountOverLimit` 이 크기만 보고 표시하므로 5MiB 이하로 줄이면 '빠짐' 표시가 없어지고, 설정 → 자료 관리의 보류 개수(`CanvasArchiveSection.tsx` `heldRecoveryCounts`)는 원문·장부가 있는 묶음만 센다. 그래서 보류 ID 중 원문·장부 어디에도 없는 것(= 이번의 큰 씬)을 따로 세어 같은 주황 칸에 "캔버스에 그대로 있지만 자동 백업을 멈춘 씬 N개 — 전체 내보내기 뒤 전체 가져오기로 다시 보냅니다"를 보인다. 지금 코드에서 보류 ID 는 늘 원문이나 장부와 함께 들어가므로(130-135행) 다른 경우에 새 경고가 뜨지 않는다.
- 동기화마다 모든 씬을 다시 해싱하던 곳 — `checkMirrorGeneration`(동기화 앞뒤, 119행)과 `mirrorSceneGenerations`(`frontend/src/lib/sceneNotebook.ts:48-61`, 동기화 안 644·760행과 카드 연결 읽기에서 부름) — 에 씬별 지문 기억을 쓴다. `sceneBackup.ts` 는 [미러 지문 중복 계산 고침](배포후보_미러지문중복_2026-11-15.md)의 `provenanceHash` 를, `sceneNotebook.ts` 는 자기 기억을 둔다(`sceneBackup` 이 `sceneNotebook` 을 가져오므로 반대 방향 import 는 순환). 같은 글자면 같은 지문이라 값은 그대로다.
- 남는 한계(받아들임): 5MiB 이하 씬 여럿이 동시에 미러와 다르고 그 원문 합이 localStorage 한도를 넘는 경우는 그대로다. 매 동기화의 본문 전체 조회(`include_data=1`)도 그대로다(1C 리뷰 낮음 5). 배포 안내에 '업데이트 직후 미러와 다른 씬은 화면에 그대로 두고 자동 백업만 보류한다(설정 → 자료 관리에서 재개)'와 '5MiB 를 넘던 씬은 줄여도 자동 백업이 다시 시작되지 않는다 — 전체 내보내기 뒤 전체 가져오기로 재개'를 적는다.
