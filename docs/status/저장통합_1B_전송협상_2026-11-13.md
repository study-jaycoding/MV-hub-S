3. v3 작업자 manifest는 content·trash·agent_chat·asset_mounts 네 역할을 정확히 포함하며 manage는 제외한다. absent는 원래 state·captured_at만 남기고 파일을 만들지 않는다. present content는 사본을 만든 뒤 기존 비밀 제거와 제거 확인을 수행하고, trash·Agent·JSON은 원문 바이트를 복사한다. 복사본을 로컬 manifest의 해시와 대조하며 content는 정제 전에 대조한다. 파일명은 WORKER_FILENAMES를 사용한다. 역할별 촬영 시각과 PINNED 보장을 유지하고 INDEPENDENT의 범위는 작업자 present 역할로 다시 계산한다. staged 크기·해시·schema로 봉인하고 계정 digest를 포함해 verify_files_v3를 통과한 뒤 공개한다.

4. 전송판별 키는 queue와 drain이 같은 함수로 계산한다. v3 키는 format_version, 역할별 state 및 존재하는 size·sha256·schema, consistency_kind, consistency_roles로 구성하고 captured_at은 제외한다. absent 역할도 키에 포함한다. v2 키의 직렬화 바이트는 기존과 같고 v1 읽기·ACK 호환은 유지한다. 같은 전송 내용의 시각만 달라진 v3는 기존 활성 행을 재사용하되 v2 행을 v3 행으로 재사용하지 않는다. 이 키가 manifest 봉인·ID·파일 검증을 대신하지 않는다.

5. v2 빈 자료 판정은 유지한다. v3는 기존 meaningful_records가 양수이거나 present Agent DB의 agent_chat_conversation 행이 하나 이상이거나 검증된 폴더 JSON의 mounts 항목이 하나 이상일 때 등록한다. present라는 이유만으로 등록하지 않는다. 추가 개수는 staged 사본에서 읽기 전용으로 판단하고 wire summary에 넣지 않는다. 검사 오류를 0으로 처리하지 않는다.

6. 비중계 share capabilities는 backup_set_format 정수 3을 알리고 중계 응답에는 로컬 능력을 덧붙이지 않는다. v3 drain만 staged manifest·정확한 present 파일·계정·content/trash를 검증하고 토큰을 확인한 뒤 같은 서버·토큰으로 capabilities GET을 수행한다. 캐시는 두지 않는다. 200 객체에서 정확한 정수 3 이상이면 지원, 키 없음 또는 정수 3 미만 및 HTTP 404/405는 server_update_required, 401은 login_required, 연결·시간초과는 network_unavailable, 잘못된 JSON·루트·키 타입 및 나머지 HTTP 상태는 capability_unknown이다. bool·문자열·실수를 정수로 변환하지 않는다. v1/v2 전송은 능력 조회를 추가하지 않는다.

7. 구서버 대응은 A다. 지원을 확인하지 못한 v3는 세트 POST를 하지 않고 기존 행과 staging을 재시도 대상으로 유지한다. 자동 루프·수동 백업·재시도 어디서도 v3를 v2 또는 단일 content로 자동 하향하지 않는다. 수동 단일 content 호환 업로드는 요청 원본과 실제 drain한 세트가 모두 구판으로 확인된 경우에만 기존대로 허용하고 ok:false를 유지한다. 요청 ID와 실제 처리 백로그는 다를 수 있으므로 실제 처리판을 결과로 전달해 함께 검사한다. 판 확인 실패도 호환 업로드를 허용하지 않는다.

8. 지원 확인 뒤 multipart는 manifest와 present 파일만 고정 이름으로 보낸다. v3 ACK는 accepted가 true이고 backup_set_id, 정확한 정수 format_version=3, manifest_sha256, present와 정확히 같은 files 키, 역할별 정확한 정수 size와 sha256이 모두 일치해야 한다. absent 혼입·누락·다른 판·다른 해시·크기 타입 오류는 ack_mismatch다. 일치한 ACK 뒤 기존 done 기록이 성공한 경우만 staging을 정리한다. 재전송은 같은 봉인 ID를 유지한다. conflict ACK는 전체 보관 성공으로 처리하되 현재 복원 기준점 승격으로 해석하지 않는다.

9. 능력 GET 제한은 10초이며 부모 자식 실행 제한은 기존 UPLOAD_TIMEOUT+15초에 이 10초를 추가한다. 로그인 300초, 업데이트 필요 3600초, 그 밖의 기존 제곱 백오프를 유지한다. 다음 시도마다 능력을 다시 확인한다. 시간초과·취소·자식 비정상 종료에는 기존 프로세스 회수와 running 복구를 유지한다. 재확인 주기·백로그·앱 종료가 있으므로 1시간 안의 전송 완료를 약속하지 않는다.

10. outbox의 각 행은 해당 판의 전체 작업자 세트이며 부분 투영 행을 만들지 않는다. 기존 pending 상한, superseded 정리, 복원 후 기준점 채택과 계보 계산은 유지한다. 실패 시 보존은 해당 행이 이 기존 정책으로 superseded되기 전까지를 뜻한다. 부모 미전송·상한 정리·다른 PC 변경 때문에 conflict가 생길 수 있다. 혼합판에서 마지막 v3를 특별 보호하는 정책과 손상 staging 자동 재구성은 이번에 추가하지 않으며 A 전 검토사항으로 남긴다.

11. status_snapshot의 unsent_roles는 현재 계정 pending/running 행에 기록된 present 역할의 합집합이다. v1/v2 역할은 모두 present로 해석하고 content·trash·agent_chat·asset_mounts 순서로 알려진 이름만 반환한다. 경로·계정·세트 ID·본문은 반환하지 않는다. done/superseded는 제외하고 로그인 계정이 없으면 빈 배열이다. 잘못된 역할 메타데이터 때문에 상태 API가 실패하거나 정상 전송으로 승격되지 않게 한다. 이 필드는 현재 대기열의 미전송 구성원이며 전체 로컬 자료나 파일 건전성의 증명이 아니다.

12. 프런트 타입에는 선택적 unsent_roles를 추가한다. 자료 관리의 서버 복제 줄 아래에서 server_update_required·failed·login_required이고 배열이 비어 있지 않을 때만 작업 기록(생성물·캔버스·편집), 휴지통, MV Agent 대화, 폴더 등록의 이름을 표시한다. pending·uploading·success에는 추가 경고를 표시하지 않는다. 업데이트 안내는 앱 실행 중 자동 재확인을 설명하며 완료 시각·NAS 복제·미연결 재시도 버튼을 약속하지 않는다. 기존 번역·접근성 방식을 따른다. 합성 격리 왕복·실패 경계·v2 회귀·화면·빌드·지도·생성 목록 검사와 비구현 별도 Claude 독립 리뷰 뒤에만 P2 완료로 보고한다.
