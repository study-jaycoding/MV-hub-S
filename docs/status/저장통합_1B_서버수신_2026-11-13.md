# 저장 통합 1B — 서버 수신·보관·NAS 준비

owner·touched_paths: 아래 계약 · reviewer: Claude `32e125d2-d3ca-4e9e-baad-81f764bba49f` 독립 리뷰 통과 · status: 완료(서버 소비자 준비만) · updated: 2026-11-13

[진행 인계](Codex인계_진행중작업_2026-11-12.md), [저장 통합 4판](저장통합_설계_2026-11-12.md) §4-3/1B, [형식 검증 준비](저장통합_1B_형식검증_2026-11-13.md)를 잇는다. 실제 서버·DB·설치본을 변경하는 작업이 아니며 dev의 코드와 임시 자료 시험만 수행한다. 서버 업데이트와 새 형식의 생성·송신 활성화는 이 묶음에 포함하지 않는다.

## 제안과 반례

- 기존 서버 경로에서 v3를 명시적으로 읽되 VERSION=2·공통 check_version·로컬 읽기·worker 생성/송신·클라이언트 ZIP 해제/설치는 유지한다. 서버 수신/전체 ACK/목록/ZIP과 서버 세트 NAS를 한 묶음으로 구현한다. 실제 새 자료의 캡처와 복원 실행은 후속이다.
- Claude 설계 세션은 이 분할과 전체 파일 보관에 동의하는 안을 제시했다. 아직 아래 계약의 양측 합의는 아니다. Codex 보조 검토는 내부 함수 준비만을 추천했다. 총괄은 외부 경로를 준비하되 새 생산을 켜지 않고 구복원 경로의 부분 자료 반환을 명시적으로 차단하는 안을 제안한다.
- 중요 반례: `/latest`는 현재 모든 세트의 content.db를 단일 파일로 반환할 수 있다. v3에도 이 동작을 허용하면 Agent·폴더 구성원이 빠진 복원이 가능하다. 최신 선택 대상이 v3인 단일 파일 요청은 409로 거절하고, 옛 v2로 조용히 바꾸지 않는다. 같은 후보 탐색에서 manifest가 없거나 읽을 수 없어 판을 확인하지 못한 세트도409다. 정상 v3의 `/latest-set`·지정 세트 ZIP은 전체를 반환하며 현재 클라이언트는 설치 전에 거절한다. 404/405로 숨겨 legacy fallback을 유도하지 않는다.
- 서버의 하나의 head와 10세트 보관 정책은 유지한다. v3 생산 뒤 구클라이언트의 복원 가용성이 사라질 수 있으므로 서버 업데이트뿐 아니라 새 클라이언트의 전체 복원·참조 재확인 구현/검증도 생산 활성화의 선행 조건이다. 구서버로의 복귀는 새 세트 읽기·보관에 영향을 준다. 이를 자동 롤백 금지 정책으로 추가하지 않고, 후속 활성화 판단에 한계로 전달한다.

## 구현 계약안

- worker v3 외곽 메타는 present content/trash의 v1 투영을 기존 정규화 함수로 대조한다. v3 원문은 엄격 JSON으로 읽으며 계정 digest·봉인·역할·present 파일 정확 집합을 검사한다. 미지/중복 multipart 파일과 absent 파일 혼입도 v3에서는 거절한다.
- 전송 이름은 content.db/trash.db/agent_chat.db/asset_mounts.json 한 벌을 backup_manifest에 두고 서버/NAS가 재사용한다. manifest에서 경로를 받지 않는다. absent는 파일·크기·해시가 없는 상태이며 ACK의 files와 실제 ZIP은 present만 담는다. 목록 role_metadata는 absent를 포함한 원래 명세를 보존한다.
- 기존 DB 파일 상한은 유지하며 Agent에도 적용한다. JSON은 1MiB, 최대 파일4개, 요청 전체는 DB3개+JSON1MiB+기존 multipart 여유다. 파일 수·개별/전체 크기·raw 요청 상한을 각각 검사한다. 이 상한은 설계값이며 실제 자료 크기 측정값이 아니다.
- 단계 폴더의 전체 파일을 검증한 뒤 공개한다. 같은 ID의 다른 manifest는 교체하지 않는다. ACK는 실제 manifest 판·해시 및 전체 present 파일의 크기/해시를 반환한다. 목록은 명세와 present 구성원 존재·크기를 확인하고, 최신 선택·지정 선택·활성화·ZIP은 전체 해시/SQLite/JSON 유효성을 재확인한다. 목록 조회마다 최대10세트의 대형DB를 다시 읽지 않으며 목록 표시 자체를 전체 무결성 재검증으로 주장하지 않는다.
- v3 거절 예외(ValueError/TypeError/KeyError/OSError/sqlite3.Error)는 적절한 실패로 처리한다. 수신 전 형식/내용 오류는 400, 크기 초과는413이며 성공 ACK·완성 세트가 남지 않는다. 파일 저장/공개 단계의 실제 I/O 실패는 성공으로 바꾸지 않고 기존 원본을 보존한다.
- NAS 서버 세트 검증·복사·재검증·경로 소유 판정·세트 단위 정리를 함께 확장한다. JSON 원문 바이트를 바꾸지 않는다. 로컬 백업/로컬 NAS는 기존 v1/v2를 유지하고 새 생성과 함께 후속 구현한다. 실 NAS·복제 스케줄은 실행하지 않는다.
- 클라이언트 ZIP 해제·설치·worker 전송의 v3 거절을 유지한다. capability를 공개하거나 형식 번호만 보고 생산을 켜지 않는다. UI의 새 구성원 표시·참조 재연결·Agent 종료/연결 회수·전체 롤백은 후속 소비자 묶음이며 1B 전체 완료로 보고하지 않는다.
- 독립 리뷰 뒤 반례 보강: 단일 latest의 후보는 이름이 유효한 완성 세트 폴더 전체다. content 파일이 있으면 기존 파일 mtime, 없으면 폴더 mtime으로 비교하며 선택된 content 누락 세트는409다. 세트 목록/폴더/content의 stat 접근 실패나 파일 자리에 디렉터리가 있어 순위를 안전하게 확인할 수 없으면409로 거절한다. 정상 v1/v2와 실제 더 최신인 단일 DB의 기존 선택은 유지한다. v3 trash 선검사의 SQLite 오류도400으로 바꾸되 v2 후단 검증의 기존 예외 전파는 보존한다. 목록의 roles는 present 파일 이름, role_metadata는 absent까지 포함한 전체 명세다.

## 근거·남은 것

- Claude 설계 응답은 도구0개 고정 원문 검토이며 실제 Fable5.2, 요청 high(실제 추론 수준 미확인)다. 총괄은 입력 제품7파일의 호출 전후 SHA256 동일을 확인했다.
- Codex는 `/latest`와 `server_restore`의404/405 fallback, 단일 head/회전을 원문으로 재확인했다. graft callers `_select_valid_set`은 ZIP 내려주기와 활성화의 두 호출을 가리키며 실제 소스와 대조했다.
- 현재 프런트 목록은 role_metadata를 그리지 않고 생성물 등 summary만 표시한다. UI의 구성원 표시와 미지원 복원 안내는 생산 활성화 전 후속 범위다. 자료를 찾았다는 것과 실제 복원이 가능하다는 것은 구분한다.
- 실제 Claude 후속은 자신의 `/latest`를 기존 동작으로 제외한다는 판단을 철회했고 Codex의409 차단에 동의했다. 목록의 과도한 반복 읽기를 피하도록 stat/전체 검증을 구분하고, manifest누락 후보도 숨기지 않는 것으로 명시했다. 바뀐 계약 `2d117eff0a35f420cb96fa772aa241ed383b61a76d2c01b333eff3b8b09bbec6`에 양측 실제 동의했다. 최신 후보인 기존 v1/v2의 manifest가 손상돼도409가 되는 보수적 변화이며 관련 시험을 확인한다.
- 구현자에게 전달할 추가 반례: NAS `.setpart-*`·`.setold-*` 잔재의 agent_chat.db, 버전별라우터2파일/기존합계 한도 유지, v3 multipart 중복/미지 역할, 현재 `/latest-set`의 손상 머리 다음 유효 세트 선택(기존 동작·기록할 한계)이다.
- implement 검사 통과 후 Codex `handoff_decisions_reconcile`에 제품/시험9파일만 배정했다. 문서·독립 리뷰·통합은 총괄 소유다. 원래1B 전체 범위는 유지하며 독립 리뷰는 설계/구현과 별도의 Claude 세션으로 진행한다. 이 시점의 시험·구현 완료를 주장하지 않는다.
