## 1. 복원한 DB 가 첫 기동에 DM 을 다시 보낼 수 있음 (J8 보완)

원인(코드로 확인): [일시 멈춤]은 지금 DB 의 `app_setting.slack_bot_config` 에 `paused` 를 쓴다(`backend/app/services/slack_client.py` `set_paused`). 옛 백업을 설치하면 설정이 백업 속 값(켜짐·안 멈춤)으로 돌아가, 서버를 켜는 순간 배달부가 돈다 — 관리자가 [다시 켜기]를 누르기 전. `tools/server_move.py install_set`(server_move_import --install)은 DB 세대값도 바꾸지 않아, 백업 뒤 이미 보낸 30분 안 코멘트 알림이 다시 나갈 수 있다. 앞서 넣은 문서 순서([일시 멈춤]→복원→[다시 켜기], `0bf6e1d2`)로는 막지 못한다.

설계:

- `backend/app/services/db_scrub.py` 에 `pause_slack_for_restore(db_path) -> bool` — **쓰기 가능한 설치 사본에만**. 기존 정제 함수(`strip_transfer_secrets`)와 같이 `sqlite3.connect` 뒤 `trash_transfer.configure_connection(conn)` 으로 열고(B1 보호 트리거를 통과하는 유일한 길), `BEGIN` → `slack_bot_config` 가 토큰(`data`)을 가진 dict 설정이면 **복원 표시 `restored=True` 를 남기고**, 아직 멈추지 않았으면 `paused=True`, `pause_reason='restored'` 도 쓴다(UPDATE 한 줄). 이미 멈춘 설정(수동·토큰 오류)은 `paused`·`pause_reason` 을 그대로 두고 표시만 더한다 → `COMMIT` → `PRAGMA wal_checkpoint(TRUNCATE)` → 닫기. 반환 = 바꿨는가(이미 표시가 있고 멈춘 설정은 False). 토큰 없음·JSON 이 아니거나 dict 가 아닌 설정·`app_setting` 이 없는 옛 DB 는 건드리지 않고 False.
- **오류는 삼키지 않는다** — B1 보호가 켜진 사본에 미완료 이전이 남아 있으면 UPDATE 가 `transfer_writer` 보호에 걸려 실패하는데, 그대로 올린다. `install_set` 의 [1/6] 은 이미 모든 예외에서 staging 을 지우고 journal 을 지운 뒤 다시 던지므로(기존 DB 는 아직 손대지 않은 단계) **설치가 거부되고 운영 DB 는 그대로**다. 즉 'B1 켜짐 + 백업 안에 이전 진행 중 + Slack 켜짐(토큰 있고 안 멈춤)' 세트는 이 도구로 설치되지 않는다(아래 결정 `b1-inflight-refused`). 지금 운영 코드에 B1 을 켜는 곳은 없다(잠재 경로).
- `tools/server_move.py install_set` 의 [1/6] staging 에서 content 사본을 만든 직후, **검사(`inspect_sqlite_database`) 전에** 부른다. 그래서 `staged_info`(설치 뒤 [5/6] 재검증의 기준)는 바꾼 뒤 값이고, UPDATE 는 행을 더하지 않아 행 수도 같다. 남은 WAL 이 있으면 검사가 실패하므로 체크포인트도 저절로 확인된다. 원본 패키지·백업 파일은 그대로다(사본만, `_verify_expected_sha` 두 번째 확인이 지킨다). 바꿨으면 "Slack 알림을 멈춤(복원됨)으로 설치 — 서버를 켠 뒤 관리 창 Slack 에서 다시 켜거나 토큰을 다시 등록" 을 출력한다.
- 다시 켜는 길(복원 표시는 아래 두 길에서만 지워진다):
  - [다시 켜기] = 기존 `set_paused(False)` → 'restored'·'manual' 은 'auth_error' 가 아니므로 막지 않고 `pause_reason` 을 비우며 `reset_floor()`(기준 시각 = 지금, 밀린 줄 닫기)를 부른다(지금 코드 그대로) + **복원 표시를 지운다**(한 줄 추가). 'auth_error' 는 지금처럼 막힌다(토큰 재등록으로).
  - **토큰 다시 등록**(예비 PC 로 복구하면 토큰이 안 풀려 `SERVER_RECOVERY.md` 가 다시 등록하라고 안내한다 · 'auth_error' 백업의 유일한 길): `save_config` 는 같은 팀이면 기준 시각을 두므로, 백업 속 기준 시각·밀린 줄(`auth_wait` 포함)이 살아 30분 안 코멘트가 다시 갈 수 있다 → `save_config` 에서 **옛 설정에 복원 표시가 있으면 같은 팀이어도 `reset_floor(reason='restored')`** (다른 팀이면 지금처럼 `team_changed`). 새 설정은 표시 없이 쓰므로 표시는 저절로 지워진다. 복원 표시가 없는 'manual'·'auth_error' 의 같은 팀 재등록은 지금처럼 기준 시각을 둔다(J7).
  - [일시 멈춤]·토큰 오류 멈춤(`set_paused(True…)`)은 표시를 그대로 둔다(설정 dict 를 고쳐 쓰므로).
- 관리 창은 '일시 멈춤'으로 보인다(문구는 바꾸지 않는다).
- 손으로 DB 파일을 덮는 복원은 이 보호가 없다 → `docs/SERVER_RECOVERY.md` 의 주의 상자를 "Slack 이 켜진 서버는 손 복사 대신 `server_move_import.bat … --install` 로 — 도구가 Slack 을 멈춤(복원됨)으로 설치하니 켠 뒤 [다시 켜기]" 로 고친다(앞의 '[일시 멈춤] 먼저' 순서 문장은 지운다 — 효과가 없다). 사본 READ_ONLY·예비 PC 토큰 재등록 문장은 둔다(재등록도 이제 기준 시각을 옮긴다고 덧붙인다).

## 2. 옛 판으로 내리면 mvhub:// 등록이 없는 실행 파일을 가리킴

원인(코드로 확인): 새 판 런처가 HKCU `Software\Classes\mvhub\shell\open\command` 에 `"<설치>\runtime\python\pythonw.exe" -I -S "<설치>\open_link.py" …` 를 등록한다(`run_agent_session.py register_open_link`). 공개판 패키지는 pythonw.exe 를 빼고 만든다. `runtime\python` 은 폴더째 바뀐다(`update_release_worker.bat` Get-UpdateComponents). 내리기(그리고 업데이트 실패 뒤 되돌리기)는 지금 설치된 새 작업자가 한다(`run_release_update.ps1` 이 설치 루트의 작업자를 같은 사용자로 부른다 — 지우는 HKCU 가 등록한 사용자의 것과 같다). 교체 목록은 들어오는 패키지에 있는 것만이라 등록이 그대로 남아, 링크를 누르면 Windows 가 없는 파일을 실행하려다 오류를 낸다. 새 판이 업데이트 중 한 번 켜진 뒤(등록) 준비 확인에 실패해 옛 판으로 되돌아가는 경우도 같다(되돌리기는 새로 생긴 파일을 치우므로 `open_link.py` 는 없어지고 등록만 남는다).

설계:

- **공용 잠금**: 런처의 등록과 작업자의 정리는 같은 이름 있는 뮤텍스 `Local\MVHubOpenLinkRegistration` 을 쥔 동안에만 등록을 읽고 쓰고 지운다(같은 사용자의 로그온 세션 안 — 런처와 작업자는 같은 사용자). 확인과 삭제 사이에 다른 설치의 런처가 정상 등록을 써서 그것까지 지우는 경합을 막는다.
  - 런처 `register_open_link(port, registry=None, lock=None)`: 잠금을 최대 2초 기다려 얻으면 지금처럼 비교·쓰기, 못 얻으면 이번 등록을 건너뛰고 False(시작은 막지 않는다 — 다음 실행에 다시 한다). `lock` 은 시험용 주입점(기본 = 실제 뮤텍스).
  - 작업자 `Clear-DanglingOpenLink`: 잠금을 최대 3초 기다려 얻은 뒤에만 읽고 지우며, 못 얻으면 경고하고 그대로 둔다.
  - 양쪽 다 **주인 없이 남은 뮤텍스(쥔 프로세스가 죽음)는 얻은 것으로 본다**(Python `WAIT_ABANDONED`=0x80, PowerShell `AbandonedMutexException`) — 못 얻음으로 보면 정리가 계속 막힌다. 얻었으면 `finally` 에서 반드시 놓는다(`ReleaseMutex` · Python 은 `CloseHandle` 도). 런처는 등록하는 동안만 쥐고 바로 놓는다(시작 내내 쥐지 않는다). 기존 `acquire_launcher_mutex` 는 '이미 있나'만 보는 방식이라 본뜨지 않는다.
- `update_release_worker.bat` 에 `Clear-DanglingOpenLink -Root <설치> [-KeyPath 'HKCU:\Software\Classes\mvhub'] [-MutexName 'Local\MVHubOpenLinkRegistration']` — `<KeyPath>\shell\open\command` 의 기본값을 읽어:
  - 첫 글자가 따옴표가 아니거나 닫는 따옴표가 없거나 경로로 풀리지 않으면(`[IO.Path]::GetFullPath` 실패) **그대로 둔다**.
  - 첫 따옴표 경로(실행 파일)를 `GetFullPath` 로 정규화해, `Root` 를 정규화하고 끝 `\` 를 붙인 접두사로 **대소문자 무시·폴더 경계** 비교(`<설치>-old` 같은 형제 폴더는 다른 설치) — 이 설치 안이고 **그 파일이 실제로 없을 때만** `<KeyPath>` 를 통째로 지운다.
  - 파일이 있거나(새 판), 다른 폴더를 가리키거나, 등록이 없으면 그대로. 어떤 실패도 경고만 하고 던지지 않는다.
  - junction 으로 들어온 설치는 런처가 `Path(__file__).resolve()` 로 등록해 경로가 안 맞아 지우지 않는다(안전한 쪽 — 잔여 한계로 남긴다).
- 부르는 곳 두 곳:
  - ① 메인 흐름에서 `Install-Package` 가 끝난 직후, 다시 켜기(`Restart-MvHubAndWaitReady`) 전 — 내린 판이 pythonw.exe 를 안 가져오면 지운다. `try { … } catch { 경고 }`.
  - ② 바깥 catch 에서 `Finalize-FailedInstall` try/catch 뒤, `$script:RecoveryState -eq 'rolled_back'` 일 때만, `try { … } catch {}` 로 감싸 원래 오류(`$InstallFailure`)를 가리지 않는다. 이 한 자리가 교체 단계 실패와 준비 확인 실패(새 판이 한 번 켜져 등록한 뒤) 모두를 덮는다. 되돌아간 판이 새 판(내리기 실패)이면 pythonw.exe 가 있어 그대로 둔다.
- 작업자 .bat 는 ASCII 만 쓴다(한글 안내는 넣지 않는다).
- 루트의 `open_link.py` 는 지우지 않는다: 옛 런처는 그 파일을 쓰지 않고, 다음에 새 판으로 올리면 패키지 것으로 바뀐다. 지우려면 교체·되돌림 장치에 '지움' 종류를 새로 넣어야 해 위험이 더 크다. 되돌리기 경로에서는 `Undo-ComponentSwaps` 가 새로 생긴 파일을 이미 치운다.
