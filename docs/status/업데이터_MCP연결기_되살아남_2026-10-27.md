## 설계

연결기 = **실행 파일이 `<설치본>\runtime\python\python.exe` 이고 명령줄의 '실행할 스크립트' 자리(첫 토큰 = 실행 파일, 그 뒤 등록 형식의 옵션 `-I`·`-S` 만 지난 첫 인자)가
`<설치본>\tools\mcp_adapter\server.py` 와 (대소문자 무시로) 정확히 같은 프로세스**(따옴표 유무만 허용 — `server.py.bak`·더 긴 경로·`other.py "<연결기 경로>"`·`-X "<연결기 경로>"` 처럼
다른 스크립트의 인자나 옵션 값은 아님 · 다른 옵션이 끼어 있거나 명령줄을 못 읽으면 앱으로 본다). 허브 `/app/setup` 이 Claude·Codex 에 등록하는 바로 그 명령이다(`routers/mcp.py`).
앱 = 그 밖의 설치본 소유 프로세스(지금 규칙 그대로). 연결기는 업무 DB 를 직접 열지 않는다(허브 HTTP 로만 — 프로필은 `%LOCALAPPDATA%`, 미리보기 HTML 은 호출자가 고른 폴더).
설치본 안에서 연결기가 잡는 것은 런타임의 실행 이미지(exe·dll·pyd)이고, 그것은 폴더 이름 바꾸기를 막지 않고 지우기만 막는다(아래 격리 실측 · Codex 1·2차 P3).

- `Test-McpConnector`(판별 하나) · `Get-MvHubProcessIds -Kind All|App|Connector`(기본 All = 지금과 같음).
- `Stop-MvHubProcesses`: 끄는 대상은 지금처럼 전부(연결기 포함 — 옛 코드로 계속 돌지 않게). **기다리는 판정은 앱만** — 앱이 0이면 끝, 연결기가 다시 떠 있으면 한 줄 남기고 계속.
  앱이 10초 안에 안 꺼지면 지금과 같은 실패(이름엔 앱만).
- `Wait-WorkerDrain`·`Start-MvHubAfterFailure`: 앱만 센다.
- `Remove-SwapLeftovers`: 이번 교체의 남은 폴더(와 `-IncludeQuarantine` 면 격리 폴더)를 지우고, **못 지운 것이 있으면 이 설치본의 연결기만 한 번 끈 뒤 다시 지운다**
  (그래도 남으면 지금처럼 경고 — 격리 폴더도 이제 경고). 연결기 끄기는 끄기 직전 신원(시작 시각)과 연결기 판별을 다시 확인한 뒤 핸들로 끄고, 실패해도 업데이트를 실패로 만들지 않는다.
  Claude·Codex 는 지금 파일에서 연결기를 다시 띄운다.
- `Finalize-FailedInstall`(새 앱이 준비 확인에 실패해 되돌릴 때): 되돌림(`Undo-ComponentSwaps`)·옛 버전 표지가 끝나고 복구 자산이 없는 경우에만 `Remove-SwapLeftovers`(격리 폴더 제외)를 부른다
  — 교체 단계 실패(`Install-Package` 안 catch)가 이미 하는 정리와 같다. 지금은 이 경로에서 정리를 안 해 `.rollback` 이 남고 다음 업데이트가 `recovery_required` 가 된다
  (원래 있던 빠짐 — 이 경로에선 새 런타임에서 되살아난 연결기가 `.rollback` 을 물기 때문에 함께 고친다, Codex 1차 P1).

### 구현 중 격리 실측에서 찾은 경합 — 되살아난 연결기의 바이트코드가 옛 자리를 되살린다(5판)

격리 실측(아래) 고친 쪽 5회 중 3회가 ③ 부분 교체 실패·④ 되돌림에서 `Move failed for runtime\python: destination already exists` 로 걸렸다(옛 쪽도 ④에서 같은 일).
남은 `runtime\python` 을 직접 보니 **`Lib\asyncio\__pycache__\base_events.cpython-314.pyc`·`Lib\__pycache__\selectors.cpython-314.pyc` 두 파일뿐** —
막 다시 떠서 모듈을 읽던 연결기가 폴더 이름이 바뀐 **뒤에** 컴파일 결과를 옛 경로에 쓰며(파이썬은 .pyc 를 쓸 때 빠진 상위 폴더를 만든다) 폴더를 되살렸다.
그러면 교체의 '새 것 → 제자리'·되돌림의 '옛 것 → 제자리' 옮기기가 실패하고, 되돌림 실패는 `recovery_required`(자동 재기동 없음)다.
새 판 런타임은 .pyc 가 없는 채(릴리스는 `__pycache__` 를 빼고 묶음) 깔려 처음 뜨는 연결기가 많이 컴파일하므로, 특히 새 앱 준비 실패 뒤 되돌림에서 일어날 수 있다.
옛 코드는 연결기가 되살아나면 끄기 단계에서 먼저 멈춰 이 경합까지 잘 안 갔다 — **이번 고침이 교체로 넘어가게 하므로 함께 막는다**.

- `Move-IntoPlace`: 교체(`Invoke-ComponentSwap`)의 새 것 → 제자리, 되돌림(`Undo-ComponentSwaps`)의 옛 것 → 제자리 옮기기를 감싼다(제자리 → `.previous`·`.rollback` 쪽은 그대로).
  최대 5번: 제자리에 무언가 있으면 **바이트코드만 든 폴더인지** 본다 — 폴더이고, 숨김 포함 전부 열거되고(열거 실패면 거부), 그 폴더와 안의 어떤 항목도 정션·심볼릭 링크가 아니고,
  파일이 모두 이름이 `__pycache__` 인 폴더 바로 안의 `*.pyc`·`*.pyc.<숫자>`(파이썬 원자 쓰기 임시)뿐(빈 폴더 포함). 아니면 지금처럼 'destination already exists' 로 실패.
  맞으면 이 설치본의 연결기를 끄고(`Stop-McpConnectors` — **끈 것의 종료를 모두 확인하지 못하면 실패**), 끈 **뒤에 다시 열거해** 여전히 바이트코드뿐일 때
  **그 .pyc 파일들만 지우고 빈 폴더만 안쪽부터 지운다**(재귀 삭제 없음 — 그 사이 다른 것이 생겼으면 지우기가 실패해 그 옮기기의 실패). 그다음 옮긴다.
  옮기기가 실패했는데 원본은 그대로이고 제자리가 다시 나타났으면(확인과 옮기기 사이에 또 생김) 처음부터 다시(5번까지).
  끈 뒤 다시 생기지 않는 근거: 되살리는 쪽은 이름 바꾸기 **전에** 뜬 연결기이고(실행 경로가 옛 경로로 보여 판별에 걸림), 새로 뜨는 연결기는 그 자리에
  `runtime\python` 이면 `python.exe` 가, `tools` 면 `server.py` 가 없어 시작하지 못한다(시작 때 쓰는 .pyc 는 `runtime` 쪽). Codex 5차 P1·P2.
- `Stop-McpConnectors` 는 '찾은 연결기가 모두 끝났음(신원이 바뀐 것은 건너뜀)'이면 참, 끄기·기다림·목록 실패가 있으면 거짓을 돌려준다(여전히 예외는 안 냄). 남은 폴더 정리는 지금처럼 결과를 무시한다.
