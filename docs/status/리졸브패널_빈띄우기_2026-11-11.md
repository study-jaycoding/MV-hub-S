"mv 리졸브에서는 트리만 뜨고, 내가 선택하면 리졸브 빈에 바로 떠서 거기서 끌어다 쓰게" → "그 방식으로"(2026-11-11 밤).

- 거르기(색·태그·생성자): 카드 칸이 없어졌으므로 **빈에 넣는 집합**을 거른다 — 앞서 권고한 '패널 보기만'은 카드 칸이 있을 때의 것이라 바꾼다(이 계약의 결정 1).

## 5판 — 1차 검토(Codex C1-1~8 · Claude 1~8) 반영 (이 절이 아래 '4판 흐름'보다 우선)

**소유(누가 넣은 항목인가) [C1-1 · Cl-1]**
- **미리 띄운 표시** = 기존 v1 표시(generation_id·project_id)에 `staged_by` 필드 하나를 더한 것. `staged_by` = 이 허브 키 = sha1(장치 id `device_identity` + 정규화한 `MEDIA_DIR`)[:16].
  기존 파서(`parse_mvhub_clip_metadata`)는 덧붙은 필드를 무시하므로 보내기·선택 감시와 호환. adopt 는 `staged_by` 없는 v1 표시로 다시 쓴다(되읽어 확인).
- **내 미리 띄운 항목** = 미리 띄운 표시의 `staged_by` 가 이 허브 키 **그리고** File Path(`_normal_path`)가 이 허브의 `MEDIA_DIR`(`_cached_source` 가 쓰는 바로 그 뿌리) 아래 **그리고** 그 파일이 이 PC 에 실제로 있음 — 셋 다일 때만 지우기·바꿔 끼우기 대상.
- 다른 허브 키의 미리 띄운 항목(같은 PC 의 다른 허브·다른 PC)은 `other_owner` — 지우지도 바꿔 끼우지도 넘겨받지도 않는다(상태 줄에 개수만). 표시 없는 사람 항목·NAS 경로 항목도 손대지 않는다.
- `MEDIA_DIR` 가 NAS 렌더 뿌리(`resolve_transfer_roots` 의 source_root)와 겹치거나 그 아래면 stage 를 하지 않고 "이 허브의 미디어 폴더가 NAS 와 겹쳐 리졸브 빈 띄우기를 쓸 수 없습니다".

**사용 횟수와 지우기 [C1-3 · Cl-2]**
- Usage 는 문자열을 정수로 읽어 **정확히 0 일 때만** 지우기 후보. 예외·빈 값·숫자 아님 = '쓰임 모름' → 보존.
- 지우기는 항목마다 **직전에 소유·Usage 를 다시 읽고**(사용자가 그사이 끌어 넣었을 수 있음) `DeleteClips([그 항목])` → 그 항목 id 가 빈에서 사라졌는지 되읽기.
- 복합 클립·Fusion·다른 타임라인 안 사용이 Usage 에 잡히는지, 그림·소리, 사용자가 동시에 끄는 경우는 **자동 지우기 실사용 전 필수 실측**(live 조건). 저장하지 않는 것은 undo·리졸브 자동 저장에 대한 보호가 아니다(결정 3).

**가져오기 자리 [C1-4 · Cl-4]**
- `ImportMedia` 는 리졸브 **지금 빈**에 넣는다. 그래서 **가져오기는 지금 빈이 목적 빈일 때만** 한다 — 처음 컷을 고를 때는 `target`(지금처럼 지금 빈을 목적 빈으로) 뒤에 stage.
  거르기 변경·15초 재조회 때 지금 빈이 목적 빈과 다르면 **가져오기를 보류**하고 상태 줄에 "새 공유물 N개 — 리졸브 지금 빈이 'C0160' 이 아니라 기다립니다 · [맞추기]"(누르면 target 뒤 stage). 임시로 빈을 바꿨다 되돌리는 길은 쓰지 않는다.
- 지우기·adopt 는 지금 빈과 무관(빈 객체·항목으로 직접).
- 스틸 그림은 기존 `_import_media_items` 규칙대로 한 건씩(이미지 시퀀스로 합쳐지지 않게).

**가져오기 부분 실패·같은 생성물 여러 항목 [C1-7]**
- 한 경로마다 `ImportMedia` 가 **정확히 1개**를 돌려주고 그 File Path 가 기대 경로와 같아야 성공. 이름(되읽기)·미리 띄운 표시(되읽기)가 실패하면 **방금 가져온 그 항목을 지우고**(Usage 0 확인 뒤) `import_failed`. 지우기도 실패하면 그 항목 id 를 결과에 싣고 다음 stage 가
  '표시 없음 + File Path 가 그 생성물의 기대 경로와 정확히 같음 + Usage 0' 인 항목을 다시 가져오지 않고 표시만 다시 찍어 이어 받는다.
- adopt 는 그 생성물의 **내 미리 띄운 항목 전부**를 처리하고, 전부 NAS 로 바뀌고 표시까지 확인돼야 성공(하나라도 실패면 실패 상태와 남은 항목 수).

**adopt 복구 기록 [C1-2 · Cl-3]**
- 바꿔 끼우기 **전에** 허브 데이터 폴더(`DATA_DIR/resolve_panel/adopt/<리졸브 프로젝트 id>/<항목 id>.json`)에 원자적으로 적는다: 리졸브 프로젝트 id·빈 id·항목 id·생성물·MV 프로젝트·이 PC 경로·NAS 경로·장부에 쓸 준비 기록(`_prepared` 와 같은 값). 장부까지 끝나면 지운다.
- adopt 가 항목을 찾는 순서: 복구 기록의 항목 id(그 빈 → 없으면 `MV Hub` 아래 전체) → 내 미리 띄운 표시 → 표시 없음 + File Path == 준비된 NAS 경로(정규화 비교). 찾은 항목이 이미 NAS 면 바꿔 끼우기를 건너뛰고 표시·저장·장부만(멱등).
- 되읽기 비교는 모두 `_normal_path`(Z:\ 와 \\NAS 차이로 잘못 replace_failed 가 나지 않게).
- 끊긴 adopt(바꿔 끼운 직후 종료·표시 실패·저장 실패·장부 실패·허브 재시작)는 다음 패널 열기(`inventory` — 아래)가 이 리졸브 프로젝트의 복구 기록을 먼저 돌려주고 화면이 같은 adopt 를 다시 부른다(준비 기록은 복구 기록에서 되살림 — 메모리 `_prepared` 가 없어도).

**패널을 열 때 — 읽기 `inventory` + 프로젝트별 쓰기 [C1-5 · Cl-6 · Cl-7]**
- `sweep` 대신 **읽기 전용 `inventory`**: `MV Hub` 아래를 훑어 내 미리 띄운 항목(리졸브 프로젝트·빈 id·항목 id·생성물·MV 프로젝트·Usage)과 이 리졸브 프로젝트의 복구 기록을 돌려준다. 쓰기 호출 0, 최대 500개(넘으면 `more`), 시간 제한 20초(넘으면 결과 없음 = 판단 안 함).
- 허브는 항목의 MV 프로젝트마다 **열람 권한**을 확인하고(못 보면 버림), 생성물의 `folder_path` 는 **DB 에서** 정한다(빈 이름에서 거꾸로 만들지 않음).
- 화면은 그 결과로: Usage>0 → 그 생성물마다 prepare(DB 의 folder_path) → adopt{bin_id, 항목 id 들}(adopt 는 받은 빈·항목을 다시 확인) · Usage 0 → `unstage`{project_id, folder_path(DB), bin_id}. 둘 다 그 MV 프로젝트의 복구 관문·권한을 지나는 보통 쓰기.
- `unstage`(= gen_ids 없는 stage)도 프로젝트 권한 검사를 건너뛰지 않는다.

**창 하나만 쓴다 [C1-6 · Cl-5]**
- 쓰기(stage·unstage·target·prepare·adopt)는 **쓰기 담당 창 하나**만: 허브가 문맥마다 마지막으로 `identity` 를 다리와 함께 연 창 id 를 담당으로 두고(새 창이 넘겨받음), 다른 창의 쓰기는 `other_window`("다른 MV 창이 리졸브를 맡고 있습니다") — 그 창은 읽기 전용으로 바뀐다.
- 담당 창의 **지금 컷 빈**은 허브가 기억해 inventory 뒤의 지우기에서 빼고, stage 순번은 (문맥, 창, 목적 빈)별 채널 — 앞 컷 정리가 새 컷 선택 때문에 stale 이 되지 않는다.
- 컷을 옮기면 앞 컷 정리(쓰인 것 adopt → 안 쓴 것 unstage)는 **선택과 떨어진 작업 줄**에서 끝까지 한다(`alive(selection)` 에 묶이지 않음). 실패해도 컷 이동은 막지 않고 실패만 상태 줄에 남긴다(다음 inventory 가 다시 잡음).
- 빠른 A→B→A: A 로 돌아왔을 때 A 의 정리가 아직 돌면 그 정리가 끝난 뒤 stage(A)(같은 빈 채널 순서).

**current-bin 요청 [C1-8 · Cl-7]**
- `GET current-bin` 에 선택 항목 `project_id`·`folder_path` 를 더한다 — 있으면 목적 빈의 내 미리 띄운 항목 중 Usage>0 생성물 id(최대 200개 읽기). 시간 제한(8초)·busy·실패면 `used` 없이 — '쓰인 것 없음'으로 보지 않는다.

**선택 따라가기 [C1-8]**
- 미리 띄운 항목은 장부가 없어, 이 PC 로컬 DB 에 없는 공유 생성물은 리졸브 선택 따라가기(`resolve_selection_monitor`)가 **adopt 뒤부터** 연결된다 — 미리 띄운 동안은 지원하지 않음(제한으로 명시, 감시 코드는 안 바꿈).

### 5판 2차 보완 (Codex C2-1~7 · Claude 2차 1~5 — 위 5판 문장과 다르면 이것이 우선)

- **표시에 항목 id [C2-2]**: 미리 띄운 표시 = v1 표시 + `staged_by` + `item_id`(가져온 직후의 그 항목 `GetUniqueId`). '내 미리 띄운 항목'은 위 세 조건에 더해 **표시의 item_id == 지금 항목 id** — 메타데이터를 지닌 채 복제된 항목은 id 가 달라 빠진다(복제본 시험).
- **패널 표시는 원문으로 쓰고 확인 [C2-5 · Cl2-2]**: 기존 `stamp_and_verify`(두 id 만 비교 — 일반 보내기용, 바꾸지 않음) 대신 패널 전용 쓰기·되읽기: stage 는 원문 JSON 의 `staged_by`·`item_id` 까지 같아야 성공, adopt 는 그 둘이 **없어진** v1 표시까지 되읽어야 성공. 일반 보내기 표시 동작은 그대로(회귀 시험).
- **표시 없는 항목은 기록이 있을 때만 [C2-1]**: 위 5판의 '표시 없음 + 기대 경로 + Usage 0 이어 받기'와 adopt 의 '표시 없음 + NAS 경로' 찾기는 **없앤다**. 대신 가져오기 뒤 이름·표시가 실패하고 지우기도 실패하면 그 항목(리졸브 프로젝트 id·항목 id·기대 경로)을 허브 기록(`DATA_DIR/resolve_panel/import/…`)에 남기고, 다음 stage 는 **그 기록의 항목 id 와 일치할 때만** 표시를 다시 찍어 이어 받는다. ImportMedia 가 돌려준 항목이 이미 있던 항목인지 불분명하면(가져오기 전 빈 항목 id 목록에 있었으면) 지우지 않는다. 기록 없는 표시 없는 항목은 모두 보존.
- **복구 직전 재확인 [C2-4]**: adopt 복구 기록에 문맥의 계정 키·허브 키를 함께 적고, 이어 받기 직전 그 항목의 File Path 가 기록된 이 PC 경로 또는 NAS 경로인지, 다른 생성물의 유효 표시가 없는지 본다 — 어긋나면 `conflict` 로 두고 자동으로 고치지 않는다(사용자가 다른 파일로 다시 연결·다른 표시로 바꾼 것을 덮지 않음).
- **쓰기 담당은 허브 전체에 하나 [C2-3 · Cl2-1]**: 문맥마다가 아니라 리졸브를 같이 쓰는 이 허브 전체에 담당 하나(계정이 다른 두 창도 하나만). `identity` 에 창 id 와 `claim`(처음 열기에서만 true)을 싣고, **폴링(claim 없음)은 담당을 바꾸지 않는다**. 담당은 ① 처음 열기 ② 다른 창의 [넘겨받기] ③ 담당 창의 폴링이 15초 넘게 끊긴 뒤의 처음 열기·넘겨받기 — 에서만 바뀐다.
  넘겨받기는 진행 중인 변경 작업이 끝난 뒤(변경 잠금을 잡은 뒤) 담당 세대를 올려 확정하고, 대기하던 쓰기 요청은 **실행 직전(잠금 안에서) 담당 세대를 다시 확인**해 다르면 other_window. 다른 창은 "다른 MV 창이 리졸브를 맡고 있습니다 · [넘겨받기]".
- **inventory 이어 보기 [C2-6]**: 결과를 (빈 경로, 항목 id) 순으로 정렬하고 한 번에 500개, 다음 쪽은 `after`(마지막 (빈 경로, 항목 id)) — 화면은 끝까지 쪽을 넘기며 처리한다(각 쪽은 읽기). 501개 이상에서 뒤쪽 쓰인 항목까지 처리되는 시험.
- **200 상한 [Cl2-5]**: 한 컷의 공유물이 200개를 넘으면 앞 200개(생성 시각 오래된 순 — 새 항목이 앞에 끼어 들락날락하지 않게)만 가져오고, 그때는 **지우기를 하지 않는다**.
- **되돌리기(undo) [C2-7]**: 바꿔 끼우기를 사용자가 되돌렸을 때 자동 회복을 **보장하지 않는다** — 되돌린 뒤의 경로·표시·항목 id 는 실측 전(live)이고, 의도적인 되돌리기를 MV 가 곧바로 다시 적용하지 않는다. 표시가 v1(소유 필드 없음)인데 이 PC 경로인 항목은 '내 미리 띄운 항목'이 아니므로 자동으로 손대지 않는다(상태 줄에 '확인 필요' 개수).
- **기존 항목은 손대지 않음 [C3-1]**: ImportMedia 가 돌려준 항목이 가져오기 전부터 빈에 있던 항목이거나 새 항목인지 확정할 수 없으면 **이름 바꾸기·소유 표시 쓰기·지우기·가져오기 기록 등록 모두 하지 않는다**(그 생성물은 `import_failed`). 기존 항목 반환 시험에서 넷 다 0.
- **가져오기 복구도 재확인 [C3-2]**: 가져오기 기록에 계정 키·허브 키·리졸브 프로젝트 id·생성물·기대 경로·항목 id 를 묶고, 다음 stage 가 이어 받기 직전 ① 계정·허브·리졸브 프로젝트가 같고 ② File Path 가 기대 경로이고 ③ 다른 유효 표시·다른 소유 표시가 없을 때만 표시를 다시 찍는다 — 아니면 `conflict` 로 두고 고치지 않음(다른 파일로 재연결·다른 표시·계정 전환 뒤 재시도 시험).
- **다른 PC 가 띄운 항목이 있을 때 [Claude 3차 참고]**: other_owner 항목은 stage 의 '이미 있음'으로 치지 않는다 — 이 PC 사본을 따로 가져와 이 PC 에서 쓸 수 있게 한다(같은 빈에 다른 PC 의 것과 둘이 보일 수 있음, 다른 PC 의 것은 손대지 않음).
- **허브 키가 바뀌면 [Cl2-3]**: `device_identity.json` 이 새로 만들어지거나 `MEDIA_DIR` 가 바뀌면 예전 미리 띄운 항목은 other_owner 가 되어 자동 정리·옮기기에서 빠진다(쓰인 것도 이 PC 경로로 남음) — 위험으로 명시, 상태 줄에 개수.

## 4판 흐름 (기록 — 위 5판이 우선)

리졸브 밖(끌기 다리 `window.mvhubResolve` 없음 = 일반 브라우저)은 지금처럼 **읽기 전용** — 트리·거르기만 보이고 아래 쓰는 요청은 하나도 부르지 않는다.

1. **컷 고르기**: `cache`(이 PC 로 받기 — 지금 그대로) → **`stage`** {문맥·창·순번, project_id, folder_path, gen_ids(거르기를 지난 그 컷 공유물, 최대 200 — 넘으면 앞 200 + 안내)}.
   허브는 gen_ids 를 권한 확인으로 불러 **허브가 정한 이 PC 원본 경로**(`_cached_source` — 화면이 보낸 경로를 쓰지 않음)와 클립 이름(`작성자 · 모델 · 길이`)을 자식에 넘긴다. 자식은:
   목적 빈(없으면 만듦 — 이제 컷을 고를 때 만든다) → 지금 빈으로 → 빈 안 미디어 항목을 표시로 분류 →
   · 원하는 생성물 중 **표시가 있는 항목이 이미 있으면 그대로**(이 PC 경로든 NAS 경로든) · 없으면 `ImportMedia([경로])` → 이름(되읽기) → 표시(`stamp_and_verify`)
   · **미리 띄운 항목**(MV 표시 + File Path 가 이 PC 캐시·미디어 뿌리 아래) 중 원하는 집합 밖이고 `Usage == 0` 인 것만 `DeleteClips` — 사람이 넣은 것·NAS 경로·쓰인 것·다른 생성물 표시는 건드리지 않음.
   저장하지 않는다(가져오기·지우기만 — 저장은 사용자 몫, adopt 때만 저장).
2. **쓰인 것 알아채기**: 2초 `current-bin`(읽기 전용)에 목적 빈의 미리 띄운 항목 중 `Usage > 0` 인 생성물 id 를 더해 돌려준다(목적 빈이 있을 때만 — 쓰기 호출 0).
3. **adopt(바뀜)**: 화면이 쓰인 생성물마다 `prepare`(NAS 복사 — 지금 그대로) → `adopt`. 자식은 목적 빈에서 그 생성물 표시 항목을 찾아
   · 이 PC 경로면 `ReplaceClip(NAS 경로)` → File Path 되읽어 NAS 경로인지 → 표시 다시 찍기(지워지므로) → guard → `SaveProject` → 장부(`record_adoption` 그대로, 결정적 transfer_id)
   · 이미 NAS 경로면 표시·저장·장부 확인만(멱등) · 다른 생성물 표시면 `conflict` 그대로 · 항목이 없으면 `not_seen`.
   상태에 `replace_failed`(바꿔 끼우기 거절·되읽기 불일치)를 더한다 — 실패류는 지금처럼 즉시 멈춤·[다시].
4. **컷을 옮길 때**: 앞 컷에 `stage` {gen_ids: []}(= 그 빈의 안 쓴 미리 띄운 항목 지우기). 그 전에 그 컷의 쓰인 항목은 adopt 가 끝났는지 보고, 남았으면 adopt 를 먼저 끝낸다.
5. **거르기를 바꾸면**: 지금 컷에 `stage` 를 새 집합으로 다시(새로 맞는 것 가져오기·안 맞게 된 안 쓴 것 지우기).
6. **자동 갱신(15초·초점)**: 목록이 늘면 `stage` 를 다시(새 항목만 가져옴). 같은 컷 재조회에서 target 을 반복하지 않는 규칙(1d4fe377)은 그대로 — stage 는 지금 빈을 다시 맞추지 않고 목적 빈에만 쓴다.
7. **패널을 열 때 `sweep`**: `MV Hub` 아래 모든 빈의 미리 띄운 항목을 훑어 `Usage > 0` 은 adopt 대상 목록으로 돌려주고(화면이 차례로 prepare·adopt), `Usage == 0` 은 지운다(지금 고른 컷의 빈은 제외).
   → 패널을 닫은 채 리졸브에서 끌어 쓴 것도 다음에 패널을 열면 NAS 로 옮겨진다. **남는 빈틈(명시)**: 패널을 다시 열기 전까지 그 클립은 이 PC 경로 — 이 PC 에서는 재생되지만 다른 PC 가 그 프로젝트를 열면 미디어 없음.

## 범위 밖 · 남는 위험

- 빈 컷 빈: 안 쓴 것을 다 지우면 그 컷 빈이 비어 남는다(지우지 않음 — `DeleteFolders` 실측 전).
- 같은 생성물을 일반 '리졸브 보내기'로도 보내면 같은 빈에 NAS 항목이 하나 더 생길 수 있다(표시가 같은 생성물이라 conflict 는 아님).
- 미리 띄운 항목을 사용자가 다른 빈으로 옮기면 stage·current-bin 은 못 보고, inventory 가 `MV Hub` 아래에서만 잡는다 — `MV Hub` 밖으로 옮긴 항목은 영영 잡히지 않는다(이 PC 경로로 남음).
- 큰 컷(수백 개) 가져오기 시간·그림/소리 항목의 Usage·리졸브 UI 를 쓰는 중의 가져오기 — 첫 실사용 실측에서 확인.
- 사용자가 Ctrl+Z 로 바꿔 끼우기를 되돌리면 장부는 NAS 인데 프로젝트는 이 PC 경로일 수 있다 — 자동 회복은 보장하지 않는다(2차 보완). API 의 가져오기·지우기·바꿔 끼우기가 리졸브 되돌리기 목록에 들어가는지는 실측 전.
- 허브 키(장치 id·MEDIA_DIR)가 바뀌면 예전 미리 띄운 항목은 자동 정리·옮기기에서 빠진다(2차 보완).
- 미리 띄운 동안은 선택 따라가기 미지원(adopt 뒤부터).
