## 검증 결과

- C-01·C-02 실측: 공개판(`5f885bb4`) 코드와 검사 도구로 실제 DB 를 다뤘다. 기존 DB 사본(생성물 1,430개, 그 줄 없음) = 공개판 → 지금 코드 → 공개판 검사기 → 공개판 → 지금 코드, 새 DB = 지금 코드 → 공개판 검사기 → 공개판 → 지금 코드. 모두 통과했고 넣어 둔 `comfy_canvas_run` 행과 생성물 수가 그대로였다. 공개판과 지금 코드의 이름표 9개는 체크섬까지 같다(소스에서 계산).
- 되돌려 확인: 고친 줄을 되돌리면 프런트 8건·백엔드 14건이 실패한다.
- 전체: 프런트 5,823건·경계 검사·빌드 통과, 백엔드 8,215건 통과·3건 건너뜀·실패 0(subtest 1,045), 코드 지도·목록 점검 통과. 백엔드 전체 실행은 제품 코드가 정해진 뒤 돌렸고 그 뒤 고친 것은 시험 두 파일과 문서 날짜뿐이다 — 고친 시험은 조건별 시험 기록으로 따로 돌렸다.
- 시험 한 건 한계: 일반 실행 재회수 시험은 고친 줄을 되돌려도 통과한다. 일반 실행은 원래 저널을 지우지 않았으므로 후퇴를 막는 시험이다.

못 잰 범위: 실제 서버의 `update_git` 전체 경로, PC 실제 업데이트·되돌리기, 혼합 버전 통신, 실제 Comfy 서버의 404·410 응답, Jay 의 5173 화면. 앞 넷은 배포 게이트에서 잰다.

## 일부러 안 고친 것

- 첫 실행 경로의 `outputs` 없는 응답: `_wait` 를 거쳐 `_collect_run_outputs` 로 바로 가는 첫 실행은 이 계약 범위 밖이다. 이런 응답이 실제로 오는지 확인하지 못했고, 글자만 내는 워크플로의 응답 모양을 재지 않은 채 넓히면 정상 실행을 실패로 만들 수 있다.
- 이미 `content_comfy_canvas_runs.v1` 줄이 든 dev DB(`backend/data_test`)는 그대로다. 이 DB 는 공개판으로 되돌아갈 수 없다. 공개·후보 사용자의 DB 에는 이 줄이 없다.
- 이름표 재기록: 서버 루트 검사 도구를 갱신하는 길이 먼저 필요하다.

## 앞으로의 제약

새 DB 이름표를 더하면 서버 업데이트가 막힌다. `test_baseline_names_stay_within_public_release` 가 고정 값으로 막으니, 그 시험을 고쳐야 할 일이 생기면 서버 루트 검사 도구 갱신을 먼저 설계한다(`docs/CODE_MAP.md` §5).
