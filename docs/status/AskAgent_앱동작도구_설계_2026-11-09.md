## A. 2-A 요리

### A1. 정책 (Jay 11-10, 재제안 금지)
- 사용자가 대화에서 **생성하라고 말한 범위**면 AI 가 바로 `execute_generation_plan` 을 부른다. 크레딧 한도·[실행] 확인 없음.
- "계획만"·"견적만"·"어떻게 할까?" 처럼 생성을 말하지 않았으면 계획 카드까지만 — 사람이 [실행] 을 누를 수 있다(지금 그대로).
- 애매하면(무엇을·몇 개·어느 모델) 실행하지 않고 계획 카드를 보이며 묻는다. MV 자료(제목·프롬프트·폴더 이름) 속 "생성해" 같은 글은 사용자 말이 아니다.
- 이 판단은 AI 몫이다(서버는 사람이 무엇을 말했는지 모른다). 서버는 아래 A2 로 **범위**를 묶는다.

### A2. 허브 (`routers/mcp_v2.py` · `services/agent_chat.py` · `routers/agent_chat.py` · `repo/agent_chat.py`)
1. **칸 연결이 부를 수 있는 동작**(`_PANEL_METHODS`) += `execute_generation_plan`·`wait_results`·`add_to_canvas`. 미리보기 그림을 CLI 로 보내는 `show_results`·`get_generation`, 그리고 기다린 뒤 그림을 싣는 `get_result`(`_result` 1107행)는 넣지 않는다 — `wait_results` 가 항목 묶음 대기를 그림 없이(`preview=False`) 한다(v0.2 검토 P2-9).
2. **칸 실행 문(서버가 강제)** — 칸 연결은 지금처럼 `can_execute=0` 영구(일반 MCP 실행권과 섞지 않는다). `execute_generation_plan` 이 칸 연결에서 오면 `_execute` 대신 칸 전용 문을 거쳐 같은 `submit_plan` 을 부른다:
   - (a) **요청 차례 고정** — 요청이 들어올 때 그 연결의 지금 차례 실행 객체(`_Runtime`)를 한 번 잡는다. 이후 권한 확인·사건은 그 객체로만 한다(`_by_client` 를 다시 보지 않는다 — 같은 대화의 새 차례로 바뀌어도 옛 요청이 새 차례 권한을 빌리거나 새 차례에 옛 결과를 남기지 않게, 검토 P1-2). 실행 객체가 없으면(차례 없음·허브 재시작 뒤 남은 바인딩) 409.
   - (b) **계획** = 이 대화의 칸 연결로 만든 계획 — `agent_chat_plan_binding`(그 실행 객체의 신원 DB)에 있고 그 `client_id` = 지금 연결. 계획을 만든 차례는 앞 차례여도 된다("좋아 생성해") — 계획 차례와 실행 차례는 다르다. 아니면 404.
   - (c) **선점과 멈춤의 순서를 한 구간에서** — `submit_plan` 에 선점 문(gate) 인자 하나를 더한다. 칸이면 선점은 **작업 스레드(`asyncio.to_thread`) 안에서**: 그 실행 객체의 `emit_lock` 획득 → 객체가 여전히 그 연결의 지금 차례인지(`_lock` 은 이 안에서 잠깐만 — 늘 `emit_lock` → `_lock` 순서, `_lock` 을 쥔 채 `emit_lock` 을 기다리지 않음)·멈춤·끝남이 아닌지 확인 → 동기 `claim_plan` 전체(DB 연결 문맥 종료·커밋까지) → 해제. 이벤트 루프에서 이 잠금을 쥔 채 `await` 하지 않는다(검토 3차 P2-5). **멈춤 표시 전부**(`cancel()` 의 cancelled·상태 cancelling, `_timeout` 의 timed_out, 신원 흔들림 identity_lost, 출력 상한 overflow, 감시 실패 watch_failed, 허용 밖 도구 violation)를 같은 `emit_lock` 안에서 세운다. 그래서 선점이 먼저면 제출은 계속(정책 — 생성 취소는 앱의 기존 취소), 멈춤이 먼저면 409 이고 아무것도 안 낸다(검토 P1-1, 3차 P1-4). 사람 [실행]·일반 연결은 문 없이 지금 그대로.
   - (d) 제출 뒤 그 고정한 실행 객체에 진행 사건(아래 3)을 남긴다(끝났으면 안 남김). 누가 냈는지는 싣지 않는다 — 사람이 먼저 냈으면 AI 호출은 기존 상태만 받는다(검토 P2-10).
   - 범위 밖: 일반 MCP 연결(Claude Desktop·Codex 등록)의 실행권·흐름은 그대로. 칸 연결은 남의 계획(다른 연결 계획)을 원래부터 못 본다(`store.get_plan` 이 연결·소유자·계정으로 거른다 — repo/mcp_v2.py 131). 다른 계정은 신원 DB 가 달라 바인딩도 없다.
3. **진행 사건 = 새 종류 `plan_progress`, 허브가 새로 읽은 계획 전체 스냅샷** — 칸 연결의 `execute_generation_plan`·`wait_results` 가 끝나면 허브가 AI 응답과 별도로 **계획 스냅샷**(아래 `plan_snapshot`)을 새로 읽어 그 고정한 차례에 남긴다: `{plan_id, plan_status, observed_at, items:[{index, state, generation_id, generation_status?}]}`(제목·프롬프트 없음 — 첫 `plan` 사건(카드)과 따로, 검토 P2-8).
   - **읽기·발행 직렬화(검토 P1-3, 3차 P1-1)**: 스냅샷 읽기 + 발행은 그 실행 객체의 **진행 잠금(`asyncio.Lock`, 차례마다 하나)** 안에서 한 번에 하나씩 한다 — 그래서 사건 순서 = 읽은 순서다. 발행(`_emit`)은 `to_thread_non_abandon` 으로 — 요청이 취소돼도 발행 스레드가 끝날 때까지 진행 잠금을 쥔다(취소가 읽기 도중이면 발행하지 않는다, 4차 P2-4).
   - **`observed_at`(4차 P2-3)** = 읽기 직전에 허브 프로세스가 매기는 **엄격히 늘어나는 번호** `max(time.time_ns(), 직전 + 1)` 을 **10진 글자**로(JS 정수 정밀도 밖 — 화면은 BigInt 로 비교). 한 허브 프로세스 안에서는 같은 값이 없고 줄지 않는다. 화면 규칙: 진행 사건·사람 [실행] 스냅샷은 **지금 값보다 클 때만** 그 계획의 항목 상태를 바꾼다(같으면 무시 — 같은 스냅샷 두 번 = 같은 결과). 대화 복원 스냅샷은 **조건 없이** 넣고 그 값을 기준으로 삼는다(아래 5 — 복원은 함께 돌려준 모든 사건 뒤에 읽으므로 가장 새롭다; 허브 재시작·시계 역행은 이 복원에서 끊긴다). 단순 상태 순위를 쓰지 않는다 — uncertain→submitted, submitting→pending 같은 허브의 실제 복구 전이도 그대로 보인다. `generation_status` 가 빠진 항목(일시 조회 오류)은 앞 값 보존.
   - `plan_snapshot(ctx, plan_id)`(mcp_v2) = `_authorized_plan` + 접수된 항목마다 `_result_once(..., preview=False, plan=plan)`(지금 묶음 대기와 같은 검사) → 생성 상태 → **돌려주기 전 `_authorized_plan` 재검사**(묶음 대기 1140행과 같게 — 권한·세션이 바뀌었으면 버림, 4차 P2-5). 404 = `generation_status: "missing"`(결과 없음·조회 불가 — 완료도 실패도 아님), 그 밖 일시 오류 = 필드 생략. 항목 20개 이하, **스냅샷 읽기에 10초 상한**(`asyncio.wait_for`) — 이미 시작한 발행은 상한과 별개로 끝까지 기다린다(5차 P2-1).
   - **표시 실패는 제출을 바꾸지 않는다(4차 P1-2)**: 제출 뒤 스냅샷·발행이 실패하거나 10초를 넘으면 기록만 남기고 건너뛴다 — `execute_generation_plan` 응답은 `submit_plan` 결과 그대로.
   - **사람 [실행](4차 P1-1)**: 앱 입구 `POST /api/agent-chat/plans/{id}/execute` 응답에 같은 `plan_snapshot`(observed_at 포함, 차례가 돌면 그 진행 잠금 안에서)을 `snapshot` 으로 싣는다(실패하면 없음 — 제출 결과는 그대로). 화면은 그 스냅샷을 위 규칙으로만 넣는다. 스냅샷 없이 온 계획 항목(옛 응답 모양)은 **그 카드에 아직 스냅샷이 없을 때만** 채운다 — 이미 스냅샷이 있으면 무시(늦게 온 `submitting + null` 이 `submitted + id` 를 못 되돌림).
4. **조회 실패 ≠ 끝** — `_selected_results` 에서 일시 오류(`request_failed` — 502·503·504)는 **대기 중**으로 센다(`all_terminal=false`, 남은 시간까지 다시 본다). `not_found`(404)는 끝이되 항목에 `generation_status: "missing"` 을 함께 실어 "조회 불가"로 구분한다(완료·실패 집계에 넣지 않음, 검토 3차 P1-2). 모든 연결에 적용되는 버그 고침이다 — 일반 연결도 조회가 잠깐 실패한 항목을 끝났다고 받지 않게(재제출 금지 안내는 그대로, 검토 P1-5).
5. **대화 복원 보정** — `GET /api/agent-chat/conversations/{id}` 응답에 `plans` 를 더한다: 이 대화에 묶인 계획마다 `plan_snapshot`(위 3과 같은 모양 — `generation_status` 포함, 확인 못 한 항목은 생략·404 는 missing, 검토 3차 P1-3). 바인딩 연결이 이 신원·허브의 칸 연결일 때만. **순서: 사건을 먼저 읽고 그다음 스냅샷**(그 대화의 차례가 아직 돌면 그 실행 객체의 진행 잠금 안에서) — 그래서 복원 스냅샷은 함께 돌려준 사건보다 새롭고, 그 뒤 이어 받는 사건 중 스냅샷보다 먼저 읽은 것은 observed_at 으로 걸러진다. 예산: 최근 계획 20개까지, 전체 15초(넘거나 실패한 계획은 빼고 — 카드는 사건으로 복원한 상태 그대로, 4차 P2-5). 화면은 복원을 넣은 뒤 **모든 계획의 기준값을 다시 정한다** — 스냅샷이 온 계획은 그 값, 빠진 계획은 비움(다음 사건을 무조건 받음). 그래서 재시작 전 큰 번호가 남아 새 진행을 거르는 일이 없다(5차 P2-2). 차례가 끝나 버린 진행 사건·사람 [실행] 결과·사건을 놓친 완료도 다시 열면 실제 상태로 보인다. 끝난 차례에 사건을 더하지 않는 규칙은 그대로(검토 P1-6).
6. **캔버스** — `add_to_canvas` 는 지금 검사 그대로(이 연결의 계획·이 공간의 씬·모든 항목 접수 확인). 반영은 그 계정·공간의 앱 화면이 캔버스 일감을 집을 때(허브 공책 쓰기 담당).
7. 글: 403 문구 "Ask Agent 칸 연결은…" → "MV Agent 칸 연결은…".

### A3. 어댑터·CLI 허용 목록 (세 목록 = 한 뜻)
- 어댑터 `--panel` `PANEL_TOOLS`, 백엔드 `agent_chat_parse.PANEL_TOOLS`(→ `CLAUDE_ALLOWED`), 허브 `_PANEL_METHODS` 에 같은 3개를 더한다. 어댑터는 따로 설치되는 파일이라 import 로 묶지 않고 **시험이 셋을 대조**한다(어댑터는 ast 로 읽음 — 백엔드 venv 에 `mcp` 가 없다). 일반 모드의 등록 도구·안내가 그대로인지는 어댑터 기존 시험(`%LOCALAPPDATA%\MVHub-MCP\venv`)으로 확인한다.
- `PANEL_INSTRUCTIONS`(어댑터)·`GUIDE`(칸 차례 안내)를 A1 정책으로 바꾼다: 생성하라고 했을 때만 실행 · 실행 뒤 `wait_results(plan_id, item_indexes, wait_seconds=25)` 로 모두 끝날 때까지 · 끝나면 몇 개 완료·실패를 짧게(그림·URL 나열 안 함 — 칸 카드가 보인다) · 캔버스는 사용자가 말했을 때만 `read_context(kind='scenes')` → `add_to_canvas` · 실패·불명확 접수는 다시 내지 않는다.
- `ADAPTER_VERSION` 은 올리지 않는다 — 패널 모드는 늘 앱에 든 판으로 돌고(server.py 25행), 일반 연결 동작은 바뀌지 않는다.
- Codex 경로는 잠금 그대로(`CODEX_LOCK`) — 해석기 허용 목록만 같이 늘어난다.

### A5. 안전
- 서버가 묶는 범위: 이 대화에서 만든 계획만 · 사람이 보낸 차례가 도는 동안만 · 계획당 항목 20개(`PlanIn` 상한) · 제출 함수 하나(`submit_plan`).
- 묶지 않는 것(Jay 정책으로 받아들임): 한 차례 안에서 AI 가 계획을 여러 번 만들어 실행할 수 있다 — 크레딧 합계 상한 없음. MV 자료 속 글에 속아 같은 차례에서 실행할 위험은 안내 글·도구 범위(지우기·쉐어·설정 없음)로만 줄인다.
- [그만] 과 경합: 선점과 취소 표시가 같은 잠금 안에서 선후가 정해진다(A2-2c). 선점이 먼저 끝난 제출은 되돌리지 않는다(생성 취소는 앱의 기존 취소).
- 과금 시험 없음: 모든 시험은 가짜 `create_gen_request`·가짜 CLI. 실제 생성 확인은 Jay 가 앱에서.

### A6. 시험
- 허브 문: 같은 대화 계획(앞 차례에서 만든 것 포함) + 도는 차례 → 제출 1회 · 차례 끝난 뒤·[그만] 뒤 409 · 차례 없음·허브 재시작 뒤 남은 바인딩 409 · 다른 대화(다른 연결) 계획·연결 없는 계획 404 · 다른 계정 신원 404 · 사람 [실행] + AI 실행 겹침 → 제출 1회 · 일반 MCP 연결 `can_execute=0` 은 그대로 403 · `wait_results`·`add_to_canvas` 칸에서 허용, `get_result`·`show_results`·`get_generation` 칸에서 403.
- 경합: 요청이 잡은 옛 차례가 끝나고 같은 대화 새 차례가 돌 때 옛 요청 → 409(새 차례 권한 안 빌림, 새 차례에 사건 없음) · 멈춤과 선점 교차 두 순서 — [그만]·시간 초과·신원 흔들림 각각(멈춤 먼저 → 409·제출 0 / 선점 먼저 → 제출 계속·멈춤은 차례만). 멈춘 뒤 409 시험은 아직 실행 전(planned) 계획으로 짠다 — 이미 제출된 계획은 `submit_plan` 이 선점 문 앞에서 지금 상태를 돌려준다(1190행, 정책상 그대로).
- 진행 사건: 실행·기다림 끝날 때마다 `plan_progress` = 새로 읽은 계획 전체 스냅샷(`observed_at`), 끝난 차례엔 없음 · 같은 차례 두 대기가 겹쳐도 사건 순서 = 읽은 순서(진행 잠금) · 일시 조회 오류 항목은 `generation_status` 없음, 404 는 missing · `_selected_results` 일시 오류만이면 `all_terminal=false`, 404 는 끝 + missing · observed_at 엄격 증가(같은 시각 두 번이어도 다른 값)·10진 글자 · 제출 뒤 스냅샷 읽기 실패·10초 초과 → 제출 응답 그대로·사건 없음 · 이미 시작한 발행은 끝까지(요청 취소에도 잠금 유지) · 스냅샷 반환 전 권한 재검사(그사이 계정 바뀜 → 버림) · 사람 [실행] 응답의 `snapshot`(실패 시 없음).
- 복원: 대화 다시 열기 응답의 `plans` = `plan_snapshot`(생성 상태 포함 — 사람 [실행]·끝난 차례 뒤 제출·사건을 놓친 완료 반영), 사건 다음에 읽음, 남의 연결 계획은 안 실음, 20개·15초 예산.

- 화면: 합치기 함수(`observed_at` BigInt 비교 — 같거나 옛것이면 무시 · 같은 스냅샷 두 번 · 허브의 복구 전이 uncertain→submitted·submitting→pending 반영 · 생성 상태가 빠진 항목은 앞 값 보존 · 제목·프롬프트 보존 · 복원 스냅샷은 조건 없이 넣고 기준이 됨 · 스냅샷 없는 사람 응답 항목은 빈 카드에만 — 최신 `submitted + id` 뒤 늦은 `submitting + null` 무시 · missing 은 완료·실패 수 밖 · 복원 뒤 빠진 계획 기준값 비움(재시작 전 큰 번호가 새 진행을 안 거름) · 첫 항목 거절·나머지 미제출 칸 글) · 보냄 카드(AI·사람 같은 글) · 확인 출처별 칸 글(접수됨·만드는 중·완료·실패·접수 확인 안 됨·거절) · 완료 썸네일(라이브러리 카드 / `getGeneration` 한 번 / 실패 글) · 누르면 크게 보기 · 복원 스냅샷 반영 · 도구 줄 이름 · 칩 ×(올림·초점에서 보임 → 빼면 다음 차례 문맥 없음·[＋ 지금 화면] 으로 다시·새 대화는 붙음) · 허브 `build_prompt` 문맥 없음 안내.

## 3. 구조 — 도구의 두 갈래

AI(CLI) → 패널 MCP(어댑터 `--panel`) → 허브 `/api/mcp/v2/client/action`(칸 연결만 쓰는 새 메서드).

### 3-1. 허브 동작 (서버에서 바뀌는 것)
- 허브가 기존 저장 함수를 **AI 용 조건을 얹어** 부른다: 대상은 이 신원의 카드만(소유·완료·쉐어 여부를 허브가 다시 확인), 한 번에 최대 200개.
- 결과 = `{done:[ids], skipped:[{id, reason}], undo_token}` · 칸에 '한 일' 카드.

### 3-2. 화면 동작 (브라우저에서 바뀌는 것 — 숨기기·캔버스·선택)
- 서버가 직접 못 하므로 **열려 있는 MV Hub 탭이 실행**한다. 이미 있는 두 무늬를 잇는다: 옛 MCP v1 의 '허브가 줄 세움 → 탭이 받아 실행 → 답'(`routers/mcp.py` 126–190, `McpConnection.tsx`)과, 칸의 차례 사건 흐름(긴 기다림).
- 흐름: AI 가 `app_action(name, args)` → 허브가 **그 차례에 묶인** 요청(`action_id`)을 만들고 차례 사건에 `ui_action{action_id, name, args}` 를 내보냄 → 그 차례를 따라 보고 있는 칸(같은 신원·같은 탭)이 **받아 실행**하고 `POST /api/agent-chat/turns/{tid}/actions/{aid}/result {ok, summary, undo}` → 허브가 MCP 호출에 그 결과를 돌려준다(최대 30초 기다림, 칸이 없거나 닫혔으면 "MV Hub 화면이 열려 있어야 해요").
- 한 요청은 **한 탭만** 실행: 결과를 처음 보낸 탭만 받아들이고(같은 `action_id` 두 번째 결과는 무시), 칸이 실행 직전에 `claim` 을 먼저 보낸다.
- 화면 쪽 실행기 = `agentActions.ts` 의 **이름 → 처리 함수 표**(앱이 이미 가진 함수만 부른다: `toggleDisabledGen`, `sceneActionRef.commitDocument`, 숨김 토글, 선택 바꾸기, 폴더·탭 열기). 표에 없는 이름은 거절.
- 계정이 바뀌었거나 칸이 그 차례의 신원이 아니면 실행하지 않는다(앞 판의 신원 검사 그대로).

- **어셋에서 끌고 오기**: 칸 입력칸이 어셋 끌어 놓기(`DRAG_TYPES.asset`)를 받는다 → 놓은 어셋이 칸에 칩으로 보이고, 허브가 그 차례 문맥에 레퍼런스 핸들로 넣어 AI 가 계획에 쓴다(지금 `read_context` 핸들 발급과 같은 검증).
- 모든 동작은 칸에 **'한 일' 카드**: "e001 실패 카드 7개 숨김 [되돌리기]" — 되돌리기는 그 동작이 바꾼 것만 되돌린다(뒤에 사람이 손댄 것은 건드리지 않음 — 되돌리기 전 지금 상태를 다시 보고 다르면 건너뛰고 알림).
- **많이 바꾸는 일은 먼저 보여 준다**: 대상이 20개를 넘거나 쉐어(팀에 보임)면 AI 가 바로 하지 않고 '할 일' 카드([하기]·[그만])를 칸에 띄워 사람이 누른다. 20개 이하 숨기기·캔버스는 바로 하고 [되돌리기].

## 5. 안전

- 새 메서드는 **칸 연결만**(`_PANEL_METHODS` 를 넓힘) — 일반 MCP 연결(Claude Desktop·Codex 등록)은 그대로. 어댑터 `--panel` 도구 목록·CLI 허용 목록(`CLAUDE_ALLOWED`)에 이름을 더한다(셋이 같은 목록 하나에서 나오게).
- 허브 동작은 대상을 허브가 다시 확인(소유·상태·쉐어 여부·공간) — AI 가 낸 id 를 믿지 않는다. 화면 동작은 그 탭의 지금 계정·씬에서만(`session.ts` 의 계정·씬 고정 그대로).
- 지우기·휴지통·계정·설정·관리자 도구는 없다. 유료는 [실행] 그대로(1절 결정 대기).
- MV 자료(제목·프롬프트·폴더 이름) 속 글은 자료일 뿐 — 도구 범위·되돌리기·20개 확인으로 피해를 묶는다.
- 기록: 모든 도구 호출·결과를 그 차례 사건에 남긴다(누가·무엇을·몇 개·되돌렸나).

## 6. 화면

- 모델·생각 깊이 칩(시안) · '한 일' 카드·'할 일' 카드 · 어셋 끌어 놓기 칩 · 답 글 마크다운(굵게·기울임·목록·코드만, HTML 은 글자로).
- 입력칸의 'MV Hub · 워크스페이스' 칩 = "AI 가 이 화면에서 일함" 뜻이 된다 — 선택한 카드 수를 함께 보인다("선택 12개").

## 7. 0단계 실측 (구현 전, 과금 없음)

1. 화면 동작 왕복: 가짜 CLI → 허브 → 칸 → 결과까지의 시간·칸이 닫혀 있을 때·탭 두 개일 때(한 탭만 실행).
2. `commitDocument` 로 만든 노드가 캔버스 되돌리기 기록에 들어가는지, 그 노드만 지우는 반대 명령이 되는지.
3. 프록시 허브에서 `publish_bundle_to_server` 를 AI 조건(내 것·완료·미쉐어)으로 걸러 부르는 자리 · 공유 서버 쓰기 금지 — **실측은 격리 HTTP 서버로만**.
4. 빠른 모드를 CLI 에서 켜는 길(설정 키 등) — 없으면 화면에서 뺀다.

## 8. 시험

- 허브: 새 메서드가 칸 연결 밖에서 403 · 남의 카드·미완료·이미 쉐어는 건너뜀(이유 포함) · 200개 상한 · unshare 되돌리기(골드 409) · 20개 넘는 쉐어는 '할 일' 카드로.
- 화면 왕복: 요청→실행→결과·시간 초과·칸 없음·두 탭(한 번만)·계정 바뀜(실행 안 함)·모르는 이름 거절.
- 화면 실행기: 숨기기·실패 숨기기·노드 만들기·잇기·카드 놓기·각 되돌리기(뒤에 사람이 바꾼 것은 건너뜀).
- 어셋 끌어 놓기 → 차례 문맥의 레퍼런스 핸들 · 마크다운(HTML 무력화) · 모델·깊이 칩.
- 기존: 일반 MCP 연결 동작 불변 · 앞 판 칸 시험 전부.
