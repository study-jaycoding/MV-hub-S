## 2. 근거 (Claude 직접 실측·확인)
- 같은 시험을 따로 돌려도 후보 5회 중 3회, **main 693c12a9 도 5회 중 2회** 실패 — 이번 후보가 만든 것이 아니라 지금 팀 공개판에도 있는 결함.
- 원인 실측(스크래치 `tk_probe.py`, 후보 코드 `cli_bridge._run` 을 그대로 쓰고 taskkill 출력만 가로챔, 8회): 3회 taskkill(`/PID 부모 /T /F`)이 **부모를 먼저 끝낸 뒤** 자식을 "There is no running instance of the task" 로 놓치고 rc 255 — 그 자식은 실제로 살아 있었다(표식 파일 생성). 성공 5회는 자식→부모 순서. 이 PC 에서 taskkill 하나가 약 2초.
- 제품 경로: `cli_bridge._terminate_cli_process`(`backend/app/services/cli_bridge.py:136-182`)는 taskkill rc≠0 이면 경고만 남기고 부모만 끝낸다(`:178-182`) → 실제 CLI 자식(npm 셰임의 node → hf.exe 등)이 남을 수 있다. CLI 를 띄우는 곳은 `_run` 하나(`:242-261`).
- 작업자는 같은 문제를 이미 Job 으로 풀었다: `agent_push.py:569`("taskkill /T 는 부모가 먼저 끝나면 자손을 못 본다")·`:654`·`:857-873`(호출마다 Job, 못 쓰면 taskkill 길). 백엔드에도 검증된 도우미 `backend/app/services/win_job.py`(`new_process_job()`·`ProcessJob.adopt_suspended`·`terminate`·`close`, KILL_ON_JOB_CLOSE)가 있고 Resolve 감시기가 같은 패턴을 쓴다(`resolve_selection_monitor.py:300-360`).

## 3. 설계 (2판 — 합의 1차 Codex·Claude P2 반영)
- **Job 만들기**: `_run` 은 `win_job.new_process_job()` 을 부른다. Windows 에서 실패하면 None 이 아니라 `OSError` 가 오므로(`win_job.py:533-541`) `OSError` 와 None(비 Windows) 모두 'Job 없음'으로 보고 경고 한 줄 뒤 **지금 길**(플래그 없이 띄움·taskkill 종료)로 실행한다.
- **띄우고 넣기**: Job 이 있으면 지금 인자·환경에 `creationflags=CREATE_SUSPENDED` **하나만** 더해 띄운다(지금 `_run` 은 플래그를 넘기지 않음 — 창 플래그 등 새로 넣지 않음). 띄우기와 `job.adopt_suspended(proc.pid)` 사이에 await 를 두지 않는다(`asyncio.to_thread` 로 감싸지 않음 — 그 사이 취소가 끼지 않게). 파이프 연결은 자식 출력을 기다리지 않으므로 `create_subprocess_exec → adopt_suspended → communicate` 순서가 맞다(Resolve 감시기 선례 `resolve_selection_monitor.py:304-326`).
- **넣기·재개 실패**: `job.terminate()`(넣었으나 못 푼 경우) → `proc.kill()` → 기한 있는 `proc.wait()` 로 멈춘 프로세스를 끝내고, **종료가 확인될 때만**(`proc.returncode is not None`) `job.close()`·경고 뒤 같은 인자로 **한 번만** Job 없이 다시 띄운다(작업자 선례 `agent_push.py:871-881`). 다시 띄워도 안전한 근거: `_run` 을 부르는 곳은 모두 읽기 전용 조회이고(generate get/list/cost·model list·account status·auth token·workspace·voices), 멈춘 채 실패한 자식은 한 줄도 실행되지 않았다. 종료 미확인(`_end_cli_parent` 처럼 오류·5초 초과를 삼키는 반환은 확인으로 쓰지 않음)·그 사이 취소면 다시 띄우지 않고 `CLIError`(취소면 `CancelledError`)로 끝내며 핸들은 닫는다.
- **취소·시간 초과(Job 있음)**: `job.terminate()` 로 트리를 한 번에 끝낸다. `terminate()` 가 `OSError` 를 내면 경고만 하고 계속 — 부모 회수(`_end_cli_parent`)를 시도하고 `finally` 의 `job.close()`(KILL_ON_JOB_CLOSE)가 남은 트리를 끝낸다. 어느 경우든 **원래 결과(`CancelledError` 또는 `CLIError("CLI 타임아웃 …")`)를 보존**하고, 정리 도중 다시 취소돼도 핸들을 닫으며 다시 띄우지 않는다. Job 종료는 바로 끝나므로 `slow_kills` 에 넣지 않는다.
- **Job 없음 길**: 지금의 taskkill 길(5초·늦은 종료 맡김·`slow_kills`·`wait_slow_kills`)을 그대로.
- **정상 종료**: `communicate()` 가 돌아온 뒤 `job.close()`(파이프를 놓고 남은 후손만 끝남 — 작업자와 같은 의미). 예외 경로 어디서든 핸들이 새지 않게 `finally` 에서 닫는다.
- **비 Windows**: `new_process_job()` 이 None → 플래그 없이 지금 그대로.
- 바꾸지 않는 것: CLI 인자·출력 처리·오류 문구·시간 제한 값·`_single_flight`·모델 갱신 종료 순서(`shutdown_model_refreshes`·`wait_slow_kills`), `win_job.py` 자체.

## 4. 남은 위험
- Job 안에서 CLI 가 자식 프로세스를 Job 밖으로 떼어 내는(breakaway) 경우는 Job 이 못 끝낸다 — 기본 Job 은 breakaway 를 허용하지 않으므로 지금 CLI 구조(node → hf.exe)에서는 해당 없음(추정, 시험·실측으로 확인).
- 멈춘 채 만든 프로세스를 Job 에 넣는 사이 예외가 나면 멈춘 프로세스가 남을 수 있다 — 실패 경로에서 반드시 끝낸다(시험).
