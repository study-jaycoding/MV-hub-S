# 에셋 캐시 '손상 캐시' 시험이 가끔 실패하던 것 — 시험이 수정 시각을 직접 옮긴다 (2026-11-06)

11-06 Slack 알림 dev 통합 중 백엔드 전체 시험(8,973건)에서 `test_asset_sync_cache.py::test_corrupted_cache_is_not_returned_and_download_failure_is_cleaned` 가 116행 `assert get_cached() == path and path.read_bytes() == PNG` 에서 실패했다. 같은 길이로 덮어쓴 캐시를 손상으로 알아채지 못하고 그대로 돌려줬다. 같은 dev 코드에서도 파일 10회 중 1회 실패했다(시작 세션 보고).

원인(직접 확인): `asset_sync_cache.file_digest` 는 (경로·크기·수정 시각 ns)가 같으면 해시를 다시 하지 않는다. 코드 주석의 shortcut "same-size edits preserving mtime need forced /verify hashing" 그대로, 합의된 한계다(`81e9bbef`). 이 시험은 받은 직후 같은 길이로 덮어쓰는데, 두 쓰기가 같은 시각 칸에 들어가면 수정 시각이 그대로라 캐시가 바뀐 것을 모른다. 같은 파일의 다른 두 시험(90·105행)은 이것을 피하려고 `os.utime` 으로 1ms 옮기는데, 이 시험만 빠져 있었다.

재현(작업실 `codex/asset-cache-flaky`, 저장소 밖 스크립트):

- 시험 첫 세 줄(받기 → 같은 길이 덮어쓰기 → 다시 읽기)을 고치기 전 제품 코드로 300번: 수정 시각이 같았던 35번이 곧 손상을 돌려준 35번이었고, 나머지 265번은 둘 다 아니었다(어긋난 경우 0). 시각이 달라진 경우 차이는 대부분 약 5ms.
- 같은 시각 흉내(같은 길이로 다시 쓰면 수정 시각을 되돌리는 pytest 플러그인)로 고치기 전 시험 5/5 실패 — 116행, 같은 메시지.
- 흉내 없이 파일 전체 30회: 4회 실패(모두 이 시험).

고친 것: 시험만. 덮어쓴 뒤 `os.utime(path, ns=(previous.st_atime_ns, previous.st_mtime_ns + 1_000_000))` — 90·105행과 같은 꼴. 제품 코드는 그대로 둔다. 판정 방식은 합의된 설계이고, 수정 시각이 안 바뀐 손상은 `/verify` 의 강제 해시가 잡는다.

고친 뒤:

- 흉내로 이 시험 5/5 통과 · 흉내로 파일 전체 5/5 통과(파일의 다른 시험에 같은 가정 없음)
- 흉내 없이 파일 전체 25회 실패 0
- 변이(크기만 보고 해시하지 않는 캐시)에서 고친 시험이 실패 — 헛통과가 아니다
