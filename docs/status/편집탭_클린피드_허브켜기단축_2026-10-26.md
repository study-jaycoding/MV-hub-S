허브가 제목을 기다리는 동안(0.43→0.6초) 피드는 이미 붙을 수 있었고, 앱은 응답을 못 받아 장면을 못 보냈다.

## 0단계 실험(격리 — 임시 프로필·임시 페이지, 크롬 155, 스크래치 `cfd\warm_probe*.py`)

1. `--no-startup-window` 로 창 없이 띄운 크롬은 **곧바로 끝난다**(남는 프로세스 0) — 창 없이 데워 둘 수 없다.
2. STARTUPINFO 로 최소화 시작(SW_SHOWMINNOACTIVE)을 줘도 키오스크는 **무시하고 보이며 초점을 가져간다**(0.31초).
3. 띄운 뒤 보이자마자 숨기면(ShowWindow 가 33~45ms 걸린다) **3번 중 1번 옆 모니터에 회색이 한 프레임** 비쳤고 초점을 잠깐 빼앗겼다 · 다른 프로세스의
   DWM 가리기(DWMWA_CLOAK)는 **접근 거부** · 투명 레이어(알파 0)는 **2번 중 1번만** 안 비침(크롬이 창 속성을 다시 쓰는 것으로 추정) → 메뉴를 열 때 미리 띄우기는 빼고(Jay 선택),
   **이미 뜬 창을 숨겨 두었다가 다시 쓴다**.
4. 이미 뜬 키오스크 창은 SetWindowPos(TOPMOST·영역·SWP_NOACTIVATE)로 **다른 모니터로 약 20ms 만에 그대로 옮겨지고**(전체 화면 유지) 숨김↔보임도 된다(페이지 보임 상태가 따라 바뀜).
5. 디코더를 작은 영상으로 미리 데워도 1080p 첫 프레임은 그대로(0.36~0.45초 vs 0.37~0.38초) — 데우기는 하지 않는다.

## 설계

창 스레드가 들고 있는 창은 하나이고 상태는 셋이다(용어를 섞지 않는다): **창 탐색 중**(띄웠지만 그 세션의 제목 창을 아직 못 찾음 — hwnd 없음) ·
**세션 창**(찾아서 맞춘 창 — 보임/숨김 규칙 대상) · **대기 창**(세션이 끝나 숨겨 둔 창 — hwnd 있음, 세션 없음, 다시 쓰기 대상).

### A. 창이 생기자마자 세션 받기(두 단계 열기)

- `POST /api/clean-feed/open` 은 **1단계**(창 스레드 `open` — 앞 창 정리·남은 것 확인·모니터 고르기·프로필 잠금 확인·크롬 띄우기)가 끝나면 세션을 등록하고 바로 답한다
  (`{session, key, instance, reused:false}` — `focus_ok` 는 뺀다). 1단계 실패는 지금처럼 409 코드(profile-in-use·profile-check-failed·cleanup-failed·no-monitor·spawn-failed).
- **2단계는 세션을 등록한 뒤에** 시작한다(1차 P1-1): 허브가 등록하고 나서 창 스레드에 `arm(세션)` 을 넣고, 창 스레드는 arm 된 '창 탐색 중' 창만 폴링한다(0.02초 간격) — arm 전에는
  그 창에 대해 아무 사건도 내지 않는다(등록 전에 결과가 와서 버려지는 순서가 없다). arm 이 오기 전에 open 이 취소·실패하면 허브가 지금처럼 그 세션의 창 닫기를 줄 세운다.
  폴링: 그 pid 의 제목 창(`MV hub Clean Feed <세션>` — 지금 규칙)을 8초 안에 찾으면 TOPMOST·모니터 영역 → 나온 모니터가 고른 모니터인지 → 띄우기 전 맨 앞 창으로 초점 되돌림 → '세션 창'
  (허브에 `adopted` 사건). 못 찾음(8초·크롬이 끝남) = `window-not-found` · 다른 모니터 = `wrong-monitor` → 창을 놓고(아래 정리) 허브가 세션을 그 사유로 끝낸다(앱·피드에 `closed{reason}` ·
  status ended_reason). 사건은 모두 세션 id 를 달고, 허브는 지금 live 인 그 세션의 것만 받는다(끝난 세션에 늦게 온 결과는 버림).
- 초점 되돌림 실패 = `focus-lost` — 세션에 보류해 두었다가 main 이 지금 있으면 바로, 없으면 붙을 때 한 번 보낸다(P2-5).
- '창 탐색 중' 창은 보임/숨김·영역 맞춤·`_mine`(그 창이 우리 것인가) 판정 대상이 아니다 — 살아 있음·제목·8초만 본다(P2-3). 창이 없는 크롬을 닫을 때는 WM_CLOSE 2초를 기다리지 않고
  바로 강제 종료 → 2초 안에 끝났는지 확인, 안 끝나면 지금처럼 핸들을 쥔 정리 실패로 남긴다. 세션 종료 통지는 정리 완료를 기다리지 않는다.
- 앱: `closed` 나 status 의 ended_reason 이 `window-not-found`·`wrong-monitor` 면 지금 open 실패와 같게 — 알림(OPEN_TEXT) + 바로 다음 고르기 한 번은 팝업 방식(`fallback`) ·
  작업 번호·지금 WS 확인은 그대로(옛 세션의 실패는 무시)(P2-5).
- `set_active` 는 허브의 **지금 live 세션**의 연결만 부른다 — 옛 세션 main 의 늦은 정리(`finally`)가 새 세션의 active 를 덮지 않는다(P2-2). 창 스레드도 세션 id 를 견준다(지금처럼).
- 다른 탭·같은 탭의 새 open 은 1단계가 끝나면 잠금이 풀려 들어온다 — 앞 세션 taken → 창 스레드 작업 큐(FIFO)에서 release/close → open 순서 그대로.

### B. 끈 창 다시 쓰기(대기 창)

- **남길지는 허브가 동기로 정한다**: 세션이 `closed`(사용 안 함·편집 탭 떠남·sendBeacon)·`taken`·`main-gone` 으로 끝나고 그 세션이 **adopted**(새로 띄운 창은 2단계 완료,
  다시 쓴 창은 새 피드의 ready)면 남긴다. 그 밖(account·user-closed·hub-stopped·window-not-found·wrong-monitor·open 실패·아직 adopted 아님 — 준비 안 된 재사용 창을 또 가져감 포함)은
  지금처럼 창을 끝낸다(P2-1).
- 남길 때: 허브가 **대기 기록**(release id·일회용 토큰 24바이트·그 세션의 앱 출처·브라우저·**계정 `Identity`(세대값·식별값)**·release Future·상태)을 만들고, end() 안에서 동기로 창 스레드에
  `release(세션, release id)` 를 넣는다(큐 순서상 뒤따르는 open 보다 먼저). 창 스레드는 그 세션 창이 살아 있고 우리 것이고 보여도 되는(adopted) 창이면 숨기고(SW_HIDE) 대기 창으로 표시
  (release id·대기 시작 시각) → 성공. 아니면 창을 끝내고 실패.
- **대기 기록의 상태**(2차 P1 반영): `reserved`(release 결과 전) → `ready`(release 성공) → `assigned`(새 세션을 붙여 assign 을 정해 둠 — 아직 안 보냄) → `delivered`(그 대기 연결로 assign 을
  보냄 = 토큰 소모, 기록 끝) · 언제든 `dropped`. release 결과는 **지금 기록이 그 release id 이고 reserved 일 때만** ready·dropped 로 바꾼다(버린·소모된 기록을 늦은 결과가 되살리지 못함).
  실패면 기록·토큰·대기 연결을 다 버린다.
- 토큰은 끝나는 세션의 **피드 연결에만** `closed/taken` 글의 `standby` 로 보낸다(앱 연결·앱의 HTTP 응답·WS 주소에 없음). 피드 화면은 세션 화면을 **언마운트**(영상 두 개의 src 를 비우고
  받기 멈춤 · 장면·표본·재동기 상태 버림)하고 **대기 화면**(검은 바탕)으로 바꿔 대기 WS 에 붙는다: 주소 `/ws/clean-feed?role=standby&session=standby`(키 쿼리 없음 — 라우터의 key 는
  빈 값 허용, main·feed 는 지금처럼 키 검사) + **하위 프로토콜 헤더 `mvhub-standby.<토큰>`** — 토큰을 주소에 넣지 않는다(uvicorn 이 INFO 로 WS 경로+쿼리를 콘솔에 남긴다 — 1차 P1-4.
  헤더는 INFO 에 안 남고 websockets 의 DEBUG 에만 남는다 · 고른 프로토콜은 101 응답 헤더로 되돌아간다 — 그 연결의 상대(피드)만 본다). 허브는 accept 전에 loopback·대기 기록 있음·상태가
  **reserved·ready·assigned 중 하나**(release 결과보다 먼저 와도 받는다 — 그래서 첫 거절·재시도가 없다)·Origin == 기록의 출처·토큰 상수 시간 비교·**계정 세대값 == 기록의 세대값**을 보고,
  같은 프로토콜을 골라 accept 한 뒤 기록이 그대로인지 다시 본다. 대기 연결은 하나(새 것이 옛 것을 끊음) · 피드가 보낼 글 없음. 거절되면 피드는 다시 붙지 않는다(그 창은 허브가 끝낸다).
- **다시 쓰기 조건**(open 안, 잠금 안): 대기 기록이 reserved 또는 ready · 같은 출처·브라우저 · **open 의 Identity 가 기록의 것과 같고 세대값이 지금 값**(1차 P1-3 — A→로그아웃→A 도 세대값이
  바뀌어 안 됨). 기록이 **reserved 면 그 release Future 가 끝나기를 기다린 뒤**(release 결과 처리는 허브 잠금을 쓰지 않는다 — 기다려도 막히지 않음) 같은 기록이 ready 인지와 Identity·세대값을
  다시 본다(2차 P1-2 — 모니터를 바꿀 때 새 open 이 앞 close 보다 먼저 와 같은 open 안에서 taken 으로 남긴 경우). 맞으면 창 스레드 `open(…, reuse=release id)` — 창 스레드는 그 대기 창이 그
  release id 이고 살아 있고 우리 것일 때만(프로필 잠금 확인보다 먼저) 새 세션을 숨긴 채 고른 모니터로 붙인다. 안 맞으면 대기 창을 끝내고 지금처럼 새로 띄운다(기록·연결도 버림).
- 붙였으면: 세션 등록(`reused=true`·`shown=False`·adopted 아님 · 3초 기한 = 등록 시각부터) → 기록 `assigned`(assign 글을 정해 둠) → **대기 연결이 지금 있으면 그 연결로 보내고 그때
  delivered**, 없으면 그 토큰의 대기 연결이 붙는 순간 보내고 delivered(2차 P1-1 — 소모는 실제로 보낸 때) → 응답 `reused:true`. 등록 → arm 큐 → 응답 사이에 다른 await 를 두지 않는다.
- **새 피드가 ready 를 보내기 전에는 창을 보이지 않는다**(1차 P1-2): 창 스레드의 세션 창에 '보여도 됨'을 두고(새로 띄운 창은 adopted 때 켜짐), 다시 쓴 창은 허브가 **그 세션의 지금 feed
  연결에서 온 ready** 를 받은 때 기한(3초)을 넘지 않았으면 `ready(세션)` 으로 켜고 그 세션을 adopted 로 한다(새로 띄운 창의 ready 로는 adopted 를 켜지 않는다 — 그쪽은 창 스레드의
  `adopted` 사건). ready 는 보여도 된다는 허락일 뿐 — `shown=True`·재동기 번호 증가는 지금처럼 실제 창의 `visible` 사건에서. 그 전까지는 앱 active 를 받아도 숨긴 채 · 그 뒤로는 지금 보임
  규칙이 **SWP_NOACTIVATE** 로 고른 모니터에 보인다(초점을 안 가져간다) → visible·resync 흐름 그대로.
- 다시 쓴 세션이 **등록 뒤 3초 안에 ready 가 없으면 `window-not-found`** 로 끝낸다(숨긴 채 창도 끝냄 · 남기지 않음) — 1초 점검에서 main-gone 보다 먼저 보고, 늦게 온 ready 도 받는 순간 기한을
  본다(P2-5). assign 을 보낸 뒤 연결이 끊겨도 같은 길로 끝난다(재시도 없음). 세션이 그 전에 끝나거나 계정 세대값이 바뀌면 assigned 기록도 버린다.
- 모든 창 스레드 명령·결과는 **식별자와 지금 상태를 함께** 본다(2차 P2-1): `arm(A)` 는 지금 창이 A 의 창 탐색 중일 때만 · `ready(A)` 는 지금 창이 A 의 세션 창일 때만 · release 결과·
  `standby-ended` 는 그 release id 의 대기 창·기록일 때만 — 옛 세션·옛 release 의 늦은 사건이 새 창·기록을 바꾸거나 닫지 않는다.
- 대기 기록의 수명: 창 스레드가 대기 창을 **10분** 안 쓰이면 끝내고(`standby-ended`) · 대기 창이 죽거나 사람이 닫으면(`standby-ended`) · 1초 점검이 **세대값이 바뀐 것**을 보면(대기 창만
  남아 있어도 점검을 돈다) · 허브 종료 — 모두 기록·토큰·대기 연결을 버리고 창을 끝낸다. 대기 창은 절대 보이지 않는다(세션이 없으면 보임 판정을 하지 않는다).
- 피드 화면은 assign 을 받으면 그 세션을 열쇠로 세션 화면을 **새로 마운트**한다(장면 rev·표본 sync·best·visibleSync·held·재시도 타이머·영상 두 개 전부 새로 — 앞 세션 것과 안 섞임) ·
  주소를 그 세션 주소로 바꿔 둔다(`history.replaceState`) · 버린 WS 의 늦은 글은 무시한다. 개발 화면 StrictMode 의 효과 두 번도 같은 결과.
- 모니터를 바꿔 고르기(같은 탭: 앞 세션 close 와 새 open — 도착 순서가 어느 쪽이든 앞 세션은 closed/taken 으로 끝나 남겨진다)도 이 길로 — 창을 옮겨 보인다(0단계 4).

### 바뀌지 않는 것

### 3차 사전 검토(Codex) — 합의(`VIBE-AGREE`, 계약 `472e4909…`) · 구현에서 지킬 P2

1. release 는 요청 수명과 떼어 둔다 — 기다릴 때 `asyncio.shield` + 시한(시한·취소가 release 자체를 취소하지 않음 — 창 큐는 취소된 Future 의 일을 건너뛴다).
