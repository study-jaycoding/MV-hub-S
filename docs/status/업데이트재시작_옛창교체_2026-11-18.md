# 업데이트 뒤 옛 창이 '업데이트 중입니다'로 남는 문제 — 새 판 실행기가 옛 창을 바꿔 연다

owner: claude(설계)·codex(구현) · reviewer: claude(독립) · status: 검증 중 · touched_paths: run_agent_session.py, backend/tests/test_launcher_window_contracts.py, docs/inventory/env_vars.md

## 증상 (Jay 보고, 11-18)

릴리스를 설치하면 cmd 창이 떠서 설치는 끝나는데, 앱 창은 '업데이트 중입니다'(시간 초과 표시) 화면에 그대로 남는다. 다시 시작한 새 판 화면으로 바뀌지 않는다.

## 원인 (코드로 확인)

1. **진행 화면은 업데이트 전 판의 코드다.** 0123·0602 의 `UpdateProgressOverlay` 는 시작부터 5분(`DEADLINE_MS`)이 지나면 상태 묻기를 그만둔다. 그 뒤에는 설치가 끝나도 새로 고치지 않는다. 이 PC 의 0602→0847 설치는 덮개 시작 약 09:42:50, 재시작 완료(committed) 09:48:09 였다. 5분이 약 20초 먼저 끝났다. 시간 초과 고침(989f4822)은 0847 부터 들어가서 0123 에서 올리는 팀에는 효과가 없다.
2. **새 판 실행기는 떠 있는 창을 그대로 쓴다.** 업데이트 일꾼(옛 판 `update_release_worker.bat` `Restart-MvHubAndWaitReady`, 3d0ff280 기준 440~511줄)은 새 판 `MV_agent.bat` 을 띄운다. 이어 `run_agent_session.py --app-window`(새 판 코드)가 `watch_app_window` 로 들어간다(`run_agent_session.py:1039`). 이미 승인된 MV Hub 창이 있으면 새 창을 띄우지 않고 그 창을 입양한다(`:1056` `if not app: spawn`). 옛 페이지를 다시 읽게 하는 길이 없다.
3. 0123 프런트에는 '허브 판이 바뀌면 새로 고침' 길이 없다. `reloadNow` 는 로그아웃·계정 전환 같은 저장소 사건에서만 불린다.

바꿀 수 있는 것은 **업데이트 뒤에 도는 새 판 코드**뿐이다. 일꾼·덮개는 옛 판 것이다. 그 새 판 코드가 새 `MV_agent.bat` → `run_agent_session.py` 다.

## 고침 (A안 — Codex 설계 검토 01a1ec31 반영 확정본)

`watch_app_window` 에서 **업데이트 부팅이고 입양한 창이 있을 때만**, 그 업데이트가 committed 되면 옛 창을 닫고 새 창을 연다.

- **업데이트 부팅 판정은 바깥 실행기에서 한다**(Codex 높음 1). 안쪽 bat 은 일반 실행에서도 `MVHUB_ACTIVATION_CONTROL`·`MVHUB_EXECUTION_NONCE` 를 넣는다(`MV_agent.bat:109`). 그 값은 기존 activated control 의 nonce 를 다시 쓴다(`update_release_contract.ps1` `Initialize-WorkerActivation`). 그래서 그 두 값만 보면 평소 재실행에서도 `_update_boot_outcome` 이 True 가 된다. 바깥 실행기(`main` → `run_guarded` → `_create_suspended_process`)는 안쪽 bat 보다 먼저 돈다. 그래서 일꾼이 넘긴 값만 본다(3d0ff280 일꾼 455~457줄. 기존 `_start_open_link_registration` 도 같은 가정이다). `_create_suspended_process` 가 자식 환경을 만들 때:
  - `MVHUB_UPDATE_WINDOW_NONCE` 를 늘 지운다.
  - `MVHUB_ACTIVATION_CONTROL` 이 있고 nonce 가 32자리 소문자 16진수일 때만 그 nonce 로 넣는다.
  - 물려받은 활성화 값이 진짜 업데이트(control pending + 같은 nonce + journal starting)가 아니면 안쪽 `Initialize-WorkerActivation` 이 실행을 멈춘다. 그래서 표식은 실제 업데이트 부팅에만 남는다.
- 감시자의 교체 후보 조건(셋 다):
  1. `MVHUB_UPDATE_WINDOW_NONCE` 가 형식에 맞고 `MVHUB_EXECUTION_NONCE` 와 같다.
  2. 시작할 때 입양한 승인 창이 있다.
  3. `_update_boot_outcome(nonce)` 가 True 다. False(롤백·대체)면 후보를 버린다. None 이면 다음 틱에 다시 본다(작은 JSON 두 개 읽기).
- 순서 = **먼저 닫고, 다 닫힌 뒤 연다.**
  1. committed 를 본 틱에 그때 살아 있는 승인 창 목록을 고정한다. 그 창들에 `WM_CLOSE` 를 **한 번만** 보낸다. 사용자가 X 를 누른 것과 같다. 그 뒤 새로 나타난 창에는 보내지 않는다. **그때 살아 있는 승인 창이 하나도 없으면** 예약하지 않고 표식만 버린다. 그 뒤 창이 없어 closed 가 나오면 지금처럼 종료(0)다. 사용자가 직전에 직접 닫은 앱을 다시 띄우지 않기 위해서다(독립 리뷰 0091d1a8 낮음).
  2. 교체를 시작하는 틱은 **고정한 옛 창이 모두 실제로 없어진 것이 확인된 틱**이다. 매 틱 맨 앞에서 본다. 각 HWND 가 `IsWindow` 가 아니거나 승인 property 가 없어야 한다. 숨겨진 채 남은 창도 '남음'으로 센다(합의 Codex 01a1ec3e 2). 이 확인은 Win32 호출이라 CIM 조회가 필요 없다. 확인되면 그 틱에서 CIM 재조회와 3번 debounce 를 기다리지 않고 바로 교체한다.
     - 실측(11-18, 고친 첫 판, 숨은 데스크톱 Chrome): 기존 closed 틱을 기다렸더니 옛 창이 사라진 뒤 새 창까지 15.5초가 걸렸다. 그 가운데 약 14초가 CIM 조회 다섯 번(한 번 약 2.3초)과 1초 대기 세 번이었다. 그동안 창도 콘솔도 안 보여 사용자가 앱이 꺼진 줄 알고 다시 실행하기 쉽다.
     - debounce 는 '보이는 창 없음' 관측이 순간적으로 흔들리는 것을 막는 장치다. 없어진 HWND 는 되살아나지 않으므로 여기서는 필요 없다. 다른 승인 창이 나타난 경우는 ③ 재확인이 받는다.
     - 옛 창이 남아 있는 동안 기존 감시는 그대로다. 사용자가 확인 창에서 '머무르기'를 고른 옛 창이 보이면 anchored 다. 옛 창이 끝내 남은 채 예약 유효기간이 지나면 예약을 버린다. 그 뒤의 closed 는 지금처럼 종료(0)다.
     - 교체 순서:
     - ① 콘솔을 숨겼으면 다시 보인다(Codex 중간 4). 새 창이 승인되면 기존 anchored 분기가 다시 숨긴다.
     - ② 브라우저 정리를 기다린다. 그 프로필의 브라우저 프로세스가 없어지거나, 보이는 창이 있는 채로 살아 있거나(종료 중 아님), 조회가 실패하면 끝낸다. 창 없는 프로세스가 남으면 그사이 여러 번 조회할 수 있다. 시한 15초는 조회 사이에만 확인하는 최선 노력이다. CIM 조회 한 번이 최대 15초라 실제 상한은 그보다 길 수 있다. **그 기다림의 마지막 조회 결과를 그대로 ③ 재확인에 쓴다.** 감시 고리의 CIM 재조회도, 별도 재확인 CIM 도 하지 않는다. 그 결과가 조회 실패면 열지 않는다. 예약이 남아 있으면 다음 틱에 다시 시도하고, 지나면 지금처럼 판정한다.
     - ③ 연기 직전 승인 창을 다시 본다. 이미 승인 창이 있으면 새로 열지 않는다. 대신 **예약을 풀고 그 창을 입양해 감시를 새로 시작한다.** 그 창이 나중에 닫히면 다시 교체하지 않고 0 으로 끝난다(합의 3).
     - ③-1 승인 창이 없으면 ④ 앞에서 예약 만료를 한 번 더 본다. 정리 기다림 동안 120초가 지났으면 열지 않고 예약을 버린다. 그 뒤 closed 는 0 이다.
     - ④ 교체 표식을 먼저 지운다(다시 교체 안 함). 그 뒤 `_spawn_app_window` 를 한 번 부른다. 그 결과로 `spawn_proc` 를 바꾸고, pid 목록·`_WatchState` 를 새로 시작한다.
     - 새 창이 안 뜨면 기존 첫 창 대기 규칙을 그대로 탄다. 40초 뒤 `APP_EXIT_NO_WINDOW`. 조회 실패 중에는 유보하고, 오래 실패하면 콘솔을 보인다. 다시 시도하지 않는다.
  - **보장하지 않는 것**(합의에서 명시 요구): `_update_boot_outcome` 이 끝내 None 이면(journal 이 committed 가 안 됨) 교체하지 않는다. 그때 옛 창은 지금처럼 남는다. CIM 조회가 계속 실패하면 교체도 종료도 유보한다. 그 사이 콘솔 복구는 기존 규칙을 따른다(30초 넘게 실패하면 콘솔을 보인다). 120초는 `WM_CLOSE` 를 보낸 뒤의 예약에만 적용된다.
  3. 120초는 **교체 예약의 유효기간**이다. `WM_CLOSE` 뒤 120초 안에 교체가 이뤄지지 않으면 예약을 버린다. 그 뒤의 closed 는 지금처럼 종료다. 이미 보낸 `WM_CLOSE` 는 되돌리지 못한다. 그래서 확인 창에서 120초 뒤 '떠나기'를 누르면 앱 종료가 된다. '머무르기' 뒤 120초 안에 직접 닫으면 새 창이 열린다. 둘 다 받아들인다.
- 저장하지 못한 편집(Codex 높음 2 — 보장 범위를 정확히):
  - 옛 페이지의 `unloadGuard`(beforeunload)가 브라우저 확인 창을 띄운다. 이것은 보조 보호다. Chromium 은 사용자가 그 문서와 상호작용한 적이 있을 때만 확인 창을 띄운다.
  - 업데이트는 본 창의 [업데이트]·[강제 업데이트] 클릭으로 시작한다. 그래서 본 창에는 늘 상호작용이 있고, 저장 안 된 편집이 있으면 확인 창이 뜬다.
  - 별도 창(`popupWindows.ts` — URL 로 연 따로 된 문서)에서 사용자가 편집했다면 그 창에도 상호작용이 있다. 그래서 확인 창이 뜬다.
  - 남는 위험: 사용자가 한 번도 손대지 않은 별도 창이 사용자 입력 없이 생긴 미저장분을 쥐고 있는 경우다. 예: 길이 자동 기록이 localStorage 쓰기 실패로 메모리에만 남은 경우(`features/timeline/session.ts`·`lib/useEditDoc.ts`). 이 창은 확인 없이 닫힌다. 편집 자료는 localStorage 에 바로 쓰이므로 쓰기 자체가 실패한 드문 경우에 한한다. 사용자가 직접 X 를 눌러도 같은 결과다. 받아들이고 기록한다.
- 기다리는 이유(1차 근거): Chromium 은 **종료 중인 브라우저에 온 새 창 요청을 버린다**. `chrome/browser/chrome_browser_main.cc` `ProcessSingletonNotificationCallback`(main, 589~596줄)에 "Drop the request if the browser process is already shutting down" 이 있다. 마지막 창이 닫힌 직후 바로 `--app` 을 부르면 창이 안 뜰 수 있다.
- 바꾸지 않는 것: 일반 실행·중복 실행·test_dev(표식 없음), 창이 없던 업데이트 부팅(지금처럼 새 창), 닫힘 debounce·콘솔 숨김·브라우저 고정, 일꾼·덮개·백엔드.

### 남는 비용

- 덮개가 스스로 새로 고치는 경우(0123 에서 5분 안에 끝난 PC, 0847 이후 판)에도 창을 한 번 닫았다 연다. 사용자에게는 '재시작'으로 보인다. Jay 가 기대한 동작('프로그램이 리스타트')과 같다. 페이지가 이미 새로 읽혔는지 밖에서 알 길이 없어 받아들인다.
- 별도 창(앱에서 띄운 승인 창)도 함께 닫힌다. 옛 코드 창이라 닫는 쪽이 맞다. 다시 열지는 않는다.

## 버린 안

- B 설치를 5분 안에 끝내기 — 파일 교체는 옛 일꾼이 한다. PC·NAS 속도에 따라 여전히 넘는다.
- C 옛 창에 F5 키를 보낸다 — Chrome/Edge 가 보낸 키 메시지를 받는지 판마다 확인할 수 없다. 앞창 권한도 필요하다.
- D 새 창을 먼저 열고 옛 창을 닫는다 — 잠깐이지만 옛·새 두 판이 같은 localStorage(캔버스 자료)를 함께 쓴다.
- E 새로 고침 여부를 알리는 새 끝점·제목 표식 — 표면이 늘어난다. 옛 판 페이지에는 효과도 없다.

## 완료 조건

- `backend/tests/test_launcher_window_contracts.py` 전체 통과. 새 시험:
  - 업데이트 부팅 + 입양 창 + committed:
    - 고정한 승인 창에 `WM_CLOSE` 를 한 번 보낸다.
    - 옛 창이 모두 없어진 틱에 종료(0)로 끝나지 않고 새 창을 한 번 연다. 그 틱에는 3번 debounce 도 감시 고리의 CIM 재조회도 기다리지 않는다. 별도 재확인 CIM 도 없다. 정리 기다림(창 없는 프로세스가 남으면 반복 조회할 수 있음)의 마지막 조회 결과를 재확인에 그대로 쓴다.
    - 새 창이 승인되면 계속 감시한다. 그 창이 닫히면 0 으로 끝난다.
  - committed 틱에 살아 있는 승인 창이 0 이면 닫기·예약·spawn 이 없다. closed 에서 0 이다.
  - committed 전에는 닫지 않는다. False(롤백)면 닫지도 열지도 않는다.
  - 교체 후보가 아닌 경우:
    - 표식 없음.
    - 표식과 실행 nonce 가 다름.
    - nonce 형식이 틀림.
    - 창을 새로 띄운 부팅.
    - **일반 부팅이 예전 committed control 을 다시 쓰는 경우.** 활성화 값은 있고 표식은 없으며 outcome 이 True 다.
  - `_create_suspended_process` 의 자식 환경:
    - 활성화 값이 있으면 표식을 넣는다.
    - 없으면 물려받은 표식도 지운다.
  - 교체 후보가 아닌 감시(일반 부팅 등)는 지금처럼 빈 관측 한두 번 뒤 창이 다시 보이면 종료가 없다(debounce 유지).
  - 정리·재확인 조회가 실패하면 열지 않는다. 예약 안이면 다음 틱에 다시 시도하고, 조회가 회복되면 판정한다.
  - 닫기 전송이 일부 창에서 실패하면 그 창이 살아 있는 동안 교체하지 않는다.
  - 고정한 옛 창이 숨겨진 채 남아 있으면(IsWindow·승인 property) 교체를 시작하지 않는다. 사라진 뒤 연다. 그 사이 예약이 지나면 closed 에서 0 이다.
  - 연기 직전 승인 창이 다시 보이면 새로 열지 않는다. 예약을 풀고 그 창을 입양한다. 그 창이 닫히면 다시 교체 없이 0 이다.
  - committed 가 끝내 안 오면(outcome 계속 None) 닫기를 보내지 않는다.
  - 120초 경계:
    - 안에 옛 창이 모두 없어지면 그 틱에 교체한다.
    - 밖이면 교체하지 않고, 창이 없어 closed 가 나오면 종료(0)다.
    - 119초에 옛 창 소멸을 확인했는데 정리 기다림이 120초를 넘겨 끝나면 새 창을 열지 않는다. spawn 직전 만료 확인이다. 그 뒤 closed 에서 0 이다.
  - 숨긴 콘솔 + 교체:
