### A. [NAS] 정리를 한 번에

- **기존 `unstage` 의 묶음 길**: `UnstageIn` 에 `bins: [{bin_id, folder_path}]`(기존 `bin_id` 와 둘 중 하나만, 요청당 최대 200 — 넘치면 프런트가 나눠 보냄). 묶음일 때 맨 위 `folder_path` 는 첫 행의 `folder_path` 로 채우고 각 행 `folder_path` 가 그 빈의 정본(맨 위 값은 형식 검사용).
- 라우터는 MV 프로젝트마다 지금 단일 길과 같은 `_project_read → resolve_transfer_roots → validate_media_root`·`import_records`, `same_file_ids` 는 행마다 그 `folder_path` 로(빈 `items` 정리에서는 실제로 쓰이지 않으나 단일 길과 같게 전달).
- 자식은 `_settle_recovery_record` 관문 뒤 **`_panel_walk(root)` 를 한 번 돌며 `path[0] == MEDIA_POOL_ROOT` 인 폴더로 ID→빈 표**를 만들고 — `_panel_bin_by_id` 와 정확히 같은 거르기(MV Hub 빈 자체·같은 이름 MV Hub 둘이면 둘 다 포함, 5판: 별도 Claude 2차 P2-1·Codex 3차 P3-1 — `_panel_settle` 의 첫 MV Hub 자식만 훑기는 쓰지 않음, 빈마다 전체 훑기 금지), 빈마다 기존 `_panel_stage(..., items=[])` — ID 로만 찾고 빈 지우기·지금 빈 옮기기 없음. 한 번 훑기가 실패하면 묶음 전체 실패(단일 호출이 모두 실패한 것과 같음).
- 빈마다 예외 나누기(5판): `_Unknown`·일반 예외·`code="resolve_error"` 로 감싼 예외는 그 빈만 실패로 적고 다음 빈, `_PANEL_STOP_CODES`(프로젝트 바뀜·복구 관문 등)는 전체 중단 — 중단할 때 지금까지의 `bin_results`·`removed` 를 예외 leftover 에 실어 바깥 예외 처리(`resolve_bridge.py:3059`)가 앞 결과를 지닌 채 돌려준다.
- `inventory_cleanup=false`([NAS])는 지금 빈도 정리, `true` 인 기존 호출은 `_owner.bin_id`·`_episode_bins` 의 `active_bin` 보호 그대로(묶음이면 해당 행만 `active_bin`).
- 결과 = 전체 `state/code/removed` + `bin_results: [{bin_id, folder_path, state, removed, …}]`(`TargetResult.bins` = 경로→빈 ID 라 다른 뜻으로 쓰지 않음). **빈 읽기 실패는 그 빈만 실패로 적고 다음 빈 — 전체 `state` 는 `ok`, `removed` 는 성공한 빈의 합**(프런트의 정리 수 셈이 `state === "ok"` 에 기대기 때문). **프로젝트 바뀜·복구 관문 실패는 앞 결과·leftover 를 지닌 채 전체 중단.** 단일 `bin_id` 요청의 결과 모양은 그대로.
- **프로젝트 바뀜은 `state` 또는 `code`** 로 본다(지금 자식 guard 예외는 `state="unavailable", code="project_changed"` — `resolve_bridge.py:3057`). [NAS] 는 그때 뒤 조각·마지막 save·다시 채우기를 하지 않고 막힘. **어느 조각이든 전체 `state` 가 `ok` 가 아니면**(빈 하나 실패는 이미 전체 ok 로 오므로 곧 프로젝트 단위 거절·busy·복구 관문) 뒤 조각·save·다시 채우기를 멈추고 알림에 `panelFailure(state)` 이유를 싣는다(5판 — 별도 Claude 2차 P3-1).
- `saveProject` 들어오기는 `savingRef.current` 로 막고(같은 렌더 두 번 눌러도 하나), 시작 때 잡은 계정 문맥·담당 세대(identity.generation)·revision 을 **정리 조각마다·마지막 save 전·다시 채우기 전에** 다시 대조해 다르면 그 뒤를 하지 않는다. 새 작업도 기존 `queue` 로. 서버 `mutation_scope`·소유 generation 재검사·`run_non_abandon` 유지.

### 프로젝트 없음 코드(진단용 — 이번엔 판정에 안 씀)

- `panel_operation` 초입: `GetProjectManager()` 는 됐는데 `GetCurrentProject()` 가 없으면 `state: "unavailable", code: "no_open_project"`, 프로젝트 매니저 자체가 없으면 `code: "no_project_manager"` — 둘 다 `resolve_project_id` 없음. 연결 실패(`api_unavailable`)·꺼짐(`not_running`)·ID 읽기 실패·`resolve_project_id` 붙은 unavailable·일반 예외·실행기 시간 초과에는 이 코드가 붙지 않는다. 라우터 `current-bin` 은 이 코드를 그대로 넘긴다. 프런트는 이번엔 이 코드로 아무것도 바꾸지 않는다(다음 계약 B 의 재료).

### B. 다음 계약 초안(이번엔 만들지 않음 — 실측 뒤 고침)
