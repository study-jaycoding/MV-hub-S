## 원인 (격리 실측 — dev `9c44d59c` 소스·같은 아침 빌드, `tools/browser_measure/servers.py` 복사본 관리자 936장, 헤드리스 크롬 1680×1000, Square 7열·줄 205px)

1. **브라우저 스크롤 고정(scroll anchoring)이 화면을 끌고 내려간다.** 바닥 근처에서 다음 쪽(200장 ≈ 5,500px)이 붙으면 scrollTop 이 붙은 높이만큼 늘었다(5,400→10,903). 손 안 댄 동안에도 쪽마다 반복(30.9·33.9·37.6초). virtua 내용 상자는 `overflow-anchor:none` 이라 빠지고, 아래 여백(`.gen-grid-tail`)이 기준점이 되는 것으로 봄(추정). 끌려 내려간 자리가 다시 바닥 근처라 `ThumbnailGrid` 자동 더 받기가 다음 쪽을 불러 끝까지 연쇄. 대조: `.gen-grid{overflow-anchor:none}` 만 주입하면 쪽이 붙어도 scrollTop 그대로·연쇄 없음.
2. **새로고침이 목록을 첫 200장으로 접는다.** `runReload` 가 첫 쪽만 받아 `setGens(prev => reconcileArrayState(prev, g))` — 길이가 다르면 통째 교체(`stateReconciliation.ts`), 커서도 첫 쪽 끝. 부르는 곳: 창 복귀·공유 탭 15초·처리 중 카드 3초 확인/15초·변경 통보·알림. 실측(창 복귀 한 번): 26,845 → 5,335(위로) → 1의 연쇄로 25,651(원래 자리와 약 1,200px 차이). 고정만 끄면 5,335 에 남는다(보던 자리를 잃음).
3. 스크롤바 크기 = 쪽이 붙을 때 +5,500px, 접힐 때 −21,000px. `itemSize` 추정 192 < 실제 205 로 한 줄에 13px 씩도 늘었다(이번 범위 밖).
4. 썸네일 캐시가 빈 첫 실행에서 다음 쪽 요청이 이미지 74개 뒤에 줄 서 2.5초 출발 못 함(이번 범위 밖).

## 설계

- 1번: 가상 격자 스크롤 상자 `.gen-grid.gen-grid-virtual` 에 `overflow-anchor: none`(실측한 범위로 한정 — Codex P2). 이 상자 안 줄 위치 보정은 virtua 가 직접 한다. `.gen-grid` 는 `ThumbnailGrid` 만 쓰고 늘 가상 격자다(캔버스 결과 창 SceneVariantPopup 도 같은 부품).
- 2번(1차 설계 → 검토로 바꿈): 같은 목록을 다시 받을 때 **이미 받은 만큼을 한 번에 다시 받는다.** 받을 수 = 지금까지 받은 **서버 원문 행 수**(공간 필터로 빠진 행 포함·위치 주입 카드 제외)를 쪽(200) 단위로 올린 값, 최대 1,000(서버 상한 2,000 — 공유 탭 200행 ≈ 6.5MB 라 낮게). 받은 범위 전체가 서버의 지금 값이라 새 카드·지운 카드·옮긴 카드·바뀐 정렬이 모두 그대로 맞고, 커서·'더 있음'·탭 캐시도 지금처럼 그 응답 하나로 정한다.
  원문 행 수는 휴지통 offset 으로 이미 세는 `trashOffsetRef` 를 일반 목록에서도 센다(첫 쪽 적용 때 = 받은 행 수, 더 받기 때 += 받은 행 수 — 휴지통 동작은 같고, 모든 목록 교체·탭 캐시가 이미 이 값을 같이 맞춘다).
  같은 목록 = 보이는 목록이 이 조회의 것(`shownSigRef === sig` — 위치 주입 화면·다른 조회·빈 목록은 제외) · 위치 주입 상태 아님(`locatedRef` 없음 — 주입 뒤 정상 응답을 한 번 적용해도 남는다) · 사본(staleList)·컷 화면 뒤(aside) 아님. 아니면 지금처럼 첫 쪽(200)만.
  **새로고침 목록이 오는 동안 더 받기는 미룬다**(`inflightRef` 가 있으면 그때의 조회 sig 만 적어 두고 돌아감). 이어 받기는 **새로고침이 같은 조회의 목록을 실제로 적용했고 그 응답에 다음 쪽이 있을 때(받은 수 >= limit — 적용하는 순간에 정함)만**, 새로고침 줄이 모두 끝난 뒤 한 번. 다른 조회를 적용했거나·실패·다음 쪽 없음이면 지운다(3차 Codex P2). 안 미루면 먼저 끝난 더 받기(600장)를 출발 때 길이(400장)의 새로고침이 덮어 목록이 줄며 튄다(2차 검토 둘 다).
  1차 설계(첫 쪽 + 이전 목록의 뒤쪽 이어 붙이기)는 버렸다 — Codex P1: 위에 새 카드가 200장 넘게 생기면 그 사이가 빠지고, 첫 쪽 카드가 뒤로 밀리면 사라진다 · Claude P2: 다른 창·기기 동기화로 지운 카드가 남고 옮겨 온 카드가 커서 사이에 빠진다(검토 원문: 아래 진행).
- 알려진 한계: 1,000장보다 깊이 내려간 목록은 다시 받을 때 1,000장으로 줄어 그 아래에 있던 화면은 1,000장째 근처로 간다 · 깊이 내려간 만큼 새로고침 응답이 커진다(작업 공간 200행 ≈ 1.6MB, 공유 탭 ≈ 6.5MB, 전송은 gzip).
