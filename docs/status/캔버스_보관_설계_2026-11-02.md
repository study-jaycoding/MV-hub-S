## 2. 코드로 확인한 지금 사실

- `/api/scenes` 는 `_proxy._LOCAL_PREFIXES`("서버 전송 금지"). 자동 저장 = IndexedDB → 2초 뒤 로컬 `scene_backup`(씬당 1행 덮어쓰기, 씬 삭제 시 행 삭제).
- 씬에는 프로젝트 칸이 없다(버킷 `_none`). `Project.workspace_id` 로 프로젝트가 워크스페이스에 묶인다. dev DB: 워크스페이스 8개가 프로젝트 1개씩 · 예외 = 워크스페이스 없는 프로젝트 1 · 프로젝트 없는 워크스페이스 1. 공유 서버 값은 미확인.
- 생성 카드는 `genId`·`genIds` 만 담는다. 그림 주소는 로컬 `generation`·`asset` 행에 있다. 없는 id 는 `POST /api/generations/batch` 가 서버에 다시 묻는다.
- dev DB `asset` 1,424행: `file_path` 가 cloudfront 주소 1,274 · `file_path` 는 로컬 경로이고 `source_url` 이 주소 150. 주소 없는 행 0. 월별 표본 18개 전부 열림(가장 오래된 표본 약 4개월, 힉스필드 보존 기간 미확인).
- `generation` 1,430행 중 `origin='synced'` 1,383. **동기화로 만든 행은 `id=new_id()`, `job_id` 만 앵커다**(`repo/generation_sync.py`). 로컬 DB 가 사라지고 동기화가 먼저 돌면 같은 결과가 다른 id 로 다시 생긴다. `job_id` 는 유일 인덱스가 아니고, `NO_REVIVE_ERROR` 실패 행은 보존한 채 같은 job_id 의 완료 행을 따로 만든다.
- 동기화는 `id = job_id OR job_id = job_id` 로 찾은 행을 갱신한다. `tombstoned_among` 은 `trash.trashed` 와 삭제 이동 중 `generation_transfer` 를 함께 본다.
- dev DB 씬 17개: 크기 가운데 31KB·최대 780KB, 'ASCII 로 감싼 길이' 최대 848KB · 노드 가운데 72·최대 428 · 씬당 생성물 가운데 8·최대 170. 표본이 작다.
- 씬이 가리키는 생성물 297개 중 이 DB 에 있는 것 25개뿐. 보관 시점에 정보가 없는 카드가 흔할 수 있다.
- 서버 전용 데이터의 본보기 = `routers/edit_shares.py`: 경로는 `_LOCAL_PREFIXES` 에 두고 핸들러가 출처 검사·화면 계정 대조·연결 고정 뒤 직접 중계, 미로그인이면 409(로컬 저장 금지). 서버 본체는 `_viewer` 로 인증.
- `raw_request` 는 `json.dumps(body)`(ensure_ascii) 라 한글 1자가 6바이트가 되고 요청·응답을 메모리에 올린다. 크기는 'ASCII 로 감싼 길이'로 잰다. 본문 상한 = `services/upload_limits.UPLOAD_REQUEST_LIMITS`.
- DB: 새 표는 `schema.sql` + `db_migrations.py` 의 `CREATE TABLE IF NOT EXISTS` 로 더한다(`edit_share` 와 같다). **새 baseline 이름표를 기록하면 서버·되돌리기의 옛 검사기가 모르는 이름이라 막는다**(`db.py` 주석, `docs/CODE_MAP.md` §5).
- Import = `parseSceneImport(text)` → `importSceneSnapshot(snap)`. 이 함수는 **부르는 순간의** 계정으로 저장한다. Export 는 `pendingGenerationAttempts` 를 그대로 싣고 `savedAt: Date.now()` 를 넣는다. 씬의 `workspace` 는 받는 쪽에서 `refWorkspaceHint` 로만 쓴다.
- 허브 기능 표식 = `GET /api/auth/config` 의 `features` → 화면 `hubHasFeature`.

### 3-1. 표 `scene_keep`(공유 서버가 권위. 표는 로컬 허브에도 생기지만 쓰지 않는다)

```sql
CREATE TABLE IF NOT EXISTS scene_keep (
  id TEXT PRIMARY KEY,                 -- 무작위 32hex
  owner TEXT NOT NULL,                 -- 정규화 email(응답에 내보내지 않는다)
  project_id TEXT NOT NULL DEFAULT '', -- '' = 프로젝트 없음. 묶음 이름표이며 FK 가 아니다
  project_name TEXT,                   -- 보관 때의 이름
  name TEXT NOT NULL,                  -- NFC·앞뒤 공백 제거, 120자 이하
  workspace_id TEXT, workspace_name TEXT, -- 보관 때의 탭 표식
  node_count INTEGER NOT NULL,
  preview TEXT NOT NULL,               -- 노드 배치 미리보기 JSON: [[종류,x,y,w,h],...] 좌표 0~1000, 칸 200개·8 KiB 이하
  missing_count INTEGER NOT NULL DEFAULT 0, -- 정보를 찾지 못한 생성물 수
  data TEXT NOT NULL,                  -- {"v":1,"scene_text":..., "generations":[...]}
  data_hash TEXT NOT NULL,
  data_bytes INTEGER NOT NULL,         -- 'ASCII 로 감싼 길이'
  revision INTEGER NOT NULL CHECK(revision > 0),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  UNIQUE(owner, project_id, name)
);
```

보관본은 본인만 본다 → 프로젝트 권한 검사를 하지 않는다(개인 프로젝트는 서버에 없을 수 있다). 생성물의 작성자는 보관본 owner 와 별개로 원래 값을 유지한다. baseline 을 기록하지 않는다.

### 3-2. API

경로는 `_LOCAL_PREFIXES` 에 `/api/scene-keeps` 를 더하고 핸들러가 `edit_shares._relay` 와 같은 방식으로 중계한다.

| 경로 | 동작 |
|---|---|
| `POST /api/scene-keeps` | 본문 `{name, project_id, project_name, workspace, scene_text, preview, overwrite_id?, overwrite_revision?}`. 허브: `scene_text` 를 읽어 생성물 id 를 **직접 추출**(화면이 보낸 목록을 믿지 않는다) → 3-3 의 묶음 → 고정한 계정을 `expect_account` 로 실어 서버로 중계. 서버: `expect_account` 가 인증 계정과 다르면 409(`edit_shares` 와 같다) → 잠금 밖에서 크기·봉투 검사와 해시 → `BEGIN IMMEDIATE` → (owner, project_id, name) 확인·할당량 확인·저장. 응답 `status`: `saved`(id, revision, missing_count) / `exists`(id, revision, updated_at — 아무것도 안 씀) / `conflict`(덮어쓰려던 행이 사라졌거나 revision·id 가 달라짐). 덮어쓰기는 `overwrite_id`·`overwrite_revision` 이 둘 다 같을 때만. 내용이 같으면 revision 그대로 |
| `GET /api/scene-keeps` | 내 목록: id·name·project_id·project_name·workspace·node_count·preview·missing_count·revision·updated_at. 행 상한이 있어 페이지를 나누지 않는다 |
| `GET /api/scene-keeps/{id}` | 내 것의 `scene_text`·revision·workspace. 없거나 남의 것은 404, detail "보관본을 찾을 수 없습니다" |
| `GET /api/scene-keeps/{id}/envelope?revision=` | 서버 전용. 허브의 복원만 부른다. 내 것이고 revision 이 같을 때만 그 행의 `data` 전체(같은 행 한 번 읽기). 다르면 409 "보관본이 바뀌었습니다", 없으면 404. **허브는 이 경로를 화면에 열지 않는다** |
| `DELETE /api/scene-keeps/{id}?revision=` | 내 것만, revision 이 같을 때만 지운다 |
| `POST /api/scene-keeps/restore` | 허브 전용. 본문 `{id, revision}`. 허브가 envelope 를 받아 검증한 뒤 3-4 대로 채우고 `{id_map, rejected, restored}` 응답. 서버 본체에서는 409 "이 PC 의 앱에서 열어 주세요" |

상한: `data` 8 MiB('ASCII 로 감싼 길이') · `scene_text` UTF-8 5MB(Import 상한과 같다) · 계정당 합계 200 MiB·행 300개(덮어쓸 행을 뺀 합으로, 쓰기 트랜잭션 안에서 잰다) · 묶는 생성물 2,000개(넘으면 `missing_count` 로 센다). POST 본문 상한은 `upload_limits` 에 등록한다. 실측 전 값이며 격리 부하로 확인한다.

봉투 `data` 검사(서버 저장 때와 허브 복원 때 같은 규칙, `repo/scene_keeps.validate_keep_envelope`): `v==1`, `scene_text` 문자열, `generations` 배열. 생성물 칸: id·job_id 문자열 200자 이하, `source` 는 `local`·`server`, status 는 `done`, created_at 문자열 40자 이하, sort_ts 숫자 또는 null, prompt·display_prompt 20,000자 이하, params 객체(JSON 64 KiB 이하), generator 는 기존 값만, asset 배열 1~32개(type 은 image·video·audio, 주소·썸네일은 `https://` 로 시작하고 4,096자 이하, 썸네일은 없어도 된다). 선택 칸(job_id·display_prompt·params·sort_ts·generator·creator_uid 등)의 null 은 허용한다. 어기면 서버는 저장 거절, 허브는 **로컬에 쓰기 전에** 복원 거절. 허브는 묶을 때 이 한도를 넘는 생성물을 그 항목만 빼고 `missing_count` 로 세므로, 정상 씬이 한 항목 때문에 거절되지 않는다.

알림: `/api/scene-keeps` 전체를 라이브러리 무변경으로 두고, `/api/scene-keeps/restore` 만 예외로 라이브러리 변경 알림을 낸다.

판 차이: 기능 표식 `scene_keep_v1` 은 로컬 허브(`AUTH off`)만 낸다. 없으면 보관·불러오기 단추를 그리지 않는다 → **공유 서버 직접 접속 화면에는 단추가 없다.** 목록이 일반 404(`detail: "Not Found"`)면 "공유 서버 업데이트가 필요합니다", 상세의 404 는 "보관본을 찾을 수 없습니다"로 가른다.

### 3-3. 보관 흐름

1. 패널 [보관] → 창을 연다. 시작할 때 계정 범위(`getAccountNamespace`)를 잡는다. 계정이 바뀌면 창을 닫는다.
2. 프로젝트 기본값 = 탭 `workspace` 의 프로젝트(`Project.workspace_id` 일치, 보관 안 된 것). 1개면 자동. 여럿이면 왼쪽에서 고른 프로젝트가 그중에 있으면 그것, 아니면 첫째. 탭 None 이거나 0개면 "프로젝트 없음".
3. [보관] → 밀린 입력 flush → 최신 씬을 다시 읽어 살아 있는 카메라와 함께 **고정**. 사본의 이름을 제출 이름으로 바꾸고 `pendingGenerationAttempts` 를 지운다. `savedAt` 은 0 으로 고정해 같은 내용은 해시가 같게 한다. 덮어쓰기 재요청은 같은 사본을 보낸다.
4. `exists` → "덮어쓰겠습니까?" → [덮어쓰기] 면 `overwrite_id`·`overwrite_revision` 으로 다시 POST. `conflict` 면 다시 확인한다.
5. 성공하면 계정이 그대로인지 보고, 이름이 다를 때만 `renameScene`, 알림. `missing_count` 가 있으면 "생성 결과 N개는 정보를 찾지 못했습니다"를 함께 알린다. 실패하면 씬은 그대로, 창에 이유를 보인다.

생성 기록 묶음(허브, 생성물별):

1. 씬의 genId·genIds·refs.source_gen_id·comfy outputs.saved_generation_id 를 모아 중복을 뺀다.
2. 로컬 행을 작은 묶음으로 읽는다. 지금 계정이 볼 수 있는 것만(`can_view_generation_with_member_projects`) `source:"local"` 로 싣는다.
3. 로컬에서 못 찾은 id 는 고정 연결로 서버 `/api/generations/batch` 에 500개씩 묻고, 볼 수 있는 결과는 `source:"server"` 로 싣는다(지금 서버에 있어도 나중에 삭제·공유 해제될 수 있어서다). 필요한 칸만 남기고 나머지는 버린다.
4. 칸: id·job_id·prompt·display_prompt·model·params·status·created_at·sort_ts·creator_uid·project_id·folder_path·generator·workspace 칸 + asset 의 type·주소·썸네일. 주소 = `file_path` 가 https 면 그것, 아니면 `source_url`. 썸네일 = `thumbnail_path` 가 https 면 그것, 아니면 비운다(캐시된 그림의 썸네일은 PC 경로다). 표시·식별에 필요한 칸만 싣고 통계·공유·최종 표시·실행 요청은 싣지 않는다.
5. `missing_count` = **지금 계정으로 정보를 확보하지 못한 수**: 서버의 `missing`(없음·권한으로 숨김을 가리지 않는다, 더 묻지 않는다)·`unavailable`·https 주소 없음·완료가 아닌 상태·봉투 칸 한도 초과·2,000개 초과.
6. 묶는 동안 크기를 누적해 8 MiB 를 넘으면 거기서 멈추고 나머지를 `missing_count` 로 센다. 서버 조회 전체에 60초 시한을 둔다. **DB 연결을 잡은 채 네트워크를 기다리지 않는다.**

`creator_uid` 는 `acct:<email>` 일 수 있다 → 봉투(소유자만, 허브만 받음)에만 두고 목록·상세·복원 결과·로그에는 내보내지 않는다.

### 3-4. 불러오기 흐름

1. 보관함 창: 시작할 때 계정 범위를 잡는다. 왼쪽은 프로젝트 목록(지금 이름이 있으면 그것, 없으면 보관 때 이름)과 개수, 맨 위 "전체". 오른쪽은 이미지 보기(노드 배치 미리보기 카드)와 리스트 보기(작은 미리보기·이름·보관 일시·노드 수)를 앱의 전환 단추로 바꾼다. 고른 보기는 브라우저에 기억한다. 고른 보관본에 휴지통 단추가 있고 앱 확인 창을 거쳐 지운다.
2. [+ 새 탭으로 열기]:
   1. 쓸 수 있는 캔버스 창인지 본다(분리 창이 떠 있는 메인·쉬는 탭이면 멈춘다). `GET /{id}` → `parseSceneImport` 로 먼저 검증한다(틀리면 여기서 끝, DB 쓰기 없음). 이때의 revision 을 기억한다.
   2. `POST /restore {id, revision}` → `{id_map, rejected, restored}`. 멱등이라 다시 눌러도 된다. 다른 창이 바꿔 409 면 "보관본이 바뀌었습니다, 다시 열어 주세요".
   3. 검증된 스냅샷 복사본에 적용한다(genId·genIds·source_gen_id·saved_generation_id): `rejected` 의 id 는 **지운다**(카드는 남는다. genId 는 남은 genIds 의 마지막, 없으면 비운다), `id_map` 의 id 는 바꾼다, 둘 다 아닌 id 는 그대로 둔다(서버에서 계속 보일 결과). 조회는 `Map` 으로 한다.
   4. 계정이 그대로인지 다시 보고, **고정한 계정으로** 가져온다. `importSceneSnapshot(snap, scope)` 는 범위가 다르면 null 을 돌려주고(지금의 `!` 단언을 없앤다) 그때는 목록 갱신·탭 선택·재연결을 하지 않는다. 저장 확정은 `confirmSceneWrite` 로 보고, 기다린 뒤 범위를 다시 본다.
   5. 탭 표식을 되돌린다(`workspace_id` 가 내 공간 목록에 있을 때만 — 자기 씬이라 과금 지정을 복원해도 된다). 실패는 따로 알린다.
3. 탭 저장이 실패하면 "기록은 복원했지만 탭을 열지 못했습니다"로 알린다. 복원한 행은 보상 삭제하지 않는다(그사이 다른 기능이 쓸 수 있다). 다시 누르면 멱등으로 이어진다.

`restore` 처리 순서: **envelope 받기(revision 일치) → 봉투 검증 → 계정 고정 연결 → `attach_trash` → `BEGIN IMMEDIATE` → 판정·삽입 → COMMIT/ROLLBACK → finally DETACH.** 트랜잭션 안에서 네트워크를 쓰지 않는다. 같은 연결에서 삭제 표식을 읽어 삭제와의 경합을 막는다(`generation_sync` 와 같다).

판정(생성물마다 — 허브의 지금 계정 로컬 DB). 결과는 `id_map` 또는 `rejected` 또는 '그대로'다:

1. **삭제**: id 나 job_id 가 휴지통·삭제 이동 중(`tombstoned_among` + id 확인, job_id 없는 항목도 id 로 본다)이거나 그 행에 `deleted_at` 이 있으면 → `rejected`.
2. **job 일치**(job_id 가 있을 때만): 같은 job_id 의 살아 있는 완료 행(결과 asset 있음)이 1개면 `id→그 행`, 2개 이상이면 `rejected`(임의로 고르지 않는다). 실패·미완료 행은 후보가 아니다.
3. **같은 id**: 같은 id 의 행이 있는데 2번에서 정해지지 않았으면 — 살아 있는 완료 행이고 job_id 가 같으면(둘 다 비어 있으면 같다고 본다) `id→id`, 그 밖(다른 job·실패·미완료·결과 없음)은 **기존 행을 바꾸지 않고** `rejected`.
4. **남의 서버 결과**: `source:"server"` 이고 작성자가 지금 계정이 아니면 넣지 않고 '그대로' 둔다 → 서버가 지금 권한으로 판단한다(삭제·공유 해제를 되살리지 않는다).
5. **삽입**: 그 밖에는 `generation`·`asset` 을 넣는다: 원래 id, `origin='synced'`, 원래 `creator_uid`, 이 PC 기본 `worker_id`, `sort_ts`(없으면 created_at 에서 계산), 검사한 `generator`, status='done'.

`rejected` 를 카드에서 지우는 까닭: 카드 조회는 id 로만 찾으므로, 다른 작업의 행과 id 가 겹친 채 두면 **엉뚱한 그림이 보인다.**

원래 id 를 유지하는 까닭: `telemetry_outbox`·서버 `team_generation_fact` 가 로컬 id 로 멱등이고, 반복 열기가 중복 행을 만들지 않는다.

### 3-5. 안 하는 것

보관본 공유·팀 보기, 덮어쓰기 이력, 그림·영상 파일 올리기, 자동 보관, 로컬 사본, 보관본에서 지금 탭 덮어쓰기, 공유 서버 직접 접속 화면의 보관, 실행 중 작업 이어 가기, `gen_reference`·통계·공유 상태 복원.

## 4. 실패 경계

| 상황 | 동작 |
|---|---|
| 서버 미로그인·연결 실패 | 보관·목록 실패로 알린다. 로컬에 쓰지 않는다. 자동 저장은 계속 |
| 화면 계정 ≠ 허브 계정, 도중 계정 전환 | 409 또는 화면 범위 재검사로 멈춘다. 아무것도 쓰지 않는다 |
| 두 창이 같은 이름을 동시에 보관 | `BEGIN IMMEDIATE`·UNIQUE·`overwrite_id`+revision 비교로 한쪽은 다시 묻는다 |
| 삭제 뒤 같은 이름으로 새로 보관된 사이의 덮어쓰기 | id 가 달라 `conflict` |
| 응답을 놓친 저장 | 다시 누르면 `exists`, 내용이 같으면 revision 그대로 |
| 씬 검증 실패 | DB 쓰기 전에 끝난다 |
| 복원 트랜잭션 실패 | 그 복원 전체 취소, 새 탭 안 만듦 |
| 복원 뒤 탭 저장 실패 | 기록은 남고 알린다. 다시 시도 가능 |
| `rejected` 가 있음 | 그 id 를 새 탭의 카드에서 지우고 탭은 연다. 개수를 알린다 |
| 복원 사이에 다른 창이 덮어씀 | envelope 의 revision 이 달라 로컬에 쓰기 전에 409 |
| 봉투 형식 위반 | 서버는 저장 거절, 허브는 로컬에 쓰기 전에 복원 거절 |
| 보관본 형식이 다른 판 | `v`·`format` 이 다르면 "이 앱에서 열 수 없는 보관본입니다" |
| 프로젝트가 사라짐 | 보관 때 이름으로 묶음 유지 |
| 서버 DB 를 보관 이전 백업으로 교체 | 그 뒤 보관본은 없어진다. 서버 복원의 일반 성질 |
