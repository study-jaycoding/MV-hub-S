**지금 흩어진 모습(직접 셈)**: 서버 운영 코드 파이썬·PowerShell 약 6,000줄(`server_supervisor` 111 · `server_activation` 499 · `server_release_update` 301 · `server_watchdog` 733 · `server_move` 1,027 · `server_move_easy` 1,230 · `backup_replicate` 671 · `deploy_fence_check` 134 · `log_viewer` 275 · `run_update_git.ps1` 510 · `restart_server_task.ps1` 185 · `qualify_release_artifact` 297 · `server_verifier` 71) + 진입 bat 13개. 같은 지식이 여러 곳에 따로 있다 — 예약 작업 이름(도구 3개 파일 11곳 + bat), 서버 끄는 순서(`server_move_easy`·`restart_server_task.ps1`·`SERVER_RECOVERY.md`), 데이터 폴더 찾기(`server_move.resolve_data_dir` 등). 이사·업데이트 도구는 루트 `backend/app` 을 import 한다(`server_move.py:46-56`, `server_move_easy.py:34-37`, `server_activation.py:18-21`).

**결론: 화면과 '할 수 있는 일 목록'은 한 곳에 모으되, 기존 도구의 코드는 옮기거나 합치지 않는다.**

- 옮기지 않는 이유: ① `server_activation`·`server_release_update`·TOOLS 파일은 서버가 stage 로 도는 동안 바꾸면 supervisor 가 시작·복구를 못 한다 — 한 묶음으로 옮기면 매번 서버를 멈추는 반입이 필요하다. ② 업데이트·이사 도구는 실서버에서 검증됐고 시험 수백 개가 붙어 있다(오늘도 고침) — 합치며 다시 짜면 그 검증이 사라진다. ③ 관리 창이 고장 나도 기존 bat 로 서버를 살릴 수 있어야 한다(비상구).
- 대신 **3층 구조**:

```
화면(tkinter)          tools/server_console/ui.py       그리기·클릭만. 판단 없음
관리 핵심(시험 가능)    tools/server_console/
                         names.py    예약 작업 이름·기본 경로·포트 — 관리 창의 '한 곳'
                         status.py   상태 판정(정상/시작 중/전환 중/준비 실패/응답 없음/정지 확인) + 관측 시각
                         logs.py     로그 파일 꼬리·이벤트→탭 분류(log_viewer 재사용, 원시 보존)
                         actions.py  ★할 수 있는 일 목록 한 곳: 이름·설명·필요 권한·사전 검사·확인 문구·실행 명령
                         jobs.py     작업 실행기(UI 와 독립 수명, 결과 기록) — 2~4판 계약 그대로
기존 도구(그대로)       run_update_git.ps1 · server_move* · backup_replicate · restart_server_task …  ← bat 로도 계속 작동
```

- **관리가 나아지는 점**: 서버로 할 수 있는 일이 `actions.py` 한 곳에 목록으로 있고, 화면·`SERVER.md` 표·시험이 같은 목록을 본다. 새 기능 = 기존 도구 + 목록 한 줄. 상태 판정도 `status.py` 한 곳.
- **중복 정리 방침**: 관리 창은 `names.py` 한 곳만 쓴다. 기존 도구들이 이걸 쓰게 바꾸는 일은 **그 도구를 다른 이유로 고칠 때 시험과 함께** 한다(한꺼번에 바꾸지 않음). 단 supervisor·activation·release_update·TOOLS 파일은 `names.py` 를 import 하지 않는다(그러면 `names.py` 가 서버 실행 코드가 되어 반입 금지 목록에 들어가야 함).
- **관리 창이 '만능'이 되지 않게**: 판단 로직(업데이트 자격·이사 안전 검사)은 기존 도구에 두고, 관리 창은 읽고·부르고·보여 주기만 한다.
- **화면 시험**: tkinter 화면은 자동 시험이 어렵다 → 판단은 전부 관리 핵심 층에 두고 거기를 시험한다. 화면은 실행해 찍어 보는 확인으로.
- **남는 구조 문제(이번 범위 밖)**: 루트 코드는 `update_git` 으로 안 바뀌어 서버 실행 코드(stage)보다 낡을 수 있다 — 루트 도구가 import 하는 루트 `backend/app` 도 마찬가지. 관리 창 자기 갱신(2단계)은 관리 창 파일만 해결한다. 근본 해결은 '루트 자동 갱신' 설계(별도, Jay 결정 후보).

**권한(6판)**: 웹이 없어졌으므로 창을 열 때 **관리자 승인 한 번**으로 창 자체를 관리자 권한으로 띄운다. 실행기는 창과 별도 프로세스라 창을 닫아도 작업이 끝까지 가고 결과를 남긴다. Python·tkinter 는 서버의 `.mvhub-runtime\python.txt` Python(표준 라이브러리 tkinter — 서버 PC 에 들어 있는지 첫 배달 전 확인), 새 패키지 설치 없음. 설치 보호 전제(루트·Python·상위 폴더는 Administrators·SYSTEM 만 쓰기)는 그대로.

- **확인은 한 번, 책임은 이렇게**: 창(ui)이 관리 핵심(`actions.py`)으로 대상(작업 종류·설치 루트·예: 업데이트할 origin/main 커밋)을 계산해 **창 안 확인 대화**에 보여 주고 사람이 [실행]을 누른다. 실행기는 실행 직전에 같은 코드로 대상을 **다시 계산해 창이 확인한 값과 비교**하고, 다르면 실행하지 않는다(확인을 두 번 묻지 않음). 앞 판의 실행기 `CONIN$` 확인은 `pythonw` 에 콘솔이 없어 이것으로 **대체**.
- **Git 업데이트의 '대상' 뜻(6차 지적, A안)**: coordinator 는 실행될 때 직접 `git fetch` 해 그때의 `origin/main` 을 고른다(`server_release_update.py:169`). 그래서 확인 대상은 **"이 설치 루트(E:\MV-hub-S)를 실행 시점의 최신 origin/main 으로 업데이트"** 로 정의한다. 확인 창에 보이는 커밋은 '지금 보이는 최신(참고)'으로 표시하고 고정 대상이 아님을 밝히며, 실제로 고른 커밋은 결과(준비 기록의 stage `source_commit`)로 보여 준다. 실행기가 비교하는 것은 작업 종류·설치 루트·서버 역할이다. 기존 제품 코드 수정 없음. (확인한 커밋만 설치하는 B안은 coordinator 수정이 필요해 하지 않는다.)
- **창 시작도 격리**: `MV_console.bat` 은 검증된 Python 을 `-I`(사용자 모듈·`PYTHON*` 무시)로 띄우고, 현재 폴더를 보호된 설치 루트로 두며, Tk 초기화 전에 `HOME`·`TCLLIBPATH` 를 지우고 `TCL_LIBRARY`·`TK_LIBRARY` 는 그 Python 의 `tcl` 폴더로만 정한다(`-I` 가 Tcl 환경까지 막는다고 가정하지 않음). tkinter 가 홈·현재 폴더의 `.Tk.py`·`.Tk.tcl` 등을 실행하는 `readprofile`(`tkinter/__init__.py:2534`)은 Tk 를 상속해 **아무것도 하지 않게** 막는다.
- **웹 때문에 있던 계약 정리**: 토큰·Host/Origin·CSP·브라우저 프로필·확장 대응, 일반 권한 화면을 위한 결과 읽기 SID·부모 추적은 **필요 없어짐**(창과 실행기가 같은 관리자 권한이라 보호된 작업 폴더를 그대로 읽음). 설치 ACL·고정 명령·환경 통제·독립 작업 수명·복구 기록은 **유지**.
- UIPI 는 낮은 무결성 프로그램의 입력 상당수를 막을 뿐, 같은 관리자 권한 프로그램이나 UIAccess 까지 막는 경계는 아니다. 클립보드·끌어 놓기 값은 믿지 않는다. **1단계에는 파일 열기 대화·탐색기/외부 프로그램 열기를 넣지 않는다**(관리자 창에서 셸 확장이 돌 수 있음) — 폴더는 경로를 보여 주고 복사만.
- 구조 규칙 보강: `names.py` 는 **관리 창 내부 기본값**(전역 설정으로 키우지 않음). supervisor·activation·release_update·TOOLS 파일은 **간접으로도** `server_console` 패키지를 import 하지 않는다(시험으로 확인). `actions.py` 는 고정 목록으로 시작(범용 실행 틀을 만들지 않음). `__init__.py` 는 Tk 초기화·작업 실행 같은 부작용이 없게.

## 구조(2판) — C안: 화면은 일반 권한, 위험한 동작만 누를 때마다 관리자 승인

```
바탕화면 "MV Hub 서버 관리" → MV_console.bat (일반 권한, 승인 창 없음)
  → tools/server_console.py   표준 라이브러리 HTTP, 127.0.0.1:임의 포트, 일반 권한
       ├─ 정적 화면 tools/server_console/{index.html, app.js, style.css}
       ├─ 읽기 API: 상태·로그·예약 작업·백업·NAS 표지(읽기만)
       └─ 동작 요청 → tools/server_console_job.py 를 관리자 승인(UAC)으로 띄움 ─┐
  → Chrome/Edge --app (일반 권한, 전용 프로필)                                  │
                                                                                ▼
  server_console_job.py (관리자, UI 와 독립 수명)
     · 전역 동작 잠금 logs\console-jobs\lock · 작업마다 logs\console-jobs\<id>\{output.log, state.json}
     · state = {kind, pid, 시작 시각, 시작 식별자, 종료 코드, 결과}
     · 정해진 동작 목록만, 인자는 실행기가 직접 다시 찾고 검증
```

- **왜 C안**: 관리자 권한으로 계속 떠 있는 웹 서버가 없고, 관리자 동작은 실행기 하나로 좁혀지며, 화면은 모의 그림 그대로 만들 수 있다. 단 UAC 창은 항상 뜨는 것도 아니고(UAC 끔·자동 승격 정책) 무엇을 하는지도 안 보여 주므로 **마지막 확인은 실행기 자신의 창**이 한다(아래). 브라우저 확장이 로그를 읽거나 동작 요청을 유도할 가능성은 남는 위험으로 인정한다.
- **실행기 최종 확인**: 실행기는 관리자 콘솔 창에 **자신이 다시 계산한** 작업 종류·설치 루트·대상(예: "E:\MV-hub-S 서버를 origin/main 으로 Git 업데이트")을 보여 주고 사람이 Y 를 쳐야 시작한다. Y 는 실제 콘솔(`CONIN$`)에서만 받고, 부모가 넘긴 표준 입력·파이프로는 승인되지 않는다. 무인 실행 없음. 화면 서버는 시작할 때 자기가 관리자 권한이 **아닌지** 확인하고, 관리자면 멈춘다.
- **실행기 입력**: 화면이 넘기는 것은 고정 작업 이름(1단계는 `git-update` 하나)과 형식이 정해진 작업 ID(영숫자 32자)뿐. 루트·Python·스크립트·명령·환경변수·출력 경로는 받지 않는다. 실행기는 자기 파일 위치와 예약 작업 `MVHub Server` 의 실행 경로를 대조해 루트를 스스로 정한다. 결과 파일에서 읽은 값으로 다음 명령을 만들지 않는다.
- **환경 통제**: 실행기는 `python -I -E`(사용자 모듈·`PYTHON*` 환경 무시)로 뜨고, 넘겨받은 환경을 믿지 않는다. updater 에 주는 환경은 실행기가 새로 만든다 — `SystemRoot`·`windir`·`ComSpec`(=`%SystemRoot%\System32\cmd.exe`)·`PATH`(System32·PowerShell·설치 확인된 Git·`.mvhub-runtime\node_dir.txt` 의 Node 만)·`TEMP`. `PYEXE`·`MVHUB_*`·`CONTENT_HUB_*` 는 지우고 필요한 것만(예: 검증 Python 은 `logs\server-verifier` 로 실행기가 직접 정함) 넣는다. 위조 환경을 넣어도 다른 실행 파일이 불리지 않는 시험을 둔다.
- **작업 폴더**: 상위 `logs\console-jobs\` 는 처음 한 번 실행기가 만들고, 이후엔 소유자(Administrators/SYSTEM)·ACL·재분석 지점(junction 등)을 검증한 뒤 재사용한다. **작업별 ID 폴더만 매번 새로 만든다**(이미 있으면 거절). 쓰기는 Administrators·SYSTEM 만.
- **결과 읽기 권한**: 읽기 권한을 받을 사용자는 화면 요청에서 받지 않고 **OS 로 확인한다** — 같은 계정 승격이면 실행기 자신의 사용자 SID, 다른 관리자 계정으로 승인했으면 실행기를 띄운 부모 프로세스(우리 화면 서버로 확인된 것: 실행 파일·스크립트 경로)의 토큰 사용자 SID. 확인하지 못하면 권한을 주지 않고, 화면에는 '결과는 실행기 창에서 확인'만 표시한다. 위조 SID 거절·다른 관리자 계정 승격을 시험한다.
- **설치 보호 전제**: 실행기는 관리자로 루트 코드를 돌리므로 **서버 루트 전체(bat·tools·`.mvhub-runtime\python.txt`·Python 설치 폴더·상위 폴더)는 Administrators·SYSTEM 만 쓸 수 있어야 한다**. 실행기의 ACL 검사(그 밖 SID 의 쓰기·수정 권한이 있으면 거절)는 잘못된 설치를 잡는 장치일 뿐, 이미 바뀐 실행기는 자기를 검사하지 않는다 — 그래서 첫 배달 때 서버 PC 에서 ACL 을 실측하고 문서에 조건으로 적는다.
- **실행기가 죽었을 때**: 실행기 잠금이 풀렸다고 다시 실행하지 않는다. 새 업데이트 전에는 실제 업데이트 흔적(`git-update.lock` 이 잡혀 있음·`server-update-request.json`·journal 이 끝 단계가 아님·`server-prepare.json` 이 running)을 확인하고, 하나라도 있거나 판단이 안 되면 **결과 확인 필요**로 막는다. 실행기는 `git-update.lock` 을 직접 잡지 않는다(자식 updater 와 교착 방지).
- **비용**: 동작마다 승인 클릭 한 번. 화면 서버는 SYSTEM 이 쓴 파일을 일반 권한으로 읽어야 한다(서버 PC ACL 실측 필요 — 못 읽으면 '확인 불가'로 표시, 권한을 자동으로 바꾸지 않는다).
- **작업 수명**: 창을 닫거나 화면 서버가 죽어도 실행기는 끝까지 간다. 다시 열면 `logs\console-jobs` 에서 진행 중·끝난 작업을 다시 보여 준다. 결과를 잃었으면 성공·실패로 추정하지 않고 **결과 확인 필요**. 창 종료를 이유로 업데이트·이사를 끄지 않는다. 종료 코드는 0/1 만 가정하지 않고 그대로 보존. `[n/6]` 은 표시용, 판정은 종료 코드.
- **실행 대상 확정**(`resolve_installation()`): 이 파일이 있는 곳이 등록된 설치 루트(예약 작업 `MVHub Server` 의 `task_launch.bat` 경로와 같고 `.git` 있는 클론)일 때만 동작. stage 사본(`logs\server-stages\…`) 안에서 실행되면 거절. 데이터 경로는 이 프로세스 환경이 아니라 **기계 환경변수**(SYSTEM 과 같은 값)로 계산.
- **코드 위조 방지**: 실행기는 관리자 권한으로 루트 코드를 돌리므로, 루트·`tools`·`.mvhub-runtime\python.txt` 를 일반 사용자가 쓸 수 있으면 동작을 거절한다(실행 전 ACL 검사).

## 보안(화면 서버 — 일반 권한이어도 지킨다)

- 127.0.0.1 에만 묶고 정규 주소는 `127.0.0.1:<port>` 하나. 정적 파일 포함 모든 요청의 `Host` 검사.
- 실행마다 새 토큰. 화면이 받은 즉시 주소에서 지우고(history.replaceState) 브라우저 저장소에 두지 않는다. 변경 요청은 토큰 + 정확한 `Origin` + `application/json` 모두 필수, `Origin` 없음·`null` 거절. CORS 없음.
- 응답: CSP `default-src 'self'`(외부 자원·인라인 스크립트 없음), `frame-ancestors 'none'`, `Cache-Control: no-store`. 로그·파일명·오류는 `textContent` 로만 넣는다.
- 요청 크기·연결 시간·동시 연결 수 제한. 경로 인자는 받지 않고 서버가 발급한 항목 ID 로만(실행기가 다시 찾고 junction·대상 변경 재확인).
- 확장 프로그램이 페이지를 읽고 조작하는 것까지는 토큰으로 못 막는다 — C안에서는 그래도 관리자 동작에 승인 창이 필요하다는 점이 마지막 방어.
- 서버 로그인(생성 접수 멈춤 — 2단계): 8010 의 상대가 진짜 우리 서버인지 먼저 확인 — 포트 주인 PID 의 실행 파일·정확한 스크립트 경로(현재 stage/루트 serve.py)·프로세스 생성 시각, `/api/ready` 의 `execution_nonce` = `server-activation.json`(nonce 는 비밀이 아니라 보조 대조). 하나라도 조회 실패면 로그인하지 않는다. 프록시·리다이렉트 금지, 표준 HTTP 배치만(TLS 설정이면 이 기능 끔). 로그인 뒤 `admin` 역할 확인. 토큰은 실행기 메모리에만.
- 경로·포트: 기계 환경변수가 실행 중인 SYSTEM 프로세스 값과 같다는 보장은 없다(`MV_server.bat` 이 `PORT`→`CONTENT_HUB_PORT` 로 덮음) → 실제 listener·ready 로 확인되지 않은 경로·포트는 '추정'으로 표시.

0. **공통 틀** — 쓰기 동작은 모두 1단계 틀(고정 동작 목록 `actions.py` → 확인 한 번 → 독립 실행기 `job_main.py` → 작업 기록·결과 보존)을 쓴다. 단 생성 접수(값 하나·API 한 번)는 화면 작업 스레드에서. **동작마다 확인 대상**을 `Plan.params` 에 담고 실행기가 실행 직전에 같은지 비교한다(1단계 `same_target` 은 종류·루트·역할만 — 넓힌다): 백업 = 확인한 옛 위치 지문·새 위치 · 주소 공지 = URL·이름·확인한 공지 판 · 배포 = file·sha256·화면이 본 `latest`/`candidate` sha(기존 `deploy_package(expect_published, expect_candidate)` 로 그대로 전달) · 재공지/해제 = 공지 ID·sha256. 모든 쓰기는 관리 창 기록 `logs\console-actions.jsonl`(시각·Windows 계정·로그인 계정·동작·확인 대상·결과·작업 ID)에 남는다 — 서버 감사 기록이 없는 동작(생성 접수 API 포함 — `gen_requests.py:418` 에 감사 없음)도 여기서 추적.
1. **관리자 로그인**(창마다 한 번) — 생성 접수 변경·릴리스 동작을 처음 누를 때 이메일·비밀번호 창 → 기존 `POST /api/auth/login`(127.0.0.1, 서버 TLS 면 https) → 토큰은 **화면 메모리에만**(파일·인자·환경변수·`request.json`·출력 로그 금지), 창을 닫으면 사라짐. 실행기에는 **상속한 표준 입력 파이프로 한 번만** 넘긴다(실행기는 시작하자마자 한 줄 읽고 닫음). 토큰이 만료되면 그 단계에서 실패로 기록하고 다시 로그인해 [이어서 하기]. 대안 기각: 저장된 `auth_secret` 으로 토큰 만들기(로그인 검사 우회·서명 비밀 취급) · 서버에 새 관리 창 열쇠 인증(발급·폐기·권한 체계 추가 — 이번 범위 밖).
2. **생성 접수** — 표시는 지금처럼 DB 읽기 전용(`inspect_fence`, '진행 중 생성 0' 은 Resolve·Comfy 까지 비었다는 뜻이 아님을 화면에 적음). [멈추기…]/[다시 받기] = 로그인 뒤 **서버 API** `GET` 으로 지금 값 확인 → 확인 창 → `PUT /api/gen-requests/deployment-pause` → `GET` 으로 결과 확인. 실행 중인 stage 가 자기 DB 에 쓰므로 관리 창의 DB 경로 짐작(기계 환경변수)에 기대지 않는다. 서버가 응답하지 않으면 바꾸지 않고 "서버가 꺼져 있어 바꿀 수 없음 — 아래 비상 절차"(SERVER.md 의 붙여넣기)로 안내.
3. **DB·백업**(실행기 작업 `backup-save`·`backup-run`) — 기존 검사를 줄이지 않는다:
   - 환경변수 `CONTENT_HUB_BACKUP_REPLICA_DIR` 가 있으면 위치는 보기만(바꾸기 막음, 이유 표시) · 예약 작업 `MVHub BackupCopy` 가 이 루트의 `task_launch.bat backup`·SYSTEM·켜짐·`IgnoreNew`·**실행 중 아님**이어야 함(라우터 `backup_replica.py:384` 의 조건과 같게 — 그 판정 코드를 루트 경로로 다시 씀).
   - [저장(시험 복사)]: 화면이 본 옛 위치 지문을 다시 비교 → 관리자 계정으로 `backup_replicate.probe()`(형식·자기 PC 여부·기존 폴더 내용 검사) → `TARGET_FILE` 원자 교체 = **'설정 저장됨' 따로 기록** → 직전 실행 시각·상태 파일 내용 보관 → `schtasks /Run` → 새 실행의 `started_at`·`target_id`(새 위치)·종료가 맞을 때만 결과로 채택(`server_move_easy.py:1309` 의 결과 확인 코드를 출발점으로 위치 지문 대조 보강). 제한 시간 넘김 = '결과 미확인' · `disabled`/`no_source` 는 종료 코드 0 이어도 성공 아님. 복사 실패여도 새 위치는 그대로 두고(관리자가 고른 값) "설정은 저장, 복사는 실패" 와 [이전 위치로 되돌리기]를 보인다. 실제 복사는 대상의 오래된 백업 정리(보관 30개)까지 하는 **기존 백업 복사**다(새 DB 백업·복원 검증 아님).
   - [지금 복사] = 위 실행·결과 귀속 부분만.
4. **주소** — 지금 주소·팀원 앱에 보이는 이름·[팀에 공지](실행기 작업 `address-notice`) = 공지 파일의 지금 판을 읽어 화면이 본 판과 같은지 확인 → `server_relocation.publish_announcement(릴리스 폴더, url, name, 기억한 판)` → 다시 읽어 우리가 쓴 판·URL 인지 확인. 기억한 판은 `.mvhub-runtime\console-state.json`. **발행자는 관리 창 하나**로 정한다(웹 탭 제거 전까지는 운영 규칙 — 옛 앱 [팀에 공지]는 잠금이 없어 막지 못함). 팀원 PC 는 알림 → **사용자가 눌러야** 새 주소로 바뀐다(자동 전환 아님 — 화면 문구도 그렇게).
5. **릴리스** — 'NAS 릴리스 폴더' 설정(4와 같이 씀) = `.mvhub-runtime\console-release\INSTALL_SOURCE.txt` 하나만 둔 관리 창 전용 폴더를 release 함수의 `root` 로 넘긴다(배포 위치 설정용으로만 — `install_mode` 를 속이는 파일 추가·`start_update` 재사용 금지). 함수(`list_packages`·`release_overview`·`package_manifest`·`promote_candidate`·`deploy_package`·`publish_announcement`)는 **실행기 안에서만** 가져오고, 가져오기 전에 환경을 정한다(`CONTENT_HUB_DATA` = 작업 폴더 안 빈 폴더 — `config.py:53` 의 `ASSETS_ROOT.mkdir` 가 실제 데이터에 닿지 않게 · AUTH·PORT 고정). 루트 코드 판의 함수가 그 릴리스의 manifest·검증 영수증 형식을 지원하지 않으면 함수가 거절하고 그대로 실패로 기록. NAS 잠금은 기존 `release.lock`(`release_update.py:596`) 그대로. 화면 목록은 화면 작업 스레드가 같은 방식으로 실행기 없이 읽기만 할 수 없으니(가져오기 부작용) **목록 읽기도 짧은 실행기 작업**(쓰기 없음)으로.
   - [배포](`release-deploy`, 단계 기록): 공지 찾기(sha) → 없으면 등록 → **이 작업에서 아직 안 했으면** announce(단계 기록 `announced`) → 공지 상태 재확인 → NAS `promote_candidate`(후보 줄) / `deploy_package`(그 밖, 화면이 본 두 표지 sha 전달). 실패·응답 유실은 단계별로 기록하고, [이어서 하기]는 기록한 단계부터(같은 작업에서 announce 를 되풀이하지 않음 — `deploy_package` 가 이미 표지면 'already', 후보만 바뀐 부분 실패면 이어서 처리). "알림은 나갔지만 배포 결과를 모름" 을 그대로 보인다(웹 `UpdateNoticesSection.tsx:149-153` 과 같은 구분).
   - [재공지](`release-announce`) = announce 만(NAS 안 건드림) · [해제](`release-remove`) = DELETE 만. 둘에 '등록→announce' 공통 순서를 쓰지 않는다.
   - 순서 안내: 생성 접수 멈추기 → Git 업데이트 → 배포 → 팀원 업데이트 뒤 다시 받기. 업데이트·배포가 실패하면 **접수는 멈춘 채로 두고** 지금 상태·다음에 할 일을 보인다.
6. **관리 도구 갱신 = 관리 창 전용 stage**(1차 지적 5 반영 — 루트 앞감기 대신). 루트는 건드리지 않는다.
   - 관리 창 코드를 `logs\console-stages\<커밋 12자리>\` 에 꺼내 그 사본으로 실행: 대상 = `tools/server_console/**` + 순수 보조 모듈 `tools/log_viewer.py`·`tools/deploy_fence_check.py`(경로에 묶이지 않는 것만 — 같은 커밋 판). 경로에 묶인 루트 도구(`tools/backup_replicate.py` 는 자기 위치로 ROOT 를 정함)와 backend 함수는 **루트 것을 명시적 경로로** 가져온다(예약 작업·서버와 같은 판을 쓰기 위해).
   - [관리 도구 갱신](`tools-update`, `git-update.lock` 을 잡고 — 이 작업은 `run_update_git.ps1` 을 부르지 않으니 잡아도 겹치지 않음): 업데이트 흔적·미확인 작업 재검사 → 루트 저장소에서 `git fetch origin`(루트 HEAD·작업 트리는 그대로) → **그 순간의 origin/main SHA 를 고정** → `git archive <SHA> <대상 경로>` 를 새 stage 폴더로(이미 있으면 거절) → 파일마다 sha256 목록 `console-stage.json` → 관리 창 시작 점검(`main.py --check` 를 그 사본으로) → 포인터 `logs\console-current.json` 원자 교체. 결과에 고정한 SHA. 옛 stage 는 최근 3개 보관([이전 관리 창으로] 되돌리기).
   - 시작: 루트 `MV_console.bat` → 루트 `main.py`(이제 **부트스트랩** — 거의 안 바뀜) → 포인터의 stage 를 목록 대조(연결 지점·크기·sha256)로 검증하고 그 사본의 `main.py` 를 같은 격리로 실행. 검증 실패·포인터 없음이면 루트 판으로 열고 상단에 "관리 창 stage 확인 실패 — 루트 판으로 열었음".
   - 교체 중 실행 파일: 실행기는 시작할 때 고정된 stage 사본에서 돌고(포인터가 바뀌어도 그 사본은 그대로), 화면은 끝난 뒤 "창을 다시 여세요" + [다시 열기](화면이 단일 실행 잠금을 놓고 부트스트랩을 다시 띄움). 열린 옛 화면이 새 stage 의 실행기를 띄우지 않게 — 실행기 경로는 **화면이 시작한 stage** 로 고정.
   - 부트스트랩·`MV_console.bat` 자체가 바뀔 때만 수동 반입(드묾). 2단계 첫 반입도 수동(부트스트랩이 생기는 판이라).
   - 기각한 대안: 루트 앞감기 + 좁은 허용 목록 — 안전하지만 main 에 앱 변경(frontend·backend)이 섞이는 순간 늘 막혀 '붙여넣기 없음' 목표를 못 지킨다.
7. **웹 관리자 창** — '공유 서버' 탭 없앰 · '업데이트' 탭은 목록 + [이 PC에 먼저 설치]만(관리자만) — 선설치에 필요한 공지 찾기/등록 호출은 남긴다(`UpdateNoticesSection.tsx:217`). 백엔드 라우트는 그대로(옛 앱·되돌리기). 다음 팀 릴리스와 함께 나가며 그 전까지는 두 곳에 기능이 있다(주소 공지는 4의 운영 규칙).
8. **1단계 고침 함께** — 로그의 터미널 색 코드 지우기·업데이트 준비 로그는 '업데이트 기록' 탭에만·출처 이름 짧게.

### 3판 — 2차 지적 반영(위 2판 항목을 이렇게 바꾼다)

- **(6) 설치 루트와 코드 경로를 나눈다.** `install_root` = 부트스트랩이 자기 위치로 정한 루트(`.mvhub-runtime\python.txt`·`MV_console.bat`·`task_launch.bat` 이 있고 서버 예약 작업이 이 루트를 가리키는지 1단계 `server_task_matches` 로 확인) — `.git`·등록 Python·`logs`(작업 기록·잠금·UI 단일 실행 잠금)·데이터는 모두 여기. `code_root` = 검증한 stage(없으면 루트) — 관리 창 모듈·실행기만. 실행기는 `--install-root`·`--code-root` 를 받고 둘 다 다시 검증.
- **(6) 진입점 역할 분리.** 루트 `tools/server_console/main.py` = **부트스트랩 전용**(표준 라이브러리만, `server_console` 패키지를 가져오지 않음): 격리 → 포인터·stage 검증 → **새 격리 프로세스**로 `python -I -B <code_root>\tools\server_console\console.py --install-root <루트>` 실행. 앱 진입점은 새 `console.py`(루트·stage 모두에 있음, `--launch`·`--check` 도 여기로). 검증 실패·포인터 없음 = 루트의 `console.py` 로 같은 방식 실행 + 상단에 "관리 창 stage 확인 실패 — 루트 판". 2단계 첫 반입 때 부트스트랩이 생긴다(수동 한 번).
- **(6) 경로에 묶인 루트 도구는 자식 프로세스로.** `backup_replicate`(가져오면 루트 `tools` 를 경로 맨 앞에 넣음 — `backup_replicate.py:42`)·backend 함수(`release_update`·`server_relocation`)는 관리 창 프로세스에서 가져오지 않고, 루트 Python `-I -B` 로 도는 **짧은 도우미 자식**이 가져와 JSON 으로만 결과를 돌려준다(쓰기 작업은 그 도우미를 실행기가 부름). 그래서 관리 창의 `log_viewer`·`deploy_fence_check` 는 늘 code_root 판이고, 시작할 때 실제 로드 경로(`module.__file__`)가 code_root 아래인지 확인해 다르면 열지 않는다.
- **(6) stage 만들기·검증·보관.**
  - 만들기(`tools-update`): `git archive <고정 SHA> <허용 경로>` 를 `logs\console-stages\.tmp-<임의>` 에 → **기대 파일 집합 = `git ls-tree -r --name-only <SHA> -- <허용 경로>`** 와 추출 결과가 정확히 같아야 함(`export-ignore` 로 빠진 파일·필수 파일 누락 거절) → 해시는 추출된 실제 바이트 → 임시 사본으로 `console.py --check`(Tk 초기화 + **모든 관리 창 모듈 가져오기**, `-B`) → 성공하면 `logs\console-stages\<SHA 40자>` 로 이름 바꿔 게시(이미 있으면 그 목록으로 재검증해 같을 때만 재사용) → 포인터 원자 교체.

  - 보관: 지우지 않는 것 = 현재 포인터 · 직전 정상 stage · **실행 중인 화면(단일 실행 잠금 파일에 code_root 기록)과 미해결 작업(작업 상태에 code_root 기록)이 쓰는 stage**. 그 밖의 것만 오래된 순으로 정리(남는 수 3 이상). [이전 관리 창으로] = 직전 정상 stage 로 포인터 교체.
  - 신뢰 범위: 포인터·목록·코드를 함께 바꿀 수 있는 계정을 자체 해시로는 못 막는다 — 1단계의 권한 위험 감수(Jay 결정)와 같은 범위로 적고, **권한 알림 대상에 `logs\console-current.json`·`logs\console-stages`(하위)·그 위 폴더를 추가**한다.
- **(5) 배포 이어서 하기 — 재조회로 판단, 자동 재공지 없음.**

- **(1) 토큰 파이프 계약** — 실행기는 `stdin=PIPE`(+ `DETACHED_PROCESS`)로 띄우고 실제 `pythonw` 조합에서 읽힘을 시험으로 확인. 실행기: 시작 직후 최대 10초·4KB 까지 한 줄 읽기, 빈 값·중간 EOF·시간 초과면 아무것도 쓰지 않고 `runner_error`(토큰을 받기 전에는 어떤 쓰기도 안 함), 읽은 뒤 stdin 닫기. 화면: 쓰고 닫기, `BrokenPipe` 는 시작 실패로 기록. 토큰은 **화면과 실행기 메모리에만**.
