# 공유 서버 백업 보관 기간 늘리기 — 최근 7 + 일별 14 + 주별 8 (2026-11-15)

Jay 11-15 "남은 것도 모두 진행 · 정할 것은 Codex 와 같이". 남은 결정 판정(Codex `decide-answer`, D6)이 "서버에도 시간축 보관 — 최근 7세트 + 일별 14일 + 주별 8주, NAS 복제도 세트 단위로 맞춘다"로 정했다. 1-A([저장통합_1A_백업보관_2026-11-12.md](저장통합_1A_백업보관_2026-11-12.md))는 서버 보관 정책을 범위 밖으로 남겼다.

## 문제 (총괄 코드 확인)

- `backend/app/services/backup.py`: 서버(AUTH 켜짐)는 최근 7세트만, 일별·주별 0. 변경 백업(조용 5분·최소 15분)이 돌아 일하는 날 7세트 = 약 1시간 51분치(dev AUTH 실측, 세트당 약 89.9MB — Codex 측정).
- `tools/backup_replicate.py`: NAS 복제는 폴더당 최신 30파일(원본에 있는 파일은 보호). 세트·시간축과 맞지 않는다.
- 결과: 늦게 발견한 손상을 되돌릴 백업이 몇 시간 만에 사라질 수 있다.

## 고침 (설계 Claude `fix-designs/C3-server-backup.md` → Codex 확정·구현 `01a1dcdb-f891`, 작업실 `codex/fix-backup-1115`)

- 서버 기본 보관 = 최근 7 + 일별 14 + 주별 8(로컬 허브 8·14·8 그대로, AUTH 에서 정책 파일을 읽지 않는 1-A 결정 유지). 1-A 의 보관 규칙 코드(곁파일·세트 조회·회전)를 그대로 쓴다.
- NAS 자동 백업 복제도 같은 시간축으로 세트 단위 정리, 원본 세트는 계속 보호. 작업자 업로드 복제의 30개 규칙은 그대로.
- 관리 창(`tools/server_console`)·`docs/SERVER.md`·`docs/SERVER_RECOVERY.md` 의 "30개" 안내를 새 규칙으로.
- 용량 추정(Codex, dev 세트 크기 기준 — 서버 실제 크기 모름): 정상 기본 정책의 단순 합 상한 29세트(보호·불완전 세트와 환경변수 증가는 제외 — 절대 상한 아님) 약 2.61GB, NAS 는 자체 보관분과 원본 보호분이 안 겹치는 경우 약 5.22GB.
- 시험: AUTH·로컬 기본값 · AUTH 회전이 최근 7 + 날마다 1 + 주마다 1 만 남김(정책 파일 무시) · NAS 가 원본 회전 뒤에도 날마다·주마다 세트를 남김. 수정 전 5실패 → 수정 후 6통과 → 제품 코드 되돌리면 다시 5실패(Codex). 샌드박스에서 못 돈 관리 창·업데이터 시험 5건은 총괄이 밖에서 통과 확인.
- 서버 적용은 Jay 의 서버 업데이트 때(이 작업은 코드만).
