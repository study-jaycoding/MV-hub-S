# 수정 창·크게 보기 원본 로딩 — 직접 받기와 로딩 링 A2 (2026-11-09)

## Jay 지시 (2026-11-09, 그대로)

- (수정 창 "원본 불러오는 중…" 사진) "이미지 수정이나 영상수정 할때 이미지처럼 딜레이가 있다. 영상이나 이미지를 크게볼때도 딜레이가 있다. 딜레이를 줄이는 방법과 줄일수없다면 로딩화면같은게 나와서 딜레이가 덜 느껴지게 시안부터 만들어서 보고"
- 시안 수정 창 A(썸네일+가운데 원형 진행)·B(칩·타임라인)·C(흐림+빛줄기), 크게 보기 A·B → "흐리게 되면서 a로 보이는 시안. a디자인을 몇개더 만들어보자" → A1~A6 → **"a2"**(크고 얇은 링, 글자는 링 안)

## 측정(11-09, 이 PC — 최근 완료분 영상 6·이미지 6, 각 2회)

- 원본 받기: CloudFront 에 없을 때(Miss) 0.4~3.4초(첫 바이트 0.35~0.96초), 있을 때(Hit) 0.07~0.47초. CDN 은 `Access-Control-Allow-Origin: *`·`Cache-Control: public, max-age=31536000, immutable`.
- 수정 창은 원본을 `fetchBlob(…, gen.id)` 로 받는다 → 허브의 각인 다운로드(`/api/download?gen_id=`): 허브가 끝까지 받아 임시 파일 → 영상은 ffmpeg 로 컨테이너 다시 쓰기(0.07~0.16초) → 브라우저. 브라우저 캐시를 못 쓰고 열 때마다 CDN 에서 다시 받는다. 수정 창엔 각인이 필요 없다(올리는 그림은 캔버스에서 새로 굽는다).
- 브라우저가 CORS 로 직접 받은 원본은 두 번째부터 4ms(캐시). 단 크게 보기의 `<img>` 가 받은 캐시는 `fetch` 가 다시 쓰지 못했다(첫 fetch 769ms) — 크게 보기 요청 방식을 바꾸면 CORS 없는 주소에서 그림이 안 뜰 위험이 있어 이번엔 손대지 않는다.
- 브라우저 처리: 영상 준비(loadeddata) 40~195ms + 프레임 PNG 굽기 23~176ms(4K 포함), 이미지 풀기 11~45ms — 작다.
- 영상 6개 중 4개는 moov 가 파일 끝(크게 보기 재생 시작이 늦는 이유, 09-20 기록과 같음).

## 정한 것

- 수정 창 원본은 브라우저가 직접 받는다(genId 를 넘기지 않음 — CORS 실패면 기존대로 허브 프록시). 다시 열면 브라우저 캐시, 받은 양으로 진행률.
- 받는 동안: 카드가 띄우는 썸네일을 흐리게 깔고(창이 처음부터 제 비율) 가운데 A2 링(% · 받은 MB / 전체 MB, 전체를 모르면 도는 링). 지시문·모델은 그동안에도 쓸 수 있고 생성 단추만 "원본 받는 중"으로 잠긴다. 원본을 못 받으면 링 대신 오류만.
- 크게 보기: 썸네일 자리 표시가 깔린 동안 같은 A2 링(진행률을 알 수 없어 도는 링 + "불러오는 중")과 흐림. 그림은 원본이 뜨면, 영상은 첫 장면이 준비되면(loadeddata) 사라진다. 썸네일을 넘기지 않는 곳(Assets·레퍼런스·정보 창)은 그대로.
- 재제안 금지 목록(09-20 기각 — 미리 받기·프리페치·허브 캐시·moov 재배치)은 건드리지 않는다.
- 도는 링은 `steps(12)` — 끝없이 도는 애니메이션은 steps() 규칙(쉬는 동안 CPU, `tests/idleCssAnimations`)이 전체 시험에서 잡았다.
- 같이 고친 것: 수정 창 원본 실패 문구의 조사("원본 영상를" → "원본 영상을", 이미지도 같은 식).
