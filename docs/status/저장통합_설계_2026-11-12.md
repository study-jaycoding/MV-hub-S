## 2. 원칙 (네 줄)

1. **잃으면 안 되는 작업물은 원본을 이 PC 허브 DB 한 곳에 둔다.** 브라우저는 "빨리 보이는 사본 + 보낼 대기열"이다.
2. **모든 작업물은 같은 저장 절차 하나를 지난다.** 저장 시점·대기열·기준판 대조·재시도·충돌 사본·상태 집계는 한 구현이 맡고, 종류별 코드는 "어디에 쓰고 무엇을 검사하나"만 맡는다. 표(테이블)까지 하나로 합칠 필요는 없다.
3. **백업은 세트 단위로 오래 남기되, 지우기는 보수적으로 한다.** 확실히 완성된 세트만 세고, 이상하면 지우지 않는다.
4. **저장 안 된 것은 저장 안 됐다고 보인다.** 허브로 못 간 것(상한 초과·꺼짐·오류)과 브라우저에도 못 쓴 것(용량 부족 등)을 구분해 보이고, 하나라도 있으면 "모두 저장됨"이라고 하지 않는다.

자동 저장을 **꺼 두면**(§4-5) [지금 저장]을 누르기 전까지는 브라우저 사본이 더 새것이다. 원칙 1 은 "켜져 있을 때 원본은 허브"로 읽는다.

주의: 여기서 "허브 DB" 는 **이 PC 의 로컬 허브**다. 다른 PC 와 자동으로 같아지지는 않는다(그건 공유 서버 발행의 일이고 이 설계 범위 밖). 얻는 것은 ① 브라우저를 바꾸거나 사이트 데이터를 지워도 남는다 ② 백업 세트에 들어가 작업자 백업으로 서버까지 복제된다(서버 보관 개수는 §4-3) ③ 같은 PC 의 다른 창(리졸브 패널 포함)이 같은 값을 본다.

## 4. 설계

### 4-1. 공통 저장 절차 ("작업 문서 저장소") — C안

**표는 그대로, 절차를 하나로(C안, Codex 권고 채택).** 1판의 A안(새 공용 표)·B안(`scene_notebook*` 에 kind)은 둘 다 접는다. B안은 본문이 `scene_backup` 에 있고 보관본·요청 영수증·옛 경로 트리거까지 얽혀 있어 "kind 칸 하나"가 아니라 큰 이관이 된다(`db_migrations.py:1012`). A안은 편집 문서를 이미 있는 `edit_doc_head/copy` 에서 굳이 옮기게 된다.

- **물리 표**: 캔버스 = `scene_backup` + `scene_notebook*` 그대로. 편집 = `edit_doc_head` + `edit_doc_copy` 그대로. 회색 표시만 새 저장소(항목별 변경 — 생성물·어셋·폴더 범위와 계정 귀속을 담는다).
- **브라우저 쪽 한 구현**(가칭 `workDocClient`): 저장 시점(자동 저장 설정) · 영속 대기열 · 기준판 대조 · 재시도 · 응답 처리 · 상태 집계를 혼자 맡는다. 종류별 어댑터는 저장·검증만. 기존 `sceneNotebook` 과 새 구현이 각자 이 절차를 계속 가지면 이름만 통합한 것이므로, 3단계 완료 조건에 "절차 코드 한 벌"을 넣는다.
- **허브 쪽**: 종류별 저장 입구에 **서버 검증을 새로 둔다**(종류·문서 버전별). 지금 허브는 JSON 객체·ID 일치만 본다. 이미 들어 있는 불완전 문서는 거절하지 않고 보존하는 호환 길을 둔다(11-11 part2 처럼 깨진 문서를 지우지 않게).

**모든 종류가 지킬 계약**:
1. **저장 이유**: 모든 허브 쓰기 입구가 이유(타이머·[지금 저장]·편집권 넘김·창 닫기·MCP 반영·이관 등)를 달고, 자동 저장 설정을 검사한다. 꺼짐에서 허용하는 명시적 저장을 이 목록으로 구분한다(§4-5).
2. **세대**: 복원하면 바뀌는 세대 식별자를 모든 종류에 둔다(캔버스는 이미 `history_id` 교체가 있음, `scene_notebook.py:419` · 편집은 판 번호만 비교해 복원 뒤 번호가 다시 올라가면 다른 내용이 통과할 수 있음, `edit_docs.py:130`). 옛 세대의 대기열은 자동으로 보내지 않고 **복구 후보로 보관**한다.
3. **기준판 보존**: 대기 중인 문서의 기준판을 허브 최신 판으로 바꿔 끼우지 않는다(덮어쓰기 방지가 무력해진다). 보내는 동안 생긴 변경은 응답이 확인한 판까지만 반영한다.
4. **임대 범위**: 지금 임대는 계정 단위라 그대로 공용화하면 캔버스를 쓰는 창이 편집 문서·회색까지 막는다. 임대 키에 충돌 범위를 넣는다 — 캔버스는 공책 단위 잠금 유지, 편집은 문서 단위, 회색은 항목별 변경이라 임대 없이.
5. **브라우저 저장 성공 확인**: 작업물 저장은 성공·실패를 돌려주는 계약으로 한다(지금 `saveJSON()` 은 실패를 삼킨다). 용량 부족·접근 차단·트랜잭션 실패면 "브라우저에도 저장 안 됨"(빨강)으로 보인다.
6. **허브 꺼짐과 `local_only` 는 다르다**: 허브가 잠깐 안 닿으면 화면은 브라우저 사본으로 계속 쓰고 대기열에 쌓았다가 다시 보낸다. `local_only` 는 큰 문서 등으로 공책 참여를 포기하고 임대를 놓은 상태다(`sceneWriter.ts:175`·`279`). 1판의 "같은 길"은 틀렸다 — 둘을 따로 다룬다.
7. **로컬 허브 전용**: 새 공통 API 는 로컬 처리 목록에 등록해 프록시가 공유 서버로 넘기지 않게 한다(`routers/_proxy.py:655`, 공책과 같은 조건).

### 4-2. 큰 문서

지금 상한은 "한 번에 보내는 양"만의 문제가 아니다 — 큰 씬 하나가 공책 전체를 `local_only` 로 만들고, 사용 중 큰 변경은 `upload_failed` 사본으로 남는데 전체 상태는 `ready` 로 보일 수 있다(`sceneNotebook.ts:554`·`750`).

- **분할 업로드는 지금 안 한다.** 지금 8MiB 묶음 전송은 여러 문서를 나누는 것이지 한 문서를 쪼개는 것이 아니다. 한 문서 분할이 정말 필요해지면(실측으로) 임시 조각 저장 → 전체 크기·해시 검증 → 중단 청소 → 다 모인 뒤 한 번에 원본 반영으로 한다.
- **상한을 실측해서 한 벌로 맞춘다**: UTF-8 바이트 기준으로 문서별·묶음·HTTP 본문 상한을 나누고, 클라이언트·허브·파일 가져오기(편집 가져오기도 1MiB, `editArchive.ts:22`)를 함께 맞춘다. 숫자는 실제 정상 문서 크기를 잰 뒤 정한다(무제한 아님 — 공책 조회가 본문을 한꺼번에 읽어 메모리에도 영향).
- **요청 크기 방어**: 지금 업로드 제한은 특정 POST 경로만 본다(`upload_limits.py:58`). 씬·편집 PUT 에도 본문 상한을 둔다.
- **상한을 넘은 문서**: 브라우저 원문 보존 · 전체 미저장 집계에 넣음(원칙 4) · 파일 내보내기 · 크기를 줄이면 다시 시도. 일반 재시도로는 안 풀리므로 재시도를 반복하지 않는다. 큰 문서 하나 때문에 나머지 문서의 허브 저장이 막히지 않게 한다.
- **백업 경계**: 큰 원본·충돌 사본이 콘텐츠 DB 를 키운다. 서버 백업은 파일당 512MiB 상한이 있어(`routers/db_backup.py:47`) "문서 저장은 됐는데 서버 백업은 실패"가 생길 수 있다 → 백업 상태 줄에 보인다.

### 4-3. 백업

**보관 규칙**: 최근 N세트 + 날마다 1세트 N일 + 주마다 1세트 N주. 세트 단위로 솎는다. 숫자는 J1.

**삭제 안전 계약**(Codex C7·Q5 채택):
- 보관 계산에는 **검증된 완성 세트만** 넣는다(대표 파일·구성원·manifest 가 다 맞는 것). 불완전 세트 때문에 정상 세트가 "넘쳤다"고 판단하지 않는다.
- 지울 때는 먼저 "지우는 중" 표식을 남기고 구성원을 지운 뒤 표식을 걷는다. 중간에 실패한 세트는 복원 목록에서 빼고 다음 정리 대상으로 남긴다(지금은 파일별로 지우며 오류를 무시한다, `backup.py:206`).
- **촬영 순서와 달력 시각을 나눈다**: 세트마다 UTC 촬영 시각과 고정 보관 시간대(한국 시간)·주 시작 기준을 기록하고, OS 시간대나 파일 mtime 으로 다시 나누지 않는다(서버 OS 는 UTC). **시계가 뒤로 간 것을 감지하면 삭제를 보류**하고, 방금 만든 정상 세트는 어떤 경우에도 지우지 않는다.
- **보관 양을 줄일 때**: 바꾸기 전에 지워질 세트 수·기간·용량을 보여 주고 확인받는다. 백업을 복원해 옛 설정이 돌아왔다고 바로 대량 솎기를 하지 않는다.
- **보호 세트**: 복원 직전 세트는 반드시 보호(지금 복원 전 `.bak` 가 회전 밖에 있는 보호를 새 체계에서도 유지, `db_transfer.py:374`). [지금 백업]으로 찍은 세트는 자동 세트와 구별해 보이고 보호 여부를 보인다. 보호 세트 용량은 따로 센다. 세트마다 `reason`(자동·수동·복원 직전)·보호 여부를 기록한다.
- **보관 정보는 manifest 밖 곁파일에**: 촬영 순서 번호(시계와 무관)·UTC 촬영 시각·보관 시간대·`reason`·보호·"지우는 중"·manifest 의 `set_id` 를 세트마다 `content_hub_<stamp>.keep.json` 에 둔다. manifest 는 필드가 정확히 일치해야 통과하므로(`backup_manifest.py:91`) 건드리지 않는다 → 1-A 는 manifest 형식·서버 수신(ZIP 허용 목록, `db_transfer.py:556`)·NAS 복제(`*.db`·`*.manifest.json` 만 복제, `backup_replicate.py:636`·`657`)를 바꾸지 않는다. 곁파일은 로컬 보관 규칙 전용이라 서버로 보내지 않는다. 그래서 로컬의 보호·촬영 순서·"지우는 중"은 NAS 정리(`prune_dir` 의 보호 = 원본에 아직 있는 파일 이름)에 전달되지 않는다 — 이 범위로 둔다.
  - **도입 등록**: 1-A 가 처음 켜질 때 기존 세트를 검증해 곁파일을 만들어 준다(`reason=도입 전`, 순서는 그때 이름순). 등록 뒤에는 **곁파일이 없거나 깨진 세트는 지우지 않고**(보호로 취급) 상태 줄에 보인다 — 새 보호 세트의 곁파일이 사라져 보호가 풀리는 일을 막는다(3차).
  - **만들 때**: 촬영 순서 번호는 생성 잠금(`_BACKUP_LOCK`) 안에서 "등록된 최댓값 + 1"로 준다. 곁파일을 원자적으로 저장한 **뒤에** 콘텐츠 대표 파일을 공개한다. 곁파일 저장이 실패하면 그 세트를 완료로 치지 않고 솎기도 하지 않는다.
  - **지울 때**: 곁파일에 "지우는 중"을 먼저 적고 → 구성원을 지우고 → 곁파일을 **마지막에** 지운다. 다시 켜질 때는 대표 DB 가 없어도 "지우는 중" 곁파일을 찾아 정리를 이어 간다(지금 `_list_backups` 는 DB 만 찾아서 콘텐츠를 먼저 지운 뒤 멈추면 남은 파일을 못 찾는다, `backup.py:95`·`212`). 복원·서버 전송용으로 복사 중인 세트는 지우지 않는다.
  - **세트 조회 하나로**: 목록(`list_backups_info`)·회전·최신본(`latest_backup_path` — 서버 전송 대기열 보강에도 쓰임, `worker_backup.py:703`)·주기 판단(지금은 mtime)·복원 선택이 같은 함수로 "완성 + 지우는 중 아님 + 촬영 순서"를 따른다(지금은 이름순·mtime 이 섞임, `backup.py:98`·`138`·`184`). 순서 번호가 빠지거나 깨지거나 겹쳐 순서를 판단할 수 없으면 **추정해서 솎지 않는다**(삭제 보류 + 상태 줄).
- **디스크 부족**: 새 세트·임시 파일·전송 대기 사본·복원 준비본 여유까지 계산한다. 부족하면 실패로 보이고 다시 시도 간격을 늘린다. 공간을 만들려고 마지막 정상 세트나 보호 세트를 자동으로 지우지 않는다. 새 세트를 검증·공개한 **뒤에만** 솎는 지금 순서는 유지한다.

**구성원과 일관성**:
- 계정 세트 = 콘텐츠·휴지통 + 그 계정 Agent 대화 DB + 그 계정 `asset_mounts.json`(+ PC 공용 `manage_hub.db` 사본, 복원은 §3 대로). 폴더 안 Agent DB 를 통째로 넣지 않는다.
- **콘텐츠·휴지통은 지금처럼 한 시점 짝**으로 뜬다(B1 — 읽기 시점을 묶고 복원 때 짝을 검사, `backup_verify.py:93`·`db_transfer.py:314`). 이 보장은 약하게 하지 않는다.
- 그 밖의 구성원(Agent 대화·폴더 등록·관리 DB)은 **구성원별 독립 스냅샷**: DB 는 SQLite 백업 API(파일·WAL 순차 복사 금지), JSON 은 바이트를 읽어 해시와 함께, 구성원마다 촬영 시각을 남긴다. 모든 쓰기를 잠가 같은 순간을 맞추지는 않는다(지금도 관리 DB 까지 같은 시점은 보장 안 함, `backup_verify.py:87`).
- 대신 구성원 사이 **참조가 있으므로 복원 뒤 확인**한다(2차 D1):
  - Agent 대화 → 콘텐츠: 대화가 생성물 ID·어셋 경로·계획 ID 를 담는다(`repo/agent_chat.py:308`, `routers/agent_chat.py:249`). 복원 뒤 콘텐츠에 없는 계획·생성물은 "연결 끊김"으로 보이고, 다시 확인하기 전에는 실행·이어하기를 막는다. 없는 계획을 자동으로 다시 만들지 않는다. 외부 CLI 세션 이어하기는 기록 열람과 따로 판정한다.
  - 폴더 등록 ↔ 콘텐츠: 씬은 `asset:{등록 이름}|{경로}` 로 파일을 찾는다(`sceneMedia.ts:30`, `routers/assets.py:348`). 시점이 섞이면 같은 이름의 **다른** 폴더를 가리킬 수 있다. 복원 뒤 등록 경로를 확인하고, 확인 못 한 이름 기반 참조는 "다시 연결" 대상으로 보인다. 이름이 같다고 다른 경로에 자동 연결하지 않는다.
  - 관리 DB ↔ 콘텐츠: 활동 집계가 `local_gen_id` 로 콘텐츠 생성물과 대조한다(`manage_db.py:45`, `manage_task_activity.py:65`). 계정 복원이 관리 DB 를 덮지 않는 방침은 그대로 두고, 집계가 서로 다른 시점일 수 있음을 인정해 기존 대조·중복 방지 경로를 시험으로 확인한다.
- 변경 감지에 `manage_hub.db`·Agent 대화·폴더 등록 변경을 더한다.

**형식 호환(C1)**: manifest 에 새 구성원(역할)을 더하면 생성·검증·전송·서버 수신·복원·NAS 복제가 함께 바뀌어야 한다. 순서 = **읽는 쪽 먼저**(서버 수신·복원이 새 역할을 받게) → 서버 업데이트 확인 → 그 뒤 생성·전송을 켬. 서버가 아직 못 받으면 로컬에만 두고 화면에 "로컬 보관됨 · 서버에는 이 구성원 미전송"을 구분해 보인다. 서버 전송의 "빈 자료" 판정(`worker_backup.py:86`·`556`)도 새 구성원만 있는 계정을 빈 것으로 보지 않게 넓힌다.

**세 층 보관을 함께 정한다**: 로컬(사용자가 고름) · 공유 서버 수신(지금 계정당 10세트) · NAS 복제(30세트, 세트 단위). 서버에서 이미 사라진 세트는 NAS 가 나중에 복제할 수 없다. 서버·NAS 값을 바꾸는 것은 서버 업데이트가 필요한 별도 일이고, **서버 실제 상태는 Jay 확인**(공유 서버 직접 접속 금지).

### 4-4. 이름·코드 정리

**꺼짐의 실패 경로 계약**(Codex Q4 채택 — 꺼짐은 "오래 사는 미전송 갈래"로 다룬다):
1. **닫기**: 앱이 제어하는 닫기·로그아웃·새로고침은 앱 대화상자 [저장하고 닫기][브라우저에 남기기][취소]로 묻는다. 브라우저의 `beforeunload` 는 마지막 일반 경고로만 쓴다(사용자 문구가 안 나오거나 무시될 수 있음 · 앱 강제 새로고침은 경고를 지움, `unloadGuard.ts:17`). 닫기 전송(64KiB 넘으면 안 만듦, `sceneNotebook.ts:313`)은 보존 보장으로 삼지 않는다.
2. **편집권 넘김**: 다른 창이 쓰려고 할 때 안 옮긴 변경을 어떻게 할지 — **J5**. 어느 쪽이든 **정상 넘김과 강제로 가져오기를 나눈다**(2차 D4). 지금은 넘기는 창이 저장을 5초까지 기다리고, 그 뒤 받는 창이 강제로 가져갈 수 있으며 서버도 저장 완료 확인 없이 허용한다(`sceneWriter.ts:288`·`302`·`359`, `scene_writer.py:118`). 그래서:
   - 정상 넘김 = 넘길 변경의 처리 결과(저장 완료 또는 로컬 보존 완료)를 **같은 임대·세대에서 확인한 뒤** 넘긴다. `ready` 만으로 성공이라 하지 않는다(업로드 실패 사본이 남아도 `ready` 일 수 있음, `sceneNotebook.ts:750`).
   - 숨겨져 있지만 응답하는 창 = 정상 넘김으로 처리하고, 받는 창에 결과를 보이며 원래 창에는 돌아왔을 때 볼 결과를 남긴다.
   - 무응답·저장 실패·상한 초과·충돌 사본이 생김 = 정상 넘김이 아니다. 넘김을 보류하거나 "강제로 가져오기"로 처리하고 받는 창에 **"이전 창의 변경이 저장됐는지 확인 못 함"**을 보인다.
   - 응답만 잃어버림 = 같은 요청의 처리 결과를 다시 물어본다. 시간 초과를 곧바로 성공·실패로 단정하지 않는다.
   - 다른 창에는 허브 판이 오래됐음을 보이고, 다시 쓸 때는 원래 기준판으로 대조한다. 충돌 결과는 같은 요청을 반복 전송하지 않게 기록한다.
3. **계정 전환·로그아웃**: 미전송 본문뿐 아니라 기준판·요청 ID·삭제 의도도 같은 계정 공간에 보존하고, 전환 중 요청은 옛 계정으로 고정한다. 회색 표시의 `ch.*` 키는 지금 계정 바꿀 때 지워지므로, 작업물로 올리기(5단계) 전에 계정 귀속·보존 이관을 먼저 한다.
4. **사이트 데이터 지우기·프로필 교체**: 허브로 안 보낸 것은 되살릴 수 없다. 안내 문구 + 미전송 변경까지 담는 파일 내보내기를 둔다(캔버스 내보내기는 이미 미확인 변경 포함, 편집·회색·Agent 까지는 별도 단계).
5. **[되돌리기](복원) 뒤**: 복원 시작 = 새 전송을 막고 진행 중 요청을 정리 → 복원 완료 = 새 세대 발급 → 옛 세대 대기열은 지우지 않고 복구 후보로. 다른 브라우저 프로필의 대기열도 다음 접속 때 세대를 대조해 걸러진다.
6. **꺼짐→켜짐**: 바꾸자마자 전부 보내지 않는다. 계정·세대·편집권을 확인한 뒤 제한된 묶음으로 보내고, 기준판을 바꿔 끼우지 않는다(§4-1 의 3).
7. **그 밖**: 꺼짐으로 바꾸는 순간 진행 중인 요청, 숨긴 창의 타이머, 재시작 뒤 대기열 재구성을 명시한다. 무기한 로컬 대기와 요청 영수증 보관 수(`MAX_REQUEST_RECEIPTS = 2048`)의 수명을 맞춘다.

**상태 색**: 정상(초록·회색) · 주황 = 꺼짐이라 안 옮김 · **빨강 = 브라우저에도 저장 실패, 또는 상한 초과로 허브에 못 가는 문서 있음**(원칙 4).

**설정을 어디에 두나**(Codex Q3 채택): 자동 저장 간격·백업 시점·보관 양은 **같은 허브의 같은 계정 값**으로 둔다. `app_setting` 에 넣기만 해서는 안 된다(주인 칸 없음 · `CONTENT_HUB_DB` 지정이나 인증 서버 구성에서는 계정별이 아님).

| 항목 | 정한 것 |
|---|---|
| 범위 | 허브 식별자 + 계정. 다른 계정 값과 섞지 않음. PC 전체 디스크 상한이 필요하면 별도 기계 설정 |
| 읽기·쓰기 | 계정 범위를 고정한 전용 API · 허용 목록(정해진 값만) 검사 · 설정 판 번호 |
| 열린 창에 퍼지기 | 허브 알림 → 다시 읽기 · 창으로 돌아올 때·다시 연결될 때도 다시 읽기(다른 브라우저 프로필에는 `storage` 이벤트가 안 감) |
| 허브가 꺼졌을 때 | 그 허브·계정에서 마지막으로 확인한 값(꺼짐이면 꺼짐 그대로). 확인한 값이 없으면 2초를 임의로 쓰지 않고 "설정 확인 대기"로 로컬에 보존 |
| 다시 연결 | 설정을 먼저 읽고 그다음 대기열을 보냄(다른 창에서 꺼짐으로 바꿨는데 옛 '켜짐' 값으로 먼저 보내지 않게) |
| 백업 루프 | 시작 때 고정된 값을 쓰는 지금 구조를 바꿔, 실행 중 설정 변경을 반영 |

**고르는 칸의 범위(제안)**: 백업 찍는 때 = 조용히 1·5·10분 / 최소 간격 5·15·30·60분. 남기는 양 = 최근 4·8·16장 / 날마다 7·14·30일 / 주마다 4·8·12주. 자유 입력 없음.

- **1-C 공개 조건**(2차 D2 — "화면 시작 때 대조"만으로는 이미 열린 창·늦게 온 요청을 못 막는다):
  1. 모든 관련 쓰기에 세대를 붙이고 **서버가 실제 쓰기와 같은 보호 범위 안에서 검사**한다 — 본문 저장뿐 아니라 삭제·되살리기·순서·닫기 저장·편집 복원 요청까지(지금 편집 요청엔 세대가 없음, `routers/edit_docs.py:34`).
  2. 복원 중에는 새 쓰기를 막고 진행 중인 DB 작업을 비운 뒤 바꾼다 — 기존 유지보수 게이트(`db.py:425`) 재사용. 클라이언트가 요청을 취소했다고 서버 작업이 취소됐다고 가정하지 않는다. 복원 전에 보낸 요청의 응답이 늦게 와서 대기열을 "완료"로 지우지 못하게 한다.
  3. 알림을 못 받은 창·다른 프로필·옛 화면도 **서버에서** 막힌다. 세대가 없는 옛 요청에 지금 세대를 자동으로 붙이지 않는다(우회가 됨) → 새로고침 요구 또는 별도 복구 길.
  4. 캔버스의 기존 `history_id` 와 공통 복원 세대는 한 관계로 묶는다(같은 값을 쓰거나 복원 경계 안에서 함께 바꿈). 지금 복원은 `scene_restore=True` 로 공책 세대를 바꾼다(`db_transfer.py:419`, `scene_notebook.py:419`).
  5. 세대 정보가 없던 시절의 대기열도 복구 후보로 다룬다. 캔버스는 세대가 바뀐 전송 묶음을 풀고 변경을 다시 구성하므로(`sceneNotebook.ts:615`) "`history_id` 가 있으니 옛 자료를 안 보낸다"가 저절로 되지 않는다.
- 1-C 는 3단계(공통 절차) 전체를 기다리지 않는다. 다만 위 조건은 캔버스·편집 두 경로 모두에 들어가야 하므로 "3단계 뒤"라는 번호만으로는 부족하다. 0·1-A 뒤 1-B·1-C 는 서로 독립이라 순서를 바꿀 수 있다.
- 5단계는 리졸브 패널 작업(`docs/status/리졸브패널_*`)의 열린 질문 "회색을 어디에 둘까"의 답이 된다.

## 6. 바꾸지 않는 것

- SQLite + 목적별 DB 파일 구성(11-06 Claude·Codex 같은 결론). 공통 절차를 위해 물리 표·DB 를 합치지 않는다.
- 생성물 기록 소유(계정별 로컬 DB · 발행분 공유 서버)와 발행 흐름.
- 미디어 파일은 백업하지 않음(의도).
- 새 백업을 검증하고 마지막에 공개한 **뒤에** 솎는 순서 · 복원 전 보존본 생성에 실패하면 복원 중단.
- 캔버스의 기준판 비교·요청 재전송 기록·계정 전환 잠금(재사용 대상).
- [서버 백업 가져오기]의 복원 확인·복원 전 보존·재로그인 흐름(이름만 바뀜).
- NAS 완료본 이름 규칙, 코멘트 저장 위치(이미 DB).

## 8. 위험과 대비

- 허브가 꺼지거나 느리면 편집이 멈춘다 → 화면은 브라우저 사본으로 즉시, 보내기만 늦게(원칙 1). 브라우저 저장이 실패하면 빨강(원칙 4).
- 옮기다 잃는다 → 옛 자리를 지우지 않고 이관 순서(§4-4)를 따르고, 옮기기 전 파일로 받아 둔다(캔버스 `ch.scenes` 흡수 때와 같은 방식).
- 편집 문서는 조작마다 저장 → 허브 쓰기가 늘어난다 → 2초 묶음, 시험으로 쓰기 횟수 확인.
- 공용 절차가 갓 안정된 캔버스를 흔든다 → 3단계 완료 조건 ①(기존 캔버스 계약 그대로) · C안이라 표 이관 없음.
- 백업 삭제가 성한 세트를 지운다 → 완성 세트만 셈 · 지우는 중 표식 · 시계 역행이면 보류 · 방금 만든 세트·복원 직전 세트 보호 · 줄일 때 미리 보이고 확인(§4-3).
- 백업을 늘리면 디스크가 는다 → 1-A 전에 실제 세트 크기를 재고, 칸에 예상 용량을 보인다. 디스크 부족 때 보호 세트를 지우지 않는다.
- 새 구성원이 서버에 안 간다 → 읽는 쪽 먼저 · "서버에는 이 구성원 미전송"을 화면에 구분(§4-3).
- 자동 저장을 꺼 둔 채 잊는다 → 주황 상태 줄(접어도 보임) · 안 옮긴 변경 수 · 닫을 때 앱 대화상자. 꺼 둔 동안 브라우저 사이트 데이터를 지우면 안 옮긴 변경은 잃는다 — 안내 문구 + 파일 내보내기.
- 복원 뒤 옛 대기열·옛 창이 복원 결과를 덮는다 → 세대 계약(§4-1 의 2) · 서버 쓰기마다 세대 검사(1-C 조건).
- 복원 뒤 다른 구성원이 옛 것을 가리킨다(Agent 의 없는 계획, 같은 이름의 다른 폴더) → 연결 끊김·다시 연결 표시, 자동 연결·자동 재생성 금지(§4-3).
- 사용자가 고른 값이 엉뚱해 백업이 너무 적거나 많다 → 고르는 칸을 정해진 범위 목록으로만 둔다(자유 입력 없음).
