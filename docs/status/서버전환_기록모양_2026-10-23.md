# 서버 staged 전환이 '기록이 바뀌었다'로 매번 실패 — 기록 값을 디스크 모양으로 맞춘다 — 2026-10-23

owner: Claude 총괄(설계·구현) · reviewer: Codex(사전 검토·독립 리뷰, 읽기 전용) · status: 설계 중 · touched_paths: 아래 계약 · updated: 2026-10-23

## 왜

잠금 지문판(`151d0596`)을 main 에 올린 뒤 Jay 가 서버에서 `update_git.bat` 더블클릭 → 준비(prepare)는 통과했다(stage `c8c32495…`·자격 기록). supervisor 전환은 06:41(KST) 실패 → 옛 프로그램(소스 트리)으로 복귀했다. 서버 journal 끝부분(Jay 화면): `recovery_starting: true` 앞의 신원 묶음(pid 18852, 생성 06:41:01) — 정렬 순서상 `recovery_process` 로 보이며 `updated_at` 06:41:04(추정: `rolled_back`, Jay 확인 대기).

**재현(이 PC, 직접)**: 준비가 끝난 격리 사본(`151d0596`, Python 3.12.10 stage)에서 **실제 `server_supervisor.py`** 를 띄워 전환(임시 DATA·포트 18611·초당 50회 요청 부하). **2/2 같은 자리에서 실패**: `checkpointed` → `advance('activation_pending')` 가 `ValueError: journal_changed`(추적된 traceback, `install_journal.py:52`) → 옛 프로그램으로 복귀·`rolled_back`(5초). 원인: `install_db_probe.snapshot()` 이 `asdict()` 로 만든 검사 행의 `components` 가 **tuple** 인데 journal 파일에는 **list** 로 저장된다(행을 JSON 왕복하면 `components` 두 행만 달라짐 — 직접 확인). `advance()` 는 디스크 값과 호출자가 들고 있는 값이 같은지 비교하므로 다음 단계가 항상 '기록이 바뀌었다'로 멈춘다(부하와 무관). 시험은 checkpoint 를 list 행으로 가짜로 넣어 이 경로를 못 봤다. 같은 사본에 아래 1·3을 넣고 다시 돌리면 **committed**(48초, 서버가 멈춘 시간 약 31초 — 그중 약 24초는 옛 서버를 멈춘 뒤의 stage 재검사).

**앞선 추정 정정**: 처음엔 '윈도우 파일 덮어쓰기 거부(PermissionError)'를 유력 원인으로 말했으나 이번 실패의 원인이 아니다. 다만 그 현상 자체는 이 PC 에서 실측됐다(읽는 프로세스 4개 × 초당 200회일 때 덮어쓰기 200회 중 3회 `PermissionError [WinError 5]`, 초당 50회는 0회). 서버는 요청마다 활성화 제어 파일을, activated 뒤에는 journal 도 읽으므로 부하가 몰리면 같은 실패(→ 복귀)가 날 수 있다.

**서버 적용 범위**: 전환을 지휘하는 supervisor·coordinator 는 저장소 루트(`E:\MV-hub-S`)의 코드로 돌고(`server_supervisor.py` 의 ROOT 는 파일 위치), `update_git.bat` 서버 역할은 루트를 바꾸지 않는다(`run_update_git.ps1` 서버 분기는 `server_release_update.py` 만 실행 — stage 는 옆 폴더). 그래서 이 고침은 **루트에 한 번 수동 반입**해야 적용된다. 반입은 staged 자격 검사를 거치지 않고 실행 중 소스 트리 서버를 새 main 으로 바꾸는 배포다.

## 고칠 것

1. `install_journal.advance`·`new_journal`: 저장할 값을 JSON 왕복(`allow_nan=False`)으로 디스크 모양과 같게 만든 뒤 쓰고 그 값을 돌려준다. 비교(`journal_changed`)·한쪽 방향 플래그 검사는 그대로.
2. `install_journal.atomic_json`: 같은 임시 파일로 `os.replace` 만, `PermissionError` 일 때 0.05초 × 최대 40회 다시 시도. 끝내 실패하면 그 오류를 그대로 올리고 이전 파일·임시 파일 정리는 기존대로. 다른 OSError 는 즉시 실패.
3. `server_supervisor.py`: 전환 실패 줄에 `ValueError` 일 때만 코드 문자열(예: `journal_changed`)을 함께 찍는다(다른 오류 메시지는 경로가 들 수 있어 형식 이름만).
4. `server_release_update.main()`: supervisor 결과를 기다리며 journal 을 **읽고 해석하는 부분에서만** 순간 `OSError`·JSON 오류가 나면 실패로 끝내지 않고 다음 초에 다시 읽는다(지금은 전환이 계속되는데 창에는 '실패'로 끝날 수 있다). `rolled_back`·`recovery_required`·`failed` 판정은 그대로 실패.
5. 시험: tuple 이 든 advance 왕복 + 변조 감지·한쪽 방향 유지 · 전 구간 시험(`test_complete_prepare_request_and_supervisor_verified_path`)의 가짜 검사 행을 실제처럼 tuple 로 · 덮어쓰기 재시도 성공·소진 · supervisor 실패 줄 · coordinator 폴링.
6. `docs/SERVER.md`: 아래 반입 절차와 '도구 변경 경고'.

## 서버 반입 절차(이번 한 번, 관리자 PowerShell — 어느 단계든 실패하면 거기서 멈추고 보고, 재시작하지 않는다)

1. **읽기만 확인**: `logs\server-install-journal.json` 의 `phase` 가 `rolled_back` · `logs\server-update-request.json` 없음 · `logs\server-current.json` 의 `path` = 루트, `build_id` = `legacy-source`, 그리고 그 내용이 journal 의 `previous` 와 같음 · `git status` 깨끗 · 루트 `HEAD` 가 예상 기준 커밋 · `git diff --name-only HEAD <SHA>` 에서 `backend/app` 아래는 `install_journal.py` 만, `frontend/` 변경 없음, `backend/requirements.txt`·`backend/requirements.lock.txt` 는 판 변경 없음(지문만). 하나라도 다르면(특히 `failed`·`committed`) **멈추고 보고**한다 — `failed` 에서 루트를 바꾸면 재시작 때 `resume → recover` 가 바뀐 루트로 막힌다.
2. **자동 재기동을 막고 실제로 멈춘다**: `Disable-ScheduledTask` 로 'MVHub Watchdog'·'MVHub Server' 를 끄고 `Stop-ScheduledTask` → 이 루트의 `server_supervisor.py`·`server_watchdog.py` 프로세스를 트리째 종료(기존 `restart_server_task.ps1` 의 종료 규칙과 같음) → 8010 을 듣는 프로세스가 없음을 확인. supervisor 를 켜 둔 채 바꾸면 그사이 서버가 죽었을 때 supervisor 가 바뀌는 중인 루트에서 다시 띄운다.
3. `git fetch origin` → `git merge --ff-only <SHA>`(위 1의 조건대로라면 의존성 설치·프런트 빌드는 필요 없다. `frontend/` 가 바뀌었다면 1에서 이미 멈췄다).
4. ff 가 성공했을 때만 `logs\server-current.json` 을 **지우지 않고** `server-current.before-intake-<날짜>.json` 으로 이름을 바꿔 보존한다(옛 소스 지문 기록이라 그대로 두면 supervisor 가 `previous_source_changed` 로 시작을 거부한다). journal·`install-checkpoints` 는 그대로 둔다.
5. `Enable-ScheduledTask` 로 두 작업을 다시 켜고 `restart_server_task.bat`(운영 단계) → `/api/ready` 의 `runtime.build_id = legacy-source`·`admission = normal` 확인.
6. 남은 stage `c8c32495` 는 재사용하지 않는다(요청 파일은 이미 지워졌다). 그다음 `update_git.bat` 더블클릭으로 새 stage 를 준비·전환해 staged 경로를 확인한다.

**도구 변경 경고**: 서버가 stage 로 돌기 시작한 뒤에는 supervisor 가 시작할 때마다 현재 stage 자격을 루트의 검사 도구 지문(`server_activation.py`·`server_release_update.py`·`qualify_release_artifact.TOOLS`)과 대조한다. 그 뒤 이 파일들을 수동 반입으로 바꾸면 supervisor 가 `stage_qualification_tools_changed` 로 **시작하지 못하고**, 이전 stage 로의 복구도 같은 이유로 실패한다. 이번 반입은 서버가 소스 트리(legacy)로 도는 지금이라 해당 없다.
