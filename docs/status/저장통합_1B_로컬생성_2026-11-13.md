# 저장 통합 1B — 로컬 생성·소비자 준비

단계: 설계 승인·구현 대기. [기존 설계](저장통합_설계_2026-11-12.md) §4-3과 [전체 클라이언트 복원](저장통합_1B_클라이언트복원_2026-11-13.md)의 후속 P1이다. 실제 Claude 설계 `88f10563`과 Codex가 아래 최종 계약 `ef2feb95`에 동의했다. Claude는 기본v2에서도 추가 변경 감지가 켜지는 반례를 지적했고 8항·회귀 조건에 판3 한정을 반영했다. 요청 Fable5.2/high·실제 Fable5.2(실제 추론값 미확인)·도구0·종료0·제공 원문 불변을 확인했다. 카메라 계측과 무거운 시험을 겹치지 않으며 코드는 아직 바꾸지 않았다.

1. 이번 묶음은 저장1B의 로컬 생성과 소비자(P1) 준비다. 제품 생성판은2로 유지하고 새v3는 임시 가짜 자료 시험에서만 명시 선택한다. v3 적용 대상은 AUTH off·계정이 있는 로컬 허브이며 그 밖은 기존v2 범위다. 실제 서버·NAS·실DB·설치본·시스템Python·main·push는 변경하지 않는다. 능력/전송(P2), 구판 복원 후속(L), 생산 활성화(A)는 별도다.
2. backup_manifest.VERSION=2와 v2 경로의 기존 의미는 유지하고 캡처 전용 판 값(기본2)만 분리한다. 네트워크/런타임 스위치·환경변수·엔드포인트·DB스키마를 추가하지 않는다. v3가 기존 worker에 들어가면 전송 없이 거절되는 경계를 시험한다.
3. v3는 캡처한 계정·content 경로·pool epoch·ENV 키 지문으로 고정한다. 계정 전환만으로는 실패시키지 않고 모든 구성원·digest·목적지는 캡처 계정에서 선택한다. _BACKUP_LOCK 앞에서 기존 pinned_share_operation에 들어가며 대기 중 epoch가 바뀌면 스냅샷 전에 실패한다. ENV 키 원문을 기록하지 않는다.
4. 기존 content/trash B1 짝과 manage 독립 스냅샷을 유지한다. v3에서만 snapshot_database_set 구간을 share_operation_write의 활성 사용 수로 감싸 직접 연결이 닫힐 때까지 복원 배수에 잡히게 한다. 이 구간에서 Agent 연결·폴더 파일 잠금을 함께 잡지 않는다. 스냅샷 뒤 epoch를 확인하고 Agent 읽기→종료, JSON 잠금→해제, 검증, 별도 공개 구간 순서로 진행한다.
5. Agent 경로는 ENV 키 또는 content 스냅샷의 auth_secret과 순수 hub_id_for/Identity.file_path로 구한다. get_secret/db_file/open_db를 캡처 조회에 쓰지 않는다. secret없는 스냅샷은 content 촬영 시각의 absent로 기록한다. 파일 부재는 stat FileNotFoundError만 인정하며 디렉터리/권한/읽기/열기 경합은 실패다. 기존 repo.connect(readonly=True)로 배수 추적되는 SQLite 백업을 하고 기존 v3 검증기를 적용한다. 선택 계정의 DB 하나만 포함하며 profiles·CLI홈·미디어는 포함하지 않는다.
6. 폴더는 mounts_file(캡처 계정)의 파일 잠금 아래 원문 바이트를 읽고 엄격한 JSON검사를 한다. 실패를 빈 목록으로 삼키는 load는 쓰지 않는다. Agent/JSON 오류는 세트 전체 실패·기존 정상본 보존·회전 없음이며 자동v2 대체나 거짓 absent로 만들지 않는다. agent_chat_busy·agent_chat_unreadable·asset_mounts_invalid 등 이유를 기존 경고 줄에 쉬운 말로 표시한다.
7. content/trash/manage 및 Agent/JSON의 실제 독립 촬영 시각을 manifest에 남기고 INDEPENDENT의 consistency_roles는 present 집합으로 계산한다. B1 보장은 강화했다고 하지 않는다. 임시 파일의 verify_files_v3(local=True) 뒤 ENV 지문을 확인하고 별도 share_operation_write 구간에서 manifest→keep→곁 구성원→content 마지막 공개한다. 공개 구간 안에서는 DB를 열지 않는다. 그 뒤 고정 작업 종료가 성공한 경우만 회전한다. 공개 직후 복원 경합으로 호출이 실패하더라도 이미 공개된 유효 세트를 지우거나 회전하지 않는다.
8. 아래 추가 stat·Agent 경로 캐시·초기 조회는 캡처 판3의 적용 범위에서만 동작한다. 기본2에서는 기존 변경 서명과 poll 동작을 그대로 유지한다. 변경 감지는 기존 stat에 manage(+WAL)·계정 폴더JSON·Agent(+WAL)를 더한다. Agent 경로 캐시의 키는 캡처 DB 경로/고정 epoch/ENV 지문이며 backup 모듈에만 둔다. 시작/복원 뒤 캐시가 없으면 poll 스레드에서 pinned_share_operation+share_operation_write 안의 raw mode=ro SELECT로 초기화한다. get_connection의 복구/초기화 경로는 쓰지 않는다. 유지보수 중·hot journal·읽기/epoch 오류는 미캐시 후 재시도한다. 스냅샷에서 secret을 읽은 직후 캐시를 갱신하며 이후 캡처 실패에도 변경 대기 상태를 유지한다. secret 생성은 content/WAL stat이 다음 캡처를 예약하고 새 Agent 파일 생성도 감지한다.
9. 로컬v3 파일 이름은 agent_chat_<stamp>.db·asset_mounts_<stamp>.json이며 absent는 파일이 없다. read_local·완성/목록/최신/용량·디스크 여유·구성원/잔재·삭제 재개·회전·로컬 NAS 복제·복원 훈련이 같은 present 집합과 검증을 사용한다. v2 훈련의3DB 기준은 유지하고 v3는 present에따라 검사/사본 해시 대조한다. keep 곁파일 규칙·원본이 있는 NAS 파일 보호·미완성 세트 보호는 유지한다. 임시 NAS만 시험하며 실제 NAS에는 쓰지 않는다.
10. Agent 대화/payload에는 임의 내용이 있으므로 비밀값 전체 부재를 보장하지 않는다. 지정 DB만 포함·전용 자격 inline저장 없음·profiles/CLI홈 제외만 검증한다. P1에는 혼합판의 마지막v3 특별보호 정책을 새로 넣지 않는다. 실제 활성화 전 구판rollback으로v2가 다시 생성될 때의 보관 보호를 A 결정사항으로 남긴다. 관련 합성 경계/기존v2 회귀·화면 경고/빌드·지도/색인 및 별도 실제Claude 독립 리뷰 뒤 dev에만 커밋한다. P1 완료는 새생산 활성화/전체1B 완료가 아니다.
