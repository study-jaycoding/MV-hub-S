# 저장 통합 1B — 전체 클라이언트 복원

[진행 인계](Codex인계_진행중작업_2026-11-12.md), [기존 저장 설계](저장통합_설계_2026-11-12.md) §3·4-3, [완료된 서버 소비자 준비](저장통합_1B_서버수신_2026-11-13.md)를 잇는다. 목표는 content·trash·Agent 기록·폴더 등록을 함께 복원하고, 기록 열람과 안전한 작업 재개까지 연결하는 것이다. 연결 차단 도우미 하나의 완성을 전체 복원 완료로 보지 않는다. 새 생산·송신 활성화, 실제 서버·DB·설치본·NAS 조작, main·push는 포함하지 않는다.

## 현재 코드에서 확인한 경계

기준 dev `92c8840b`. 기존 다른 작업의 추적 변경 14개를 보존했다. 이 조사는 제품·실사용 데이터 변경이나 실행 시험이 아니다.

1. `routers/db_transfer.py`의 ZIP 해제는 content/trash만 받고 v3를 거절한다. `_install_db`는 전환 잠금→content 유지보수→보존본→같은 볼륨 준비→검증→교체→보안 초기화/로그아웃→실패 보상 복구 흐름이다. 이 흐름을 모든 복원 구성원으로 확장해야 한다.
2. 총괄 직접 대조: `services/auth.py:hub_id`는 보안 키와 content 경로의 HMAC이다. `_post_install_security_init`은 보안 키를 회전한다. 복원 전 허브 이름으로만 Agent 파일을 설치하면 재로그인 후 다른 이름의 파일을 볼 수 있다. 환경변수 키가 고정된 경우는 경로가 같을 수 있어 두 경우를 나눠야 한다.
3. Codex 조사: `_RestoreTarget`은 Agent 신원/경로·폴더 JSON 경로를 캡처하지 않는다. `CONTENT_HUB_DB`를 직접 지정했을 때 폴더 JSON은 content 옆이 아닐 수 있다. `Identity.file_path()`는 조회만 하지만 `db_file()`은 파일을 만들므로 목적지 확인에 쓰지 않는다.
4. Codex 조사: 서버 복원 두 입구는 `_proxy.proxying()`이 필요하여 AUTH on에서는 진입하지 않는다. 단일 DB import는 AUTH on에서도 가능하며, 이때 요청 인증 계정은 `request.state.account`다. 기존 `_RestoreTarget.email=""`을 Agent 계정으로 사용하면 안 된다. `mcp_v2._capture`에는 복구 쓰기/원격 확인이 섞여 있어 단순 경로 캡처용 호출은 부적합하다. AUTH on의 실제 폴더 소비 경로도 계정 폴더가 아닌 DATA_DIR이다.
5. Codex 조사: `resumable=False`는 대화 이어하기/기존 포크만 막고 `/plans/{id}/execute`는 막지 않는다. 옛 MCP 자격으로 접근하는 read_context/add_to_canvas도 별도 경계다. 대화 삭제는 외부 CLI 세션 파일을 지울 수 있어, 복원된 외부 실행 식별자와 경로를 자동 재사용하면 안 된다. 계획 연결은 조회용으로 보존하되 실행 권한으로 인정하지 않아야 한다.
6. Codex 조사: 기존 새 대화는 새 CLI·새 MCP client를 사용하지만, 기록 전체를 문맥으로 넘기는 기능은 없다. 기존 포크는 원래 CLI 세션을 resume하므로 복원 기록의 안전한 재개와 같지 않다. 원본을 열람용으로 유지하고 사용자가 검토한 과거 글만 새 대화의 참고자료로 넘기는 안을 비교한다. 실제 생성/CLI 실행 승인을 과거 기록에서 가져오지 않는다.
7. Codex 조사: 폴더 원문은 name/path/owner만 허용한다. 수동 경로 실패 뒤 동명 PM/설치 폴더로 넘어가는 fallback, locate의 직접 경로 탐색, 목적지 전송 작업자의 직접 load가 있어 한 함수만 차단하면 우회된다. 조회 중 옛 owner 이관도 JSON을 쓴다. 별도 계정 확인 표식을 쓰는 안은 이 경로와 원문 보존을 함께 다뤄야 한다.
8. 총괄·Codex 대조: content 유지보수는 DB 연결 문맥을 기다릴 뿐, 이미 해석한 외부 파일 경로의 쓰기 전체를 기다리지 않는다. 목적지 작업자는 DB 조회 뒤 파일 link/rename을 하고, 일부 import/정리도 별도 파일 확정/삭제를 한다. 계정 pin·종료 때 epoch 검사는 이미 일어난 파일 변경을 되돌리지 못한다. 기존 `share_operation_write` 재사용 또는 별도 접수/배수 범위를 결정해야 한다. 이미 반환한 FileResponse의 읽기와 외부 파일 쓰기는 구분한다.

조사 담당: `handoff_decisions_reconcile`(복원 입구·목적지), `priority_db_design_review`(Agent 참조·안전한 재개), `restore_mounts_explorer`(폴더 사용·진행 중 파일 작업). 모두 읽기 전용 책임으로 조사했으며 제품 시험을 실행한 결과가 아니다.

## 합의 전에 고정할 사항

- 보안 키 회전 이후 Agent 목적지, 이전/최종 경로의 차단·보존·원상복구, 고정 환경 키, 계정/설정 변경 거절.
- v3의 명시적 absent와 구판에 역할이 없는 경우를 구분. PC 공용 manage는 계속 복원하지 않는다. 구판 복원 후 기존 Agent 기록의 가시성도 검토한다.
- runtime/발급 진행 중에는 복원을 거절하고 epoch/cache를 바꾸지 않는 기존 Claude 제안. 그 밖에는 최초 요청 세대 고정·실제 연결 종료 배수·늦은 요청의503·실패 정리 쓰기 금지. 발급은 취소돼도 실제 작업 종료까지 보호한다.
- 검증한 원문과 준비 파일의 동일성, 신뢰된 보안 정제/스키마 초기화의 시점, 세 번째/네 번째 교체·초기화·로그아웃 실패 시 전체 보상 복구.
- 복원 대화의 열람·누락 참조 표시·실행 차단 및 명시 확인 뒤 새 자격으로 작업 재개. 외부 CLI 이어하기와 기록 조회를 같은 승인으로 묶지 않는다.
- 폴더 확인 표식의 손상/재시작/계정 전환·옛 확인 요청 처리, 동명이경로 fallback/직접 소비 차단, 진행 중 파일 변경과 복원의 순서.
- 위 조건을 포함한 가짜 자료의 HTTP 전체 복원→재로그인→기록/폴더 확인→작업 재개 시험. Windows 파일 종료/교체·시간 초과·늦은 요청·구판 호환·실패 원상복구를 별도로 확인한다.

아직 구현 계약 합의·제품 구현·실행 검증·독립 리뷰 완료가 아니다. 실제 Claude에 새 경계를 전달해 검토 중이다. 도구 없는 고정 소스 입력으로 요청했고, 호출 종료 후 실제 모델·원문 지문 불변을 확인한다.

## 후속 대조와 선택

- 실제 Claude의 두 후속 응답을 회수했다. 요청 `mvhub-design`·Fable5.2/high, 실제 모델 `claude-fable-5-2`, 실제 추론 수준 미확인이다. 도구0·고정 원문 검토이며 입력9파일과8파일의 전후 SHA256 불변을 각각 확인했다. CLI 종료0이다.
- Claude는 기존 대화 재활성/옛 CLI 참조 보관 열을 제안했다가 Codex 반례에 따라 철회했다. 원본은 실행 잠금을 유지하고, 기존 기록 조회의 허용 목록으로 사용자/AI 글만 가져와 새 대화에 참고자료로 넣는 안에 동의했다. 일괄 '확인 안 됨' 표시도 철회하고, 없는 계획·생성물과 확인하지 못한 자료를 구분하기로 했다.
- Claude는 복원 JSON의 이름만 차단하는 안을 철회했다. JSON에 없는 이름·absent 조합도 동명 경로로 잘못 이어질 수 있으므로 기본 미확인으로 두고 확인한 이름/정규 경로 쌍만 허용한다. 별도 sidecar 대신 content DB의 계정별 app_setting 값을 사용하면 같은 복원 거래·롤백 안에 들어가고 원문 JSON도 보존할 수 있다.
- 총괄은 '확인 종료'로 차단 값을 삭제하는 추가 기능을 채택하지 않는다. 확인하지 않은 이름을 한꺼번에 허용하면 원래 경로 확인 요구를 약화한다. 확인 상태는 유지하고 새 수동 등록도 현재 복원 세대를 명시한 사용자 행동으로 확인한다. PM 자동 폴더도 처음 사용할 때 경로 확인이 필요할 수 있다는 동작은 문구로 알린다.
- content DB 전체의 소유 이메일을 입증하는 필수 내부 표식은 현재 생성·정제 경로에 없다(Codex 소스 조사). shared_server_email은 전송 때 제거되고 provider_email은 CLI 계정이며, my_creator_uid도 이메일 증명이 아니다. 존재하지 않는 표식을 새 필수 조건으로 만들지 않고 외곽 digest와 접수 계정을 대조한다. 향후 생산 단계의 계정/Agent 선택 검증을 이를 대신 완료한 것으로 보지 않는다.
- 임시 파일을 이용한 총괄 진단(`e6026e`, 종료0): pinned_share_operation은 복원 세대가 바뀐 뒤 파일을 쓴 경우 종료 때 실패했고 파일은 이미 존재했다. 같은 고정 세대에서 share_operation_write를 파일 쓰기 직전에 사용하면 파일 생성 전에 거절했다. DB 연결·서버·실제 Assets 입구는 실행하지 않은 도우미 경계 진단이며, 임시 폴더는 정상 정리됐다. 실제 각 호출부의 통합 시험은 아래 계약 조건이다.

## 전체 복원 계약안

<!-- restore-contract:begin -->
1. 기존 서버 복원 두 HTTP 입구에서 전체 v3를 받는다. 지원 대상은 AUTH off·활성 계정·공유 서버 연결이 있는 로컬 허브이며 현재 입구 경계를 넓히지 않는다. 단일 파일 import와 v1/v2 해제의 의미는 유지한다. VERSION=2·생산/송신 활성화 금지도 유지한다.
2. 다운로드·ZIP 목록/중복/고정 이름·manifest64KiB·구성원별/전체 크기·엄격 JSON·정확 present 집합·원문 해시·SQLite/폴더 구조·B1 짝·계정 digest를 검증한다. 외곽 digest는 접수 email의 slug와 일치해야 한다. 내부의 선택적 신원 필드를 계정 전체 소유 증명으로 삼지 않는다. 미지원/손상 v3에서 옛 단일 파일로 조용히 내려가지 않는다.
3. 접수 때 content 경로·환경/계정 쌍·옛 Agent Identity/경로·mounts 경로를 고정한다. 순수 hub 계산을 auth와 복원이 재사용한다. 새 DB secret를 미리 만들고 환경 키 우선 규칙을 적용해 최종 Agent 경로를 계산하며, 환경·신원·경로가 달라졌으면 교체 전에 거절한다. 비밀값은 기록/응답에 내보내지 않는다.
4. Agent runtime 또는 발급 작업이 있으면409로 거절하고 세대·gate·_opened를 바꾸지 않는다. 없으면 서비스 잠금 아래 옛/최종 대상의 접수를 닫고 세대를 변경한다. 실제 연결 종료를 잠금 밖에서 기다린 다음 transition→content maintenance→필요한 JSON 파일 잠금 순으로 들어간다. 연결 count는 SQLite 열기 전부터 close 성공까지다. 기한 초과/close 실패면 교체하지 않는다. 실제 gate를 닫았던 경우에만 _opened를 무효화하고 푼다.
5. HTTP Agent와 MCP 기록 조회는 최초 신원/세대를 ContextVar로 고정하고, plain Thread에는 그 값을 명시 전달한다. 늦은 읽기·claim·start·예외 정리는 새 DB로 쓰지 않고503이다. 발급→대화 생성/포크→커밋 판정→실패 회수는 기존 non-abandon 도우미의 단일 작업 스레드에서 보호하며 취소 후에도 실제 종료까지 발급 수를 유지한다. 초기 busy409에는 아무 상태 변경이 없다.
6. 교체 대상의 원래 존재 여부와 보존본을 먼저 확보한다. Agent 경로가 새로 생기면 옛 파일을 보존하고, 동일 경로면 별도 보존본을 만든다. 각 대상 볼륨의 준비 파일에 다시 원문 검증을 수행하고 그 파일을 교체한다. 이후 신뢰된 스키마/보안 초기화와 Agent 채택은 별도 명시된 변경이며 복구 경계 안이다. 어느 교체/초기화/계정 해제 단계가 실패해도 content·trash·Agent·JSON·활성 포인터의 원래 상태를 되돌린다. 복구 실패를 성공으로 숨기지 않고 보존본을 남긴다. PC manage는 교체하지 않는다.
7. v3 absent는 최종 대상의 부재를 복원하되 기존 파일은 먼저 보존한다. v1/v2에 새 역할이 없는 경우와 다르다. 구판 복원은 기존 Agent/JSON 바이트를 유지하며 hub 회전에 따른 기존 Agent 가시성 문제는 별도 열린 후속으로 기록한다.
8. v3 보안 초기화에서 복원 content의 MCP 자격을 명시 회수한다. Agent 채택은 restored_from·resumable=0을 기록하고 외부 CLI 실행/삭제에 사용되는 식별자·경로를 비운다. 원문 사건과 plan_binding은 읽기용으로 유지한다. 실행·견적·포크·이어하기·외부 세션 삭제는 서버가 거절한다. 새 대화는 새 자격/CLI로 가능하다. 정상 대화의 기존 기능은 유지한다.
