# 배포 후보 — 확정마다 모든 씬을 다시 해싱하던 것 (2026-11-15)

## 무엇을 찾았나

배포 후보 넓은 실측(격리 S 화면, 헤드리스, 5회) 결과, 캔버스 휠 확대·축소·판 이동마다 **입력 반응은 1ms 미만**인데 손을 뗀 지 약 0.5초 뒤 50~100ms 긴 작업이 1~2개씩 났다(휠 축소 5회 모두, 화면 간격 최대 150ms). CPU 기록의 상위 함수는 번들의 `Gf` = `frontend/src/lib/editShare.ts` 의 JS SHA-256(`sha256Js`)이다.

- 시점: 카메라 기록 묶기(유휴 500ms 뒤 확정)와 같다.
- 경로: `sceneBackup.ts` `initSceneBackup` 의 확정 구독 → 공책 기능이 없는 허브면 `advanceMirrorProvenance(ns(), knownText)` → 이전·지금 글자 합집합의 **모든 씬**마다 `sha256Js(이전 글자)` 를 계산하고, 기준 지문이 맞으면 `sha256Js(지금 글자)` 를 또 계산한다. 카메라만 바뀐 확정도, 바뀌지 않은 씬도 전부 다시 해싱한다.
- 어디서 타나: 공책 기능(`scene_writer_v1`)이 없는 허브 — 로그인 모드인 공유 서버 화면을 브라우저로 직접 열 때(`backend/app/services/scene_writer.py` `enabled()` = `not AUTH_ENABLED`), 현장 스위치 `CONTENT_HUB_SCENE_WRITER=0` 인 로컬 허브. 팀원이 평소 쓰는 공책 허브(로컬 허브 기본 켬)는 이 길을 타지 않는다.

## 고침

`advanceMirrorProvenance` 의 결과를 바꾸지 않고 계산만 줄인다.

1. 이전 글자와 지금 글자가 같은 씬은 건너뛴다 — 기준 지문이 맞으면 같은 값을 다시 쓰고, 안 맞으면 그대로 두므로 계산해도 `raws` 가 바뀌지 않는다.
2. 직전에 계산한 (글자, 지문)을 씬마다 하나 기억해, 다음 확정의 '이전 글자'가 그 글자면 다시 해싱하지 않는다(같은 글자면 같은 지문). 범위(계정)가 바뀌면 비운다.

카메라만 바뀐 확정이면 바뀐 씬 하나의 지금 글자만 한 번 해싱한다(전: 모든 씬 × 2).
