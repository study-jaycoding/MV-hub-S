## 4. 결정

### D1. 배달부 = **저장 때 깨우기 + 5초 안전망**, 최근 창을 끝까지 다시 훑는다

**깨우기(v0.4 새로, Jay 결정)**
- 선례 그대로: `PeriodicShareStateReconciler`(확인 `services/share_state_reconciler.py:927-975`) — `kick()` 은 `loop.call_soon_threadsafe(event.set)` 만 하고, 작업 고리는 `wait_for(event.wait(), timeout=5초)` 뒤 `clear()` → 한 바퀴. 동기 라우트(threadpool)에서 불러도 안전.
- 코멘트가 서버 DB 에 들어가는 곳은 **세 곳**(확인): `repo/assets.py:449` 새 코멘트 INSERT, `repo/share.py:647` 번들 INSERT OR IGNORE, `repo/trash.py:704` 휴지통 복원 `_insert_row`. (v0.4 의 "두 곳뿐"은 틀렸다 — 내 grep 이 `INSERT INTO generation_comment` 글자만 찾아 `_insert_row(conn, "generation_comment", …)` 를 놓쳤고, Codex 3차가 짚어 다시 확인했다.)
- **즉시 깨우는 것은 정상 새 작성·번들 발행 두 길**:
  1. `routers/generation.py:1221` 공개 코멘트 저장(`repo.add_generation_comment`) **성공 반환 뒤** — 저장 함수가 스스로 COMMIT 한 뒤 반환한다(Codex 확인 `repo/assets.py:460`). 비공개 길(`:1194`)·서버로 넘기는 길(`:1209`)은 깨우지 않는다(넘겨받은 서버가 자기 자리에서 깨운다).
  2. `routers/publish.py:350` 번들 받기(`repo.import_bundle_payload`) **반환 뒤** — 명령 처리기 길(`usecases/share.py:69`, `publish.py:339-350`)도 이 안에서 돈다(확인).
- **안전망(5초)이 잡는 것**: 휴지통 복원(옛 시각 보존이라 보통 floor·30분 창 밖), 번들 부분 성공(항목별로 확정하므로 뒤 항목 실패로 예외가 나도 앞 항목 코멘트는 저장됨 — Codex 확인 `repo/share.py:860-865`), 깨우기를 놓친 경우.
- 깨우기는 **선례의 저수준 `kick()` 만** 쓴다 — 바깥 `kick_share_state_reconciler()` 는 DB 세대 검사를 먼저 하므로 그대로 따라 하지 않는다(확인 `share_state_reconciler.py:952,981`). 보내기만 하고 기다리지 않는다. 예외는 삼키고 기록만(코멘트 저장 응답을 절대 바꾸지 않음). DB 를 건드리지 않는다. 배달부가 안 도는 곳(로컬 허브·토큰 없음)에서는 loop 가 없어 아무 일도 안 한다(선례 `kick` 의 `loop is None` 검사).
- 한 바퀴 도는 중 여러 번 깨워도 한 바퀴만 더 돈다(Event 하나). 깨우기를 놓쳐도(저장 직후 서버 종료 등) 5초 안전망이 잡는다.
- 이 변경이 코멘트 저장 코드에 들어가는 것은 **두 자리에 한 줄씩**뿐이다(휴지통 복원 길은 건드리지 않는다).

**한 바퀴(Codex 2차 [P1] 500행 누락 반영)**
- 후보 = `is_private=0 AND julianday(created_at)` 이 아래 조건을 모두 만족하는 줄. SQLite `julianday` 는 `YYYY-MM-DD HH:MM:SS`·`T` 구분·소수 초·`Z`/`±HH:MM` 을 모두 읽고, 못 읽으면 NULL → 제외(추정 — SQLite 문서 기준, 구현 첫 단계에서 서버 사본의 실제 형식 분포를 세어 NULL 이 되는 형식이 있으면 파이썬 해석으로 보완).
  - `julianday(floor) <= jd <= julianday('now','+2 minutes')`
  - `jd >= julianday('now','-30 minutes')`
- `(jd, id)` 순서로 **500개씩 끝까지 넘긴다**(keyset: 다음 쪽 = `(jd, id) > (마지막 jd, 마지막 id)`). "최신 500개만 다시 보기"는 하지 않는다. rowid 는 쓰지 않는다(삭제·VACUUM 재배치, 확인 `schema.sql:535`).
- 비용: 색인이 없어 바퀴마다 표 전체를 훑는다(추정 — 코멘트 수만 줄이면 수 ms). 구현 때 서버 사본 크기로 실측. 느리면 그때 색인을 검토하되 **이름표·옛 검사기 영향부터 확인**(D4).
- 그다음 받을 사람 계산(D2) → `slack_dm_outbox` 에 `INSERT OR IGNORE`(UNIQUE(comment_id, recipient_email)). 같은 코멘트를 여러 번 훑어도 중복 줄은 안 생긴다.

**floor(이 시각 전 코멘트는 안 보냄)** = `app_setting.slack_notify_floor`
- 처음 켤 때 = 그 순간. **DB 세대가 바뀌었을 때(`_install_db` 로 복원·교체·이사)** = 그 순간(D3 세대 검사와 함께).
- 토큰을 **다른 Slack 팀**으로 바꾸면 = 그 순간. **같은 팀 토큰 교체는 floor 유지**(밀린 최근 알림은 이어서 보냄 — J7 추천안).
- 관리 창 [다시 켜기](일시 멈춤 뒤) = 그 순간 + 미발송 줄 모두 닫기(`resumed`). 단순 파일 복사 복원 절차는 "멈춤 → 복원 → 다시 켜기"(D3).

**남는 한계**: 배달부가 30분 넘게 멈추면 그동안 코멘트는 Slack 으로 안 간다(알림 종엔 남음, J5). 시각 없는 옛 번들 코멘트는 들어올 때 now 가 붙어 새 알림처럼 갈 수 있다(확인 `share.py:647`, J6 — 실제 대상은 D2 로 걸러짐).

### D2. 받을 사람 = 알림 종 규칙, **받는 사람 계정으로** 다시 계산 (v0.3 그대로 — 2차 해소)
- 후보 ID: 생성물 `creator_uid`, 부모 코멘트 `author`(확인 `_common.py:55-58`). 작성자 본인 제외. 빈 값·`me`·모호한 uid 는 **제외**.
- ID → 계정: `user_…` 는 `account.creator_uid` 로, `acct:<email>` 은 `account.email` 로 찾되 **지금 account 행이 있고 `status='approved'`**.
- uid가 plain email인 옛 행은 알림 종과 같이 대상이 아니다(제외). 2차 리뷰 후 총괄 결정 (a)에 따라 B7의 이메일 직접 조회와 그 시험을 제거했다. approved 조건과 발송 직전 재확인은 유지한다.
- 볼 수 있는지: 그 계정의 `actor_uid`, `read_all`(그 계정 global_role), `my_member_projects(actor_uid)` 로 `ALERT_COMMENT_TARGET_PREDICATE` + `alert_comment_visibility_clause` 를 그 사람 기준으로. 요청 문맥은 쓰지 않는다.
- **같은 함수**를 대기열 넣을 때와 보내기 직전에 쓴다. `muted` 는 옛 칸이라 무시.

### D3. 대기열·선점·**보내기 시작 기록**·정산 (Codex 2차 [P1] lease·5xx·복원 반영)

**줄의 상태**: `대기` → (선점) → `보내는 중`(`send_started_at` 기록·커밋) → `보냄` / `닫힘(사유)`, 그리고 `인증 대기`. **한 번 `보내는 중`이 된 줄은 다시 `대기`로 돌아가지 않는다** — 예외는 **"처리되지 않았음이 확실한" 응답 셋뿐**: 연결 전 실패 · 429 · 토큰 오류(아래). 그 셋만 `send_started_at` 을 지운다.

- 선점: `lease_token/lease_until`(선례 `asset_destination_outbox`, 확인 `services/asset_destination.py:96-104`). **`send_started_at` 이 있는 줄은 lease 가 끝나도 다른 배달부가 집지 않는다** — 선례와 다른 점(선례는 만료 작업을 다시 집음, Codex 확인 `:98`).
- 보내기 직전: D2 다시 확인 + 연결 유효(D6 team_id 일치) + 코멘트 아직 있음·비공개 아님·생성물 안 지워짐 + **줄의 `db_generation` = 지금 DB 세대**. 아니면 닫음.
- 보내기 시작: `send_started_at = now`, `token_revision` 을 **먼저 커밋**한 뒤 HTTP. lease 시간(60초) > HTTP 제한 시간(10초) → 살아 있는 배달부는 lease 안에 끝낸다.
- 결과:
  - `ok:true` → `sent_at`.
  - **연결 전 실패**(DNS 실패·연결 거절 — 요청을 보내기 전임이 확실한 것)만 → `send_started_at` 지우고 백오프 `min(3600, 60·n²)`.
  - **1차 리뷰 후 정정(2026-11-05)**: urllib은 연결/전송 시간 초과를 구분하지 못하므로 **연결 시간 초과는 `unknown`으로 닫음(중복 방지 쪽)**.
  - 429 → Slack 이 처리하지 않았다고 알려 준 것 → `send_started_at` 지우고 `Retry-After` 뒤.
  - **HTTP 5xx·응답 대기 중 시간 초과·연결 끊김 = 결과 불명** → `unknown` 으로 닫고 다시 보내지 않는다(J4).
  - 영구 오류(`user_not_found`·`channel_not_found`·`account_inactive`·`is_bot`…) → 닫음(지우지 않음).
  - **토큰 오류**(Slack 이 `ok:false` + `invalid_auth`·`token_revoked`·`not_authed` 로 답함 = 메시지가 만들어지지 않음, 추정 — Slack 문서 기준, 구현 때 확인) → `send_started_at` 을 지우고 **`인증 대기`**(그 호출에 쓴 토큰 revision 기록). 그 revision 은 멈추고, **같은 팀 새 revision 이 등록되면 `인증 대기` 줄은 `대기`로 돌아가 이어서 보낸다**(J7). 다른 팀 revision 이면 `team_changed` 로 닫는다. `인증 대기` 도 아래 15분 stale 시계(대기열에 넣은 때부터)를 따른다 — 15분 안에 토큰을 고치면 이어서 가고, 넘으면 `stale`(J9). (Codex 3차 [P1]: v0.4 대로면 시작 표시가 남아 lease 만료 뒤 `unknown` 으로 닫혀 새 토큰으로도 못 보냈다.)
- **되살리기(서버 재시작 때·바퀴마다)**: `send_started_at` 이 있고 결과가 없으며 lease 가 끝난 줄 → `unknown` 으로 닫는다(다시 보내지 않음).
- **오래된 줄**: 대기열에 넣은 지 **15분** 넘은 `대기`·`인증 대기` 줄 → `stale` 로 닫는다(v0.3 의 1시간에서 줄임 — 백오프 재시도는 사실상 3번까지, J9).
- **DB 세대**: 줄마다 넣을 때의 영속 DB 세대값(`share_db_generation`, Codex 확인 — `_install_db` 가 바꾼다 `routers/db_transfer.py:170`)을 적는다. `db.pool_epoch()`(프로세스 안 값)는 쓰지 않는다. 세대가 다른 미발송 줄은 `db_changed` 로 닫고, floor = 지금.
- **단순 파일 복사 복원**(서버를 끄고 DB 파일을 덮어쓰는 경우)은 세대값이 같이 되돌아가 알아챌 수 없다 → 복원 절차에 "Slack 멈춤 → 복원 → [다시 켜기]" 한 줄을 넣는다(다시 켜기 = floor 지금 + 미발송 닫기). 절차를 안 지키면 최근 30분 안 코멘트 알림이 한 번 더 갈 수 있다 → J8.
- 정산은 그 줄의 `lease_token` 이 그대로이고 같은 DB 세대일 때만. 네트워크 왕복은 DB 잠금 밖.

### D7. 열기 = 사람이 누른 것만, 창 하나만, 실제로 열렸을 때만 성공 (Codex 2차 [P1] 반영)

**받는 조건**
- 허브 `GET /api/open/generation/{gen_id}?c={comment_id}` — `_LOCAL_PREFIXES`. `for` 는 **뺀다**(`acct:` 는 uid 전환 때 바뀌고 이메일이 들어 있음). 대신 "지금 로그인한 계정이 그 코멘트를 볼 수 있나"로 판단(아래).
- 검사는 **두 층으로 나눈다**(Codex 3차 [P1]):
  1. **보안 검사 — 실패하면 바로 거절**(403·고정 문구, 단추 없음): 접속 주소(client) 루프백 + `Host` = `127.0.0.1:<허브 포트>` + prefetch 아님(`Sec-Purpose`/`Purpose: prefetch` 거절) + 전역 제한(2초에 1번).
  2. **사람이 누른 것인지 — 부족하면 단추 페이지**: 최상위 탐색(`Sec-Fetch-Mode: navigate`·`Sec-Fetch-Dest: document`) + `Sec-Fetch-User: ?1`. 보안 검사를 통과한 정상 로컬 요청에서 **이것만 부족할 때만** 바로 열지 않고 고정 안내 페이지의 [MV hub에서 열기] 단추를 준다.
- **로컬 처리기 셋 모두(단추 POST · `/api/open/claim` · `/api/open/ack`) 가 각자 직접** 보안 검사(루프백 client + Host) + 같은 출처(`Origin` = 허브 주소, `Sec-Fetch-Site: same-origin`)를 한다. 기본 미들웨어의 원격 차단은 설정으로 꺼질 수 있어 그것에만 기대지 않는다(Codex 확인 `main.py:1044`, `config.py:131`).
- Slack 앱이 기본 브라우저로 링크를 넘길 때 `Sec-Fetch-User` 가 붙는지는 (추정·P2 실측) — 안 붙으면 늘 단추 한 번을 더 누르게 된다.

**창 하나만 맡기**
- 허브: `ws.broadcast({type:"open_generation", gen_id, comment_id, open_id})`(AUTH off 소켓 = 이 허브의 모든 창, 확인 `ws.py:188-196`).
- 프런트 메인 창(`?embed` 아님, 숨김·최소화 포함)은 **Web Locks(`navigator.locks`) 로 창 안 대표를 하나** 둔다 — 대표가 닫히면 잠금이 다음 창으로 자동으로 넘어간다(죽은 대표 교체). 대표만 처리.
- 대표는 `POST /api/open/claim {open_id, window_id}`(허브 로컬) → 허브가 **처음 신청 하나만 승인**(허브 프로세스 안 원자적 사전), 나머지는 409. 브라우저 프로필이 둘이라 대표가 둘이어도 한 창만 연다.

**코멘트 확인 → 열기 → 결과**
- 대표 창: 그 생성물 코멘트 목록을 직접 불러와(서버 권한 그대로 — `require_view_generation`, 확인 `generation.py:1168`) **그 `comment_id` 가 그 생성물에 있고 지금 계정에 보이는지** 확인 → 있으면 `openComment(gen_id)` + 그 코멘트 읽음 처리(확인 `NotificationCenter.tsx:325`) → `POST /api/open/ack {open_id, window_id, ok:true}`.
- 목록 불러오기 실패·코멘트 없음·안 보임 → 열지 않고 `ack ok:false, reason`. 지금 패널은 조회 오류를 삼키므로(Codex 확인 `GenCommentPanel.tsx:47-59`) **열기 처리는 패널과 따로 결과를 받아** 판정한다.
- `/api/open/claim`·`/api/open/ack` 는 `_LOCAL_PREFIXES`(허브 로컬). 허브는 ack 를 **대기 중 open_id + 승인한 window_id + 열기 시작 때 계정**이 모두 같을 때만 받는다.
- 허브는 최대 3초 기다려 문구를 고른다: "MV hub 에서 열었어요(이 탭은 닫아도 돼요)" / "열지 못했어요 — 이 계정에서 볼 수 없는 코멘트예요" / "MV hub 창이 꺼져 있거나 응답이 없어요".
- 로컬에 없는 생성물은 현재 계정의 서버 권한으로 조회됨(확인 `library.py:1136-1142`).
- 창 앞으로: (추정·**P2 실측으로 결정**) 후보 = 허브가 메인 창 HWND 를 복원(SW_RESTORE) + TOPMOST→NOTOPMOST → 못 하면 작업표시줄 깜빡임 + 탭 문구. 지금 `raise_over_foreground` 는 맨 앞이 앱 창일 때만(Codex 확인 `app_windows.py:25,54`).
- 링크 포트: 관리자 설정 `open_base_url`(기본 `http://127.0.0.1:8010`, 확인 `MV_agent.bat:29`). 포트를 바꾼 PC 는 v1 한계.

## 11. 구현 조건 (Codex 3차 — 합의 판단과 분리, 구현·리뷰 때 지킬 것)

- **깨우기**: 저수준 `kick()` 만 재사용(바깥 함수의 DB 세대 검사 안 따라 함). 예외까지 삼켜 저장 응답 보존.
- **최근 창 조회**: 한 바퀴 안에서 floor·현재 시각·DB 세대를 고정. 쪽마다 표 전체를 다시 읽을 수 있으니 **여러 쪽 + 연속 깨우기를 포함한 전체 비용**을 실측. 기존 `created_at` 색인은 `julianday(created_at)` 정렬용이 아니다(Codex 확인 `schema.sql:546`). DB 작업은 이벤트 루프 밖에서, 긴 쓰기 잠금 없이.
- **보내기 시작**: 시작 기록은 유효한 lease 소유자만 원자적으로 확정. 10초 제한은 각 네트워크 단계가 아니라 **HTTP 작업 전체**에. 시작된 줄은 다른 배달부가 다시 보내지 않는다.
- **대기 코드**: 계정 생성 시각은 초 단위(Codex 확인 `schema.sql:220`) — 그것 하나로 재가입을 가른다고 가정하지 말고 재생성 때 반드시 달라지는 값을 실제로 고른다.
- **열기**: 목록 조회 뒤 계정이 바뀌면 패널 표시·읽음 요청도 멈춘다(ack 거절만으로는 늦음). 대표 창이 닫히는 순간의 요청은 다시 넘기거나 분명한 실패로.
- **Slack 출구**: 검사한 user id 와 실제 보내는 목적지가 같아야 한다. DM 채널을 쓰는 호출은 **검증된 user ↔ 채널 대응**으로만(따로 받은 user id 만 보고 다른 채널로 보내는 꼴 금지).
- **정제**: 사본을 만드는 모든 호출자에서 실패가 전파되는지 확인. 기존 Comfy 정제 변경은 섞지 않는다.
- 줄 상태(`인증 대기` 등)를 칸 하나로 둘지 기존 칸 조합으로 둘지는 구현 때 정한다.
- **인증 대기 해제**(Codex 4차): 토큰 등록 순간의 처리에만 기대지 않는다. 새 revision 등록 직후 옛 요청의 토큰 오류가 늦게 도착해도, **다음 바퀴에서 현재 revision·team 과 대조해 재개**할 수 있어야 한다(D3 재개 계약의 시험 항목).

### 3. 결정(안)

#### S1. 링크
- `mvhub://open/<gen_id>?c=<comment_id>` — 포트·주소를 링크에 넣지 않는다. gen_id·comment_id = 기존 `_ID`(`^[A-Za-z0-9_.:-]{1,200}$`, 확인 `open_generation.py`) · 링크 전체 ≤ 512자 · scheme 소문자 `mvhub`, host `open`, path 세그먼트 1개, query 는 `c` 하나만(중복·다른 키·fragment 거절).
- Slack 메시지는 글자 링크 하나(시안 v4 모양, 주소만 바뀜).

#### S2. 처리기 = **별도 파일 `open_link.py`(설치 루트)** — 런처와 분리 (Codex P1 인자 주입)
- `run_agent_session.py` 의 argparse·여러 실행 모드(`--close-app-window` 등, 확인 `:1213-1245`)를 **거치지 않는다**. 표준 라이브러리만, 경로는 `Path(__file__)` 기준(`-I` 는 스크립트 폴더를 import 경로에서 뺀다 — 필요한 것은 이 파일 안에 둔다).
- 시작하자마자: argv 가 정확히 `[스크립트, "--port", <1–65535 숫자>, <링크>]` 가 아니면 아무것도 하지 않고 끝(안내 창도 없음). 포트는 등록 명령에 고정돼 `%1` 앞에 있어 링크가 바꿀 수 없고, 링크가 인자를 늘리면 개수에서 거절된다 · 링크가 `mvhub:` 로 시작하지 않거나 엄격 파싱 실패면 끝. 링크 글자를 셸·명령·다른 프로세스 인자로 넘기지 않는다.
- 시험: 등록 명령 문자열에 `%1` 자리를 악성 링크(`"` · `\"` · `%22` · ` --close-app-window` · 줄바꿈 · 탭 · 512자 초과)로 바꾼 명령줄을 **`CommandLineToArgvW` 로 실제 분리**해 argv 개수·값을 확인 — 깨끗한 한 경우만 받아들인다.

#### S3. 연결 파일(비밀값) — **설치·포트마다 하나, 그 포트를 잡은 허브만 쓴다** (Codex P1 비밀값 · 2차 P1 단일 작성자)
- 위치 `%LOCALAPPDATA%\MVHub\open-link\<install_id>-<port>.json` — `install_id` = 런처와 같은 식(`sha1(str(root).casefold())[:10]`, 확인 `run_agent_session.py:287-290`; 허브는 `BACKEND_DIR.parent` 를 root 로 — 두 계산이 같은지 시험). 설치·포트마다 따로라 같은 설치의 8013·8472 허브가 서로 덮지 않는다(2차 지적: mutex 는 `MVHub_Launcher_<port>_<install_id>` 라 설치 단위가 아니다, 확인 `:806`).
- **비밀값은 파일로만 오가고 네트워크로는 절대 보내지 않는다** (Codex 3~6차 P1 의 뿌리: `serve.py:74` 가 `SO_REUSEADDR=1` 이라 Windows 에서 여러 프로세스가 같은 포트를 들을 수 있고, 듣기 표·잠금·PID 대조는 "확인과 연결 사이" 틈과 PID 재사용을 닫지 못한다).
  - v0.4~0.6 의 mutex·듣기 표·PID 대조는 **뺀다**. 소켓 옵션·서버 시작 동작은 **바꾸지 않는다**(배타 바인드는 TIME_WAIT 동안 재시작 바인드 실패 위험으로 채택 안 함 — 추정, Microsoft 소켓 문서).
  - 대신 **양방향 HMAC 증명**(S5): 처리기는 요청마다 새 nonce·시각과 HMAC 서명만 보내고, 허브는 결과와 함께 같은 nonce 에 대한 HMAC 증명을 돌려준다. 비밀값을 모르는 수신자는 ① 처리기 요청에서 비밀값을 얻지 못하고(서명은 그 한 요청에만 유효) ② 증명을 만들지 못해 처리기가 결과를 믿지 않는다(창도 올리지 않는다).
  - **여러 허브가 같은 파일을 쓰면**(같은 설치·같은 포트를 손으로 두 번 띄운 이상 상황) 마지막에 쓴 허브의 비밀값만 맞는다 → 요청이 다른 허브로 가면 서명 검사에서 거절되고, 처리기는 증명을 못 받아 "MV hub 를 다시 켜 주세요" — **잘못 열기·비밀값 유출 없이 실패만**. 원자 교체(임시 파일 → `os.replace`)·쓰고 다시 읽기는 유지.
  - 범위: **명시적으로 켠 로컬 허브만** — `MVHUB_OPEN_LINK=1` 이고 AUTH off 일 때만 게시·native. 실사용 런처(MV_agent → `run_agent_session.py` 일반 실행, 등록과 짝)가 허브 자식 환경에만 넣는다.
  - **시험 격리(Codex 5차 P1)**: 부모 환경에서 물려받지 않게 — `tools/browser_measure/servers.py` 의 `isolated_base_env`(:68-72)·`backend/tests/conftest.py`(:47) 의 환경 정리에 `MVHUB_OPEN_LINK`·`MVHUB_REGISTER_LINK` 를 **명시적으로 지운다**(dev_hub 의 `hub_env` 도 `isolated_base_env` 를 거친다). 이 기능의 자동 시험은 임시 `LOCALAPPDATA` 를 지정하고서만 켠다. 부모에 두 값이 이미 있을 때도 실제 `%LOCALAPPDATA%` 에 아무것도 안 생기는지 시험.
  - 게시 시점: `serve.py` 경로(소켓 바인드·listen → Uvicorn 실행, Codex 확인 `serve.py:124`)에서 **바인드 뒤**. 직접 `uvicorn.run()` 경로(`app/main.py:1530`)는 게시하지 않는다. lifespan 안에 넣지 않는다(직접 `uvicorn.run()` 경로 `app/main.py:1530` 은 lifespan 이 바인드보다 먼저 — 그 경로는 **게시하지 않는다** = 전용 링크 미지원). dev_hub(`import serve`)도 serve.py 경로라 같은 규칙.
- **어느 허브로 갈지 = 등록 명령의 포트**(S7: 실사용 런처가 자기 포트로 등록). "마지막에 쓴 파일" 을 고르지 않는다.
- 허브 시작 때마다 새 비밀값 `secrets.token_urlsafe(32)`(43자 ASCII) → 같은 폴더 임시 파일에 쓰고 `os.replace` 로 원자 교체 → 다시 읽어 같은지 확인 → 메모리에 보관. 처리기는 읽기만.
- 내용 `{port, key, install_root, written_at}` — 처리기는 port 가 인자와 같고 install_root 가 자기 루트와 같은지 확인(다르면 "MV hub 를 다시 켜 주세요"). 상대 프로세스의 신원은 PID 가 아니라 **HMAC 증명**으로 확인한다(PID 재사용 무관). 실행 중 파일이 지워지거나 깨지면 처리기는 "MV hub 를 다시 켜 주세요" 안내(허브는 다음 시작 때 다시 쓴다). 허브는 고장 난 파일을 고치지 않는다(쓰는 순간을 시작 한 번으로 고정).
- 권한: 사용자 `LOCALAPPDATA` 상속(그 사용자·SYSTEM·Administrators) — **구현 때 `icacls` 로 실제 확인**(가정 금지).
- 비밀값은 응답·로그·오류 문구·네트워크 어디에도 넣지 않는다(파일과 두 프로세스 메모리에만).

#### S4. 처리기 → 허브 요청 (Codex P1 프록시·리다이렉트)
- 목적지 고정 `http://127.0.0.1:<port>` (port 는 연결 파일의 정수 1–65535). `urllib.request.build_opener(ProxyHandler({}), _NoRedirect)` — 선례 `tools/server_console/server_api.py:225`. 3xx 는 실패로 끝(따라가지 않음).
- 전체 시간 예산 8초(허브 쪽: 계정 조회 + 방송 + ack 대기 3초 + 창 찾기). 시간 초과 뒤 **자동 다시 보내기 없음**.
- 시험: 환경 `HTTP_PROXY`·가짜 프록시를 켜도 루프백으로 직접 가는지, 302 응답에 비밀값을 실은 채 따라가지 않는지.

#### S5. 허브 — 공통 열기 코어 + native (Codex P2 응답·시간)
- `_open()` 을 **코어(구조화 결과)** 와 **포장**으로 나눈다: 코어 결과 = `opened`(hwnd 목록 포함) · `denied`(코멘트 없음·볼 수 없음·계정 바뀜) · `no_window`(3초 안에 ack 없음) · `busy`(전역 2초 제한) · `unsupported`(서버 모드). HTTP GET/POST 는 지금처럼 HTML, native 는 JSON.
- `POST /api/open/native`: `/api/open/` 는 이미 `_LOCAL_PREFIXES`(확인 `_proxy.py:585`) → 서버로 중계 안 함. 검사 = `require_loopback_request` + Host(`127.0.0.1:<PORT>`·`localhost:<PORT>`) + **요청 서명**. 브라우저용 검사(Sec-Fetch·Origin)는 쓰지 않는다 — **보안 근거는 비밀값을 아는지의 증명**(허브 CORS 는 5173 출처에 모든 헤더를 허용하므로 CORS 로 막힌다고 보지 않는다, Codex 확인 `config.py:59`·`main.py:786-789`).
- **양방향 HMAC(SHA-256) 형식**(비밀값 = 연결 파일의 43자 문자열을 UTF-8 바이트로):
  - 요청 헤더 `X-MVHub-Open-Time`(유닉스 ms, 정수) · `X-MVHub-Open-Nonce`(`secrets.token_urlsafe(24)`, 32자) · `X-MVHub-Open-Sig` = hex(HMAC(key, `"mvhub-open-req\n{time}\n{nonce}\n{port}\n{generation_id}\n{comment_id}"`)). 본문은 `{generation_id, comment_id}` JSON(서명에 같은 값이 들어간다 — 바꾸면 서명 불일치).
  - 허브 검사 순서: ① 헤더·본문 형식(길이·문자·타입 — time 은 13자리 이하 십진 정수, nonce 32자 `[A-Za-z0-9_-]`, sig 64자 소문자 hex, generation_id·comment_id 는 `_ID`) ② 시각이 허브 시계 **±10초** 안(처리기와 허브는 같은 PC 시계를 쓴다) 그리고 이 비밀값을 만든 시각 이후 ③ 서명 `hmac.compare_digest` ④ **서명이 맞으면 같은 이벤트 루프에서 await 없이 nonce 중복 검사와 등록을 한 번에**(이미 있으면 401) — 열기 코어의 첫 대기보다 먼저. 하나라도 틀리면 401 고정 문구(어느 것이 틀렸는지 말하지 않음) — 열기를 하지 않는다.
  - **nonce 보관 = 이 비밀값의 수명 내내**(허브가 다음에 시작해 새 비밀값을 만들 때까지) — 시간이 지나도·용량 때문에도 **지우지 않는다**(Codex 7차 P1: 유효한 nonce 를 지우면 같은 요청이 다시 통과). 한 번 클릭 = 1개라 하루 수천 개도 수십 KB(추정). 상한 20,000개에 닿으면 새 요청을 실행하지 않고 거절(`busy`, "MV hub 를 다시 켜 주세요") — 다시 켜면 새 비밀값이라 옛 서명은 모두 무효.
  - 서명이 맞은 요청은 결과(`opened`·`busy`·`denied`·`no_window`)와 상관없이 그 nonce 를 **소비**한다(다시 보내도 401).
  - 응답 JSON `{result, hwnd, proof}` · `proof` = hex(HMAC(key, `"mvhub-open-res\n{nonce}\n{result}\n{hwnd}"`)). 처리기는 proof 가 맞을 때만 result·hwnd 를 믿고, 틀리거나 없으면 "MV hub 를 다시 켜 주세요"(창도 올리지 않음).
  - 다시 보내기(replay): 가로챈 요청은 nonce 집합(비밀값 수명 내내 보관)에서 막힌다. 시스템 시계가 되돌아가도 nonce 는 시각과 무관하게 남아 있어 재사용되지 않는다. 응답 위조: proof 를 못 만든다 — 처리기는 **이번 요청에서 만든 nonce 와 읽은 키로만** proof 를 검증하고, 검증 전에는 result·hwnd 로 아무것도 하지 않는다. hwnd 는 JSON 정수(bool 아님)만, result 는 정해진 5개 문자열만.
  - 같은 포트의 다른 수신자가 요청을 거절하거나 다른 곳으로 넘기는 것은 **가용성** 문제로 남는다(그때도 처리기는 위조 결과를 받아들이지 않는다).
- 나머지 경로·시험·허브 결과 5종은 그대로.
- 서버(AUTH on)에서는 열기를 **절대 하지 않는다**(인증 미들웨어 401 이든 경로 404 든 결과만 고정 — 시험으로).

#### S6. 연 창 = 올릴 창 (Codex P1 대상 창 · 2차 P1 ack 수명 · 2차 P2 0/복수·표식 경합)
- **ack 는 기다림 없이 먼저 확정**: 검사가 통과하면 같은 이벤트 루프 안에서(await 없이) `accepted=True`·`ok`·`marker` 를 기록하고 `accepted` 이벤트를 깨운다. 이미 accepted 인 요청에 오는 ack 는 409(중복 차단).
- **그다음 창 찾기**(별도 기한): marker 제목의 최상위 창 검색(`raise_marked` 의 찾기 부분, 최대 0.6초) → 결과(hwnd 목록)를 기록하고 `found` 이벤트를 깨운 뒤 답한다(창은 답을 받은 뒤 제목을 돌려놓는다 — 찾기가 답보다 먼저라 제목 경합 없음). 지금처럼 TOPMOST→NOTOPMOST 들어 올리기도 여기서.
- **기다리는 쪽(`_open` 코어)의 두 기한**: ① ack 도착 ≤ 3초(지금과 같음 — 없으면 `no_window`) ② ack 를 받았으면 창 찾기 ≤ 1초 더. 요청 항목은 코어가 끝날 때만 지운다 — 찾는 도중 지워지지 않는다.
- 창 찾기가 예외·시간 초과로 끝나도 `found` 는 **반드시** 깨운다(finally). 코어가 이미 끝난 뒤 도착한 늦은 찾기 결과는 요청을 다시 바꾸지 않는다(항목이 없거나 끝남 표시면 버림). HTTP 응답과 창의 제목 복원 순서는 지금 그대로.
- **열기 성공은 창 찾기와 무관**: ack `ok` 면 결과는 `opened`(+ `hwnd` 0개면 `focus: unavailable`). HTTP 열기도 같다 — 창 찾기 실패가 이미 성공한 열기를 실패로 바꾸지 않는다.
- **hwnd 규칙**: marker 는 창마다 새 UUID 라 정상이면 1개. 0개 → 처리기는 Win32 호출을 하지 않는다(안내도 없음 — 코멘트는 열렸다). 2개 이상(이상 상황) → 첫 것도 고르지 않고 0개처럼 다룬다(깜빡일 대상도 없음).
- 처리기는 그 HWND 를 **다시 확인**: `IsWindow` · 이 설치의 승인 표식 Window Property `MVHubAppWindow_<install_id>`(확인 `run_agent_session.py:562-609`). 표식은 런처 watcher 가 제목을 본 뒤 붙이므로(시작 직후 0.7초 대기, 확인 `:599-605`·`:899`) **최대 1.5초 동안 0.1초 간격으로 다시 본다** — 끝까지 없으면 올리지 않는다(다른 창으로 대신하지 않음). 둘 다 맞으면 `ShowWindow(SW_RESTORE)`(최소화일 때) → `SetForegroundWindow`, 반환값과 `GetForegroundWindow() == hwnd` 로 성공 판정, 실패면 그 hwnd 에 `FlashWindowEx`.
- (추정) Slack(앞 창)이 띄운 처리기라 앞으로 가져오기가 허용될 수 있다 — 조건을 만족해도 거절될 수 있다(Microsoft 문서). **실측으로 결정**, 실패하면 깜빡임으로 끝(허브 쪽 TOPMOST→NOTOPMOST 들어 올리기는 그대로 둔다).

- 웹페이지가 허브 native 를 직접 부르는 것은 서명(비밀값을 알아야 만든다)으로 막는다. 비밀값은 네트워크로 오가지 않아 같은 포트에 끼어든 수신자도 얻지 못한다. 같은 사용자 권한으로 연결 파일을 읽을 수 있는 로컬 프로그램은 막지 못한다(이미 그 사용자 권한 — 받아들임).

#### S11. 섞여 도는 동안·켜는 순서 (Codex P2 혼합 버전)
- 새 링크를 여는 것은 **open_link.py + 등록 + native 를 가진 앱을 한 번 실행한 PC** 뿐. 그 전 판(이 브랜치의 http 판 포함 — 아직 배포 안 됨)은 못 연다.
- 켜는 순서(기존 §5 에 추가): 서버 업데이트 → 앱 릴리스가 팀에 퍼짐(**각자 한 번 실행 = 등록**) → 관리자가 토큰 등록. 이 순서를 지키는 동안 J10(예비 http 링크 없음)의 전환 기간 위험 = "새 앱을 아직 한 번도 안 켠 사람은 Windows '앱 필요' 창"뿐.

#### S11-b. 구현 조건 모음(합의 판단과 분리, 구현·리뷰 때 지킬 것)
- **연결 파일은 종료 때 지우지 않는다**(Codex 7차 P1: "읽고 내 키인지 확인 → 지움" 은 그사이 다른 허브가 교체한 파일을 지울 수 있다). 다음 시작이 원자 교체로 덮는다. 허브가 꺼진 동안 남은 파일 → 처리기는 연결 거절을 받아 "MV hub 가 꺼져 있어요" 안내(비밀값은 보내지 않으니 남은 파일이 위험하지 않다). 소켓은 정상 종료·바인드 실패·lifespan 실패에서 지금처럼 정리.
- 처리기의 8초는 개별 소켓 호출이 아니라 **전체 작업 기한**(monotonic). 응답 본문 ≤ 4KB, 연결 파일 ≤ 4KB.
- HMAC 메시지는 정해진 구분자·순서·UTF-8 로만 만들고(위 S5 문자열 그대로, 형식 검사를 통과한 값만 넣는다), 서명·증명 비교는 `hmac.compare_digest`. nonce 집합 규칙은 S5(지우지 않음·상한에서 거절).
- 시험 추가: 정상 서명 요청의 동시 재전송(하나만 실행) · 상한 근처에서 첫 요청 재전송 · 시각 경계(±10초 안팎·비밀값 생성 이전) · result 와 hwnd 각각 변조 · 다른 nonce 의 응답 · bool hwnd · 허브 A 종료 중 B 의 파일 교체(파일이 지워지지 않음).
- 창 찾기가 늦게 끝나도 끝난 요청을 바꾸거나 뒤늦게 다른 창을 올리지 않는다.
- `opened` 와 초점 이동 실패를 분리 · hwnd 0·복수·승인 표식 없음에서 대체 창 선택 금지.
- 배포본의 실제 `pythonw -I -S` 실행 · 새 설치·업데이트·롤백 · 기존 HTTP 열기와 제목 복원 동작을 검증.
- 설치 루트 계산(런처 `_install_id` ↔ 허브 `BACKEND_DIR.parent`)이 같은지 시험.
- (Codex 8차) 상한 경계에서 기존 nonce 를 지우거나 캐시를 초기화하지 않고 새 요청은 코어 실행 없이 거절 · 정상 서명에 대한 `busy` 응답에도 proof 를 붙인다 · nonce 집합 초기화는 **새 비밀값 생성과 함께만**(설정 조회·오류 복구에서 같은 키로 비우지 않음) · 응답은 검증 전 HWND 동작에 쓰지 않는다.
