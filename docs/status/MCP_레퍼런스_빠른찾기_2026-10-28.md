## 지금 왜 느린가 (10-28 실측·코드 확인)

- MCP에 그림을 넘길 도구가 없다. 대화에 붙인 그림은 허브에서 이름으로 다시 찾아야 한다.
- `read_context(kind='references', asset_project=…)`는 **파일 이름에 한 낱말이 들어 있는지**만 보고, 최대 50개에서 끊으며 다음 쪽이 없다(`backend/app/routers/mcp_v2.py` `_issue_references`). 실제로 "매튜" 검색이 50개에서 잘려 필요한 파일이 안 보였다.
- 후보 그림을 볼 수 없다. 이번에는 NAS를 직접 열어 썸네일을 만들어 맞췄다 — 걸린 시간 대부분.
- NAS 훑기는 원인이 아니다: `Z:\PROJECT_MUDX\10_ai\assets` 폴더 72·파일 1,178개를 0.1초에 훑었다.
- 대화에 붙인 그림은 원본을 줄여 다시 저장한 사본이다(붙인 것 2000×1116 JPEG·WEBP ↔ 원본 5504×3072). sha256이 달라 **에셋 대장 번호·파일 지문으로는 원본을 못 찾는다.** dev `data_test`의 대장은 0건(훑기 안 함). 공유 서버 대장 상태는 미확인.
- Claude 데스크톱은 대화에 붙인 그림을 `%TEMP%\claude\<프로젝트 키>\<세션 ID>\images\<번호>.<확장자>`에 둔다(여러 세션 폴더에서 같은 형태 확인).

### 원본 대조 실측 (뻘뻘뻘 에셋 그림 572장, 원본에서 256px로 줄여 계산)

- **거르기 없이 전체 비교**(칸 평균 = 차이 그림을 16×9로 BOX 축소, 572장 전부): 붙인 매튜 1등 1.0(정답)·2등 94.0, 붙인 조개언덕 1등 1.0(정답)·2등 103.0. 차이 계산만 572회 61ms. 원본에서 줄이는 데 68.3초(4개 동시, 썸네일 캐시 없이). 모양 지문(dHash)으로 후보를 거르면 대비가 약한 닮은 그림을 놓칠 수 있다(Codex 3차 반례: dHash 64인데 칸 차이 2.0) → 거르지 않는다.

## 설계

### 1. 가져와 바로 쓰기 — 새 MCP 도구 `import_reference`

- **입력**: `file_path`, `workspace_scope`·`workspace_id`, 선택 `asset_project`(원본 대조), 선택 `project_id`(앱 가져오기와 같은 동기화 대상), 선택 `label`(저장 이름).
- **읽어도 되는 파일(LLM 입력과 독립)**: 어댑터는 **지금 대화의 첨부 폴더 하나**만 읽는다 = 자기 프로세스 환경 변수 `CLAUDE_CODE_SESSION_ID`(호스트가 넣는 값, 도구 인자 아님)로 정한 `%TEMP%\claude\<한 단계>\<그 세션 ID>\images\` 바로 안의 그림 파일. 세션 ID가 없거나 UUID 형식이 아니거나 그 폴더가 정확히 하나가 아니면 가져오기를 거부하고 앱 가져오기를 안내한다. 다른 프로젝트·다른 세션·이전 세션의 첨부는 허용하지 않는다. `file_path` 자체를 승인 근거로 삼지 않는다. 그 밖의 경로·UNC·장치 경로(`\\?\`·`\\.\`)·ADS(드라이브 뒤 `:`)·경로 중간의 심볼릭 링크·정션 등 재분석 지점은 거부한다. 파일을 연 뒤 연 파일이 검사한 파일과 같은지(파일 번호·크기) 확인한다. 바깥 파일은 대화에 붙이거나 앱 에셋 탭으로 imp/cap에 넣는다(MCP가 임의 경로를 읽지 않는다).
- **그림만**: PNG·JPEG·WEBP, 확장자와 머리 바이트가 둘 다 맞아야 한다. 최대 64MiB. GIF·영상·소리는 이번 범위 밖(앱 가져오기 사용). 여러 프레임 WEBP(애니메이션)는 가져오되 원본 대조를 하지 않고 사본으로 둔다.
- **보내기**: 어댑터는 파일을 통째로 메모리에 올리지 않고 원시 바이트를 흘려 보내며, 실제 보낸 바이트도 상한으로 자른다. 메타데이터는 쿼리 인자.
- **허브 창구**: 새 `POST /api/mcp/v2/client/references/import`. 기존 loopback·브라우저 차단·`X-MVHub-MCP` 헤더·연결 비밀·계정 검증은 그대로 쓰되 **JSON 64KiB 본문 검사와 분리한 업로드용 검사**를 둔다(`backend/app/routers/mcp.py`). 이 경로를 `upload_limits.UPLOAD_REQUEST_LIMITS`에 등록해 파싱 전 원시 본문 상한을 건다. 기존 JSON 64KiB 제한은 그대로다. 허브도 머리 바이트·확장자·크기를 다시 검사한다(어댑터를 거치지 않은 직접 호출 대비).
- **저장**: 앱 끌어놓기와 같은 `imports` 저장(`_commit_import_and_sync` — 같은 내용은 지문으로 재사용), 앱 가져오기와 같은 계정·공유 연결 고정 범위(`capture_local_operation`·`pinned_share_operation`).
- **핸들 발급**: 파일 확정과 트리 무효화 뒤 `_asset_tree`로 합본 파일 노드를 조회한다. `source` = `kind="asset"`, `project="imp/cap"`, `path="imports/<실제 저장명>"`, 발급 워크스페이스. `version` = 그 노드 값. 참조 경로 = `asset:imp/cap|imports/<실제 저장명>`. 기존 권한·판 검사(`_references`)를 우회하지 않는다.
- **권한 재검사**: `project_id`가 있으면 현재 연결·선택 공간에서 접근 가능한 프로젝트인지 파일 확정 **전에** 검증한다. 오래 걸린 대조 뒤, 파일 확정과 핸들 발급 전에 연결·계정·공간 권한을 다시 검사한다. 동기화 예약 실패(`sync_state`)는 로컬 저장 성공과 구분해 돌려준다.
- **응답**: `{reference:{id,name,type,path,project}, stored:"original"|"copy", reused, match:{attempted, complete, linked, candidates:[{id,name,path,cell_diff}]}, sync_state}`. 받은 `reference.id`를 기존 `prepare_generation_plan.items[].reference_ids`에 그대로 넣는다. 생성 경로는 바꾸지 않는다.

### 2. 원본 자동 연결 (보수적)

- `asset_project`가 있고 한 프레임 그림이면 저장 **전에** 그 프로젝트 에셋 그림과 대조한다. 대조 범위 = 그 프로젝트 트리의 그림 노드 전부.
- **트리 완전성**: 트리 읽기 결과에 노드·깊이 상한 도달, 폴더·파일 조회 실패 여부를 함께 전달한다(`backend/app/services/asset_tree.py`). 완전성 정보는 해당 트리와 같은 스캔 결과·캐시 세대에 묶어 저장하고 반환한다 — 동시 요청 사이에 공유되는 '마지막 스캔 상태'로 전달하지 않는다. 의도적으로 빼는 폴더(숨김·opaque·render 등 기존 정책)와 탐색 실패를 구분한다. 잘림·실패가 있으면 자동 연결하지 않는다. 기존 트리 호출자의 반환 형식은 바꾸지 않는다.
- **비교**: 거르지 않고 범위 안 **모든** 한 프레임 그림과 비교한다. 양쪽을 원본 썸네일(256px, `thumbs.ensure_thumb`) 기준으로 가로 192×세로 108로 맞추고, 차이 그림을 16×9 칸 평균으로 줄인 뒤 R·G·B 채널 값 중 가장 큰 값 = `cell_diff`. 모양 지문(dHash) 같은 거르기·메모리 기억은 쓰지 않는다(Codex 3차: 거르면 대비가 약한 닮은 그림을 놓친다). 썸네일 디스크 캐시가 다음 호출을 빠르게 한다.
- **자동 연결 조건(모두 만족)**: ① 트리 완전·범위 안 모든 그림 비교 완료·읽기 실패 0 ② 1등 `cell_diff` ≤ 2.5이고 1등과 붙인 그림의 가로세로 비율 차이 2% 이하 ③ 범위 안 그림이 1장이거나 2등 `cell_diff` ≥ 4.0 (**10-29 재합의로 대체** — 아래 「10-29 연결 기준 재합의안」, 정본은 계약). 하나라도 어기면(시간 초과·누락·읽기 실패·트리 잘림·동률·닮은 그림) 원본으로 단정하지 않고 **사본 핸들 + `match.complete`/`linked=false` + `cell_diff`가 가장 작은 후보 최대 5장**을 돌려준다.
- 응답과 도구 설명은 이것을 "가장 닮은 원본"이라고 부르고, 같은 원본이라는 증명으로 표시하지 않는다.
- **실행 상한**: 트리 조회와 썸네일·차이 계산을 하나의 대조 작업으로 묶어 프로세스 전체 작업자 2개 안에서만 돌린다. 대조 슬롯은 1개이고 **실제 작업이 끝날 때까지** 잡고 있는다 — 15초 응답 한도가 지나 응답을 먼저 돌려줘도 슬롯은 그대로이며, 그동안 들어온 요청은 기다리지 않고 바로 사본 경로(`match.attempted=false`, 사유 `busy`)로 간다. 대기열을 두지 않는다. 15초는 트리 조회·락 대기를 포함한다. 한도를 넘으면 새 썸네일 작업을 제출하지 않는다. 비교 전후로 원본 파일 판(mtime_ns-크기)이 트리 노드 판과 다르면 그 그림은 읽기 실패로 센다. 작업 스레드에서도 연결 계정 고정 범위를 유지한다.
- 에셋 대장 DB·스키마는 쓰지 않는다(실측: 지문이 달라 못 찾고, dev 대장은 비어 있음).

### 3. 검색 보강

- 에셋 자료 검색(`asset_project`가 있을 때): 이름이 아니라 **경로 전체**(폴더 포함)에서 공백으로 나눈 낱말이 **모두** 들어 있는 것(대소문자 무시). 한 낱말 검색은 기존 이름 일치 항목을 제외하지 않는다(경로 일치가 더해져 첫 쪽 구성은 달라질 수 있음).
- 결과 순서 = 트리 순서(폴더 먼저·이름순, `build_tree`). `offset`은 걸러낸 뒤 적용한다. 응답은 기존 `references` 배열을 유지하고 각 항목에 `path`, 응답에 `next_offset`(더 없으면 `null`)을 더한다. `offset`은 0~100,000, 범위 밖·`asset_project` 없는 `offset`은 422. 쪽 사이에 트리가 바뀌면 빠지거나 겹칠 수 있다(한계로 기록).

### 호환·배포

- 허브 기능 표시에 `reference_import`(가져오기)와 `reference_search`(검색 확장)를 따로 더한다. 어댑터는 `offset`을 지정했을 때만 보내고 그때만 `reference_search`를 요구한다. 옛 허브에는 새 인자를 보내지 않고, 새 기능이 필요한 호출만 `hub_outdated`로 거부한다. 기존 도구·인자는 그대로 동작한다.
- 새 도구는 영속 연결에만 등록한다. 도구 수: native 15 · conversation 14 · 구형 연결 7(`tool_count`와 실제 목록 일치).
- 허브 코드가 바뀌므로 앱 업데이트(릴리스)가 필요하다. MCP 독립 업데이트(server.py만)로는 부족하다.
