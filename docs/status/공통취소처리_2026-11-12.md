# 공통 스레드 작업의 반복 취소 처리

## 요청과 현재 단계

- 사용자 요청: 인계된 열린 작업을 모두 진행하고 필요하면 병렬로 나눠 통합한다. 커밋은 dev만, main 병합·push는 사용자 담당이다.
- 출발점: [인계 §3-1](Codex인계_진행중작업_2026-11-12.md#3-1-to_thread_non_abandon--취소가-반복되면-헛돌며-다른-작업을-굶김).
- 단계: 재현·설계 중. 담당·범위·완료 조건의 정본은 아래 계약이다.
- 기준: dev `18d09bd7049791469c9fd8f4b1ede77eb2f712de`. 기존 다른 작업자의 미커밋 변경은 보존한다.
- Codex 총괄이 조사·구현하고 Claude `mvhub-design`으로 설계 검토, 다른 Claude `mvhub-review` 세션으로 독립 검토한다. Claude 요청 모델은 현재 설정의 `claude-opus-5-5`, 추론 high이며 실제 실행값은 응답 후 기록한다. 최초 설계 1회와 쟁점 재검토 1회, 최초 독립 리뷰 1회와 수정 재검토 1회를 기준으로 한다. 새 근거가 필요하면 범위부터 다시 확인한다.
- 공유 서버·실사용 DB·앱 프로세스에는 접근하거나 쓰지 않는다. 격리 시험과 소스 변경만 수행한다.

## 확인한 근거

- `async_tools.py`는 반복 취소를 억제하며 `asyncio.shield(worker)`를 다시 기다린다. 격리 재현(Python 3.14.3 / AnyIO 4.13.0)에서 0.1초 대기 중 shield 진입 3,748회와 프로세스 CPU 0.094초를 관측했다. 다른 태스크가 완전히 멈추지는 않았으므로 기존 보고를 '항상 멈춤'으로 확대하지 않는다. 재현한 문제는 의미 없는 반복 취소 대기로 인한 CPU 소모다.
- `agent_chat.py`의 fork 경로는 AnyIO shield를 별도로 두었다. 공통 함수의 호출자는 백업·DB 전송·파일 등록·생성 요청·동기화 등에도 있다. 이 작업에서는 호출자의 정책을 일괄 변경하지 않는다.
- 기존 시험은 정상 결과·예외, 1회 취소, 간격을 둔 asyncio 반복 취소를 확인한다. AnyIO 지속 취소와 다른 태스크의 진행 여부는 확인하지 않는다.

## 검증과 남은 일

- 재현: 단일 스레드와 AnyIO 취소 범위만 사용, 앱/DB import 없이 수행했다. 위 반복 대기와 CPU 사용을 확인했다. 제품 파일 수정 전이다.
- 설계 검토: Claude 실제 모델 `claude-opus-5-5`, 세션 `3be1b72c-f462-45d1-9273-0db356e2c118`, 도구 Read/Grep만 사용, 제품 수정·시험 없음. 계약에 동의했고 취소 뒤 구간만 AnyIO shield, 직접 asyncio 취소용 반복 대기 유지, 원래 취소 재전파, worker 예외 명시 회수를 요구했다.
- Codex 확인: 설치된 AnyIO 4.13.0의 `CancelScope.__enter__`가 부모 범위의 태스크 집합에서 제외하고 `_deliver_cancellation`이 보호된 자식 범위를 건너뛰며 `is_anyio_cancellation`이 취소 메시지를 판별한다. 별도 메모리 내 후보로 기존 asyncio 시험 3개 통과. [AnyIO 공식 취소 안내](https://anyio.readthedocs.io/en/stable/cancellation.html)의 반복 취소·정리 중 보호 설명도 대조했다(현재 문서는 4.16, 로컬 소스는 4.13).
- 회귀 시험을 먼저 추가해 원본의 반복 대기 2,560회/0.1초를 실패로 확인했다(출력 `59592f`). 수정 후 해당 시험은 통과했다.
- 새 예외 검증의 첫 버전은 이벤트 루프 오류가 전혀 없어야 한다고 가정했으나 Python 3.14.3의 `asyncio.tasks._log_on_exception`은 `fut.exception()`으로 회수한 뒤에도 `RuntimeError exception in shielded future`를 의도적으로 보고한다. 이 표준 라이브러리 동작은 원본/수정본 모두 관측됐다. 시험은 정확히 이 메시지와 시험이 만든 동일 예외만 허용하고 미회수 예외·다른 오류는 계속 거절한다. 제품에서 오류 보고를 숨기지는 않는다.
- 구현은 취소 뒤 AnyIO 보호, 기존 asyncio 보호 대기 유지, worker 예외 회수의 최소 변경이다.
- 시험: 전용 6개 + 하위 사례 2개 통과(0.84초), 기존 백업·보관·계정 고정·파일 등록 149개 통과(15.23초). 원본 함수를 메모리에서 주입하면 새 반복 취소 시험이 실패하고 수정 함수를 주입하면 통과함도 확인했다. 실제 파일은 되돌리지 않았다.
- 독립 리뷰 요청: 새 Claude `mvhub-review` 세션, Fable/high(공통 운영의 동시성 중요 리뷰 기준). 요청 전 대상 지문 `1e295164e9fd122510a8c6f74c75631f86b7563bc1cb327c7a307283e2e836d9`. 실제 모델과 판정은 응답 후 기록한다.
- 첫 독립 리뷰 세션 `7c520cde-1b2b-4731-917b-5c5712d39a31`은 실제 `claude-fable-5-2`로 읽기만 수행했으나 `autocompact_thrashing` / `rapid_refill_breaker`로 종료 코드 1, 판정 없이 중단됐다. 통과 근거로 쓰지 않는다. 새 세션 `532c9e40-bc68-4d98-aa01-4b6229f73a89`에 정책·계약·두 대상 파일 전체와 SHA256·원본 변경 전 동작·시험 결과를 고정해 전달했다. 이 호출은 도구 없이 검토하며 불필요한 MCP 연결만 호출 단위로 제외했다. 전역 설정·훅·권한 정책은 변경하지 않았다.
- 추가 직접 관측: 같은 0.1초 취소 대기 각본의 수정본은 대기 진입 2회, 프로세스 CPU 측정값 0.000초(측정 해상도 이하), 스레드 종료 후 호출자 정리를 보였다. 전체 앱 부하 성능을 뜻하지 않는다.
- 코드 지도·목록 검사 통과. graft는 재빌드했고 작업 트리 기준 영향 후보와 실제 호출부를 대조했다. `--base 18d09bd7` 결과는 먼저 커밋한 MCP 시험만 다루므로 공통 함수 영향 근거로 쓰지 않았다. 기존 정책 등 다른 작업자의 변경은 이 검증 범위에서 제외했다.
- 독립 리뷰 결과: 도구 없는 고정 원문 검토, 실제 `claude-fable-5-2`, PASS·차단 지적 없음. 부모가 대상 지문 불변과 실제 응답 토큰을 대조했다. 읽기 전용 검토가 실제 시험을 대신한 것은 아니다.
- 리뷰 후 보충: AnyIO `run`/TaskGroup 안에서 지속 취소와 직접 `task.cancel()` 2회를 겹친 격리 시험도 통과했다(시험 기록 `656ef88cbbba40cf968cf96e8973acf4`). 코드·시험 파일은 바꾸지 않았다.
- 남은 한계: Python 3.14의 스레드 실패 시험은 명시적인 `worker.exception()` 한 줄의 필요성 자체를 증명하지 않는다. 전체 이벤트 루프 종료가 worker 태스크까지 직접 취소하는 상황과 worker의 `BaseException`은 기존 경계이며 이번 요청 취소 수정으로 해결됐다고 하지 않는다. 리뷰의 강제 종료 시 추가 로그 가능성은 추정으로 남긴다.
- 의존성: `backend/requirements.txt`와 `requirements.lock.txt` 모두 AnyIO 4.13.0을 직접 고정하고 있다. 새 의존성 추가 없음.
- 마감: 실제 양측 계약 합의·별도 Claude 리뷰·필수 시험 근거를 확인한 integrate 검사 통과. 코드 지도·목록 검사 및 graft build/check 통과. dev 코드 커밋 `6d631291`. 실사용 프로세스 재시작·공유 서버 쓰기·main 병합·push는 하지 않았다.
