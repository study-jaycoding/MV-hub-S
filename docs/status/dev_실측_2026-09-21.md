## 4. 설계 — Claude 안 + Codex 적대적 검토로 합의(2026-09-21)

### A1 — 옛 저장 자리를 따로 기억한다

- 새 테이블 `final_export_old(dest_path PK, gen_id, project_id, noted_at)`(이 PC 의 DB). 저장 대장 `final_export` 는 생성물당 한 줄이라 경로가 덮어써진다 — 옛 자리는 여러 개일 수 있어(A→B→C) 누적 테이블이 가장 작다(Codex: 한 칸짜리 '이전 경로'로는 A 를 다시 잃는다).
- 적는 때: ①`record_export` 가 다른 경로로 덮어쓰기 직전 ②`forget_exports`(대장에는 있는데 새 자리에 없음)가 지우기 직전. 프로젝트를 모르는 줄은 적지 않는다(조회는 언제나 프로젝트로 한정).
- 쓰는 곳: `_save_finals_scan` 이 훑을 **폴더**를 고를 때만. 파일을 옮길 근거로는 쓰지 않는다 — 판정은 종전 그대로(이름 규칙 + 각인의 gen_id·hub 일치 + 지금 대상의 자리 제외 + 10분 + 이동 전후 각인 재확인).
- 지우는 때: 렌더 폴더 **안**의 경로인데 그 파일이 더 이상 없을 때(미러가 옮겼거나 손으로 지움). 렌더 폴더 밖 경로는 확인도 삭제도 하지 않는다(폴더를 되돌릴 수 있다 — Codex).
- 영구 삭제의 고아 정리 대상에는 넣지 않는다 — 생성물이 지워져도 NAS 에 남은 우리 파일을 찾을 마지막 단서다(Codex).
- 시험: 폴더가 바뀐 컷이 비교의 `extra` 에 나온다(두 번 비교해도) · 저장(업데이트) 뒤에도 나온다 · 미러가 옮긴 뒤 줄이 지워진다 · 옛 자리의 사람 파일은 세기만 한다 · 영구 삭제된 생성물의 옛 파일도 나온다.
- 남는 한계: 영구 삭제된 생성물의 **지금 자리** 파일은, 그 폴더가 더 이상 어떤 대상의 폴더도 아니면 여전히 못 찾는다(이번 범위 밖 — 종전부터).

### A2 — 상태 조회는 디스크에 묻지 않는 목적지 계산을 쓴다

- `project_folders`: `safe_dest` 의 글자 검증을 `_dest_parts` 로 떼고(검증 순서·결과 동일), 새 `ledger_dest(render_resolved, folder_path, filename)` = 검증 + 순수 결합(I/O·`resolve()`·`safe_join` 금지). `save_finals_status` 는 렌더 폴더 해석 1회 + 대상마다 `ledger_dest`. 쓰기·스캔은 계속 `safe_dest`.
- 알려진 한계: 렌더 폴더 **안쪽**에 심볼릭 링크·junction 이 있으면 '이미 저장'이 '새로 저장'으로 보인다(`saved_at` 도 빈다). 저장은 실제 폴더를 확인해 건너뛴다.
- 시험: 상태 조회 중 `safe_dest`·`safe_join` 을 막아도 통과 · 잘못된 경로는 여전히 "경로 안전성 위반" · 결과(saved·saved_at)는 종전과 같다.

### A3 — 실행 중 프로젝트 전환

- 실행 중(`busy`)에는 프로젝트 선택을 잠근다. `onSave`·`onMirror` 는 시작할 때의 프로젝트를 잡아 두고, 끝났을 때 프로젝트가 같을 때만 결과·오류·재확인 창·비교 버리기·상태 다시 읽기를 반영한다(`busy` 해제는 언제나). 비교는 이미 요청 번호로 늦은 응답을 버린다.

### A4 — 사유 도배

- 렌더 폴더 미연결이라는 **공통 사유만** 줄에서 숨긴다(원본 없음·경로 안전성 위반 같은 개별 사유는 그대로). 건수 칸의 설명은 저장 불가 사유가 전부 같으면 그 사유, 아니면 "원본 없음 등".

### A5 — 고치지 않는다(기록만)

- 표시뿐이고 조건이 매우 좁다. 잘 도는 코드에 이론상 위험으로 손대지 않는다는 기준에 따른다(Codex 동의).

### A6 — '우리 파일'의 증거는 이 PC 의 대장(gen_id + 정확한 경로)

- 각인에는 프로젝트가 없다(형식을 바꿀 수 없다). 위임 모드에서는 각인의 gen_id 가 서버 id 라 로컬 생성물 표로 소속을 못 본다 → 쓸 수 있는 양성 증거는 이 PC 의 대장뿐이다.
- `extra` 조건에 **(gen_id, 그 파일의 정확한 경로)가 이 프로젝트의 대장(`final_export` 지금 자리 ∪ `final_export_old` 옛 자리)에 있을 것**을 더한다. gen_id 만으로는 부족하다(Codex: 같은 생성물의 복사본·다른 확장자·프로젝트를 옮긴 이력). 증거 조회에는 상한을 두지 않는다(이력 표시용 `list_exports` 의 상한을 쓰지 않는다).
- 달라지는 것: 다른 PC 가 저장했고 이 PC 가 적어 둔 적 없는 파일은 이 PC 의 미러가 정리하지 않는다(모르는 파일로 센다). 틀리는 방향이 '안 옮김'이다.

### A7 — 같은 렌더 폴더를 다른 프로젝트도 쓰면 정리하지 않는다 (Codex 코드 리뷰의 추가 P1 에 대한 완화)

- 생성물을 다른 프로젝트로 옮긴 뒤에도 옛 프로젝트의 대장 증거는 남는다. 두 프로젝트가 같은 렌더 폴더·같은 목적지를 쓰면 그 증거가 새 프로젝트의 **지금 파일**을 가리킨다 → 같은 렌더 루트(경로 글자 비교)를 쓰는 다른 프로젝트가 이 PC 의 목록에 있으면 정리 후보를 내지 않고 이유(`cleanup_blocked`)를 돌려준다. 이유 문장에 프로젝트 이름은 넣지 않는다(보는 사람에게 안 보이는 프로젝트일 수 있다).
- **부분 완화다** — 아래 6절의 미해결 항목 참고.

## 6. Claude 와 Codex 의 판단이 갈렸던 곳 — **Jay 결정(2026-09-21)으로 닫음**

- **C1 → 한계로 둔다.** Jay: 여러 프로젝트가 렌더 폴더를 함께 쓰는 일은 **없다**. 서버 API 는 만들지 않는다(그런 구성이 생기면 다시 연다).
- **C2 → 치운다.** Jay: 프로젝트를 옮긴 생성물의 옛 저장본은 옛 프로젝트의 미러가 치우는 게 맞다(지금 동작 그대로 — 코드 변경 없음). 재제안하지 않는다.

### C1. 렌더 트리가 겹치는 프로젝트를 이 PC 가 모르는 경우 (Codex: P1 · Claude: 드문 구성의 남은 한계)

- A7 의 가드는 이 PC 의 프로젝트 목록만 본다. ①권한 밖이라 목록에 없는 프로젝트 ②매핑 드라이브와 UNC 처럼 글자가 다른 같은 폴더 ③한 프로젝트의 Render 안에 다른 프로젝트의 Render 가 들어 있는 구성에서는 가드가 안 걸린다(Codex 코드 리뷰 — **실행으로 재현한 것은 아니다**).
- 그때 일어나는 일: 옛 프로젝트에서 저장한 뒤 **그 겹치는 프로젝트로 옮겨 간 생성물**의 파일을 옛 프로젝트의 미러가 확인 창을 거쳐 격리 폴더로 옮긴다. 지워지지 않고, 새 프로젝트의 다음 업데이트가 다시 저장한다.
- 닫는 방법: 서버가 "이 렌더 트리와 겹치는 프로젝트가 있는가 · 이 생성물들의 현재 프로젝트"를 알려 주는 새 API(서버 배포 필요). Claude 추천: 지금은 한계로 두고, 팀이 실제로 렌더 폴더를 공유하는 구성을 쓰는지 Jay 가 알려 주면 그때 정한다.

### C2. 다른 렌더 폴더를 쓰는 프로젝트로 옮겨 간 생성물의 옛 파일 (Codex: P1 · Claude: 의도된 동작)

- Codex 3라운드 실측: P1 으로 저장한 생성물을 (렌더 폴더가 다른) P2 로 옮기면, P1 의 비교가 P1 Render 에 남은 그 파일을 '폴더에만 남은 것'으로 보고 미러가 격리 폴더로 옮긴다.
- Claude 의 판단: 미러의 정의("폴더를 프로그램과 똑같이 맞춘다") 그대로다 — 그 생성물은 더 이상 P1 의 것이 아니고, P2 는 자기 렌더 폴더에 따로 저장한다. 확인 창에 파일 이름이 나온다. Codex 의 판단: 소속이 바뀐 생성물은 옛 프로젝트의 정리 후보가 아니어야 한다.
- 당시의 선택지: 옛 프로젝트의 미러가 치운다(Claude 안) / 남겨 둔다(Codex 안 — 그러면 그 파일은 어느 미러도 치우지 않는다). → **Jay: 치운다.**
