## 한 줄 답

**대체로 맞다.** 고른 에피소드의 영상을 이 PC 로 미리 받아 다빈치 컷 빈에 이 PC 파일로 넣어 두고, MV 패널 [저장]을 누르면 타임라인에 쓴 것만 NAS 로 복사해 경로를 NAS 로 바꿔 끼운 뒤 저장한다. 허브에 새 생성물이 생기면 실시간 알림으로 받아 빈에 뒤따라 넣는 것도 이미 돈다. 다른 점 넷:

1. **temp 가 아니다** — 허브의 이 PC 미디어 폴더(보존 미디어: 50GiB 한도, 자동 삭제 없음). 리졸브가 쓰는 동안 파일이 사라지지 않는 대신 쌓이기만 한다.
2. **'모두'가 아니다** — 고른 에피소드의 컷마다 거르기를 통과한 오래된 순 200개까지.
3. **NAS 로 가는 건 MV 패널 [저장] 때, 타임라인에 쓴 것만**(예외: 패널을 다시 열 때 중단됐던 전환을 이어 마침). 안 쓴 것은 그때 빈에서 지운다. Ctrl+S·리졸브 자동 저장은 이 과정을 거치지 않아 이 PC 경로가 그대로 저장된다 — 리졸브 스크립트 API 에 저장 알림이 없다.
4. **사람이 다른 컷 빈 안에 있으면 그 컷은 미리 넣지 못한다** — 공식 API 의 가져오기가 '지금 빈'에만 넣기 때문. 그 컷 빈에 들어갈 때 채운다. 그리고 미리 받아 둔 컷이라도 패널에서 끌려면 그 컷을 고른 뒤 띄움 응답이 와야 한다. **→ 정정(같은 날 오후): 이것이 Jay 가 느끼는 지연의 주원인이다 — 8절.**

## 3. Jay 가 원하는 동작 — 되나

- **받는 범위·용량**: 지금은 고른 에피소드만·컷마다 200개(거르기 통과). 에피소드를 바꾸면 새 에피소드를 받고 앞 에피소드 파일은 남는다. 보존 미디어 50GiB 를 라이브러리 등 다른 기능과 같이 쓰고 자동 삭제가 없다 — 넘치면 새 받기만 실패한다(그 생성물은 미리 띄우기에서 빠지고 컷에 들어갈 때 실패 알림). 에피소드 하나에 몇 GB 인지는 생성물 크기 분포를 재지 않아 모른다. 캐시를 지우는 기능은 리졸브가 그 파일을 가리키고 있을 수 있어 이번 범위 밖(후속 후보).
- **바뀜 감지**: 웹소켓 + 15초 + 창 초점으로 이미 된다 — 새 감지 장치는 필요 없다. 패널은 생성물 ID 단위로만 다룬다. 같은 생성물 ID 의 파일 내용이 바뀌는 경우(지문 비교)는 이번에 확인하지 않았다(미확인).
- **이미 놓인 클립 바꿔 끼우기**: `ReplaceClip` 은 같은 항목 ID·타임라인 구간을 지킨다(실측). 하지만 공식 설명이 "underlying asset and metadata" 를 바꾼다고 하므로(pyi `:2126-2127`) 길이가 다른 새 테이크로 자동 교체하면 편집 구간이 어긋날 수 있다. NAS 전환(같은 파일의 복사본)에만 쓰고, 새 테이크 자동 교체는 권하지 않는다.
- **쓰는 중 파일 교체 안전성**: 이 PC 캐시 파일은 자동 삭제가 없어 리졸브가 가리키는 동안 사라지지 않는다. NAS 복사는 `.part` 로 다 쓴 뒤 덮어쓰지 않는 이름 바꾸기라 반쯤 쓴 파일이 보이지 않는다(`resolve_transfer.py:634-656`).
