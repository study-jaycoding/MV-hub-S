### 1번 묶음의 계약 (코덱스 합의)

- `julianday(created_at)` **표현식 인덱스**를 쓴다.
- 날짜 범위는 **시작 이상 · 다음 날 시작 미만**으로 쓴다.
- 경계는 **현재 운영 서버의 시간대 의미를 보존**한다. UTC 서버를 KST 로 바꾸는 **정책 변경은 섞지 않는다**.
- `GROUP BY date(...)` 나 전체 합계용 `CASE` 까지 기계적으로 바꾸지 않는다.
  특히 **예산 기간 조건을 `WHERE` 로 옮기면 전체 누적 합계가 달라진다**.
- 종료일·자정·혼합 시각 형식·NULL/잘못된 시각, 소수·환불·권한·읽기 스냅샷을 함께 검증한다.
- ★**동률 정렬**: 코덱스 측정에서 날짜 범위 조회의 **동률 모델 행 순서가 달라졌다**(정렬이 금액만 지정).
  순서를 계약으로 볼 거면 명시적 동률 기준을 넣는다.

**측정 근거**(내가 직접 잰 것): 실제 22,392행에서 `date(created_at,'localtime')` **8.62 ms `SCAN`**
→ `julianday()` 표현식 인덱스 **0.04 ms `SEARCH`**, **244배**, 결과 완전 동일(156건·4020.0크레딧).

**코덱스가 잰 것**: `team_overview` 함수 기준 — 전체 기간 97.18 → 97.81 ms(**변화 없음**),
9월 1~10일 59.32 → **9.40 ms**. → **D-4 가 D-3 전체를 해결하지 않는다**(전체 기간 집계는 따로 남는다).
쓰기 비용: 1,000건 upsert 에 **+1.4~2.0 ms**, 인덱스 **356 KiB**, 생성 9.24 ms — 채택을 막을 비용이 아니다.

### 2번 묶음(A-8)의 계약 (코덱스 합의)

- **(a) 어디서**: 작업자 PC 가 맞지만 `agent_push.py` 일 필요는 없다. 견적은 이미 **로컬 허브**의
  `cli_bridge.estimate_cost` 가 하고, 로컬 metrics 는 기존 팩트 전송 경로가 서버로 보낸다.
  → **로컬 허브의 배경 작업**으로 계산하고 **기존 전송 경로를 재사용**한다. 에이전트에 중복 구현하거나
  팩트 스키마에 params 를 넣지 않는다.
- **(b) 오늘 가격**: `credit_source` 표시만으론 부족하다. 현재 합계가 source 와 무관하게
  `COALESCE(real_credits, est_credits, 0)` 을 쓰고 **예산에도 연결**된다.
  → 기존 `real_credits`·당대 `est_credits`·생성 시각을 **보존**하고, **별도 `repriced_credits` +
  `price_observed_at`** 을 저장한다. 화면엔 "현재 관측 가격으로 재산정" 과 **커버리지**를 따로 표시하고,
  **기존 사용량·예산·원장 합계에 자동 편입하지 않는다.**
  ★"오늘 실행" ≠ "오늘 가격 관측" — 견적 함수는 실패 시 **만료 캐시도 반환**한다. 관측 시각을 함께 다뤄야 한다.
- **(c) 옵션 부족**: 근거 없는 기본값 대입 금지. 셋으로 나눈다 —
  ①가격 결정 정보 완전 → 재산정 ②그 모델에서 옵션 무관함이 **검증됨** → 재산정
  ③누락·지원 종료·스키마 해석 불가·필수 미디어 정보 부족 → **미상 유지**.
  영상은 옵션만으로 안 끝난다 — `video_edit` 는 **입력 영상의 실제 길이가 가격을 정해** 더미로 견적 불가(코드에 명시).
- **(d) 호출**: 무과금은 확인했으나 공급자의 **공식 호출 제한·제재 기준은 미확인**.
  기존 조합 캐시·단일비행 재사용, PC 당 낮은 동시성, 대화형 작업 우선, 실패 백오프·중단·재개.
  **견적 실패는 NULL 로 남기고 0 을 만들지 않는다.**
- **저장·전송도 같은 묶음**: 로컬 저장과 전송 대기 표시를 **같은 트랜잭션**으로. 서버는
  **값+관측 시각을 함께 비교해 오래된 재전송을 거부**한다. 견적 필드만 기존 전체 팩트 endpoint 로 보내면
  **다른 메타데이터를 기본값으로 덮을 수 있다.**

## E. 코덱스 적대적 검토 — 내 초안 3개가 전부 깨짐

### E-1. 안 A(목록에서 `params.prompt` 제거) — **깨진다**

코덱스 반례 (전부 내가 재확인):

1. **소비처가 있다.** `recipeScene.ts:23` 이 `Object.entries(params)` 로 **모든** primitive 를
   복사하고(`prompt` 제외 안 함), `ModelCard.tsx:46` 이 표시하며 `sceneBackup.ts:212` 가
   `JSON.stringify` 로 백업 비교에 쓴다. → **"아무도 안 쓴다" 는 틀렸다.**
2. **목록 전용 자리가 아니다.** `generation_rows.py:43` `_attach_children` 은 목록·상세·배치·
   히스토리·소스 검색이 **공유**한다(`generations_query.py:248,345` · `history.py:103,189` · `sources.py:164`).
3. **★항상 중복이 아니다.** 재생성은 `row.prompt` 만 바꾸고 `params.prompt` 는 그대로 둔다
   (`repo/generations.py:971` · `usecases/gen_requests.py:1383`). 코덱스가 `override_prompt_model`
   을 메모리 SQLite 로 **실제 실행해** 증명했다.

**내 재확인**: DB 전량 1332건 중 `params.prompt != prompt` 가 **2건(0.2%)**.
내 200건 표본에서는 0건이었다 — **표본이 법칙이 아니었다.**

→ 수정 방향: **두 값이 정확히 같을 때만** 생략하고 불일치는 보존. 생략 시 프론트 복원 필요.

### E-2. 안 B(`generate list` 로 폴링 대체) — **깨진다**

내가 걱정한 "목록이 앞서간다" 가 아니라 **"목록이 뒤처진 채 남는다"** 가 진짜 반례다:

```
list: waiting  /  get: completed + 결과 URL
→ 내 설계는 list 가 waiting 이라 get 을 안 부른다 → 영원히 미확정
```

이 상황은 **회귀 시험으로 저장소에 남아 있다** (`backend/tests/test_agent_contracts.py:1973`).
잡이 `active` 에 남으면 슬롯을 채워 **새 생성까지 막는다**(`agent_push.py:2829,2844`).

**필수 조건**: 목록 상태와 무관하게 잡마다 **최대 간격을 정해 `get` 을 수행**해야 한다.
목록은 *우선순위 힌트*로만 쓴다.

**추가 반례**: 100건 벽은 남이 없어도 넘는다 — 긴 잡 하나가 도는 동안 후속 100건이
완료되면 밀려난다. `_MAX_IN_FLIGHT_JOBS` 는 환경설정으로 **256** 까지 간다(`agent_push.py:2207`).

**내 A-2 실측의 가치 정정**: `expected_image_inputs > 0 and not detailed` 분기
(`agent_push.py:2287`)는 **유일 호출부가 이미 `detailed=True`**(`agent_push.py:2414`)라
**실행되지 않는 죽은 분기**다. → 제거해도 **CLI 절감 0회**. 내 발견은 사실이었으나 실익이 없다.

### E-3. 안 C(중복 엔드포인트 통합) — **조건부**

두 API 는 **권한·범위가 다르다**:

| API | 권한 |
|---|---|
| `projects/workspace-options` (`routers/projects.py:132`) | `create_project` 필요, **전체 공간** |
| `manage/workspaces` (`routers/manage.py:498`) | `read_all` 이면 전체, **일반 멤버는 본인 공간만** |

→ projects API 로 통일하면 일반 멤버가 **403**. manage API 로 통일하는 방향은 가능
(현재 `create_project` 를 가진 `product_manager` 는 `read_all` 도 가짐 — `rbac.py:45`).
**URL 만 통일하면 횟수는 안 준다** — 결과 공유/in-flight 합치기까지 해야 한다.

### E-4. 코덱스가 지적한 "내가 놓친 더 큰 문제"

1. **team-fresh 는 갱신이 계속 폐기될 수 있다.** 페이지마다 최신 요청인지 검사하는데
   (`ProjectSection.tsx:333` · `projectApi.ts:49`), 전체 조회가 15초보다 오래 걸리면
   **매번 완독 전에 폐기**된다. 실제 지연 발생은 미확인. 또 `since` 만 전진시키면
   **공유 해제·삭제·폴더 이동이 반영되지 않는다**(서버는 변경 이력이 아닌 현재 집합을 반환 — `repo/projects.py:674`).
2. **입력 이미지 검증이 부분 누락을 통과시킨다.** 조건이 "기대>0 인데 관측≤0" 뿐이라
   기대 2장·관측 1장이 통과한다(`agent_push.py:2300`).
3. **200초는 최악값이 아니다.** 순차 `get` 의 timeout 이 120초라 8건이 모두 타임아웃이면
   **약 16분** 정지(`agent_push.py:2388`).

- 못 본 잡·후보의 상태는 **건드리지 않는다** — 확인 못 한 것을 실패로 기록하면 기아가 된다.

| 직접 확인 | 자체 예산 | 패스 예산의 **70%** |
| 재조정 순회 | 자체 예산 | 패스 예산 전체 |

**후보 조회 HTTP 만 예산에서 뺀 이유**: 여기에도 게이트를 걸었더니 "한 패스 최소 1건" 보장이
무력해져 **재조정이 영영 0회**가 됐다(시험 6건 실패로 드러남). 직접 확인이 예산을 다 쓰는
상황이 바로 그 경우다. 반면 `replay_outbox` 는 못 보낸 항목을 보관해 다음에 재시도하는 것이
**원래 계약**이라 잘라도 잃는 것이 없다.

**예산의 의미(파일 전체 공통)**: 예산은 **새 호출을 시작할지**만 가른다. 시작한 호출은 정상
timeout 을 온전히 받는다 — 남은 예산으로 timeout 을 자르면 끝낼 수 없는 시간만 주고 실패한다.
그래서 **한 패스는 예산 + 마지막으로 시작한 호출 1건**만큼 넘을 수 있다(ACK HTTP 기본 60초는 그 위).
이건 한계로 남긴다, 해결했다고 적지 않는다.

### J-2. B-8 — 상태 DB 연결을 **반드시 닫는다**

`with sqlite3.Connection` 은 트랜잭션만 끝내고 **연결은 닫지 않는다**(코덱스 지적).
이 경로는 한 사이클에 10회 이상 불린다. `_state_db()` contextmanager 를 만들어 9곳을 바꿨다 —
정상이면 커밋, 예외면 롤백, **언제나 close**.

실측 `_state_connect` 1회 **1.24ms**(connect 0.10 + PRAGMA·DDL 1.13), 사이클당 약 **12ms**.
**연결 캐시·DDL 최적화는 보류** — 12ms 는 작고, `synchronous=FULL` 내구성을 유지한 채 다시 재는 것이 먼저다.

### J-3. D-8 — 위임 판정이 **서버 전체를 멈추지 않는다**

`data_proxy_middleware` 는 `async def` 인데 그 안의 `proxying()` 이 DB 를 읽고, 그 경로가

## L. 묶음 ③ — 프론트 갱신·소규모 정리 (2026-09-12)

### C-16. 열린 패널 상세 폴이 **미읽음 수가 바뀔 때마다 처음부터 다시 시작**

### B-10. 참조 재다운로드·재해시 — **보류 유지**, 단 ★예상 못 한 사실이 나왔다

코드를 따라가 확인한 것:

1. 레퍼런스는 **전부** `_resolve_ref` 를 지나며, 그 모든 분기가 `_download_ref` 로 간다.
   `_download_ref` 는 매번 `tempfile.mkstemp()` 로 **새 임시파일**을 만든다.
2. `_file_fingerprint` 의 캐시 키는 `(정규화 경로, 크기, mtime_ns)` 다.
3. `_upload_for_media`(`agent_push.py:2146`)가 받는 경로는 언제나 그 새 임시파일이다.

→ **그 해시 캐시(`_fp_cache`, 512칸)와 in-flight 합치기는 이 경로에서 한 번도 적중할 수 없다.**
   주석이 말하는 "같은 대형 레퍼런스를 동시 4제출하면 4번 읽는다 → 1회로 합친다" 는
   **경로가 안정적인 로컬 파일에만** 성립하는데, 지금 그런 분기가 없다.

**실제로 작동하는 중복 제거는 업로드 쪽이다** — `_upload_for_media` 는 **digest 키**로 캐시·합치기를
하므로 같은 내용의 레퍼런스는 **업로드가 한 번만** 일어난다(그건 정상이다).
그래서 N개 제출이 같은 레퍼런스를 쓸 때 실제 반복 비용은 **다운로드 N회 + 해시 N회**이고
(해시는 실측 1ms/MB), 업로드는 1회다.

★**데드 코드로 보이지만 지우지 않았다** — 이번 작업 범위 밖이고, 지침대로 보고만 한다.
★재개 조건(그대로): URL 내용 변경·만료·인증 범위를 함께 다루는 **다운로드 캐시 설계**가 먼저다.
 지금 쓸 수 있는 가장 좁은 안은 "한 배치 실행 안에서만 URL→임시파일을 재사용" 인데,
 배치 도중 원본이 바뀌면 지금은 새 내용을 집어 오지만 캐시하면 옛 내용을 쓴다 — 그 차이를 승인해야 한다.

### R-2. 2단계 — 프록시 구간까지 (허브 ↔ 공유 서버)

1단계는 **브라우저 ↔ 서버** 만 줄였다. 로컬 허브 사용자의 가장 비싼 구간은 **허브 ↔ 공유 서버**
(인터넷)인데 `urllib` 이 `identity` 를 보내 그대로였다. 코덱스 설계대로 그 구간을 열었다.

| 함수 | 한 일 |
|---|---|
| `_proxy.raw_request` | `Accept-Encoding: gzip` **명시** + 응답 `Content-Encoding` 을 보고 해제 |
| `decode_proxy_body`(신설) | 해제·상한·오류 처리를 한 곳에 모아 **시험 가능**하게 |
| `stream_download`·`_forward_stream` | **`identity` 를 명시** — 바이트·Range 계약 보존 |
