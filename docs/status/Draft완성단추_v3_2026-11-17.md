원본 프롬프트·seed·길이·레퍼런스·mode는 기존 완성 경로대로 보존한다.

#### 2-2 서버 중복 방지 새 규칙

판정 단위는 다음과 같다.

`creator_uid + 원격 draft_job_id + finish_resolution`

워크스페이스나 캔버스 attempt가 다르다는 이유로 같은 원격 드래프트·같은 화질 중복을 허용하지 않는다.

**요청 행 검사**

원격 draft job은 기존처럼 다음 두 위치에서 찾는다.

- `payload.params.draft_job_id`
- `payload._draft_finish_job_id`

화질은 다음 순서로 해석한다.

`payload.params.resolution` → `payload._draft_finish_resolution` → `"1080p"`

`_draft_finish_job_id`만 있는 옛 예약 행은 1080p로 해석한다. 명시적으로 예상 밖 화질이 기록된 행은 임의로 1080p로 바꾸지 않고 보수적으로 차단한다.

같은 판정 단위의 요청은 다음 조건에서만 종결로 인정한다.

| 요청 상태 | 잠금 해제 조건 |
|---|---|
| `done`·`failed` | `terminal_at` 존재 |
| `canceled` | `terminal_at` 존재 **및** 확인된 제출 전 취소 또는 원격 종료 근거 존재 |
| 그 밖의 상태 | 해제하지 않음 |
| 상태와 무관하게 `terminal_at` 없음 | 해제하지 않음 |

`trash.py:52-62`의 `_NONTERMINAL_REQUEST_PHASES`에는 `preparing`, `pending`, `claimed`, `submitting`, `running`, `tracking`, `verifying`, `blocked`, `recovery_required`가 포함된다. 전부 계속 차단한다. 알 수 없는 신규 상태도 통과시키지 않는다.

`terminal_at` 단독으로 원격 종료를 추정하지 않는다.

**삭제·취소 근거**

기존 삭제 정책은 유지하면서, Draft 완성 요청의 **제출 전 취소 사실**만 payload에 남긴다.

- `_remove_main_for_transfer`와 `_cancel_orphan_requests`가 기존 상태 `preparing`·`pending`·`claimed`를 취소할 때, 같은 트랜잭션에서 `_draft_finish_release_reason="not_submitted"`를 기록한다.
- 대상은 `params.draft_job_id` 또는 `_draft_finish_job_id`가 있는 Draft 완성 요청이다.
- `submitting` 이후 요청의 영구 삭제에는 이 표식을 찍지 않는다.
- 원격 종료를 확인한 기존 취소 경로는 `_RETIRED_REQUEST_NOTE`를 남긴다(`trash.py:256-262`). 이 경로의 `canceled+terminal_at`는 해제할 수 있다.
- 옛 `canceled` 행에 제출 전 취소 근거가 없고 원격 종료 경로도 확인되지 않으면 차단을 유지한다.
- `submission_started_at`가 없다는 사실만으로 미제출을 인정하지 않는다. 기존 에이전트 호환 claim은 이 시각 없이 `submitting`으로 갈 수 있다(`repo/gen_requests.py:1727-1732`).

따라서 휴지통 이동·영구 삭제·부팅 정리로 `recovery_required`의 중복 과금 방어가 사라지지 않는다.

**자식 행 검사 유지**

`generation.params.draft_job_id`와 화질이 같은 자식도 검사한다.

- 진행 상태 자식은 차단한다.
- `done`·`failed`·`nsfw` 자식이라도, 대응 요청에서 위 종결 조건이 확인되어야 통과한다.
- 요청이 없는 실패 자식은 계속 차단한다.
- `deleted_at`가 있거나 화면에서 보이지 않는다는 이유로 이 안전 검사를 제외하지 않는다.

이 검사는 제거하지 않는다. 키·캔버스 예약 없는 경로에서는 자식 INSERT가 커밋된 뒤 요청을 만든다(`usecases/gen_requests.py:1606-1615`). 그 사이에는 자식 행만 중복 요청을 막을 수 있다.

**동시성·표식**

검사·승자 표식·자식 INSERT는 기존 `BEGIN IMMEDIATE` 트랜잭션 안에서 수행한다.

- 승자 예약에 `_draft_finish_job_id`와 `_draft_finish_resolution`을 함께 기록한다.
- 아직 복제에 성공하지 않은 빈 `preparing` 예약끼리는 서로 잠그지 않는다.
- 같은 화질 동시 요청은 하나만 성공한다.
- 다른 화질 요청은 각각 하나씩 성공할 수 있다.
- 일반 키·캔버스 예약·두 경로가 섞인 경쟁·예약 없는 경로를 모두 검증한다.

충돌은 기존처럼 409와 `X-MVHub-Submission: not-started`로 반환한다. 문구에는 “이미 완료된”을 빼고 해당 화질과 기존 생성 ID를 표시한다.

MCP는 기존처럼 `draft_job_id`를 거절한다. Draft 완성 기능을 추가하지 않는다.

#### 2-3 드래프트 만료 — 에이전트의 좁은 확정 실패 예외와 화면 안내

**에이전트 판정 위치**

`_submit_one`에서 `_run_cli_json` 반환과 `_extract_created_id` 실행 **뒤**, 작업 ID가 없는 분기에만 예외를 추가한다(`agent_push.py:3497-3513`).

다음 조건이 모두 맞아야 한다.

1. `model == "seedance_2_5"`.
2. `params.draft_job_id`가 비어 있지 않음.
3. `params.draft is False`.
4. 복구된 생성 작업 ID가 없음.
5. 직접 반환된 CLI 실패 사유의 오류 본문 시작이 정확한 만료 문장임.

실제 전달 사유는 다음 구조다.

```text
CLI 실패: Error: Seedance 2.5 draft has expired — cmd: …
```

에이전트는 저장된 카드 전체 문구를 검색하지 않는다. 직접 반환된 실패 사유의 `CLI 실패:`와 선두 `Error:`를 처리하고, `— cmd:` 뒤 인자는 판정에서 제외한다. 만료 문장 끝에는 문자열 경계 또는 정상적인 문장 경계가 있어야 한다.

다음은 확정 실패로 분류하지 않는다.

- 다른 오류 뒤나 명령 인자·프롬프트 속에만 만료 문장이 있음.
- 타임아웃·JSON 파싱 실패·부분 출력에 만료 문장이 있음.
- 모델 또는 `draft_job_id` 조건이 다름.
- 작업 ID를 확보함.
- 오류 구조가 예상과 달라 판정하기 어려움.

표시 전용인 `_cli_error_message`의 넓은 파싱 결과를 그대로 과금 안전 판정으로 승격하지 않는다.

**보고 경로**

조건을 만족하면 정제한 원래 `CLI 실패: …` 사유로 기존 `_fail`을 한 번 호출한다.

- 자동 재시도하지 않는다.
- `_require_submission_recovery`는 호출하지 않는다.
- `/fail` 요청 실패까지 성공으로 간주하지 않는다. 서버에 적용되지 않았다면 기존 lease 복구 안전망이 남는다.
- 작업 ID가 있으면 기존 outbox·앵커·원격 추적 경로를 유지한다.
- 그 밖의 작업 ID 없는 오류는 기존처럼 `recovery_required`에 격리한다.

서버 `/fail` 변경은 필요 없다. `fail_request`의 구 에이전트 격리 조건은 `제출 실패`·`제출 처리 예외` 앞말이다(`usecases/gen_requests.py:1330-1340`). `CLI 실패: Error: Seedance 2.5 draft has expired …`는 `apply_local_failure`로 전달되어 요청 `failed+terminal_at`와 생성물 실패가 원자적으로 기록된다(`repo/generations.py:655-700`).

사용자 전달 `no_match` 1건을 모든 경우의 원격 미제출·무청구 증명으로 확대하지 않는다. 이 예외는 특정 서비스 거절 문장에 제한한다.

**화면 안내**

- 오류 판정 도우미 하나를 `lib/seedanceDraft.ts`에 둔다.
- 화면에서는 기존 `generationErrorMatches`를 사용하여 저장된 `제출 진단:`·CLI 앞말을 처리한다.
- `generationDisplay.ts`에서 실패·복구 보류 카드의 제목을 `드래프트 만료`, 할 일을 `새 드래프트를 만드세요`로 표시한다.
- 공용 `generationIssue.ts` 분류 코드와 Python 짝 분류는 변경하지 않는다.
- 완료 카드나 실제 진행 단계의 오래된 오류를 만료 실패로 덮지 않는다.

고르기 창에서는 **선택한 원격 draft job과 일치하는 자식**에 유효한 만료 오류가 있을 때 두 화질 항목을 비활성화하고 지정 문구를 표시한다.

같은 캔버스 카드에 오래된 드래프트와 새 드래프트가 함께 있어도, 오래된 job의 만료가 새 드래프트를 막아서는 안 된다.

옛 `recovery_required` 행을 자동으로 `failed`로 바꾸거나 다시 제출하지 않는다.

#### 2-4 ‘이 드래프트로 만든 것’ 개수·진행 중 표시

고르기 창을 열 때 `api.history(draft.id)`를 한 번 조회한다. 매번 열 때 갱신하며 별도 장기 캐시는 추가하지 않는다.

집계 대상은 다음 조건을 모두 만족하는 직접 자식이다.

- 모델이 `seedance_2_5`.
- `params.draft_job_id === selectedDraft.job_id`.
- 삭제 표시가 없음.
- 화질이 1080p 또는 4k. 옛 값 없음은 1080p로 해석.

순수 집계 함수는 `lib/seedanceDraft.ts`에 둔다.

- **만든 것:** `status === "done"`이고 명시적인 미종결 실행 단계가 없는 자식.
- **진행·확인 중:** `preparing`·`pending`·`claimed`·`submitting`·`running`·`tracking`·`verifying`·`blocked`·`recovery_required` 실행 단계. 실행 단계가 없을 때는 기존 `pending/running` 상태를 보조로 사용.
- **만료:** 2-3의 모델·원격 job·오류·카드 상태 조건을 만족하는 자식.

자식은 ID로 중복 제거한다. 실패·진행 중 결과는 완료 개수에 넣지 않는다.

0인 화질은 개수 설명에서 생략한다. 둘 다 0이거나 조회가 실패하면 개수 부분을 생략한다. 조회 실패를 “진행 중 요청 없음”이라는 확정 결과로 저장하지 않는다.

선택 대상·원격 job·계정/서버/워크스페이스 문맥이 바뀌면 이전 응답을 버린다. 열려 있는 동안 현재 시도의 접수·완료 변화가 발생하면 해당 history를 갱신하여 오래된 진행 표시가 계속 남지 않게 한다.

history는 현재 남은 연결과 생성물의 표시 자료다. 삭제된 요청·표식·수동 연결 해제까지 포함한 전체 과금 원장이 아니므로 서버 중복 검사를 대신하지 않는다.

#### 2-5 견적

기존 `sharedCostEstimate(model, opts)`를 사용한다.

```text
model = seedance_2_5
opts = normalizeSeedanceDraftParams(
  model,
  { ...draft.params, resolution: 선택 화질 }
)
```

드래프트 생성용 플래그와 옛 `draft_job_id`는 견적 옵션에서 제거하고, 원본 길이와 관련 옵션은 보존한다.

- Draft 단추가 보일 때 1080p·4K 견적을 각각 요청한다.
- 기존 12시간 캐시·동시 요청 합치기·실패 비캐시를 사용한다(`useModels.ts:383-403`).
- 컴포넌트가 다시 그려질 때마다 요청하지 않도록 안정적인 옵션/효과 의존성을 사용한다.
- 늦게 온 이전 선택의 응답은 현재 선택을 덮지 않는다.
- 실패 시 자동 재시도 루프나 고정 단가 계산을 추가하지 않는다.
- 정상 견적 0은 숫자 `0`으로 표시한다.
- 견적을 못 받으면 **숫자만** 생략한다. `✦`와 단추 기능은 유지한다.

사용자 전달 실측은 1080p 초당 16, 4k 초당 28이다. 자동 시험에서는 4초의 64·112를 모의 응답으로 사용한다. 이 값으로 실제 청구를 보장하지 않는다.

#### 2-6 화면과 요청 상태

**화면**

- 닫힘: `Draft 1080p ✦64 ⌃`.
- 견적 없음: `Draft 1080p ✦ ⌃`.
- 고르기 창 순서: 설명 → `4K로 생성 ✦112` → `1080p로 생성 ✦64`.
- 4K 항목은 테두리, 1080p 항목은 기존 라임 `#c8ef40` 채움·검정 글자.
- 설명은 길이·Higgsfield 견적·누를 때마다 새로 생성하고 크레딧이 든다는 사실·확인된 완료 개수를 표시한다.
- 첫 단추 클릭은 창만 연다. 생성 제출은 화질 항목 클릭에서만 시작한다.
- 진행 중인 화질만 비활성화한다. 다른 화질 선택을 위해 막대 단추 전체를 잠그지 않는다.
- 만료면 두 항목을 비활성화한다.
- 기존 `canFinishDraft` 권한 조건을 유지한다.
- 바깥 클릭·Esc로 닫고 Esc 후 단추로 초점을 돌린다. 키보드로 열기·항목 선택이 가능해야 한다.
- `aria-expanded`·창 연결 정보·항목별 처리 상태를 제공한다.
- 선택이 바뀌면 열린 창을 닫는다.
- 기존 메뉴 닫힘 훅을 재사용한다. `useMenuPlacement("up")`의 아래쪽 반전 동작을 그대로 채택하지 않는다. 창은 위에 두고 공간 부족은 높이 제한·내부 스크롤로 처리한다.
- 새 문구 끝에 `...`를 쓰지 않는다.

**호출 계약**

- `onFinishDraft(generation, resolution)`.
- 진행 상태는 화질별로 조회한다.
- `draftDone`은 제거한다.
- App의 라이브러리 호출은 `onCanvas=false`, 캔버스·결과 창 호출은 기존 캔버스 연결 동작을 유지한다.
- `VariantDraftControls`의 `finish`·`busy`도 화질을 받도록 변경하고 `done`을 제거한다.
- `SceneBoard.tsx`가 해당 타입을 그대로 전달한다면 필요한 전달부만 맞춘다.

**useDraftRequests**

열쇠는 선택 원본 ID·캡처한 원격 draft job·화질의 조합으로 한다. 모든 Map 조회·삭제·현재 시도 확인·진행 집합에 같은 열쇠를 사용한다.

- 서버 요청 전 동기적으로 시도를 확보하여 빠른 연속 클릭을 막는다.
- 같은 화질은 동시에 한 시도만, 다른 화질은 별개로 처리한다.
- 현재 시도의 확정 완료·실패를 관측하면 잠금을 해제한다.
- `recovery_required` 또는 명시적 미종결 실행 단계가 우선한다.
- 목록 누락·조회 실패·시간 경과만으로 잠금을 풀지 않는다.
- `scope.isCurrent()`와 시도 객체 동일성 검사를 유지한다.
- 이전 시도의 늦은 응답이 같은 열쇠의 새 시도를 해제하지 못하게 한다.
- `completed` 영구 잠금과 불필요해진 `terminal` 상태는 제거한다.

**접수 불명**

현재 `App.tsx:1983-1987`의 “잠금을 풀고 다음에는 새 키로 제출” 동작을 바꾼다.

- 시도에 원래 PreparedSubmission·캔버스 예약을 캡처한 재확인 함수를 보존한다.
- 접수 불명 상태를 새 생성 가능 상태로 바꾸지 않는다.
- 사용자가 같은 화질을 다시 누르면 해당 함수로 **같은 의도만 재확인**한다. 새 `prepareRegenerateSubmission`·키·canvas attempt를 만들지 않는다.
- 재확인이 실행되는 동안 연속 클릭을 막는다.
- 접수 여부가 계속 불명확하면 원래 시도와 예약을 유지한다.
- 원래 키와 묶인 미제출 거절만 정리한다. 접수 불명 뒤 재확인의 `rejected`·`prepare_failed`는 원래 요청이 미제출됐다는 증거가 아니므로 불명 상태·잠금·예약을 유지한다. 최초 제출의 확정 거절은 기존 정리 경로를 따른다.
- 서버가 기존 완료 결과를 반환하면 그 결과를 연결하고 시도를 닫는다. **그다음 클릭부터** 새 생성 의도를 허용한다.
- 문맥이 바뀌면 이전 시도의 재확인을 실행하지 않는다.
- 자동 재제출·무한 재확인·새 공용 복구 체계는 추가하지 않는다.

### CRITERIA — 관측 가능한 성공 조건

1. 4초 Draft 선택 시 모의 견적 64·112가 올바른 화질에 표시된다. 견적 실패 시 숫자만 빠지고 생성할 수 있다.
2. 막대 단추 클릭으로 제출은 발생하지 않는다. 창은 위로 열리고 설명 → 4K → 1080p 순서다.
3. 4K 클릭은 `finish_draft=true`, `finish_resolution="4k"`를 보낸다. 기본값·값 없음은 1080p다.
4. 480p·720p·8k 등 허용하지 않은 완성 화질은 422, `finish_draft` 없는 화질 지정은 제출 전 400이다.
5. 같은 원격 draft·같은 화질의 미종결 요청은 409와 `not-started`를 반환한다. 다른 화질은 접수할 수 있다.
6. `done/failed+terminal_at` 이후 새 키의 같은 화질 요청은 새 자식을 만든다. 같은 키의 재시도는 기존 자식을 반환한다.
7. `failed/done`이라도 `terminal_at`가 없거나, 미종결 단계·알 수 없는 상태면 차단한다.
8. 자식 휴지통 이동·영구 삭제·부팅 정리 후에도 제출 불명 요청은 같은 화질을 차단한다. 확인된 제출 전 취소와 원격 종료 취소만 해제한다.
9. `_draft_finish_job_id`만 있는 옛 행은 1080p를 차단한다. 종결 근거 없는 실패 자식 시험은 계속 통과한다.
10. 일반 키·캔버스·혼합·예약 없는 동시 요청에서 같은 화질 승자는 하나다. 서로 다른 화질은 각각 접수된다.
11. 같은 일반 키·캔버스 attempt에 화질을 바꾸면 409다. 4k 제출 지문은 정확히 일치할 때만 통과한다.
12. 접수 불명 후 첫 요청이 이미 완료된 반례에서도, 재확인은 기존 키·예약으로 기존 결과만 회수한다. 두 번째 유료 작업을 만들지 않는다.
13. 실제 앞말 구조의 만료 오류에서만 `_fail` 1회, 복구 격리 0회다. 다른 모델·draft job 없음·부분 출력·인자 속 문구·다른 오류는 기존 격리를 유지한다.
14. 작업 ID가 있으면 만료 문구가 함께 있어도 기존 작업 추적 경로를 유지한다.
15. 실제 서버 `/fail` 경로에서 만료 사유가 요청 `failed+terminal_at`와 생성물 실패로 기록된다. 기존 구 에이전트 모호 실패는 계속 격리된다.
16. 새 실패 카드·옛 복구 보류 카드 모두 만료 안내를 표시한다. 같은 캔버스의 오늘 만든 새 드래프트는 오래된 job의 만료에 영향받지 않는다.
