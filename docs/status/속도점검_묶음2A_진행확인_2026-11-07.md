# 속도 점검 묶음 2-A — 생성 완료 확인 박자·보이는 변화 없는 쓰기의 목록 신호·쉬는 중 CLI (2026-11-07)

상위 기록: [전체 속도·자원 점검](속도점검_2026-11-07.md) 묶음 2의 2-1·2-2·2-3·2-4. 에이전트 추적 계약과 알림 계약에 닿아 **중요 작업**(설계 합의 → 구현 → 독립 리뷰)으로 한다.

## 지금 동작(소스 확인, dev `95a80e84`)

1. **완료가 늦게 보인다.** 제출이 끝나면 `execute_pending` 이 빠지고 진행 중 작업은 `tracking_pass` 만 본다. `tracking_pass` 는 대기(`GET /api/agent/wait`, 허브가 25초 붙잡음) 한 바퀴마다 한 번 돈다. 작업마다 처리 중이면 `next_direct_check = 지금 + 30초`(`_DIRECT_CHECK_INTERVAL_SECONDS`). 25초째 바퀴는 아직 30초 전이라 건너뛰고 약 50초째 바퀴에서 본다 → 끝난 생성이 **평균 약 25초·최대 약 50초** 늦게 뜬다. 제출 직후 한 번(아직 처리 중)·그다음 약 50초 뒤 순서.
2. **확인할 때마다 모든 창이 목록 전체를 다시 받는다.** 처리 중 보고 `POST /api/gen-requests/{rid}/reconcile` 은 '라이브러리 바뀜' 판정(`mutation_notify`, 경로 목록에 없음)이고 에이전트는 출처 머리글이 없어 **출처 없는 synced** → 열린 창마다 `reload`. 처리 중 분기(`usecases/gen_requests.py` `_reconcile_request` 1096~)는 `record_request_check`(gen_request 표) + `set_status(gen, "running", note)` — 이미 running·같은 note 면 화면에 바뀌는 것이 없다. 실제 바뀜(note 생김·완료·실패)은 그 분기가 WS `progress` 를 따로 보낸다.
3. **MCP 읽기 동작도 같다.** `POST /client/action`(mcp_v2) 의 read_context·wait_results·get_result·get_generation·show_results·estimate_plan·get_plan 등이 200 이면 출처 없는 synced. 실행(execute)은 내부 호출로 `create_gen_request` 를 불러 HTTP 알림이 따로 없으므로 **그 신호가 새 카드를 알리는 유일한 계기**다(유지해야 한다).
4. **계정 보고**(`POST /api/ingest/account-report`, 공유 서버) 도 보고마다 그 계정 창에 synced. 크레딧은 `credits_changed` 를 따로 보낸다. 라이브러리에 닿는 것은 첫 신원 연결(`_ingest_core` 의 linked_uid) 순간뿐으로 보인다(조사원 보고 — 합의 때 확인).
5. **쉬는 중에도 CLI 를 띄운다.** 대기 바퀴마다 `_begin_account_cycle()` 로 계정 캐시를 비우고 `tracking_pass` 첫 줄이 `_cycle_account_email(cli)` → CLI `account status`(node+hf.exe, 약 470ms) — 할 일이 없어도 약 25초마다(시간당 약 140번). 신원 재확인 자체는 의도된 계약이다(`test_agent_account_snapshot.py` 머리말: CLI 계정 A→B 전환 반례).

## 고칠 안(Claude 설계 v2 — Codex 사전 검토 `01a1b3c1` 반영)

v1 에서 바꾼 것: A 의 대기 계산 범위·소켓 시한·백오프 분리·'최대 15초' 보장 삭제(Codex P2 4건) · B 의 reconcile 판정을 '먼저 읽은 행'에서 '쓰는 문장의 실제 바뀜'으로(Codex P2: 툴팁이 단계·공급자 상태를 그림, 읽기·쓰기 사이 경합) · account-report 는 뺌(Codex P2: 보고마다 프로젝트 자동 편입으로 보이는 목록이 바뀔 수 있다) · MCP 는 정확한 메서드 이름 목록(Codex) · C 의 빈 응답 판정·DB 범위·선조회 비용(Codex P2 2건).

**A. 확인 박자를 대기에 맞춘다.**
- 허브 `GET /api/agent/wait?timeout=<초>`: 선택 인자, 1~25 로 자르고 없으면·잘못된 값이면 25(옛 에이전트 그대로).
- 에이전트: 직전 `tracking_pass` 가 **실제로 처리한 (서버, CLI 계정) 범위**의 메모리 추적 목록에서 가장 이른 `next_direct_check` 까지 남은 시간을 대기 시간으로 쓴다(1~25초, 추적 0건이면 25). 이 계정 값은 대기 계산용 힌트일 뿐 — 다음 패스의 신원 확인을 대신하지 않는다. 다른 계정의 남은 추적 항목은 대기 계산에 넣지 않는다(Codex: CLI 를 B 로 바꾸면 A 의 지난 기한이 계속 1초 대기를 만든다).
- 서버 대기 인자와 소켓 시한은 따로: `urlopen` 시한은 지금 35초 그대로(옛 허브가 인자를 무시하고 25초 붙잡아도 끊지 않는다 — 옛 허브에서는 개선이 없을 뿐).
- 정상 확인 간격 30 → 15초(`_DIRECT_CHECK_INTERVAL_SECONDS`). 실패 백오프는 따로 30·60·120초 그대로(새 상수, 지금 식과 같은 값). 허브가 기록하는 '다음 확인'(`record_request_check(next_seconds=30)`)도 15로 맞춘다(툴팁의 다음 확인 시각이 실제 예약과 같게).
- 기한순 처리·못 본 항목 기한 보존·70% 몫·복구/재조정 최소 1건 시도·시작한 호출의 정상 시한은 그대로. 패스를 15초로 자르지 않는다. **완료 표시 상한은 약속하지 않는다**(패스 초과·64건 예산 때문) — 목표는 불필요한 기다림을 없애는 것(같은 가정의 평균 약 25초 → 약 7.5초 + 조회·보고 비용, 추정).

**B. 보이는 변화 없는 쓰기는 라이브러리 신호를 내지 않는다(판정은 처리 코드, 미들웨어는 표시를 따름).**
- 공통 장치: 처리 코드가 `request.state.library_unchanged = True` 를 세우면 `main.py` 의 `mutation_notify` 가 `DOMAIN_LIBRARY` 만 뺀다(빼는 규칙은 `mutation_notify.py` 의 작은 함수로 두고 시험한다 — `notification_domains` 자체는 그대로). 처리 결과(응답 본문) 모양은 바꾸지 않는다: reconcile 은 라우터가 넘긴 빈 dict 에 유스케이스가 판정을 적는다. 응답의 `X-MVHub-Mutation-Domains` 도 실제로 알린 영역과 같게. 표시가 없으면 지금과 같다. `_proxy.py` 의 위임 경로·`notification_domains` 기본 동작은 그대로(이번 대상 `/api/gen-requests`·`/api/mcp/` 는 일반 중계 제외 경로라 영향 없음 — Codex 확인).
- reconcile 처리 중 반복 보고: **쓰는 그 순간의 원자적 판정**으로 가른다. 두 저장 함수가 각각 한 트랜잭션(`BEGIN IMMEDIATE`) 안에서 읽고·쓰고 결과를 셋 중 하나로 돌려준다 — `changed`(대상이 있고 값이 바뀜) · `same`(대상이 있고 종결 보호에 걸리지 않았으며 원하는 값과 같음 — 확인 시각만 갱신·카드는 쓰지 않음) · `not_applied`(대상 없음·종결 보호: gen_request 는 done/failed/canceled, generation 은 done). `repo.set_status` 는 같은 값이면 쓰지 않는다. `repo.record_request_check` 는 단계·공급자 상태·사유를 비교한다. **둘 다 `same` 이고 이 보고가 `progress` 를 보내지 않을 때(note 없음 = 일반 처리 중)만** 표시한다 — note 가 있는 보고(unknown·action_required)는 `progress(running)` 을 보내므로, 판정 직후 다른 요청이 완료를 저장하면 그 메시지가 완료 카드를 덮을 수 있어 synced 를 남긴다(독립 리뷰 1차 P2). `not_applied` 가 하나라도 있으면 지금처럼 신호 — 이미 done 인 카드에 늦은 unknown/action_required 보고가 와서 note 의 `progress(running)` 이 완료 카드를 덮을 때, 그 synced 가 화면을 DB 값으로 되돌리는 계기다(Codex 2차 P2). queued→running·단계/공급자 상태/사유 변화·완료·실패·되살리기·note 생김은 지금처럼 신호. 이 경우 툴팁의 '마지막 확인 시각' 은 목록 3초 폴링·다음 실제 변화 때 바뀐다(히스토리 보드의 시각 표시는 그때까지 묵는다 — 남는 위험).
- mcp_v2 `client/action`: 아래 정확한 읽기 메서드만 표시 — `read_context`·`get_result`·`get_generation`·`wait_results`·`show_results`·`estimate_plan`·`get_plan`·`request_execution`(지금은 계획 조회). `execute_generation_plan`(내부 `create_gen_request` 라 이 신호가 새 카드의 유일한 계기 — 일부 제출 뒤 attention 반환 포함)·`prepare_generation_plan`·`add_to_canvas`·`import_reference`·모르는 메서드는 그대로 신호.

**C. 쉬는 중 CLI 를 건너뛴다.**
- `tracking_pass` 머리에서: 메모리 추적 목록이 모든 범위에서 비고, 상태 DB 에서 **정규화한 이 서버의 모든 계정·unknown 범위**에 `tracked_job`·`anchor_outbox` 행이 없으면(`_tracked_load(server, None)` 은 unknown 만이라 쓰지 않는다), 복구 후보·재조정 후보 HTTP 를 먼저 본다. **둘 다 200 이고 필드가 실제 빈 list** 일 때만 CLI 없이 돌아간다. DB 조회 실패·401/404/5xx/시한 초과·필드 없음은 쉬는 판정을 하지 않고 지금 경로로.
- 선조회 결과는 같은 패스 안에서 기존 `recovery_probe_pass`·`reconcile_pass` 가 다시 묻지 않게 넘겨 쓴다(같은 서버·같은 요청 범위에서만). 첫 조회에서 후보가 나오면 나머지 선조회는 생략하고 지금 경로로. 후보 HTTP 결과를 CLI 신원으로 쓰지 않는다(AUTH-off 허브에서는 활성 계정 기준이라 — Codex).
- 신원 계약 그대로: `_begin_account_cycle`·push 직전 계정 수집·제출 경로는 바꾸지 않는다. pending 확인·주기 계정 보고도 그대로. 다른 계정의 남은 행 때문에 생략이 안 되는 것은 보수적 비용으로 둔다(행을 지우거나 옮기지 않는다).

## 남는 위험·확인할 것

- A: 추적 1건당 CLI `generate get` 이 지금(실제 약 50초에 1번)의 약 3.3배. Higgsfield 쪽 한도 근거 없음 — 한도 오류가 보이면 간격만 되돌린다(박자 맞추기는 남김). 추적 중 허브 대기 요청이 다음 확인 시각마다로 는다.
- B: 처리 코드가 실제 변경을 빠뜨리고 표시를 세우면 미들웨어는 복구 못 한다 — 표시는 위 두 곳·정확한 메서드 목록에만. 히스토리 보드의 '마지막 확인 시각' 은 실제 변화가 올 때까지 묵을 수 있다.
- C: 선조회 HTTP 비용이 쉬는 바퀴마다 둘(로컬 허브, CLI 1회보다 싸다). 후보가 빈 직후 새 작업은 깨움 신호·다음 바퀴가 맡는다.
- account-report 의 synced 는 이번에 그대로(보고마다 프로젝트 자동 편입 판정이 필요해 따로 설계).
