확실히 작은 완전 충족안은 찾지 못했다.

## 4. A 의 구조

### 4-1. 탭 상태

| 상태 | 조건 | 하는 일 |
|---|---|---|
| 쓰는 탭 | 프로필 잠금(`mvhub-scene-writer`) + 허브가 인정한 임대 토큰 | 편집·배경 쓰기·원래 씬 올리기 |
| 임대 미확인 | 쓰던 탭인데 허브 끊김·갱신 실패·정지/BFCache 에서 돌아옴 | 편집은 IndexedDB 에 계속(지금처럼). 원래 씬 올리기는 멈춘다. 허브가 같은 토큰을 인정하면 잇고, 아니면 '임대 잃음' |
| 넘겨준 탭 | 프로필 잠금만 | 편집·배경 쓰기·허브 올리기 없음. 보드 자리에 "캔버스는 다른 브라우저에서 열려 있습니다 [여기서 열기]" |
| 쉬는 탭 | 프로필 잠금 없음 | 지금 그대로(`CANVAS_OTHER_TAB`) |

- 임대는 **프로필 단위**다 — 메인 탭이 토큰을 쥐고, 분리 캔버스 창은 지금처럼 IndexedDB 에 쓰며 허브 올리기는 메인 탭의 미러가 토큰과 함께 한다.
- 메인이 죽고 분리 창만 남으면 그 창은 **로컬 전용**이다(IndexedDB 에만 쓰고 허브에는 안 올린다 — 토큰이 없다). 그 프로필에 메인이 다시 뜨면 `claim` → 맞추기가 그 편집을 올린다
  (그사이 다른 브라우저가 임대를 쥐었으면 그 편집은 이 브라우저에 남아 있다가, 다시 넘겨받을 때 맞추기의 '먼저 올리기'에서 사본이 된다).
- **옛 인계에 새 판을 붙이지 않는다.** 분리 창의 인계(`handover:true`)에는 그 창이 연 때의 임대 세대를 싣는다. 메인의 지금 세대와 같을 때만 원래 씬에 넣고,
  다르면(그사이 임대를 잃었다 되찾음) 원래 씬을 바꾸지 않고 `[옛 창]` 로컬 사본으로 넣는다 — 되찾은 뒤 받은 다른 브라우저의 내용을 현재 토큰으로 덮지 않게.
- '임대 잃음'을 안 순간: 밀린 연산은 지금 '캔버스가 다른 창에 떴다'와 같은 길(`setAsidePendingWrites`)로 `[옛 창]` 사본. 확정했지만 못 올린 씬은 이 브라우저 IndexedDB 에 그대로 있다가
  다시 넘겨받을 때 맞추기의 '먼저 올리기'로 들어간다(허브가 그사이 바뀌었으면 사본). 화면은 넘겨준 탭.

### 4-2. 허브 임대 (새 · 허브 메모리)

- 열쇠 = 계정 범위 + 계정 전환 세대(전환마다 +1 — A→B→A 로 이름이 같아져도 옛 토큰은 무효). 값 = {토큰(무작위), 허브 부팅 id, 탭 id, 받은 시각, 마지막 갱신, 넘겨 달라는 탭}. DB 에 적지 않는다.
- `POST /api/scenes/writer` {action, tab, token}: `claim`(비었거나 만료면 새 토큰) · `renew`(20초마다) · `release`(pagehide 의 sendBeacon — 최적화일 뿐 결과를 믿지 않는다) ·
  `request`(넘겨 달라 — WS `scene_writer_want`) · `claim`+`force`(5초 뒤 — WS `scene_writer_changed`) · `status`(받는 탭이 1초마다 5초까지 본다 — WS 를 믿지 않으려고).
- 만료 90초. 숨은 탭 타이머는 늦춰지고 정지된 탭은 아예 안 돈다 — 그래서 만료는 '죽었을 수 있음'의 표시일 뿐이고, 판정은 **토큰**으로 한다. 정지에서 돌아온 탭은 첫 일로 `renew` 해 보고, 거절이면 '임대 잃음'.
- **토큰 검사와 DB 반영은 계정별 잠금 하나 안에서 한다** — 검사 직후 강제 인계가 끼어 앞 요청이 늦게 반영되는 길을 막는다. 허브가 다시 켜지면 모든 토큰이 무효 → 탭은 새로 `claim` 하고 **맞추기를 다시** 한 뒤에 원래 씬을 쓴다.
- 원래 씬 올리기(`PUT /api/scenes/backup` + 머리글 `X-MVHub-Scene-Writer: <토큰>`): 토큰이 맞을 때만 쓴다. **토큰이 없거나 틀리면 409, 아무것도 안 쓴다**(새 판 배포 전부터 열려 있던 옛 판 탭 포함 — 그 편집은 그 프로필 IndexedDB 에 남아 있다가, 새 판으로 다시 열 때 그 프로필이 이미 합류했으면 맞추기로, 합류 전이면 '허브 전 사본'(수동 복구)으로 간다 — 5장).
- 토큰 없이 허브에 쓰는 길은 없다(Jay 가 처음 합치기를 빼서 2차 설계의 '보존 올리기'와 쓰는 탭의 '새 행 찾기'는 필요 없어졌다 — 허브 행은 쓰는 탭만 만든다).
- MCP 캔버스 추가: 표식이 켜진 허브는 옛 완료 API(`routers/mcp_v2.py:1301`)를 토큰 없이 받지 않는다. 완료는 씬 올리기 요청에 실어 그 씬이 **원래 id 로 `saved`** 된 같은 트랜잭션에서만 확정한다
  (`copied`·`too_big`·지움 충돌은 완료가 아니다 → 작업은 대기로 남아 쓰는 탭이 다시 붙인다). 완료 영수증이 허브에 남으므로 사용자가 카드를 지운 뒤 다시 붙지 않는다.
  뜻으로는 '그 원래 행에 필요한 처리 영수증이 같은 트랜잭션에서 확인됨'이다 — 이미 저장돼 `same` 으로 온 재시도도 영수증이 확인되면 완료(구현 계획에서 시험으로 정한다).
- 표식 `scene_writer_v1`(AUTH off 허브만). 표식이 없으면 지금 동작 그대로.

### 4-3. 넘기기

1. 받는 탭: [여기서 열기] → `request`.
2. 쥔 탭: ① 새 입력·새 배경 작업 시작을 막는다 ② 분리 캔버스 창이 떠 있으면 지금의 돌려받기로 먼저 거둔다 ③ `settleSceneWrites(…, flushPending)` — 입력 대기·끌기까지 내보내 확정
   ④ 2초 묶음을 기다리지 않고 바로 올리고 **허브 확인**을 받는다 ⑤ 토큰으로 `release`. 하나라도 실패하거나 5초를 넘기면 '정상 인계'로 알리지 않는다.
3. 받는 탭: 풀림(또는 5초 뒤 `force`) → `claim` → 4-4 맞추기 → **깨끗한 한 바퀴가 끝나야 편집이 풀린다**(지금 `promoteToWriter` 의 '다시 읽기 성공 뒤 풀기'와 같은 규칙).
- 화면 문구를 둘로 나눈다: "넘겨받았습니다" / "강제로 넘겨받았습니다 — 다른 브라우저의 마지막 편집은 그 브라우저를 다시 열 때 `[옛 창]` 탭으로 들어옵니다".
- 다른 브라우저가 닫혀 있으면(흔한 경우) 1~2 없이 켜자마자 `claim` → 맞추기.

### 4-4. 맞추기 (임대를 새로 받을 때마다 · 허브 재시작·정지 복귀 뒤 포함)

네트워크는 저장소 큐 밖에서 하고, 로컬에 넣는 것만 큐(저장 계약 규칙 5)에 조건부 연산으로 넣는다(큐 안에서 네트워크를 기다리지 않는다 — 자기 대기 방지).

1. 고정: 씬마다 (로컬 글자, 판) 한 쌍 · 로컬 지움 표시 · 순서와 순서 판.
2. 올리기(토큰): 판 이후 바뀐 씬은 판과 함께 — 허브 판이 다르면(다른 브라우저가 고침) 사본 행. 지움 표시는 판과 함께 — 허브 판이 다르면 지우지 않는다(편집을 살림). 순서는 순서 판과 함께 — 다르면 허브가 합친다(허브 순서 + 모르는 id 뒤에, 중복·없는 id 정리).
   - **판 역행·행 소실·이력 바뀜**(허브 DB 를 옛 백업으로 되돌림·새 DB): 허브 `scene_history_id` 가 판의 것과 다르거나, 허브 rev 가 판보다 작거나, (history, rev) 는 같은데 지문이 다르거나, 판이 있는데 행이 없으면
     '판 모름'으로 본다 — 로컬 = 판 내용이면 로컬을 다시 올리고(지금 미러가 사라진 행을 다시 넣는 것과 같다, `sceneBackup.ts:482`), 로컬·허브가 서로 다르면 사본.
3. 허브 목록을 **다시 받는다**(올린 결과가 반영된 상태).
4. 받기(조건부 연산, 결과는 '실제로 넣었나'로 돌려준다 — 규칙 6):
   - 허브에만 있는 살아 있는 씬 → 없을 때만 더한다.
   - 로컬이 고정한 글자 그대로이고 허브 판이 앞섰다 → 허브 것으로 바꾼다.
   - 2에서 사본으로 간 씬 → 원래 id 는 허브 것으로, 내 내용은 사본 행 id 의 새 탭(`[옛 창] 이름`)으로.
   - 허브 지움 표식 + 로컬이 판 그대로 → 지운다.
   - 순서: 로컬 순서가 고정 뒤 그대로면 허브 순서로.
5. 건너뛴 연산·일부 묶음 실패·계정/토큰 변경이 하나라도 있으면 1부터 다시(3번까지). 그래도 안 되면 넘겨준 탭에 머물며 오류 + [전체 내보내기].
- **못 올리는 씬(5MiB 초과 — `too_big`)**: 판 이후 바뀌었는데 올리지 못한 씬은 '실패'로 치지 않고, 4의 바꾸기 **전에 같은 트랜잭션에서** 내 내용을 새 id 의 로컬 전용 `[옛 창]` 탭('백업 안 됨' 표시)으로 남긴 뒤
  원래 id 를 허브 것으로 맞춘다(되돌리기 기록 없이 덮이지 않게). 넘기기(4-3 ④)의 허브 확인 대상에서 빼고, 넘기는 쪽 안내에 "이 브라우저에만 남는 씬 N개"를 띄운다.
- 판은 **로컬에 실제로 넣은 것만, 그 연산과 같은 트랜잭션에서** 바꾼다(4-5 의 IndexedDB 판).
- 같은 id 로 받는 씬은 Comfy 실행 상태·진행 중 생성 표식을 그대로 둔다 — 새 브라우저에서 생성·Comfy 복구가 이어진다(`mergeScenesFromBackup` 처럼 빼지 않는다). 새 id 사본은 지금 사본 규칙대로 뺀다(7장 경계).
- 받은 씬의 되돌리기 기록은 지문이 어긋나 이어지지 않는다(지금 동작).

### 4-5. IndexedDB 에 더하는 것 (프로필)

- **지움 표시** `["d", 버킷, id]` = {의도 id, 판}: 버킷에서 씬 키가 빠지는 그 트랜잭션에서 같이 쓴다 — 올리기 전에 꺼져도 다음 맞추기가 되살리지 않는다.
  - 허브: 이미 지움 표식이면 판과 무관하게 '지워짐'으로 답한다(응답 유실 뒤 재시도도 성공). 살아 있는데 판이 다르면 지우지 않고 '남김' — 로컬은 표시를 거두고 그 씬을 다시 받는다(편집을 살림).
  - 확인은 **같은 의도 id 의 표시만** 거둔다.
  - **명시적 되살리기 의도는 내용이 같아도 남는다.** 사용자가 지운 씬을 되돌리면 그 트랜잭션이 지움 표시를 **되살림 표시** `["r", 버킷, id]` 로 바꾼다. 되살림 표시가 있는 씬은
    판과 내용이 같아도 '올릴 변경'이고, 허브가 지움 표식이면 쓰는 탭의 되살림 올리기로 되살린다(새 rev). 허브 확인 뒤에만 표시를 거둔다. 허브가 아직 살아 있으면 표시만 거둔다.
- **판** `["b", 버킷, id]` = {rev, 지문}: 맞추기·올리기 결과를 씬과 같은 트랜잭션에서. 옛 localStorage 판 장부는 지우지 않고 읽지도 않는다(시작·합류가 판을 새로 쓴다 — 5장).
- **순서 판·미전송 표시**: 순서가 바뀌는 그 트랜잭션에서.
- 미러 묶음에 **최대 대기 10초**(지금은 변경마다 2초를 다시 재 계속 고치면 무한히 미뤄진다).

### 4-6. 허브 저장 (로컬 `scene_backup` 확장)

- `rev`(정수, 쓰기·지우기·되살리기마다 +1)와 `deleted_at` 칸. 새 계약의 판은 (`scene_history_id`, `rev`, 지문) 셋이다(지문만으로는 '지웠다 같은 내용으로 다시 만듦'을 못 가르고, rev 만으로는 DB 복원을 못 가른다).
  `scene_history_id` 는 허브 DB 안에 만든 무작위 값이다.
- **옛 허브가 바꾼 행 알아보기·되살리기**(공개판으로 되돌려 쓴 경우 — 7장): `scene_backup` 에 `rev_hash` 칸(새 허브가 그 rev 를 쓸 때의 지문)을 둔다. 옛 허브는 `data`·`data_hash` 만 바꾸고
  `rev`·`rev_hash`·`deleted_at` 은 모른다 → `data_hash ≠ rev_hash` 인 행 = 옛 허브가 고친 행. 그리고 공책이 시작된 계정에서는 DB **트리거**가 옛 허브의 덮어쓰기(`rev` 그대로·지문 바뀜)와
  행 삭제 **직전 내용**을 '시작 전 보관'과 같은 보관 표에 사유 `legacy_overwrite`/`legacy_delete` 로 남긴다. 두 보관은 따로다 —
  덮어쓰기는 **새 판이 쓴 내용을 처음 덮을 때만**(직전 `data_hash = rev_hash` 일 때 — 되돌린 동안 편집마다 쌓이지 않게, 그 뒤 옛 판 편집은 옛 앱 쪽에 있다),
  삭제는 **늘** 직전 내용을 남긴다(앞선 덮어쓰기 보관 때문에 빼지 않는다). 중복은 (계정, 프로젝트, 씬, `scene_history_id`, 사유, 내용 지문)이 같을 때만 한 번으로 친다.
  예: 새 판 `X` → 옛 판에서 `Y` 로 고침(X 보관) → 옛 판에서 지움(Y 보관) — X·Y 모두 남는다.
  새 허브는 맞추기 목록을 줄 때 먼저 정리한다: 옛 허브가 고친 살아 있는 행은 그 내용을 그대로 두고 rev+1·`rev_hash` 를 맞추며, 트리거가 남긴 직전 내용이 지금과 다르면 `[옛 창]` 사본 행으로 살린다 ·
  옛 허브가 고친 지움 표식 행은 되살린다(편집을 살림) · 옛 허브가 지운 행은 지운 채로 두되 직전 내용은 보관 표에 남는다. 이 정리는 **허브가 시작할 때 한 번** 하고(다른 새 허브 쓰기가 먼저 와서
  `data_hash ≠ rev_hash` 표시를 지우지 않게), 맞추기 목록 전에도 남은 것이 있으면 한다. 새 허브 자신은 `scene_backup` 행을 물리적으로 지우지 않는다 — 예외는 공책 시작 확정(살아 있는 행 전부를 '시작 전 보관'에 복사한 뒤 교체 — 그 시점엔 공책이 없어 트리거가 돌지 않는다), 계정 정리(공책 행 → `scene_backup` → 보관 행 순서로
  같은 트랜잭션에서 지워 트리거가 보관 행을 다시 만들지 않게)와 리맵의 물리 삭제('둘 다 지움 표식 → 하나', '살아 있음+살아 있음 → 옮겨 오는 쪽을 사본으로 옮긴 뒤 원래 행 삭제') —
  리맵 때 트리거가 숨은 보관 행을 하나 더 남길 수 있으나 잃는 것은 없다. 정리가 보관본으로 `[옛 창]` 사본을 만들 때 사본 id 는 (원래 id, 보관본 지문)으로 고정하고 쓴 보관본에 표시해, 되돌리기를 여러 번 해도 같은 사본이 다시 생기지 않게 한다.
  공책을 확정할 때(브라우저 시작·빈 브라우저·복원) 모든 살아 있는 행의 `rev_hash = data_hash` 로 맞춘다 — 비어 있으면 첫 덮어쓰기 보관이 빠진다.
  공개판에서 계정 정리를 했다면 그 계정 씬의 직전 내용이 DB 보관 표에 남는다(개인 자료) — 새 판에서 같은 계정 정리를 다시 하면 지워진다(7장 경계).
- **되돌리기 호환 고정**: 판의 지문 = `scene_backup.data_hash`(새 칸에 두지 않는다) · IndexedDB `DB_VERSION` 2·`layout` 2 그대로(새 키는 같은 `kv` 저장소) · `release/compatibility.json` 의 protocol·db_schema 그대로 ·
  기존 표의 기본키·유일키 그대로(칸·표·트리거 추가만). 옛 스키마 검사기는 칸이 더 있어도 통과한다(`schema_compat.py:381`, 분리 Claude 세션 확인) — 트리거가 옛 검사기·옛 허브 시작을 막지 않는지는 c15 로 실측한다.
- **복원·교체된 DB 는 이전 쓰기 이력과 구분된다.** 이 앱이 하는 DB 복원·교체(작업자 백업 복원·DB 교체/병합 도구·계정 리맵)는 끝에 새 `scene_history_id` 를 만든다.
  그 밖의 길로 옛 DB 가 돌아온 경우도 잡도록, 쓰는 탭의 조건부 쓰기는 rev 와 **지문이 둘 다** 판과 같을 때만 받고, 맞추기는 (history, rev) 가 같은데 지문이 다르면 '판 모름' 재조정으로 본다.
- 지우기 = 표식(글자는 남김) + MCP 대기 작업 취소를 한 트랜잭션에서. 표식 행에 판이 맞는 쓰는 탭의 올리기만 되살린다. 그 밖은 사본.
- MCP 캔버스 추가 대상 확인(`repo/mcp_v2.py:200-203` 의 직접 SQL)도 같은 쓰기 트랜잭션 안에서 `deleted_at IS NULL` 을 본다 — 옛 GET 필터와 별개의 필수 변경.
- 옛 `GET /api/scenes/backup` 은 **살아 있는 행만** 준다(옛 앱의 자동 복구·가져오기·MCP 조회가 지운 씬을 되살리지 않게). 새 맞추기 목록은 표식·rev 까지 준다.
- 탭 순서 표(새, 계정·프로젝트마다 1행: id 목록·rev).
- MCP 캔버스 추가 완료(`done`)는 그 카드를 담은 씬 올리기와 **같은 요청·같은 트랜잭션**에서 처리한다 — 카드가 허브에 남기 전에 완료로 끝나 강제 인계 뒤 카드가 사라지는 길을 막는다.
- 계정 리맵(두 신원에 같은 씬 id): 살아 있음 + 살아 있음, 내용 다름 → 옮겨 오는 쪽을 새 id 사본으로(지우지 않는다 — 지금 `ignore_del` 의 '손실 무해' 전제가 깨진다) ·
  살아 있음 + 지움 표식 → 살아 있는 쪽이 이긴다 · 둘 다 표식 → 하나. 리맵 뒤 그 계정의 rev 는 새로 매기고 `scene_history_id` 를 바꿔 모든 브라우저가 '판 모름' 재조정을 한다.
  MCP 대기 작업은 살아남은 원래 id 를 가리킨다(사본에는 없다). 순서 표는 합친다. 계정 정리에도 새 표를 넣는다.
- 작업자 백업 요약은 살아 있는 씬 수와 보존 행 수를 나눠 센다.
- 새 사본 이름은 앞에 `[옛 창] `. 이미 있는 `bk_` 행은 허브 공책 시작 때 '시작 전 보관'으로 옮겨진다(5장).
- 공책 id(계정별)·시작 칸(시작 시도 id 별)·'시작 전 보관' 표(새). 보관 표는 지움 표식과 따로다 — 지움 의도(되살리기·지움 충돌 규칙)와 섞이지 않게.
- 표 추가는 `schema.sql` + `db_migrations.py` 의 `IF NOT EXISTS`/ALTER, baseline 이름표는 쓰지 않는다(옛 검사기가 막는다).

## 5. 허브 공책 시작 (처음 합치기 없음 — Jay 2026-11-09)

- 지우는 것 없음: 각 프로필의 IndexedDB 내용(아래 '허브 전 사본')·옛 localStorage `ch.scenes`·옛 판 장부·허브의 기존 행을 지우지 않는다.
- 허브는 계정마다 **공책 id**(`scene_notebook_id`)를 둔다. 공책 id 는 쓰기 이력 `scene_history_id`(4-6)와 따로다 — '처음 합류했나'는 공책 id 로, '판이 맞나'는 history 로 본다.
- **허브 공책 시작** — 계정에 공책 id 가 없을 때, 새 판으로 처음 임대를 받은 브라우저의 캔버스가 허브 공책이 된다.
  - 그 브라우저는 씬·탭 순서를 **시작 칸**(살아 있는 행과 다른 곳, 시작 시도 id 로 묶음)에 올린다. 여러 요청으로 나눠도 살아 있는 행은 그동안 그대로다.
  - 마지막 요청에서 허브가 한 트랜잭션으로 **확정**한다: 토큰·계정·시작 시도 id·받은 개수가 맞고 공책 id 가 아직 없을 때만 —
    ① 지금 살아 있는 행 **전부**(시작 브라우저와 같은 id 의 다른 내용 포함)를 '시작 전 보관' 표(숨김, 지움 표식과 따로)에 복사 ② 살아 있는 행을 시작 칸 내용으로 바꿈
    ③ 공책 id 를 만들고 ④ 숨긴 씬에 걸린 MCP 대기 작업을 '씬 숨김으로 취소'(완료 아님, 다른 씬에 붙이지 않음). 같은 시도의 재시도(응답 유실)는 같은 확정 결과를 돌려받는다.
  - 끊기면 확정이 없으니 아무것도 바뀌지 않는다. 다음 임대자가 새 시도로 처음부터 한다(끊긴 시도의 시작 칸은 버린다).
  - **빈 브라우저는 공책이 되지 않는다**: 씬이 하나도 없는 브라우저가 먼저 임대를 받으면, 확정된 살아 있는 행(지금까지의 미러)을 그대로 공책으로 확정한다(시작 칸은 쓰지 않는다 — 끊긴 시도의 반쪽은 공책이 될 수 없다).
  - 운영: 새 판 첫 실행은 평소 쓰는 앱 창으로 연다. 다른 브라우저를 먼저 열면 그 브라우저 캔버스가 공책이 된다 — 그래도 앱 창의 캔버스는 아래 '허브 전 사본'으로 남아 꺼낼 수 있다.
- **처음 합류** — 이 프로필이 아직 어느 공책에도 합류한 적 없을 때만. 합치지 않는다. 한 트랜잭션에서 ① 그 브라우저의 지금 캔버스 전부를 IndexedDB **'허브 전 사본'** 칸
  (계정·공책 id 마다 따로, 있으면 덮지 않는다)에 남기고 ② 씬·순서를 허브 공책으로 바꾸고 ③ 판·'합류함'(계정·공책 id)을 쓴다. 꺼져도 트랜잭션 전이면 그대로, 뒤면 표시가 있어 다시 하지 않는다.
  - 설정 → 캔버스 자료에 "허브로 바꾸기 전 이 브라우저 캔버스 N개 [내려받기]" 한 줄. 파일은 지금 형식(`mvhub-scenes-full` v1)이라 지금의 [전체 가져오기](덮지 않고 더함·다르면 `[사본]`)로 다시 넣을 수 있다
    — 다만 가져오기는 Comfy 실행 상태를 빼므로 진행 중 실행의 연결까지 되살리지는 않는다(`sceneArchive.ts:142`).
- **이미 합류한 프로필**은 공책 id·history 가 바뀌어도(DB 복원·계정 리맵) 다시 합류하지 않는다 — 4-4 의 '판 모름' 재조정으로 간다(미전송 편집은 먼저 올리기, 허브와 다르면 사본). '허브 전 사본'은 다시 쓰지 않는다.
  history 가 바뀐 '판 모름'에서 **로컬이 판 내용 그대로인 씬은 올리지 않는다** — 허브에 행이 있으면 허브(복원본) 것을 받고, 행이 없을 때만 다시 올린다(고치지 않은 씬마다 사본이 생기지 않게. 2·3단계 리뷰 P2-5 결정).
- **이미 합류한 프로필이 공책 없는 허브를 만나면**(같은 주소 허브의 데이터 초기화·재설치, 표식이 꺼진 동안 공책 없는 옛 DB 복원 등): 허브에 살아 있는 행이 있으면 빈 브라우저 규칙처럼 그 행들을 공책으로 확정하고,
  허브가 비어 있으면 이 프로필의 캔버스로 시작한다. 그 뒤는 맞추기로 간다(이 프로필의 판 이후 편집은 먼저 올리기 → 다르면 사본). 다시 합류하지 않고 '허브 전 사본'도 다시 쓰지 않는다(2·3단계 리뷰 P1 결정).
- **시작할 캔버스에 5MiB 넘는 씬이 있으면** 시작을 확정하지 않는다(일부만 공책으로 만들지 않는다). 원본은 그대로 두고 어느 씬이 넘는지 알린다. 상한을 몰래 늘리거나 그 씬만 빼고 성공으로 치지 않는다
  (2026-11-09 실측: 릴리스 DB 씬 3개·최대 약 577KB — 지금은 해당 없음). 중단되면 임대를 풀고 그 브라우저는 '허브 꺼짐'과 같은 로컬 편집 상태로 둔다(큰 씬을 줄일 수 있게) — 안내에 넘는 씬 이름을 띄운다.
- **DB 복원은 첫 시작이 아니다**: 이 앱의 복원 길(작업자 백업 복원·DB 교체, `routers/db_transfer.py:412`)은 복원한 뒤 새 history 를 만들고, 복원한 DB 에 공책 id 가 없으면
  **복원한 살아 있는 행을 그대로 공책으로 확정**한다(브라우저가 자기 캔버스로 다시 시작해 복원 자료를 숨기지 않게).
- 합류한 뒤로는 4-4 맞추기 그대로다. 옛 판 장부(지문)·1A 갈래(`fork`)는 읽지 않는다 — 시작·합류가 판을 새로 쓰기 때문에 이관 규칙이 필요 없다.

## 6. 완료 조건 (격리 허브·격리 프로필)

1. 브라우저 1에서 편집·탭 순서 변경·삭제 → 닫음 → 브라우저 2를 열면 같은 씬·순서·내용, 지운 씬 없음.
2. 둘 다 열림: 2는 [여기서 열기] → 5초 안 **정상 인계**: 1의 입력 대기·끌기 중 편집까지 2에 보인다. 정상 인계와 5초 뒤 강제 인계를 따로 판정한다.
3. 1의 브라우저 프로세스를 강제 종료 → 2에서 강제 인계 → 2에서 같은 씬을 고침 → 1을 다시 켬: 1의 확정된 미전송 편집은 `[옛 창]` 탭, 원래 씬은 2의 내용. 확정된 것 중 잃은 씬 0(확정 전 입력은 약속하지 않는다).
4. 씬 삭제를 확정한 직후(미러 전) 강제 종료 → 다시 켜도 그 씬이 돌아오지 않는다.
5. 경합: 인계 중 세 번째 브라우저 취득 · 계정 A→B→A · 허브 재시작 · BFCache 복귀 · 분리 창만 살아 있음 · 강제 인계 직후 옛 쓰는 탭의 늦은 올리기·순서·release — 원래 씬을 바꾸지 못한다.
6. 진행 중 생성·Comfy 실행·MCP 완료 직전 인계 → 새 브라우저에서 카드와 결과 연결까지 이어진다.
7. 실패 주입: 올리기 성공 후 응답 유실 · 일부 묶음 성공 후 실패 · 로컬 반영 중단 · 판 저장 실패 뒤 재시작 — 다음 맞추기가 바로잡고 잃는 것 없음.
8. 허브 공책 시작: 프로필 3개에 서로 다른 캔버스 → 새 판을 앱 창으로 먼저 켬 → 그 캔버스가 허브 공책(그 전 허브 행은 같은 id 의 다른 내용까지 '시작 전 보관', DB 에 남음) →
   다른 프로필을 켜면 허브 공책이 보이고, 그 프로필의 이전 캔버스는 [내려받기] → [전체 가져오기]로 되살릴 수 있다. 옛 저장소 그대로. 따로 판정할 순서:
   ① 시작 중 첫 묶음만 올리고 끊김 → 빈 브라우저가 임대 → 반쪽이 공책이 되지 않음 ② 마지막 요청 응답 유실 → 재시도가 같은 확정 결과
   ③ 합류한 프로필이 있는 채 DB 복원·계정 리맵(history·공책 id 바뀜) → 다시 합류하지 않고 재조정, '허브 전 사본' 그대로
   ④ 공책 id 없는 옛 DB 를 복원 → 복원한 행이 공책이 되고 브라우저가 숨기지 않음 ⑤ 숨긴 씬에 MCP 대기 작업 → '씬 숨김으로 취소'.
9. 허브를 끈 채 쓰는 탭에서 편집 → 저장 실패 경고 없이 계속 → 허브를 켜면 새 토큰·다시 맞추기 뒤 자동으로 올라간다.
10. 새 판 배포 전부터 열려 있던 옛 판 탭의 올리기는 409, 원래 씬 그대로. 그 탭의 편집은 그 프로필이 아직 합류 전이면 '허브 전 사본'(수동 복구)으로, 이미 합류했으면 다시 열 때 맞추기로 들어온다.
11. 작업자 백업·복원(옛 DB 포함)·계정 리맵 뒤 표식·순서·사본이 그대로.
12. 편집 1회 화면 반영·저장 확정이 10-07 실측(0.2ms·약 4ms)과 같은 범위. 바뀐 씬 10개(각 150KB) 맞추기 1초 안.
13. 표식 없는 허브·공유 서버 직접 접속(AUTH on)은 동작 변화 없음. 기존 시험 전부 통과.

## 7. 실패 경계 (약속하지 않는 것)

- 한 PC·한 설치 폴더·한 계정 안만. 다른 설치 폴더는 DB 가 달라 그대로 따로다.
- 5MiB 넘는 씬은 브라우저 사이에 오가지 않는다('백업 안 됨' 표시 유지). 상한은 실측 뒤 따로.
- 강제 인계·허브 재시작 경합에서는 `[옛 창]` 탭이 생길 수 있다(잃지는 않는다).
- 브라우저가 죽으면 마지막 미러 뒤의 확정된 편집(최대 대기 10초 + 재시도 중인 것)은 그 브라우저를 다시 열 때 들어온다. 확정 전 입력은 지금처럼 잃을 수 있다.
- 새 id 사본(`[옛 창]` — 강제 인계·허브 재시작 경합에서 생긴다)의 진행 중 생성·Comfy 실행은 그 카드에 **자동으로 다시 붙지 않는다**. 대신 사본의 `backupForkOf` 에
  원래 씬·카드·실행/생성 시도 id 를 남겨(다시 실행하지 않는 참조) 결과를 찾을 길을 둔다. 생성물은 라이브러리에, Comfy 결과는 허브 실행 기록(`comfy_canvas_run`)에 남는다.
  실행 표식이 허브에 오르기 전에 강제 인계가 일어나면 원래 id 쪽도 자동으로 이어지지 않을 수 있다.
- **다른 브라우저의 예전 캔버스는 자동으로 합쳐지지 않는다(Jay 결정).** 그 브라우저를 새 판으로 열면 허브 공책으로 바뀌고, 예전 것은 그 브라우저 안 '허브 전 사본'으로만 남는다(꺼내려면 [내려받기] → [전체 가져오기]).
  수동 가져오기는 진행 중 Comfy 실행의 연결까지 되살리지 않는다. 허브의 '시작 전 보관'은 화면에 다시 꺼내는 길이 없다(DB 에만 남는다). 열지 않는 브라우저는 그대로다.
- 옛 판 탭의 편집은 새 판으로 다시 열기 전까지 안 들어오고(그 프로필이 합류 전이면 그때도 '허브 전 사본'으로만 남는다 — 수동 복구),
  **옛 판 탭에서 지운 씬은 새 판이 지움 표시를 모르므로 다시 나타날 수 있다**(잃는 쪽이 아니라 되살아나는 쪽).
- 메인이 닫히고 분리 창만 남은 동안의 편집은 그 프로필에 메인이 다시 뜰 때까지 허브에 안 올라간다.
- **옛 판(공개판)으로 되돌려 쓰는 것은 막지 않는다**(DB 쓰기 프로토콜을 올리지 않음 — 올리면 공개판으로 되돌리기가 깨진다, 저장 계약 '남은 한계'와 같은 판단). 옛 허브는 지움 표식·rev 를 모르므로
  되돌린 동안 지운 씬이 다시 보이거나 옛 앱이 원래 씬을 덮을 수 있다. 덮이거나 지워지기 직전 내용은 DB 트리거가 보관하고, 새 판으로 돌아오면 `rev_hash` 로 옛 허브가 고친 행을 알아 정리한다(4-6) —
  잃지는 않고, 되살아나거나 `[옛 창]` 사본이 생기는 쪽이다. 옛 허브가 지운 씬은 지운 채로 두고 직전 내용은 DB 보관 표에만 남는다(화면에 꺼내는 길 없음).
  공개판에서 계정 정리를 했다면 그 계정 씬의 직전 내용도 DB 보관 표에 남는다(개인 자료) — 새 판에서 같은 계정 정리를 다시 하면 지워진다.
- 되돌리기 기록·지금 연 탭은 브라우저마다 따로다(카메라는 씬 안에 있어 따라온다).
