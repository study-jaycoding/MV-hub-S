# 리졸브 패널 — 기존 빈을 보존하고 없는 빈만 추가

## 선택 근거와 한계

- 별도 Codex `priority_db_design_review`가 실제 호출과 시험을 읽어 **② 패널 자동 재정렬을 없애고 없는 빈만 추가**를 추천했다. 총괄도 `_panel_episode_bins`, `panel_operation`의 복구 관문·현재 빈 복귀, 기존 시험과 프런트 응답 계약을 읽었다.
- 기존 기록의 실사용 보고에서는 MoveFolders 뒤 API 순서는 맞았지만 왼쪽 목록은 새 빈을 아래에 보였다. 이번에 실제 Resolve에서 재측정한 결과가 아니다. ① 뒤 빈을 새로 만드는 안은 ID·내용 이동·삭제가 필요하며 왼쪽 이름순 달성도 기존 문서의 미검증 추정이다.
- ②는 **왼쪽 목록 이름순을 해결하는 안이 아니다.** 현재 기존 빈·클립·ID를 보존하며, 새 빈이 끝에 추가되는 모양을 받아들인다. 패널 target에서 불필요한 저장·DRP 백업·이동·재생성을 제거하는 것이 목표다. 보내기 경로의 공통 정렬과 기존 복구 차단은 유지한다.
- 패널이 남긴 순서 어긋남을 다음 **[보내기]**의 기존 정렬이 처리할 수 있어, 그때의 저장·DRP·MoveFolders 및 드문 복구 실패 위험은 남는다. 기존 미복구 기록을 이번 변경으로 자동 해제하지 않는다.

## 검증 계획

기존 가짜 MediaPool/Project 시험을 재사용해 target의 부작용을 감시하고 기존 빈 ID·클립·자식 보존, 새 빈 생성·재호출, 현재 빈 복귀, 부분 실패·프로젝트 변경·복구 대기를 확인한다. 실제 프로그램의 왼쪽 목록·속도·NAS 파일은 이번 격리 시험으로 확인했다고 쓰지 않는다. 구현 후 별도 Claude 독립 리뷰와 관련 시험 근거를 연결한다.

## 설계 합의 (11-13)

- 실제 Claude `mvhub-design` 새 세션 `81a7dcc9-49fc-4dd7-b111-1a9fcb66b917`, 요청 Fable/high·실제 `claude-fable-5-2`가 위 계약 그대로 동의했다. 도구 없는 고정 원문 검토이며 총괄이 입력3파일 SHA256 전후 동일을 확인했다. 역할·ponytail은 제공 본문/훅 적용이라는 상대 보고이고 실제 추론 수준은 미확인이다.
- 기존 패널 재정렬 시험은 보존·선택·실패 조건으로 고쳐야 하며 조용히 지우지 않는다. 생성 중 프로젝트 전환 및 같은 이름 다른 빈으로 복귀하지 않는 경계도 확인한다. 공통 `_reconcile_folder_tree`와 보내기 시험은 유지한다.
- 총괄은 Claude 반례 후보의 `_create_tree`, `_desired_tree` 호출, `_reconcile_folder_tree`의 없는 경로 생성과 `useResolvePanel`의 `order_error` 소비를 대조했다. 제품 변경은 기존 fallback 생성 루프를 자연순으로 실행하는 최소안으로 시작하고, 성능 회귀가 확인되면 새 이유·근거로 범위를 다시 검토한다. 기존 실기기 300형제/9.5초 주석을 이번 패널 변경의 측정 결과로 쓰지 않는다.
- 추가 소스 확인에서 `_subfolder`의 이름 경합 정리도 `DeleteFolders`를 부르는 것을 찾았다. 같은 Claude 설계 세션은 기존 계약 SHA 그대로 `cleanup_duplicate=True` 기본값을 두고 target의 관리 루트·컷·일반 목적지 생성 세 지점만 False로 하는 최소안에 동의했다. 보내기 등 다른 호출은 기본값을 유지한다. 별도 독립 리뷰가 아닌 설계 보완이며, 요청 Fable/high·실제 claude-fable-5-2, 도구 0회·고정 발췌 검토, 총괄이 호출 전후 resolve_bridge.py 원시 SHA256 동일을 확인했다.
- 이름 경합에서는 삭제 0을 우선한다. API가 만든 빈 사본은 실패로 알리고 남기며, 다음 target은 원래 이름의 winner를 찾아 사본을 더 만들지 않아야 한다. 계약의 ‘중복 빈 생성’ 실패 조건은 정상 반복과 이 재시도를 뜻한다. **경합 때 남은 빈 사본은 사람이 정리해야 하며, keep_current=False의 실패에서는 현재 빈이 그 사본에 머물 수 있다.** 컷 반복문의 응답은 기존대로 실패 경로만 담는다.
- 경합 시험은 DeleteFolders의 예외 주입만으로 판정하지 않고 호출 수 0을 직접 확인한다. 가짜 AddSubFolder도 반환 사본을 현재 빈으로 바꾸고, 세 생성 지점·keep_current 복귀·실패 응답의 사본 ID 배제·재시도·기존 보내기 중복 정리 기본값을 검증한다.

## 구현·시험 결과

- Codex 위임 구현자는 담당3파일만 변경했다. 총괄은 호출부·실패 응답과 시험 본문을 대조했다. 최종 변경은 패널 재정렬 제거·자연순 생성·패널 경합 삭제 차단, 관련 시험 및 프런트 설명 주석이다.
- 수정 전 보존 시험은 기존 C30 객체가 바뀌어 실패했다(시험 기록 `e58272164c3d4290a5d8aaf2464c9395`). 최종 `test_resolve_bridge.py`는 **169개+하위7개 통과, 5.06초**, 기록 `0611879e6b3d415084095ba0545a155a`다. 이름 경합 후 keep_current의 동일 객체·ID 복귀는 컷/관리 루트 두 시험으로 별도 보강했다. 복귀 직전 현재 빈이 copy임을 직접 관측하며, 실패 보고·삭제0·재시도 중복 없음도 확인한다.
- `test_resolve_panel.py` **84개+하위3개 통과, 6.32초**, 기록 `1f1cde301da440e5b996efc98dee9d24`. 프런트 resolvePanelApi/App/PluginRules **109개 통과·기존11개 건너뜀, 7.03초**, 기록 `0d63e10744ea4970965318b89de362a0`. 합계 고유362개+하위10개 통과다.
- 위 두 회귀 결과 뒤에는 시험2개만 추가했다. 추가 구간을 뺀 원시 바이트가 이전 시험 파일 SHA256과 같은지, 제품2파일이 그대로인지, 원시 시험 기록의 종료 코드·지문·로그 해시·통과 수가 맞는지 직접 검증하여 selection_errors/regression의 현재 지문 근거로 연결했다. 같은 회귀 시험을 다시 실행한 것은 아니다.
- 최종 대상 지문은 `64dd5ce146e18fef4d3dcc572702f3aba915a6604e8f474c26928ab5938a2faa`다. CODE_MAP은 문서 참조1223개 중 누락0, 코드994개 중 미등재0. diff 검사 통과. 제품 엔드포인트·환경변수·DB 표·백그라운드 작업을 바꾸지 않아 inventory 재생성은 불필요하다.
- 실제 Resolve·왼쪽 목록·실기기 속도·NAS 실파일은 시험하지 않았다. 가짜 Resolve와 임시 자료만 사용했으며 새 빈이 끝에 붙는 표시, 다음 보내기의 기존 정렬, 이름 경합 사본 잔존은 앞의 한계를 유지한다.
