# MCP 연결 시험 흔들림 — 'cards 실패는 get_plan에 안전하게 보이고 재제출하지 않는다'

owner: claude · reviewer: codex(차이 리뷰 PASS) · status: 완료(프런트 전체 기록은 게이트 뒤) · touched_paths: frontend/tests/mcpConnection.test.tsx

## 증상 (11-18)

- 프런트 전체 시험을 한꺼번에 돌릴 때만 가끔 실패한다(시험 기록 `ab9270fd`). 같은 트리에서 직접 전체 실행·재기록·혼자 13회(게이트가 함께 돌던 10회 포함)는 모두 통과했다.
- 실패 모양: `get_plan` 응답의 `execution` 이 `running: false`·`error` 가 아니다(아직 실행 중).
- 배포 게이트의 프런트 전체 단계에서도 날 수 있어 배포 전에 고친다.

## 원인 (코드로 확인 + 추정)

- 시험은 실행을 시작한 뒤 `get_plan` 을 **정해진 10번**만 묻고 끝을 기다린다(`mcpConnection.test.tsx` 239~). 한 번 묻는 사이에 이벤트 루프를 몇 번 양보하지만, 횟수 제한이라 충분한 경과 시간을 보장하지 않는다.
- `execute_generation_plan` 은 실행 완료를 기다리지 않고 돌아오고, 그 뒤 사전 확인·카드 저장 경로가 계획 지문을 `crypto.subtle.digest`(`mcpPlans.ts:82`)로 여러 번 차례로 계산한다. 시험은 Node 의 webcrypto 를 쓰는데, 이 계산은 다른 스레드에서 실제 시간이 걸린다. 이 시험에서 HTTP·씬 저장 확인은 바로 끝나는 가짜라, 실패 지점까지 다른 실제 시간 대기는 없다(Codex 확인 — 10초 시간 제한은 실행 경로가 아닌 연결 확인 화면에 있다).
- 추정: 전체 시험이 여러 작업자로 PC 를 바쁘게 하면 지문 계산이 늦게 끝나고, 그 사이 10번 묻기가 먼저 끝나 실패한다. 원래의 병렬 실패를 직접 재현하지는 못했다(혼자 돌리면 안 난다) — 아래 실험은 digest 를 늦추면 같은 증상이 난다는 것까지만 보인다.

## 재현 (실험 설정 — 저장소 밖 scratchpad 의 `vite.slow.config.ts`·`slow_digest_setup.ts`)

- Node webcrypto 의 `digest` 만 진짜 시간 60ms 늦춘 설정으로 돌렸다('바쁜 PC' 흉내).
- 고치기 전: 'preflight·cards 실패는 get_plan에…' 두 시험이 실패했다 — 전체 시험 때의 실패와 같은 모양이다(digest 지연으로 같은 증상 재현. 원래 병렬 실패와 같은 원인인지는 추정).
- 같은 설정에서 '제출이 60초 걸려도…'(가짜 시계 시험)는 공용 기다림 `until`(정해진 300틱)이 모자라 실패했다. 다만 첫 실험 설정은 늦추는 데 가짜 시계에 걸리는 `setTimeout` 을 써서, 이 실패에는 설정 탓도 섞여 있었다. 그래서 진짜 `setTimeout` 으로 고친 설정에서 다시 확인했다.

## 고침

- 시험만 고친다(제품 코드 그대로).
  1. `get_plan` 을 묻는 사이에 실제 시간 5ms 를 기다리고, 횟수를 200번(최대 약 1초 남짓)까지 늘린다. 끝나면 바로 빠져나오므로 평소 시간은 그대로다.
  2. 공용 기다림 `until` 을 정해진 300틱 대신 진짜 시간 3초까지로 바꾼다. 시계는 파일 머리에서 잡은 진짜 `Date.now` 를 쓴다. 가짜 시계를 켠 시험에서 `Date.now` 가 멈춰 끝없이 돌지 않게 하기 위해서다. 시험 시간 제한(5초)보다 먼저 끝나 '요청이 끝나지 않았다'는 이유를 말한다.
- 고친 뒤: 60ms 늦춘 설정에서 25개 모두 통과, 보통 설정에서 25개 통과(약 3초, 전과 같음).

  - 파일 머리에서 잡은 `Date.now` 는 Vitest 4.1.12 가짜 시계에서도 진짜다(전역 `Date` 를 바꿀 뿐 원래 함수는 그대로).
