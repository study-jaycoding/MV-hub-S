# 저장 통합 1B — 새 구성원 형식 검증 준비

owner·touched_paths: 아래 vibe-intent 참조 · reviewer: Claude `c1660fa7-d08d-4333-ba17-3009e3ffcdb1` 승인 · status: 완료(형식 검증 준비만) · updated: 2026-11-13

[진행 인계](Codex인계_진행중작업_2026-11-12.md), [저장 통합 4판](저장통합_설계_2026-11-12.md) §4-3/1B의 첫 묶음이다. J1~J5·B1 짝·독립 스냅샷·읽는 쪽 먼저 도입하는 기존 합의는 유지한다. 이 기록의 완료는 **형식 검증 준비**만 뜻하며 Agent/폴더 자료의 실제 백업·수신·복원·NAS·전송 완료가 아니다.

## 선택과 범위

- 기존 `VERSION=2`, `check_version`, 현재 생성·송신판과 소비자 분기는 유지한다. 새 독립 검증 입구 `validate_v3`·`verify_files_v3` 및 엄격 JSON 읽기만 준비하고 소비자에는 연결하지 않는다. 기존 v1/v2는 그대로 읽으며 실제 수신·복원·NAS·송신 입구가 v3를 거절하는지 시험으로 고정한다.
- 이유: `VERSION`만 3으로 올리면 `{1,VERSION}`가 v2를 거절하고 worker의 생성판도 자동 3으로 바뀐다. `check_version`을 먼저 넓히면 소비자가 새 형식을 v1 경로로 취급할 수 있다. 읽기 지원과 현재 생성판의 분리는 실제 첫 v3 소비자를 여는 다음 묶음에서 한다.
- 제품 변경은 `backup_manifest.py` 한 파일, 시험은 기존 계약 시험 파일에만 추가한다. v2와 v3가 같이 쓰는 시각·schema·standalone·B1 확인은 필요한 최소 공통 함수로 추출하되 v2 의미·거절 동작을 유지한다. 파일명 상수·능력 표식·실제 캡처·복원·UI는 아직 추가하지 않는다.

## v3 세부 형식

- 최상위 필드는 v2 local/worker의 정확 집합을 유지한다. `format_version=3`, `payload_version=1`은 정확한 정수다. `set_id`/`backup_set_id` 봉인과 `account_scope_digest` 대조는 유지한다.
- 역할은 worker `{content,trash,agent_chat,asset_mounts}`, local은 거기에 `manage`를 더한 정확 집합이다. content는 반드시 present다. 누락을 absent로 추정하지 않는다.
- present 공통 필드는 `{state,captured_at,size,sha256}`이고 `state="present"`, `size`는 bool 아닌 양의 정수다. content/trash/manage는 기존 `schema`가 필수이고 Agent/JSON에는 schema 필드를 허용하지 않는다.
- absent는 `{state:"absent",captured_at}`만 허용한다. 크기·해시·schema·실제 파일 경로가 있으면 거절한다. 이는 해당 신원 경로의 FileNotFound를 확인한 빈 상태이며 읽기 실패·파손은 부재가 아니다. 실제 삭제/초기화는 이번에 구현하지 않는다.
- 모든 시각은 64자 이하의 시간대 있는 ISO 문자열이며 null 금지다. 최상위 시각은 content 시각과 같고 PINNED이면 trash 시각도 같다. 역할 사이 시간의 선후는 시계 역행을 고려해 강제하지 않는다.
- `consistency_kind`는 PINNED 또는 INDEPENDENT만 허용한다. PINNED는 present content/trash와 `['content','trash']`; INDEPENDENT는 **present 역할 전체**를 정렬한 목록이다. 이는 독립 촬영이라는 뜻이며 JSON까지 동일 순간임을 주장하지 않는다.
- 폴더 JSON은 원문 바이트의 크기·해시를 확인한 뒤 UTF-8(BOM 없음)·중복 키/NaN/Infinity 없음·루트 `{mounts:[...]}`를 검사한다. 항목은 name/path 필수, owner 선택의 문자열이며 name/path는 공백만이면 안 된다. owner 누락/빈 문자열은 옛 형식으로 허용하고 이름 중복은 거절하지 않는다. 미지의 키는 거절한다. **1MiB 상한은 제한된 메모리 사용을 위한 설계값이며 실측값이 아니다.** 폴더를 열거나 자동 연결하지 않는다.
- Agent 파일은 비어 있지 않은 WAL/journal이 없는 독립 SQLite를 read-only immutable으로 검사한다. quick_check, `user_version==0`, 아래 고정 기준선의 필수 표·열 존재를 확인한다. 기준선은 `backup_manifest.py`에 두고 제품 검증기에서 `repo.agent_chat`를 import하지 않는다. `_NEW_COLUMNS`가 없는 옛 파일과 추가 표·열은 허용한다. 원본에 마이그레이션/쓰기를 하지 않는다. **버전 0인 미래 비호환 변경이나 실제 계정 소유권을 독립 증명하는 검사는 아니다.** 다음 단계에서 이 한계를 숨기지 않는다.
- Agent 고정 기준선: `agent_chat_conversation` = id, engine, model, effort, cli_session_id, client_id, mcp_entry, title, resumable, created_at, updated_at. `agent_chat_turn` = id, conversation_id, idempotency_key, status, text, context, reason, created_at, ended_at. `agent_chat_event` = turn_id, seq, kind, payload, created_at. `agent_chat_plan_binding` = plan_id, turn_id, client_id, created_at. 옛 파일 시험은 별도 고정 SQL로 만들고, 현재 `_SCHEMA`에 기준선이 포함되는지 확인하는 시험과 실제 `open_db`로 만든 임시 파일의 검증을 둔다. 현재 스키마의 추가 표·열이 옛 백업의 새 필수 조건이 되지 않게 한다.
- 전달된 파일 집합은 present 역할과 정확히 같아야 하며 바이트·크기·schema·B1 짝을 검증한다. 고정 전송 이름은 content.db/trash.db/agent_chat.db/asset_mounts.json, 로컬 추가 이름은 agent_chat_STAMP.db/asset_mounts_STAMP.json으로 다음 소비자에서 대응한다. manifest 자체에 임의 파일명/경로를 넣지 않는다.

## 설계 근거·남은 묶음

- Codex `handoff_decisions_reconcile`의 두 차례 읽기 조사와 총괄의 실제 소스 대조 후, Claude `mvhub-design` `88f10563-67ca-4315-b4d7-d5da1d7f8de2`(요청 Fable/high·실제 claude-fable-5-2)가 독립 검증기만 먼저 추가하는 작은 안을 제시했다. 도구 없는 고정 원문 검토이며 7개 입력 제품 파일의 호출 전후 SHA256 동일. ponytail 본문을 적용했다는 상대 보고이고 실제 추론 수준은 미확인이다. 이 초안 시점에는 구체 계약 재확인 전이었으며 아래 후속에서 합의했다.
- 계약 재검토에서 Claude는 자신의 ‘현재 `_SCHEMA`에서 필수 표·열을 얻기’ 제안을 철회했다. 앱에서 새 표를 추가하면 이미 저장한 옛 백업이 무효화되는 반례다. 총괄도 동의하여 위 고정 기준선과 독립 옛 SQL 시험으로 수정했다. 이 재검토 입력3파일의 원시 SHA256 전후 동일을 총괄이 확인했다.
- 후속 실제 응답에서 Claude가 변경 계약 `4a6ec32b4e1b944d89c4be66213a3007c3d06deb77ed98388bea1cc52667d149`에 동의했고 Codex도 동일 계약에 동의했다. 요청 Fable/high·실제 claude-fable-5-2, 실제 추론 수준 미확인, 도구 0개 고정 문서 검토다. 기준선 변경은 형식 계약 변경이므로 현재 스키마를 따라 조용히 고치지 않는다. NAS 거절 시험은 실제 도구 모듈을 호출할 수 있는지까지 확인하고, 불가하면 미확인으로 남긴다. 이 합의 뒤 implement 검사 통과와 바인딩 전환을 확인하고 Codex 담당자에게 제품/시험2파일 구현을 배정했다. 문서·독립 리뷰·통합은 총괄 소유다.
- 후속 수신·복원·NAS는 전체 파일 ACK, 고정 이름, Agent runtime/열린 연결 종료와 `_opened` 무효화, 원본 보존·전체 롤백, 외부 CLI 세션·계획·폴더 참조 재확인 전 실행 차단을 포함한다. `shutdown()` 호출만으로 파일 교체가 안전하다고 하지 않는다.
- 송신 후속: 봉인한 v3를 v2로 고쳐 쓰는 것은 금지한다. 구서버에 별도 v2 content/trash 세트를 보내고 새 구성원 미전송을 표시하는 방안은 기존 §4-3과 양립할 수 있어 다음 묶음에서 확정한다. 이번에는 v3를 생산하지 않으므로 현재 백업·전송을 중단하지 않는다.
- 실제 자료 크기·과거 user_version/손편집 JSON, 실제 수신 서버판은 열람/변경하지 않았다. 형식 준비가 끝나도 저장 통합 1B 전체는 계속 진행 중이다.
- 구현 준비 조사에서 기존 `test_backup_replicate._module()`을 재사용해 임시 폴더의 정상 v3 manifest를 `_set_manifest()`가 거절하는지 확인할 수 있음을 읽기 대조했다. 실제 복제/스케줄 실행 함수는 호출하지 않는다. Agent의 필수 표를 VIEW로 위장하는 경우와 stat 이후 커지는 JSON도 기존 ‘표·1MiB 제한’ 기준에 포함해 검증한다. 이는 실행 결과가 아닌 구현 준비다.

## 구현·검증
