## 왜 바꿨나

캔버스 씬(카드·연결·그룹)은 브라우저 `localStorage` 한 키(`ch.scenes`)에 통째로 들어 있었다. 출처당 한도가
약 520만 글자라 큰 씬이 쌓이면 찼고, 찬 뒤에는 **편집이 조용히 되돌아갔다** — "레퍼런스를 생성 카드에
연결해도 선이 사라진다"는 신고(2026-10-07)의 원인이다. 실측으로 재현했다: 꽉 찬 상태에서 연결선 하나를
더하는 저장이 `QuotaExceededError` 로 실패한다.

그래서 ① 저장 자리를 IndexedDB 로 옮기고 ② 저장이 안 될 때 화면을 되돌리지 않고 알리며 ③ 옛 자료는
사용자 조작 없이 전부 옮긴다(Jay 요구: "지금 찬 것을 큰 데로 옮기고 똑같이 쓸 수 있어야 한다").

## 구조 — 화면 값은 그 자리에서, 확정은 뒤따라

| 이름 | 뜻 |
| --- | --- |
| 확정본(`confirmed`) | IndexedDB 에 실제로 들어 있는 내용(이 창이 마지막으로 확인한 것) |
| 밀린 연산(`pending`) | 아직 확정 안 된 내 편집(연산 목록) |
| 화면 값(`working`) | 확정본 + 밀린 연산. **앱이 읽고 쓰는 값** |

쓰기는 화면 값에 동기로 반영되고(`applySceneOp`), 저장은 한 트랜잭션에서 **저장소의 최신 내용 위에 밀린 연산을
차례로 다시 실행**한 뒤 쓴다(`runStoreTx`). 그래서 늦게 끝난 저장이 그사이의 새 편집을 덮지 않고, 다른 창이
그사이 한 변경도 덮지 않는다. IndexedDB 는 다른 창에 신호를 보내지 않으므로 확정할 때마다
`BroadcastChannel("mvhub-scenes")` 로 알리고, 받은 창은 다시 읽어 화면 값을 다시 계산한다.

### 저장 배치 — 씬 하나가 한 키 (DB 버전 2)

DB `mvhub-scenes`, object store `kv`. 키는 글자다.

| 키 | 값 |
| --- | --- |
| `["s", 버킷, 씬 id]`(JSON 배열 글자) | 씬 하나 |
| `["o", 버킷]` | 그 버킷의 씬 id 순서(탭 순서). **이 키가 있으면 버킷이 있다** — 빈 배열 = 빈 버킷 |
| `layout` | `2` — 이 배치로 초기화가 끝났다는 표식 |
| `version` | 씬이 바뀔 때마다 +1 |
| `absorbBase`·`generation`·`conflicts`·`migrationInfo` | 흡수 기준·이관 세대·충돌 목록·이관 진단 기록 |

버킷 키는 `<계정 네임스페이스>::_none`(`scenes.ts` 의 `keyOf`).

- **평소 저장은 버전 숫자만 읽고, 바뀐 씬·순서만 쓴다.** 버전이 내가 아는 것과 같으면 메모리의 확정본이 곧 저장소
  내용이다. 다르면(다른 창이 썼다) 같은 트랜잭션에서 씬 전체를 읽어 기준으로 삼는다.
- 무엇이 바뀌었는지는 **객체가 같은가**로 본다(`diffScenes`). 연산은 버킷을 새 배열로 갈아 끼우고 안 바뀐 씬은
  같은 객체로 둔다. 제자리에서 고치는 연산은 저장에서 빠지므로, 개발·시험 빌드에서는 저장소에 든 씬을 얼려
  그런 연산이 그 자리에서 던지게 한다.
- 재생은 작업본(`live = {...base}`)에만 하고, **확정본은 트랜잭션이 끝난 뒤에만** 간다.
- 쓰기 트랜잭션은 `durability: "strict"` 를 요청한다(확정 = 디스크 기록까지). 적용값은 `sceneStoreDurability()`.
- **DB 버전을 올린 까닭**: 옛 배치(버전 1, 씬 전체가 `scenes` 한 키)를 쓰는 창과 같이 열리면, 그 창은 지워진 옛
  키를 다시 만들어 "확정"이라 알리고 새 창은 그것을 읽지 않는다. 버전이 다르면 동시에 열리지 못한다 — 옛 창이
  닫힐 때까지 새 창은 오류 화면("다른 창을 닫고 다시 시도")에 머문다. 옛 배치의 자료는 열 때 한 트랜잭션으로 푼다.
- 연결이 끊기면(더 새 판이 DB 를 올릴 때·브라우저가 끊을 때) 다음 저장 때 다시 연다. **다시 이은 뒤에는 버전이
  같아 보여도 전체를 다시 읽는다**(그사이 저장소가 지워지고 다른 창이 새로 만들었을 수 있다). `layout` 표식이
  없는 저장소에는 쓰지 않는다 — 저장 실패로 알리고, 내보내기는 화면 값을 준다.

### 읽기 — 씬별 사본을 한 번만 만든다

저장소가 든 객체는 밖에 내주지 않는다. `listScenes` 등이 주는 것은 저장소가 씬마다 한 번 만든 **사본**이고,
안 바뀐 씬은 같은 사본을 다시 준다(목록 배열은 매번 새것). **받은 씬은 고치지 않는다** — 고칠 때는 새 객체를
만들어 `updateScene` 등에 넘긴다. 개발·시험 빌드에서는 사본을 얼려, 고치려는 코드가 그 자리에서 던진다.
DB 미러는 같은 자리에 기억된 JSON 글자를 그대로 쓴다(`listPersistedSceneTexts`).

### 지키는 규칙(Codex 와 합의 — 깨지면 자료를 잃는다)

1. 동기 반환의 성공은 "화면 값에 반영됨"이다. 저장소 확정과 구분한다.
2. 연산은 순수하다 — id·시각·계정 키·입력은 접수 때 고정하고, 버킷은 새 배열로 갈아 끼운다(재생해도 같은 결과).
3. 한 연산은 확정에 한 번만 들어간다(트랜잭션이 잡은 묶음만 뺀다).
4. 화면 값 = 확정본 + 밀린 연산. 재생에서 던진 연산은 버리되 화면 값에서도 걷어내고 그 작업에 실패로 알린다.
5. 저장·옛 저장소 흡수·다른 창 재조회·충돌 정리·전체 가져오기는 한 줄로 차례대로 돈다.
6. 내구성이 필요한 흐름은 **그 작업의 확정 결과**(`confirmSceneWrite`)와 **확정본에 실제로 들어갔는지**를 함께
   본다 — 생성 제출 전 표식(`App.prepareCanvasGenerationBatch`), 자산 재연결 판정 기억(`sceneAssetRelink.applyFound`),
   DB 백업 복구 보고(`sceneBackup`).
7. 밀린 연산은 끝없이 늘지 않는다. 같은 씬을 잇달아 고치는 연산은 하나로 합치고(`merge` — 인접하고 아직 저장으로
   떠나지 않은 것만), 상한(200)에 닿으면 새 연산을 **거절하고 알린다**. 쌓인 연산을 "지금 내 버킷 통째"로 뭉쳐
   줄이지 않는다 — 재생될 때 다른 창이 확정한 변경을 지운다.
8. DB 미러·복구 판정·계정 귀속은 확정본 기준이다(`listPersistedScenes`·`hasPersistedSceneBucket`). 옛 계정 없는
   버킷(`_none`)의 귀속은 확정된 뒤에만 화면에 보인다.
9. 실패한 저장의 결과는 확정본이 되지 않는다. 씬·순서·버전·메타는 한 트랜잭션에서 전부 되거나 전부 안 된다.

## 옛 저장소에서 옮기기

- 앱(메인 화면)은 `bootSceneStore()` 가 끝난 뒤에 뜬다. 분리 창(Assets·관리)은 씬을 쓰지 않아 기다리지 않는다.
- **옛 `localStorage` 는 지우지 않는다.** 업데이트가 열려 있는 캔버스 창을 닫아 주지 않아, 옛 판 창이 계속 거기에
  쓰기 때문이다. 대신 그 변경을 흡수한다(`sceneAbsorb.planAbsorption` — 지난번 본 옛 내용·지금 새 내용·지금 옛
  내용을 견준다. 시각은 쓰지 않는다).
- 이관 표식(`pending`/`committed` + 세대)은 `localStorage` 와 **쿠키** 두 곳에 적는다. 꽉 찬 PC 에서는
  `localStorage` 에 표식 한 줄도 못 쓰기 때문이다.
- 표식이 `committed` 인데 저장소가 초기화돼 있지 않으면(사이트 데이터 삭제 등) 옛 내용을 되살리지 않고 빈 상태로
  연다 — 로컬 허브 DB 백업 복구(`sceneBackup`)가 맡는다.
- 옛 자료의 담을 수 없는 모양(배열 아닌 버킷·id 없는 항목·같은 id 의 둘째)은 빼고 옮긴다 — 그것 때문에 이관이
  통째로 실패해 앱이 안 뜨는 일이 없게.
- 저장소를 못 열면 빈 화면으로 진행하지 않고 오류 화면에 머문다(다시 시도 + 옛 자료 원문 내려받기).
  부팅 도중의 예외도 같은 화면으로 간다(`bootSceneStore` 는 던지지 않고 실패를 값으로 돌려준다). 이관 표식을
  못 읽으면(깨진 쿠키 등) '표식 없음'으로 추측해 열지 않는다 — 끝난 이관을 처음으로 보고 옛 내용으로 덮을 수 있다.
- **이관 진단 기록**(`migrationInfo`): 실제로 옮긴 그 트랜잭션에서 한 번, 옮긴 씬 수·옮긴 원문의 글자 수·옛 저장 칸
  전체 글자 수·1KB 시험 쓰기의 결과(됨/할당량 초과/확인 못 함)를 적는다. 설정의 '캔버스 자료'와 전체 내보내기
  파일에 보인다. 신고가 난 PC 에서 "정말 가득 차 있었나"를 가늠하는 **단서**다(확증은 아니다 — 시험 쓰기가 됐다고
  씬을 저장할 여유가 있었다는 뜻은 아니다).

## 사용자에게 보이는 것

- **저장이 안 될 때**: 편집은 화면에 남고 저장소가 간격을 늘려 가며 다시 시도한다. 그동안 탭 줄 오른쪽에
  `⚠ 저장 안 됨 — 눌러서 파일로 내려받기` 가 계속 떠 있다(알림 한 줄은 다른 알림에 덮인다).
- **옛 판 창과 같은 씬을 각자 고쳤을 때**: 묻지 않고 옛 창 쪽 내용을 `[옛 창] 이름` 탭으로 살린다(둘 다 남는다).
  같은 씬이 또 엇갈리면 손대지 않은 사본 탭을 최신으로 갈아 끼운다(탭이 끝없이 늘지 않게).
- **설정 → 캔버스 자료**: `전체 내보내기`(아직 확정 안 된 편집까지 싣는다) / `전체 가져오기`(덮지 않는다 — 없는
  씬만 더하고, 같은 씬인데 내용이 다르면 `[사본] 이름` 탭으로 따로 둔다. 같은 파일을 두 번 가져와도 또 생기지 않는다).
  파일 형식 `mvhub-scenes-full` v1. 그 아래 한 줄에 "지금 캔버스 N개 · 옮길 때: …"(위 진단 기록).
- 입력 저장은 400ms 디바운스에 **최대 대기 2초**(계속 쳐도 2초 안에 한 번 내보낸다), 창이 가려질 때 바로 내보낸다.
- **DB 백업에서 빠지는 씬**: 서버는 씬 1개가 UTF-8 5MiB 를 넘으면 요청 전체를 거절한다. 넘는 씬만 전송에서 빼고
  알린다(올린 것으로 적지 않고 서버의 옛 사본도 지우지 않는다. 작아지면 다시 올린다).

## 밖에서 온 씬·id

- 씬 파일·전체 파일의 씬은 `scenes.readSceneBody`/`readStoredScene` 관문에서 **필드마다, 배열은 원소까지** 모양을
  본다. 모양이 다른 필드는 지우고 원소는 빼며, 카드 자체를 못 읽으면 파일을 거절한다.
- 씬에 적힌 id 로 사전(일반 객체)을 조회할 때는 **자기 속성만** 본다(`lib/ownEntry.ts`) — `map["toString"]` 은
  Object.prototype 의 함수를 준다. 생성물 캐시(`genData`)·레퍼런스 부모·**서버 응답 사전**(`batch.items`) 모두.
  가져오기 검증의 id 금지(`isSafeId`)는 보조다 — 옛 저장소 이관·기존 저장소·백업 복구는 그 관문을 지나지 않는다.

| 다시 켜기(44MB) | 약 0.2초 · 내용 동일 |
| 옛 판 창의 쓰기 | 안 건드린 씬은 가져옴 · 엇갈린 씬은 `[옛 창]` 탭으로 |
| 창을 띄운 채 저장소가 지워지고 다른 창이 새로 초기화 | 원래 창의 다음 저장이 새 저장소를 따름(다른 창이 보는 것과 같음) |
| 전체 내보내기(약 44MB) / 같은 파일 다시 가져오기 | 약 70ms / 중복 0 |

## 남은 한계

- **다른 창이 떠 있으면** 한 창의 편집마다 그 창이 씬 전체를 다시 읽는다(15MB 약 5ms, 44MB 약 25ms — 그 창이 치르는
  비용). 숨은 창의 재조회를 미루는 것은 하지 않는다: 그 창의 백그라운드 쓰기(생성 완료 반영 등)가 낡은 화면 값으로
  카드 배열을 통째로 넣어 다른 창의 편집을 덮을 수 있다. 변경분만 읽는 재조회가 후속 후보다.
- 아직 저장소에 확정되지 않은 입력(캔버스 메모리의 입력 대기 최대 2초, 저장 지연, 실패 재시도 중인 연산)은 강제
  종료에서 남지 않을 수 있다. `strict` 는 **확정된** 트랜잭션의 내구성만 높인다.
- 서버 쪽 `scene_backup` 은 여전히 조건 없이 덮는다(여러 브라우저 프로필이 번갈아 올리면 늦게 올린 쪽이 남는다).
  조건부 갱신·삭제 표식은 API·복구 계약 변경이라 별도 작업이다.
- 저장소가 지워진 채(다른 창이 새로 만들지도 않은 채) 떠 있는 창은 저장이 실패한다 — '저장 안 됨'으로 알리고
  내보내기가 화면 값을 준다. 새로 고치면 부팅이 빈 상태로 열고 DB 백업 복구가 돈다(그때 내보내지 않은 밀린 편집은 없다).
