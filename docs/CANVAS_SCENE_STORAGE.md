## 왜 바꿨나

### 복원 세대 보호(1C-1)

**11-17 최초 시작 변경**([Jay 결정·Codex 자문](status/허브공책_기본켬_첫시작확인_2026-11-17.md)): 아래의 보관·허브 채택은 이미 시작된 공책과 확인된 복원·보류 자료에 적용한다. 미시작 공책에서 출처 미확인 자료가 허브와 다르면 로컬 씬·순서를 유지하고 자동 전송과 임대를 멈춘다. 기존 `cleanUpgrade`가 성립할 때만 조용히 이어 간다. 그 밖에는 캔버스 알림 줄에서 [이 캔버스로 시작]을 확인받는다. [나중에]는 접힌 안내만 남기며, 편집·focus·타이머가 확인을 대신하지 않는다. 합치기 창은 열지 않는다.

확인 버튼은 기다리는 동안의 로컬·허브 원문과 제어 자료를 다시 대조한 뒤 입력·끌기를 확정하고 임대를 새로 얻는다. 계정·복원 세대·허브 판·자료가 달라졌거나 진행 중 임대를 잃으면 그 확인으로 쓰지 않는다. 저장 실패도 시작 허가로 쓰지 않는다. 승인한 최종 씬으로 기존 시작 절차를 실행하며, 비어 있지 않은 로컬로 시작할 때 허브 옛 행은 `before_start`로 보관한다. 기존 **0개 시작**은 살아 있는 허브 행으로 공책을 만들고, 양쪽이 비면 씬을 만든 뒤 재시도한다. 이미 시작한 다른 브라우저가 있으면 이 브라우저 원문을 보관하고 그 공책에 합류한다. 최초 합류에도 `nj.restoreGeneration`을 적어 다음 동기화에서 다시 출처 미확인으로 전환하지 않는다. 5MiB 초과 씬이 하나라도 있으면 작은 씬도 올리지 않고 시작을 중단하며 로컬 편집을 유지한다.

`sceneNotebook.ts`는 세대가 없거나 달라진 브라우저의 씬·충돌·기준판·삭제·되살리기·순서·시작 진행·미전송 요청을 `nr` 보관 목록에 넣고 허브를 채택하는 일을 한 IndexedDB 트랜잭션으로 처리한다. 다만 업데이트 직후 세대 기록이 없고 로컬 씬·순서가 허브 행과 같으며 미전송 연산·의도·시작/쓰기 진행·충돌이 없으면 보관본 없이 현재 세대만 채택한다. 허브 공책이 미시작(`notebook_id=null`)이거나 순서 판이 0이면 임시 배열 순서를 비교하지 않고 ID 집합과 ID별 본문을 비교한다. 깨끗하면 로컬 순서를 유지하고 순서 저장만 대기시킨다. 허브 행으로 공책을 시작할 때 생기는 첫 순서 판은 같은 시작 진행·임대·이력과 한 판 증가를 확인해 이어받으며, 시작 응답을 잃어도 다시 확인한다. 이 깨끗한 채택으로는 ‘복원 전에 남겨 둔 것’이 나타나지 않는다. 허브 전용 행(`bk_` 포함)·로컬 전용 씬·다른 본문이 있으면 기존처럼 로컬 전체를 보관하고 허브 전체를 채택한다. 공책은 씬별 부분 채택 대신 공통 순서·제어 자료를 포함한 한 스냅샷을 보존하며, 로컬 전용 씬을 자동 전송하지 않는다. 실제 세대가 다르면 내용이 같아도 보관하며, 보관 실패 시 전환하지 않는다. 빈 복원 공책은 옛 씬으로 다시 시작하지 않으며, 채택 뒤 새 사용자 편집부터 현재 세대로 시작한다. 늦은 성공 응답은 새 조회의 세대와 로컬 진행 기록이 일치할 때만 정리한다.

공책을 끈 옛 미러는 옛 장부를 `mvhub.mirrorRecovery:<계정>`의 복구 후보로 먼저 격리하고, 출처 대응은 원문 대신 SHA-256 지문으로 적는다. 원문은 보류한 씬만 보존한다. 세대 기록이 없는 씬도 fork가 없고 본문이 현재 서버 행과 같으면 현재 기준판을 채택해 이후 편집의 자동 전송을 이어 간다. 깨끗한 씬의 장부만 격리한 경우에는 보류 묶음을 표시하지 않는다. 시작 때 연결이 끊겨도 확인된 같은 세대의 로컬 편집 출처는 유지한다. 보류한 씬은 전체 가져오기로 사용자가 선택하고 로컬 확정·현재 허브 기준판을 확인한 뒤 재개한다. 재개된 씬은 주황 묶음의 보류 개수에서 빠지고, 다른 보류도 없으면 묶음을 숨긴다. 보관 원문 자체는 지우지 않는다. 다른 저장 경로의 대기열은 재개하지 않는다.

카드는 옛 제거·되살리기 대기열과 당시 자동 스캔 중 현재 세대 서버 목록에 없는 소속을 `mvhub.cardRecovery:<계정>`에 격리한다. 같은 세대로 채택된 씬만 조회 병합·전송하며, **옛 스캔의 보류 소속은 보내지 않고 채택 이후 새로 담은 소속만 자동 백필**한다. 자료 관리의 ‘복원 전에 남겨 둔 것’에서 보관본·개수·파일 내보내기를 제공한다. 1C-2의 `[되돌리기]`와 로컬 세트 복원은 후속 범위다.

**첫 전환 복구 동선**(공책 켬에서만, [기록](status/공책첫전환복구동선_2026-11-15.md)): 보관 묶음(`nr`)에 지금 캔버스에 없거나 내용이 다른 이 계정 씬이 있으면, 본 창 캔버스 탭에 알림 줄을 묶음마다 한 번 띄운다(`components/scene/CanvasRestoreNotice.tsx`, 본 묶음은 `mvhub.restoreNoticeSeen:<계정>`). 고르기 창에서 고른 씬은 기존 전체 가져오기(`importSceneArchiveText`) 규칙으로 지금 캔버스 버킷에 더한다 — 없는 ID 는 그대로, 같은 ID 다른 내용은 `[사본]`, 충돌 기록은 싣지 않고 보관함은 그대로 둔다. 허브에서 지운 씬의 ID 를 되살리면 지운 판의 내용이 보관 판으로 바뀐다(기존 되살림 규칙). 설정의 ‘복원 전에 남겨 둔 것’ 칸에 [보관한 씬 고르기]가 같은 창을 연다. 알림은 씬 저장 알림을 구독하지 않고, 합류가 묶음을 새로 적을 때(`subscribeRestoreArchived`)·계정·기능·다른 탭·낡은 읽기 회복·focus 때만 보관함을 읽는다. 가져오기(`importSceneArchiveText`)가 로컬 저장을 마친 뒤 계정이 바뀌어 있으면(공책 켬), 실제 병합에서 같은 ID 로 들어간 씬의 카드 소속 되살리기를 가져오기를 시작한 계정의 대기열(`ch.sceneCardRevives.v1.<계정>`)에 그때 읽은 복원 세대로 넣고 계정 전환 오류를 던진다 — 그 계정이 다시 활성일 때 기존 전송이 보낸다(`sceneCardLinks.queueCardRevivesFor`, 파일 가져오기도 같다). 공책 끔에서는 이 동선 없이 기존 내려받기·전체 가져오기만 둔다(끔의 미러 재개가 서버 지문을 기준판으로 삼아 서버 내용을 바꿀 수 있어서).

캔버스 씬(카드·연결·그룹)은 브라우저 `localStorage` 한 키(`ch.scenes`)에 통째로 들어 있었다. 출처당 한도가
약 520만 글자라 큰 씬이 쌓이면 찼고, 찬 뒤에는 **편집이 조용히 되돌아갔다** — "레퍼런스를 생성 카드에
연결해도 선이 사라진다"는 신고(2026-10-07)의 원인이다. 실측으로 재현했다: 꽉 찬 상태에서 연결선 하나를
더하는 저장이 `QuotaExceededError` 로 실패한다.

그래서 ① 저장 자리를 IndexedDB 로 옮기고 ② 저장이 안 될 때 화면을 되돌리지 않고 알리며 ③ 옛 자료는
사용자 조작 없이 전부 옮긴다(Jay 요구: "지금 찬 것을 큰 데로 옮기고 똑같이 쓸 수 있어야 한다").

## 구조 — 화면 값은 그 자리에서, 확정은 뒤따라

| 이름 | 뜻 |
| --- | --- |
| 확정본(`confirmed`) | IndexedDB 에 실제로 들어 있는 내용(이 창이 마지막으로 확인한 것) |
| 밀린 연산(`pending`) | 아직 확정 안 된 내 편집(연산 목록) |
| 화면 값(`working`) | 확정본 + 밀린 연산. **앱이 읽고 쓰는 값** |

쓰기는 화면 값에 동기로 반영되고(`applySceneOp`), 저장은 한 트랜잭션에서 **저장소의 최신 내용 위에 밀린 연산을
차례로 다시 실행**한 뒤 쓴다(`runStoreTx`). 그래서 늦게 끝난 저장이 그사이의 새 편집을 덮지 않고, 다른 창이
그사이 한 변경도 덮지 않는다. IndexedDB 는 다른 창에 신호를 보내지 않으므로 확정할 때마다
`BroadcastChannel("mvhub-scenes")` 로 알리고, 받은 창은 다시 읽어 화면 값을 다시 계산한다.

### 저장 배치 — 씬 하나가 한 키 (DB 버전 2)

DB `mvhub-scenes`, object store `kv`. 키는 글자다.

| 키 | 값 |
| --- | --- |
| `["s", 버킷, 씬 id]`(JSON 배열 글자) | 씬 하나 |
| `["o", 버킷]` | 그 버킷의 씬 id 순서(탭 순서). **이 키가 있으면 버킷이 있다** — 빈 배열 = 빈 버킷 |
| `layout` | `2` — 이 배치로 초기화가 끝났다는 표식 |
| `version` | 씬이 바뀔 때마다 +1 |
| `absorbBase`·`generation`·`conflicts`·`migrationInfo` | 흡수 기준·이관 세대·충돌 목록·이관 진단 기록 |

버킷 키는 `<계정 네임스페이스>::_none`(`scenes.ts` 의 `keyOf`).

- **평소 저장은 버전 숫자만 읽고, 바뀐 씬·순서만 쓴다.** 버전이 내가 아는 것과 같으면 메모리의 확정본이 곧 저장소
  내용이다. 다르면(다른 창이 썼다) 같은 트랜잭션에서 씬 전체를 읽어 기준으로 삼는다.
- 무엇이 바뀌었는지는 **객체가 같은가**로 본다(`diffScenes`). 연산은 버킷을 새 배열로 갈아 끼우고 안 바뀐 씬은
  같은 객체로 둔다. 제자리에서 고치는 연산은 저장에서 빠지므로, 개발·시험 빌드에서는 저장소에 든 씬을 얼려
  그런 연산이 그 자리에서 던지게 한다.
- 재생은 작업본(`live = {...base}`)에만 하고, **확정본은 트랜잭션이 끝난 뒤에만** 간다.
- 쓰기 트랜잭션은 `durability: "strict"` 를 요청한다(확정 = 디스크 기록까지). 적용값은 `sceneStoreDurability()`.
- **DB 버전을 올린 까닭**: 옛 배치(버전 1, 씬 전체가 `scenes` 한 키)를 쓰는 창과 같이 열리면, 그 창은 지워진 옛
  키를 다시 만들어 "확정"이라 알리고 새 창은 그것을 읽지 않는다. 버전이 다르면 동시에 열리지 못한다 — 옛 창이
  닫힐 때까지 새 창은 오류 화면("다른 창을 닫고 다시 시도")에 머문다. 옛 배치의 자료는 열 때 한 트랜잭션으로 푼다.
- 연결이 끊기면(더 새 판이 DB 를 올릴 때·브라우저가 끊을 때) 다음 저장 때 다시 연다. **다시 이은 뒤에는 버전이
  같아 보여도 전체를 다시 읽는다**(그사이 저장소가 지워지고 다른 창이 새로 만들었을 수 있다). `layout` 표식이
  없는 저장소에는 쓰지 않는다 — 저장 실패로 알리고, 내보내기는 화면 값을 준다.

### 읽기 — 씬별 사본을 한 번만 만든다

저장소가 든 객체는 밖에 내주지 않는다. `listScenes` 등이 주는 것은 저장소가 씬마다 한 번 만든 **사본**이고,
안 바뀐 씬은 같은 사본을 다시 준다(목록 배열은 매번 새것). **받은 씬은 고치지 않는다** — 고칠 때는 새 객체를
만들어 `updateScene` 등에 넘긴다. 개발·시험 빌드에서는 사본을 얼려, 고치려는 코드가 그 자리에서 던진다.
DB 미러는 같은 자리에 기억된 JSON 글자를 그대로 쓴다(`listPersistedSceneTexts`).

### 지키는 규칙(Codex 와 합의 — 깨지면 자료를 잃는다)

1. 동기 반환의 성공은 "화면 값에 반영됨"이다. 저장소 확정과 구분한다.
2. 연산은 순수하다 — id·시각·계정 키·입력은 접수 때 고정하고, 버킷은 새 배열로 갈아 끼운다(재생해도 같은 결과).
3. 한 연산은 확정에 한 번만 들어간다(트랜잭션이 잡은 묶음만 뺀다).
4. 화면 값 = 확정본 + 밀린 연산. 재생에서 던진 연산은 버리되 화면 값에서도 걷어내고 그 작업에 실패로 알린다.
5. 저장·옛 저장소 흡수·다른 창 재조회·충돌 정리·전체 가져오기는 한 줄로 차례대로 돈다.
6. 내구성이 필요한 흐름은 **그 작업의 확정 결과**(`confirmSceneWrite`)와 **확정본에 실제로 들어갔는지**를 함께
   본다 — 생성 제출 전 표식(`App.prepareCanvasGenerationBatch`), 자산 재연결 판정 기억(`sceneAssetRelink.applyFound`),
   DB 백업 복구 보고(`sceneBackup`).
7. 밀린 연산은 끝없이 늘지 않는다. 같은 씬을 잇달아 고치는 연산은 하나로 합치고(`merge` — 인접하고 아직 저장으로
   떠나지 않은 것만), 상한(200)에 닿으면 새 연산을 **거절하고 알린다**. 쌓인 연산을 "지금 내 버킷 통째"로 뭉쳐
   줄이지 않는다 — 재생될 때 다른 창이 확정한 변경을 지운다.
8. DB 미러·복구 판정·계정 귀속은 확정본 기준이다(`listPersistedScenes`·`hasPersistedSceneBucket`). 옛 계정 없는
   버킷(`_none`)의 귀속은 확정된 뒤에만 화면에 보인다.
9. 실패한 저장의 결과는 확정본이 되지 않는다. 씬·순서·버전·메타는 한 트랜잭션에서 전부 되거나 전부 안 된다.
10. 캔버스가 분리 창에 떠 있는 동안 씬은 그 창만 쓴다. 원래 창의 일반 쓰기는 `applySceneOp` 가 거절한다(`paused` — 저장 실패가 아니라 알리지 않는다).
    닫는 창의 인계(`adoptCanvasSceneWrites`)만 받는다. 입구를 지나지 않는 쓰기는 호출부가 막는다 — 전체 가져오기는 단추를 막고, 옛 저장소 흡수·충돌 정리는 그 창이 하며 충돌 정리는 풀린 뒤 다시 돈다.
    떠 있음을 안 순간 이 창에 밀려 있던 일반 연산은 표시해(`setAsidePendingWrites`) 다시는 재생하지 않는다 — 카드 배열을 통째로 재생해 그 창의 편집을 덮기 때문이다. 씬에 쓰지 않고 충돌 목록으로 옮겨(저장본=mine, 이 창 편집=theirs) `[옛 창]` 사본으로 살린다.
    떠 있는 동안 메인 창이 켜지면 옛 저장소를 흡수하지 않고 읽기만 한다 — 이 창이 먼저 읽어 둔 낡은 원문이 그 창이 흡수한 것을 되돌리지 않게.
    분리 창은 하나다. 저장소를 열기 전에 `claimCanvasWindow` 로 잠금을 받고(최대 3초, 새로 고침이면 옛 문서가 곧 푼다), 못 받으면 저장소를 열지 않고 물러난다. 다른 메인 탭에서 띄우면 잠금을 보고 빈 창을 닫고 안내한다.
    기록 [한곳 쓰기](status/캔버스_분리창_한곳쓰기_2026-10-31.md) · [최종 검토 지적](status/최종검토지적_7건_2026-11-01.md) · [dev 메인 전환](status/dev메인전환_검토수정_2026-11-01.md).
11. 씬을 쓰는 메인 탭은 하나다. 메인 문서는 첫 그리기 전에 잠금 `mvhub-scene-writer` 를 요청해 최대 0.5초 기다리고(새로 고침의 새 문서가 옛 문서의 해제보다 먼저 올 수 있다), 받으면 문서 수명 동안 쥔다. 못 받으면 쉬는 탭이라 분리 창을 둔 메인 창과 같은 상태다(`isCanvasFloating` 참: 쓰기 멈춤·저장본 따르기·보드 없음·배경 복구 쉼). 쥔 문서가 끝나면 저장소를 다시 읽는 데 성공한 뒤에만 풀리고, 되돌리기 기록은 그 탭이 남긴 슬롯까지 찾는다(못 읽으면 기록 없이 연다). 쉬는 탭은 닫히는 분리 창의 인계를 받지 않는다. 잠금 없는 주소·옛 판 탭은 이 규칙 밖이다.
    기록 [배포 전 남은 제한](status/배포전_남은제한_해결_2026-11-02.md).

## 옛 저장소에서 옮기기

- 앱(메인 화면)은 `bootSceneStore()` 가 끝난 뒤에 뜬다. 분리 창(Assets·관리)은 씬을 쓰지 않아 기다리지 않는다.
- **옛 `localStorage` 는 지우지 않는다.** 업데이트가 열려 있는 캔버스 창을 닫아 주지 않아, 옛 판 창이 계속 거기에
  쓰기 때문이다. 대신 그 변경을 흡수한다(`sceneAbsorb.planAbsorption` — 지난번 본 옛 내용·지금 새 내용·지금 옛
  내용을 견준다. 시각은 쓰지 않는다).
- 이관 표식(`pending`/`committed` + 세대)은 `localStorage` 와 **쿠키** 두 곳에 적는다. 꽉 찬 PC 에서는
  `localStorage` 에 표식 한 줄도 못 쓰기 때문이다.
- 표식이 `committed` 인데 저장소가 초기화돼 있지 않으면(사이트 데이터 삭제 등) 옛 내용을 되살리지 않고 빈 상태로
  연다 — 로컬 허브 DB 백업 복구(`sceneBackup`)가 맡는다.
- 옛 자료의 담을 수 없는 모양(배열 아닌 버킷·id 없는 항목·같은 id 의 둘째)은 빼고 옮긴다 — 그것 때문에 이관이
  통째로 실패해 앱이 안 뜨는 일이 없게.
- 저장소를 못 열면 빈 화면으로 진행하지 않고 오류 화면에 머문다(다시 시도 + 옛 자료 원문 내려받기).
  부팅 도중의 예외도 같은 화면으로 간다(`bootSceneStore` 는 던지지 않고 실패를 값으로 돌려준다). 이관 표식을
  못 읽으면(깨진 쿠키 등) '표식 없음'으로 추측해 열지 않는다 — 끝난 이관을 처음으로 보고 옛 내용으로 덮을 수 있다.
- **이관 진단 기록**(`migrationInfo`): 실제로 옮긴 그 트랜잭션에서 한 번, 옮긴 씬 수·옮긴 원문의 글자 수·옛 저장 칸
  전체 글자 수·1KB 시험 쓰기의 결과(됨/할당량 초과/확인 못 함)를 적는다. 설정의 '캔버스 자료'와 전체 내보내기
  파일에 보인다. 신고가 난 PC 에서 "정말 가득 차 있었나"를 가늠하는 **단서**다(확증은 아니다 — 시험 쓰기가 됐다고
  씬을 저장할 여유가 있었다는 뜻은 아니다).

## 사용자에게 보이는 것

- **저장이 안 될 때**: 편집은 화면에 남고 저장소가 간격을 늘려 가며 다시 시도한다. 그동안 탭 줄 오른쪽에
  `⚠ 저장 안 됨 — 눌러서 파일로 내려받기` 가 계속 떠 있다(알림 한 줄은 다른 알림에 덮인다).
- **옛 판 창과 같은 씬을 각자 고쳤을 때**: 묻지 않고 옛 창 쪽 내용을 `[옛 창] 이름` 탭으로 살린다(둘 다 남는다).
  같은 씬이 또 엇갈리면 손대지 않은 사본 탭을 최신으로 갈아 끼운다(탭이 끝없이 늘지 않게).
- **설정 → 캔버스 자료**: `전체 내보내기`(아직 확정 안 된 편집까지 싣는다) / `전체 가져오기`(덮지 않는다 — 없는
  씬만 더하고, 같은 씬인데 내용이 다르면 `[사본] 이름` 탭으로 따로 둔다. 같은 파일을 두 번 가져와도 또 생기지 않는다).
  파일 형식 `mvhub-scenes-full` v1. 그 아래 한 줄에 "지금 캔버스 N개 · 옮길 때: …"(위 진단 기록).
- 입력 저장은 400ms 디바운스에 **최대 대기 2초**(계속 쳐도 2초 안에 한 번 내보낸다), 창이 가려질 때 바로 내보낸다.
- **떠 있는 캔버스 창을 닫을 때**: 닫히는 페이지의 쓰기는 끝난다는 보장이 없다. 그래서 그 창은 pagehide 에서 끌기와 밀린 입력을
  확정한 뒤, 미확정 변경을 씬 단위로 `window.opener` 손잡이에 넘기고 메인 창이 자기 연산으로 잇는다
  (`sceneStore.unconfirmedSceneWrites` → `scenes.adoptCanvasSceneWrites`). 버킷을 통째로 넘기지 않는다 — 고친 씬은 대상이 남아
  있을 때만 바꾸고 새 씬은 없으면 더하며 이미 있으면 바꾼다(먼저 출발한 쓰기가 앞 내용까지만 닿은 경우). 받았다고 답하면 넘긴 연산은 그 창에서 재생하지 않는다. 메인 창이 부팅 중이거나 닫히는
  중이면, 또는 pagehide 가 `persisted` 면 넘기지 않고 그 창이 직접 쓴다(끝난다는 보장은 없다). 메인 창은 저장소를 다시 읽는 데 성공한
  뒤에 캔버스를 돌려받는다 — 실패하면 다시 읽는다. 저장이 막힌 동안은 '떠 있음' 자리에 [전체 내보내기] 안내가 뜬다.
  기록 [닫는 순간](status/캔버스_닫는순간_2026-10-31.md).
- **캔버스 창을 띄울 때·새로 고칠 때**: 띄울 때는 밀린 입력과 저장 중인 쓰기가 모두 확정된 뒤에 연다(`settleSceneWrites`, 3초 안에 안 끝나면 열지 않고 알린다). 새로 고친 창은
  메인 창이 넘겨받은 쓰기가 끝난 뒤에 저장소를 연다(`openerSceneWritesSettled`) — 끝내 확정하지 못하면 스스로 닫고 메인 창이 돌려받는다. 메인 창은 창이 쥔 잠금
  (`mvhub-canvas-window`)으로 신호 없이 끝난 창과 새로 고침 전부터 떠 있던 창을 안다. 잠금은 생존 확인일 뿐 편집 권한이 아니다.
  잠금이 없는 주소(보안 문맥이 아닌 곳)에서는 창의 끝을 확인할 근거가 없어 띄우지 않는다 — 남아 있던 창도 저장소를 열지 않고 물러난다.
- **DB 백업에서 빠지는 씬**: 서버는 씬 1개가 UTF-8 5MiB 를 넘으면 요청 전체를 거절한다. 넘는 씬만 전송에서 빼고
  알린다(올린 것으로 적지 않고 서버의 옛 사본도 지우지 않는다. 작아지면 다시 올린다).

## 사용자가 누른 씬의 공유 서버 보관

2026-11-02 구현 추가. 위 IndexedDB 자동 저장과 로컬 `scene_backup` 미러는 그대로이며, 보관 단추를 누른 씬만 공유 서버 `scene_keep`에 저장한다. 설계 정본은 [캔버스 보관 설계](status/캔버스_보관_설계_2026-11-02.md)이며, 휴지통 복원은 [후속 설계](status/캔버스_보관_휴지통복원_2026-11-02.md)를 따른다. 서버 왕복 실측·공개판 호환·독립 리뷰의 완료 여부는 해당 구현 보고로 확인한다.

- 프런트 `sceneKeep.ts`가 최신 씬·카메라를 사본으로 잡는다. `scenes.exportSceneKeepText`는 제출 이름을 반영하고 `savedAt=0`으로 고정하며 `pendingGenerationAttempts`와 Comfy 실행 상태(`status`·`runId`·`error`)를 제거한다. Comfy 설정·결과는 보존하며 기존 파일 Export와 자동 저장은 이 정규화를 쓰지 않는다.
- 탭 표식이 있으면 보관 창은 앱에서 선택한 공간과 관계없이 그 탭 공간의 프로젝트를 조회한다. 응답 대기·조회 실패 중에는 보관하지 않는다. 표식 없는 탭은 현재 프로젝트 목록을 쓴다.
- 보관본은 계정·프로젝트·이름마다 한 벌이다. 덮어쓰기는 사용자가 본 `overwrite_id`와 `overwrite_revision`이 모두 맞아야 한다. 목록은 본인 것만 보이고 작성자 식별 정보가 담긴 생성 기록 봉투는 일반 상세 응답에 싣지 않는다.
- 설명은 `scene_keep.description`에 최대 2,000자로 저장한다. NFC 정규화만 하고 앞뒤 공백·줄바꿈은 보존하며, 설명만 바꿔도 해시와 revision이 바뀐다. 두 CREATE 정의는 설명을 `data` 앞에 두고, 기존 dev 표만 ALTER로 마지막에 추가한다. baseline은 바꾸지 않는다.
- 보관 창은 같은 프로젝트·정규화한 이름의 설명을 채운다. 직접 입력한 값(빈 글자 포함)은 보존하고, 손대지 않은 설명은 `exists`·`conflict`의 최신 서버 값으로 표시와 재시도 사본을 함께 갱신한다. 설명은 프로젝트·이름별로 기억하므로 확인 취소 뒤 이름을 바꿔도 다른 보관본의 설명을 붙이지 않는다.
- 보관함 카드의 우클릭·메뉴 키로 열기·삭제를 수행한다. 설명은 두 줄 넘침을 실제 높이로 재서 끝을 흐리고, 설명 단추는 전체 글 읽기 창을 연다. 메뉴는 body 포털에 두며, 메뉴·읽기 창의 Esc는 그 겹만 닫는다. 세부 설계는 [보관함 화면·설명](status/캔버스_보관함화면_2026-11-02.md)을 따른다.
- 탭 표식이 없는 보관본은 목록·상세에서 `workspace: null`을 반환한다. 화면은 옛 서버의 `{id: null, name: null}`도 표식 없음으로 처리한다. 빈 계정 DB의 첫 복원에서도 요청에 고정된 계정 UID로 내 서버 결과를 판정한다.
- 허브가 씬의 생성물 참조를 수집한다. 로컬에서 확보하지 못한 참조는 서버 batch로 500개씩 조회하고, 원래 씬 id와 실제 행 id가 다른 경우 `scene_ids`로 대응을 보존한다. 결과 파일 자체는 복사하지 않고 HTTPS 주소·선택 썸네일과 생성 기록을 저장한다. 확보하지 못하거나 상한을 넘은 참조는 `missing_count`로 알린다.
- 열기는 상세를 받은 뒤 `parseSceneImport` 검증→같은 revision의 서버 봉투로 로컬 복원→`id_map` 교체·`rejected` 제거→고정 계정으로 새 탭 가져오기 순서다. 보관본을 열면 휴지통에 있는 결과도 그대로 돌아온다. 휴지통에서는 빠진다. 다만 그 결과의 파일까지 이 PC에서 사라졌으면 빈 카드로 남고 그 결과는 휴지통에 그대로 있다. 내 완료 결과 중 사용 가능한 자산이 있는 항목을 기존 휴지통 복원 함수로 꺼내므로 태그·코멘트·공유·참조를 보존한다. 기존 메인 행은 덮지 않고 삭제 이동 중인 생성물은 막는다. 휴지통에 같은 id가 없고 같은 job의 항목이 없거나 모두 실패로 확정된 경우에는 봉투로 채운다. `confirmSceneWrite` 뒤 계정을 재검사하고, 탭 저장 실패 시 복원한 기록을 보상 삭제하지 않는다.
- 휴지통 복원은 항목마다 계정 전환 잠금 안에서 epoch와 후보를 다시 확인하고, 항목 사이에는 잠금을 놓는다. 60초 시한을 넘으면 남은 항목을 꺼내지 않는다. B1 전송 표식이 남은 실패는 기존 재조정으로 정리한 뒤 진행하며, 정리되지 않으면 409로 중단한다. 다음 열기는 살아 있는 완료 행을 다시 판정하므로 같은 job의 실패 휴지통 행이 남아 있어도 복원한 행에 연결된다.
- 탭이 만들어졌으나 저장 확정이 실패하면 열린 탭의 선택·바인딩 정리 흐름을 유지하며 저장 미확정 경고를 표시한다. `sort_ts`가 없는 생성물은 저장 검사와 복원에서 같은 시각 계산 규칙을 적용한다. `created_at`을 해석할 수 없으면 묶음에서 제외해 `missing_count`에 센다.
- 한 보관본의 봉투는 ASCII JSON 8 MiB, 씬 원문은 UTF-8 5 MiB, 계정 합계는 200 MiB·300행, 묶는 생성물은 2,000개까지다. 미리보기는 좌표 0~1000의 노드 색 칸으로 200개·8 KiB까지다. 부하 상한의 적정성은 별도 격리 실측 대상이다.
- `scene_keep_v1` 표식은 AUTH off 허브에서만 내보낸다. 보관·불러오기 단추는 이 표식이 있을 때만 나타나며, 공유 서버 직접 접속에서는 제공하지 않는다. 보관본 저장·삭제는 라이브러리 변경 알림을 내지 않고 `/restore`만 낸다.

관련 시험: `frontend/tests/sceneKeep.test.tsx`, `frontend/tests/sceneKeepWindow.test.tsx`, `backend/tests/test_scene_keeps.py`. 기존 저장 시험과 별도로 사본 불변성·계정 전환·ID 별칭·복원 거절·덮어쓰기 경합·상한을 확인한다.

## 남은 한계

- **다른 창이 떠 있으면** 한 창의 편집마다 그 창이 씬 전체를 다시 읽는다(15MB 약 5ms, 44MB 약 25ms — 그 창이 치르는
  비용). 숨은 창의 재조회를 미루는 것은 하지 않는다: 그 창의 백그라운드 쓰기(생성 완료 반영 등)가 낡은 화면 값으로
  카드 배열을 통째로 넣어 다른 창의 편집을 덮을 수 있다. 변경분만 읽는 재조회가 후속 후보다.
- 아직 저장소에 확정되지 않은 입력(캔버스 메모리의 입력 대기 최대 2초, 저장 지연, 실패 재시도 중인 연산)은 강제
  종료에서 남지 않을 수 있다. `strict` 는 **확정된** 트랜잭션의 내구성만 높인다.
- 2026-10-15부터 새 앱의 `scene_backup` 미러는 `base_hash` 조건부 쓰기다. 판이 다르면 사본 행을 남긴다.
  옛 앱의 판 없는 형식만 조건 없이 덮는다. 아래 허브 공책 모드는 토큰·rev·지움 표식까지 확인한다.
- 저장소가 지워진 채(다른 창이 새로 만들지도 않은 채) 떠 있는 창은 저장이 실패한다 — '저장 안 됨'으로 알리고
  내보내기가 화면 값을 준다. 새로 고치면 부팅이 빈 상태로 열고 DB 백업 복구가 돈다(그때 내보내지 않은 밀린 편집은 없다).
- 옛 판 탭은 쓰기 잠금을 모른다 — 그 탭을 새로 고치기 전까지 새 판 탭과 함께 쓰면 마지막 쓰기가 이긴다(공개 버전까지의 동작이다). 새 판의 저장 통지는 글자가 달라(`saved-writer`) 옛 판의 `saved` 를 받은 메인 탭이 경고를 띄운다(10분에 한 번, 가려진 탭은 보일 때). 막지는 못한다. 저장소 버전을 올려 막으면 공개판으로 되돌리기가 깨진다. 쓰는 탭이 캔버스를 안 보고 있어도 둘째 탭은 캔버스를 못 쓰고, 탭이 넘어갈 때 미저장 프롬프트·선택은 이어지지 않는다.
- 같은 씬의 충돌이 여럿이면 한 번의 복구에서는 사본이 각각 남지만, 앞선 복구에서 만들어 손대지 않은 사본은 다음 복구가 한 번 갈아 끼운다(옛 창이 같은 씬을 계속 고칠 때 탭이 늘지 않게 하는 동작이다).
  부팅 흡수·가져오기의 `mergeConflicts` 는 같은 씬의 충돌을 하나로 줄인다.
- 다른 씬에 있는 동안 끝난 Comfy 결과는 보드가 없어 받는 길을 타지 않는다 — 그 씬으로 돌아오면 되돌리기 기록의 지문이 어긋나 기록을 잇지 못한다.
- 복구 창으로 다시 붙인 Comfy 결과는 카드에는 보이지만 출력 목록에 없어 View 직접 연결·뒤 노드 입력에는 나오지 않는다(다시 실행하면 나온다).
- 분리 창 잠금을 3초 안에 못 받으면 창이 물러난다 — 메인이 3초 넘게 멈춘 채 분리 창을 새로 고치는 경우 창이 닫히고 메인이 돌려받는다(닫을 때 넘긴 쓰기는 메인에 남는다).
- 글자 노드 편집칸의 되돌리기는 칸 안 기록이다(`lib/textEditHistory`) — 칸을 닫으면 버리고 그 뒤는 캔버스 되돌리기가 맡는다. 글 끝에서 Enter 를 치면 브라우저가 줄 끝 표시용 줄바꿈을 하나 더 두어 저장 글에 줄바꿈이 하나 많다.

## 허브 공책 — 브라우저 공통 캔버스

설계 정본은 [브라우저 공통 설계](status/캔버스_브라우저공통_설계_2026-11-09.md) 4~7장이다.
2026-11-09 작업 계약 `canvas-hub-notebook`의 구현이다(dev `4d00c28e`, 독립 리뷰·격리 브라우저 실측 9사례 통과).
표식 `scene_writer_confirm_v1`은 로컬 허브(AUTH off)에서 기본 켬이다(2026-11-17 [Jay 결정](status/허브공책_기본켬_첫시작확인_2026-11-17.md)이 11-15 [기본 끔 결정](status/배포후보_공책기본끔_2026-11-15.md)을 대체). 출처 미확인·서로 다른 최초 캔버스는 확인을 누른 브라우저의 자료로 시작한다.
정확히 `CONTENT_HUB_SCENE_WRITER=0`이면 끈다. 변수 없음·`1`·빈 값·오타는 켬이다(`364b0dd4` 계약). 이미 시작된 공책은 이 값과 무관하게 토큰 없는 원래 씬 쓰기를 계속 막는다. `=0`은 데이터 롤백이 아니다. 공유 서버(AUTH on)는 꺼져 있다.
`scene_writer_confirm_v1`이 없는 허브에서는 종전 미러·복구·화면을 유지하고, 일반 편집은 공책 키를 읽거나 쓰지 않는다.
서버는 옛 `scene_writer_v1`을 알리지 않는다. 공책 조회·임대·시작·토큰 쓰기·닫기는 `X-MVHub-Canvas-Protocol: confirm-v1` 헤더를 요구하고, 없는 요청은 `409 canvas_client_update_required`로 거절한다. 토큰 해제만 하는 옛 unload beacon은 허용한다. 열린 1011 탭이 기능을 다시 읽거나 옛 표식을 기억하고 있어도 공책을 받아 로컬 판을 교체하지 못한다. 옛 화면의 새로고침 안내를 소급해서 추가할 수는 없으므로 새 화면은 직접 새로고침해서 연다. 서버·프런트는 함께 갱신해야 한다.
첫 확인 전에는 출처(미러 기록의 raws 제외·씬별 장부·제어 자료·허브 지문)를 대조하고, 입력 확정 뒤 최신 씬 내용으로 승인한다. 그 뒤 시작 전송 중에는 원문까지 고정하여 변경 시 다시 묻는다. 로컬 0개는 허브 씬을 불러온다고 안내하며, 이 경우 허브 행을 before_start로 보관하지 않는 기존 계약을 유지한다. 나중에 접기는 같은 계정·같은 출처/허브/개수의 질문에 대해 sessionStorage에 유지한다(저장 차단 시 현재 부품에서만 유지).
복원·보류 자료를 보관하고 시작 전 허브 판을 받으면 합류 기록에 `awaitingStart: true`를 적어, 다음 0개 시작도 확인을 받는다. 로컬·허브가 모두 비면 질문 없이 `empty_notebook`으로 머문다. 표식 없는 옛 `notebookId: ""` 기록은 같은 복원 세대에서 **기준 행이 이어질 때** 합류한 것으로 취급한다. 기준 있는 씬의 허브 행이 하나라도 없거나, 행의 이력이 다르거나, 리비전이 후퇴했거나 같은 리비전의 지문이 바뀌었으면 로컬 원문·제어 자료를 보관하고 선택된 공책으로 합류한다. tombstone과 읽기 실패로 건너뛴 행도 실제 행으로 센다. 정상적으로 리비전이 증가한 기존 공책에서는 ID만 채우고 미전송 편집·지움·되살림·순서·쓰기 진행을 유지한다. 시작 영수증이 남으면 기존 순서 승계를 먼저 마친다. 이는 기존 kv 값의 선택 필드이며 IndexedDB 버전·DB 스키마는 바꾸지 않는다.

확인 대기 기록에는 받은 판의 `receivedFingerprint`도 적는다(카메라 제외). 같은 세대·이력에서 다른 브라우저가 먼저 시작하면, 받은 판 그대로인 경우 두 번째 씬 보관 묶음을 만들지 않고 합류한다. 실제 편집·지움·순서·쓰기 진행이나 복원 세대 변경은 계속 보관하며, 원문이 같은 진행 기록만 추가됐다면 제어 자료만 보관한다. 다만 받은 판과 시작 결과가 같고 동일 복원 세대·이력·임대의 0개 시작 기록만 남았으면 별도 보관 없이 정리한다(커밋 응답 유실). 먼저 확인한 브라우저의 판으로 시작하며, 보류 브라우저가 먼저 확인하면 받아 둔 허브 판을 확정하고 대기 표식을 지운다.

서버도 같은 소유자·프로젝트·이력의 `before_start` 기록이 있고 현재 행이 없으면, base가 붙은 그 ID의 쓰기를 `409 notebook_rejoin_required`로 거절한다. 원문 그대로 재등록하거나 자동 사본으로 공책에 섞는 경로를 함께 막고, 같은 요청 묶음은 롤백한다. base 없는 새 씬·명시적 복원, 현재 행이 있는 정상 충돌·tombstone 되살림은 기존 계약을 유지한다. 기존 `scene_archive` 복합 기본키를 조회하며 스키마를 바꾸지 않는다. 이 서버 방어는 행 없는 옛 base 쓰기에 한정되므로 프런트 합류 판정도 필요하다.

배포 안내: **업데이트 뒤에는 열려 있는 앱 창을 모두 새로 고침해 주세요.** 같은 프로필의 옛 1011 창은 미러 방식으로 편집해 삭제 의도(d)를 남기지 않을 수 있다. 기존 프로필 Web Lock은 유지하지만 화면 판을 확인하는 장치는 아니며, 삭제한 씬의 재등장 가능성은 실제 혼용 실측 전까지 남는 위험이다. 새 코드에서 사라진 ID를 삭제 의도로 추정하지 않는다.

### 판·의도와 맞추기

같은 `kv`에 다음 키를 둔다. DB 버전 `2`·layout `2`는 유지한다.

| 키 | 내용 |
| --- | --- |
| `["b", 버킷, id]` | `{history, rev, hash}` |
| `["d", 버킷, id]` / `["r", 버킷, id]` | 지움 / 명시적 되살림 `{intentId, base}` |
| `["ob", 버킷]` | 순서 판과 미전송 의도 id |
| `["nj", 계정]` / `["na", 계정, 공책 id]` | 한 번만 합류했다는 표시 / 허브 전 사본 |
| `["ns", 계정]` / `["nw", 계정]` | 시작 시도 / 고정한 요청과 재시도 request_id |

씬 삭제·되돌리기·순서 변경은 씬과 의도를 같은 트랜잭션으로 확정한다. 늦은 응답은 같은 의도 id만 거둔다.
맞추기는 **고정 → 판 이후 변경 올리기 → 다시 받기 → 조건부 반영**이며 경합하면 최대 세 바퀴 재시도한다.
업로드 도중 편집됐더라도 원래 id의 `saved`/`same` 영수증은 로컬 판이 고정 때와 같을 때만 판을 잇는다.
최신 글자는 그대로 두며, 새 삭제 의도는 남기고 방금 저장한 판으로 잇는다. 허브 조건 실패가 같은 묶음의 사용자 편집까지 실패시키지 않는다.
미러는 평소 2초 묶음, 계속 편집해도 최대 10초 안에 시작한다.

history가 바뀌었는데 로컬 내용이 기존 판 그대로면, 허브에 행이 있을 때는 올리지 않고 복원본을 받는다. 행이 없을 때만 다시 올린다.
공책 없는 허브를 이미 합류한 프로필이 만나면 살아 있는 허브 행을 공책으로 확정하고, 없으면 현재 로컬 씬으로 시작한다.
그 뒤 맞추기로 가며 합류와 허브 전 사본을 다시 쓰지 않는다.

못 올린 씬은 원래 id를 받기 전에 새 id의 로컬 `[옛 창]` 사본으로 보존한다. 사본이 5MiB 이하로 줄면
그 사본 id를 새 씬으로 올린다. 같은 id 수신은 실행 연결을 유지하지만 새 id 사본은 능동 실행 연결을 빼고 원래 표식을 참고용으로 남긴다.
손상된 허브 씬은 해당 행만 건너뛰고 알린다. 허브 원본과 이미 있는 로컬 행을 보존하며, 정상 행은 계속 받는다.

**규칙 2의 제한된 예외:** 분리 창 인계 연산은 재생 시 전달받은 현재 임대 세대를 검사한다. 인계의 세대와 같으면 원래 씬에 적용하고,
다르면 고정한 사본 id로 `[옛 창]`을 만든다. 일반 편집은 여전히 순수 재생이며, 인계 중 id·시각을 새로 만들지 않는다.
표식이 없거나 세대가 같으면 인계 사본 본문을 미리 만들지 않는다.

### 허브·MCP·되돌리기 호환

- 토큰 검사와 DB 반영은 계정별 잠금 안에서 직렬화한다. 공책 계정의 옛 토큰 없는 PUT은 409다.
  지우기는 본문을 남긴 표식이며 옛 GET에는 살아 있는 행만 나온다. 판은 `(history, rev, data_hash)`로 검사한다.
- MCP 완료는 씬 PUT의 `mcp_complete`에 싣는다. 원래 id의 `saved`/`same`과 `mcpAttachmentReceipts` 확인을
  같은 DB 트랜잭션에서 마친 `mcp_done`만 완료 근거다. `copied`·`too_big`은 대기로 남기며 옛 완료 API를 부르지 않는다.
  처리 영수증이 있어 사용자가 삭제한 카드를 재전달로 다시 붙이지 않는다. 숨긴 씬의 대기는 시작 확정 때 취소한다.
- 앱의 DB 복원·계정 리맵은 새 history를 만든다. 복원 DB에 공책 id가 없으면 복원한 살아 있는 행으로 확정한다.
  리맵은 서로 다른 살아 있는 두 행을 사본으로 보존하고, 살아 있는 행이 지움 표식보다 우선한다.
- DB 쓰기 프로토콜·`release/compatibility.json`·기존 기본키/유일키는 바꾸지 않는다. 스키마는 칸·표·트리거만 더한다.
  공책 계정 트리거는 옛 허브의 첫 덮어쓰기 직전 내용(`data_hash = rev_hash`)과 매 삭제 직전 내용을 별도로 보관한다.
  중복 키는 계정·프로젝트·씬·history·사유·내용 지문이다. X → Y → 삭제라면 X와 Y를 각각 남긴다.
- 새 허브 시작 때 `data_hash != rev_hash`인 행을 정리해 rev·지문을 맞추고, 고정 사본 id로 필요한 보관본을 살린다.
  옛 허브가 바꾼 지움 표식 행은 되살리되 삭제된 본문을 사본으로 만들지 않는다. 계정 정리는 공책 → 씬 → 보관 순서다.
  공개판에서 지운 계정의 보관본은 새 판에서 같은 계정을 다시 정리하기 전까지 남는 경계가 있다.
- 작업자 백업의 서버용 `canvases` 요약은 살아 있는 씬 + 카드 소속 행 수다. 보관 행 수는 이 PC 화면용이며
  서버 v2 매니페스트에 새 요약 키를 보내지 않는다.

구현 시험과 브라우저 실측은 구분한다. 격리 실측 입구는 `tools/verify_canvas_notebook_measure.py`이며
실행·구형 허브 되돌리기·성능 비교 결과는 총괄이 별도로 확인한다. 이 문서의 갱신은 그 검증을 대신하지 않는다.
