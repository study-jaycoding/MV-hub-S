## PR 인계 (pr-review-2026-10-21-r1)

새 기능 묶음·후보부터 [PR_GATE](PR_GATE.md)를 적용한다. 기존 적대적 검토와 다음 묶음·영향 범위 규칙을 유지하고 PR에 같은 전체 리뷰를 반복하지 않는다. 총괄은 기존 작업 기록과 PR에 head/base·실제 검사 SHA, 지적 ID·수정 커밋·재검토 결과·미해결을 연결한다. main 병합과 배포는 각각 사용자 직접 승인 후에만 한다. 이미 진행 중인 후보·세션·작업실은 강제 전환하지 않는다.

사용자가 맡긴 새 기능 묶음이 완성되면 별도 PR 요청을 기다리지 않고 PR_GATE의 2026-10-21 허용 범위에서 Draft PR과 리뷰 기록을 준비한다. 진행 중인 다른 변경이나 기존 고정 후보를 임의로 포함하지 않는다.

## 수정과 검토의 묶음 (2026-10-15 Jay 결정)

"하나하나 만들 것을 일일이 실측하고 고치면 끝이 없다. 배포 준비 전이나 검토를 지시하면 그때 새로 만든 것들을 모두 검토한다 —
한꺼번에 문제를 찾아서 한 번에 고친다." (10-14 에 수정 하나마다 전체 시험 15분·Codex 왕복 3~5회·격리 실측을 돌려 작은 화면
수정이 하루 종일 걸렸고, 두 세션이 같은 지적을 따로 고치는 중복도 났다.)

- **평소 = 빠른 수정**: 논리적인 변경 묶음별로 고친다 → 자기 검토·관련 시험과 필요한 타입 검사/빌드 → 다음 수정.
  버그는 변경 전 재현 또는 유효한 실패 근거를 확보한다. 수정마다 독립 리뷰·전체 실측·전체 시험·모델 왕복을 돌리지 않는다.
  작업판 기록은 `구현`까지 적고 `리뷰`·`마감`은 묶음 검토 때 적는다. 구현 완료와 검토 완료를 구분한다.
- **묶음 검토 = 기능 묶음 완성 또는 Jay의 `검토`·`배포 준비` 요청 때**: 해당 기능의 변경 범위를 고정한다.
  누적 검토이면 선택한 후보 SHA와 포함된 변경·의존성을 기록한다. dev의 미커밋 변경 전체나 진행 중인 다른 작업을 임의로 포함하지 않는다.
  제품 변경 묶음은 독립 리뷰·필요한 사용 흐름/성능 실측·전체 시험을 한 차례씩 계획하고, 같은 대상·환경의 유효한 결과는 재사용한다.
  문서·역할 지침만 바뀌면 본문 일치·링크·설정 형식·정책 충돌을 확인하며 제품 전체 시험·실측은 강제하지 않는다.
  지적은 하나의 목록으로 모아 담당자와 재현 조건을 붙이고 한 담당자가 각 지적을 수정한다. 서로 같은 문제를 중복 수정하지 않는다.
  수정 후에는 해당 지적 재현과 변경 영향의 관련 시험을 다시 확인한다. 공유 계약·DB·위험 경계 변경, 새 반례,
  영향 범위를 한정할 수 없는 실패가 있으면 필요한 전체 시험·독립 검토를 확대한다. 횟수를 채웠다는 이유로 실패를 통과시키지 않는다.
- **예외 = 위험 변경**: 위 표의 설계 합의는 구현 전, 독립 리뷰·필요 검증은 실사용 실행 전에 마친다.
  검토용 격리 사본에서의 비파괴 시험은 가능하다. 자동 시험은 비용 없이, 사용자 요청의 실제 생성 확인은 별도 실사용 모드에서 한다.
- 사소한 화면·문구·사용성 지적은 담당 작업실·재현 조건과 함께 기록하고 묶음 검토 때 함께 고친다.
  관련 시험·빌드 실패, 저장 오류, 데이터 손상·유실, 보안·권한 문제, 중복 과금 위험은 즉시 원인 작업실에서
  해결하고 관련 확인을 다시 한다. 해당 문제가 남은 변경은 통합·배포하지 않는다. 즉시 수정한다고 매번 전체 실측을 반복하지는 않는다.

## 전체 순서와 독립성

위험 변경은 1~6을 따른다. 빠른 수정에는 4의 구현·자기 검토·관련 시험만 적용한다.
묶음 검토는 기존 요구·설계와 고정된 대상을 받아 5~6부터 진행하며, 새 요구나 설계 결함이 드러난 부분만 1~3으로 돌아간다.

1. Claude가 범위·데이터 흐름·위험 경계·완료 조건을 설계한다. 화면 작업이면 별도 디자인 역할이 화면/상태별 기준을 보완한다.
2. Codex가 실제 호출 경로·실패 조건을 확인하고 반례와 구현 계획을 낸다.
3. 두 모델의 실제 응답으로 설계를 확정한다. 해결되지 않은 A/B 선택은 근거와 추천을 Jay에게 보고한다.
4. 합의된 소유자(Codex 기본값)가 구현하고 자기 검토·관련 시험을 수행한다.
5. 구현하지 않은 모델의 별도 세션이 독립 리뷰한다(Codex 구현→Claude, Claude 구현→Codex). 중요한 변경은 설계 세션과도 분리한다. 검증 담당은 부족한 실측만 수행하며 동일 대상·환경의 기존 시험 근거를 재사용한다.
6. 지적을 모아 원인 작업실에서 수정하고 영향 범위를 다시 검증한다. 기존 두 담당자가 최종 대상·근거·미해결을 대조한다. 마감만을 위한 추가 에이전트는 만들지 않는다.

리뷰어에게 요구·설계 계약·안전선·대상 변경은 주되, 구현자의 자기 정당화나 이전 승인 결론을 먼저 주입하지 않는다.
구현자의 자기 검토는 독립 리뷰를 대신하지 않는다. 같은 모델의 추가 검토를 상대 모델의 독립 리뷰 완료로 기록하지 않는다. 상대 호출 불가와 미확인을 보고한다. 리뷰와 실측은 서로 대신할 수 없다.
같은 파일의 쓰기는 한 번에 한 담당자만 한다. 독립 모듈을 병렬화하면 각 담당 경로를 먼저 나누고 총괄이 합친다.

## 작업판 기록

Jay 는 작업 흐름 판(Claude Code 모드 `mvhub-board`)에서 작업마다 위 순서의 몇 단계인지·담당·남은 것을 본다(2026-10-14 Jay 결정).
판은 git(작업 폴더·브랜치·커밋 안 한 파일·dev 에 들어갔는지)과 아래 기록을 읽는다.

- **단계를 넘어갈 때마다** 그 작업 폴더 맨 위의 `.mvhub-board.txt` 에 한 줄을 덧붙인다. 지우거나 고치지 않는다.
  git 이 무시하는 파일이다(저장소 공통 `info/exclude`) — 커밋하지 않는다.
- 한 줄 = `시각 | 작업 이름 | 단계 | 담당 | 남은 것`. 단계는 `설계`·`사전검토`·`합의`·`구현`·`리뷰`·`마감`·`통합`·`게이트`·`배포` 중 하나,
  다 끝나면 `끝`. Jay 결정을 기다리면 `·Jay`, 보류면 `·보류` 를 붙인다(`마감·Jay`). 같은 작업은 같은 이름으로 적는다(판이 이름으로 묶는다).
- 적는 법(PowerShell — 작은따옴표로 `$` 가 풀리지 않게):
  `Add-Content -Encoding utf8 .mvhub-board.txt ('{0} | 편집 탭 그림 길이 | 구현 | Codex | 리뷰·실측' -f (Get-Date -Format 'yyyy-MM-dd HH:mm'))`
- 읽기 전용 역할(독립 리뷰·실측)은 적지 않는다 — 그 역할을 부른 주 세션이 결과를 받고 적는다.
- 이 기록은 판의 표시용이다. 리뷰·검증·완료의 증거는 아래 '검증 대상과 완료 조건'을 따른다.

## 검증 대상과 완료 조건

- 코드 검증 대상은 Git SHA만으로 정하지 않는다. 실제 브랜치·SHA·dirty 여부·대상 diff와 파일 SHA-256을 함께 기록한다.
  검증 중 다른 변경이 생기면 영향을 판정하고 관련 확인을 다시 한다. 임의의 stash·WIP 커밋은 만들지 않는다.
- 결과에는 역할·실행 주체/세션 식별자·대상·수행 범위/명령·증거 위치·결과·미해결을 남긴다.
  요청한 모델·추론 수준과 실제 모델 메타데이터를 구분한다. 실제 ID를 확인할 수 없으면 미확인으로 기록한다.
  설계 검토는 코드 SHA 대신 운영안 버전을 쓸 수 있다.
- 지적 상태는 `수정 후 검증` / `오탐 근거 확인` / `미해결·보류` / `Jay 결정 필요`로 구분한다.
- 필수 범위에 미확인·보류가 남으면 **공동 완료가 아니다**. 사용자와 범위를 명시적으로 줄였을 때만 축소 완료로 기록한다.
  상대 호출 실패나 응답 없는 역할을 암묵적으로 통과시키지 않는다. `상대 보고` 표기는 출처 구분이지 독립 확인이 아니다.
- 제품 코드 완료·현황 문서 정리 완료·설정 로드·호출 성공·권한 차단·실제 배포를 별도 결과로 적는다.
  두 모델이 동의해도 실패한 시험이나 부족한 실측 근거가 사라지는 것은 아니다.

## 시간·사용량과 격리

작업 시작 전에 필요한 역할과 시간·호출 또는 토큰 한도를 적는다. 모델·추론 수준은 아래 동적 선택 기준으로 정한다.
두 번 왕복했으면 같은 지적이 반복되는지 점검한다. 새 재현·반례·측정과 진전이 있을 때만 정한 한도 안에서 계속한다.
커밋 SHA만 바뀐 것은 새 근거가 아니다. 상한 도달은 완료가 아니라 보류이며, 계속할 가치와 남은 판단을 보고한다.
고정 절감률이나 성능 향상을 약속하지 않는다. 시범에서는 경과 시간·호출/사용량·재작업·발견 결함을 기록해 비교한다.

역할별 도구·승인 모드·샌드박스 제한을 고정하지 않고 호스트의 실제 권한을 상속한다. 상위 제한과 제품 안전선은 유지한다.
설계·리뷰·설명은 제품 파일을 수정하지 않는다. 이는 행동 책임이며 기술적인 쓰기 차단 보장이 아니다.
리뷰 시작·종료 때 Git 상태와 대상 파일 지문을 대조한다. 변경이 보이면 불변으로 통과시키지 말고 쓰기 주체와 영향부터 확인한다.
역할 위반이면 중단·범위 보고 후 기존 사용자 변경을 보존하는 복구안을 제시한다. 다른 세션의 변경을 임의 되돌리지 않는다.
읽기 전용 진단 호출은 선택할 수 있으며 그때의 차단 관측을 전체 권한 세션에 일반화하지 않는다.
실측은 임시 데이터·포트·프로세스·산출물을 분리하고 제품 코드를 고치지 않는다. 쓰기가 필요한 시험은 격리 사본에서 실행한다.
로그와 임시 결과는 Git 제외 경로나 작업 폴더 밖에 둔다. 시작한 프로세스는 식별자와 종료 상태를 기록한다.
기능 구현은 위 작업실 선택 규칙을 따른다. 읽기 전용 리뷰마다 새 checkout/worktree를 만들지는
않는다. 검증 대상을 고정할 수 없거나 쓰기 충돌이 있으면 검토·실측용 사본도 따로 분리한다.
기본 dev와 필요한 임시 작업실은 [WORKROOMS](WORKROOMS.md)의 데이터·포트·브라우저 분리 규칙을 따른다.
임시 작업실의 변경이 dev에 자동 반영됐다고 보고하지 않는다. 상시 통합 브랜치로의 병합 의무는 종료했다.

## 모델·추론 선택 (2026-10-21 사용자 승인)

역할·작업 부하에 따라 총괄이 호출마다 지원 모델과 추론 수준을 실제로 선택한다. 공통 운영안의 모델 기준을 참조한다.
이전 2026-10-14 고정 배치와 우회 호출 설명은 동적 선택으로 대체하며 당시 배치 결정/검증은 [도입 기록](status/문서정리_운영안_2026-10-14.md)에 보존한다.

- MV Hub의 DB 마이그레이션·인증/권한·삭제/복구·업데이터·복잡한 공유/동기화 설계와 리뷰는 처음부터 고성능/high 이상을 선택한다.
  구현은 어려운 구간만 상향하고, 검증은 시험 설계·결과 해석이 어려울 때 상향한다. 단순 실행·대기만으로 올리지 않는다.
- 동일 문제가 반복되거나 증거가 모순되면 자료/계약 누락을 먼저 확인한 뒤 해당 쟁점만 상향한다. 최고 추론 수준을 모든 단계의 기본값으로 쓰지 않는다.
- 추적된 역할 정의 4개에는 `model`·`effort`·`model_reasoning_effort`를 고정하지 않는다. 생략 자체는 자동 라우팅이 아니라 부모 모델 상속이다.
  총괄이 호출 인자로 선택값을 전달하고 요청 모델·추론·선택 이유와 실제 응답 메타데이터를 기록한다. 실제값이 없으면 미확인으로 둔다.
- `.claude/settings.json`과 `.codex/config.toml`은 주 세션의 시작 기본값이다. 모델 선택 정책이나 역할별 고정값으로 해석하지 않는다.
  모델별 기본 effort보다 명시 호출값이 적용됐는지 확인하고, 지원하지 않는 호출 도구이면 지원되는 CLI 세션으로 인계한다.
- 현재 세션에 모델 이름을 말한 것만으로 바뀌었다고 하지 않는다. 설정 전환을 확인할 수 있으면 재사용하고, 아니면 필요한 구간만 새 세션으로 넘긴다.
  호출별로 공유 역할 파일을 덮어쓰지 않는다. 모델 거절·예상 밖 대체·응답 없음은 합의/리뷰 성공이 아니다.
- MCP/네이티브 역할 호출이 실제 지원하는 모델 선택 방식을 먼저 확인한다. CLI fallback은 역할 본문을 전달하고 모델/추론을 명시한다.
  Claude는 `--model`·`--effort`, Codex는 `--model`·`-c model_reasoning_effort=...`를 사용한다. 역할 파일 경유와 본문 전달을 구분해 기록한다.
- 읽기 전용/격리 진단은 호출별로 선택할 수 있다. 전체 권한은 제품 데이터·서버·배포에 대한 추가 승인이 아니며 쓰기가 필요한 시험의 사본/데이터 분리는 유지한다.
- 실제 CLI 경로·`--version`·작업 폴더·응답·종료 코드를 확인한다. `CODEX_CLI_PATH`는 존재와 실행 확인 뒤 사용하고 앱 경로 성공을 npm 경로 성공으로 기록하지 않는다.
  모델 후보는 실행 시점 지원 목록과 대조하며 임의 이름/조용한 하향을 사용하지 않는다. 호출 불가이면 보류·보고하고 같은 실패를 무한 반복하지 않는다.

권한 상속·역할 로드·응답 회수·모델 메타데이터·제품 파일 불변·기술적 쓰기 차단은 서로 다른 관측이다.
격리/차단을 실제로 주장할 때만 그 범위의 별도 시험을 근거로 삼는다. 권한을 상속하는 역할 설치의 성공 조건에 쓰기 차단을 요구하지 않는다.
설정 형식은 아래 공식 근거, 구체 경로·버전·시점별 증거는 [도입 기록](status/문서정리_운영안_2026-10-14.md)을 따른다.

## 스킬과 문서 사용

두 도구는 아래 조건에서 **사용자가 다시 지시하지 않아도 담당자가 먼저 적용**한다. 설치되어 있다는 사실과 실제 사용은 구분한다.

| 시점·조건 | 적용할 도구와 확인 |
|---|---|
| 코드 설계·구현·수정·리팩터링·의존성 선택 | 설치된 `ponytail` 본문을 세션에서 한 번 읽고 최소한의 완전한 변경을 선택한다. 기존 구현·표준 기능을 먼저 확인하고 호출부·시험·설정까지 필요한 수정은 끝낸다. 안전 검사와 실패 처리를 줄이지 않는다 |
| 코드 변경 리뷰 | `ponytail-review` 본문을 읽고 정확성·보안·부하·누락 시험·성능·불필요한 복잡성 순서로 점검한다. 독립 리뷰 세션과 실제 시험을 대신하지 않는다 |
| 낯선 모듈 탐색·버그 원인 추적·공용 함수/계약 변경 전 | graft `skeleton`·`grep`·`callers` 중 필요한 것을 사용해 구조와 호출 후보를 좁힌다. 특히 버그 수정과 반환값·인자 변경은 실제 호출부까지 확인한다 |
| 동작·공용 모듈·의존 관계를 바꾼 뒤 | 미커밋 변경은 graft `blast`, 커밋된 변경은 작업 기준 SHA로 `blast --base <SHA>`를 실행해 영향 후보와 관련 시험을 확인한다. 실제 diff의 범위와 맞는지 대조하고 필요한 시험을 선택한다 |
| 문구·서식·역할 지침만 바꾼 작업 | 본문·링크·설정 형식을 확인한다. 소스 색인이 낡아 조회에 필요한 경우를 제외하고 graft 재빌드·호출 관계 분석·제품 전체 시험은 생략한다 |

graft는 프로젝트 지침의 **래퍼로만** 호출한다. 색인이 낡았으면 쓰기 가능한 담당자가 먼저 build/check를 수행한다.
`init`·외부 업로드·deep/유료 모델 호출을 이 규칙으로 허용하지 않는다. `ponytail-audit` 전수 검사는 전체 감사가 요청된 경우에만 사용한다.
graft 결과는 탐색 후보다. 중요한 결론은 실제 소스·호출부·시험으로 확인하고, 도구가 제시하는 시험 연결 비율을 실행 커버리지로 간주하지 않는다.
`blast --base`는 기준과 HEAD의 커밋 차이여서 미커밋 변경을 포함하지 않는다. 두 종류가 섞이면 각각 확인하고, 미추적 새 파일은 별도 점검한다. 기본 `blast`는 작업 트리가 깨끗하면 직전 커밋으로 돌아가므로 출력 기준을 반드시 확인한다.
절감 토큰 추정값도 실제 시간·크레딧 절감 실측으로 보고하지 않는다.

Claude 역할의 `skills`는 미리 읽게 하는 설정이며, 설치·허용·실제 로드는 별도로 확인한다.
본문 주입이 확인되지 않으면 설치된 정확한 `SKILL.md`를 읽는다. CLI로 역할을 대신할 때도 이 절차와 역할 책임·제품 안전선을 전달한다.
Codex 하위 역할에도 필요한 스킬 경로와 이 절의 적용 조건을 전달하며, 부모가 읽었다는 이유만으로 자식의 로드를 확정하지 않는다.
리뷰어는 기존 색인의 정적 조회와 원본 읽기를 할 수 있으나 인덱스 재빌드나 제품 변경은 하지 않는다. 필요한 쓰기 작업은 총괄이 수행하고 근거를 전달한다.
설치 부재·실행 실패·권한 제약이면 미사용 이유를 기록하고 `rg`·직접 읽기·기존 시험으로 대체한다. 사용할 수 없는 스킬을 적용했다고 쓰지 않는다.

완료 기록에는 **실제 읽은 스킬·실행한 graft 명령과 얻은 근거**, 해당하는데 생략했다면 그 이유를 짧게 남긴다.
테스트 절차를 역할/스킬마다 복제하지 않고 [TESTING](TESTING.md)과 기존 도구를 참조한다.

현재 상태는 [CURRENT_STATUS](CURRENT_STATUS.md)에 짧게, 설계·검토·증거는 관련 기존 문서에 둔다.
장기 보존할 새 작업 기록이 필요할 때만 `status/`에 만들고, 본문에 `owner`, `reviewer`, `status`, `touched_paths`, `updated`를 남긴다.
YAML `status`는 문서 위상이고 본문의 `status`는 작업 단계다. 과거 결정·수치를 오늘 사실로 덮지 않는다.

- 훅은 알려진 편집/명령의 누락·불일치를 검사하는 보조 장치다. 현재 클라이언트의 로드·차단·오류 동작을 따로 확인한다. 임의 셸/MCP·수동 조작·다른 작업실·진행 중인 세션 전체의 차단이나 상대 리뷰의 품질을 보장하지 않는다. 적용/시험 근거는 [기존 도입 기록](status/문서정리_운영안_2026-10-14.md)에 남긴다.
