# Claude · Codex 작업 운영

이 문서는 역할 호출과 완료 판단의 기준이다. 제품의 설계·시험·배포 계약을 다시 정의하지 않는다.
안전·Git 권한은 [AGENTS](../AGENTS.md)·[CLAUDE](../CLAUDE.md), 시험 방법은 [TESTING](TESTING.md),
문서 위상은 [README](README.md)를 따른다. 설정·호출 실증 상태는 [도입 기록](status/문서정리_운영안_2026-10-14.md)에 구분한다.

## 작업 크기와 호출

작업 폴더 선택은 [작업실 운영](WORKROOMS.md)을 따른다. 요청을 받은 앱이나 현재 폴더만으로
담당 범위를 정하지 않는다. 현재 상태·기존 작업실·담당 경로를 확인하고, 새 기능·개선은 해당
기능 작업실에서 진행한다. 기존 진행 작업은 그대로 두고, 작은 문서·문구 수정은 충돌이 없는
현재 폴더에서 처리할 수 있다. 작업 위치와 확인할 화면을 사용자에게 짧게 알린다.

| 작업 | 운영 |
|---|---|
| 작고 되돌리기 쉬운 문구·서식·단순 수정 | 한 담당자의 구현·자기 검토·관련 확인으로 끝낸다. 모델 왕복을 강제하지 않는다 |
| 일반 기능 | 짧은 공동 설계·구현·독립 리뷰. 실측 필요 여부는 변경의 완료 조건으로 정한다 |
| 구조·DB·인증·공유·동시성·배포·되돌리기 어려운 변경 | 아래 전체 순서. 위험 경계를 발견하면 진행 중에도 이 단계로 올린다 |

역할은 네 가지 기능이며 상주 프로세스 네 개가 아니다. 현재 주 세션이 해당 역할이면 재호출하지 않는다.
작업을 맡길 때 목표·경로·입력·제약·완료 조건·시간/호출 한도를 함께 전달한다.

| 역할 | 기본 실행 주체 | 입력 → 결과 |
|---|---|---|
| 총괄·설계 | Claude 주 세션 또는 `mvhub-design` | 요구·현황·계약 → 범위·대안·완료 조건·작업 소유권 |
| 사전 검토·구현 | Codex 주 세션 또는 `mvhub-implement` | 초안·소스 → 반례·구현 계획 → 합의 후 코드·자기 검토·관련 시험 |
| 독립 리뷰 | 설계/구현과 분리된 Claude `mvhub-review` | 요구·합의 계약·대상 변경 → 근거가 있는 지적·미확인 범위 |
| 실측·검증 | 구현과 분리된 Codex `mvhub-verify` | 완료 조건·고정 대상 → 격리 환경의 관측·수치·재현 증거 |

사전 검토와 구현은 기본적으로 같은 Codex 세션에서 한다. 중요한 변경에서 독립된 반론이 필요할 때만 추가 세션을 연다.
배포 전용 상주 역할은 두지 않는다. 배포는 기존 Gate·고정 릴리스 폴더·Jay 지시를 만족한 담당자가 수행한다.

## 전체 순서와 독립성

1. Claude가 범위·데이터 흐름·위험 경계·완료 조건을 설계한다.
2. Codex가 실제 호출 경로·실패 조건을 확인하고 반례와 구현 계획을 낸다.
3. 두 모델의 실제 응답으로 설계를 확정한다. 해결되지 않은 A/B 선택은 근거와 추천을 Jay에게 보고한다.
4. 합의된 소유자(Codex 기본값)가 구현하고 자기 검토·관련 시험을 수행한다.
5. 별도 Claude 세션이 독립 리뷰한다. 검증 담당이 필요한 실측을 수행한다.
6. 지적을 수정하고 변경 영향을 다시 검증한다. 두 모델이 최종 대상과 근거·미해결 목록을 대조한 뒤 마감한다.

리뷰어에게 요구·설계 계약·안전선·대상 변경은 주되, 구현자의 자기 정당화나 이전 승인 결론을 먼저 주입하지 않는다.
구현자의 자기 검토는 독립 리뷰를 대신하지 않는다. 리뷰와 실측은 서로 대신할 수 없다.
같은 파일의 쓰기는 한 번에 한 담당자만 한다. 독립 모듈을 병렬화하면 각 담당 경로를 먼저 나누고 총괄이 합친다.

## 작업판 기록

Jay 는 작업 흐름 판(Claude Code 모드 `mvhub-board`)에서 작업마다 위 순서의 몇 단계인지·담당·남은 것을 본다(2026-10-14 Jay 결정).
판은 git(작업 폴더·브랜치·커밋 안 한 파일·dev 에 들어갔는지)과 아래 기록을 읽는다.

- **단계를 넘어갈 때마다** 그 작업 폴더 맨 위의 `.mvhub-board.txt` 에 한 줄을 덧붙인다. 지우거나 고치지 않는다.
  git 이 무시하는 파일이다(저장소 공통 `info/exclude`) — 커밋하지 않는다.
- 한 줄 = `시각 | 작업 이름 | 단계 | 담당 | 남은 것`. 단계는 `설계`·`사전검토`·`합의`·`구현`·`리뷰`·`마감`·`통합`·`게이트`·`배포` 중 하나,
  다 끝나면 `끝`. Jay 결정을 기다리면 `·Jay`, 보류면 `·보류` 를 붙인다(`마감·Jay`). 같은 작업은 같은 이름으로 적는다(판이 이름으로 묶는다).
- 적는 법(PowerShell — 작은따옴표로 `$` 가 풀리지 않게):
  `Add-Content -Encoding utf8 .mvhub-board.txt ('{0} | 편집 탭 그림 길이 | 구현 | Codex | 리뷰·실측' -f (Get-Date -Format 'yyyy-MM-dd HH:mm'))`
- 읽기 전용 역할(독립 리뷰·실측)은 적지 않는다 — 그 역할을 부른 주 세션이 결과를 받고 적는다.
- 이 기록은 판의 표시용이다. 리뷰·검증·완료의 증거는 아래 '검증 대상과 완료 조건'을 따른다.

## 검증 대상과 완료 조건

- 코드 검증 대상은 Git SHA만으로 정하지 않는다. 실제 브랜치·SHA·dirty 여부·대상 diff와 파일 SHA-256을 함께 기록한다.
  검증 중 다른 변경이 생기면 영향을 판정하고 관련 확인을 다시 한다. 임의의 stash·WIP 커밋은 만들지 않는다.
- 결과에는 역할·실행 주체/세션 식별자·대상·수행 범위/명령·증거 위치·결과·미해결을 남긴다.
  요청한 모델·추론 수준과 실제 모델 메타데이터를 구분한다. 실제 ID를 확인할 수 없으면 미확인으로 기록한다.
  설계 검토는 코드 SHA 대신 운영안 버전을 쓸 수 있다.
- 지적 상태는 `수정 후 검증` / `오탐 근거 확인` / `미해결·보류` / `Jay 결정 필요`로 구분한다.
- 필수 범위에 미확인·보류가 남으면 **공동 완료가 아니다**. 사용자와 범위를 명시적으로 줄였을 때만 축소 완료로 기록한다.
  상대 호출 실패나 응답 없는 역할을 암묵적으로 통과시키지 않는다. `상대 보고` 표기는 출처 구분이지 독립 확인이 아니다.
- 제품 코드 완료·현황 문서 정리 완료·설정 로드·호출 성공·권한 차단·실제 배포를 별도 결과로 적는다.
  두 모델이 동의해도 실패한 시험이나 부족한 실측 근거가 사라지는 것은 아니다.

## 시간·사용량과 격리

작업 시작 전에 필요한 역할과 시간·호출 또는 토큰 한도를 적는다. 모델은 아래 승인된 프로젝트 배치를 기본으로 사용한다.
두 번 왕복했으면 같은 지적이 반복되는지 점검한다. 새 재현·반례·측정과 진전이 있을 때만 정한 한도 안에서 계속한다.
커밋 SHA만 바뀐 것은 새 근거가 아니다. 상한 도달은 완료가 아니라 보류이며, 계속할 가치와 남은 판단을 보고한다.
고정 절감률이나 성능 향상을 약속하지 않는다. 시범에서는 경과 시간·호출/사용량·재작업·발견 결함을 기록해 비교한다.

정적 리뷰는 도구를 읽기로 제한한다. 프롬프트의 '쓰기 금지'는 운영체제나 도구의 차단을 대신하지 않는다.
실측은 임시 데이터·포트·프로세스·산출물을 분리하고 제품 코드를 고치지 않는다. 쓰기가 필요한 시험은 격리 사본에서 실행한다.
로그와 임시 결과는 Git 제외 경로나 작업 폴더 밖에 둔다. 시작한 프로세스는 식별자와 종료 상태를 기록한다.
기능 구현은 위 작업실 선택 규칙을 따른다. 읽기 전용 리뷰마다 새 checkout/worktree를 만들지는
않는다. 검증 대상을 고정할 수 없거나 쓰기 충돌이 있으면 검토·실측용 사본도 따로 분리한다.

## 모델 배치 (2026-10-14 승인)

| 역할·단계 | 기본 모델 · 추론 수준 | 상향 모델 · 추론 수준 |
|---|---|---|
| Claude 설계·총괄 | `claude-opus-5-5` · `medium` | `claude-fable-5-1` · `high` |
| Codex 사전 검토 | `gpt-6.1-sol` · `high` | `gpt-6-astra` · `high` |
| Codex 구현 | `gpt-6.1-sol` · `medium` | `gpt-6-astra` · `high` |
| Claude 독립 리뷰 | `claude-opus-5-5` · `high` | `claude-fable-5-1` · `high` |
| Codex 실측·검증 | `gpt-6.1-sol` · `medium` | `gpt-6-astra` · `high` |
| 필요할 때만 부르는 문서 분류·단순 요약 보조 | `claude-sonnet-5-5` 또는 `gpt-6-luna` · `medium` | 판단이 필요하면 담당 역할에 반환 |

- DB 마이그레이션·인증/권한·삭제/복구·업데이터·복잡한 공유/동기화 설계와 리뷰는 처음부터 상향한다.
  구현은 어려운 구간만 상향하고 나머지는 기본 모델을 쓴다. 실측의 상향은 시험 설계나 결과 해석이 어려울 때다.
- 일반 작업도 두 차례 수정 뒤 같은 문제가 반복되거나 증거가 모순되면 재현 자료를 정리해 해당 쟁점만 상향한다.
  정해진 테스트를 실행·기다리는 일만으로 상향하지 않는다. `xhigh`는 별도 난제 판단 때만, `max`는 기본으로 쓰지 않는다.
- 총괄이 호출 전에 역할·단계·모델·추론 수준을 선택한다. 현재 세션에 다른 모델 이름을 말하는 것만으로 설정이 바뀌지는 않는다.
  주 세션이 이미 해당 역할·설정이면 재호출하지 않는다. 마지막 합의용 에이전트를 추가하지 않는다.
- Claude 역할 파일은 Opus 5.5를 명시한다. 상향은 같은 역할의 호출별 `model`·`effort` 재정의로 처리한다.
  두 값 중 하나라도 재정의를 지원하지 않거나 적용을 확인할 수 없으면 같은 역할 본문과 도구 제한을 전달한 새 CLI 세션에
  `--model claude-fable-5-1 --effort high`를 명시하고, 역할 파일 경유 호출과 구분해 기록한다.
- Codex 역할 파일은 구현/실측용 Sol `medium`을 명시한다. custom 파일 값이 호출별 override보다 우선하므로
  `mvhub-implement`를 그대로 부르면서 `high`/Astra가 적용됐다고 간주하지 않는다.
  사전 검토(`Sol high`)·상향(`Astra high`)은 일반 새 세션에 해당 파일의 `developer_instructions`를 전달하고
  `model`과 `model_reasoning_effort`를 명시한다. CLI는 `--model`과 `-c model_reasoning_effort=...`를 사용한다.
  사전 검토 등 읽기만 하는 CLI 호출은 `exec --sandbox read-only`를 반드시 함께 지정한다.
  쓰기가 필요한 실측은 먼저 격리 사본·임시 데이터 경로를 만들고 그 사본을 작업 디렉터리로 지정한다.
  지원되는 샌드박스의 쓰기 범위가 사본 안인지 확인한 뒤 실행하며, 전역 쓰기 권한을 그대로 상속하지 않는다.
  같은 작업 세션의 단계 전환을 지원하면 설정 변경을 확인해 재사용한다. 공유 역할 파일을 호출마다 덮어쓰지 않는다.
- 모델·단계가 바뀌어도 권한을 넓히지 않는다. 리뷰는 읽기 도구만, 실측은 읽기 전용/격리 실행 경계를 유지한다.
  현재 호출 도구가 설정을 지원하지 않으면 지원 경로로 바꾸거나 미확인으로 보고한다.
- 실제 모델이 요청과 다르거나 호출 불가이면 자동 통과·임의 하향을 하지 않는다. 실행 메타데이터로 확인하고 보고한다.
  프로젝트 설정은 새 세션의 기본값이며 이미 열린 채팅의 모델이 자동으로 바뀌었다고 주장하지 않는다.

Claude 프로젝트 설정은 모델별 `modelSettings`에도 Opus `medium`·Fable `high`를 명시한다.
리뷰 역할의 `effort: high`와 상향 호출의 명시적 `--effort high`를 함께 사용하며, 전역의 모델별 선호를 수정하지 않는다.
CLI 경로마다 버전과 지원 모델이 다를 수 있다. 모델 거절이나 실행 도구 초기화 실패 시 설치된 다른 CLI를 확인할 수 있다.
후보는 실제 실행 파일의 존재와 경로를 확인하고 해당 경로의 `--version`으로 버전을 먼저 확인한다.
그다음 실제로 사용할 작업 폴더와 권한에서 exec 읽기를 통과한 뒤 작업에 사용한다.
`CODEX_CLI_PATH`는 파일 존재와 위 실제 검사를 통과한 경우에만 후보로 사용하고, 값이 없으면 검증된 명시 경로를 사용한다.
경로를 바꿔도 요청한 모델과 권한을 유지하며, 모델을 임의로 낮추거나 권한을 완화하지 않는다.
실행 경로·버전·실제 응답을 기록하고, 앱 경로의 성공을 npm/PATH 경로의 성공으로 바꿔 기록하지 않는다.
자식별 workspace 직접 쓰기 성공과 read-only 쓰기 거부·대상 해시 불변, 격리는 각각 별도로 검증한다.
exec 읽기 성공만으로 쓰기 권한이나 격리를 입증하지 않는다. 검사가 실패하면 무한 재시도하지 않고 보류하며 원인을 기록한다.
실행 경로나 버전이 바뀌면 같은 순서로 다시 검사한다.
구체 경로·버전·일시별 관측과 미해결 범위는 기존 [도입 기록](status/문서정리_운영안_2026-10-14.md)을 참조한다.

공식 형식은 아래 설정 근거를 따른다. 모델 이름·가격·기능 지원은 바뀔 수 있으므로 개정 시 확인하고,
실제 CLI 버전·호출 성공·아직 확인하지 못한 범위는 [도입 기록](status/문서정리_운영안_2026-10-14.md)에 남긴다.

CLI 입력은 파일/표준 입력으로 전달하고 응답·실제 실행 주체·종료 코드를 회수한다. 연결이 없거나 실패하면 미확인으로 보고한다.

현재 클라이언트가 역할 정의를 읽었는지와 호출·쓰기 차단은 별도 실증으로 확인한다. 새 디렉터리의 첫 역할은 새 세션에서 확인한다.

[Claude subagents](https://code.claude.com/docs/en/sub-agents). 공식 설명과 로컬 실증 결과가 다르면 실제 제한을 기록한다.

## 스킬과 문서 사용

두 도구는 아래 조건에서 **사용자가 다시 지시하지 않아도 담당자가 먼저 적용**한다. 설치되어 있다는 사실과 실제 사용은 구분한다.

| 시점·조건 | 적용할 도구와 확인 |
|---|---|
| 코드 설계·구현·수정·리팩터링·의존성 선택 | 설치된 `ponytail` 본문을 세션에서 한 번 읽고 최소한의 완전한 변경을 선택한다. 기존 구현·표준 기능을 먼저 확인하고 호출부·시험·설정까지 필요한 수정은 끝낸다. 안전 검사와 실패 처리를 줄이지 않는다 |
| 코드 변경 리뷰 | `ponytail-review` 본문을 읽고 정확성·보안·부하·누락 시험·성능·불필요한 복잡성 순서로 점검한다. 독립 리뷰 세션과 실제 시험을 대신하지 않는다 |
| 낯선 모듈 탐색·버그 원인 추적·공용 함수/계약 변경 전 | graft `skeleton`·`grep`·`callers` 중 필요한 것을 사용해 구조와 호출 후보를 좁힌다. 특히 버그 수정과 반환값·인자 변경은 실제 호출부까지 확인한다 |
| 동작·공용 모듈·의존 관계를 바꾼 뒤 | 미커밋 변경은 graft `blast`, 커밋된 변경은 작업 기준 SHA로 `blast --base <SHA>`를 실행해 영향 후보와 관련 시험을 확인한다. 실제 diff의 범위와 맞는지 대조하고 필요한 시험을 선택한다 |
| 문구·서식만 바꾼 작업 | 호출 관계 분석과 전체 코드 감사를 억지로 실행하지 않는다. 파일 수정 뒤 색인 갱신 등 프로젝트 마무리 규칙은 그대로 따른다 |

graft는 프로젝트 지침의 **래퍼로만** 호출한다. 색인이 낡았으면 쓰기 가능한 담당자가 먼저 build/check를 수행한다.
`init`·외부 업로드·deep/유료 모델 호출을 이 규칙으로 허용하지 않는다. `ponytail-audit` 전수 검사는 전체 감사가 요청된 경우에만 사용한다.
graft 결과는 탐색 후보다. 중요한 결론은 실제 소스·호출부·시험으로 확인하고, 도구가 제시하는 시험 연결 비율을 실행 커버리지로 간주하지 않는다.
`blast --base`는 기준과 HEAD의 커밋 차이여서 미커밋 변경을 포함하지 않는다. 두 종류가 섞이면 각각 확인하고, 미추적 새 파일은 별도 점검한다. 기본 `blast`는 작업 트리가 깨끗하면 직전 커밋으로 돌아가므로 출력 기준을 반드시 확인한다.
절감 토큰 추정값도 실제 시간·크레딧 절감 실측으로 보고하지 않는다.

Claude 역할의 `skills`는 미리 읽게 하는 설정이며, 설치·허용·실제 로드는 별도로 확인한다.
본문 주입이 확인되지 않으면 설치된 정확한 `SKILL.md`를 읽는다. CLI로 역할을 대신할 때도 이 절차와 도구 제한을 전달한다.
Codex 하위 역할에도 필요한 스킬 경로와 이 절의 적용 조건을 전달하며, 부모가 읽었다는 이유만으로 자식의 로드를 확정하지 않는다.
읽기 전용 리뷰어에게 graft 실행 권한을 추가하지 않는다. 필요한 조회는 총괄이 실행해 전달하고 리뷰어는 원본 소스를 직접 확인한다.
설치 부재·실행 실패·권한 제약이면 미사용 이유를 기록하고 `rg`·직접 읽기·기존 시험으로 대체한다. 사용할 수 없는 스킬을 적용했다고 쓰지 않는다.

완료 기록에는 **실제 읽은 스킬·실행한 graft 명령과 얻은 근거**, 해당하는데 생략했다면 그 이유를 짧게 남긴다.
테스트 절차를 역할/스킬마다 복제하지 않고 [TESTING](TESTING.md)과 기존 도구를 참조한다.

현재 상태는 [CURRENT_STATUS](CURRENT_STATUS.md)에 짧게, 설계·검토·증거는 관련 기존 문서에 둔다.
장기 보존할 새 작업 기록이 필요할 때만 `status/`에 만들고, 본문에 `owner`, `reviewer`, `status`, `touched_paths`, `updated`를 남긴다.
YAML `status`는 문서 위상이고 본문의 `status`는 작업 단계다. 과거 결정·수치를 오늘 사실로 덮지 않는다.

## 시범 통과 기준

1. 역할/스킬의 실제 로드와 상대 모델 호출·응답 회수를 확인한다.
2. 시험용 파일 쓰기 요청이 읽기 전용 역할에서 차단되는지 확인하고, 대상 파일이 변하지 않았는지 대조한다.
3. Jay가 맡긴 작은 실제 작업에서 설계·구현·독립 리뷰·필요 실측의 전체 흐름을 확인한다.
4. 시간·사용량·재작업·미확인 항목으로 운영 비용을 평가한다. 진행 중인 다른 작업을 임의의 시험 대상으로 가져오지 않는다.

위 단계가 남으면 정책·설정 준비와 시범 검증 완료를 구분해 보고한다.
