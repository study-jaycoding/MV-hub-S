# 작업자 PC 오프디스크 백업 계약 (RL-23)

상태: **구현 전 기준 문서 — 아직 구현되지 않음**

기준일: 2026-08-17

위험 상태의 단일 기준은
[RISK_REDUCTION_PLAN_2026-08-15.md](RISK_REDUCTION_PLAN_2026-08-15.md)의 Gate 0 표다.
이 문서는 RL-23을 구현할 때 지켜야 할 데이터 흐름·성공 판정·관측·검증 계약을 정한다.

## 1. 한 줄 결론

작업자마다 NAS 경로를 직접 연결하는 방식을 기본으로 삼지 않는다. 백업은 아래 두 단계를
서로 구분해 자동화한다.

1. **작업자 PC → 공유 서버:** 계정별 개인 DB 백업 세트를 인증된 공유 서버에 자동 업로드한다.
2. **공유 서버 → NAS·다른 디스크:** 서버가 받은 작업자 백업과 서버 자체 백업을 기존
   `backup_replicate` 경로로 복제한다.

첫 단계가 성공해야 `작업자 오프디스크 백업 성공`, 두 번째 단계까지 성공해야 `재해 복제 성공`이다.
둘 중 하나만 성공한 상태를 전체 백업 성공으로 표시하지 않는다.

## 2. 현재 코드에서 확인한 사실

### 작업자·서버 공통 로컬 백업

- `backend/app/services/backup.py`가 SQLite 온라인 백업 API로 일관된 스냅샷을 만든다.
- 콘텐츠 DB를 기준으로 휴지통 DB와 관리 DB가 있으면 같은 시각의 세트로 백업한다.
- 로그인된 작업자는 `backend/data/backups/<계정>/` 아래에 계정별로 보관한다.
- 기본 위치는 원본 DB와 같은 PC의 `backend/data/backups`이고 기본 보관량은 7세트다.
- 따라서 기본 설정만으로는 PC 디스크 고장·분실·랜섬웨어에 대비한 오프디스크 백업이 아니다.

### 작업자 → 공유 서버 백업

- 설정의 `서버에 백업`은 `/api/db/server-backup`을 수동 호출한다.
- 현재 전송물은 활성 계정의 콘텐츠 DB 1개다. 일관 스냅샷을 만든 뒤 세션 토큰과 서명키를
  지우고 공유 서버로 보낸다.
- 공유 서버는 `backend/data/db-backups/<계정>/`에 계정별 최근 10개를 보관한다.
- 현재는 자동 실행, 영속 재시도 큐, 마지막 성공 시각, 실패 이유의 구조화된 상태가 없다.
- 휴지통 DB를 포함하는 한 세트 단위 전송도 아직 없다. 관리 DB는 팀 데이터의 원본이 공유
  서버이므로 작업자 계정 백업에 다시 넣지 않는다.

### 공유 서버 → 외부 저장소 복제

- `tools/backup_replicate.py`가 서버 자체 `backups`와 작업자 업로드 `db-backups`를
  NAS·다른 디스크로 복제한다.
- `.part`에 먼저 복사하고 SQLite `quick_check`를 통과해야 교체하며, 실패가 있으면 종료코드 1이다.
- `register_autostart.bat`가 매일 실행되는 작업 스케줄러 항목을 등록한다.
- 현재 결과는 `logs/backup_replicate.log`에서만 확인한다. 대상 미설정도 종료코드 0으로 건너뛰므로
  관리 화면이 이를 정상 복제로 오해하면 안 된다.

## 3. 해결해야 하는 위험

| 위험 | 현재 결과 | RL-23 목표 |
|---|---|---|
| 작업자 PC 디스크 손실 | 로컬 백업도 함께 손실될 수 있음 | 공유 서버에 자동 보존 |
| 수동 버튼 의존 | 사용자가 잊으면 최신 백업이 없음 | 백그라운드 자동 업로드·재시도 |
| 콘텐츠 DB 1개만 전송 | 작업자 휴지통 상태가 복구에서 빠질 수 있음 | 한 시각의 `content + trash` 개인 DB 세트 보존 |
| HTTP 200만 성공으로 해석 | 일부 파일·옛 요청을 성공으로 오판 가능 | 세트 ID·파일 역할·해시를 포함한 명시적 ACK |
| 앱·네트워크 중단 | 실패가 다음 실행으로 이어지지 않음 | 로컬 영속 outbox와 지수 백오프 |
| 서버 복제 대상 미설정 | 작업 자체는 정상 종료 | `미설정`을 운영 경고로 별도 표시 |
| 텍스트 로그만 존재 | 마지막 정상 시점과 지연 시간을 즉시 알기 어려움 | 구조화 상태와 관리 화면 표시 |

## 4. 목표 데이터 흐름

```text
작업자 SQLite 원본
    ↓ 온라인 스냅샷·무결성 검사
계정별 로컬 백업에서 개인 소유 세트(content·trash)
    ↓ 영속 업로드 outbox·인증·멱등 전송
공유 서버 계정별 백업 세트
    ↓ 예약 복제·무결성 검사
NAS 또는 다른 물리 디스크
    ↓ 격리 복원 드릴
ready·로그인·핵심 테이블 수 검증
```

각 화살표는 독립된 상태를 가진다. 앞 단계 실패가 사용자 화면 요청을 오래 막아서는 안 되며,
재시작 뒤에도 대기 작업이 사라지면 안 된다.

## 5. 백업 세트 계약

한 백업 세트는 다음 정보를 가진 불변 객체로 취급한다.

| 필드 | 의미 |
|---|---|
| `backup_set_id` | 같은 요청을 다시 보내도 중복 저장되지 않는 안정 ID |
| `created_at` | UTC 생성 시각 |
| `roles` | 작업자 업로드는 `content` 필수, 존재할 때 `trash` 포함 |
| `size_bytes` | 역할별 실제 파일 크기 |
| `sha256` | 역할별 전송 전·후 동일성 확인 |
| `schema_version` | 복원 호환성 판정용 버전 |
| `app_version` | 문제 추적용 MV Hub 버전 |

계정 소유권은 업로드 본문의 이메일 문자열이 아니라 **공유 서버가 검증한 로그인 세션**으로 정한다.
프롬프트·생성 URL·세션 토큰·비밀번호·원본 사용자 경로는 manifest와 운영 로그에 넣지 않는다.

`manage_hub.db`의 PM 프로젝트·작업·팀 통계는 공유 서버가 최종 정답이다. 작업자 PC의 관리 DB를
계정 백업으로 서버에 되올려 보내지 않는다. 서버의 `content + trash + manage` 운영 세트는 서버
자체 백업과 외부 복제 단계에서 별도로 보호한다.

## 6. 작업자 자동 업로드 계약

1. 로컬 백업 세트가 무결성 검사를 통과한 뒤에만 outbox에 등록한다.
2. 자동 업로드는 사용자 API 응답과 분리된 저속 백그라운드 작업으로 실행한다.
3. 같은 `backup_set_id`는 동시 실행·재시작·네트워크 재시도에도 서버에 한 세트만 남긴다.
4. 서버는 모든 파일의 크기·SHA-256·SQLite 무결성을 확인하고 임시 위치에서 최종 위치로
   공개한 뒤 ACK를 반환한다.
5. 작업자는 ACK의 세트 ID와 파일 역할이 현재 outbox 행과 모두 맞을 때만 성공 처리한다.
6. 로그인 만료는 백업 폐기가 아니라 `로그인 대기` 상태다. 재로그인 뒤 자동 재시도한다.
7. 구버전 서버가 세트 업로드를 지원하지 않으면 `서버 업데이트 필요`로 표시하고 콘텐츠 DB 1개
   업로드를 전체 세트 성공으로 승격하지 않는다.
8. 앱 종료 때 새 전송을 시작하지 않고 현재 작업을 제한 시간 동안 정리한다. 다음 시작에서
   `running`은 다시 `pending`으로 복구한다.

## 7. 서버 외부 복제 계약

1. 서버 자체 백업과 작업자가 올린 완성 세트만 복제한다.
2. 대상이 미설정이면 `disabled` 또는 `misconfigured`이며 성공이 아니다.
3. 복사 중 파일·세트는 최종 목록에 노출하지 않는다. 모든 파일 검증 뒤에만 원자적으로 공개한다.
4. 원본에 아직 존재하는 완성 세트는 복제본 회전 때문에 삭제하지 않는다.
5. 일부 파일 실패, 대상 접근 거부, 공간 부족, 해시·무결성 실패는 모두 실행 실패다.
6. 상태 파일은 앱 데이터 경로에 원자적으로 저장해 프로그램 업데이트로 사라지지 않게 한다.
7. 로그에는 전체 UNC 경로·계정 이메일·예외 원문 대신 단계, 개수, 지연, 안전한 오류 코드만 남긴다.

## 8. 화면과 운영 상태

작업자 계정·설정 화면에는 아래 항목만 간단히 표시한다.

- 로컬 백업: 마지막 성공 시각, 세트 구성, 보관 개수
- 공유 서버 백업: `대기 / 전송 중 / 성공 / 로그인 대기 / 실패 / 서버 업데이트 필요`
- 공유 서버 마지막 성공 시각과 현재 대기 개수
- 실패한 경우 안전한 오류 코드와 `지금 다시 시도` 버튼

서버 관리자 화면 또는 운영 상태에는 아래 항목을 표시한다.

- 복제 대상 `설정 / 미설정 / 접근 실패`
- 마지막 시도·마지막 성공 시각
- 복제 지연 시간, 신규·유지·실패 세트 수
- 가장 오래된 미복제 세트의 나이

경로와 계정 정보를 보아야 하는 상세 화면은 로컬 관리자에게만 허용한다. 원격 일반 사용자는
서버 파일 경로를 읽거나 바꿀 수 없어야 한다.

## 9. 업데이트 호환성과 배포 순서

DB·API 변경은 추가 방식으로 만들고 기존 수동 `server-backup/server-restore`를 바로 삭제하지 않는다.

1. 새 세트 저장과 멱등 ACK를 지원하는 공유 서버를 먼저 배포한다.
2. 서버의 외부 복제 상태 기록과 경보를 확인한다.
3. 새 작업자 자동 업로드를 배포한다.
4. 구버전 작업자 수동 단일 DB 백업이 계속 동작하는지 확인한다.
5. 새 작업자에서 업데이트 전 로컬 백업이 보존되고 outbox가 재개되는지 확인한다.

서버가 준비되지 않은 상태에서 작업자만 먼저 업데이트해도 생성·작업 기능은 계속 사용할 수 있어야
한다. 이 경우 백업만 `서버 업데이트 필요`로 남기고 성공으로 위장하지 않는다.

## 10. 완료 조건

RL-23은 아래를 모두 통과한 뒤에만 Gate 0에서 완료로 바꾼다.

- [ ] 작업자 `content + trash` 개인 세트 생성과 같은 세트 ID 보존
- [ ] 서버 자체 `content + trash + manage` 운영 세트의 외부 복제 보존
- [ ] 동일 세트 20회 동시 전송에서 서버 저장 1세트·ACK 1계약 확인
- [ ] 업로드 중 작업자 종료 → 재시작 → 같은 세트 자동 재개
- [ ] 공유 서버 5분 단절 → 백오프 → 복구 뒤 대기 0과 마지막 성공 갱신
- [ ] 로그인 만료에서 데이터 폐기·무한 재로그인 반복 없음
- [ ] 서버 디스크 부족·부분 쓰기·손상 파일이 성공으로 표시되지 않음
- [ ] NAS 미설정·접근 거부·복구 뒤 상태 전이가 정확함
- [ ] 실제 다른 물리 장치에 복제된 세트로 격리 복원 드릴 통과
- [ ] 구버전 작업자와 새 서버, 새 작업자와 구버전 서버의 혼합 버전 회귀
- [ ] 업데이트 전후 백업 설정·상태·outbox 보존
- [ ] 백엔드 전체 회귀, 프론트 전체 회귀·빌드·아키텍처 검사 통과
- [ ] 운영 로그에 토큰·이메일·프롬프트·URL·전체 사용자 경로가 없음

## 11. 이번 문서화에서 하지 않은 것

- 아직 API·DB·백그라운드 작업·화면 코드를 구현하지 않았다.
- 실제 NAS 경로를 설정하거나 파일을 복사하지 않았다.
- 운영 서버·작업자 설치본의 배포 가능 상태를 선언하지 않았다.
- 보관 기간과 용량 한도의 최종 운영값은 실제 DB 크기와 NAS 용량을 측정한 뒤 정한다.
