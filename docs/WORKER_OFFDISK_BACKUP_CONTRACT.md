# 작업자 PC 오프디스크 백업 계약 (RL-23)

상태: **내부 구현·회귀·로컬 실측 완료 — 실제 NAS/다른 물리 장치 복원 훈련 대기**

기준일: 2026-08-19

위험 상태의 단일 기준은
[RISK_REDUCTION_PLAN_2026-08-15.md](RISK_REDUCTION_PLAN_2026-08-15.md)의 Gate 0 표다.
이 문서는 RL-23을 구현할 때 지켜야 할 데이터 흐름·성공 판정·관측·검증 계약을 정한다.

## 1. 한 줄 결론

작업자마다 NAS 경로를 직접 연결하는 방식을 기본으로 삼지 않는다. 백업은 아래 두 단계를
서로 구분해 자동화한다.

1. **작업자 PC → 공유 서버:** 계정별 개인 DB 백업 세트를 인증된 공유 서버에 자동 업로드한다.
2. **공유 서버 → NAS·다른 디스크:** 서버가 받은 작업자 백업과 서버 자체 백업을 기존
   `backup_replicate` 경로로 복제한다.

첫 단계가 성공해야 `작업자 오프디스크 백업 성공`, 두 번째 단계까지 성공해야 `재해 복제 성공`이다.
둘 중 하나만 성공한 상태를 전체 백업 성공으로 표시하지 않는다.

## 2. 현재 구현 상태

### 작업자·서버 공통 로컬 백업

- `backend/app/services/backup.py`가 SQLite 온라인 백업 API로 일관된 스냅샷을 만든다.
- 콘텐츠 DB를 기준으로 휴지통 DB와 관리 DB가 있으면 같은 시각의 세트로 백업한다.
- 로그인된 작업자는 `backend/data/backups/<계정>/` 아래에 계정별로 보관한다.
- 기본 위치는 원본 DB와 같은 PC의 `backend/data/backups`이고 기본 보관량은 7세트다.
- 로컬 세트가 만들어지면 `worker_backup.py`가 개인 소유 `content + trash`를 별도 staging에
  복사하고 무결성·크기·SHA-256을 확인한 뒤 영속 outbox에 등록한다.
- 메타데이터가 바뀐 뒤 기본 5분 동안 추가 변경이 없으면 새 세트를 만들며, 잦은 편집 중에는
  기본 15분보다 자주 업로드하지 않는다. 변경이 없어도 기존 하루 주기 백업은 유지한다.
- 생성물·태그·캔버스·에셋·프로젝트·휴지통이 모두 비어 있는 새 PC DB는 서버로 올리지 않는다.
- outbox DB와 staging은 `backend/data`에 있어 릴리스 업데이트가 교체하지 않는다. 로컬 백업만으로는
  여전히 디스크 손실에 대비할 수 없으므로 공유 서버 ACK까지 별도 성공으로 추적한다.

### 작업자 → 공유 서버 백업

- 백그라운드 작업은 60초 간격으로 outbox를 확인하고 한 번에 한 세트만 저속 전송한다. 네트워크
  실패는 영속 대기와 지수 백오프로 남고, 로그인 만료는 폐기하지 않고 `login_required`로 남는다.
- 공유 서버의 `POST /api/db-backup/sets`는 세션에서 계정 소유권을 정하고, manifest·역할·크기·
  SHA-256·SQLite 무결성을 검증한다. 임시 폴더를 완성한 뒤에만
  `backend/data/db-backups/<계정>/sets/<backup_set_id>/`로 공개한다.
- 같은 세트의 재전송은 한 폴더로 멱등 처리하며, 작업자는 세트 ID와 역할별 크기·해시가 모두 맞는
  명시적 ACK만 성공으로 인정한다. 설정의 수동 백업 버튼은 같은 큐를 즉시 실행한다.
- 서버는 계정별 현재 기준점(head)과 PC별 부모 세트를 비교한다. 다른 PC의 오래된 기준에서 시작한
  세트도 삭제하지 않고 `conflict` 버전으로 보관하되 자동으로 현재 기준점을 바꾸지 않는다.
- 자동 동작은 **서버로 올리기만** 한다. 서버 데이터는 사용자가 설정의 `메타데이터 동기화`에서
  PC·시각·요약을 확인하고 특정 버전을 선택했을 때만 로컬에 적용한다.
- 구버전 서버에는 기존 단일 콘텐츠 DB 백업을 호환용으로 시도하지만, 이를 세트 성공으로 승격하지
  않고 `server_update_required`로 남긴다. 관리 DB는 공유 서버 원본이므로 작업자 세트에 넣지 않는다.

### 공유 서버 → 외부 저장소 복제

- `tools/backup_replicate.py`가 서버 자체 `backups`와 작업자 업로드의 기존 단일 DB·완성 세트를
  NAS·다른 디스크로 복제한다.
- 단일 DB는 `.part`, 세트는 임시 디렉터리에 먼저 복사한다. 역할·크기·해시·SQLite 검증이 모두
  끝난 뒤에만 공개하며 실패가 있으면 종료코드 1이다.
- `register_autostart.bat`가 매일 실행되는 작업 스케줄러 항목을 등록한다.
- 결과는 안전한 로그와 `backend/data/backup_replica_status.json`에 함께 남는다. 대상 미설정,
  아직 실행되지 않음, 접근 실패, 성공을 서로 다른 상태로 기록하며 운영 상태의 경고 후보에 포함한다.

## 3. 구현 전 위험과 현재 대응

| 위험 | 구현 전 결과 | 현재 대응 |
|---|---|---|
| 작업자 PC 디스크 손실 | 로컬 백업도 함께 손실될 수 있음 | 공유 서버에 자동 보존 |
| 수동 버튼 의존 | 사용자가 잊으면 최신 백업이 없음 | 백그라운드 자동 업로드·재시도 |
| 콘텐츠 DB 1개만 전송 | 작업자 휴지통 상태가 복구에서 빠질 수 있음 | 한 시각의 `content + trash` 개인 DB 세트 보존 |
| HTTP 200만 성공으로 해석 | 일부 파일·옛 요청을 성공으로 오판 가능 | 세트 ID·파일 역할·해시를 포함한 명시적 ACK |
| 앱·네트워크 중단 | 실패가 다음 실행으로 이어지지 않음 | 로컬 영속 outbox와 지수 백오프 |
| 서버 복제 대상 미설정 | 작업 자체는 정상 종료 | `미설정`을 운영 경고로 별도 표시 |
| 텍스트 로그만 존재 | 마지막 정상 시점과 지연 시간을 즉시 알기 어려움 | 구조화 상태와 관리 화면 표시 |
| 새 PC의 빈 DB 자동 업로드 | 쓸 데이터가 없는 최신본이 기존 백업을 가릴 수 있음 | 의미 있는 레코드가 0이면 업로드 대기 |
| 여러 PC의 오래된 상태 업로드 | 마지막 도착본이 최신 작업을 덮을 수 있음 | 부모 기준점 비교·충돌 버전 보존·자동 승격 금지 |
| 자동 다운로드·복원 | 현재 PC 작업을 사용자 모르게 덮을 수 있음 | 목록 조회와 선택 복원만 허용 |

## 4. 목표 데이터 흐름

```text
작업자 SQLite 원본
    ↓ 온라인 스냅샷·무결성 검사
계정별 로컬 백업에서 개인 소유 세트(content·trash)
    ↓ 영속 업로드 outbox·인증·멱등 전송
공유 서버 계정별 백업 세트
    ↓ 예약 복제·무결성 검사
NAS 또는 다른 물리 디스크
    ↓ 격리 복원 드릴
ready·로그인·핵심 테이블 수 검증
```

각 화살표는 독립된 상태를 가진다. 앞 단계 실패가 사용자 화면 요청을 오래 막아서는 안 되며,
재시작 뒤에도 대기 작업이 사라지면 안 된다.

## 5. 백업 세트 계약

한 백업 세트는 다음 정보를 가진 불변 객체로 취급한다.

| 필드 | 의미 |
|---|---|
| `backup_set_id` | 같은 요청을 다시 보내도 중복 저장되지 않는 안정 ID |
| `created_at` | UTC 생성 시각 |
| `roles` | 작업자 업로드는 `content` 필수, 존재할 때 `trash` 포함 |
| `size_bytes` | 역할별 실제 파일 크기 |
| `sha256` | 역할별 전송 전·후 동일성 확인 |
| `schema_version` | 복원 호환성 판정용 버전 |
| `app_version` | 문제 추적용 MV Hub 버전 |
| `device` | 업데이트에도 보존되는 무작위 PC ID와 화면용 PC 이름 |
| `parent_backup_set_id` | 이 세트가 이어받은 서버 기준점. 여러 PC 충돌 판정에 사용 |
| `summary` | 생성물·태그·캔버스·에셋 등 비밀값 없는 개수 요약 |

계정 소유권은 업로드 본문의 이메일 문자열이 아니라 **공유 서버가 검증한 로그인 세션**으로 정한다.
프롬프트·생성 URL·세션 토큰·비밀번호·원본 사용자 경로는 manifest와 운영 로그에 넣지 않는다.

`manage_hub.db`의 PM 프로젝트·작업·팀 통계는 공유 서버가 최종 정답이다. 작업자 PC의 관리 DB를
계정 백업으로 서버에 되올려 보내지 않는다. 서버의 `content + trash + manage` 운영 세트는 서버
자체 백업과 외부 복제 단계에서 별도로 보호한다.

## 6. 작업자 자동 업로드 계약

1. 로컬 백업 세트가 무결성 검사를 통과한 뒤에만 outbox에 등록한다.
2. 자동 업로드는 사용자 API 응답과 분리된 저속 백그라운드 작업으로 실행한다.
3. 같은 `backup_set_id`는 동시 실행·재시작·네트워크 재시도에도 서버에 한 세트만 남긴다.
4. 서버는 모든 파일의 크기·SHA-256·SQLite 무결성을 확인하고 임시 위치에서 최종 위치로
   공개한 뒤 ACK를 반환한다.
5. 작업자는 ACK의 세트 ID와 파일 역할이 현재 outbox 행과 모두 맞을 때만 성공 처리한다.
6. 로그인 만료는 백업 폐기가 아니라 `로그인 대기` 상태다. 재로그인 뒤 자동 재시도한다.
7. 구버전 서버가 세트 업로드를 지원하지 않으면 `서버 업데이트 필요`로 표시하고 콘텐츠 DB 1개
   업로드를 전체 세트 성공으로 승격하지 않는다.
8. 앱 종료 때 새 전송을 시작하지 않고 현재 작업을 제한 시간 동안 정리한다. 다음 시작에서
   `running`은 다시 `pending`으로 복구한다.
9. 같은 PC의 내용 해시가 같으면 파일 수정 시각이 달라도 같은 ID로 수렴해 새 버전을 만들지 않는다.
10. 서버 기준점과 부모가 다르면 버전은 보존하되 `conflict`로 표시하고 자동 적용·자동 승격하지 않는다.

## 6-A. 수동 적용 계약

1. 설정의 `메타데이터 동기화`는 서버 백업을 자동 적용하지 않고 버전 목록만 조회한다.
2. 목록은 PC 이름, 생성 시각, 앱 버전, 크기, 생성물·태그·캔버스·에셋 개수와
   `현재 / 이전 / 다른 PC 버전` 상태를 보여준다.
3. 사용자가 고른 정확한 `backup_set_id`만 내려받으며, 단순히 마지막에 도착한 파일을 복원하지 않는다.
4. 적용 전 다운로드 크기·해시·SQLite 무결성과 역할 구성을 검증한다.
5. 현재 로컬 DB를 먼저 별도 보관하고 유지보수 게이트 안에서 원자 교체한다. 실패하면 원래 DB로
   롤백하고, 성공하면 세션 정보를 제거해 재로그인하게 한다.
6. 선택 버전 적용 성공 뒤에만 해당 버전을 새 서버 기준점으로 활성화한다. 이후 자동 업로드는
   이 기준점을 부모로 이어간다.

## 7. 서버 외부 복제 계약

1. 서버 자체 백업과 작업자가 올린 완성 세트만 복제한다.
2. 대상이 미설정이면 `disabled` 또는 `misconfigured`이며 성공이 아니다.
3. 복사 중 파일·세트는 최종 목록에 노출하지 않는다. 모든 파일 검증 뒤에만 원자적으로 공개한다.
4. 원본에 아직 존재하는 완성 세트는 복제본 회전 때문에 삭제하지 않는다.
5. 일부 파일 실패, 대상 접근 거부, 공간 부족, 해시·무결성 실패는 모두 실행 실패다.
6. 상태 파일은 앱 데이터 경로에 원자적으로 저장해 프로그램 업데이트로 사라지지 않게 한다.
7. 로그에는 전체 UNC 경로·계정 이메일·예외 원문 대신 단계, 개수, 지연, 안전한 오류 코드만 남긴다.

## 8. 화면과 운영 상태

작업자 계정·설정 화면에는 아래 항목만 간단히 표시한다.

- 로컬 백업: 마지막 성공 시각, 세트 구성, 보관 개수
- 공유 서버 백업: `대기 / 전송 중 / 성공 / 로그인 대기 / 실패 / 서버 업데이트 필요`
- 공유 서버 마지막 성공 시각과 현재 대기 개수
- 실패한 경우 안전한 오류 코드와 `지금 다시 시도` 버튼

서버 관리자 화면 또는 운영 상태에는 아래 항목을 표시한다.

- 복제 대상 `설정 / 미설정 / 접근 실패`
- 마지막 시도·마지막 성공 시각
- 복제 지연 시간, 신규·유지·실패 세트 수
- 가장 오래된 미복제 세트의 나이

경로와 계정 정보를 보아야 하는 상세 화면은 로컬 관리자에게만 허용한다. 원격 일반 사용자는
서버 파일 경로를 읽거나 바꿀 수 없어야 한다.

## 9. 업데이트 호환성과 배포 순서

DB·API 변경은 추가 방식으로 만들고 기존 수동 `server-backup/server-restore`를 바로 삭제하지 않는다.

1. 새 세트 저장과 멱등 ACK를 지원하는 공유 서버를 먼저 배포한다.
2. 서버의 외부 복제 상태 기록과 경보를 확인한다.
3. 새 작업자 자동 업로드를 배포한다.
4. 구버전 작업자 수동 단일 DB 백업이 계속 동작하는지 확인한다.
5. 새 작업자에서 업데이트 전 로컬 백업이 보존되고 outbox가 재개되는지 확인한다.

서버가 준비되지 않은 상태에서 작업자만 먼저 업데이트해도 생성·작업 기능은 계속 사용할 수 있어야
한다. 이 경우 백업만 `서버 업데이트 필요`로 남기고 성공으로 위장하지 않는다.

## 10. 완료 조건

- [x] 작업자 `content + trash` 개인 세트 생성과 같은 세트 ID 보존
- [x] 서버 자체 `content + trash + manage` 운영 세트와 작업자 세트의 외부 복제 코드 보존
- [x] 동일 세트 20회 동시 전송에서 서버 저장 1세트·ACK 1계약 확인
- [x] 업로드 중 작업자 종료 → 재시작 → 같은 세트 자동 재개
- [x] 공유 서버 5분 단절 상당의 반복 실패 → 백오프 → 복구 뒤 대기 0과 마지막 성공 갱신
- [x] 로그인 만료에서 데이터 폐기·무한 재로그인 반복 없음
- [x] 서버 디스크 부족·부분 쓰기·손상 파일이 성공으로 표시되지 않음
- [x] 복제 대상 미설정·접근 실패·정상 복구의 구조화 상태 전이 확인
- [ ] 실제 다른 물리 장치에 복제된 세트로 격리 복원 드릴 통과
- [x] 구버전 작업자와 새 서버, 새 작업자와 구버전 서버의 혼합 버전 회귀
- [x] 릴리스 업데이트가 `backend/data`의 백업 설정·상태·outbox를 교체하지 않음

- [x] 빈 새 PC DB 업로드 차단, 동일 내용 중복 생략, PC별 충돌 버전 보존
- [x] 특정 버전 선택 다운로드·무결성 검사·원자 복원·실패 롤백·복원 기준점 승계
- [x] 자동 업로드와 사용자 선택 적용이 분리되어 자동 다운로드·자동 덮어쓰기 없음

## 11. 검증 근거와 남은 외부 작업

내부에서 다음을 확인했다.

- 작업자 outbox·세트 업로드·선택 복원·복제·자동 변경 백업 관련 집중 회귀 64개 통과
- 2026-08-19 전체 백엔드 1,021개·29 subtests, 프론트 82개 파일·593개,
  프로덕션 빌드·아키텍처 검사 통과
- 20개 동시 동일 세트 저장, 중단 복구, 로그인 만료, 네트워크 실패 후 재시도, 디스크 쓰기 실패,
  손상 파일, 혼합 버전, 업데이트 보존 회귀 통과
- 격리 브라우저에서 로컬 백업 수·세트 구성·공유 서버 상태·재시도 버튼 표시와 앱 출처 콘솔 오류
  0건 확인
- 2코어·below-normal·256MiB 상한의 100명 단기 실측에서 요청 2,920건 모두 200, WebSocket·
  장기 폴링 각 100개, SQLite lock 0건, 최대 RSS 196,182,016바이트 확인

아직 실제 NAS 경로를 설정해 다른 물리 장치에 복사하고, 그 복제본만으로 예비 PC에서 격리 복원하는
월간 훈련은 하지 않았다. 따라서 Gate 0의 RL-23은 이 훈련이 끝날 때까지 **부분 해결**로 유지한다.
보관 기간과 용량 한도의 최종 운영값도 실제 DB 증가량과 NAS 용량을 측정한 뒤 확정한다.
