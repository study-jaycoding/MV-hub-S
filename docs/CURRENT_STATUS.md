## 2026-08-18 추가 안정화

- **비공개 코멘트 경계:** 공유 서버의 공개 코멘트 수와 계정 로컬 비공개 코멘트 수를 정확히 합치고,
  다른 계정으로 바뀌면 이전 계정의 코멘트 캐시를 재사용하지 않는다. 비공개 코멘트는 팀 공유·발행·
  통계에서 제외된다는 실제 보존 범위로 안내 문구도 바로잡았다.
- **캔버스 생성물 제거 복구:** 카드에서 생성물을 뺀 의도를 계정별 영속 대기열에 네트워크 전부터
  기록한다. 전송 실패·오프라인·앱 재시작과 늦은 서버 조회 뒤에도 자동 백필이 제거 항목을 되살리지
  않는다.
- **원격 다운로드 상한:** 크기를 미리 알 수 없는 원격 파일이 각인 상한을 넘으면 임시 디스크 사용을
  제한한 채 각인 없이 전체 원본을 스트리밍한다. 중단·완료 뒤 upstream과 임시파일을 회수한다.

  502를 남기지 않고 그 값을 일시 재사용한다.
- **릴리즈 생성·종료 로그:** 빈 격리 폴더에 설치하는 릴리즈 빌드에서는 작업 PC에 설치된 선택적
  패키지의 충돌 경고를 오인하지 않게 했고, Python 3.14에서 정상 종료 뒤 `KeyboardInterrupt`
  스택이 다시 출력되는 현상을 막았다. 시작 실패와 비정상 종료 판정은 그대로 유지한다.
- **릴리즈 해시·임시폴더 자립성:** 관리된 Windows에서 `Get-FileHash`를 찾지 못해 첫 설치가
  중단되는 현상을 실제 재현했다. 설치·업데이트·빌드·릴리즈 선택의 해시를 .NET 구현으로 통일하고,
  `TEMP`가 비어 있어도 LocalAppData 임시폴더로 안전하게 이어지도록 했다.
- **외부 도구 연결 정확성:** 설정 창의 첫 Resolve 확인이 끝나기 전에 재확인을 눌러 8초 검사 프로세스가
  겹치던 경계를 막았다. Comfy는 저장하지 않은 대상·주소·키를 이전 저장값으로 검사하지 않으며 저장·

## 2026-08-19 사전 배포 적대 검증

- **검증 Python 자동 선택:** 사전 배포 게이트가 단순히 PATH의 `python`을 믿지 않고 `pytest`와
  `psutil`을 실제로 불러올 수 있는 환경만 선택한다. 선택한 절대 경로는 결과 JSON에 남긴다.
- **저사양 조건 고정:** 100명 부하의 기본 서버 조건을 2개 논리 CPU·below-normal 우선순위로
  명시한다. 이전 64코어·normal 결과는 기능 부하 근거로만 보존하고 저사양 근거로 사용하지 않는다.
  `7387eaf0` 게이트 재실행은 2회 합계 23,007건 모두 200, 2회차 p95 41.82ms·p99 156.53ms,
  WebSocket·에이전트 롱폴 각 100, SQLite lock·통신 오류 0, 워밍업 뒤 RSS 증가 0.35%였다.
- **로그인 폭주 격리:** PBKDF2 20만 회 보안 강도는 유지하되 CPU·DB 검증 동시 수를 사용 가능한
  CPU에 맞춰 제한한다. 대기 요청은 공용 sync API 스레드를 점유하지 않고, 취소된 요청도 실제
  검증이 끝나기 전에 처리 자리를 반납하지 않는다. 100명이 같은 순간 로그인해 전부 200,
  p95 7.82초였고, 같은 시간 일반 상태 API 106회도 전부 200·p95 42.01ms였다.
- **장기 시험 조건 일치와 TLS 자립성:** 8시간 자동 실행기도 문서와 같은 CPU 제한·낮은 우선순위·
  30초 자원 표본·RSS 512MiB·지연·메모리 증가 합격선을 실제 부하 도구에 전달한다. 기본 시험용
  인증서가 없거나 만료됐거나 24시간 안에 만료되면 127.0.0.1/localhost 전용 30일 인증서와 개인키를
  자동 재생성한다. 서버 준비 실패에는 마지막 연결 오류를 남겨 만료 인증서 같은 원인을 숨기지 않는다.
  `ab0384e5` 전체 Gate는 백엔드 946개·21 subtests, 프론트 79개/571개, 빌드·DB 복원을 통과했다.
  100명 2회는 합계 23,152건 모두 200, 2회차 p95 37.81ms·p99 137.34ms, WebSocket·롱폴 각
  100개, SQLite lock·통신 오류 0, 워밍업 뒤 RSS 증가 2.3%, 최대 RSS 254,451,712바이트였다.
- **Windows 업데이트 실행 안정화:** 한 줄 bootstrap은 자기 자신이 교체되는 업데이트 구조를
  유지하면서 PowerShell의 간헐적 cross-language dot-source 오류를 피한다. 작업자의 정확한 종료
  코드도 1로 뭉개지지 않고 자동화에 전달한다. 서버 재시작은 더 이상 포트 소유 명령에
  `serve.py`라는 이름이 있다는 이유만으로 프로세스를 종료하지 않는다. 감독기가 현재 설치본의
  절대 `backend/serve.py` 경로로 자식을 실행하고, 재시작 도구는 그 경로가 일치할 때만 남은
  포트 소유자를 회수한다. 다른 앱의 동명 스크립트는 종료하지 않고 안전하게 실패한다.
- **Comfy 비용 없는 왕복:** 고유 임시 DB·미디어·포트의 실제 MV Hub 백엔드와 HTTP 호환 서버 사이에서
  3건을 제출했다. 성공 2건은 PNG 다운로드, 실패 1건은 해당 prompt만 삭제했고 `/interrupt` 호출,
  입력 임시파일과 in-flight 잔재는 모두 0이었다. 실제 Cloud 계정·크레딧 검증은 아니다.
- **Resolve 실제 왕복:** Resolve Studio 20.3.2에서 임시 프로젝트에 `c0015`를 먼저 넣고 `c0010`을
  나중에 넣어도 자연 정렬됐고, 같은 원본 재가져오기는 건너뛰었다. 2개 Render All 출력과 시퀀스
  폴더를 확인한 뒤 렌더 잡·임시 프로젝트를 지우고 원래 프로젝트를 복원했다.
- **캔버스 소속 교차 브라우저 갱신:** 카드-생성물 소속은 DB에 저장해도 기존 화면이 최초 1회만
  읽어 다른 브라우저의 늦은 변경을 새로고침 전까지 보지 못하는 경계를 적대 리뷰에서 확인했다.
  화면이 보이는 동안 30초마다, 창 복귀·온라인 복귀 때 즉시 다시 읽되 응답이 달라진 경우에만
  캔버스 합치기를 실행한다. 같은 응답의 불필요한 저장·렌더를 막았고 관련 21개, 프론트 전체
  571개·아키텍처 검사·배포 빌드와 실제 캔버스 35초 레이아웃 안정성 확인을 통과했다.
- **동명 워크스페이스 정확 선택:** `#+`/`#-`와 관리 선택기가 표시명이 같은 워크스페이스를 ID
  뒷자리로 구분하고, 변경 요청도 이름이 아닌 정확한 UUID로 보낸다. 혼합 배포의 구서버가 다른
  UUID를 돌려주면 변경 전에 중단한다. 관련 백엔드 53개, 프론트 전체 574개, 배포 빌드를 통과했고
  실제 관리 화면에서 동명 공간 2개가 서로 다른 ID와 멤버 수로 전환되며 콘솔 오류가 없음을 확인했다.

## 최근 내부 구현·검증을 완료한 작업

- **RL-02 — 작업 워크스페이스 스냅샷 구현 완료**

  수동 작업과 생성에서 파생된 폴더 작업에 생성 당시 `workspace_scope/id/name`을 저장한다. 프로젝트가
  A에서 B로 이동한 뒤 같은 폴더가 재사용돼도 A의 상태·메모·담당과 B의 작업이 섞이지 않는다. 기존
  손상 데이터는 개인·팀으로 추측하지 않고 `unresolved`로 정규화하며, 관리 권한이 있는 사용자의 과거
  기록에서만 확인할 수 있다.

  마이그레이션 사전 검사는 원본 해시, 두 번 실행 뒤 동일 건수, 외래키·SQLite 무결성, 롤백 건수를
  확인한다. `generation.folder_path/workspace_*`가 없던 실제 구버전 형태도 원본이 아닌 복사본에서
  코어 스키마를 먼저 올린 뒤 관리 스키마를 이관해 끝까지 통과한다. 500개가 넘는 프로젝트는 나눠
  읽고, 서버 내부 오류나 인증 오류를 빈 목록으로 숨기지 않는다. 작업 쓰기는 프로젝트 권한을 먼저
  확인한 뒤 과거·미귀속 상태를 판정해 비멤버에게 내부 상태가 먼저 노출되지 않는다. 대소문자·공백만
  어긋난 복구 가능한 레거시 값은 먼저 `team/ws-a` 형태로 정규화하고, 실제 잘못된 값만 `unresolved`로
  격리한다. 같은 경로의 DB 파일이 교체돼도 pool epoch가 작업 응답 캐시 표식에 포함돼 이전 본문을
  재사용하지 않는다. 백엔드 전체 1,002개·29 subtests,
  프론트 80개 파일·587개, 프로덕션 빌드·아키텍처 검사·
  Python 컴파일을 통과했다. 2,000개 작업을 압축 없이 계속 재전송한 적대 시험이 p95 약 1초로
  실패한 뒤, 권한·공간·DB 변경 표식을 포함한 private ETag 재검증과 gzip 결과 캐시를 적용했다.

  Personal/MILLIONVOLT/R&D를 빠르게 왕복해 최종 선택 공간만 남는 것을 확인했다. 과거 기록의 선택·상태·날짜·
  설명 입력은 모두 읽기 전용이었고, B 활성 작업과 이전 공간 잔상 0, 보드·캘린더 범위 유지,
  앱 출처 콘솔 오류 0건을 확인했다. 라우터 검사 직후 프로젝트가 이동하는 경계도 실제 저장과 같은
  쓰기 트랜잭션에서 다시 검사해 과거·미귀속 작업 변경을 차단했다. 이후 전체 diff 적대 검토와 전체 회귀·빌드·아키텍처·Python

- **RL-23 — 작업자 PC 오프디스크 백업**

  작업자 로컬 백업의 `content + trash`를 한 세트로 묶어 공유 서버에 자동 업로드한다. 세트는
  별도 영속 outbox에 먼저 등록하고, 네트워크 실패·로그인 만료·앱 종료 뒤에도 폐기하지 않는다.
  공유 서버는 세션 계정별로 크기·SHA-256·SQLite 무결성을 확인한 뒤에만 세트를 공개하며, 정확한
  세트 ID와 역할별 ACK가 모두 맞아야 작업자가 성공 처리한다.

  서버의 외부 복제는 기존 단일 DB와 새 완성 세트를 모두 처리하고 결과를 구조화 상태로 남긴다.
  설정 화면은 로컬 세트 구성, 공유 서버 백업 상태·마지막 성공·대기 수와 재시도 버튼을 표시한다.
  릴리스 업데이트는 상태 DB·outbox·staging이 있는 `backend/data`를 교체하지 않는다.

  동일 세트 동시 저장 20회, 관련 회귀 84개, 백엔드 전체 887개·21 subtests, 프론트 76개
  파일·535개, 프로덕션 빌드와 아키텍처 검사를 통과했다. 격리 브라우저에서 상태 표시와 앱 출처
  콘솔 오류 0건을 확인했고, 100명 저사양 단기 실측도 통과했다. 실제 다른 물리 장치 복원 훈련은
  남아 있어 RL-23 상태는 부분 해결이다.

RL-05 브라우저 실측은 임시 SQLite DB와 테스트 계정만 사용했고 실제 Higgsfield CLI는 호출하지
않았다. 따라서 이 결과는 중복 과금 방지 내부 계약을 증명하지만 실제 크레딧 생성 왕복을 대신하지 않는다.

## 운영 배포 전 남은 확인

- 최신 `dev` 격리 환경의 실제 Higgsfield 1건 왕복은 통과했다. 운영 설치본 배포 직후 같은 경로를
  다시 확인
- 최신 `dev` 격리 서버의 두 계정 publish → 조회 → unpublish 왕복은 통과했다. 운영 공유 서버의
  실제 계정·혼합 버전 배포에서도 같은 결과와 감사 이력을 재확인
- 실제 Comfy 워크플로우 실행과 Resolve의 실제 가져오기·내보내기(Resolve 실행·연결·제품/프로젝트 조회는 통과)
- 실제 NAS 백업 복제의 최신성·오프디스크 복사와 예비 PC 복구 시간 측정
- 운영 설치본의 업데이트 → 자동 재시작 → ready → 로그인 → 주요 화면 확인

상세 합격 조건은 위험 계획의 `Gate 6 — 외부 통합과 병합·배포 검증`을 따른다.

## 갱신 규칙

- 위험 상태는 Gate 0 표에서 먼저 바꾼 뒤 이 문서의 요약을 맞춘다.
- 테스트 숫자는 전체 회귀를 실제로 다시 실행했을 때만 갱신한다.
- 브랜치의 앞선 커밋 수처럼 매번 변하는 숫자는 문서에 고정하지 않는다.
- 외부 실측을 하지 않았다면 `검증 완료`나 `배포 가능`으로 표현하지 않는다.
