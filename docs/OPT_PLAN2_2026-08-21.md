# 최적화 라운드 2 설계 v2 (2026-08-21 밤, 서베이2+실측 → v1 → 코덱스 검토 반영 확정)

v1→v2 (코덱스 설계 검토 반영): ①실행 순서 확정 = **1-B → 1-A → 1-C → 1-D → 2-E → 2-D →
2-A → 2-C → 2-B(보안 단독 리뷰) → 3-A → 3-B → 3-C → 3-D → 3-E** (2-E 는 웨이브 1로 상향,
2-B 는 인증 경계 변경이라 별도 보안 커밋으로 강등, agent_push 3건은 순서 고정)
②2-D·2-A·2-B·3-A 는 아래 확정 계약대로만 구현 ③1-D 는 구 DB 마이그레이션 순서 게이트 선행.

### 확정 계약 (코덱스 검토 반영)

**2-D warm-메모**: (URL,width) 단위로 "최근 warm"과 "확인 중(in-flight)"을 분리, 확인·선점은
한 lock 안에서. **성공한 ensure_thumb 만** warm 기록(실패·취소는 in-flight 해제만). 값에
확인된 cache_path 를 함께 저장 — evict_thumb_cache 가 지운 JPG 경로로 **targeted 무효화**
(전체 클리어 금지). 원본 LRU(cache_thumb_source) eviction 은 warm 무효화 사유 아님(리사이즈
JPG 독립 유효). 한계 문서화: 원본·JPG 모두 소실 시 TTL 동안 prewarm 생략→on-demand 복구
(성능 저하일 뿐 정확성 무해), 단일 uvicorn worker 전제(멀티프로세스는 중복 검사·교차
eviction 미감지 — on-demand 로 회복). 초기값: monotonic TTL 300s·LRU 20,000키·폭 256/512 만.
테스트: 동시 목록 2개에서 URL별 원본 확인 1회·폭별 생성 1회 / 실패 미기록 / targeted
eviction / TTL 만료 / LRU 상한.

**2-A known-jobs**: 반환에 명시적 보류값 도입(None=판별 실패 → 이번 사이클 보류, set=확정
차집합) — 빈 set 과 보류를 구분. 행렬: 빈 입력 / 정상 200 / malformed 200 / 404·405→정상
GET / 404·405→GET 실패·malformed / 3xx·4xx·429·5xx·0. 각 케이스에서 ingest 에 jobs 가
실리는지까지 검사(현재 버그: GET 실패=빈 known 오인→전량 선택).

**2-B 정적 스킵(보안 단독 리뷰)**: prefix 허용목록이 아니라 **동적 경로 제외 방식** —
snapshot 가드 뒤·토큰 읽기 전에 `path.startswith("/api/") or path.startswith("/media")` 가
아닌 요청만 통과. /api/assets/file·thumb·/api/media-thumb·/api/download·/api/auth/me·
logout·/api/agent/download·/api/resolve/script 등은 전부 API 경계 안(스킵 금지). /media
검사 정규화 금지. /ws 는 대상 아님. 검증: 쿠키 있는 정적 get_account 0회·보호 API 1회·
snapshot 가드·AUTH-off 원격 403 순서 불변.

**3-A snapshot 경계**: "한 번의 _initial_cycle 또는 wait 복귀 후 한 반복" 안에서만 재사용,
35초 대기 경계 넘김 금지. execute_pending 의 workspace 변경 뒤 workspace/credits 재수집,
CLI 재로그인 성공 시 즉시 폐기. bat 은 출력+errorlevel 모두 보존되는 1회 호출로. 테스트:
동일 email 전파·계정 전환·workspace set·재귀 push·bat 종료코드.

**1-D migration 순서 게이트**: 인덱스는 schema.sql 금지, asset parent_id ALTER '뒤'
migration 에서 생성. 테스트: parent_id 없는 구형 asset_comment DB 로 init_db 성공→partial
index 존재→2회째 부팅 멱등 + sqlite_master.sql 의 WHERE 절 + EXPLAIN 확인.

**3-E 선행조건**: init_db 스레드 실행 안전성·CLI task 의 DB 비의존·시작 실패 시 task 회수
증명 없이는 착수 금지.
