# 공유·최종 상태 보상 계약 (RL-11 — 대체됨)

기준 구현: `18d63560`

> [!CAUTION]
> **이 문서는 현행 계약이 아니다.** RL-11 당시의 *1회성 원격 보상* 규칙을 그대로 보존한 과거
> 기록이다. 아래 4·5번과 실패 표의 "원격 작업을 되돌린다"는 지금 구현과 **반대**다.
>
> 현행 계약은 [SHARE_STATE_RECONCILIATION_DESIGN.md](SHARE_STATE_RECONCILIATION_DESIGN.md) 의
> **converge-forward** 다 — 서버가 확정한 사용자 의도는 로컬 장애 때문에 되돌리지 않고,
> 영속 원장에 기록한 뒤 reconciler 가 서버의 현재 권위 상태를 관측해 로컬 미러를 앞으로
> 수렴시킨다(`backend/app/main.py` 의 `periodic_share_state_reconciler`,
> `backend/app/services/share_state_reconciler.py`).
>
> 아래 본문은 **왜 그렇게 바뀌었는지** 판단하기 위한 근거로만 읽는다.

로컬 허브와 공유 서버 사이에서 `공유됨`과 `최종 선택` 상태가 다르게 남지 않게 하려던 당시 계약이다.
구현 위치는 `backend/app/routers/share.py`, 회귀 테스트는
`backend/tests/test_share_state_consistency.py` 였다.

## 지켜야 하는 불변식

1. **최종 선택된 생성물은 공유 상태여야 한다.** 즉 `is_final = true`이면 공유 레코드가 존재해야 한다.
2. 프록시 모드의 공유 상태는 공유 서버 응답을 먼저 확인하고 로컬 표시를 나중에 바꾼다.
3. 원격 결과가 불명확하면 성공으로 추측하지 않는다. 로컬 상태도 임의로 바꾸지 않는다.
4. 로컬 반영에 실패하면 재시도·재조회로 실제 상태를 확인하고, 필요하면 원격 작업을 되돌린다.
5. 텔레메트리 변경 표시는 로컬 상태가 일관된 뒤에만 남긴다.

## 작업별 판정표

| 요청과 결과 | 로컬 처리 | 사용자에게 보이는 결과 |
|---|---|---|
| 공유 해제 요청인데 로컬 생성물이 최종 선택 상태 | 네트워크 요청 전에 중단 | `409`; 먼저 최종 선택을 해제하라고 안내 |
| 공유 서버의 공유 해제 성공 | 로컬 공유 표시 제거 | 성공 |
| 서버가 명시적으로 `generation 없음`을 반환하고 로컬이 최종 아님 | 이미 해제된 것으로 보고 로컬 공유 표시 제거 | 성공 |
| 단순 `Not Found` 또는 알 수 없는 `404` | 로컬 상태 유지 | 원격 오류 전달 |
| 최종 해제 원격 성공 + 로컬 반영 성공 | 로컬 `is_final` 해제 | 성공 |
| 로컬 반영 중 예외 뒤 재조회 결과가 이미 해제됨 | 성공한 쓰기로 확정 | 성공 |
| 로컬 반영이 계속 실패하고 원격 재최종 지정 성공 | 원격을 이전 상태로 복구하고 로컬 유지 | `503`; 일관성은 복구됐지만 요청은 실패로 안내 |
| 로컬 반영 실패 + 원격 보상도 실패 | 로컬을 성공으로 표시하지 않음 | `502`; 운영 로그로 추적 |
| 최종 해제에서 공유 서버가 `404` 반환 | 의미를 추측하지 않고 로컬 유지 | 원격 오류 전달 |

## `404`를 모두 같은 뜻으로 보지 않는 이유

혼합 버전 업데이트 중에는 구형 공유 서버에 새 엔드포인트 자체가 없어 `Not Found`가 올 수 있다.
이를 “이미 공유 해제됨” 또는 “이미 최종 해제됨”으로 해석하면 로컬 표시만 바뀌어 상태가 어긋난다.
따라서 공유 해제의 **명시적인 생성물 부재 응답**만 멱등 성공으로 인정한다. 최종 해제의 `404`는
항상 실패로 유지한다.

## 자동 검증

PowerShell에서 프로젝트 루트를 기준으로 실행한다.

```powershell
cd backend
py -3 -m pytest tests\test_share_state_consistency.py -q
```

합격 기준은 12개 통과다. 실제 임시 SQLite DB에서 최종→공유 불변식과 최종 해제 반영을 확인하고,
모의 공유 서버로 구버전 `404`, 쓰기 후 응답 유실, 재시도, 원격 보상 성공·실패를 확인한다.

관련 공유·프록시 묶음 62개와 백엔드 전체 778개도 함께 통과해야 한다. 실제 두 계정과 운영 공유
서버를 잇는 `publish → 조회 → unfinalize/unpublish` 왕복은 자동 테스트가 대신할 수 없으므로
[RISK_REDUCTION_PLAN_2026-08-15.md](RISK_REDUCTION_PLAN_2026-08-15.md)의 Gate 6 외부 실측으로 남긴다.

## 로그와 운영 판단

보상 실패는 오류로 기록하되 인증정보, 전체 프롬프트, 원본 URL은 기록하지 않는다. 운영자는 HTTP
상태와 로컬·원격 생성물 식별자를 이용해 재확인한다. 사용자가 성공 응답을 받지 않았다면 화면만 보고
다시 공유 해제·최종 해제를 반복하기 전에 서버 상태를 먼저 조회한다.
