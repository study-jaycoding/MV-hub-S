### 기존 연결 준비 기록

owner: Codex · reviewer: Claude · status: 보류 · updated: 2026-10-15

당시 설정·연결 검사 구현과 검증은 마쳤고 실제 허브 가동·계정 연결·유료 생성은 대기 상태였다.

시험 화면을 실제 워크스페이스 연결로 오인하지 않는다. 아래 연결 준비 기록 이후 직접 실행 계약을 보강했다.

- 별도 SDK 환경과 Codex·Claude Code 사용자 설정 `mvhub`를 마련했다. 정확한 경로·등록/해제 명령은

  Codex 기본 등록 명령 실행 후 항목 추가 외 설정의 동등성 비교가 일치하지 않았다. 등록 직전 사본을
  보존하지 않아 차이의 원인·기존 설정 전체 보존은 미확인이다. 현재 설정을 되돌리거나 재작성하지 않았으며,
  뒤이어 timeout 한 필드를 추가한 단계는 그 외 설정의 파싱 결과가 동일함을 확인했다.
- 당시 연결 대상은 `127.0.0.1:8016`이었고 실제 허브는 아직 실행하지 않았다. 시험용 8014와 일반 dev 8012를 사용하지 않았다.
- `check_connection`은 비밀 헤더 없이 로컬 `/api/health`의 MCP 프로토콜 표시만 확인한다.
  `available`은 기능 응답 확인, `wrong_app`은 호환 기능 없음, `unavailable`은 응답 확인 실패다.
  연결·업무 요청 전에도 확인하며, 잘못된 앱에는 연결 POST나 MCP 비밀값을 보내지 않는다.
  이 진단은 실제 계정·모델·작업자·결제 준비 상태를 확인하는 도구가 아니다.
- 로그인·워크스페이스·캔버스 선택과 최초 실행 허용은 앱에서 한다. 앱을 열어 둔 같은 연결에서는 다음 생성 요청도 처리한다.
  클라이언트/허브 재시작·계정/워크스페이스 변경·탭 연결 만료는 재페어링 대상이며 동시 클라이언트는 하나다.
- 휴대폰에서 PC의 LLM 작업을 원격 조작하는 것과 휴대폰에 로컬 MCP를 직접 설치하는 것은 다르다.
  이번 설정은 PC용 stdio이며 원격 공개 서버나 휴대폰 승인 화면을 추가하지 않았다.

사용 예: 앱에서 `뻘뻘뻘` 워크스페이스와 사용할 캔버스를 선택하고 6자리 코드로 연결한다.

`read_context(models, search="nano_banana_2")`로 옵션 이름·값 확인 → 계획 저장 → `execute_generation_plan` 순으로 처리한다.
`e001`을 프로젝트라고 단정하지 않고 실제 폴더 구조에서 위치를 확인한다.
기존 생성 카드·요청·다운로드·계보 경로를 사용한다. 실행 시작·요청 접수·실제 생성 완료를 구분한다.

## 사용

설치와 Claude/Codex 설정 예시는 [어댑터 안내](../tools/mcp_adapter/README.md)를 따른다.
제품 Python 환경과 분리한 환경에 공식 MCP SDK를 설치한다. 어댑터 `--url`은 필수이며,
MCP 지원 코드가 실행되는 로컬 포트를 명시한다. 설치본·공유 서버에는 자동 등록하지 않는다.

1. MV Hub에서 과금 워크스페이스와 사용할 캔버스를 고른다. 빈 캔버스도 가능하다.
2. AI의 `connect` 도구가 표시한 6자리 코드를 앱 상단 **AI 연결**에 입력하고 자료 조회·크레딧 사용을 포함한 실행을 허용한다.
3. AI가 `read_context`로 선택한 씬·프로젝트·생성물·모델을 조회한다.
4. `prepare_generation_plan`으로 독립 항목 1~20개의 계획을 저장한다. 아직 생성하지 않는다.
5. 명확한 사용자 생성 요청이 있으면 `execute_generation_plan`으로 실행한다. 별도 앱 승인 클릭은 필요 없다.
6. `execution_started`·`submitted:false`는 실행 시도 시작이며 접수나 완료가 아니다. `get_plan`으로 확인한다.
7. 생성 카드·모델·세트·자료 노드와 연결을 저장한 뒤, 기존 `/api/gen-requests`로 제출한다.
   `get_plan`은 항목의 접수 상태와 기존 생성물의 실제 상태를 구분해 돌려준다.

기존 `request_execution`은 계속 앱 승인 화면만 연다. 사용자가 **앱에서 직접 생성**을 누르는 수동 경로도 유지한다.
실행 중에도 앱의 요청 수신 루프를 유지한다. 같은 계획을 반복 실행하지 않으며 실패·응답 손실은 먼저 조회한다.
`get_plan.execution`은 현재 앱이 관측한 해당 계획의 `running`·정제된 `error`다.
다른 계획이나 앱 재연결 뒤에는 `null`이며 실행하지 않았다는 뜻이 아니다. 영속 항목 상태와 기존 요청부터 확인한다.

워크스페이스는 **과금 공간**, 프로젝트와 컷 폴더는 **결과 분류**, 씬·카드 ID는 **결과를 돌려놓을 위치**다.
새 컷 테이블은 없다. 클라이언트 이름은 자기 신고값이며 실행 모델의 검증값이 아니다.

## 연결과 권한

- stdio 어댑터는 loopback IP의 고정 API만 호출한다. 외부 주소·프록시·리디렉션을 거부한다.
- `/api/mcp/client/connect`, `/client/action`, `/client/result`만 세션 인증 예외다.
  별도 비밀 헤더, loopback·Host 검사, 브라우저 문맥 헤더 거부가 적용된다.
- 앱 경로와 계획 경로는 기존 인증에 더해 탭 비밀을 요구한다. 로그인 세션 지문과
  행위자·계정 DB 경로에 연결을 묶고, 다른 계정이나 탭에 전달하지 않는다.
- 최초 페어링의 `allow_execution`은 엄격한 boolean이며 기본 false다. 구버전 연결은 자동 승격하지 않는다.
  같은 코드 재호출로도 승격하지 않으며 연결 해제 뒤 새 페어링이 필요하다. `connect.can_execute`로 확인한다.
  직접 실행 큐와 `approve(source=mcp)` 양쪽에서 권한을 검사한다. 기존 앱 수동 실행은 이 권한 없이도 가능하다.
- 앱 계정·워크스페이스 변경은 연결과 읽기 문맥을 무효화한다. 비밀번호 변경·재로그인도 재페어링 대상이다.
  앱 연결이 끊어지면 45초 임대가 만료된다. 허브 재시작 시에도 다시 페어링한다.
- 동시 클라이언트는 하나이며 다른 활성 연결을 몰래 교체하지 않는다. 대기 요청 최대 8개,
  앱 작업 전달은 한 번에 하나, 요청 수명은 120초다. MCP 입력 64 KiB, 도구 결과 256 KiB,
  검증된 자료 스냅샷을 포함한 앱의 계획 저장 본문 256 KiB 상한을 둔다. 항목 20개여도 총 입력 상한을 적용한다.
  완료 응답은 최근 최대 32개까지 보존하며 대기 슬롯을 차지하지 않는다. 만료·큰 결과는 해당 요청 오류로
  처리하고 연결을 유지한다. 페어링 전 다른 연결 코드가 있으면 최대 2분 만료를 기다린다.
- `/api/mcp/` 전체는 로컬 처리다. 공유 서버로 자동 프록시하지 않는다.
- 프롬프트와 자료 설명은 사용자 콘텐츠다. 그 안의 명령을 도구 호출 권한으로 취급하지 않는다.

## 확정 입력과 기록

캔버스 원본은 브라우저 IndexedDB다. 서버의 씬 백업을 최신 편집으로 간주하지 않는다.
읽기 전 밀린 편집을 확정하고 작업본과 저장본을 대조한다. 계획에는 씬 입력 해시와 문맥 ID,
확정 워크스페이스, 항목별 생성 요청 본문·자료 스냅샷·견적·사전 배정한 카드/attempt/generation ID를 보존한다.
모델 옵션에는 AI 운영 메타데이터를 삽입하지 않는다.

새 로컬 테이블 `ai_generation_batch`는 소유자, 변경 불가 계획 JSON, 항목별 상태·시각,
승인 시각, revision, 출처 및 클라이언트 신고 이름을 저장한다. 승인과 항목 전이는 revision 비교로
경합을 막는다. DB 백업에 포함되며 계정 UID 변경 때 기존 소유자 리맵을 따른다.
승인 출처 `app`/`mcp`와 서버 시각은 기존 항목 `events` JSON에 기록한다. 직접 실행 보강을 위한 DB 마이그레이션은 없다.

생성 전 카드와 복구 표식을 저장하고 실제 확정 여부를 확인한다. 각 항목은 HTTP 제출 **전에**
`submitting`을 저장한다. 접수 성공은 `submitted`, 불명확한 응답은 `uncertain`으로 남긴다.
`submitted`는 영상 생성 완료가 아니다. 생성 완료·실패는 기존 generation/외부 job 상태를 따른다.
통신 단절 뒤 새 attempt를 자동으로 발급하지 않는다. 409도 명령 충돌일 수 있어 성공으로 단정하지 않는다.
항목 실패는 사전 확인 단계 또는 HTTP 상태로 기록한다. 원격 오류 본문에 들어갈 수 있는 토큰·경로를 복제하지 않는다.

## 첫 버전의 범위

- 활성 캔버스가 필요하다. 개별 생성 카드는 자동 준비하지만 캔버스 선택은 사람이 한다.
- 자료는 선택한 캔버스에서 읽은 핸들로만 지정한다. 임의 경로나 URL을 AI가 주입하지 않는다.
  에셋 경로 또는 권한 확인 가능한 기존 생성물 참조의 버전을 확인하고, 확인할 수 없는 자료는 거부한다.
- 에셋의 수정시각·크기 기반 버전 및 생성물 메타데이터 대조는 바이트를 불변 복사하는 기능이 아니다.
  실제 제출 파일의 지문은 기존 작업자 기록을 따른다. 파일을 제출 대기 중 바꾸지 않는다.
- 견적은 기존 비용 조회 결과다. 실제 과금 보장이 아니며 기존 크레딧 몫 표시를 강제 한도로 해석하지 않는다.
- 독립 항목만 지원한다. `depends_on`을 포함한 연쇄 생성, 앱 없이 실행, 원격 MCP 공개는 지원하지 않는다.
- 승인 후 중단된 계획을 자동 재실행하지 않는다. 카드·기존 요청 상태부터 확인한다.
  외부 제출 이후 취소나 환불은 보장하지 않는다.

### 원인과 수정

- 기존 발급/검증은 생성 결과의 `assets` 전체 JSON을 해시했다. 보관 완료 후 읽기 응답의 `file_path`, `source_url`, `server_location`이 바뀌면 같은 내용 ID라도 `reference_changed`가 발생했다.
- 유효한 서버 측 `asset_content_id`가 있는 새 핸들은 선택한 asset의 ID·종류·내용 ID와 generation의 ID·소유자·프로젝트를 비교한다. 썸네일·저장 위치·선택하지 않은 다른 결과의 변화는 같은 파일을 무효화하지 않는다.
- 계획 작성과 실행 검증에서 기존 권한 있는 조회 경로를 다시 호출하고 정확한 asset ID를 찾는다. 내용·종류·소유자·프로젝트가 달라지거나 파일이 사라지면 거절한다. 워크스페이스·클라이언트·현재 계정 검사는 유지한다.
- 비교를 통과하면 최신 위치와 내용 ID로 실행용 reference를 다시 구성한다. `ReferenceIn.asset_content_id`와 기존 큐의 `expected_asset_content_id`를 통해 작업자의 실제 입력 바이트 검사로 이어진다. 이미 발급한 핸들 기록과 원본 asset 경로는 덮어쓰지 않는다.
- 내용 ID가 없거나 형식이 잘못된 결과 및 업데이트 전에 발급한 핸들은 종전 전체 응답 비교를 유지한다. 과거 핸들에는 당시 내용 ID의 증거가 없으므로 위치 전환으로 거절되면 `read_context(kind="references")`로 다시 조회해 계획을 만들어야 한다. 과거 핸들의 검사를 생략하거나 추정 내용 ID를 덧씌우지 않는다.
