## 1. 무엇을

PM 창 '완료' 탭의 "완료만 저장하기"를 넓힌다(Jay 2026-09-21).

| 단추 | 하는 일 | 단계 |
|---|---|---|
| **공유 저장**(라임) | 공유 중이지만 최종은 아닌 것 중 폴더에 없는 것만 저장 | 1 |
| **최종 저장**(골드) | 최종(★) 중 폴더에 없는 것만 저장 — 종전 "완료만 저장하기" | 1 |
| **비교**(마주 도는 화살표 아이콘) | 읽기만. 프로그램이 원하는 집합(공유+최종)과 렌더 폴더를 견줘 ①새로 저장할 것 ②폴더에만 남은 우리 파일 ③같은 것 ④모르는 파일 을 보여 준다 | 2 |
| **➡ 미러** | ① 저장 + ② 정리 — 끝나면 폴더가 프로그램과 같다 | 3나 |
| **❯ 업데이트** | ①만 저장(공유+최종 한 번에) | 3가 |

- 미러·업데이트는 **비교를 실행해야 켜진다.** 프로젝트를 바꾸거나 프로그램 쪽 상태가 달라지면 다시 꺼지고 비교를 새로 해야 한다(낡은 비교로 실행 금지).
- 단추 오른쪽 두 줄 설명(Jay 가 고친 글): "미러 - 실시간 동기화 (삭제 및 변경 가능)" / "업데이트 - 추가분 누적 동기화". 여기서 '실시간'은 "누른 그 시점의 프로그램 상태 그대로"라는 뜻이다 — 계속 자동으로 맞추는 기능은 없다(누를 때 한 번).

## 2. Jay 결정(2026-09-21)

1. **공유본 위치** = 컷 폴더 안의 `shared/`(`Render/<폴더>/shared/<이름>`). 최종본 경로는 종전 그대로 — 이미 저장된 최종본이 안 움직이고, 폴더만 봐도 어느 것이 최종인지 구분된다.
2. **보류 포함** — 보류는 "공유는 됐지만 최종이 아닌" 검토 상태라 공유 저장에 들어간다.
3. **미러의 정리 = 옮기기** — 지우지 않고 `Render/_mvhub_removed/<날짜_시각>/<원래 상대경로>` 로 옮긴다. 되돌리기 = 제자리로 옮기기.

## 3. 규칙

- **종류** `final` · `shared`(`services/final_export.py::KINDS`). 두 집합은 겹치지 않는다 — 공유→최종이 되면 `final` 로만 센다. 공유 판정의 권위 = 서버의 `share` 원장(`EXISTS share`), 위임 모드에서 로컬 목록으로 판정하지 않는다.
- **저장 폴더** `project_folders.export_folder(folder_path, kind)`. 사실(targets)의 `folder_path` 는 컷 폴더 그대로 두고(폴더 우클릭 좁히기 기준), 목적지를 계산할 때만 `shared/` 를 붙인다.
- **"이미 저장" 판정** `routers/manage.py::_dest_state` — 아래는 **옛 이름**(`<컷>_<gen 12자>`)의 규칙이다. 2026-10-08 부터 새 저장은 번호 이름이고 판정은 `_locate_export` 가 한다(§6). 옛 이름에는 gen_id 앞 12자만 있어 이름이 같다고 같은 생성물은 아니다(Codex P0).
  대장이 그 경로를 기억하면 saved(싸다) → 아니면 각인을 읽어 **다른 생성물이면 conflict**(건너뛰지도 덮어쓰지도 않고 "같은 이름의 다른 파일"로 알린다) → 각인이 없으면 종전처럼 saved(각인 이전 파일·다른 PC 의 각인 실패본이 전부 충돌로 뒤집히지 않게). **파일을 옮기는 미러는 이 느슨한 판정을 쓰지 않는다**(각인 일치만).
- **구서버 방어** — `GET /api/manage/save-finals/targets?kind=` 는 응답에 `kind` 를 되돌려 준다. 구서버는 kind 를 모르고 최종 목록을 주므로, 되돌아온 kind 가 다르면 로컬 허브는 공유 기능만 끈다(`shared_supported=false`). 최종 저장은 구서버에서도 그대로 된다.
- `…/content/{gen_id}`(바이트 중계)는 종류를 가리지 않고 "어느 종류든 저장 대상"이면 통과한다.
- `POST /api/manage/save-finals?kind=final|shared|all` — 기본 `final`(폴더 우클릭 '최종 저장'은 그대로 — 2026-10-08 부터 폴더 우클릭 '공유 저장'이 `kind=shared` + `folder_path` 로 같은 API 를 쓴다). `all` 은 최종 먼저.
  `all` 에서 한 종류가 통째로 막히면(예: 구서버라 공유 불가) 이미 저장한 쪽의 결과를 잃지 않고 오류 줄로만 남긴다(Codex P1).
- 상태 조회에서 공유 쪽 조회만 실패하면 최종 목록은 그대로 주고 `shared_supported=false`·`shared_error` 로 알린다 — 새 기능의 장애가 기존 최종 저장을 막지 않는다(Codex P1). 프런트는 `shared_supported === true` 일 때만 공유 저장을 켠다.
- 각인 읽기(영상은 ffmpeg)는 **비교·저장 때만** 한다 — 대장에 없는 기존 파일에 한해서. 상태 조회는 폴더도 각인도 보지 않는다(3-0).

- **원본을 찾는 순서** `routers/manage.py::_export_source` — 로컬 `/media/…` 파일 → 없으면 남아 있는 원본 주소(`asset.source_url`, 힉스필드 CDN). 위임 모드의 바이트 중계(`…/content/{gen_id}`)와 단독 경로가 같은 함수를 쓴다.
  둘 다 없으면 **사실 단계에서** `원본 파일 없음(다시 받을 주소도 없음)` 으로 저장 불가 표시 — 종전에는 저장을 눌러야 "로컬 원본 없음"이 나왔다. 원본 주소가 만료됐으면 `원본 다운로드 실패`(주소 수명은 확인하지 못했다).

## 3-0. 탭을 열 때는 대장(DB)만 본다 (Jay 2026-09-21)

- 상태 조회(`GET …/save-finals`)의 `saved` 는 **이 PC 의 저장 대장 `final_export`** 로만 정한다 — 대상마다 NAS 를 확인하면 공유본 수백 건이라 탭을 열 때마다 느리다(공유 저장을 넣으면서 생긴 회귀였다: 대상 2건 → 408건).
  실측(테스트 DB 사본, 대상 408건): 대상 판정 DB 조회 약 10ms×2 · 사실 목록 조립 약 90ms · 대장 조회 1ms — **DB 는 병목이 아니다.** 느린 쪽은 NAS 의 파일 확인(건당 SMB 왕복)과 대장에 없는 기존 파일의 각인 읽기(영상은 ffmpeg)였다(이 PC 에는 NAS 가 없어 그 시간은 재지 못했다).
- 대장은 ①저장할 때 적히고 ②**비교가 실제 폴더에 맞춘다** — 폴더에는 있는데 안 적힌 것(다른 PC 가 저장)은 적고, 적혔는데 폴더에 없는 것(손으로 지움·미러가 옮김)은 지운다. 그래서 비교 한 번 뒤에는 빠른 표시도 정확하다.
- 저장·업데이트·미러는 언제나 실제 폴더를 확인한다(대장만 믿고 건너뛰지 않는다). `같은 이름의 다른 파일` 충돌은 비교·저장 때 드러난다.
- 화면: 단추 다섯 개 모두 "~하시겠습니까? 예/아니오" 확인 창을 거친다. 단추 순서는 **예 · 아니오**(Jay 2026-09-21). 미러의 확인 창은 옮길 파일 목록을 함께 보여 주고, "N개 옮기고 M개 저장"은 단추 안이 아니라 **단추 바로 앞의 글**로 둔다(문구 · 예 · 아니오 — 누르기 전에 개수를 읽게).
- 상태 조회에서 디스크에 가는 것은 **대상 수와 무관한 두 가지뿐**이다: 렌더 폴더 확인·경로 해석(호출당 몇 회)과 저장 이력 최근 20건의 파일 확인(`list_exports` 의 상한). 대상마다의 목적지는 `project_folders.ledger_dest`(글자 검증 + 순수 결합)로 만든다 — 2026-09-21 실측에서 `safe_dest`(대상마다 `resolve()` 3회)가 406건에 260~540ms 였고(NAS 면 건마다 왕복), 고친 뒤 같은 조건 4ms. 쓰기·비교·미러는 계속 `safe_dest`. 한계: 렌더 폴더 **안쪽**에 심볼릭 링크·junction 이 있으면 '이미 저장'이 '새로 저장'으로 보인다(저장은 실제 폴더를 확인해 건너뛴다).
- 저장 대상 표(Jay 2026-09-21): 작업 탭 같은 격자선 표 — 구분 · 컷 · 파일 이름 · 종류 · 상태 · 저장한 때. 씬(폴더의 앞부분)별 묶음 줄, 컷 = 폴더의 마지막 마디, 위에 거르기 단추(전체 · 최종 · 공유 │ 새로 저장 · 이미 저장 · 저장 불가, 하나만 켜짐 · 프로젝트를 바꾸면 전체로). 표는 창 높이를 따라 늘어난다(최소 340px — 그보다 작은 창에서는 창이 스크롤된다). `저장한 때`는 대상마다 내려오는 `saved_at`(대장의 시각 UTC → 화면에서 이 PC 의 시각)이다 — 저장 이력은 최근 20건뿐이라 표를 못 채운다. 종류는 파일 확장자로 정한다(`lib/media.ts`).

## 3-1. 비교 · 업데이트(구현)

- `GET /api/manage/save-finals/compare?project_id=` — **로컬 전용**(`_LOCAL_EXACT` 에 이 경로만), 프로젝트 관리 권한. **렌더 폴더는 읽기만** 하고, 이 PC 의 저장 대장은 폴더에 맞춘다(3-0).
  `to_add`(프로그램에는 있는데 폴더에 없다) · `extra`(폴더에만 남은 우리 파일) · `blocked`(저장 불가·같은 이름의 다른 파일) · `same` · `unknown`(세기만) · `cleanup_blocked`(정리를 하지 않는 이유 — 아래).
  ★`extra` 의 조건(2026-09-21 실측 뒤 강화): 이름 규칙(옛 이름 `<시퀀스>_<gen 앞 12자>` 또는 번호 이름 `…_<share|fin>_<번호>` — §6) + 각인(hub 표식·gen_id) + **이 PC 의 대장이 그 생성물을 이 프로젝트로 바로 그 경로에 저장했다고 기억할 것**(`repo_manage.export_places` — (gen_id, 정확한 경로), 상한 없음). 각인에는 프로젝트가 없어서 각인·이름만 보면 같은 폴더에 있는 **다른 프로젝트의 파일**까지 옮긴다(실측으로 재현). 다른 PC 가 저장했고 이 PC 가 적어 둔 적 없는 파일은 `unknown` 이다 — 그 PC 에서 정리한다.
  대장의 두 곳: `final_export`(지금 자리 — 생성물당 한 줄이라 다시 저장하면 경로가 덮어써진다) + `final_export_old`(**옛 자리** — 덮어쓰기·지우기 직전에 남긴다. 컷 폴더가 바뀐 생성물의 옛 파일을 찾는 유일한 단서). 옛 자리는 **그 폴더를 실제로 열거했는데 그 이름이 없었을 때만** 잊는다(`is_file()` 의 False 는 NAS 순간 단절일 수 있다). 렌더 폴더 밖 경로는 훑지도 확인하지도 지우지도 않는다. 영구 삭제의 고아 정리 대상이 아니다(생성물이 지워져도 남은 파일을 찾을 단서).
  훑는 폴더 = 대상 목적지의 부모 + 위 대장의 자리들(렌더 루트 아래만). 렌더 루트 전체를 재귀로 훑지 않는다.
  `cleanup_blocked`: **같은 렌더 폴더를 쓰는 다른 프로젝트가 이 PC 의 프로젝트 목록에 있으면** 정리 후보를 내지 않는다(저장은 그대로). 생성물을 그 프로젝트로 옮겨 간 경우 이 프로젝트의 대장 증거(같은 gen_id·같은 경로)가 새 프로젝트의 **지금 파일**을 가리키기 때문이다. 경로는 글자로 견준다(구분자·대소문자·끝의 `/Render` 무시). 매핑 드라이브(`Z:`)는 이 PC 의 대응표로 UNC 로 바꿔 견준다 — `Z:\x` 와 `\\nas\share\x` 는 같은 폴더다(2026-09-22, `path_safety.unc_for_drive` — 디스크·네트워크는 묻지 않는다). 이 PC 에서 드라이브 대응을 알 수 없는 경로(연결 안 된 드라이브 글자 등)는 같은 폴더일 수 있다고 보고 정리를 막는다. 이유 문장에 프로젝트 이름은 넣지 않는다.
  공유 쪽 조회가 실패하면 비교 전체를 실패시킨다 — 반쪽 비교로 '폴더에만 남은 것'을 잘못 세지 않게.
  ★`extra` 의 12자 접두 일치는 **보여 주기용**이다. 미러가 파일을 옮길 때는 각인의 gen_id 전체 일치만 허용한다.
- 업데이트 = `POST …/save-finals?kind=all`. 비교 결과의 목록이 아니라 **그 시점의 대상**을 저장한다 — 저장만 하므로 비교 뒤 새 대상이 더 들어가도 안전하고, 충돌 방어는 POST 가 그대로 한다.
- 화면: 비교 결과는 프로젝트 변경·저장·새로고침 신호 때 버린다(요청 순번으로 늦게 온 응답도 버린다).

## 3-3. 진행률 · 취소(구현, 2026-09-22)

공유본은 한 프로젝트에 수백 건이라 한 번 누르면 **말없이 수백 개를 내려받는다** — 느린 것과 멈춘 것을 구별할 수 없고 멈출 수도 없었다.

- **작업 id 를 만들지 않는다.** 저장은 프로젝트당 한 번만 돈다(`_save_finals_lock`) → "지금 이 프로젝트의 저장"은 언제나 하나라서, 프로젝트별 기록 하나면 된다. 시작/조회/취소 3단 수명주기는 이 제약에서 군더더기다.
- `GET …/save-finals/progress?project_id=` · `POST …/save-finals/cancel?project_id=` — 둘 다 **로컬 전용**(`_LOCAL_EXACT`)이고 저장과 같은 프로젝트 관리 권한이다. 저장이 이 PC 에서 도니 그 상태도 이 PC 가 안다.
- **`run`(실행 세대)** 를 같이 주고받는다 — 끝난 저장에 늦게 도착한 취소가 **다음** 저장을 죽이지 않게(코덱스 P1). 취소는 현재 세대이고 아직 돌고 있을 때만 받는다.
- **기록은 잠금을 잡은 뒤에 만든다** — 잠금을 기다리던 다음 요청이 먼저 만들면 앞 실행의 진행 수와 취소가 섞인다(코덱스 P1).
- **취소의 뜻**: 받던 파일 하나는 끝내고 **그다음을 시작하지 않는다**. 이미 저장·건너뛴 것은 되돌리지 않는다 — 저장은 더하기만 하므로 '반쪽'이 아니라 '덜 한 것'이고, 다시 누르면 이어서 한다(멱등). 큰 파일 하나를 받는 중이면 그 파일이 끝날 때까지는 멈추지 않는다.
- **미러는 취소되면 정리를 시작하지 않는다** — 파일을 옮기기 시작하면 중간에 멈출 수 없다(코덱스 P1). 저장한 것만 두고 "다시 비교하세요"로 끝낸다.
- `done` 은 '끝난 수'가 아니라 **'손댄 수'**다(계약). 순차 처리라 끝난 수와 최대 1 차이이고, 루프 본문이 여러 군데서 빠져나가도 세는 자리를 하나로 두기 위해서다. 화면 문구도 "처리 중"이다. `kind=all`·미러는 종류별로 대상을 조회해 더하므로 **분모가 도중에 한 번 는다**(최종 → 공유).
- **한계**: 기록은 메모리에만 있다 — 서버를 다시 켜면 사라지고, 프로세스가 여럿이면(지금은 하나) 잠금과 마찬가지로 프로세스마다 따로라 지원하지 않는다. 끝난 기록은 10분 남겨 창을 닫았다 열어도 "지난 저장"을 보여 주고, 다음 저장이 시작할 때·조회할 때 만료된 것을 버린다. **탭을 닫으면 저장이 끝까지 간다는 보장은 없다**(받던 파일 하나는 마치고 멈춘다).

## 3-2. 미러(구현) — `POST /api/manage/save-finals/mirror`

로컬 전용(`_LOCAL_EXACT`), 프로젝트 관리 권한. 순서: 프로세스 잠금 → **NAS 잠금** → 1차 스캔(공유를 못 읽거나 구서버면 여기서 중단 — 아무것도 안 건드린다) → 정리 비율 확인 → 최종·공유 저장 → **다시 스캔** → 옮기기.

옮기는 파일 = ①사용자가 확인 창에서 본 목록 ∩ ②실행 시점에 다시 훑은 `extra` ∩ ③mtime 이 10분보다 오래된 것 ∩ ④옮기기 직전에 다시 읽은 각인이 그대로인 것(hub 표식 + gen_id 전체).

| 위험(Codex) | 막는 장치 |
|---|---|
| 다른 PC 가 막 저장한 파일을 낡은 판단으로 옮김 | 실행 시점 재스캔(그 파일은 대상이라 `extra` 가 아니다) + 10분 가드 + 직전 각인 재확인 |
| 원본을 잃어 '저장 불가'가 된 대상의 **이미 저장돼 있던 파일**을 남은 것으로 오인 | `protected` = 지금 대상인 모든 목적지(저장 가능 여부와 무관) + 저장 불가 대상의 gen_id 는 `extra` 에서 제외. 파일 이름은 원본을 못 찾아도 계산한다 |
| 두 PC 가 동시에 미러 | NAS 잠금 파일(`_mvhub_sync/<해시>.lock`, O_EXCL). **자동 인계 없음** — 긴 미러를 죽은 것으로 오인하면 둘이 동시에 정리한다. 15분 넘게 잡혀 있으면 오류 문구가 지울 파일을 알려 준다. 풀 때는 소유 토큰이 내 것일 때만 지운다 |
| 원하는 집합이 비어 보여 전부 정리 | 정리 > 5개이면서 남는 것보다 많으면 409 → 화면이 한 번 더 확인받고 `allow_many` 로 재요청. **저장하기 전에** 묻는다 |
| 저장은 됐는데 2차 스캔이 실패 | 저장 결과를 살리고 정리만 건너뛴다(오류 줄 "다시 비교하세요") |
| 볼륨이 달라 이름 바꾸기가 실패 | 건별 오류로 남고 원본은 그대로(복사 후 삭제로 대체하지 않는다) |

옮기기 직전의 각인 확인과 이름 바꾸기 사이에도 틈이 있다(원자적이지 않다). 그래서 **실제로 옮겨진 파일**을 한 번 더 읽어 다른 파일이 딸려 왔으면 제자리로 돌려놓는다(그 사이 제자리에 새 파일이 생겼으면 덮지 않고 격리 폴더에 둔 채 알린다). 잠금 해제의 토큰 확인→삭제도 원자적이지 않다(SMB 에는 비교-후-삭제가 없다).

**남은 한계**

- ⓪ 렌더 트리가 겹치는 다른 프로젝트를 이 PC 가 모르는 경우에는 세 갈래다(2026-09-22 정리 — 매핑 드라이브와 UNC 로 글자가 다른 같은 폴더는 `cb4580b8` 부터 잡는다).
  - 가. **아직 옮길 위험**: 권한 밖이라 이 PC 의 목록에 없는 프로젝트, 한 프로젝트의 Render 안에 다른 프로젝트의 Render 가 들어 있는 구성은 위 가드가 못 잡는다. 그때 다른 프로젝트로 옮겨 간 생성물의 파일을 옛 프로젝트의 미러가 (확인 창을 거쳐) 격리 폴더로 옮길 수 있다. 닫으려면 서버가 모든 프로젝트의 렌더 루트와 생성물의 현재 소속을 알려 주는 API 가 필요하다 — **만들지 않는다**(Jay 2026-09-21: 렌더 폴더를 함께 쓰는 프로젝트는 없다. 그런 구성이 생기면 다시 연다 — `status/dev_실측_2026-09-21.md`).
  - 나. **안전하지만 막힘**: 드라이브 대응을 이 PC 가 모르면 같은 폴더일 수 있다고 보고 정리를 막는다 — 매핑을 고치기 전까지 그 프로젝트는 정리되지 않는다(저장은 된다).
  - 다. **문구**: 나 의 경우에도 이유 문장은 "같은 렌더 폴더를 쓰는 다른 프로젝트가 N개"라고 말해 실제(판정 불가)보다 강하다. 문장은 `routers/manage.py` 가 만든다 — 2026-09-22 에는 그 파일을 다른 세션이 고치는 중이라 그대로 두었다(그 작업이 커밋된 뒤 "같은 폴더인지 확인할 수 없는" 경우를 가려 말하게 고친다).
- ① 잠금을 모르는 구버전 앱과의 공존은 완전 보장이 아니다(위 장치로 창을 좁히고, 틀려도 파일은 격리 폴더에 남아 되돌릴 수 있게 할 뿐). **팀 전체가 새 버전으로 올라간 뒤에 미러를 쓰는 것이 안전하다.**
- ② 저장 대장이 PC 마다 따로라, 다른 PC 가 예전에 **다른 폴더**에 저장해 둔 파일은 그 PC 에서 미러해야 정리된다(NAS 공유 목록은 미구현).
- ③ 격리 폴더는 자동으로 비우지 않는다.

## 4. 미러 설계 때의 요구(Codex P0·P1) — 위 3-2 가 구현

- 저장 잠금(`_save_finals_lock`)은 한 PC 안에서만 통한다 — 다른 PC 가 같은 NAS 에 막 저장한 파일을 낡은 비교로 옮길 수 있다 → NAS 에 두는 협력 잠금 파일.
- 저장 대장은 PC 마다 따로라, 폴더가 바뀐 뒤 옛 폴더에 남은 다른 PC 의 파일을 다 찾지 못한다 → NAS 에 두는 공유 저장 목록(manifest) 또는 훑는 범위 규칙.
- 격리 폴더 이름은 실행마다 고유해야 한다(같은 날 두 번 덮어쓰기 금지). 옮기다 끊긴 경우 다음 비교에서 원본·격리본을 함께 본다. 격리 폴더는 비교에서 제외.
- 옮길 수 있는 파일 = 이름 규칙 + 각인의 gen_id 일치 + 이 프로젝트의 생성물(구현: 이 PC 의 대장이 (gen_id, 그 경로)를 이 프로젝트로 기억 — 3-1). 그 밖은 "모르는 파일"로 세기만 한다.
- 대상 사실을 못 받았거나 정리 비율이 비정상적으로 크면 막는다("원하는 집합이 비어 보여서 전부 정리"가 최악의 사고).
- 비교·미러는 프로젝트 **관리** 권한. 비교 API 는 로컬 전용이며 `_LOCAL_EXACT` 에 그 경로만 넣는다(`/save-finals/` 접두를 통째로 로컬로 돌리면 `targets`·`content` 위임이 깨진다).

**프로젝트를 옮긴 생성물**(Jay 결정 2026-09-21): 다른 렌더 폴더를 쓰는 프로젝트로 옮겨 간 생성물의 옛 저장본은 **옛 프로젝트의 미러가 치운다** — 그 생성물은 더 이상 옛 프로젝트의 것이 아니고 새 프로젝트는 자기 폴더에 따로 저장한다(확인 창에 파일 이름이 나오고, 지우지 않고 격리 폴더로 옮긴다). '소속이 바뀌었으니 남겨 둔다'로 바꾸지 않는다.

## 6. 파일 이름 — 번호 이름과 이름 장부(2026-10-08)

owner: Claude · reviewer: Codex(설계 검토 5회 — 서버 배정안 → 렌더 폴더 장부안으로 바뀜, 마지막 수정 요청 2건 반영) · status: 검증 중

**Jay 결정(2026-10-08)**

1. 저장 파일 이름 = `<폴더 마디 전부를 '_' 로>_<종류>_<번호 3자리 이상>` — 예: 폴더 `e020/c0010` 의 공유본 `e020_c0010_share_001.mp4`, 최종본 `e020_c0010_fin_001.mp4`. 번호는 폴더·종류마다 따로 올라간다.
2. **옛 이름(`<컷>_<gen 12자>`)으로 이미 저장된 파일은 그대로 둔다** — 이름을 바꾸지도, 새 이름으로 다시 저장하지도 않고 '이미 저장'으로 본다. 새로 저장하는 것만 번호 이름.
3. 폴더 우클릭 `공유 저장 · 최종 저장`과 완료 탭의 저장은 같은 API 라 함께 바뀐다. 공유본 위치(`shared/`)는 그대로.
4. 다빈치 내보내기 파일은 종류와 상관없이 `…_davinci_<번호>` — 저장본과 **서로 다른 파일**이다(토큰이 달라 이름이 겹치지 않는다). 미러는 다빈치 파일을 건드리지 않는다.

**번호의 권위 = 렌더 폴더 안의 장부** `services/export_names.py` — `<Render>/_mvhub_sync/names/<컷 폴더 키의 해시>/`

| 항목 | 뜻 |
|---|---|
| `n.<토큰>.<번호>` | 이 번호의 주인(생성물) — 번호는 한 생성물만 갖는다 |
| `g.<토큰>.<gen 해시>` | 이 생성물의 번호 — 생성물은 번호를 하나만 갖는다(이름·확장자는 처음 배정한 그대로) |
| `d.<토큰>.<번호>` | 그 이름의 파일을 우리가 확정했다는 표식 |

- 서버·DB 가 아니라 파일 곁에 둔다 — PC 마다·단독/위임 모드마다·DB 복원 뒤에도 같은 답이 나와야 한다. **서버 코드는 바뀌지 않았다**(서버가 주는 `filename` 은 여전히 옛 이름이고, 허브가 그것을 옛 저장본을 알아보는 데만 쓴다).
- 항목은 '임시 파일에 다 쓴 뒤 **덮어쓰지 않는 이름 바꾸기**'로만 만들고 고치지 않는다 → 두 PC 가 같은 번호·같은 생성물을 다퉈도 먼저 만든 쪽 하나만 남는다(진 쪽 번호는 결번).
- 번호는 **쓰기 직전에만** 생긴다(`allocate`). 상태 조회·비교는 읽기만 한다(`name_of`) — 탭을 여는 것으로 번호가 생기지 않는다. 그래서 저장 전인 대상은 이름이 비어 있고 화면은 "저장할 때 정해짐"을 보인다.
- 다음 번호 = max(장부의 번호, **목적지 폴더에 실제로 있는 번호**) + 1 — 장부를 잃어도 이미 있는 파일의 이름을 다른 생성물에 주지 않는다. 한 번 쓴 번호는 다시 쓰지 않는다.
  목적지 폴더는 **저장·전송 한 번에 한 번만** 훑는다(장부 객체가 폴더별 가장 큰 번호를 기억한다 — 파일마다 훑으면 NAS 열거가 '새 파일 수 × 폴더의 파일 수'였다, 2026-10-13). 내가 준 번호와 다른 PC 가 준 번호는 장부로 안다. 훑은 뒤 누가 **장부 없이** 다음 번호 이름의 파일을 놓으면 그 번호를 건너뛰지 못한다 — 덮어쓰지 않고 그 건만 '같은 이름의 다른 파일'로 실패하며(번호를 잡은 뒤의 재확인 + `commit_new` 두 겹), 그 파일을 치우면 같은 이름으로 저장된다.
- 읽지 못했거나 서로 어긋난 장부(짝 없는 `g`·`d`, 깨진 JSON, 이름·폴더 불일치)는 '없음'이 아니라 오류다 — 저장은 그 건을 실패로 남기고, 비교·미러는 통째로 멈춘다(503).

**'이미 저장' 판정** `routers/manage.py::_locate_export`(저장·비교 공용)

- 번호 이름 파일(`_numbered_state`)은 **증거가 있어야** 인정한다: 이 PC 의 대장이 같은 경로를 기억 · 장부가 이 생성물의 이름이라 하고 `d` 도 있음 · 각인이 우리 것이고 이 생성물. 번호 자리는 장부의 이름이고, 장부가 모르면 대장이 기억하는 자리(이 컷·종류의 번호 이름일 때)다. 각인 없는 파일을 이름만으로 인정하지 않는다(ffmpeg 가 없는 PC 는 각인을 못 읽으므로 장부가 주 증거다). 일반 파일이 아니거나 0바이트면 충돌.
- 순서: 번호 이름이 저장돼 있으면 그것 → 아니면 옛 이름(종전 `_dest_state` — 각인이 없으면 저장된 것으로 본다) → 번호 자리에 다른 파일이 있으면 충돌 → 그 외 없음. 옛 이름 자리의 남의 파일은 새 저장을 막지 않는다.
- 확정은 `export_names.commit_new` — Windows `os.rename`(대상이 있으면 실패), POSIX 하드링크. `os.replace` 로 물러서지 않는다. 받는 사이 그 이름의 파일이 생겼으면 덮지 않고 다시 판정한다.
- 상태 조회는 디스크를 보지 않는다(3-0 그대로): 대장의 자리가 이 대상의 목적지 폴더이고 이름이 옛 이름이거나 이 컷·종류의 번호 이름이면 저장된 것.
- 비교의 `extra`(폴더에만 남은 우리 파일): 이름이 번호 이름(`share`·`fin`)이거나 옛 이름 + hub 각인 + 이 PC 대장의 (gen, 정확한 경로). `davinci` 이름은 될 수 없다.

**한계**

- 새 판과 옛 판 앱이 섞인 동안, 옛 판 PC 는 장부를 모르고 옛 이름으로 저장한다 → 번호 이름으로 이미 저장된 생성물이 옛 이름으로 한 번 더 생길 수 있다(덮어쓰기는 없다).

- 대장이 같은 경로를 기억하거나 장부(`n`+`d`)가 맞으면 **각인을 읽지 않는다**(옛 이름과 같은 절충 — 비교·저장 때마다 NAS 의 영상에 ffmpeg 를 돌리지 않는다). 그래서 그 자리에 사람이 다른 생성물의 파일을 바꿔 넣은 경우는 저장·비교가 알아채지 못한다(우리 코드는 번호 이름을 덮어쓰지 않으므로 손으로 바꿔 넣을 때만 생긴다). 파일을 옮기는 미러는 옮기기 직전에 각인을 다시 읽는다(3-2).
- 원본을 잃은 대상(사실의 `reason`)은 종전대로 '저장 불가'가 먼저다 — 이미 저장된 파일이 있어도 표에는 저장 불가로 보이고, 그 파일은 `protected` 로 지킨다. 번호 이름과 무관한 기존 계약이라 바꾸지 않았다(바꾸면 미러의 정리 비율 계산도 달라진다).
- 확정 직후 `d` 를 적기 전에 프로세스가 죽으면 그 파일은 다른 PC 에서 (각인을 못 읽으면) 충돌로 보인다.
- 저장 각인(`file_stamp`, ffmpeg `-c copy`)이 `-map` 없이 일부 트랙(타임코드 등)을 빼는 것은 이번 변경과 무관한 기존 동작이다.

- **한계**: 다운로드만 한 `work` 는 렌더 폴더에 파일도 `d` 도 없다 — 그 생성물의 `n`·`g` 를 함께 잃으면 그 번호가 다른 생성물에 다시 갈 수 있다(되살릴 증거가 없다).

**저장(공유·최종)** `routers/manage.py`

- 서버가 주는 대상 사실에 `job_id`·`creator_name`(유일한 이름 해석기 `resolve_display_names`)·`project_name` 을 더한다(단독 저장 분기도 같은 필드). 허브는 **그 키가 응답에 있을 때만** v2 로 **새 번호를 받는다** — 옛 서버면 새 배정은 §6 그대로(추측으로 채우지 않는다). 다만 **이미 있는 v2 배정·파일을 알아보는 것은 서버 판과 무관**하다(프로젝트 id 와 생성물 id 만 있으면 장부 v2 를 찾는다 — 서버를 옛 판으로 되돌린 날 v2 저장본을 잊고 §6 이름으로 또 저장하지 않게). v2 배정이 이미 있는 생성물은 옛 서버에서도 그 이름으로 다시 저장한다.
- 이미 저장됐는지: 후보 넷의 '저장됨'을 **모두** 먼저 본다 — ① v2 이름(장부 v2) ② §6 번호 이름(옛 장부) ③ **이 PC 의 대장이 이 생성물을 이 종류의 목적지 폴더에 저장했다고 기억하는 자리(이름 꼴을 따지지 않는다)** ④ 같은 생성물이 예전 번호로 확정해 둔 v2 파일(`r` 로 이어진 번호) ⑤ 옛 이름. 하나라도 저장돼 있으면 새로 배정하지 않는다. ①②③④ 는 모두 `protected` 다 — ③ 을 이름 꼴로 거르면 장부를 잃었거나 이름이 읽히지 않는 지금 대상의 파일이 '새로 저장할 것'이자 '폴더에만 남은 것'이 되어 미러가 치운다.
- v2 파일을 인정하는 증거는 §6 과 같은 셋: 이 PC 대장의 같은 경로 · 장부(`g` + 그 종류의 `d`) · 각인.
- 비교의 `extra` 사전 거르기(`export_names.saved_shape`)·빠른 상태는 v2 이름 꼴도 저장본 이름으로 본다. v2 이름의 종류는 **폴더 마디 바로 뒤의 표식**이다 — 폴더·작업자·프로젝트 이름에 `work`·`fin` 같은 글자가 있어도 읽힌다. 그런 표식이 둘 이상이라 가릴 수 없는 이름만 정리 대상에서 빠진다(모르는 파일로 남는다). v2 로 읽히면 그 종류가 정한다 — 작업자 이름이 `fin` 인 다빈치 파일(`…_davinci_fin_001`)이 §6 꼴로 읽혀 저장본이 되지 않는다. `work`·`davinci` 는 저장본이 아니다.
- **예외(알고 둔다)**: 같은 렌더 폴더·같은 컷 폴더를 함께 쓰는 다른 프로젝트로 옮긴 생성물은, 이 PC 가 옛 프로젝트 이름으로 저장해 둔 파일이 그 자리에 있으면 ③ 으로 '저장됨'이다(새 프로젝트 이름으로 또 저장하지 않는다). 대장이 없는 다른 PC 는 새 이름으로 저장한다. 두 프로젝트가 한 렌더 폴더를 쓰는 구성은 미러의 정리도 막아 둔 예외 구성이다(3-1 의 `cleanup_blocked`).
- 저장 한 번(종류 둘)은 장부 한 벌(`Books`)을 같이 쓴다 — v2 장부는 종류와 무관해 종류마다 다시 읽을 까닭이 없다.

**다빈치** `services/resolve_transfer.py` — 전에 보낸 파일 찾기: §6 장부의 확정된 `davinci` 파일 → v2 의 확정된 `davinci` 파일(지금 번호 → 이어지기 전 번호) → (없으면) 원본을 받아 v2 이름으로 놓는다. 원본 주소가 만료돼도 이미 보낸 파일은 다시 보낼 수 있다는 §6 의 성질을 지킨다.

- 이름의 재료(프로젝트·작업자 이름·`job_id`)는 전송에 실려 오는 **생성물 카드**의 것이다(`project_name`·`creator_name` — 카드에 보이는 그 이름, 같은 해석기). 카드에는 전부터 있던 필드라 **서버를 바꾸지 않아도** 다빈치는 v2 이름으로 간다.
- 번호는 저장본과 **같은 장부·같은 번호**다(같은 렌더 폴더의 `names2/`). 공유 저장이 먼저 001 을 받은 생성물을 다빈치로 보내면 `…_davinci_…_001` 이다.
- §6 이름으로 보낸 파일이 지워졌으면 v2 이름으로 새로 놓는다(§6 장부에는 새 번호를 만들지 않는다).
- 전에 보낸 파일을 그대로 쓸 때도 이 PC 가 새로 알게 된 열쇠(나중에 채워진 `job_id`)를 장부에 잇는다(`_link_keys` — 저장의 '건너뜀'과 같다). 안 이으면 그 열쇠만 아는 PC 가 같은 영상을 새 번호로 한 번 더 놓는다.
- 원본을 복사하는 동안 번호가 이어지면 그 파일은 옛 번호 이름으로 놓인다 — **그 뒤에 다시 보낼 때**는 '이어지기 전 번호의 확정 파일'로 찾아 그대로 쓴다. 확정하려는 이름을 다른 전송이 먼저 확정한 경우에도 다시 읽은 장부로 같은 식으로 찾는다(지금 이름만 견줘 거절하지 않는다). 다만 복사 중에 번호가 이어지고 **다른 PC 가 그 새 번호로 같은 때에 보내면** 사본이 둘이 될 수 있다(저장의 '남는 틈'과 같은 종류 — 덮어쓰기는 없다).

**다운로드** `routers/library.py::download_names`(`POST /api/download/names`) · `frontend/src/lib/download.ts`

- 허브 로컬 라우트가 이름을 정한다(`_proxy._LOCAL_EXACT` — 장부가 이 PC 가 보는 렌더 폴더에 있다). 요청은 **생성물 id 만** 받고, 이름·종류·확장자는 허브가 권한을 확인해 다시 읽은 카드에서 만든다 — 조회·권한은 캔버스 일괄 조회(`get_generations_batch`)와 한 곳이다(존재 은닉·공유 서버 위임 포함). 화면이 보낸 값은 장부에 들어가지 않는다. 볼 수 없거나 없는 생성물, **아직 받을 결과물이 없는 생성물**(생성 중·실패 — 완료됐고 첫 에셋에 원본 자리가 있어야 한다)은 응답에서 빠진다: 생성 중인 카드에 이름을 주면 확장자(`.bin`)가 번호와 함께 굳어 나중의 저장·다빈치까지 그 확장자를 쓴다.
- 종류 = 카드의 지금 상태: 최종(`is_final`) → `fin` · 공유(`shared` — 보류 포함) → `share` · 그 밖 → `work`. 확장자는 원본의 것(`project_folders.export_ext`).
- 실제 다운로드를 누를 때만 부른다(목록·미리보기로는 번호가 생기지 않는다). 한 번에 200건까지(화면이 나눠, 한 묶음씩 차례로 보낸다), 번호 받기는 이 허브에서 한 번에 한 요청씩(`_DOWNLOAD_NAMES_LOCK`) — 앞의 요청이 끝나기를 **3초까지만** 기다리고, 못 잡으면 임시 이름을 준다(NAS 가 멎은 요청 뒤에 줄을 세우면 워커 스레드가 차서 허브의 다른 요청까지 선다).
- 화면은 이름 요청에 제한 시간을 둔다(10초 + 건당 0.3초, 최대 60초) — 허브가 답하지 않아도 옛 이름으로 다운로드를 시작한다. 단건과 일괄이 같은 생성물의 이름을 동시에 물으면 한 답을 같이 쓴다(따로 물어 한쪽만 번호를 못 받으면 같은 파일을 두 이름으로 받게 된다).
- 번호를 받지 못하면(렌더 폴더 미연결·NAS 불통·장부 오류·프로젝트나 폴더가 없음·다른 요청이 번호를 받는 중) 같은 꼴에 번호 자리만 `x<공통 열쇠 해시 8자>` 인 임시 이름을 주고(`numbered=false`) 화면이 알린다 — 다운로드는 막지 않는다. 임시 이름은 장부에 적지 않는다. 이름 요청 자체가 실패하면 화면은 옛 이름(`vid-<id 8자>` 등)으로 받고 같은 안내를 띄운다.
- 화면: 카드의 ⤓·히스토리 보드·크게 보기는 `downloadGeneration`(누르자마자 '다운로드 시작'을 알리고 이름을 받는다 — 이름을 받는 동안의 연타는 하나로 모인다), 선택 막대의 일괄 다운로드는 `nameGenerationItems`(받기 직전에 한 번에). 에셋 파일(생성물이 아닌 것)과 `fetchBlob` 은 이름을 묻지 않는다.
- 이름 받기는 라이브러리를 바꾸지 않는다 — 변경 방송 대상이 아니다(`mutation_notify._NOTIFY_NO_LIBRARY_CHANGE_PATHS`).
- 같이 고친 것: 다운로드 응답의 `Content-Disposition` 에 한글 이름을 그대로 실으면 응답이 500 으로 깨져(latin-1) 화면이 '각인 없이 직접 받기'로 빠졌다 — 새 이름은 프로젝트명이 한글이라 거의 매번 해당한다. RFC 5987 `filename*` 로 싣는다(`library._attachment`). 이름 상한도 120 → 200자(v2 이름은 150자까지 — 짧게 자르면 확장자가 잘린다).

**옛 판과 섞인 동안**: 옛 판 앱은 §6 이름으로 저장한다 — v2 로 이미 저장된 생성물이 §6 이름으로 한 번 더 생길 수 있다(덮어쓰기는 없다).

**배포 순서**: 다운로드·다빈치 보내기는 앱(허브)만 새 판이면 v2 이름이다(이름 재료가 카드에 이미 있다). **공유 저장·최종 저장은 공유 서버도 새 판이어야** v2 이름이다 — 서버가 옛 판인 동안 새로 저장하는 것은 §6 이름으로 가고(이미 v2 로 받은 번호가 있는 생성물은 그 이름), 서버를 올린 뒤부터 v2 다. 서버를 먼저 올려도, 앱을 먼저 올려도 깨지는 것은 없다.
