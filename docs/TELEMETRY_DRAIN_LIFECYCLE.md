# 텔레메트리 전송 수명주기

작성일: 2026-08-16  
대상 위험: `RL-10` — 내부 계약 완료 (`dfaa2672`)

## 1. 목적

생성물 메타데이터를 관리 대시보드로 보내는 동안 공유 서버가 느리거나 꺼져 있어도 다음 동작을
막지 않는 것이 목적이다.

- 로컬 생성 적재(`/api/ingest`, `/api/ingest/mcp`) 응답
- 다른 텔레메트리 변경 예약
- SQLite 유지보수 게이트와 다른 짧은 로컬 DB 작업
- 앱 종료와 재시작

## 2. 확인된 실제 원인

초기 감사 문서에는 “DB 락 안에서 60초 네트워크 대기”라고 요약돼 있었다. 코드를 다시 추적한
결과, outbox 조회와 전송 결과 반영은 각각 별도 SQLite 연결을 사용하며 원격 HTTP 호출 전에
연결을 닫고 있었다.

실제 문제는 다음 두 가지였다.

1. 프로세스 전체의 `_drain_lock`을 원격 HTTP 왕복 동안 계속 보유했다.
2. 동기 FastAPI ingest 라우터가 `drain_telemetry()`를 직접 호출해 공유 서버 응답을 기다렸다.

따라서 해결 기준은 “DB 코드를 옮기는 것”이 아니라 **로컬 응답, 전송 소유권 조정, 원격 네트워크,
짧은 DB 정산을 분리하는 것**이다.

## 3. 현재 상태 흐름

```text
ingest 트랜잭션
  └─ generation 저장 + telemetry_outbox dirty 표시
       └─ schedule_telemetry_drain()만 호출하고 로컬 응답 반환
            └─ 메인 이벤트 루프에서 50ms 묶음 예약
                 └─ drain 소유자 1개 선점
                      ├─ 짧은 DB 조회 후 연결 반환
                      ├─ 상태 락 없이 공유 서버 HTTP 전송
                      ├─ 짧은 DB 성공/실패 정산
                      └─ 전송 중 새 요청이 있었으면 outbox 재조회
```

동기 FastAPI 라우터는 anyio 작업 스레드에서 실행될 수 있다. 앱 시작 때 메인 이벤트 루프를
등록해 두고, 동기 라우터는 `call_soon_threadsafe`로 예약 신호만 전달한다. 등록된 루프가 없거나
종료 중이면 예약은 실패해도 outbox의 dirty 행은 지우지 않으므로 다음 시작·동기화 때 다시 보낼 수
있다.

## 4. 동시 실행 규칙

| 상황 | 처리 |
|---|---|
| 전송이 없는 상태에서 첫 요청 | 해당 호출이 전송 소유자가 된다. |
| 이미 전송 중인 상태에서 새 요청 | 기다리지 않고 `후속 전송 필요` 표시만 남긴다. |
| 느린 공유 서버 응답 대기 중 | 전송 상태 락을 놓고 있으므로 다른 호출은 즉시 반환한다. |
| 전송 성공 중 같은 행이 다시 변경됨 | 스냅샷의 정수 `dirty_rev`와 현재 행을 비교해 옛 성공·실패가 새 변경을 덮지 않게 한다. |
| 전송 실패 | outbox 행을 남기고 기존 제곱 백오프 규칙으로 재시도한다. |
| 전송 코드에서 예외·취소 발생 | 소유권 상태를 반드시 해제해 다음 전송이 다시 선점할 수 있게 한다. |

`_drain_state`는 소유자와 후속 요청 여부를 바꾸는 짧은 구간에서만 사용한다. DB 조회, HTTP 요청,
DB 정산 중에는 이 상태 락을 보유하지 않는다.

## 5. 종료 규칙

앱 종료 시 다음 순서로 처리한다.

1. 동기 작업 스레드가 방금 게시한 예약 콜백을 이벤트 루프 task로 승격한다.
2. 이미 예약된 task가 끝날 때까지 최대 10초 기다린다.
3. 직접 실행 중인 drain 소유자가 있으면 남은 시간만 기다린다.
4. 제한시간이 지나면 종료를 무기한 막지 않고 dirty outbox를 다음 시작의 안전망으로 남긴다.
5. 종료한 이벤트 루프를 다시 사용하지 않도록 루프 연결을 해제한다.

## 6. 이 변경이 보장하는 것과 보장하지 않는 것

보장하는 것:

- 공유 서버 텔레메트리 HTTP 응답 때문에 일반 ingest 응답이 직접 기다리지 않는다.
- 느린 전송 중 다른 drain 요청은 락을 기다리지 않는다.
- 전송 중에도 별도의 SQLite 유지보수 게이트와 로컬 DB 쓰기를 수행할 수 있다.
- 실패·취소 뒤 소유권이 풀려 다음 재시도가 가능하다.
- 빠르게 몰린 예약은 하나의 백그라운드 task로 합쳐진다.
- 같은 생성물이 같은 밀리초 안에 다시 바뀌어도 `dirty_rev`가 증가하므로 옛 전송 결과와 구분한다.
- 기존 DB에는 `dirty_rev=1`을 무중단 추가하고, 아직 보내지 않은 outbox 행을 그대로 보존한다.

아직 보장하지 않는 것:

- `account_status`와 `account_transactions`의 공유 서버 보고는 별도 경로이며 아직 동기 프록시와
  독립 재시도 큐 문제가 남아 있다. 이는 `RL-13` 범위다.
- 실제 운영 공유 서버의 장시간 지연·재시작·혼합 버전 왕복은 Gate 6 외부 실측이 필요하다.

## 7. 검증 기준

```powershell
cd backend
py -3 -m pytest `
  tests\test_telemetry_delivery.py `
  tests\test_manage_telemetry.py `
  tests\test_ingest_core.py `
  tests\test_syncer_telemetry.py `
  tests\test_touch_telemetry.py -q
```

`dfaa2672` 기준 대상 37개를 5회 연속 통과했다. 다음 상황을 포함한다.

- 동기 작업자 100개가 메인 이벤트 루프의 drain 하나로 합쳐짐
- 느린 전송 중 두 번째 drain 호출이 0.2초 안에 반환
- 전송 중 유지보수 게이트 획득과 새 dirty 쓰기 가능
- 같은 `dirty_at` 안에서도 `dirty_rev`로 늦은 성공·실패와 새 변경을 구분
- 구버전 outbox 스키마에 revision을 추가해도 대기 행 보존
- 전송 실패 뒤 다음 호출 재시도
- 종료 시 예약·직접 실행 drain 대기

같은 작업 트리에서 백엔드 전체 766개, 프론트 75개 파일·527개, 업데이트 관련 40개,
프론트 아키텍처 검사와 프로덕션 빌드가 통과했다. 격리 `test_dev`에서는 로그인 유지 상태로
작업 공간→공유 & 리뷰→캔버스 전환, 앱 콘솔 오류 0건, 종료 뒤 5173·8012 포트 반환을 확인했다.
기존 프론트 빌드만 있는 환경의 서버 부팅 smoke도 통과했다. 이 수치는 실제 공유 서버 장애 실측을
대신하지 않는다.
