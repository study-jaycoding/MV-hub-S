# 텔레메트리 전송 수명주기

작성일: 2026-08-16  
대상 위험: `RL-10` 전송 수명주기 완료 (`dfaa2672`), `RL-12` 성공 관측 완료 (`46c6198b`),
`RL-13` 계정 상태·거래 보고 복구 완료 (`9216ee96`)

## 1. 목적

생성물 메타데이터를 관리 대시보드로 보내는 동안 공유 서버가 느리거나 꺼져 있어도 다음 동작을
막지 않는 것이 목적이다.

- 로컬 생성 적재(`/api/ingest`, `/api/ingest/mcp`) 응답
- 다른 텔레메트리 변경 예약
- SQLite 유지보수 게이트와 다른 짧은 로컬 DB 작업
- 앱 종료와 재시작

## 2. 확인된 실제 원인

초기 감사 문서에는 “DB 락 안에서 60초 네트워크 대기”라고 요약돼 있었다. 코드를 다시 추적한
결과, outbox 조회와 전송 결과 반영은 각각 별도 SQLite 연결을 사용하며 원격 HTTP 호출 전에
연결을 닫고 있었다.

실제 문제는 다음 두 가지였다.

1. 프로세스 전체의 `_drain_lock`을 원격 HTTP 왕복 동안 계속 보유했다.
2. 동기 FastAPI ingest 라우터가 `drain_telemetry()`를 직접 호출해 공유 서버 응답을 기다렸다.

따라서 해결 기준은 “DB 코드를 옮기는 것”이 아니라 **로컬 응답, 전송 소유권 조정, 원격 네트워크,
짧은 DB 정산을 분리하는 것**이다.

## 3. 현재 상태 흐름

```text
ingest 트랜잭션
  ├─ generation 저장 + telemetry_outbox dirty 표시
  └─ 계정 상태·거래가 있으면 account_report_outbox에 먼저 기록
       └─ schedule_telemetry_drain()만 호출하고 로컬 응답 반환
            └─ 메인 이벤트 루프에서 50ms 묶음 예약
                 └─ drain 소유자 1개 선점
                      ├─ 생성 텔레메트리와 계정 보고를 각각 짧게 조회
                      ├─ 상태 락 없이 각 공유 서버 HTTP 전송
                      ├─ 각 채널을 독립적으로 성공/실패 정산
                      │    ├─ 생성 CAS 성공이면 telemetry_delivery_state 갱신
                      │    └─ 계정 보고 CAS 성공이면 account_report_delivery_state 갱신
                      └─ 전송 중 새 요청이 있었으면 outbox 재조회
```

동기 FastAPI 라우터는 anyio 작업 스레드에서 실행될 수 있다. 앱 시작 때 메인 이벤트 루프를
등록해 두고, 동기 라우터는 `call_soon_threadsafe`로 예약 신호만 전달한다. 등록된 루프가 없거나
종료 중이면 예약은 실패해도 outbox의 dirty 행은 지우지 않으므로 다음 시작·동기화 때 다시 보낼 수
있다.

## 4. 동시 실행 규칙

| 상황 | 처리 |
|---|---|
| 전송이 없는 상태에서 첫 요청 | 해당 호출이 전송 소유자가 된다. |
| 이미 전송 중인 상태에서 새 요청 | 기다리지 않고 `후속 전송 필요` 표시만 남긴다. |
| 느린 공유 서버 응답 대기 중 | 전송 상태 락을 놓고 있으므로 다른 호출은 즉시 반환한다. |
| 전송 성공 중 같은 행이 다시 변경됨 | 스냅샷의 정수 `dirty_rev`와 현재 행을 비교해 옛 성공·실패가 새 변경을 덮지 않게 한다. |
| 전송 실패 | outbox 행을 남기고 기존 제곱 백오프 규칙으로 재시도한다. |
| 전송 코드에서 예외·취소 발생 | 소유권 상태를 반드시 해제해 다음 전송이 다시 선점할 수 있게 한다. |

`_drain_state`는 소유자와 후속 요청 여부를 바꾸는 짧은 구간에서만 사용한다. DB 조회, HTTP 요청,
DB 정산 중에는 이 상태 락을 보유하지 않는다.

## 5. 마지막 성공 관측 규칙(RL-12)

`telemetry_outbox.pushed_at`은 같은 생성물이 다시 dirty 되면 `NULL`로 돌아간다. 따라서 이 열의
최댓값만 읽으면 과거에 정상 전송된 적이 있어도 성공 기록이 사라진다. 현재 구현은 계정 DB마다
`telemetry_delivery_state(id=1)` 한 행을 두고 `last_success_at`을 UTC ISO 시각으로 보존한다.

| 상황 | 마지막 성공 시각 |
|---|---|
| 공유 서버 또는 격리 manage DB에 실제 반영되고 현재 `dirty_rev` CAS도 성공 | 갱신 |
| 같은 생성물이 다시 변경되어 outbox가 dirty로 복귀 | 이전 성공 시각 유지 |
| 전송 중 다시 변경된 뒤 도착한 오래된 ACK | 갱신하지 않음 |
| 외국 계정 항목·원본 없는 항목을 전송 없이 큐에서 정리 | 갱신하지 않음 |
| 전송 실패·서버 skipped | 갱신하지 않음 |

기존 DB는 최초 스키마 보장 때 과거 `MAX(pushed_at)`을 한 번 옮긴다. 관측 API
`GET /api/sync-status` 자체는 새 테이블을 만들지 않는 읽기 전용이며, 구버전 DB에서 상태 테이블이
아직 없을 때만 기존 `pushed_at`을 호환값으로 읽는다. 로컬 계정 메뉴는 마지막 성공과 현재 대기
건수를 함께 표시하고, 공유 서버 화면에서는 로컬 outbox를 불필요하게 폴링하지 않는다.

## 6. 계정 상태·거래 보고 재시도 규칙(RL-13)

계정 상태와 거래는 생성물 집계와 데이터 모양·완료 조건이 다르므로 같은 outbox 행에 섞지 않는다.
로컬 DB에는 `account_report_outbox`와 `account_report_delivery_state`를 두고 다음 규칙을 적용한다.

| 데이터 | 큐 식별 방식 | 의미 |
|---|---|---|
| 계정 상태 | 계정별 최신 상태 한 행 | 크레딧·플랜은 최신 스냅샷만 필요하다. |
| 거래 | 생성 시각·크레딧·동작·표시 이름의 안정 키 | 같은 거래를 재보고해도 한 건이고, 나중에 확인된 모델은 같은 행에 보강한다. |

- 로컬 `/api/ingest`는 계정 보고를 원격 서버에 동기 전달하지 않고 큐 기록 뒤 응답한다.
- 같은 내용이 반복돼도 실패 횟수와 다음 재시도 시각을 초기화하지 않는다.
- 실제 내용이 바뀌거나 모델 정보가 보강되면 `dirty_rev`가 증가한다.
- 거래 재시도에는 최신 계정 상태도 함께 보내 서버가 이메일·계정 경계를 검증할 수 있게 한다.
- 이메일이나 creator UID를 확인할 수 없으면 다른 계정으로 추측하지 않고 실패 처리한다.
- 공유 서버 `POST /api/ingest/account-report`는 계정 상태와 거래 쓰기가 모두 성공한 뒤에만
  명시적 ACK를 반환한다.
- 로컬은 명시적 ACK와 현재 `dirty_rev`가 모두 맞을 때만 완료한다. 구버전 서버의 404, 잘못된
  응답, 네트워크 단절은 성공으로 간주하지 않고 큐에 남긴다.
- 예외 — **dead-letter**: 큐 payload 파싱 실패는 즉시, 같은 revision 에서 **409 가 3회 연속**이면
  `dead_lettered_at` 을 찍어 자동 재시도 대상에서 제외한다(`services/account_report_delivery.py`,
  `repo/manage_account_reports.py`). 행은 삭제되지 않고 상태 API 의 `account_report_dead` 개수로 보인다.
  같은 키가 새 내용으로 다시 큐잉되면 `dead_lettered_at` 이 지워져 되살아난다.
- 생성 텔레메트리와 계정 보고의 실패·마지막 성공은 서로 독립적으로 보존한다.

## 7. 종료 규칙

앱 종료 시 다음 순서로 처리한다.

1. 동기 작업 스레드가 방금 게시한 예약 콜백을 이벤트 루프 task로 승격한다.
2. 이미 예약된 task가 끝날 때까지 최대 10초 기다린다.
3. 직접 실행 중인 drain 소유자가 있으면 남은 시간만 기다린다.
4. 제한시간이 지나면 종료를 무기한 막지 않고 dirty outbox를 다음 시작의 안전망으로 남긴다.
5. 종료한 이벤트 루프를 다시 사용하지 않도록 루프 연결을 해제한다.

## 8. 이 변경이 보장하는 것과 보장하지 않는 것

보장하는 것:

- 공유 서버 텔레메트리 HTTP 응답 때문에 일반 ingest 응답이 직접 기다리지 않는다.
- 느린 전송 중 다른 drain 요청은 락을 기다리지 않는다.
- 전송 중에도 별도의 SQLite 유지보수 게이트와 로컬 DB 쓰기를 수행할 수 있다.
- 실패·취소 뒤 소유권이 풀려 다음 재시도가 가능하다.
- 빠르게 몰린 예약은 하나의 백그라운드 task로 합쳐진다.
- 같은 생성물이 같은 밀리초 안에 다시 바뀌어도 `dirty_rev`가 증가하므로 옛 전송 결과와 구분한다.
- 기존 DB에는 `dirty_rev=1`을 무중단 추가하고, 아직 보내지 않은 outbox 행을 그대로 보존한다.
- 같은 항목이 다시 dirty 되어도 마지막 실제 반영 성공 시각은 사라지지 않는다.
- 전송하지 않은 큐 정리와 늦은 ACK를 정상 전송으로 오인하지 않는다.
- 계정 상태·거래가 일시적인 서버 장애나 구버전 서버 때문에 조용히 사라지지 않는다(행 보존). 단 계정 경계
  409 가 3회면 dead-letter 로 자동 재시도는 멈춘다(§6).
- 같은 거래 재전송은 중복 행을 만들지 않고, 뒤늦게 확인된 모델 정보는 보강할 수 있다.
- 계정 보고 실패가 생성 텔레메트리 성공 시각을 덮거나 그 반대가 되지 않는다.

아직 보장하지 않는 것:

- 실제 운영 공유 서버의 장시간 지연·재시작·혼합 버전 왕복은 Gate 6 외부 실측이 필요하다.
- 성공한 거래 식별 행의 장기 보관·압축 정책은 아직 별도 운영 기준이 없다.

`dfaa2672` 기준 대상 37개를 5회 연속 통과했다. 다음 상황을 포함한다.

- 동기 작업자 100개가 메인 이벤트 루프의 drain 하나로 합쳐짐
- 느린 전송 중 두 번째 drain 호출이 0.2초 안에 반환
- 전송 중 유지보수 게이트 획득과 새 dirty 쓰기 가능
- 같은 `dirty_at` 안에서도 `dirty_rev`로 늦은 성공·실패와 새 변경을 구분
- 구버전 outbox 스키마에 revision을 추가해도 대기 행 보존
- 전송 실패 뒤 다음 호출 재시도
- 종료 시 예약·직접 실행 drain 대기

같은 작업 트리에서 백엔드 전체 766개, 프론트 75개 파일·527개, 업데이트 관련 40개,
프론트 아키텍처 검사와 프로덕션 빌드가 통과했다. 격리 `test_dev`에서는 로그인 유지 상태로
작업 공간→공유 & 리뷰→캔버스 전환, 앱 콘솔 오류 0건, 종료 뒤 5173·8012 포트 반환을 확인했다.
기존 프론트 빌드만 있는 환경의 서버 부팅 smoke도 통과했다. 이 수치는 실제 공유 서버 장애 실측을
대신하지 않는다.

`46c6198b`의 RL-12 검증은 백엔드 대상 38개와 프론트 시각 포맷 3개, 백엔드 전체 780개,
프론트 76개 파일·530개, 업데이트 40개, 아키텍처 검사와 프로덕션 빌드를 통과했다. 기존 DB 성공
시각 이관, 재dirty 뒤 기록 보존, 늦은 ACK, 전송 없는 큐 정리까지 포함한다. 격리 데이터로 띄운
로컬 Vite 화면에서는 계정 메뉴의 `마지막 성공 / 대기 없음`, 앱 콘솔 오류 0건, 종료 뒤
5173·8012 포트 반환과 기존 8010 프로세스 보존을 확인했다.

`9216ee96`의 RL-13 검증은 계정 보고 대상 백엔드 19개, 백엔드 전체 790개, 프론트
76개 파일·533개, 업데이트 40개, 아키텍처 검사와 프로덕션 빌드를 통과했다. 계정 최신 상태
단일화, 거래 안정 키 중복 방지, 모델 보강, 동일 보고의 백오프 유지, 늦은 ACK의 revision 차단,
서버 양쪽 쓰기 뒤 명시적 ACK를 포함한다.

격리 Vite 5173 → 로컬 AUTH-off 허브 8012 → 임시 AUTH-on 공유 서버 8201의 실제 HTTP·브라우저
경로에서는 실패 2건 표시, 계정 경계의 fail-closed 409, 정상 신원으로 재시도한 `pushed: 2`,
대기·실패 0건과 계정 보고 마지막 성공 시각을 확인했다. 앱 출처 콘솔 오류는 0건이었고 종료 뒤
세 포트가 모두 반환됐다. 임시 DB와 테스트 계정만 사용했으므로 실제 운영 공유 서버·실제 크레딧
왕복을 대신하지 않는다.
