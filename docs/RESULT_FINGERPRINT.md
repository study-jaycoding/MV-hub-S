# 결과 파일 부분 지문

작성일: 2026-10-03 · 설계: Claude · 검토: Codex(설계 4회 → 승인, 코드 리뷰 반영) · 결정: Jay("가볍게", 기존 장부에 칸 추가)

## 1. 목적

NAS 에 저장된 결과 파일은 이름이 바뀌면 생성물과 이어지지 않는다. 파일 **내용**으로 다시 잇기 위한 **재료**를
팀 장부(`manage_hub.db` `team_generation_fact`)에 모은다. 실제로 NAS 를 훑어 잇는 일과 화면은 이 문서의 범위 밖이다.

## 2. 근거(2026-10-03 실측)

- NAS 파일과 힉스필드 CDN 원본은 바이트까지 같았다(3/3).
- CDN 에 `Range: bytes=0-65535` 요청 하나면 `206` + `Content-Range: bytes 0-65535/<전체 크기>` 로
  **전체 크기와 앞 64KiB** 를 함께 받는다. 앞 64KiB sha256 이 NAS 파일 앞 64KiB 와 같았다(3/3).
- 생성물당 결과 파일은 1개였다(Jay PC 853/853, 서버 950/950).
- 장부 팩트는 설계상 "프롬프트·미디어 제외"다. 그래서 **URL 은 장부에 넣지 않는다.**

## 3. 계약

- 값은 한 쌍이다: `result_bytes`(원본 전체 크기) + `result_head_sha`(앞 64KiB — 더 작으면 전체 — 의 sha256,
  소문자 64자리 hex). 이름은 **부분 지문**이다. 같은 파일이라고 확정하지 않는다.
- 서버 장부의 값은 **서버가 마지막으로 받은 유효한 쌍**이다. 관측 순서와 원본임은 보장하지 않는다.
  MCP 이미지가 원본 대신 축소본을 결과로 넣는 경로가 있다(`services/mcp_ingest.py`).
- 이 값을 쓰는 쪽의 표시 규칙:

  | 상황 | 표시 |
  |---|---|
  | 쌍이 같고, **현재 장부 안에서** 그 쌍을 가진 job 이 하나뿐 | "지문 일치(부분)" |
  | 쌍이 같은 job 이 여럿 | "후보 N" — 임의로 하나 고르지 않는다 |
  | 크기만 같음 | "크기 후보" |

  어느 것도 작업자·모델의 확정 귀속이 아니라 **관측된 일치**다. **데이터를 고치거나 지우는 근거로 쓰지 않는다.**
- 결과가 2개 이상인 생성물은 수집하지 않는다. 결과가 여러 개로 바뀌었을 때 옛 값을 무효화하는 경로는 없다.

## 4. 작업자 PC(로컬 허브)

### 4.1 저장 — `asset` 칸

| 칸 | 뜻 |
|---|---|
| `result_bytes`, `result_head_sha` | 부분 지문 쌍 |
| `result_probe_fail` | 연속 실패 수. 3이면 다시 시도하지 않는다 |
| `result_fp_sent_to` | 이 쌍을 받았다고 확인해 준 공유 서버 주소(origin) |

동기화가 asset 을 지우고 다시 넣을 때(`repo/generation_sync.py`), 포스터 승계와 같은 '같은 결과물' 판정
(타입 동일 + 원본 키 `source_url or file_path` 동일 + 행 1개)이면 네 칸을 새 행에 승계한다. 원본이 다르면 새 행은
비어 있다(다시 수집·다시 전송).

### 4.2 수집기 — `services/result_probe.py`

- **도는 곳:** 워커 허브 + MANAGE 켜짐 + 읽기 전용이 아님(`main.py` 가 시작). 로그인·uid 는 회차마다 확인한다.
  서버가 이 기능을 아는지와 상관없이 수집한다(로컬에 모으는 것은 해가 없다).
- **주기:** 시작 2분 뒤부터 5분마다 최대 20건, 순차.
- **대상:** 지문 없음 + 실패 3 미만 + 내 생성물 + `done` + 미삭제 + 결과 정확히 1개. 최신부터.
- **읽기:** 캐시된 완성 파일(`/media/…`)이 있으면 그 파일. 없으면 원본 URL 에
  `Range: bytes=0-65535`, `Accept-Encoding: identity` 로 요청한다. 사설망·리다이렉트 우회 방어는 media_cache 와 같다.
  - `206`: `Content-Range` 가 `bytes 0-E/T` 이고 T>0, E=min(65536,T)-1, 받은 길이가 E+1 이어야 한다.
  - `200`: Content-Length 가 양의 정수이고 앞 min(65536, L) 바이트를 정확히 받아야 한다.
  - `Content-Encoding` 이 없거나 identity 여야 하고, text/*·HTML 머리면 실패다.
  - 연결·읽기 한 번 15초, 한 건 30초 상한이다. 읽기는 `read1`(호출당 recv 한 번)이라 조금씩 흘러드는 응답도
    '상한 + recv 한 번'을 넘지 않는다.
- **기록:** 네트워크는 트랜잭션 밖이다. 기록 트랜잭션에서 done·미삭제·uid·결과 1개·원본 키 동일·아직 비어 있음을
  다시 확인한다. 하나라도 어긋나면 지문도 dirty 도 남기지 않는다. 맞으면 쌍을 적고 텔레메트리 dirty 를 찍는다.
  실패면 같은 조건에서 실패 수를 올린다.
- **계정:** 회차 시작 때 계정 키·uid 를 잡고, DB 작업마다 그 범위로 고정한다. 네트워크 단계는 취소할 수 있고,
  DB 기록은 `to_thread_non_abandon` 으로 끝까지 마친다.
- 1건 이상 기록했거나 재전송을 걸었으면 텔레메트리 드레인을 예약한다(dirty 만으로는 전송이 예약되지 않는다).
- **하루 한 번 재전송:** 쌍은 있는데 `result_fp_sent_to` 가 지금 서버 주소가 아닌(NULL 포함) 내 생성물 최대
  200건을 dirty 로 표시한다. '하루'는 프로세스 기준이라 앱을 다시 켜면 첫 회차에 한 번 더 돈다.
- **한계:** 일부는 포기할 수 있다(실패 3번). 모든 결과가 자동으로 채워진다고 보장하지 않는다.

### 4.3 전송과 전달 확인

- `build_telemetry_facts` 는 결과가 정확히 1개이고 쌍이 완전할 때만 쌍을 싣는다. 확인용 `_fp_asset_id` 도 같은
  조회에서 잡지만, 드레이너가 `_` 로 시작하는 키를 떼고 보낸다.
- 삭제 스냅샷(`repo/trash.py`)에도 같은 규칙으로 쌍을 싣는다.
- 드레이너(`services/telemetry_drain.py`, `routers/_telemetry.py`)는 서버 주소를 한 번 잡아 **그 주소로 보내고**
  (`_proxy.proxy_json(..., base=origin)`), 응답 때 이렇게 정산한다.
  - 지금 설정 주소가 보낸 주소와 다르면 → 정산하지 않는다.
  - 응답에 `result_fingerprint: 1` 이 있으면 → 전송에 성공한 항목만, asset id·쌍이 보낼 때와 같을 때 `result_fp_sent_to=origin`.
  - 표식이 없으면(옛 서버 — 지문 칸을 버렸을 수 있다) → 같은 조건으로 `result_fp_sent_to=NULL`.

## 5. 서버(팀 장부)

- `team_generation_fact` 에 `result_bytes INTEGER`, `result_head_sha TEXT` 칸이 있다(`manage_db._migrate_schema`).
- 검증은 `manage_db.fingerprint_pair` 한 곳에서 한다. 크기는 1 이상 2^63−1 이하 정수, 지문은 64자리 소문자 hex
  (`fullmatch`), 둘 다 있어야 한다. 어긋나면 둘 다 버린다. 입력 모델(`TelemetryFactIn`)은 두 필드를 느슨하게 받아,
  잘못된 값 하나로 배치 전체가 422 가 되지 않게 한다.
- 갱신: 완전한 쌍이 오면 쌍을 함께 바꾸고, 아니면 기존 쌍을 둔다. 한쪽만 바뀌는 경로는 없다.
- job 중복 정리(같은 계정·job·다른 local id 행 삭제): 들어온 쌍이 완전하면 그 쌍을 쓴다. 비었으면 기존·지워질 행의
  완전한 쌍이 한 종류뿐일 때만 승계한다. 둘 이상이면 고르지 않고 비운다(같은 local id 행의 쌍도 비운다).
- tombstone: 기존 행이 있으면 쌍을 보존하고, 새로 보충하지 않는다. 기존 행이 없어 새로 넣을 때는 스냅샷의 쌍을 쓴다.
- push 응답에 `result_fingerprint: 1` 을 넣는다. 새 칸은 API 로 내보내지 않는다(쓰는 기능이 생길 때 정한다).

## 6. 배포

배포 순서는 상관없다. 옛 서버면 확인이 남지 않아 하루 한 번 다시 보낸다. 그래도 **서버 먼저**를 권한다.
