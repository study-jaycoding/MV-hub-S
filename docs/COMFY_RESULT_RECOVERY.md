## 목적과 사용자 동작

원격에서 이미 접수·완료했을 수 있는 작업을 일반 실패로만 표시해 다시 생성하는 위험과,
완료 후 다운로드 오류 때문에 결과 근거가 사라지는 문제를 분리한다.

설정의 **Comfy 미회수 실행** 목록은 카드 삭제·씬 변경과 별개로 유지한다.

- 목록 조회: 로컬 기록만 읽는다. 원격 상태를 자동 조회하지 않는다.
- 결과 회수: 이미 알려진 같은 원격 작업의 상태·상세·파일만 받는다. 새 생성 요청은 없다.
- 내 작업에 저장: 받은 로컬 파일을 기존 라이브러리 저장 경로로 연결한다. 원격 호출은 없다.
- 기록 정리: 사용자가 원격 상태 확인 체크 후 선택한 기록만 없앤다. 원격 작업을 취소하지 않는다.
- 접수 여부 불명: 같은 계정의 제공자 화면에서 직접 확인한다. 자동 재제출·추측한 ID로 조회하지 않는다.

“새 생성 요청 없음”은 제공자가 조회·전송을 절대로 과금하지 않는다는 보장이 아니다.

## 기록과 소유권

SQL 테이블·열을 추가하지 않고 기존 `app_setting`의 `comfy_run_journal`에
`{v:1, legacy_imported, runs:[]}` 봉투를 저장한다. 원문 비밀키·프롬프트·워크플로는 저장하지 않는다.
각 실행은 로컬 job ID, owner, 기기, 연결 지문, 원격 prompt ID, phase와 전체 출력 목록을 갖는다.

- AUTH on: 논리 owner는 요청 계정의 정규화 email이다. 물리 DB pin과 혼동하지 않는다.
- AUTH off: 접수 때 고정한 계정 DB의 email 또는 단독 로컬을 owner로 쓴다.
- 신원·설정은 같은 DB pin 아래에서 캡처하고 worker 전체에도 그 pin을 전달한다.
- UID는 진단·생성자 귀속용이다. UID가 나중에 발견됐다는 이유로 같은 소유자의 회수를 막지 않는다.
- 기기 식별자는 DB 밖의 기존 기기 식별 파일에서 잠금 보호된 공용 진입점으로 캡처한다.

| 동작 | 필요한 경계 |
|---|---|
| 목록·used | 같은 owner만, 타인의 개수/내용 비노출 |
| job ID 상태·회수·정리 | 다른 owner는404, 존재 여부 비노출 |
| 결과 회수 | 같은 owner·기기·연결 지문, 알려진 prompt ID와 충분한 근거 |
| 로컬 재저장 | 새 출력 경로의 owner+기기 scope 일치. 연결 설정 변경은 허용 |
| 기록 정리 | 같은 owner의 진행 중이 아닌 기록. 다른 기기·legacy도 가능 |

DB 전체 미해결 실행은 **200개**까지다. 초과 시 새 submit을409로 거부하며 기존 기록을 축출하지 않는다.
목록/used는 owner별이므로 자신의 목록이 적더라도 다른 계정 사용으로 접수가 막힐 수 있다.
포화 신호 외 타인의 내용은 반환하지 않는다. 출력 개수·직렬화 바이트를 임의로 잘라내지 않는다.
봉투가 손상되었거나 형식을 알 수 없으면 빈 기록으로 덮어쓰지 않는다. 이 안전 거부는 새 실행뿐
아니라 목록·정리·저장 등 같은 원장을 확인하는 경로에도 영향을 준다. 자동 수리/초기화는 하지 않는다.

## 접수와 상태 전이

제출 직전 원장 쓰기와 cap 판정이 성공해야 provider submit을 호출한다.
동일 DB의 read/check/write는 한 backend 프로세스 내 공통 lock으로 직렬화한다.
준비·회수 진입도 먼저 활동으로 등록하고 업데이트 상태를 재검사해 경합 시 거부·정리한다.

| 관측/phase | 처리 |
|---|---|
| submitting | 제출 직전 근거. 재시작하면unknown |
| 유효한 prompt ID | running, 동일 작업 추적 |
| 제출 응답3xx·비2xx·깨진2xx·전송 후 단절 | unknown, 자동 재제출/취소0 |
| 전송 전임이 분명한 URL 스킴·DNS·연결거절·인증서 검증 실패 | not_submitted, 잃을 결과가 없는 기록 정리 가능 |
| 원격 성공 관측 | 메모리에 먼저 기록, 결과 상세/파일 회수 실패는result_pending |
| collecting | 명시 결과 회수 중. collect job ID·단조 순번·phase로 쓰기 권한 대조 |
| collected | 전체 미디어 다운로드 완료, 라이브러리 저장 확인 대기 |
| orphaned | 재시작/추적 단절. 취소 성공을 뜻하지 않음 |

submit만 자동 redirect를 따라가지 않는다. DNS 등의 “전송 전” 판정은 HTTPError가 아닌
URLError 내부의 명확한 원인에 한정한다. 일반 SSL 오류·reset·timeout을 미접수로 단정하지 않는다.
확정된 원격 terminal 뒤에는 실패 처리에서 원격 취소를 다시 보내지 않는다.
제출 뒤 원장 쓰기 실패는 메모리 진행을 유지하는 best-effort이며 크래시 내구성까지 보장하지 않는다.

## 결과·파일·저장 확인

상세 조회·다운로드의 일시 오류는 최초1회와 추가3회, 대기2/4/8초로 제한한다.
408/429/5xx·일시 연결/시간 초과가 대상이며 인증·영구 오류는 즉시 멈춘다.
404/410 결과 없음은 받은 파일과 미회수 근거를 보존한다. 회수 경로는 submit을 호출하지 않는다.

출력 주소는 `comfy/<owner+device scope16>-<원래 job32>-<출력 digest16>.<ext>`다.
다운로드 전 **전체 출력 목록**을 원장에 반영하며 파일은 고유 `.part`에 받은 뒤 원자 교체한다.
이미 계획된 정확한 경로에 비어 있지 않은 파일이 있으면 교체 후 기록 사이의 장애를 복구할 수 있다.
디렉터리 전체를 훑어 결과를 추측하지 않는다.

저장 배치 전체의 출력 주소를 먼저 검사한다. 정상 새 주소는 scope 불일치403이다.
원문 segment는 `[0-9A-Za-z_-][0-9A-Za-z._-]*`에 맞고 끝이 점이 아니어야 한다.
인코딩·역슬래시·콜론·query/fragment·공백·물결표·빈/`.`/`..` segment와 새 형식의 대소문자
별칭은400이다. 경로를 정규화해 임의로 다시 쓰거나 여기서 파일 존재 여부를 검사하지 않는다.

**호환성 변경:** 공식 UUID legacy·정상 샤딩 주소는 유지하지만 비정규 legacy의 새 저장도400이다.
이미 저장된 파일·행·미디어 GET·입력 계보를 변경하거나 마이그레이션하지 않는다.

기존 같은 파일 경로의 라이브러리 저장 멱등성을 사용한다. 배치 중간에 실패하면 성공한 출력만
`finally`에서 ACK하고 원래 저장 예외를 보존한다. 전체 출력 ACK가 끝나야 원장 기록을 제거한다.
옛 collect의 늦은 완료/ACK는 현재 collect job ID·순번·phase가 달라졌으면 버린다.
접수에서도 같은 토큰을 실행 snapshot보다 먼저 읽고, 원장 edit 잠금 안에서 다시 대조한다.
동시에 시작된 회수·정리가 새 claim이나 완료 phase를 덮거나 삭제하려 하면 기존409로 거부한다.
배치 정리는 입력 순서로 검사하고 하나라도 실패하면 어느 행도 삭제하지 않는다. 새 잠금 중첩이나 시간 정책은 없다.
텍스트만 있는 확정 완료, 확정 실패, 확실한 미접수처럼 잃을 미디어가 없는 종결도 정리 가능하다.
설정의 재저장은 출력 파일 목록만 보낸다. 원래 카드의 프롬프트·파라미터·입력 계보·프로젝트/폴더를
원장에서 복원하는 기능이 아니며 기존 저장 API의 기본 메타데이터를 사용한다.

## 구버전·재시작

구키 `comfy_inflight_runs`는 원문을 동결하고 새 실행을 쓰지 않는다.

- AUTH on: owner 증거 없는 legacy는 이관·목록·조작·cap 점유0이다. 첫 사용자에게 귀속시키지 않는다.
- AUTH off: 해당 DB owner의 근거 불충분 orphaned로 한 번 이관한다. 목록 prompt ID는 숨기고
  명시 정리만 허용한다. 원격 조회/취소/회수0, cap에는 포함한다.
- 이관과 marker는 같은 한 번의 봉투 쓰기로 기록한다.
- 실제 DB 경로+AUTH mode마다 프로세스 내 최초 접근에서 로컬 복원한다. 요청 owner별로
  반복 복원해 살아 있는 다른 사용자의 실행을 orphaned로 만들지 않는다.
- lazy 접근은 원격 호출0. 명시 boot만 외부 복구 허용·소유/기기/연결 일치·미완료 근거가 있을 때
  조건부 취소를 원장 lock 밖에서 수행한다. AUTH on boot에는 요청 owner가 없어 취소하지 않는다.

구버전은 새 원장을 이해하지 못하며 구키에 대한 과거 취소 규칙을 가진다. SQL 변경이 없다는
이유로 단순 구버전 복귀가 복구 안전성을 보장한다고 해석하지 않는다.

## UI 응답 순서

목록의 성공·실패 모두 계정 수명(epoch)과 최신 요청 번호가 일치할 때만 표시한다.
실제 액션 시작은 이전 GET을 무효화하지만 무시된 중복 클릭은 요청 번호를 바꾸지 않는다.
busy 회수는 계정 수명으로 보호해 더 최신 조회가 시작돼도 버튼이 영구 잠기지 않게 한다.
기존 공통 HTTP 인증/오류 처리를 재사용하고, 미회수 오류는 job ID와 별도 안내를 보존한다.

## 검증과 남은 한계

CAS 후속 포함 관련 backend352개/프런트39개 통과와 실제 Claude 독립 코드 승인을 확인했다.
앞선 root 프런트 전체1,837개·빌드·구조 검사 통과는 후속4개 시험·EN 키 추가 전 기준이다.
독립 코드 리뷰·전체 backend·최종 실측 완료 여부는 점검 장부의 최신 기록을 따른다.

- 200실행×100출력=20,000 manifest 전량 보존, 약3.56MB. 실제 합성 SQLite3회에서 읽기58–98ms,
  전체 봉투 read/check/write201–274ms. 단일 PC 관측이며 큰 원장의 지연 비용은 남는다.
- 복사 반복/attempt/출력 경계의 시간 예산만 검사한다. header·chunked trailer·blocking 호출 내부의
  엄격한 전체 시간 상한은 없다.
- 디스크 사후 기록 실패와 크래시가 겹치면 최신 완료 근거를 잃을 수 있다.
- 오래된 snapshot의 collect/dismiss 반례는 CAS 보강 뒤409·새 claim 보존으로 바뀌었다.
  상태 변화 직후의 보수적인409도 가능하며 UI는 최신 목록을 재조회해 새 요청을 허용한다.
- 회수 thread 시작과 phase 복원 기록 쓰기가 함께 실패하면 메모리 failed owner가 남아
  즉시 재회수를 거부할 수 있다. 기존 메모리 만료/재기동 복구 정책의 한계이며 새 대기 정책은 추가하지 않는다.
- 카드 수명과 실행 취소가 겹치면 배너는 best-effort다. 특히 plan/batch 경로는 이전 실행의
  늦은 결과를 버릴 수 있으므로 미회수 설정 목록을 확인 기준으로 사용한다.
- 같은 경로의 DB 파일을 프로세스 실행 중 교체한 것은 bootstrap 집합이 감지하지 못한다.
- TTL 후 회수권을 넘겨받아도 옛 worker가 같은 결정적 파일을 교체할 수 있다. 원장은 CAS 보호되지만
  파일 교체 경쟁 자체가 없다는 보장은 아니다. 기존 파일 재사용은 양수 크기만 확인한다.
- 공통 lock은 단일 backend 프로세스의 계약이다. 여러 독립 프로세스의 같은 DB 경쟁 보장 아님.
- 기존 미디어 GET은 소유자별 비공개 정책이 아니다. 이 변경은 미디어 전체 접근제어를 대체하지 않는다.
- email/기기 식별 파일이 바뀌면 옛 신규 경로 재저장이 막힐 수 있다. 파일/기록을 지우지 않는다.
- 실제 유료 Cloud·운영 DB·NAS·설치본 업데이트·물리 다른 PC 복원은 이번 격리 검사로 대체하지 않는다.
