# RL-02 작업 워크스페이스 스냅샷 설계

작성 기준: 2026-08-19 `dev` (`af41fe57`)

## 결론

프로젝트가 다른 워크스페이스로 이동해도 과거 작업의 상태·메모·담당·수치가 섞이지 않도록
**작업(`project_task`)에 생성 당시 워크스페이스 스냅샷을 저장하는 A안**을 채택한다.

생성물의 워크스페이스만 보고 조회 때마다 작업 범위를 동적으로 넓히는 B안은 사용하지 않는다.
현재 작업의 고유 기준이 `(project_id, folder_path)` 하나라서, 프로젝트 이동 뒤 같은 폴더를 다시
사용하면 이전 공간과 새 공간이 같은 작업 행을 공유하게 된다. 그러면 PM이 편집한 상태·일정·메모·
담당자까지 공간 사이에서 섞일 수 있다.

## 지켜야 할 데이터 원칙

1. `generation.workspace_*`는 **생성·과금 당시 스냅샷**이며 프로젝트 이동으로 바꾸지 않는다.
2. `project.workspace_*`는 **현재 위치**다.
3. `project_task.workspace_*`는 **작업이 속한 위치의 스냅샷**이다.
4. 프로젝트 이동은 기존 작업을 옮기지 않는다. 새 공간에서 새 생성물이 생기면 새 작업을 만든다.
5. 같은 프로젝트·같은 폴더라도 워크스페이스가 다르면 서로 다른 작업이다.
6. 과거 공간에서는 읽기 전용 기록을 볼 수 있지만 현재 공간의 작업으로 수정해서는 안 된다.
7. 기존 데이터의 귀속을 확정할 근거가 없으면 추측하지 않고 `unknown`으로 남기며 관리자에게 표시한다.

## 스키마 변경

`project_task`에 다음 필드를 추가한다.

- `workspace_scope TEXT NOT NULL DEFAULT 'unknown'`
- `workspace_id TEXT`
- `workspace_name TEXT`
- `workspace_origin TEXT NOT NULL DEFAULT 'snapshot'`
  - `snapshot`: 신규 작업 생성 시 확정
  - `generation`: 기존 작업을 연결 생성물로 확정
  - `unknown`: 확정 불가

기존 고유 인덱스 `(project_id, folder_path)`는 제거하고 작업 스냅샷까지 포함한다.

- 팀 작업: `(project_id, workspace_id, folder_path)`
- 개인·미상 작업은 별도의 부분 인덱스로 중복을 막는다.

단순히 nullable `workspace_id` 하나만 고유 인덱스에 넣으면 SQLite에서 `NULL`끼리 중복을 허용하므로
개인·미상 작업의 인덱스를 분리해야 한다.

## 기존 데이터 마이그레이션

삭제나 임의 병합 없이 다음 순서로 진행한다.

1. 변경 전 DB 세트(content·trash·manage)를 백업하고 무결성을 확인한다.
2. 자동 폴더 작업은 같은 `(project_id, folder_path)`의 생성물을 워크스페이스별로 집계한다.
3. 한 워크스페이스만 확인되면 기존 작업에 그 스냅샷을 기록한다.
4. 여러 워크스페이스가 확인되면 기존 작업은 `unknown`으로 그대로 보존해 PM 메모·일정·담당자를
   잃지 않는다. 각 공간에는 폴더·시퀀스와 생성물 파생값만 가진 별도 과거 작업 행을 만든다.
   관리자가 원본의 귀속을 명시적으로 확정하기 전에는 어느 공간으로도 자동 이동하지 않는다.
5. 복제되는 공간별 행에는 PM 메모·일정·담당자를 임의로 복제하지 않는다.
6. 수동 작업은 명시적으로 연결된 생성물들이 한 공간이면 그 공간으로 확정한다.
7. 연결 생성물이 없거나 여러 공간에 걸친 수동 작업은 현재 프로젝트 위치로 추측하지 않고
   `unknown`으로 남겨 `귀속 확인 필요`로 표시한다.
8. 마이그레이션은 재실행해도 행이 늘어나지 않는 멱등 방식으로 작성한다.

서버 운영 DB에 적용하기 전에는 읽기 전용 사전 검사로 다음 개수를 보고해야 한다.

- 여러 워크스페이스에 걸친 프로젝트 수
- 같은 폴더가 여러 워크스페이스에 존재하는 수
- 연결 생성물이 여러 워크스페이스에 걸친 수동 작업 수
- 근거 생성물이 없는 수동 작업 수

## 조회·권한 변경

현재 `WorkBoard`는 현재 워크스페이스의 프로젝트 목록만 먼저 가져오므로 이동한 프로젝트의 과거
작업을 요청할 수 없다. 일반 프로젝트 목록의 의미를 넓히지 않고 관리 전용 조회를 추가한다.

- 활성 화면: 현재 프로젝트 위치와 같은 작업 스냅샷만 반환
- 과거 기록: 선택 워크스페이스의 작업 스냅샷과 이동한 프로젝트 이름을 함께 반환
- 컷 집계: 현재 `project.workspace_*`가 아니라 `project_task.workspace_*`와 일치하는 생성물만 사용
- 과거 작업 PATCH·재정렬·삭제: 기본 거부. 명시적인 관리자 복구 동작만 별도 제공

권한은 현재 프로젝트 위치만 비교하면 안 된다. 과거 기록 조회는 다음 두 조건을 모두 만족해야 한다.

1. 사용자가 선택한 과거 워크스페이스의 현재 유효 멤버이거나 전역 `read_all` 권한이 있다.
2. 프로젝트 읽기 역할이 있거나 전역 `read_all` 권한이 있다.

프로젝트 이동 때 새 공간 멤버를 추가하더라도 이전 공간의 역할을 자동 삭제하지 않는 현재 동작은
별도 권한 감사 대상으로 남긴다. 과거 공간 멤버십 검사 없이 누적된 `project_member`만 신뢰하면
다른 워크스페이스 기록이 노출될 수 있다.

## 필수 회귀 시나리오

- A 공간에서 `ep001/c0010` 생성 후 프로젝트를 B로 이동하고 같은 폴더에서 다시 생성
- A 과거 화면은 A 생성물·A 작업만, B 활성 화면은 B 생성물·B 작업만 표시
- A 작업 메모·상태·담당 변경이 B 작업에 영향을 주지 않음
- B에서 A로 다시 이동해도 기존 A 작업이 중복 생성되지 않고 이어짐
- 미상·개인·팀 작업의 고유 인덱스가 각각 중복을 차단
- 정상 상태의 작업 GET은 SQLite 쓰기를 발생시키지 않음
- 이전 공간 멤버가 아닌 사용자는 과거 프로젝트 존재도 조회할 수 없음
- 마이그레이션 2회 실행 뒤 작업 수와 연결 수가 동일
